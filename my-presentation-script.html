02
Objects before control flow

Six objects, then the fix request

Done
VPIDBCBFramePAGE_PTRglobal fcntthread holder4 call arguments
English script
Say: “Before tracing code, I want six nouns to stay separate. A VPID is the logical (volid, pageid) identity. A BCB is reusable control state. Its permanently paired frame stores the bytes. A PAGE_PTR is only a borrowed view into those bytes. Global fcnt says how many successful fixes protect the BCB across threads. A thread holder says which thread owes how many matching unfixes.”

Then introduce the normal fix call as four concrete arguments plus the current thread:

  1. VPID: which logical page?
  2. PAGE_FETCH_MODE: what allocation/residency knowledge does the caller assert?
  3. PGBUF_LATCH_MODE: shared READ or exclusive WRITE access?
  4. PGBUF_LATCH_CONDITION: if incompatible, return now or allow waiting?
Keep brief: there are seven fetch modes, but this talk needs mainly OLD_PAGE, NEW_PAGE, and OLD_PAGE_IF_IN_BUFFER.
한국어 대본
말하기: “Code 흐름을 보기 전에 여섯 개의 명사를 분리하겠습니다. VPID는 (volid, pageid)로 이루어진 logical identity입니다. BCB는 재사용되는 control state이고, BCB와 영구적으로 짝을 이룬 frame이 실제 bytes를 담습니다. PAGE_PTR는 그 bytes를 잠시 빌려 보는 pointer일 뿐입니다. Global fcnt는 여러 thread를 합쳐 이 BCB를 보호하는 successful fix 수이고, thread holder는 어느 thread가 unfix를 몇 번 갚아야 하는지 기록합니다.”

그다음 normal fix call을 현재 thread와 네 개의 실질적인 입력으로 설명합니다.

  1. VPID: 어느 logical page인가?
  2. PAGE_FETCH_MODE: caller가 allocation/residency에 대해 무엇을 알고 있는가?
  3. PGBUF_LATCH_MODE: shared READ인가, exclusive WRITE인가?
  4. PGBUF_LATCH_CONDITION: 충돌하면 즉시 돌아갈 것인가, 기다려도 되는가?
짧게: fetch mode는 일곱 개지만, 이번 발표에서는 OLD_PAGE, NEW_PAGE, OLD_PAGE_IF_IN_BUFFER를 중심으로 봅니다.

03
Fix convergence

Hit, cold miss, load owner, and identity

Done
candidateprotected recheckA = load ownerB = waiterINVALID → VOIDpublishretry
English script
Say: “A hash hit gives us a candidate, not yet a trustworthy identity. The bucket mutex stabilizes the resident chain while we inspect it. We then acquire the BCB mutex and compare the requested VPID again, because the reusable BCB may have been detached and rebound between observations.”
Correct the wording: there is no separate ‘hash-entry VPID’ copy. The hash chain contains BCBs. The first and second checks read the BCB’s VPID under different protection.

Two-thread cold miss

  1. A and B both miss the same VPID.
  2. A registers the VPID load-lock first and becomes load owner.
  3. B links itself as a waiter and sleeps; B owns no page yet.
  4. A first tries the INVALID-list head. The claimed BCB changes INVALID → VOID; no BCB object is newly allocated.
  5. A assigns the VPID, reads OLD_PAGE bytes from DWB/data volume or initializes NEW_PAGE, validates identity, grants itself ownership, publishes the BCB, and releases the load lock.
  6. B wakes and retries normal lookup. It earns its own latch and fix debt.
Identity pair: requested VPID == protected BCB.vpid; then BCB.vpid == the page-header (volid,pageid) for permanent pages.
한국어 대본
말하기: “Hash hit는 아직 신뢰할 수 있는 identity가 아니라 candidate만 줍니다. Bucket mutex로 resident chain을 안정화한 상태에서 후보를 찾고, 이어서 BCB mutex를 잡은 뒤 requested VPID와 다시 비교합니다. 두 관찰 사이에 재사용 가능한 BCB가 detach되고 다른 VPID로 rebind될 수 있기 때문입니다.”
표현 교정: 별도의 ‘hash-entry VPID’ 사본은 없습니다. Hash chain의 node가 BCB입니다. 첫 번째와 두 번째 확인은 서로 다른 protection 아래에서 같은 BCB VPID를 읽습니다.

두 thread의 cold miss

  1. A와 B가 같은 VPID를 동시에 miss합니다.
  2. A가 VPID load-lock을 먼저 등록해 load owner가 됩니다.
  3. B는 waiter로 연결되어 잠듭니다. 아직 page ownership은 없습니다.
  4. A는 먼저 INVALID-list head를 요청합니다. 가져온 BCB는 INVALID → VOID가 되며, 새 BCB object를 heap allocation하는 것이 아닙니다.
  5. A가 VPID를 지정하고, OLD_PAGE면 DWB/data volume에서 읽고 NEW_PAGE면 frame을 초기화합니다. Identity를 확인하고 자신의 ownership을 grant한 뒤 BCB를 publish하고 load lock을 풉니다.
  6. B는 깨어나 normal lookup을 다시 수행하고, 자기 latch와 fix debt를 따로 얻습니다.
Identity pair: requested VPID == protection 아래의 BCB.vpid, 이어서 permanent page라면 BCB.vpid == page header의 (volid,pageid)입니다.
Visual cue: walk A across the upper owner lane, stop B in the lower wait lane, then finish at “retry,” not “receive A’s provisional BCB.” / 위쪽 owner lane에서 A를 따라가고, 아래쪽 B를 wait에 멈춘 뒤 마지막은 “provisional BCB 전달”이 아니라 “retry”로 끝냅니다.
Verified mechanism: Lesson 03; protected lookup page_buffer.c:7594–7722; load owner/waiter 7981–8178; invalid-first allocation and materialization 8181–8634; page-header identity 11243–11279.
04
Ownership accounting

One successful fix, one debt

Done
global fcntholder fix_countnested debtequal PAGE_PTRsix-step simulationone success ↔ one unfix
English script
Say: “Every successful fix creates exactly one matching unfix debt. Global fcnt protects residency across all threads. A per-thread holder records this thread’s nested fix_count. Equal PAGE_PTR values do not merge debts.”
Run the Lesson 04 simulation: A fix, A fix, B fix, A unfix, B unfix, A unfix. Global counts: 1,2,3,2,1,0.

After A's first unfix, A still owns one nested debt. After B's unfix, B no longer owns the page. After A's final unfix, global fcnt reaches zero for this closed example and the latch can become idle.

Do not collapse the ledgers: global fcnt answers whether any ownership blocks reuse; one thread's holder answers whether that caller may still use the pointer and owes another release.
한국어 대본
말하기: “Successful fix 한 번은 matching unfix debt 한 개를 만듭니다. Global fcnt는 모든 thread의 ownership을 합쳐 residency를 보호합니다. Per-thread holder의 fix_count는 이 thread가 갚아야 할 nested debt를 기록합니다. 같은 PAGE_PTR가 여러 번 돌아와도 debt는 합쳐지지 않습니다.”
Lesson 04 simulation: A fix, A fix, B fix, A unfix, B unfix, A unfix 순서로 누릅니다. Global count는 1,2,3,2,1,0입니다.

A의 첫 unfix 뒤에는 A의 nested debt가 하나 남습니다. B가 unfix하면 B의 ownership은 끝납니다. 마지막 A unfix 뒤에는 이 closed example의 global fcnt가 zero가 되고 latch가 idle state로 갈 수 있습니다.

두 ledger를 합치지 않습니다: global fcnt는 reuse를 막는 ownership이 하나라도 있는지 답하고, 한 thread의 holder는 그 caller가 pointer를 계속 써도 되는지와 release를 더 해야 하는지 답합니다.
Visual cue: show “3 = A:2 + B:1,” then follow the six events. Point at who may still use a pointer after each unfix. / “3 = A:2 + B:1”을 보여주고 여섯 event를 따라갑니다. 각 unfix 뒤에 누가 pointer를 계속 쓸 수 있는지 짚습니다.
Evidence: Lesson 04; holder and global tuple page_buffer.c:460–488; grant accounting 6277–6634; release accounting 3062–3201, 6128–6275, 6636–6883.
4A
Per-thread ownership index

Holder lifecycle, cost, and redesign boundary

Done
linear H7 initial+10 growthbinding zeroglobal zerofree-list recycleredesign boundary
English script
Say: “The current thread finds an existing holder by scanning its active list for the BCB address. With H distinct held BCBs, one lookup is worst-case O(H). This is a source-visible risk, not a measured bottleneck.”
  • Each thread begins with seven reserved entries; exhaustion adds ten-entry backing sets. Neither number is a maximum or evidence of the developer's expected maximum.
  • Nested same-BCB fixes reuse one entry and increment fix_count.
  • Thread-local zero returns the active binding to that thread's free list.
  • Global fcnt zero is different: it can release the latch, perform LRU placement/movement, grant waiters, or service deferred flush work.
  • Backing storage remains until page-buffer finalization: retained high-water capacity, not a demonstrated allocator leak.
Redesign boundary: do not add artificial fixes, queue the current unfix asynchronously, or substitute pgbuf_simple_fix() for general fix. A different index is possible, but it must preserve per-owner nested counts, promotion, ordered watchers, pointer lifetime, and cleanup.
한국어 대본
말하기: “현재 thread는 active list에서 BCB address를 비교해 existing holder를 찾습니다. 서로 다른 held BCB가 H개라면 lookup 하나가 worst-case O(H)입니다. Source-visible risk이지 측정된 bottleneck은 아닙니다.”
  • Thread마다 일곱 entry를 먼저 reserve하고 부족하면 열 개 단위 backing set을 추가합니다. 어느 숫자도 maximum이 아니며, developer가 예상한 maximum이라는 evidence도 없습니다.
  • 같은 BCB의 nested fix는 entry 하나를 재사용하고 fix_count만 올립니다.
  • Thread-local zero에서는 active binding을 해당 thread의 free list로 돌려보냅니다.
  • Global fcnt zero는 다른 event입니다. Latch release, LRU placement/movement, waiter grant, deferred flush 처리가 일어날 수 있습니다.
  • Backing storage는 page-buffer finalization까지 유지됩니다. Retained high-water capacity이지 검증된 allocator leak은 아닙니다.
Redesign boundary: 불필요한 extra fix를 만들거나, 현재 unfix 전체를 async queue에 넣거나, general fix를 pgbuf_simple_fix()로 대체하지 않습니다. Index representation은 바꿀 수 있지만 per-owner nested count, promotion, ordered watcher, pointer lifetime, cleanup을 보존해야 합니다.
Visual cue: show active → free for the binding, then say that backing storage remains pool-owned. / Binding은 active → free로 이동하지만 backing storage는 pool-owned 상태로 남는다고 말합니다.
Verified mechanism and derived cost: Lesson 4A; layout/allocation page_buffer.c:438–500, 5922–6086; lookup/removal 6090–6275; global-zero path 6636–6883; general consumers 6312–6537, 12268–13531; simple-fix restriction 2688–2811.
05
Caller completes correctness

Lock, latch, and fix debt are different

Done
logical lockpage latchvalidatemutatelog / page LSADIRTYrelease every exit
English script
Say: “The team already knows transaction locks, so I will keep the contrast short. A transaction lock protects logical class or row ownership. A page latch protects the current in-memory bytes. A successful fix supplies temporary access, not complete caller correctness.”

For a logged WRITE mutation, the caller still owes this sequence:

  1. hold the required logical lock;
  2. fix with WRITE and validate the page/record conditions;
  3. mutate the bytes while latched;
  4. append the correct recovery log and advance page LSA when required;
  5. call pgbuf_set_dirty() to publish propagation debt;
  6. transfer or unfix every ownership debt on every exit.
Keep the verbs separate: logging is recovery evidence; page LSA describes the logged page image; DIRTY requests page propagation; unfix ends ownership. None is a synonym for commit, flush, or eviction.
한국어 대본
말하기: “Transaction lock은 팀 lock manager 세미나에서 이미 다뤘으니 차이만 짧게 보겠습니다. Transaction lock은 logical class나 row ownership을 보호하고, page latch는 현재 memory bytes 접근을 보호합니다. Successful fix는 temporary access를 제공할 뿐 caller correctness를 완성하지 않습니다.”

Logged WRITE mutation을 위해 caller가 추가로 지켜야 할 순서입니다.

  1. 필요한 logical lock을 보유합니다.
  2. WRITE fix 후 page/record 조건을 validate합니다.
  3. Latch를 보유한 동안 bytes를 변경합니다.
  4. 맞는 recovery log를 append하고 필요하면 page LSA를 전진시킵니다.
  5. pgbuf_set_dirty()로 propagation debt를 publish합니다.
  6. 모든 exit에서 ownership debt를 transfer하거나 unfix합니다.
동사를 분리합니다: logging은 recovery evidence, page LSA는 logged page image의 경계, DIRTY는 page propagation 요청, unfix는 ownership 종료입니다. 어느 것도 commit, flush, eviction과 같은 말이 아닙니다.
Visual cue: trace the center spine only: WRITE latch → validate → mutate → log/page LSA → DIRTY → transfer or unfix. / 가운데 spine만 따라갑니다: WRITE latch → validate → mutate → log/page LSA → DIRTY → transfer 또는 unfix.
Interface and caller evidence: Lesson 05; representative heap path heap_file.c:23120–23324; NEW_PAGE allocation boundary file_manager.c:5420–5590.
06
One flush generation

Actors, two LSA questions, and DWB

Done
4 peer daemonspage-flushpost-flushcheckpointpage LSAoldest_unflush_lsaG / G+1DWB
English script
Say: “Server mode attempts to create four independent page-buffer daemon roles. Only pgbuf-page-flush selects and submits dirty victim candidates. pgbuf-page-post-flush completes BCB state and victim handoff after submission. Maintenance adjusts quota policy, and flush-control handles soft pacing.”

The daemon is only one flush path. Checkpoint, explicit foreground callers, a WRITE owner servicing an async request, and stand-alone victim pressure can also execute the common generation protocol.

Two boundaries, two questions

Copied page LSAHow new are the copied bytes? Force WAL through this LSA before submitting the page image.
oldest_unflush_lsaHow far back does unpaid dirty history begin? Use it to select checkpoint work and bound redo progress.
Example: “Boundary 150, oldest 100, page LSA 170: select the page, force WAL through 170, and write the current copy. If oldest is 200 and page LSA 220, checkpoint may skip it; another flusher may still write it safely after forcing WAL through 220.”
Two risks: false checkpoint progress can start redo after unpaid history; page-before-WAL ordering can persist bytes whose explaining log is absent.
한국어 대본
말하기: “Server mode는 서로 독립적인 네 개의 page-buffer daemon role을 만들려고 합니다. 그중 pgbuf-page-flush만 dirty victim candidate를 고르고 submit합니다. pgbuf-page-post-flush는 submit 이후 BCB state와 victim handoff를 마무리합니다. Maintenance는 quota policy를 조정하고, flush-control은 soft pacing을 담당합니다.”

Daemon은 여러 flush path 중 하나입니다. Checkpoint, explicit foreground caller, async request를 처리하는 WRITE owner, stand-alone victim pressure도 같은 generation protocol을 실행할 수 있습니다.

두 boundary는 서로 다른 질문에 답합니다

Copied page LSA복사한 bytes가 얼마나 최신인가? Page image를 submit하기 전에 WAL을 이 LSA까지 force합니다.
oldest_unflush_lsa갚지 않은 dirty history가 어디서 시작했는가? Checkpoint 대상 선택과 redo progress의 lower bound에 씁니다.
예시: “Boundary 150, oldest 100, page LSA 170이면 이 page를 선택하고 WAL을 170까지 force한 뒤 현재 image를 씁니다. Oldest 200, page LSA 220이면 checkpoint는 skip할 수 있지만, 다른 flusher가 WAL을 220까지 force한 뒤 미리 쓰는 것은 안전합니다.”
두 위험: 잘못된 checkpoint progress는 unpaid history보다 늦게 redo를 시작하게 하고, page-before-WAL 위반은 그 bytes를 설명할 log 없이 page만 남길 수 있습니다.

07
Replacement safety

Invalid first; then a bounded safe-victim search

Done
INVALID O(1)selected LRUD demotionsK ≤ 1000 nodes4 safety questionstry-lockprotected recheck
English script
Say: “A miss tries the INVALID-list head first. That is an O(1) pop, not a scan of every BCB. Only when INVALID is empty does policy select an LRU and search its LRU3 zone.”

For one selected-list call, the helper cost is O(M + K):

  • M is optional pre-scan zone demotion work;
  • K is the number of BCB nodes visited in that selected LRU3, capped at 1,000.
Evidence boundary: the 1,000-node cap is verified policy. The pinned source does not document why 1,000 was chosen, so do not invent a rationale. It is unrelated to the count of private LRU descriptors.

Four checks

  1. no user: fcnt == 0;
  2. no unpaid or in-flight write: not DIRTY and not FLUSHING;
  3. no waiter or handoff/avoid-victim flag;
  4. BCB try-lock succeeds, then all facts pass the protected recheck.
Say: “The LRU mutex stabilizes the list. The BCB try-lock never waits while that list mutex is held. The first observations are hints; the recheck under BCB protection authorizes detach.”
한국어 대본
말하기: “Miss가 나면 먼저 INVALID-list head를 시도합니다. 모든 BCB를 scan하는 것이 아니라 O(1) pop입니다. INVALID가 비었을 때만 policy가 LRU 하나를 선택하고 그 LRU의 LRU3 zone을 탐색합니다.”

선택된 list 한 번의 helper cost는 O(M + K)입니다.

  • M은 scan 전에 일어날 수 있는 zone demotion 작업량입니다.
  • K는 선택된 LRU3에서 방문한 BCB node 수이며 최대 1,000입니다.
Evidence boundary: 1,000-node cap 자체는 verified policy입니다. 하지만 pinned source에는 왜 1,000인지 rationale이 없으므로 이유를 만들어 말하지 않습니다. Private LRU descriptor 수와도 무관합니다.

네 가지 확인

  1. 사용자 없음: fcnt == 0
  2. 갚지 않았거나 진행 중인 write 없음: DIRTY/FLUSHING이 아님
  3. waiter 또는 handoff/avoid-victim flag 없음
  4. BCB try-lock 성공 후 모든 조건을 protection 아래 다시 확인
말하기: “LRU mutex는 list를 안정화합니다. 그 mutex를 보유한 동안 BCB try-lock은 기다리지 않고 실패하면 skip합니다. 처음 관찰은 hint이고, BCB protection 아래의 recheck가 detach를 허가합니다.”
Visual cue: stop at each gate. Emphasize that fcnt == 0 is necessary but insufficient. / 각 gate에서 잠시 멈춥니다. fcnt == 0은 필요조건이지만 충분조건이 아니라고 강조합니다.
Verified mechanism and policy: Lesson 07; invalid pop page_buffer.c:8905–8983; victim predicate 9265–9325; bounded scan, try-lock, recheck, detach 9327–9538. See the focused evidence note.
09
Latch queue

Five outcomes before any fairness claim

Done
immediateconditional rejectwaittimeout / interruptwakeup + grantNO_LATCH by owner4,950 inspections
English script
Say: “After a resident BCB is found, a fix has five caller-visible outcomes: immediate grant, conditional rejection, queued wait, timeout or interrupt, and wakeup plus grant. Only the two grants create fix debt.”

PGBUF_UNCONDITIONAL_LATCH means waiting is allowed if the request conflicts. It does not force every request to sleep. A waiting THREAD_ENTRY is a request, not a holder.

NO_LATCH: on a BCB it means resident but no READ/WRITE content latch is granted; on a wait request it can be a cancellation tombstone; on a watcher it can be initialization metadata. Always name the owning field.

Queue cost

The BCB stores a singly linked head and no tail. Appending with W queued nodes is O(W). Building 100 waiters before any dequeue performs about 1+…+99 = 4,950 node inspections (or 4,851 actual next-link advances).

Do not overclaim: source proves structural cost, not a measured bottleneck. Why there is no tail pointer is not documented. A timeout/interrupt cancels or removes the ungranted request; arbitrary removal is worst-case O(W) and uses BCB protection.

At global zero-crossing, a WRITE grant stops the scan. If READ is selected, one forward scan may grant later compatible readers across queued writers. Therefore the source does not promise strict FIFO or starvation freedom.

한국어 대본
말하기: “Resident BCB를 찾은 뒤 fix에는 caller 관점의 다섯 outcome이 있습니다. Immediate grant, conditional rejection, queued wait, timeout 또는 interrupt, wakeup 후 grant입니다. 이 중 실제 fix debt를 만드는 것은 두 grant뿐입니다.”

PGBUF_UNCONDITIONAL_LATCH는 충돌할 때 기다려도 된다는 뜻입니다. 모든 request가 반드시 sleep한다는 뜻은 아닙니다. 기다리는 THREAD_ENTRY는 request이지 holder가 아닙니다.

NO_LATCH: BCB field에서는 resident지만 READ/WRITE content latch가 없다는 뜻이고, wait request에서는 cancellation tombstone, watcher에서는 initialization metadata일 수 있습니다. 항상 owning field를 함께 말합니다.

Queue cost

BCB에는 singly linked head만 있고 tail은 없습니다. 이미 W개가 있으면 append는 O(W)입니다. Dequeue 없이 100개를 쌓으면 약 1+…+99 = 4,950번 node inspection이 발생합니다. 실제 next-link advance로 세면 4,851번입니다.

과장하지 않기: source가 증명하는 것은 구조적 cost이지 측정된 bottleneck이 아닙니다. Tail pointer가 없는 design rationale도 문서화되어 있지 않습니다. Timeout/interrupt는 아직 grant되지 않은 request를 cancel하거나 제거하며, arbitrary removal은 worst-case O(W)이고 BCB protection을 사용합니다.

Global zero-crossing에서 WRITE를 grant하면 scan을 멈춥니다. READ가 선택되면 한 번의 forward scan으로 queued writer를 건너 뒤의 compatible reader들도 grant할 수 있습니다. 따라서 strict FIFO나 starvation freedom은 보장된다고 말할 수 없습니다.

Ordered multi-page ownership

Release later pages before waiting for an earlier page

Done
A < BT1 holds BT2 holds Aconditional firstselective releasesorted refixpage_was_unfixed
English script
Say: “Ordered fix exists because individually valid page latches can form a cycle. If A sorts before B, T1 holding B must not sleep for A while T2 holds A and waits for B.”
  1. Try the requested page conditionally while current watched pages stay fixed.
  2. If it succeeds, attach the watcher and finish—no release occurred.
  3. If it would block, keep pages that sort before the request.
  4. Fully unfix pages that sort after the request.
  5. Fix the request unconditionally, then refix released pages in canonical order.

The representative heap order is group → rank → VPID. The access method supplies the meaning; page buffer executes the ordered transition.

After refix: a watcher with page_was_unfixed=true regained ownership, not old knowledge. Rebuild record pointers, slot choices, free-space decisions, and cross-page conclusions derived behind that protection gap.
한국어 대본
말하기: “Ordered fix가 필요한 이유는 각각 정당한 page latch가 cycle을 만들 수 있기 때문입니다. A가 B보다 먼저라면, B를 가진 T1이 A를 기다리고 A를 가진 T2가 B를 기다리는 상태를 허용하면 안 됩니다.”
  1. 현재 watched page를 유지한 채 requested page를 conditional로 먼저 시도합니다.
  2. 성공하면 watcher를 붙이고 끝냅니다. Release는 일어나지 않았습니다.
  3. 기다려야 한다면 request보다 먼저 정렬되는 page는 계속 hold합니다.
  4. Request보다 뒤에 정렬되는 page는 완전히 unfix합니다.

Replacement from first principles

One BCB through five list-membership states

Done
worked defaultINVALIDVOIDLRU1LRU2LRU3private domaindirect-victim handoff
English script
Say: “Under the worked baseline—512 MiB data buffer, 16 KiB page, max_clients=100, HA off—we get 32,768 BCB/frame pairs. Internal MAX_NTRANS=102 gives 32 shared LRUs and 152 private LRUs, so 184 descriptors. These are derived example values, not universal constants.”
32,768 pairs · S = 32 · P = 102 + 50 = 152 · L = 184

Five membership states

  • INVALID: on the global free list, no resident VPID.
  • VOID: on neither INVALID nor any LRU; it may be loading, fixed, moving, or detached.
  • LRU1: hot protected zone.
  • LRU2: second-chance protected zone.
  • LRU3: cold zone searched for ordinary victims.
Travel story: “Startup INVALID → miss claims VOID → first final unfix enters private LRU1 if this context has a private domain, otherwise shared LRU2 → later insertions and threshold pressure demote boundary nodes LRU1→LRU2→LRU3 → a fix of an LRU3 page normally boosts it to LRU1 on final unfix → a clean idle LRU3 candidate may detach to VOID, lose the old hash identity, and receive a new VPID.”

Private means replacement-policy domain, not access control. Several contexts may share one private LRU, and another transaction can fix its BCB. Domain mismatch at final unfix can move a BCB private → VOID → shared LRU2.

Victim-source order and queues: policy tries the caller's eligible own private list, one advertised other-private list, one advertised shared list, then an own-list fallback. It consumes advertised LRU indexes rather than scanning every list. The index queues request capacities 2P for private, 2P for big-private, and 2S for shared, rounded to powers of two; these are index-queue capacities, not page partitions.
Direct-victim flag: a separate handoff flag says a producer reserved this BCB for a waiting allocator. It blocks ordinary victim scan and can be revoked if the BCB becomes fixed again. It is not a sixth list-membership state.
