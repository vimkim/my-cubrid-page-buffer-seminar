00 · Decode BCB identity

One stable slot can represent different pages over time

A BCB is a preallocated buffer-pool descriptor paired with one frame. Its memory address is stable, but its current identity is the resident page named by bcb->vpid. Safe victimization ends that mapping so the same BCB/frame slot can later represent another VPID.

TimeSame BCB addressCurrent identityState
T1BCB[42]VPID AResident in exactly one LRU list/zone.
T2BCB[42]No resident VPIDSafely detached/invalid for reuse.
T3BCB[42]VPID BRebound and later placed in one LRU list/zone.

Many threads may fix the same current BCB when latch compatibility permits—for example, multiple READ holders. That is shared ownership of one page identity, recorded by global fcnt plus per-thread holders. It is not multiple BCB identities.

One BCB is not in many LRUs at once. Private and shared LRUs are alternative list domains. LRU1/LRU2/LRU3 are zones within its one current LRU. A BCB may move between lists or become detached over time, but its single link fields cannot make it an ordinary member of several lists simultaneously.

What an identity mismatch would mean: code saved an unprotected candidate observation while the slot represented A, but later examined the same BCB address after it had been rebound to B. It must discard the stale A-based decision and retry. In the ordinary LRU path, holding the LRU mutex and then acquiring BCB protection prevents this during the final detach; the helper is not merely an explicit saved_vpid == bcb->vpid test.
01 · Two questions

Safe now? Then: preferable now?

Policy receives only candidates that have survived the hard gate and protected handoff.

LayerQuestionMay optimization change it?
EligibilityCan these frame bytes and this mapping be discarded and rebound without violating any right or propagation debt?No—not while preserving the interface contract.
PolicyAmong eligible frames, which one best serves locality, fairness, quota, and allocation progress?Yes, if every hard predicate and final recheck remains intact.

An optimization may reorder safe candidates. It may not manufacture safety.

02 · Hard eligibility

Five proofs stand between observation and reuse

  1. Identity is stable: the BCB still represents the VPID and list candidate that selection examined.
  2. No ownership remains: global fcnt, per-thread holders, granted rights, and transient claims cannot authorize any remaining fixer.
  3. No generation debt remains: DIRTY would discard unpropagated bytes; FLUSHING would rebind while a copied generation still refers to this identity.
  4. No conflicting waiter exists: latch waiters or in-progress protocol states can carry rights that a casual counter read omits.
  5. Final protected revalidation succeeds: lock the BCB and recheck identity, flags, ownership, zone, and handoff conditions immediately before unlink or reuse.

Verified mechanism: pinned ordinary LRU selection scans the victim zone, rejects avoid-victim flags and fixed frames, conditionally locks the BCB, calls pgbuf_is_bcb_victimizable(..., true), and only then removes it from the list. Read page_buffer.c:9293–9538.

03 · Break the shortcut

fcnt == 0 is one sample, not a reuse proof

Candidate also has…Why zero fixes is insufficient
DIRTYReuse would discard a resident generation that still needs propagation.
FLUSHINGAn in-flight copy still carries this frame identity; Lesson 6's generation is incomplete.
A latch waiterThe waiter may carry a pending acquisition right not represented by the sampled count.
Changed identity or zoneThe selection observation became stale before the handoff.
Presentation trap: “unfixed” is not a synonym for “victimizable.” It answers only the current fix-debt coordinate.
04 · Changeable machinery

Only eligible frames enter replacement policy

LRU zones and placement, private versus shared domains, quotas, candidate queues or hints, and direct assignment affect locality, fairness, CPU cost, and progress. They do not redefine whether reuse is safe.

A direct-victim assignment is revocable: if its candidate is fixed again before consumption, the allocator requests another candidate. Policy yields to newly acquired ownership; it does not force reuse.

Implementation policy: the specific zones, quotas, queue priorities, search order, and timeout strategy belong to this revision. The hard interface condition remains: no successful fixer or incomplete generation may survive a rebind.

05 · Keep lifecycle verbs separate

Release, propagate, rebind, invalidate, and deallocate are different operations

OperationWhat changesWhat usually remains
UnfixOne caller's fix debt is consumed.The resident VPID ↔ BCB/frame mapping.
FlushOne copied dirty generation is propagated.Residency and possibly a newer DIRTY generation.
VictimizationA safe resident frame is detached for reuse.The logical page still exists on storage.
InvalidationA resident mapping is removed or rejected for coherence/lifecycle reasons.Logical allocation unless separately changed.
Logical deallocationFile/disk ownership says the page no longer exists as allocated storage.No automatic proof that every cached reference is already gone.

Avoid-deallocation bookkeeping for vacuum is not itself an ordinary victim blocker; do not infer that similarly named lifecycle machinery participates in LRU eligibility.

06 · Evidence boundary

The existing runtime runs did not evict a frame

Source establishes the pinned selection mechanism. The recorded workload did not force eviction or identify a physical victim.

Therefore it cannot validate victim order, physical-frame reuse, direct-victim revocation, or pressure-path fairness. Those claims require a bounded pressure experiment with frame identity and state observations—not merely a successful workload in a pool that never filled.
