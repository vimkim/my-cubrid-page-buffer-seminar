Part 1 · Boundary와 object

무엇이 존재하고, correctness는 누가 책임지는가?

필수PGBUF-QB-001Lesson 1

1. page-buffer Module이 책임지는 것은 무엇이며, caller에게 남는 책임은 무엇인가?

model answer 보기

Model answer: Module은 page identity를 resident byte에 mapping하고, fix, latch, dirty/flush, replacement protocol로 그 byte를 일시적으로 보호합니다. 그러나 caller가 올바른 page를 골랐는지, 논리적으로 유효한 변경을 했는지는 알지 못합니다. allocation 지식, logical locking, page-layout validation, recovery 의미, retry, 완전한 cleanup은 caller와 인접 Module의 책임입니다.

이렇게 방어하세요: fix 성공은 access contract를 입증할 뿐, caller correctness까지 입증하지는 않습니다.

Canonical answer와 source anchor · Lesson 1

필수PGBUF-QB-003Lesson 1–2

2. VPID, BCB, frame, PAGE_PTR, holder는 어떻게 다른가?

model answer 보기

Model answer: VPID는 logical page identity입니다. BCB는 현재 resident인 identity 하나를 위한 volatile control state이고, byte를 저장하는 frame과 짝을 이룹니다. PAGE_PTR는 그 byte를 잠시 빌려 보는 view일 뿐 page identity도 ownership record도 아닙니다. global fcnt가 frame을 reuse로부터 보호하고, 각 thread의 holder는 자신이 상환할 release debt를 따로 기록합니다.

이렇게 방어하세요: identity가 바뀌어도 같은 pointer가 다시 나올 수 있고, identity가 그대로여도 frame address는 바뀔 수 있습니다.

Canonical answer와 source anchor · Lesson 2

CounterexamplePGBUF-QB-004Lesson 2

3. page가 동시에 resident, unfixed, dirty일 수 있는가?

model answer 보기

Model answer: 가능합니다. residency, fix ownership, latch state, dirty/flush state, victim eligibility는 서로 독립적인 axis입니다. caller가 변경된 page를 unfix해도, 그 page는 resident이면서 나중에 propagation해야 할 dirty 상태로 남을 수 있습니다. fcnt==0이라는 이유만으로 victim으로 삼아서는 안 됩니다. dirty, flushing, waiter, transient owner, identity 조건도 여전히 중요합니다.

이렇게 방어하세요: “resident”는 위치, “fixed”는 reuse protection, “dirty”는 propagation debt를 설명합니다.

Part 2 · Acquisition과 ownership

성공해 보이는 path에서도 왜 다시 확인하는가?

예상 challengePGBUF-QB-009Lesson 3

4. victim이나 hash candidate를 찾은 뒤 BCB identity를 왜 다시 확인하는가?

model answer 보기

Model answer: 첫 lookup은 candidate만 찾습니다. thread가 fix, release, remove, reuse에 필요한 protection을 얻기 전에 다른 thread가 resident mapping을 바꿀 수 있습니다. protection 아래의 identity check는 중요한 transition 시점에도 BCB가 예상한 VPID를 나타낸다는 사실을 입증합니다.

이렇게 방어하세요: 같은 BCB address가 아직 존재하는지를 보는 것이 아닙니다. 고정된 slot이 지금도 같은 identity를 가졌는지 확인하는 것입니다.

Canonical answer와 source anchor · Lesson 7

예상 challengePGBUF-QB-015Lesson 4

5. 여러 thread가 BCB 하나를 공유할 수 있는가? 그렇다면 여러 LRU에 들어가는가?

model answer 보기

Model answer: 호환되는 여러 reader는 같은 BCB를 동시에 fix할 수 있습니다. resident BCB 하나와 global fcnt 하나를 공유하지만, thread마다 별도의 holder entry와 nested release debt를 가집니다. 그렇다고 BCB가 여러 LRU list에 복제되는 것은 아닙니다. LRU membership은 BCB 하나에 대한 replacement-policy상의 위치이지, thread별 ownership이 아닙니다.

이렇게 방어하세요: thread별 holder ledger는 “누가 release해야 하는가?”에 답하고, LRU state는 “replacement가 어디를 탐색해야 하는가?”에 답합니다.

필수PGBUF-QB-013Lesson 5

6. page latch를 이미 잡았는데도 caller에게 transaction lock이 필요한 이유는?

model answer 보기

Model answer: page latch는 memory 안의 page image 하나에 대한 짧은 physical access를 직렬화합니다. transaction lock은 transaction conflict와 visibility rule 전반에서 logical database object를 보호합니다. byte를 보호한다고 logical permission이 생기지 않고, logical permission만으로는 byte를 수정하는 동안 보호할 수 없으므로 heap mutation에는 둘 다 필요할 수 있습니다.

이렇게 방어하세요: 두 mechanism은 대상 object, owner, lifetime이 다릅니다.

Part 3 · Mutation과 durability

어느 generation이 durable해졌는가?

필수PGBUF-QB-023Lesson 5

7. mutation, logging, page LSA, dirty, release의 올바른 순서는?

model answer 보기

Model answer: caller는 먼저 logical permission을 확보하고 destination을 validation합니다. 그다음 page owner를 통해 mutation하고, recovery record를 append하며, 필요한 경우 page LSA를 전진시킨 뒤 resident generation을 dirty로 표시합니다. 마지막으로 성공 path와 error path 모두에서 모든 watcher를 넘기거나 release합니다.

이렇게 방어하세요: WRITE latch만으로는 recovery 의미, dirty publication, 모든 exit의 cleanup 중 어느 것도 제공되지 않습니다.

Canonical answer와 source anchor · Caller mutation card

예상 challengePGBUF-QB-028Lesson 6

8. generation G와 G+1은 무엇이며, DIRTY와 FLUSHING이 동시에 설정될 수 있는 이유는?

model answer 보기

Model answer: “generation”은 flush 대상으로 고른 page byte와 LSA snapshot 하나를 추론하기 위한 label이지, 저장된 version number가 아닙니다. flusher는 G를 복사하고 그 작업을 FLUSHING으로 표시합니다. 이후 writer가 resident page를 바꾸면 그 새 byte가 G+1이 되고 DIRTY가 다시 설정됩니다. G가 성공적으로 끝나도 G+1은 dirty로 남을 수 있으므로 FLUSHING과 DIRTY가 겹쳐도 모순이 아닙니다.

이렇게 방어하세요: FLUSHING은 이전에 복사한 image의 작업이 진행 중이라는 뜻이고, DIRTY는 현재 resident image에 아직 propagation debt가 있다는 뜻입니다.

Canonical answer와 source anchor · Flush-generation card

필수PGBUF-QB-027Lesson 6

9. WAL-before-data는 어디서 보장되며, flush 성공은 home page의 durability를 뜻하는가?

model answer 보기

Model answer: 복사한 page image를 제출하기 전에 page-buffer flush는 해당 image의 page LSA까지 WAL을 force하도록 log management에 요청합니다. 이후 image는 설정된 DWB 또는 direct data-volume path를 따릅니다. 이 boundary에서의 성공은 DWB에 수용됐거나 direct write가 반환됐다는 뜻일 수 있지만, physical home page가 persistent해졌다고 자동으로 입증하지는 않습니다.

이렇게 방어하세요: WAL은 recovery ordering gate이고, DWB는 page-image propagation을 보호하며, physical durability는 더 아래의 boundary입니다.

Canonical answer와 source anchor · Lesson 6

Part 4 · Replacement와 progress

eligibility가 먼저, policy는 그다음

필수PGBUF-QB-029Lesson 7

10. 어떤 조건을 만족해야 BCB를 안전하게 victim으로 삼을 수 있는가?

model answer 보기

Model answer: LRU policy가 candidate를 지목할 수는 있지만, reuse 전에는 protection 아래의 최종 gate를 통과해야 합니다. BCB가 unfixed이고 clean이며 flushing 중이 아니어야 하고, 자격을 막는 waiter나 transient ownership이 없어야 하며, 조건부로 protect할 수 있고, 여전히 예상한 identity에 binding되어 있어야 합니다. fcnt==0이나 LRU 위치만으로는 충분하지 않습니다.

이렇게 방어하세요: policy는 탐색할 위치를 고르고, hard predicate는 파괴적인 reuse를 허가합니다.

Canonical answer와 source anchor · Replacement-safety card

AdvancedPGBUF-QB-040Lesson 12

11. 즉시 사용할 free BCB가 없으면 어떻게 되는가?

model answer 보기

Model answer: allocator는 progress protocol에 들어갑니다. invalid 상태나 eligible victim을 찾고, flush 또는 background progress를 유도하며, direct-victim reservation을 기다리거나 소비한 뒤 retry합니다. timeout, interrupt, all-buffers-dirty 조건은 bounded exit를 제공할 수 있습니다. free list가 비었다는 것은 pressure를 뜻할 뿐, deadlock이나 starvation의 증거는 아닙니다.

이렇게 방어하세요: safety는 eligibility로 세우고, liveness는 producer, wakeup, retry, bounded exit에 달려 있습니다.

Part 5 · Advanced mechanism

일시적인 ownership gap을 건너면 무엇이 달라지는가?

AdvancedPGBUF-QB-035Lesson 11

12. ordered fixing은 왜 page를 먼저 release할 수 있으며, 무엇이 stale해지는가?

model answer 보기

Model answer: 여러 page를 충돌하는 순서로 acquire하지 않도록 helper가 watcher를 release하고, 필요한 순서를 정렬한 뒤 refix할 수 있습니다. refix는 identity의 ownership을 복원하지만, release 전에 얻은 관찰 결과까지 복원하지는 않습니다. page_was_unfixed가 gap을 알리면 page-local pointer, slot, offset, 비교 결과, traversal 결정을 다시 계산해야 합니다.

이렇게 방어하세요: refix 뒤 VPID가 같아도 byte나 그 byte에서 도출한 판단까지 같다는 뜻은 아닙니다.

Canonical answer와 source anchor · Ordered-watcher card

AdvancedPGBUF-QB-046Lesson 13

13. redo는 page LSA를 어떻게 사용해 같은 record를 두 번 적용하지 않는가?

model answer 보기

Model answer: redo는 recovery page를 WRITE로 fix하고 log record LSA와 page LSA를 비교합니다. page가 이미 그 record를 반영한다면 redo를 skip하고 ownership을 release합니다. 그렇지 않으면 recovery function을 적용하고 page LSA를 전진시킨 뒤, 필요한 경우 page를 dirty로 표시하고 scope cleanup으로 release합니다.

이렇게 방어하세요: 이것은 LSA gate에서 page-image idempotence를 입증하지만, 임의의 callback side effect까지 자동으로 idempotent하다고 입증하지는 않습니다.

Canonical answer와 source anchor · Lesson 13

Evidence 원칙PGBUF-QB-055Lesson 8, 16

14. VS-10, VS-11, VS-12 packet은 defect가 실제로 존재한다는 단정인가?

model answer 보기

Model answer: 아닙니다. VS-* packet은 우려 사항에 대한 version-sensitive evidence record이지 판결문이 아닙니다. candidate의 source path, 현재 evidence level, 빠진 proof, status owner를 묶어 둔 것입니다. 더 강한 결론으로 승격하려면 정확한 control flow, 뒷받침된 reachability, 남아 있는 state의 evidence, caller 또는 production impact, target branch 재확인이 필요합니다. packet마다 현재 evidence level이 다를 수 있습니다.

이렇게 방어하세요: “source에서 보이는 early return”은 “도달 가능한 state leak”보다 약하고, 그것도 “입증된 production defect”보다는 약합니다.

Maintainer 방어PGBUF-QB-070Lesson 8, 16

15. 어떤 test가 page-buffer 변경의 안전성을 실제로 입증하는가?

model answer 보기

Model answer: 모든 변경에 통하는 test는 없습니다. risk를 실제로 가로지르는 seam을 골라야 합니다. Interface 변경에는 대표 caller regression, ordering race에는 deterministic interleaving, unwind에는 이름이 명확한 fault injection과 state assertion, replacement policy에는 통제된 pressure, durability에는 crash/recovery evidence가 필요합니다. 그리고 무엇을 test하지 못했는지도 정확히 밝혀야 합니다.

이렇게 방어하세요: 실행이 위험한 transition을 한 번도 지나지 않는다면 반복 횟수가 많아도 더 강한 evidence가 되지 않습니다.

LRU policyReader Q4Lesson 12

4. private/shared LRU는 몇 개이며 quota는 무엇을 뜻하나요?

직접 답변 보기

답변: 개수는 설정과 실행 mode에 따라 달라집니다. Shared 자동 개수는 MAX_NTRANS에서 시작해 list당 약 1,000 buffers를 목표로 하며 최소 네 개이고, 명시 shared count 상한은 1,000입니다. 이 숫자는 private list의 상한이 아닙니다. Server mode에서 private count -1은 MAX_NTRANS + 50이 되고, 0은 private quota를 끄며, 명시 양수는 이 baseline에서 4–4,050입니다. Automatic MAX_NTRANS에는 reserved connection도 들어가며 initializer가 1,000으로 clamp하지 않습니다. 한 BCB는 한 list에만 속합니다. Quota는 placement와 search를 이끌 뿐 fix 수를 제한하거나 reuse를 허가하지 않습니다.

답변: shared LRU1/LRU2 기본 비율은 40%/5%이고 private quota target은 5%/5%를 확보합니다. activity-weighted private quota는 smoothing되며 5,000 pages와 pool 절반으로 제한되고, shared remainder는 list당 최소 target 50을 둡니다. 이 숫자는 모두 고정 revision의 policy이지 Interface contract가 아닙니다.

5. fix와 unfix는 무엇을 뜻하나요?

직접 답변 보기

Holder lifetimeReader Q10Lesson 4

10. Holder entry는 어떻게 살아 있고, unfix를 느리게 만들 수 있나요?

직접 답변 보기

답변: initialization은 thread마다 entry 일곱 개를 예약하고, 모두 쓰면 열 개 단위 set으로 storage를 늘립니다. 첫 fix는 free entry 하나를 한 BCB에 binding해 해당 thread hold list의 앞에 붙입니다. Nested fix는 fix_count를 늘려 같은 entry를 재사용합니다. 마지막 matching unfix는 binding을 제거하고 entry를 해당 thread free list로 돌려보내지만, backing memory는 page-buffer finalization까지 남습니다.

Performance 판단: bottleneck은 가능하지만 자동으로 성립하지는 않습니다. Find는 그 thread가 hold한 서로 다른 BCB 수에 선형이고, final removal은 singly linked list를 다시 걸을 수 있습니다. 작거나 LIFO인 hold set은 저렴하지만 불리한 순서는 quadratic traversal을 누적할 수 있습니다. 여러 thread가 한 BCB를 사용하면 대신 공유 atomic latch에서 contend할 수 있고, 한 thread가 한 page를 nested fix하는 경우에는 holder list가 길어지지 않습니다. 이를 zero-count LRU work, wakeup, flush와 분리해서 profile해야 합니다.

Replacement safetyReader Q11Lessons 7 and 12

11. Victim selection에는 왜 protected handoff가 필요한가요?

직접 답변 보기

Handoff: LRU scan은 pointer를 지목할 뿐입니다. Lock 전 “모두 clear” read는 ownership, flag, waiter state, list state가 바뀌면 stale해집니다. BCB try-lock과 현재 state recheck가 detach를 허가합니다. Removal은 membership을 PGBUF_VOID_ZONE으로 바꾸고 BCB lock을 유지한 채 반환하여 A를 보고 내린 결정이 B로 rebind된 뒤 작용하지 않게 합니다.

Safety: fcnt > 0, next_wait_thrd != NULL, non-idle latch/transient protocol state, DIRTY, FLUSHING, direct-victim flag는 ordinary reuse를 막습니다. DIRTY는 전파되지 않은 현재 byte를 보호하고, FLUSHING은 이전 snapshot과 identity에 연결된 completion을 보호합니다.

Pressure: nonresident materialization은 invalid list를 먼저 시도하고 free slot이 없을 때만 victim을 찾습니다. 모든 BCB가 fixed이면 하나도 빼앗지 않습니다. Server mode는 이후 unfix를 기다리거나 timeout/interrupt/shutdown으로 끝나며, no-daemon path는 동기식으로 retry하고 victim이 없으면 실패합니다.

One LRU: 한 BCB에는 link 한 쌍과 encoded list index/zone 하나가 있습니다. Private-to-shared move는 새 list에 add하기 전에 VOID로 remove합니다. LRU object는 pool lifetime을 가지며 context assignment와 BCB membership은 더 짧습니다.

Cross-private LRUReader Q12Lesson 12

12. 한 transaction은 다른 private LRU에서 victim을 어떻게 찾나요?

직접 답변 보기

Discovery: transaction object를 조사하거나 모든 private list를 순회하지 않습니다. LRU3 candidate가 있는 over-quota private list가 lock-free circular queue에 integer index를 advertise합니다. Victimizer는 big-private queue를 먼저 consume하고 허용될 때 regular queue를 사용하여 index를 곧바로 buf_LRU_list[lru_idx]에 mapping합니다.

Locking: 선택한 list 하나만 lock하고 LRU3 entry를 최대 1,000개 scan하며 BCB를 try-lock합니다. 집중된 hot list에서는 contention이 가능하지만 모든 private LRU mutex를 도는 sweep은 없습니다. 심한 bottleneck 주장은 측정 evidence가 필요합니다.

Zones: new private BCB는 보통 LRU1 top, new shared BCB는 LRU2 middle에 들어갑니다. Threshold pressure는 LRU1→LRU2→LRU3로 demote합니다. 충분히 old인 LRU2 hit와 ordinary LRU3 hit는 LRU1으로 boost됩니다. Private LRU1/LRU2 target은 quota의 5%/5%이고 shared 기본값은 shared target의 40%/5%입니다.

Ordered ownershipReader Q13Lesson 11

13. ordered fix의 input, output, 내부 단계는 무엇인가요?

직접 답변 보기

Input: thread_p, 요청 VPID, fetch mode, latch mode, clean in/out watcher다. caller는 access-method rank와 optional heap group으로 watcher를 초기화하며 pgptr는 null이어야 한다. 이미 hold한 watcher array를 따로 넘기지는 않는다. helper가 현재 thread의 holder list를 통해 찾아낸다.

Output: function은 integer status를 반환한다. 성공하면 req_watcher.pgptr가 요청한 watched fix이고 watcher에 latch/rank/group/link state가 기록된다. release/refix gap을 지난 기존 watcher는 pointer와 page_was_unfixed=true를 받는다. partial failure에서는 앞의 watcher만 복구되고 뒤의 watcher는 null일 수 있으므로 각각 확인해야 한다.

내부 경로: 다른 page를 hold한 채 요청을 conditionally 시도하고 성공하면 watcher를 attach하고 끝낸다. reject되면 watched holder를 검증하고 요청보다 앞에 정렬되는 page는 유지한다. 뒤에 정렬되는 page에는 avoid-deallocation을 등록하고 완전히 unfix한다. 필요하면 모르는 heap group을 찾고 group→rank→VPID로 정렬한 뒤 요청과 release된 page를 그 순서대로 unconditionally acquire한다. fix count와 watcher chain을 복구하고 avoid-deallocation을 balance하며 error 때 요청 fix를 unwind한다.
