LRU / F42 / P

LRU 동작 예제: 최초 배치, 냉각, 리스트 선택

동일한 프레임이 miss, 최초 배치, 재접근을 거치는 과정을 따라갑니다. 설명을 펼치기 전에 다음 상태를 예측해 보세요. 첫 시퀀스는 LRU1 위치 유지로 끝납니다. 이후 스캔에 따른 냉각, 다른 문맥에 의한 이동, 꽉 찬 풀의 첫 victim 리스트 선택까지 이어갑니다.

0 · 큰 풀의 일부를 살펴보기

소스에 따라 구성한 예제이며 실행에서 관찰한 기록이 아닙니다. 기준 리비전은 CUBRID f799e05d77d5300c6ea5753b4a6cc7caee6d8912입니다. 교과서적인 exact LRU는 접근한 항목을 매번 가장 최근 위치로 옮깁니다. 여기서는 실제 fix와 final-unfix 분기를 확인한 뒤 이동 여부를 예측합니다.

서버 모드이며 num_buffers = 32768; shared_lists = 32; private_lists = 4입니다. private chain 수는 명시적으로 설정했습니다. 실행 문맥 A의 private-local 인덱스는 p = 0, 전체 리스트 인덱스는 32입니다. 실행 문맥 B는 p = 1, 전체 인덱스 33을 사용하며 확인 지점 8까지는 활동하지 않습니다. 페이지 P와 R은 A의 작은 working set입니다. 이후의 순차 스캔과 B의 접근이 이 집합에 영향을 줍니다. P와 R은 디스크에 존재하는 유효한 페이지이며, 시작 시 resident hash에는 없습니다. F42와 F43은 고정된 프레임/BCB 쌍의 이름이지 페이지 ID가 아닙니다.

시작 시 상주 페이지는 2,000개입니다. private 리스트 32에 100개, shared 리스트 0에 1,900개가 있고 나머지 리스트는 비어 있습니다. INVALID에는 30,768개가 있으며 F42, F43 순서로 시작합니다. shared 리스트 0의 노드는 모두 LRU3에 있습니다. 리스트 32의 LRU1/2/3 노드 수는 2/48/50이고, LRU1 순서는 H1 → H2입니다. H2가 bottom_1이며, LRU2의 48번째 노드가 bottom_2입니다. 그 뒤에 LRU3 노드 50개가 이어집니다.

리스트 32의 quota는 1,000이고 LRU1/LRU2 임계치는 50/50입니다. 확인 지점 0–10까지 이 값을 유지하며, 지점 11에서 명시적으로 변경합니다.

quota와 shared 임계치 계산 펼치기

앞선 유효 quota 조정 결과에서 private_pages_ratio = 0.5이고 평활화한 private activity가 모두 리스트 32에 속한다고 정했습니다. 따라서 all_private_quota = 2000 * 0.5 = 1000이고 리스트 32의 quota = 1000, private 보호 구간별 임계치는 1000 * 0.05 = 50입니다. 다른 private quota는 0입니다. shared 임계치는 floor((32768 - 1000) / 32) = 992를 기준으로 floor(992 * 0.4) = 396, floor(992 * 0.05) = 49입니다. 작은 가상 풀의 규칙으로 바꾼 것이 아니라, 지정한 스냅샷 입력에 실제 정책 계산을 적용한 값입니다.

확인 지점 5까지는 언급하지 않은 페이지를 모두 그대로 둡니다. 중간에 daemon/quota 조정, 다른 문맥의 접근, 오류, waiter, dirty 전환, flush, 예약, vacuum hint는 없습니다. 각 이벤트가 끝난 뒤 다음 이벤트가 시작합니다. P와 R은 clean, non-hot 상태이며 avoid-victim과 move-to-bottom 플래그가 없습니다. AOUT은 비활성입니다. 리스트 32는 tick_list = 1000에서 시작하고 quota epoch는 adjust_age = 10으로 유지됩니다. 새 F42/F43의 hit_age = 0이며 리스트 32의 현재 lru_hits = 0입니다. 리스트 tick과 quota epoch는 서로 다른 기준입니다.

Implementation policy: 리스트 구성, quota와 임계치 계산. 수량 계산 근거와 unfix/epoch 근거를 함께 참고하세요.

1 · Miss: F42에 P 적재

이전 상태: P는 비상주이고 F42는 INVALID의 첫 노드입니다. invalid 프레임은 30,768개입니다. A가 OLD_PAGE와 READ latch로 요청합니다. fix가 성공해 반환했을 때 페이지 식별자, fix count, 리스트 상태는 무엇일까요?

상태와 소스 근거 확인
F42 represents P; fcnt = 1; latch = READ; zone = VOID
INVALID = 30,767; list 32 counts = 2 / 48 / 50; tick_list = 1000

할당기는 invalid-list mutex 아래에서 F42를 꺼내고 BCB를 보호한 상태에서 VOID로 전환합니다. 성공한 miss 경로가 P를 적재하고 hash에 공개하며 holder/fix를 부여합니다. victim은 필요하지 않았고, VOID는 아직 LRU 소속이 아닙니다. 기존 상주 페이지 2,000개는 변하지 않습니다. 표시한 상태는 pop 직후가 아니라 fix가 성공한 뒤의 상태입니다.

bufptr = pgbuf_Pool.buf_invalid_list.invalid_top;
pgbuf_Pool.buf_invalid_list.invalid_top = bufptr->next_BCB;
pgbuf_Pool.buf_invalid_list.invalid_cnt -= 1;

Verified mechanism: INVALID에서 꺼내기. 이후의 claim/적재/hash 공개 경로 확인.

2 · Final unfix: F42 배치

이전 상태: F42/P는 VOID, READ, fcnt 1입니다. A가 유일한 fix를 해제하며 대기 중인 reader/writer나 특별한 hint는 없습니다. P는 private LRU1, private LRU2, shared LRU2 중 어디로 갈까요?

상태와 소스 근거 확인
F42/P: fcnt = 0; latch = NO_LATCH; list = 32; zone = LRU1
LRU1 top -> F42 -> H1 -> H2
counts = 3 / 48 / 50; tick_list = 1001; F42.tick_lru_list = 1000

fix count가 0이 된 unfix가 VOID 분기로 들어갑니다. A의 private 인덱스는 32이고 AOUT은 꺼져 있으므로 아래 조건이 private-top 배치를 선택합니다. BCB를 보호한 상태에서 helper가 리스트 32를 잠그고 기존 tick을 저장한 뒤 F42를 맨 위에 연결하고 리스트 tick을 증가시킵니다. 3은 50 이하이고 3 + 48 = 51은 100 이하이므로 경계 노드는 강등되지 않습니다. INVALID는 30,767개 그대로입니다. epoch 등록으로 F42.hit_age는 10, lru_hits는 1이 됩니다.

3 · R 적재와 해제: P 위에 새 이웃 추가

이전 상태: F42/P가 private LRU1의 맨 위에 있습니다. A가 비상주 R을 다음 invalid 프레임 F43에 성공적으로 fix한 뒤 final-unfix합니다. 이제 F42는 어디에 있을까요?

상태와 소스 근거 확인
F43/R and F42/P: fcnt = 0; latch = NO_LATCH; list = 32; zone = LRU1
LRU1 top -> F43 -> F42 -> H1 -> H2
counts = 4 / 48 / 50; tick_list = 1002; F43.tick_lru_list = 1001
INVALID = 30,766; resident pages = 2,002

R에도 같은 miss/최초 배치 분기를 적용합니다. F43은 fix 중 잠시 VOID에 있다가 final unfix 때 새 top이 됩니다. F42는 그 바로 아래에 그대로 연결되어 있습니다. 보호 구간 합계 52는 100 이하이고 LRU1 노드 4개는 50 이하이므로 강등은 없습니다. F42의 저장 tick은 1000 그대로입니다. F43이 epoch 10을 등록하면서 lru_hits는 2가 됩니다. 새 이웃이 생겼으므로 다음 재접근에서 위치가 그대로인지 눈으로 확인할 수 있습니다.

bcb->tick_lru_list = lru_list->tick_list;
pgbuf_lru_add_bcb_to_top (thread_p, bcb, lru_list);

Verified mechanism: 삽입. top 삽입 시 tick_list 증가 · 구간 조정 조건.

4 · P hit: 가장 최근 위치로 이동할까?

이전 상태: F43이 F42 위에 있습니다. F42/P는 clean LRU1이며 fcnt 0, NO_LATCH입니다. A가 P를 다시 READ-fix하는 데 성공합니다. fix를 보유하는 동안의 순서를 예측해 보세요.

상태와 소스 근거 확인
F42/P: fcnt = 1; latch = READ; list = 32; zone = LRU1
LRU1 top -> F43 -> F42 -> H1 -> H2
counts = 4 / 48 / 50; tick_list = 1002; INVALID = 30,766

lock-free READ helper는 idle 상태인 NO_LATCH/zero-count 조합을 거절합니다. 일반 보호 경로가 READ 소유권과 holder를 부여하며, F42의 리스트 연결은 바꾸지 않습니다. fix 동안 P는 교체로부터 보호되지만 top 노드가 된 것은 아닙니다. 이번 접근에 대한 unfix hit 표본도 아직 등록되지 않았습니다. 아래 발췌는 fast path 거절 조건의 앞부분입니다. 나머지 식별자 조건과 return은 링크에서 확인하세요.

조건을 결정하는 소스 분기 펼치기

5 · 다시 final unfix: 여전히 R 아래일까?

이전 상태: A가 F42/P를 READ, fcnt 1로 보유합니다. private 인덱스는 여전히 32와 일치하며 P는 hot이 아닙니다. waiter 없이 P를 final-unfix하면 R 위로 올라갈까요?

상태와 소스 근거 확인

LRU1 top -> F43 -> F42 -> H1 -> H2
counts = 4 / 48 / 50; tick_list = 1002; F42.tick_lru_list = 1000
adjust_age = 10; F42.hit_age = 10; lru_hits = 2

일반 zero-count 분기가 LRU1을 확인합니다. 특별한 hint, private-domain 불일치, hot-and-old 이동 조건이 없으므로 위치를 유지하고 재사용을 등록합니다. F42는 이미 epoch 10에 기여했으므로 lru_hits도 2 그대로입니다. 다시 읽으면서 fix/holder 상태는 바뀌었지만 리스트 순서와 현재 epoch의 표본 수는 변하지 않았습니다. 이 keep 분기에서는 LRU mutex를 잡고 다시 연결할 필요가 없으며, 보호된 unfix에는 BCB mutex를 보유한 상태로 진입합니다.

6 · 같은 풀에서 이어가기

INVALID 30,766개, 상주 2,002개, 리스트 32의 개수 4/48/50, tick 1002, epoch 10, F43 → F42 → H1 → H2 순서를 그대로 이어갑니다. 다음 이름은 기존에 이름을 붙이지 않은 상태를 구체화할 뿐 페이지를 추가하지 않습니다. 기존 LRU2 프레임 48개를 Z1 → … → Z48, LRU3 프레임 50개를 C1 → … → C50이라고 부릅니다. C50이 나타내는 페이지는 Q입니다. 이들은 페이지 식별자와 구별되는 영구 프레임의 별칭입니다.

남은 INVALID 연결을 G1 → … → G30766이라고 부릅니다. A는 아직 상주하지 않는 서로 다른 유효한 디스크 페이지 S1부터 S30766까지 순서대로 이 프레임에 읽습니다. 각 페이지마다 OLD_PAGE/READ fix와 final unfix를 성공적으로 마친 뒤 다음으로 넘어가며, 지정된 지점에서 멈춥니다. G 프레임의 초기 hit_age는 0입니다. 기존 페이지와 새 페이지 모두 clean이며 flushing, 예약, avoid-victim 플래그, waiter, 특별한 unfix hint가 없습니다. 이벤트 사이에는 fcnt 0, NO_LATCH입니다. Direct-victim 대기자는 없으며 AOUT은 계속 비활성입니다.

계산을 확정하는 추가 상태

이어서 시작할 때 리스트 32의 tick_lru3 = 100이고 C1…C50의 tick_lru3는 99…50입니다. 따라서 C50이 가장 오래되었고 victim_hint = C50입니다. Shared 리스트 0의 후보 수는 1,900개, private 32는 50개입니다. 일반 private 광고 큐는 비어 있고 shared 큐는 [0], big-private 큐는 빈 상태이며 큐 등록은 성공한다고 가정합니다. 언급하지 않은 리스트와 해당 lru_hits 표본은 0이며, 리스트 32의 표본 두 개는 그대로입니다. 한 번의 shared 삽입에 사용할 add_shared_lru_idx = 0, avoid_shared_lru_idx = -1이고, 비어 있는 shared 리스트 1의 tick_list = 0입니다. 이는 측정값이 아닌 구성한 초기값입니다.

명시적으로 예약한 quota 조정 전까지 임계값 50/50과 quota 1,000을 유지합니다. 스캔 도중 승인된 조정이 없다는 것은 예제의 실행 순서 가정이며, 실제 스캔이 daemon 기상 전에 끝난다는 주장이 아닙니다. 리스트 상주 수가 quota를 넘어도 됩니다. Quota는 교체 선택에 영향을 주지만 INVALID가 프레임을 공급하는 동안의 수용 한도는 아닙니다.

7 · S1…S49 스캔: 경계 계산

이전 상태: 리스트 32는 4/48/50입니다. A가 각 스캔 페이지의 적재와 final unfix를 마치며 아직 P/R에 재접근하지 않습니다. 몇 번째 삽입에서 P가 LRU1을 벗어날까요? S49 이후 개수와 두 경계 프레임을 예측해 보세요.

Verified mechanism: 합산 구간 조정과 강등 · 리스트 mutex 안의 삽입.

8 · 냉각된 P 재사용

이전 상태: P는 LRU2의 첫 프레임이고 저장 tick은 1000입니다. 리스트 tick은 1051, LRU2 개수는 50입니다. A가 P를 READ-fix하고 final-unfix합니다. 리스트 이벤트로 잰 나이가 승격하기에 충분할까요? 벽시계 시간이나 quota epoch로 판단하는 조건이 아닙니다.

상태와 소스 근거 확인 
age = 1051 − 1000 = 51 ≥ floor(50 / 2) = 25
LRU1: F42/P → G49 → … → G1        bottom_1 = G1
LRU2: F43/R → H1 → H2 → Z1 → … → Z47
counts = 50 / 50 / 51; tick_list = 1052
F42.tick_lru_list = 1000; hit_age = 10; lru_hits[32] = 51

일반 fix는 P를 이동시키지 않고 소유권을 부여합니다. Final unfix에서 A의 인덱스는 리스트 32와 같고 P는 여전히 non-hot이므로 LRU2의 old-enough 조건을 확인하고 통과합니다. BCB를 보호한 채 boost가 리스트 32를 잠그고 P를 분리해 top에 삽입한 뒤 zone 1만 조정합니다. 이때 R이 LRU2로 내려갑니다. Boost는 tick_list를 증가시키지만 P의 저장 tick은 다시 쓰지 않습니다. INVALID와 상주 수는 그대로입니다. 이후 같은 문맥에서 LRU1에 재접근하면 이 가정 아래에서는 확인 지점 5처럼 위치를 유지합니다.

if (PGBUF_IS_BCB_OLD_ENOUGH (bufptr, pgbuf_lru_list_from_bcb (bufptr)))
  {
    /* boost */
    pgbuf_lru_boost_bcb (thread_p, bufptr);
  }

Verified mechanism: 나이 조건 · LRU2 분기 · 보호된 boost.

9 · B가 같은 P에 접근

이전 상태: A가 P를 해제했고 B는 private-local p = 1, 전체 리스트 인덱스 33을 가집니다. B가 P를 READ-fix한 뒤 final-unfix합니다. B 전용 사본이 생길까요, P가 리스트 33으로 갈까요, 아니면 기존 소속이 바뀔까요?

상태와 소스 근거 확인 
private 32: 49 / 50 / 51; tick_list = 1052; top = G49
shared 1:   0 / 1 / 0; tick_list = 1
F42/P: shared 1, LRU2; saved tick = 0; hit_age = 10
shared 1 top = bottom_2 = bottom = F42; bottom_1 = NULL
list 33 remains empty; INVALID = 30717; resident = 2051

Private 문맥 불일치 33 != 32만으로 충분하며 P가 hot일 필요는 없습니다. B가 fix를 보유하는 동안 P는 private 32에 남습니다. Fix count가 0이 되는 unfix가 BCB mutex를 계속 보유한 채 private-list mutex 아래에서 분리해 VOID를 거칩니다. 그 리스트 mutex를 해제한 다음 목적지 shared-list mutex 아래에서 연결합니다. 선택기는 add_shared_lru_idx를 0에서 1로 증가시켜 1 % 32 = 1을 선택합니다. 균형 통계 갱신이나 회피 분기는 개입하지 않습니다. 새 middle 삽입은 목적지 tick 0을 저장하고 1로 증가시키며, 1 ≤ 49이므로 강등하지 않습니다.

P는 여전히 하나의 프레임에 있는 하나의 상주 식별자이며 동시에 한 리스트에만 속합니다. Private 문맥은 페이지 독점 소유권을 뜻하지 않습니다. 이동 후 hit 등록을 시도하지만 P의 hit_age가 이미 10이므로 어느 리스트에도 epoch 10 표본을 추가하지 않습니다. 이미 shared인 페이지는 A가 접근한다는 이유만으로 private으로 돌아가지 않습니다.

if (thread_private_lru_index != bcb_lru_idx)
  {
    return true;
  }

Verified mechanism: 이동 조건 · 목적지 선택기 · 순차 리스트 잠금과 VOID.

10 · 교체를 호출하기 전에 스캔 완료하기

A의 S50…S30766 스캔을 이어갑니다. P/R에 더 접근하지 않으며 quota 조정도 없습니다. 각 miss는 여전히 다음 INVALID 프레임을 사용합니다. 마지막 final unfix 이후 상태를 계산해 보세요. 축출된 페이지가 있을까요? 다음 miss도 INVALID를 사용할 수 있을까요?

상태와 소스 근거 확인

완료한 n이 50부터 30766일 때마다 resident = 2002 + n, INVALID = 30766 − n, private 크기 = 101 + n입니다. S50은 강등 없이 LRU1을 50개로 복원합니다. 이 범위의 모든 n에서 개수는 50 / 50 / (n + 1), tick_list = 1003 + n, tick_lru3 = n + 51입니다. S51부터는 삽입마다 보호 구간의 오래된 노드 하나가 내려갑니다. 이 유한한 수열은 모든 삽입을 명시합니다. 말줄임표는 반복 표시만 생략하며 상태를 바꾸는 이벤트를 생략하지 않습니다.

INVALID = 0; resident = 32768
private 32 = 30867 = 50 / 50 / 30767; tick_list = 31769; tick_lru3 = 30817
LRU1: G30766 → … → G30717       bottom_1 = G30717
LRU2: G30716 → … → G30667       bottom_2 = G30667
LRU3: G30666 → … → G1 → F43/R → H1 → H2 → Z1 → … → Z48 → C1 → … → C50/Q
shared 0 = 1900; shared 1 = F42/P; all other lists empty
30867 + 1900 + 1 = 32768; lru_hits[32] = 30768

아직 축출은 일어나지 않았습니다. Quota가 INVALID 우선 할당을 뒤집지는 않습니다. G1…G49의 저장 리스트 tick은 1002…1050이고, G50…G30766은 P의 추가 boost tick을 반영해 n + 1002를 저장합니다. F43의 저장 tick은 1001 그대로입니다. C50은 계속 bottom이자 victim_hint이며 private LRU3 노드 30,767개 모두 후보에 맞는 플래그를 가집니다. 이 광고 개수는 보호된 적격성 판정이 아니며 fix count 재검증을 포함하지 않습니다. S900에서 리스트 크기가 1001이 되어 quota 1000을 처음 넘을 때 private 큐 [32]가 등록되었고, 아직 소비자는 실행되지 않았습니다.

bufptr = pgbuf_get_bcb_from_invalid_list (thread_p);
if (bufptr != NULL)
  {
    return bufptr;
  }

Verified mechanism: victim 탐색보다 앞선 INVALID · 후보 광고 · 구간 개수와 후보 플래그.

11 · 승인된 quota epoch 한 번

이제 private quota가 활성화되고 is_adjusting = 0이며 이전 승인된 조정 이후 측정한 diff_usec = 10000000인 시점에 quota 조정을 한 번 실행합니다. 페이지 이벤트는 겹치지 않습니다. 이전 조정에서 unfix shard를 초기화했고, 이 추적은 일반 final unfix를 30,771번 수행했습니다(기존 3번, 스캔 30,766번, P boost 1번, B 접근 1번). 수집된 hit는 모두 private 32의 30,768개입니다. Activity, quota, 임계값과 리스트 이동을 예측해 보세요.

상태와 소스 근거 확인 
adjust_age: 10 → 11; all lru_hits reset to 0
lru_activity[32] = floor(1000000 × 30768 / 10000000) = 3076
other private activity = 0; shared rate is floored to 1 for the ratio
private_pages_ratio = clamp(3076 / 3077, 0.01, 0.998) = 0.998
all_private_quota = floor(32768 × 0.998) = 32702
quota[32] = min(32702, 5000, 16384) = 5000
private thresholds = 250 / 250; other private quotas = 0
shared target = max(floor((32768 − 32702) / 32), 50) = 50
shared thresholds = 20 / 2

1 ms 조건을 통과하며 이 간격에서는 500 ms 조건으로 반환하지 않습니다. Unfix 활동량 30,771은 낮은 활동량 기준 floor(8192/100) = 81보다 큽니다. 10초가 되었으므로 기존 값과 혼합하지 않고 activity와 비율을 새 값으로 대체합니다. Shared 계산에는 개별 리스트의 hard cap 적용 전 all_private_quota를 사용하며 남은 quota를 재분배하지 않습니다. 임계값이 커졌다고 기존 노드를 승격하지는 않습니다. Private 보호 구간 100은 quota 5000 이하이며 shared 1의 유일한 LRU2 노드도 새 임계값 이하입니다. 개수, 위치, 리스트 tick, P/R의 hit_age 10, INVALID는 그대로입니다. 후보 합계 32667 ≥ floor(0.1 × 32768)이므로 victim_rich는 true가 됩니다.

lru_hits = ATOMIC_TAS_32 (&monitor->lru_hits[i], 0);
/* compute hits per second */
lru_hits = (int) (onesec_usec * lru_hits / diff_usec);
quota cap과 조정 조건 펼치기
new_quota = (int) (new_lru_ratio * all_private_quota);
new_quota = MIN (new_quota, PGBUF_PRIVATE_LRU_MAX_HARD_QUOTA);
new_quota = MIN (new_quota, pgbuf_Pool.num_buffers / 2);

lru_list = PGBUF_GET_LRU_LIST (i);
lru_list->quota = new_quota;
lru_list->threshold_lru1 = (int) (new_quota * PGBUF_LRU_ZONE_MIN_RATIO);
lru_list->threshold_lru2 = (int) (new_quota * PGBUF_LRU_ZONE_MIN_RATIO);

if (PGBUF_LRU_LIST_IS_ONE_TWO_OVER_QUOTA (lru_list))
  {
    pthread_mutex_lock (&lru_list->mutex);
    pgbuf_lru_adjust_zones (thread_p, lru_list, false);
    pthread_mutex_unlock (&lru_list->mutex);

    PGBUF_BCB_CHECK_MUTEX_LEAKS ();
  }

서로 다른 세 이력입니다. 리스트 이벤트 나이는 LRU1/2 삽입으로 증가합니다. Hit_age는 승인된 quota epoch마다 BCB당 한 번 표본을 남깁니다. 포화되는 hot-fix 휴리스틱의 임계값은 64입니다. 여기서 P의 일반 fix는 네 번, R은 한 번, 각 스캔 페이지는 한 번뿐입니다. Quota 조정이 승인되어도 P가 hot이 되거나 저장 리스트 tick이 갱신되지는 않습니다.

Implementation policy: 조건, 평활화, cap, shared 임계값 · hot-fix 이력 · epoch 표본.

근거의 한계: VS-*는 불확실성 레지스트리의 항목 식별자입니다. VS-21은 근사 표본 수집, 재사용·wrap 문제, 시간 관련 주석과 실행 조건의 불일치를 기록합니다. 이 직렬 계산은 해당 문제를 고치지도, 동시 실행에서 통계가 정확하다고 보장하지도 않습니다. 불확실성 레지스트리 확인.

12 · A는 어느 리스트를 탐색할까?

이전 상태: INVALID는 비어 있습니다. A의 전체 private 인덱스는 32, quota는 5000, 크기는 30867, 보호 구간은 100, 광고된 후보는 30767개입니다. 큐는 일반 private [32], big-private [], shared [0]입니다. Page-flush daemon은 사용 가능하지만 이 예측 도중 실행하지 않습니다. A가 상주하지 않는 새 유효 페이지 T를 요청합니다. 처음 선택할 리스트를 예측하고 후보를 탐색하거나 잠그기 전에 멈추세요.

상태와 소스 근거 확인 
own protected-over-quota: 100 > 5000 → false
own total-over-quota and candidates: 30867 > 5000 and 30767 > 0 → true
next call: pgbuf_get_victim_from_lru_list(thread_p, 32)
no queue consumed; no BCB detached; no permission to overwrite Q

이제 실제로 INVALID 우선 할당이 실패하므로 victim 탐색에 들어갑니다. Own-private 조건이 광고를 소비하지 않고 32를 직접 선택합니다. 이 helper는 선택한 리스트를 잠그고 LRU3를 확인한 뒤 hint에서 최대 1,000개 위치를 살펴봅니다. Bottom C50이 clean이므로 탐색 전에 오래된 hint를 C50으로 맞춥니다. 보호 구간 100은 탐색 전 quota 강등을 유발하지 않습니다.

if (PGBUF_LRU_LIST_IS_ONE_TWO_OVER_QUOTA (lru_list)
    || (PGBUF_LRU_LIST_IS_OVER_QUOTA (lru_list) && lru_list->count_vict_cand > 0))

이 own 탐색이 실패한다면 30867 > 5000 + max(10, 50)이므로 다른 private 탐색을 big-private 큐로 제한합니다. 그 큐는 비어 있으므로 일반 [32]를 소비하지 않고 shared 광고 0으로 넘어갑니다. 이는 조건부 경로이며 이미 실행한 추가 이벤트가 아닙니다. 보호된 후보 확보에 성공하면 그 전에 반환합니다. 탐색 실패가 안전하지 않은 프레임 재사용을 허용하지는 않습니다.

Verified mechanism: 리스트 선택 제어 흐름 · 선택한 리스트 탐색과 보호된 재검증 · 제한된 큐 탐색.

선택은 안전한 재사용이 아닙니다. VS-19는 big-private 큐의 최초 생산 경로가 미해결임을, VS-20은 maintenance 보조 루프가 작성된 그대로는 실행되지 않음을 기록합니다. 둘 다 기아나 성능에 대한 결론을 뒷받침하지 않습니다. AOUT은 계속 비활성이며 runtime victim 실험을 했다고 주장하지 않습니다. 근거의 한계 확인.

보호된 재사용과 정책 검토로 이어가기

이 종료 지점은 quota 조정 후, A의 T 할당 전입니다. 앞의 예측은 선택한 리스트 helper를 실제 실행하지 않았습니다. BCB·리스트 mutex를 보유하지 않고 남은 fix도 없으며, 분리되거나 예약된 페이지도 없습니다. C50/Q는 private 32의 bottom이자 hint에 있는 clean LRU3이며 fcnt 0, NO_LATCH, waiter 없음, 부적격 후보 플래그 없음입니다. 이전 노드는 C49입니다. F42/P는 저장 tick 0인 shared 1 LRU2, F43/R은 저장 tick 1001인 private 32 LRU3에 남습니다. Epoch는 11, 두 페이지의 hit_age는 10이며 모든 lru_hits 표본은 0입니다(평활화된 lru_activity[32]는 3076 유지).

새 실행 순서를 시작할 때 완전한 종료 연결 상태와 quota 입력을 사용하세요. 이후 시나리오에서 dirtying, fix, 예약, hint 변경을 추가하면 이를 명시해야 합니다. 임계값은 250/250이지만 private BCB 연결은 여전히 50/50/30767개입니다. 리스트 32를 선택했다고 C50을 분리하거나 Q를 T로 바꿀 권한이 생기지 않습니다. 보호된 후보 프로토콜이 필요합니다.
