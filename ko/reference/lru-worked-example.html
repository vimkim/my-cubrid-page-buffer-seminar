LRU 동작 예제: 최초 배치부터 정책 검토까지

동일한 프레임이 miss, 최초 배치, 재접근을 거치는 과정을 따라갑니다. 설명을 펼치기 전에 다음 상태를 예측해 보세요. 스캔에 따른 냉각, 다른 문맥에 의한 이동, 리스트 선택, 보호된 프레임 재사용, 동시 실행 중의 진행까지 이어갑니다. 마지막에는 즉시 승격이라는 가상 정책을 검토합니다. 각 대안은 지정한 스냅샷에서 다시 시작하므로 분기 사이에 상태를 이어 붙이지 마세요.

0 · 큰 풀의 일부를 살펴보기

소스에 따라 구성한 예제이며 실행에서 관찰한 기록이 아닙니다. 기준 리비전은 CUBRID f799e05d77d5300c6ea5753b4a6cc7caee6d8912입니다. 교과서적인 exact LRU는 접근한 항목을 매번 가장 최근 위치로 옮깁니다. 여기서는 실제 fix와 final-unfix 분기를 확인한 뒤 이동 여부를 예측합니다.

서버 모드이며 num_buffers = 32768; shared_lists = 32; private_lists = 4입니다. private chain 수는 명시적으로 설정했습니다. 실행 문맥 A의 private-local 인덱스는 p = 0, 전체 리스트 인덱스는 32입니다. 실행 문맥 B는 p = 1, 전체 인덱스 33을 사용하며 확인 지점 8까지는 활동하지 않습니다. 페이지 P와 R은 A의 작은 working set입니다. 이후의 순차 스캔과 B의 접근이 이 집합에 영향을 줍니다. P와 R은 디스크에 존재하는 유효한 페이지이며, 시작 시 resident hash에는 없습니다. F42와 F43은 고정된 프레임/BCB 쌍의 이름이지 페이지 ID가 아닙니다.

시작 시 상주 페이지는 2,000개입니다. private 리스트 32에 100개, shared 리스트 0에 1,900개가 있고 나머지 리스트는 비어 있습니다. INVALID에는 30,768개가 있으며 F42, F43 순서로 시작합니다. shared 리스트 0의 노드는 모두 LRU3에 있습니다. 리스트 32의 LRU1/2/3 노드 수는 2/48/50이고, LRU1 순서는 H1 → H2입니다. H2가 bottom_1이며, LRU2의 48번째 노드가 bottom_2입니다. 그 뒤에 LRU3 노드 50개가 이어집니다.

리스트 32의 quota는 1,000이고 LRU1/LRU2 임계치는 50/50입니다. 확인 지점 0–10까지 이 값을 유지하며, 지점 11에서 명시적으로 변경합니다.

quota와 shared 임계치 계산 펼치기

앞선 유효 quota 조정 결과에서 private_pages_ratio = 0.5이고 평활화한 private activity가 모두 리스트 32에 속한다고 정했습니다. 따라서 all_private_quota = 2000 * 0.5 = 1000이고 리스트 32의 quota = 1000, private 보호 구간별 임계치는 1000 * 0.05 = 50입니다. 다른 private quota는 0입니다. shared 임계치는 floor((32768 - 1000) / 32) = 992를 기준으로 floor(992 * 0.4) = 396, floor(992 * 0.05) = 49입니다. 작은 가상 풀의 규칙으로 바꾼 것이 아니라, 지정한 스냅샷 입력에 실제 정책 계산을 적용한 값입니다.

확인 지점 5까지는 언급하지 않은 페이지를 모두 그대로 둡니다. 중간에 daemon/quota 조정, 다른 문맥의 접근, 오류, waiter, dirty 전환, flush, 예약, vacuum hint는 없습니다. 각 이벤트가 끝난 뒤 다음 이벤트가 시작합니다. P와 R은 clean, non-hot 상태이며 avoid-victim과 move-to-bottom 플래그가 없습니다. AOUT은 비활성입니다. 리스트 32는 tick_list = 1000에서 시작하고 quota epoch는 adjust_age = 10으로 유지됩니다. 새 F42/F43의 hit_age = 0이며 리스트 32의 현재 lru_hits = 0입니다. 리스트 tick과 quota epoch는 서로 다른 기준입니다.

Implementation policy: 리스트 구성, quota와 임계치 계산. 수량 계산 근거와 unfix/epoch 근거를 함께 참고하세요.

1 · Miss: F42에 P 적재

이전 상태: P는 비상주이고 F42는 INVALID의 첫 노드입니다. invalid 프레임은 30,768개입니다. A가 OLD_PAGE와 READ latch로 요청합니다. fix가 성공해 반환했을 때 페이지 식별자, fix count, 리스트 상태는 무엇일까요?

상태와 소스 근거 확인
F42 represents P; fcnt = 1; latch = READ; zone = VOID
INVALID = 30,767; list 32 counts = 2 / 48 / 50; tick_list = 1000

할당기는 invalid-list mutex 아래에서 F42를 꺼내고 BCB를 보호한 상태에서 VOID로 전환합니다. 성공한 miss 경로가 P를 적재하고 hash에 공개하며 holder/fix를 부여합니다. victim은 필요하지 않았고, VOID는 아직 LRU 소속이 아닙니다. 기존 상주 페이지 2,000개는 변하지 않습니다. 표시한 상태는 pop 직후가 아니라 fix가 성공한 뒤의 상태입니다.

Verified mechanism: INVALID에서 꺼내기. 이후의 claim/적재/hash 공개 경로 확인.

6 · 같은 풀에서 이어가기

INVALID 30,766개, 상주 2,002개, 리스트 32의 개수 4/48/50, tick 1002, epoch 10, F43 → F42 → H1 → H2 순서를 그대로 이어갑니다. 다음 이름은 기존에 이름을 붙이지 않은 상태를 구체화할 뿐 페이지를 추가하지 않습니다. 기존 LRU2 프레임 48개를 Z1 → … → Z48, LRU3 프레임 50개를 C1 → … → C50이라고 부릅니다. C50이 나타내는 페이지는 Q입니다. 이들은 페이지 식별자와 구별되는 영구 프레임의 별칭입니다.

남은 INVALID 연결을 G1 → … → G30766이라고 부릅니다. A는 아직 상주하지 않는 서로 다른 유효한 디스크 페이지 S1부터 S30766까지 순서대로 이 프레임에 읽습니다. 각 페이지마다 OLD_PAGE/READ fix와 final unfix를 성공적으로 마친 뒤 다음으로 넘어가며, 지정된 지점에서 멈춥니다. G 프레임의 초기 hit_age는 0입니다. 기존 페이지와 새 페이지 모두 clean이며 flushing, 예약, avoid-victim 플래그, waiter, 특별한 unfix hint가 없습니다. 이벤트 사이에는 fcnt 0, NO_LATCH입니다. Direct-victim 대기자는 없으며 AOUT은 계속 비활성입니다.

계산을 확정하는 추가 상태

이어서 시작할 때 리스트 32의 tick_lru3 = 100이고 C1…C50의 tick_lru3는 99…50입니다. 따라서 C50이 가장 오래되었고 victim_hint = C50입니다. Shared 리스트 0의 후보 수는 1,900개, private 32는 50개입니다. 일반 private 광고 큐는 비어 있고 shared 큐는 [0], big-private 큐는 빈 상태이며 큐 등록은 성공한다고 가정합니다. 언급하지 않은 리스트와 해당 lru_hits 표본은 0이며, 리스트 32의 표본 두 개는 그대로입니다. 한 번의 shared 삽입에 사용할 add_shared_lru_idx = 0, avoid_shared_lru_idx = -1이고, 비어 있는 shared 리스트 1의 tick_list = 0입니다. 이는 측정값이 아닌 구성한 초기값입니다.

명시적으로 예약한 quota 조정 전까지 임계값 50/50과 quota 1,000을 유지합니다. 스캔 도중 승인된 조정이 없다는 것은 예제의 실행 순서 가정이며, 실제 스캔이 daemon 기상 전에 끝난다는 주장이 아닙니다. 리스트 상주 수가 quota를 넘어도 됩니다. Quota는 교체 선택에 영향을 주지만 INVALID가 프레임을 공급하는 동안의 수용 한도는 아닙니다.
