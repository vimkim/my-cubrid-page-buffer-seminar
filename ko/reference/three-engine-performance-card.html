Performance 개선 기회 funnel

  1. Observe: held-list depth, 확인한 node 수, shared CAS 시도/재시도 횟수, fix/unfix당 cycle을 측정합니다.
  2. Localize: held-set 크기, thread 수, target page 공유도를 각각 따로 변화시켜 원인을 좁힙니다.
  3. Low-risk prototype: global fcnt는 그대로 유지하면서 per-thread holder lookup을 빠르게 만듭니다.
  4. Higher-risk prototype: shared CAS traffic의 영향이 크다고 입증된 경우에만 nested ownership을 local에서 aggregate합니다.
  5. Prove: promotion, waiter ordering, zero-crossing wakeup, last-unfix LRU 작업, victim exclusion이 유지됨을 증명합니다.
현재 결론: source에서 추론한 개선 기회일 뿐, 측정된 성능 향상이 아닙니다. 현재 evidence로는 세 engine의 latency나 throughput을 비교할 수 없습니다.

30초 답변

CUBRID의 두드러진 seam은 normal fix가 residency protection, per-thread holder, 요청한 page latch를 하나로 결합한다는 점입니다. PostgreSQL은 pin과 content lock을 독립적으로 다루며, 첫 shared contribution 이후 반복되는 pin은 backend local에 유지합니다. InnoDB는 fix count와 latch state를 분리하되 그 lifetime은 MTR memo에 기록합니다. CUBRID에서 가장 먼저 검증할 performance 가설은 held-set depth가 늘어날 때 linear holder lookup 비용이 어떻게 증가하는지입니다. Shared atomic traffic이 지배적인 비용으로 확인된 뒤에만 nested-fix aggregation을 고려해야 합니다.
