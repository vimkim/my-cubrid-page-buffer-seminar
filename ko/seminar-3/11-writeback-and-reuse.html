CUBRID 페이지 버퍼 daemon과 PostgreSQL 페이지 교체

몇몇 페이지를 반복해서 읽는 동안 대량 스캔과 아직 기록할 페이지 변경이 버퍼 풀을 채웁니다. 구성한 실행 순서는 각각 독립된 상태에서 시작합니다. 목적과 비용에 대한 설명은 소스에 의도가 명시되어 있지 않으면 추론입니다.

요청에는 프레임이 필요하지만 기존 페이지도 보존해야 한다

데이터베이스 요청이 필요한 페이지는 가득 찬 버퍼 풀에 없습니다. 프레임은 페이지 하나를 담는 메모리 슬롯입니다. Descriptor는 그 프레임의 현재 페이지 식별자와 공유 상태를 저장합니다. 이 요청을 처리하는 서버 프로세스인 backend는 공간을 마련하려고 dirty 프레임을 선택했습니다.

Dirty 페이지에는 아직 데이터 파일에 써야 할 변경이 남아 있습니다. Pin을 보유하면 프레임이 현재 페이지를 계속 담도록 보호합니다. 다른 backend도 같은 페이지를 pin하고, 필요한 content lock을 획득한 뒤 변경할 수 있습니다.

Writeback은 기존 페이지의 바이트를 데이터 파일에 씁니다. Invalidation은 그 뒤 기존 페이지와 프레임의 mapping을 제거합니다. 쓰기 성공은 재사용의 준비입니다. 현재 pin과 dirty 상태를 보호 아래 검사해야 invalidation을 허용할 수 있습니다. 비동기 I/O도 저장 작업을 마칠 때까지 프레임을 보호하는 별도의 수명 pin을 보유할 수 있습니다.

11 · 3 / 21

바이트를 보호한 뒤 페이지보다 로그를 먼저 쓴다

새 쓰기 시도에서 시작합니다. 요청 backend는 dirty 영구 페이지를 pin한 상태입니다. 영구 페이지는 장애 복구를 위해 변경을 로그에 기록하는 페이지입니다. Pin은 현재 페이지 식별자를 유지합니다. 별도의 content lock은 충돌하는 변경으로부터 바이트를 보호합니다.

WAL은 write-ahead logging, 즉 선행 로그 기록입니다. 복구 로그가 설명하는 데이터 파일 변경보다 그 로그가 먼저 영속 저장장치에 도달해야 합니다. 페이지의 LSN은 log sequence number로, 이 이미지에 필요한 로그 위치를 나타냅니다. FlushBuffer는 최소한 share-exclusive content 보호를 보유한 채 그 위치를 읽습니다. 영구 페이지의 WAL을 먼저 영속화하고 안정된 바이트를 씁니다.

쓰기를 마치면 페이지가 clean이 될 수 있습니다. 대량 읽기 전략은 BULKREAD, 대량 쓰기는 BULKWRITE, 유지보수는 VACUUM을 사용합니다. BULKREAD ring에서 얻은 dirty 영구 페이지 후보에 WAL 영속화가 필요하면 backend는 쓰는 대신 후보를 거절할 수 있습니다. 거절은 로컬 슬롯을 비우고 lock과 pin을 반납합니다. 공유 페이지 식별자와 dirty 작업은 보존합니다. BULKWRITE와 VACUUM은 이 거절 경로를 택하지 않습니다.

11 · 4 / 21

보호 아래 연결을 제거하기 전까지 다른 사용자가 찾을 수 있다

페이지 쓰기가 성공한 뒤의 상태를 이어서 봅니다. 요청 backend는 자신의 pin을 계속 보유하지만 content lock은 해제했습니다. Pin은 페이지 식별자를 유지합니다. Content lock은 쓰는 동안 바이트를 보호했습니다. 기존 페이지와 프레임의 mapping이 남아 있으므로 다른 backend도 페이지를 찾아 자신의 pin을 획득할 수 있습니다.

Invalidation은 기존 조회 항목을 제거하는 작업입니다. InvalidateVictimBuffer는 mapping partition lock으로 조회를 보호하고, header lock 아래 현재 descriptor 상태를 검사합니다. 다른 pin이 남았거나 페이지가 dirty여서 데이터 파일에 쓸 작업이 있으면 거절합니다. 자신의 pin만 남고 clean 상태여야 연결을 제거할 수 있습니다.

다른 backend가 자신의 pin을 유지하면 늘어난 공유 refcount가 재사용을 막습니다. 페이지를 변경한 뒤 떠나면 refcount는 1로 돌아와도 dirty flag가 재사용을 막습니다. 다음 사례는 두 번째 실패를 따로 살펴봅니다.

다른 backend가 떠나도 새 변경은 남는다

독립된 새 사례: A는 재사용할 프레임을 구하는 backend입니다. B는 페이지를 변경하는 다른 backend입니다. R은 A가 선택한 프레임에 현재 담긴, 변경을 로그에 기록하는 영구 페이지입니다. A는 R을 쓴 뒤에도 자신의 pin을 보유합니다. 기존 mapping도 남아 있습니다. 진행 중인 I/O는 없습니다.

Content lock은 쓰기나 변경 중 페이지 바이트를 보호합니다. A가 해제한 뒤 B는 R을 pin하고 변경 보호를 획득하여 새 변경을 로그에 기록하고 R을 dirty로 만든 다음 떠날 수 있습니다. 이 사례의 공유 refcount는 일반 backend pin의 공유 참조를 셉니다. B가 떠나면 1로 돌아오지만, dirty flag에는 B의 미완료 변경이 남습니다.

Q21 · 남은 pin은 무엇을 증명할까?

예측 질문: 이제 A의 pin만 남았지만 R은 다시 dirty입니다. refcount=1이면 R의 mapping을 제거해도 될까요?

논의 후 설명 보기

아닙니다. 검사 시점에 A만 공유 pin을 보유한다는 뜻입니다. 아직 쓰지 않은 변경에 대해서는 알려 주지 않습니다. InvalidateVictimBuffer는 mapping과 header lock 아래 refcount=1과 BM_DIRTY 없음이라는 두 조건을 모두 요구합니다. A의 이전 쓰기는 B의 이후 변경을 포함할 수 없습니다. A는 이 후보를 반납하고 재시도합니다.

재사용 후보를 마련하는 예산은 checkpoint 작업을 대신하지 못한다

Background writer는 향후 할당에 쓸 가능성이 있는 clean 페이지를 준비합니다. Checkpoint는 복구 경계를 만듭니다. 선택된 dirty 페이지를 쓰고, 저장장치 동기화와 로그 작업까지 마쳐야 합니다. 두 주체는 서로 다른 목적에 따라 작업을 선택합니다.

독립된 새 사례: P와 Q는 pin도 진행 중인 I/O도 없는 두 dirty 상주 페이지입니다. P는 이번 checkpoint 대상으로 선택됐고 usage credit이 3입니다. Q의 usage credit은 0입니다. Usage credit은 최근 사용을 나타내는 작은 보존 카운터입니다. 교체 선호에 영향을 주지만 쓰기 의무를 결정하지는 않습니다.

Q22 · 각 주체는 어떤 작업을 마쳐야 할까?

변경 제안: Background writer가 실행 중이므로 checkpoint의 페이지 처리를 생략하려 합니다. Background writer는 Q를 고려할 수 있지만 일반적인 청소 정책은 credit이 있는 P를 건너뜁니다. 이 작업으로 checkpoint가 필요한 결과를 얻을까요?

논의 후 설명 보기

아닙니다. Background writer는 자신의 예산 안에서 Q처럼 pin이 없고 credit이 0인 페이지를 찾습니다. Checkpoint는 credit이 양수여도 P처럼 선택된 작업을 처리합니다. Backend나 background writer가 실제로 쓴 결과는 선택된 페이지의 checkpoint 쓰기를 충족할 수 있습니다. 하지만 그 주체가 실행 중이라는 사실만으로는 충족되지 않습니다. Checkpoint에는 이후 동기화와 로그 단계도 필요합니다.

세 쓰기 주체는 서로 다른 결과를 목표로 한다

Dirty 상주 페이지가 있는 가득 찬 풀로 돌아갑니다. 여기서는 역할을 비교합니다. 앞 경합 사례의 다음 사건이 아닙니다. 각 쓰기 주체는 content 보호와 페이지의 로그 규칙을 따르지만, 성공한 쓰기의 목적은 서로 다릅니다.

할당 backend

요청을 처리하는 프로세스가 dirty 교체 후보를 선택하고 pin합니다. Content lock을 시도해 페이지를 쓴 뒤 보호 아래 invalidation을 시도합니다. 실패하면 그 후보를 반납하고 재시도합니다.

Background writer

이 worker는 스캔과 쓰기 예산 안에서 pin이 없고 credit이 0인 페이지를 clean으로 만듭니다. Usage credit은 보존 선호를 나타냅니다. 향후 후보를 준비하지만 특정 요청을 위해 예약하지는 않습니다.

Checkpointer

이 worker는 복구 경계를 위해 선택된 dirty 페이지를 처리합니다. 양수 usage credit도 필요한 쓰기를 취소하지 않습니다. 이후 동기화와 로그 작업까지 마쳐야 복구 경계가 완성됩니다.

11 · 9 / 21

용량 그룹과 페이지 credit은 서로 다른 정보를 기억한다

새 정책 비교에서 시작합니다. 클라이언트의 서버 측 작업 문맥인 여러 세션이 페이지를 다시 읽는 동안 대량 스캔이 같은 풀을 채웁니다. 프레임은 페이지 하나를 담는 메모리 슬롯입니다. 이 작업들이 용량을 두고 경쟁하는 모습을 각 정책은 어떻게 기록할까요?

CUBRID의 교체 domain은 상주 프레임을 묶는 정책 그룹입니다. Quota는 그 그룹의 목표 용량 몫입니다. Private domain은 세션을 용량 계산과 연결하고, shared domain은 공통 정책 소속을 기록합니다. Private domain은 페이지를 독점할 권한을 주지 않습니다. 여러 세션이 private 목록 하나를 공유할 수도 있습니다.

PostgreSQL의 일반 전역 Clock은 상한이 있는 usage credit으로 공유 descriptor를 탐색합니다. 이 보존 카운터는 조건에 맞는 접근을 모으지만 사용자의 식별자는 저장하지 않습니다. Backend의 private refcount는 현재 페이지 식별자를 유지하는 미반납 pin을 기록합니다. 사용 중임을 관리하는 기록이며 상주 용량 quota가 아닙니다. Ring은 대량 연산이 공유 프레임 ID를 담는 로컬 배열입니다.

추론: CUBRID의 명시적인 용량 계산이 혼합 workload에 도움이 될 수 있지만 quota, 큐, 목록 이동을 관리하는 비용도 듭니다. Pin이나 ring은 일반적인 클라이언트별 용량 공정성을 보장하지 않습니다. 정책 상태가 더 많다는 사실로 처리량이나 hit ratio의 우위를 증명할 수는 없습니다.

독립된 새 사례: A는 할당 backend이고 B는 다른 backend입니다. R은 변경을 로그에 기록하는 영구 페이지이며 선택한 프레임에 담겨 있습니다. A는 R을 쓰고 content 보호를 해제했지만 pin은 유지했습니다. 이후 B가 R을 pin하고 보호 아래 변경을 로그에 기록했습니다. R을 dirty로 만든 뒤 자신의 pin을 반납했습니다. 진행 중인 I/O는 없습니다.

Pin은 현재 페이지 식별자를 유지합니다. 반납해도 페이지 바이트를 쓰지는 않습니다. Refcount는 pin 참조 수입니다. 일반 backend pin은 보유 중인 backend마다 공유 참조 하나를 기록합니다. DIRTY는 미완료 데이터 파일 작업입니다. 기존 mapping을 제거하려는 보호된 invalidation 검사에서 refcount는 1이고 DIRTY는 설정돼 있습니다.

최종 dirty 검사를 없애려는 제안은 무엇을 보존해야 하며, 어떤 관측으로 그 설명을 검증하겠습니까?

연결 제거 논증 보기

Refcount만으로는 부족합니다. 중간 변경을 배제하거나 다른 protocol로 그 이미지를 보존해야 합니다. 구현 경로에서는 현재 BM_DIRTY 때문에 재사용을 거절합니다. Ring의 후보 확보, 전역 fallback 방문, content-lock 실패, 대량 읽기의 WAL 거절, dirty/refcount에 의한 invalidation 실패를 따로 기록합니다. 그러면 탐색 압박과 쓰기 경로의 경합을 구분할 수 있습니다. 이 구성한 사례로 엔진 간 성능 우승을 정할 수는 없습니다.

소스는 다른 사용자나 미완료 쓰기 중 하나만 있어도 거절한다

선택한 페이지를 쓴 뒤의 최종 invalidation에서 시작합니다. Pin은 페이지 식별자를 유지하고 공유 refcount는 backend나 진행 중인 저장 작업이 보유한 참조 수를 셉니다. BM_DIRTY는 미완료 데이터 파일 작업입니다. 호출자는 mapping partition lock과 buffer header lock을 보유합니다. 조회 항목과 현재 상태를 보호한 채 두 조건을 검사합니다.

 * If somebody else pinned the buffer since, or even worse, dirtied it,
 * give up on this buffer: It's clearly in use.
 */
if (BUF_STATE_GET_REFCOUNT(buf_state) != 1 || (buf_state & BM_DIRTY))
{
	Assert(BUF_STATE_GET_REFCOUNT(buf_state) > 0);

	UnlockBufHdr(buf_hdr);
	LWLockRelease(partition_lock);

	return false;
}

||는 둘 중 하나만 실패해도 후보를 거절한다는 뜻입니다. 다른 backend가 검사 전에 unpin하면 refcount는 1이지만 BM_DIRTY는 남을 수 있습니다. false를 반환하면 기존 페이지 mapping은 유지됩니다. 호출자는 후보의 pin을 반납하고 재시도합니다.

기존 페이지를 예약해 중간 변경을 막는다

독립적으로 초기화한 설명용 대안: Backend가 재사용할 dirty 페이지를 선택했고 다른 backend나 I/O가 보유한 pin은 없습니다. Pin은 페이지 식별자를 유지합니다. 새 예약은 기존 mapping을 제거할 때까지 다른 조회 경로의 pin을 막습니다. 중간 사용을 허용한 뒤 재검사하는 방식 대신 처음부터 그 사용을 배제합니다.

  1. 예약에 소유자와 취소 상태를 저장합니다. 모든 조회와 pin 경로가 합의한 lock 순서 아래 예약을 확인해야 합니다.
  2. Content lock을 보유하여 바이트를 쓰는 동안 변경을 배제합니다. 페이지의 로그 위치를 읽고 일치하는 선행 기록 로그(WAL)를 영속 저장장치에 기록합니다.
  3. 안정된 바이트를 씁니다. Mapping 보호 아래 자신의 소유권만 남고 clean 상태인지 확인합니다. 예약을 해제하기 전에 기존 mapping을 제거합니다.
  4. 오류나 취소 때는 기존 페이지를 계속 조회할 수 있게 하고 미완료 dirty 작업을 남깁니다. 예약을 지운 뒤 예약 소유자의 pin을 반납합니다.

이후 변경과의 경합은 막지만 이제 저장장치 지연 동안 새 읽기와 쓰기도 기다립니다. 모든 조회와 content 경로, checkpoint와의 상호작용에 일관된 순서와 정리가 필요합니다. 구현 protocol은 중간 사용을 허용하므로 쓰기에 성공한 뒤에도 재사용을 포기할 수 있습니다.

쓰기와 invalidation 사이의 공백을 관측하기

아직 실행하지 않은 실험, 독립된 시작 상태: A는 프레임을 구하는 backend이고 B는 두 번째 backend입니다. R은 선택한 영구 페이지이며 변경을 로그에 기록합니다. A는 R의 페이지 식별자를 유지하는 유일한 pin을 보유합니다. 관측할 공백에서는 진행 중인 I/O가 없습니다. 아래 통제할 공백 전에 A는 content 보호와 WAL 순서 아래 R을 씁니다.

전체 고정 리비전, build, pool 크기, WAL과 I/O 설정, workload를 기록합니다. 이 PostgreSQL 사례는 CUBRID의 double-write-buffer(DWB) protocol을 사용하지 않습니다.

가설
나중에 생긴 dirty 변경 때문에 pin 참조 수인 공유 refcount가 1로 돌아와도 보호된 invalidation은 R을 거절한다는 가설입니다.
통제하는 변화
FlushBuffer 이후 GetVictimBuffer가 content lock을 해제한 지점에서 멈춥니다. A의 invalidation 시도 전에 B가 R을 pin하고 보호 아래 변경을 로그에 기록합니다. Dirty로 표시하고 unpin하게 합니다.
정확한 관측
제안하는 probe는 페이지 로그 위치(LSN), content-lock 결과, 쓰기 이후 DIRTY/refcount, mapping/header lock 구간, InvalidateVictimBuffer 결과를 기록합니다. 내장 IOOP_REUSE/IOOP_EVICT 횟수는 최종 invalidation이 거절될 수 있는 지점보다 앞에서 증가합니다.
반증 기준과 한계
새 DIRTY가 남은 R의 mapping을 제거하면 보존 주장에 어긋납니다. Eviction 횟수만으로 연결 제거를 증명할 수는 없습니다. Checkpoint 영속성에는 이후 동기화와 로그 증거가 필요합니다. 멈춤과 probe의 overhead도 시간 측정에 영향을 줍니다.
