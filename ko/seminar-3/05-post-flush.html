Flush가 끝났는데 왜 요청은 기다릴까?

G는 제출됐지만 Q는 여전히 기다립니다. Queue는 완료 정리를 위임하고 direct-victim 제안으로 이어질 수 있습니다. 소비 전에 다른 caller가 P를 fix하거나 dirty로 만들 수 있고, 공개된 제안도 취소될 수 있습니다. Producer, consumer, 수신 allocator는 서로 다른 실행입니다. 기존 flush waiter와 현재 frame 할당 waiter가 기다리는 조건도 다릅니다.

현재 배정을 거절하더라도 기존 완료의 정리는 끝내야 합니다. 수신 allocator는 보호된 현재 상태 확보를 통해 재사용 권한을 얻습니다. 공개된 pointer나 제안은 취소될 수 있습니다.

Queue에는 페이지 내용이 아니라 BCB 포인터를 넘긴다

이 시점에는 stable page generation이 설정된 DWB/direct-write submission boundary를 넘었지만, BCB에는 아직 이전 flush가 진행 중이라고 기록되어 있습니다. 이 state를 clear하고 flush waiter를 깨우며 clean frame을 기다리는 allocator에 직접 줄지 판단하는 일은 CPU-side bookkeeping입니다. handoff는 이 bookkeeping 담당자만 바꾸며 page write를 반복하지 않습니다.

  1. 이동하는 것: copy한 page image가 아니라 control record를 가리키는 PGBUF_BCB * 하나입니다.
  2. 받는 곳: bounded flushed_bcbs queue를 거쳐 post-flush daemon이 받습니다.
  3. 받은 쪽이 하는 일: 현재 BCB를 lock하고 다시 확인한 뒤 이전 FLUSHING state를 clear하고 flush waiter를 깨우며, 가능하면 clean frame을 allocator에 reserve합니다.
  4. 여기서 하지 않는 일: post-flush는 새 page I/O를 시작하지 않습니다.

page-flush가 submission을 만들었고, post-flush가 존재하며, allocator가 기다리고, 8,192-entry queue가 pointer를 받아야만 delegate합니다. 조건 하나라도 맞지 않으면 이미지를 제출한 caller가 같은 BCB bookkeeping을 직접 수행합니다. Checkpoint나 명시적 caller도 이 일반 완료 분기를 사용합니다.

DWB가 켜져 있으면 successful submission은 stable image가 DWB에 들어갔다는 뜻일 수 있어 home-volume write보다 앞섭니다. 따라서 이 handoff는 page-buffer submission boundary를 나타낼 뿐, 보편적인 disk durability나 transaction durability를 뜻하지 않습니다.

Post-flush가 실행될 때는 상태가 달라졌을 수 있다

Post-flush는 queue가 빌 때까지 drain합니다. pointer마다 BCB를 lock하고 fix 0, LRU3 membership, clean/eligible flag, private list라면 quota를 다시 봅니다. submission 뒤 resident page가 fix되거나 다시 dirty해지거나 hot해졌을 수 있습니다.

현재도 eligible해야 live direct-victim waiter 하나에게 reserve할 수 있습니다. 결과와 무관하게 old FLUSHING generation을 끝내고 BCB flush waiter를 깨웁니다. work를 consume하면 다음 pause는 1 ms로 reset되고, 연속 idle timeout은 10 ms, 100 ms를 거쳐 wake-only infinite sleep으로 갑니다.

Clean 페이지를 unfix하면 누가 allocator를 깨우는가?

모든 frame이 fixed라서 탐색에 실패한 allocator가 잠든 뒤, reader들이 clean 페이지를 반납하는 상황을 구성해 보자. Unfix만으로 즉시 배정을 보장하지는 않는다. 일반 LRU3 페이지의 마지막 unfix는 보통 승격이나 private→shared 이동을 수행하므로, 반납한 페이지가 계속 cold 후보로 남는 것도 아니다.

Unfix가 직접 배정하는 경로도 있다. Vacuum worker 또는 임시 볼륨의 특정 LRU3 경로와 VOID의 vacuum 경로가 해당한다. LRU 재조정으로 다른 BCB가 LRU3으로 내려갈 때도 적격성 검사, BCB trylock과 재검사를 통과하면 배정할 수 있다. 모든 unfix마다 깨우는 규칙은 아니다.

Page-flush는 후보 탐색 중 이미 clean한 BCB를 발견해 배정할 수 있다. 반면 post-flush는 flushed_bcbs 큐를 소비하며, read unfix로 생긴 모든 clean BCB를 탐색하지 않는다. 수정하지 않은 WRITE fix도 기존 페이지가 이미 clean이었다는 조건이 있어야 같은 사례가 된다.

소스는 victim 압박에서 completion 작업을 넘긴다고 명시합니다. Handoff에는 page-flush producer, 존재하는 post-flush daemon, allocation waiter, queue 삽입 성공이 모두 필요합니다. Queue full 또는 다른 조건 실패는 local completion으로 갑니다. Post-flush는 BCB를 잠그고 배정을 시도한 뒤, 배정 거절에도 FLUSHING을 지우고 flush waiter를 깨웁니다. Allocator wake 뒤에도 보호된 수령 검사가 남습니다.

연속 소유권으로 검사를 대체하면 비용도 바뀝니다

설명용 대안: 보호 구간을 떠나기 전에 F를 reserve하고 새 fix를 막으며 수명이 보장된 reservation token을 전달합니다. 이 수령 경쟁을 피할 수 있지만 lookup, 취소, 버려진 waiter, 종료 처리를 조정해야 합니다. I/O 내내 LRU mutex를 보유하면 무관한 list 연산도 저장장치를 기다립니다. 연속 reservation은 고정 소스의 구현이 아닙니다.

구현된 대안: Local completion은 handoff 불가·queue full에도 두 번째 thread 없이 완료 이미지의 정리와 flush-waiter wake를 유지합니다. 그 순간 frame offer까지 할 필요는 없습니다.

L은 list 수, K는 검사한 node 수, C는 정렬 후보 수, N은 가능한 neighbor 범위, T는 counter shard 수입니다. 해당 page-flush pass의 구조 비용은 O(T + L + K + C log C + C·N)입니다. Queue 정리는 Q개 BCB 항목, S개 stale allocator 기록, W개 flush waiter에 O(Q + S + W)를 더합니다. Atomic retry, lock 경쟁, I/O 지연은 제외한 비용입니다.

Reviewer가 “enqueue 당시 clean” boolean을 전달해 consumer와 receiver 검사를 없애려 합니다. VPID는 여전히 P입니다. Consume 전에 P가 hot해지고 writer가 dirty로 만든 뒤 fix를 반납했습니다. 어떤 검사는 정책이며 어떤 생략은 안전성을 위협할까요?

Cold zone·private quota 검사는 retention 정책입니다. 현재 dirty와 fix·invalid-victim 검사는 재사용과 소유권을 보호합니다. Writer가 떠나 fix가 0이 돼도 dirty 작업은 없어지지 않습니다. Enqueue boolean은 오래된 증거입니다.

일관된 대안: 완료 기록과 재사용 예약 분리
