CUBRID 페이지 버퍼 데몬과 PostgreSQL 페이지 교체

반복해서 읽는 페이지들과 대규모 스캔이 한정된 메모리 슬롯을 두고 경쟁합니다. 수정된 페이지는 안전하게 기록해야 합니다. 각 사례는 독립적인 시작 상태에서 출발하며, 실제 실행을 기록한 결과가 아닙니다.

쓰기가 끝나도 allocator는 왜 기다릴 수 있는가?

새 사례에서 시작합니다. 페이지 P는 데이터베이스의 논리적 페이지로, 프레임이라는 한 페이지용 메모리 슬롯에 있습니다. G는 이미 쓰기 경로에 제출한 안정된 바이트 사본을 가리킵니다. 설명을 위한 표기이며 저장된 세대 카운터가 아닙니다. 다른 요청은 프레임이 필요하지만, 아직 재사용할 프레임을 받지 못했습니다.

BCB(buffer control block)는 프레임에 어떤 페이지가 있는지와 현재 상태를 기록합니다. 이 레코드의 FLUSHING 플래그는 제출한 이미지의 완료 처리가 아직 남아 있음을 나타냅니다. Flush 대기자는 그 처리가 끝나기를 기다립니다. allocator는 재사용할 프레임을 기다리는 할당 요청 주체입니다. 한쪽의 대기가 끝나도 다른 쪽은 계속 기다릴 수 있습니다.

세 주체를 구별해서 따라갑니다. Page-flush는 이미지를 제출합니다. Post-flush는 BCB의 완료 처리를 맡고 프레임을 제안할 수 있습니다. Allocator는 제안을 받을 때 다시 검사해야 합니다. 제안은 재사용 전에 취소될 수 있습니다.

큐에 들어간 flush는 어느 스레드가 마치는가?

BCB 목록에서 flush 대기자만 골라 깨운다

독립적으로 구성한 목록입니다. 같은 BCB에 READ 접근, flush 완료, WRITE 접근을 기다리는 스레드들이 연결돼 있습니다. request_latch_mode는 대기의 종류이며, PGBUF_LATCH_FLUSH는 flush 완료 대기를 나타냅니다. pgbuf_block_bcb()는 일반 요청을 BCB 목록 끝에 연결합니다. Latch 승격 요청은 별도로 맨 앞에 놓습니다.

BCB.next_wait_thrd → READ → FLUSH → WRITE → FLUSH → NULL
BCB.next_wait_thrd → READ → WRITE → NULL

두 번째 줄은 pgbuf_wake_flush_waiters()가 실행된 뒤의 목록입니다. 이 함수는 BCB mutex를 보유한 채 전체 목록을 순회하고, flush 대기 항목만 연결에서 제거합니다. READ·WRITE 대기자는 남습니다. 이들의 접근 권한은 pgbuf_wakeup_reader_writer()가 latch와 fix 수를 부여하는 별도 경로에서 처리합니다.

  1. 제거한 항목마다 pgbuf_wakeup_uncond()를 호출합니다.
  2. 이 함수는 대상 스레드의 th_entry_lock을 잡고 resume_status를 THREAD_PGBUF_RESUMED로 바꾼 뒤 pthread_cond_signal(&thread_p->wakeup_cond)을 호출합니다.
  3. 스레드는 pthread_cond_wait()에서 기다리고 있었습니다. 이 대기는 entry mutex를 잠든 동안 놓고, 반환 전에 다시 획득합니다. Flush 대기 등록 시 entry mutex를 먼저 잡고 BCB mutex를 놓으므로 등록과 잠들기 사이의 깨우기도 이 잠금 절차로 조율합니다.

Post-flush와 제출자의 직접 완료 경로는 같은 flush 대기자 helper를 사용합니다. 깨우기는 대기에서 돌아올 기회를 주며, 그 프레임의 재사용 권한을 주지 않습니다. 일반 I/O 오류 처리도 이 helper를 사용하므로 신호만으로 쓰기 성공이나 저장장치 영속성을 입증할 수 없습니다.

프레임 대기자는 별도 큐에서 꺼내 깨운다

빈 자리와 교체 후보를 찾지 못한 allocator의 대기 경로를 봅니다. pgbuf_allocate_bcb()는 자신의 스레드 레코드를 direct-victim 큐에 produce(thread_p)로 넣고, THREAD_ALLOC_BCB_SUSPENDED 상태로 스레드별 condition variable인 자기 wakeup_cond에서 시간 제한이 있는 대기를 합니다. thread_suspend_timeout_wakeup_and_unlock_entry()가 내부에서 pthread_cond_timedwait()을 호출합니다. 이 allocator는 특정 BCB의 flush 대기 목록에 연결되지 않습니다.

  1. 적격한 BCB를 가진 생산자는 pgbuf_assign_direct_victim()을 호출합니다. 이 함수는 pgbuf_get_thread_waiting_for_direct_victim()으로 큐에서 THREAD_ENTRY *를 consume()합니다. 보통 높은 우선순위 큐를 먼저 보지만, 네 번째 조회마다 낮은 우선순위 큐를 먼저 시도합니다.
  2. 대상 entry를 잠그고 여전히 할당 대기 상태인지 확인합니다. 이미 대기를 끝낸 오래된 항목이면 건너뛰고 다른 요청을 찾습니다.
  3. thread_wakeup_already_had_mutex()로 대상의 condition variable에 신호를 보내고 THREAD_ALLOC_BCB_RESUMED를 기록합니다. 이어 pgbuf_Pool.direct_victims.bcb_victims[waiter_thread->index]에 BCB 포인터를 기록한 뒤 entry mutex를 풉니다.

소스에서는 신호 호출이 포인터 기록보다 앞에 있지만, 깨어난 스레드도 같은 entry mutex를 다시 얻어야 하므로 기록을 마치기 전에 대기에서 반환할 수 없습니다. pgbuf_get_direct_victim()은 자기 슬롯을 원자적으로 비우며 포인터를 가져오고, BCB를 잠가 제안이 취소됐는지와 현재 재사용 조건을 검사합니다. 그 검사에서 거절되면 allocator는 다시 후보를 구합니다.

따라서 flush 대기자를 깨우는 일과 allocator에게 프레임을 제안하는 일은 서로 다른 목록, 상태, 수신 절차를 갖습니다.

큐로 어떤 작업을 넘기는가?

이미지 제출에 성공한 상태에서 이어갑니다. 페이지 바이트는 DWB(double-write buffer, 원래 볼륨에 쓰기 전 사용하는 별도 임시 기록 영역) 또는 직접 쓰기 경로에 들어갔습니다. 프레임의 제어 레코드인 BCB에는 완료 정리가 남아 있습니다. FLUSHING은 그 처리가 남아 있음을 기록하고, flush 대기자는 완료를 기다립니다. Page-flush는 이미지를 제출한 스레드, post-flush는 백그라운드 소비자, allocator는 프레임이 필요한 요청 스레드입니다. LRU3는 교체 후보가 있는 차가운 영역입니다. Private list의 quota는 보유할 페이지 수의 정책 목표입니다. 현재의 영역과 quota는 프레임을 제안할지에 영향을 줍니다.

큐는 PGBUF_BCB * 하나를 전달합니다. 페이지 바이트 없이 프레임의 제어 레코드 주소만 담습니다. Post-flush는 그 레코드를 잠그고 현재 조건을 통과한 프레임을 제안할 수 있습니다. 그 뒤 이전 FLUSHING 상태를 정리하고 flush 대기자를 깨웁니다. 새 페이지 I/O를 시작하지는 않습니다. 풀은 이 큐와 BCB 저장 공간을 소유합니다. 큐에 포인터가 있는 동안 그 레코드는 살아 있어야 합니다. 이전 FLUSHING은 완료 처리가 큐에 남아 있는 동안 일반 victim 경로의 재사용을 막습니다. 8,192개 항목의 용량은 컴파일된 정책이며 운영자가 조절하는 설정이 아닙니다.

풀이 consumer와 대기 작업보다 오래 살아 있어야 합니다. 포인터 자체는 수명 보장이 아닙니다. 이전 FLUSHING은 위임한 완료를 처리할 때까지 일반 victim 재사용도 막습니다.

큐가 가득 차면 누가 완료 처리를 하는가?

Q09 · 완료 큐가 가득 찬 경우

독립적으로 구성한 시작 상태: 페이지 P는 프레임에 있습니다. G는 그 바이트를 안정되게 복사한 이미지이며, 설명용 표기이지 저장된 카운터가 아닙니다. Page-flush는 이 이미지 제출에 성공했습니다. 프레임의 제어 레코드인 BCB에는 아직 FLUSHING=1과 flush 대기자가 남아 있습니다. Post-flush가 존재하고 allocator도 기다리지만 완료 큐가 가득 찼습니다. 삽입에 실패하면 완료 처리 책임은 제출자에게 남습니다.

소비자는 왜 현재 상태를 다시 검사하는가?

이미지 제출 후 BCB 포인터를 큐에 넣는 데 성공했다고 가정합니다. BCB는 주소가 유지되는 제어 레코드이지만, post-flush가 실행되기 전에 페이지의 현재 상태는 달라질 수 있습니다. 각 fix는 호출자가 프레임을 사용하는 동안 재사용되지 않도록 보호합니다. fcnt는 아직 반납하지 않은 fix 수입니다. DIRTY는 보존해야 할 수정 바이트가 남아 있다는 뜻입니다. LRU3는 교체 후보가 있는 차가운 영역이고, private list의 quota는 보유량의 정책 목표입니다.

Post-flush는 포인터를 꺼내고 판단을 보호하는 BCB mutex를 잡습니다. 재사용을 막는 플래그, 현재 fix, BCB에 연결된 대기자 중 하나라도 있으면 배정을 거절합니다. 이 대기자 검사는 연결된 flush 대기자도 보수적으로 포함합니다. 더 뜨거운 영역으로 이동했거나 private list가 더 이상 quota를 초과하지 않아도 거절합니다. 모든 검사를 통과하고 실제 allocator가 계속 기다리면 post-flush는 direct-victim 제안을 게시할 수 있습니다. Allocator가 나중에 유효성을 다시 확인해야 하는 예약입니다.

프레임 제안 여부와 관계없이 소비자는 이전 FLUSHING 상태를 정리하고 flush 대기자를 깨웁니다. 큐가 빌 때까지 항목을 소비합니다. 어느 항목이든 하나를 소비하면 allocator의 프레임 수신 여부와 무관하게 다음 대기를 1 ms로 초기화합니다. Looper의 이전 wake 결과도 대기 증가를 초기화합니다. 유휴 대기는 1, 10, 100 ms를 거쳐 시간 제한 없이 wake만 기다리는 상태로 갑니다. 이 값은 컴파일된 정책이며 완료 기한이 아닙니다. Post-flush만 켜고 끄거나 주기를 정하는 독립적인 공개 설정은 없습니다.

Clean 페이지를 반납하면 allocator가 깨어나는가?

독립적으로 구성한 실행 순서입니다. 모든 프레임(한 페이지용 메모리 슬롯)에 fix가 남아 있어 reader의 사용을 보호하고 있습니다. allocator는 재사용할 프레임을 찾지 못해 잠들었습니다. 이후 reader들이 clean 페이지를 unfix하여 사용을 반납합니다. Clean은 보존할 dirty 작업이 없다는 뜻이고, unfixed는 fix가 하나도 남지 않았다는 뜻입니다. 어느 한 조건만으로 즉시 제안되는 것은 아닙니다.

LRU3는 교체 후보가 있는 차가운 영역입니다. 이 영역의 페이지를 일반 경로에서 마지막으로 unfix하면 보통 승격하거나 세션과 연결된 private list에서 shared list로 옮깁니다. 반납한 페이지가 계속 차가운 후보로 남는 것은 아닙니다. 특정 vacuum worker 경로나 임시 볼륨 경로에서는 LRU3 프레임을 직접 배정할 수 있습니다. Vacuum 경로는 LRU 영역 바깥의 VOID에서도 배정할 수 있습니다. Vacuum은 더 이상 유효하지 않은 데이터베이스 데이터를 정리하는 백그라운드 작업입니다.

영역 조정 중 다른 프레임의 제어 레코드인 BCB가 LRU3으로 들어오면 그 프레임을 제안할 수도 있습니다. 이 경로는 적격성을 검사하고 기다리지 않고 BCB mutex를 잡아 보는 trylock을 시도한 뒤 재검사합니다. Page-flush도 탐색 중 이미 clean인 후보를 제안할 수 있습니다. Post-flush는 flushed_bcbs만 소비하며 reader가 반납한 모든 페이지를 탐색하지는 않습니다. 수정하지 않은 WRITE fix도 원래 페이지가 이미 clean이었다는 조건에서만 이 사례에 해당합니다.

후보 수집과 정렬이 끝나면 page-flush는 각 BCB를 잠그고 저장한 VPID와 현재 식별자를 비교합니다. DIRTY(보존할 수정 바이트), 기존 FLUSHING이 없는지, 현재 사용 여부, 차가운 영역의 적격성도 검사합니다. 그런 다음 로그를 남기는 이 페이지 경로의 WAL 조건을 검사합니다. 복사한 이미지를 복구하는 데 필요한 로그가 페이지를 기록하기 전에 내구성을 확보해야 한다는 조건입니다. 식별자가 같아도 그 사이 새 fix나 flush가 생기거나 더 뜨거운 영역으로 옮겨갈 수 있습니다.

제출에 성공해도 완료 정리는 남습니다. Page-flush는 post-flush 데몬과 allocator 대기자가 있고 큐 삽입이 성공하면 완료 처리를 위임하며, 그렇지 않으면 직접 마칩니다. Post-flush는 현재 적격성을 검사하고 제안을 게시할 수 있으며, 이전 FLUSHING 정리와 대기자 wake를 마칩니다. 이후 allocator가 별도로 보호된 수신 검사를 합니다. 수신에 성공해야 사용할 프레임을 얻습니다. 그 뒤의 victimization도 재사용 전에 이전 페이지 식별자를 제거해야 합니다.

완료 항목이 많아지면 어떤 작업이 늘어나는가?

CPU 작업량과 대기 시간을 구별해서 봅니다. Page-flush의 한 회차는 교체 목록을 탐색하고, 설정에 따라 후보를 정렬하며, 이웃 페이지를 검사할 수 있습니다. Post-flush는 제어 레코드 포인터를 소비하고 오래된 allocator 대기 기록을 건너뛰며 flush 대기자를 깨웁니다. 아래 식은 구조적인 연산 수입니다. Lock 경쟁, 원자 연산 재시도, 스케줄링, 저장장치 지연이 실제 경과 시간에 더해집니다.

탐색 비용에서 T는 합산할 스레드별 카운터 조각 수, L은 방문한 교체 목록 수, K는 검사한 연결 목록 항목 수, C는 정렬할 후보 수, N은 후보마다 검사할 수 있는 이웃 페이지 수입니다. 카운터 읽기, 탐색, 정렬, 이웃 검사를 합치면 명시한 정렬·이웃 경로에서 O(T + L + K + C log C + C·N)의 작업이 필요합니다.

큐 비용에서 Q는 실제 소비한 BCB 완료 항목 수, S는 건너뛴 오래된 allocator 대기 기록 수, W는 처리한 flush 대기자 수입니다. 이 작업은 O(Q + S + W)를 더합니다. 소비 중 생산자가 큐를 다시 채울 수 있으므로 계속 채워지는 큐의 drain 작업량은 큐 용량으로 제한되지 않습니다.

관측한 fcnt=0은 집계된 fix가 없다는 뜻이지만 적격성을 보증하지는 않습니다. pgbuf_is_bcb_fixed_by_any는 대기 사용자도 검사합니다. 제어 레코드 mutex가 실제 결정을 보호합니다. Drain 반복문은 데몬 stop 플래그를 확인하지 않습니다. Stop 요청만으로 시간 상한이나 모든 큐 항목의 drain 완료가 보장되지는 않습니다.

각 fix는 현재 사용을 보호합니다. DIRTY는 unfix 이후에도 보존해야 할 수정 바이트가 남았음을 기록합니다. 차가운 LRU3 영역과 private list의 quota 초과 여부는 보유 정책에 따라 후보를 고르는 조건입니다. 재사용을 막는 플래그와 현재 사용은 페이지 식별자가 같아도 재사용을 막습니다.

차가운 영역·private quota 검사는 보유 정책을 적용합니다. 현재 dirty와 fix·invalid-victim 검사는 남은 작업과 사용자의 권한을 보호합니다. Writer가 떠나 fix가 0이 되어도 그 dirty 바이트는 없어지지 않습니다. 큐의 boolean은 과거 상태를 설명합니다.

후속 질문: 각 검사는 서로 다른 구간을 보호합니다. 하나를 없애려면 그 구간에서 관련 상태가 바뀔 수 없음을 보여야 합니다. 식별자가 같다는 사실만으로는 이를 보장할 수 없습니다.

구별할 관측: 큐 삽입, BCB lock 시 상태, 완료, 제안 게시, 보호된 수신의 시간을 기록합니다. 거절 이유도 따로 기록합니다. 묶어서 집계한 skip 카운터는 개별 조건을 구별하지 못합니다. Q07–Q13과 각각의 독립 trace에 세부 사례가 남아 있습니다.

Q&A · enqueue 때 clean과 unfixed를 함께 저장하면 제안이 안전해지나요?

둘 다 과거 관측입니다. 소비 전에 writer가 사용권을 얻고 dirty 변경을 만들 수 있으며, 나중의 offer도 reader가 무효화할 수 있습니다. 그 사실을 유지하려면 각 관련 구간 전체의 보호가 필요합니다.

완료와 예약을 별도 기록으로 나눌 수 있는가?

이미지를 쓰기 경로가 수락한 상태에서 설명용 설계를 시작합니다. 제출 스레드는 여전히 완료 정리를 해야 하며, allocator는 별도로 재사용할 프레임이 필요합니다. 완료 ticket은 이전 이미지를 식별하고 그 제어 레코드의 수명을 유지합니다. 별도의 재사용 예약은 보호된 현재 상태 검사에 따라 프레임을 확보할 권한을 기록합니다.

  1. 재사용을 거절하더라도 각 완료 ticket은 정확히 한 번 확인하고 처리합니다.
  2. 현재 프레임을 보호된 상태에서 검사한 뒤에만 예약을 발급합니다.
  3. 새 사용은 예약을 취소할 수 있지만 이전 flush 완료까지 취소하지는 않습니다.
  4. 수신자는 유효한 예약을 원자적으로 소비하거나 재시도합니다. 취소·종료 시 ticket을 정리한 뒤 저장 공간을 회수합니다.

이는 대안 설계의 요구 사항이며 고정 리비전의 큐가 보장하는 성질은 아닙니다. 이미지·예약의 추가 식별자와 수명 관리가 오래된 기록을 권한으로 오해하지 않게 합니다. 연속 예약은 새 사용을 막는 대신 경쟁 비용이 달라집니다. 실제 큐가 가득 찬 경로도 이미 직접 완료 처리를 하므로 이 데몬 없이 완료의 정확성을 유지할 수 있습니다.

Q&A · 완료 처리와 reservation 취소를 분리하는 이유는 무엇인가요?

재사용 허가를 취소해도 성공한 이미지 제출이 되돌아가지는 않습니다. 기록을 나누면 이전 완료는 정확히 한 번 처리하면서 stale하거나 부적절한 재사용 예약은 거부할 수 있습니다.

완료 처리와 배정을 어떤 관측으로 구별할 수 있는가?

아직 실행하지 않은 실험 제안입니다. P는 프레임에 있는 페이지이고, G는 성공적으로 제출한 안정된 이미지의 설명용 표기이며 저장된 카운터가 아닙니다. Allocator가 프레임을 기다립니다. 큐가 가득 찬 경우, 소비 전 새 dirty 수정이 생긴 경우, 제안 후 reader가 fix한 경우마다 이 시작 상태를 독립적으로 복원합니다. 하나의 연속 실행으로 합치지 않습니다.

전체 고정 리비전, 빌드, 풀·로그 설정, DWB(double-write buffer)와 I/O 경로, workload를 기록합니다. 상세 카운터를 해석하려면 먼저 통계 수집을 활성화하고 시작 시 extended_statistics_activation 마스크를 설정해야 합니다. 마스크는 초기화 때 캐시됩니다. 기본값 15에는 페이지 버퍼 victimization 비트 16과 데몬 비트 64가 없습니다. 이 카운터는 프레임별 인과 이력을 제공하지 않습니다.

가설
완료 처리를 마쳐도 allocator가 프레임을 받지 못할 수 있습니다. 배정 실패와 완료 실패는 조사할 원인이 서로 다릅니다.
통제하는 변화
이미지 제출 성공을 유지합니다. 독립적으로 초기화한 실행 순서마다 큐 가득 참, 새 dirty 수정, 나중의 fix 중 해당 사건만 바꿉니다.
정확한 관측
활성화 조건을 갖추면 생산자별 배정 카운터를 사용할 수 있습니다. 추가로 제안하는 probe는 BCB와 식별자별로 큐 삽입·소비, 이전 FLUSHING 해제, 거절 이유, 제안 게시·취소, 보호된 수신 결과를 연결합니다.
반증 기준과 한계
소비자가 일반적인 배정 거절 뒤 정상 반환했는데 이전 FLUSHING이 남아 있다면 완료 처리 주장이 반증됩니다. 큐에 항목이 있거나 배정 횟수가 있다는 사실만으로 수신 성공을 입증할 수는 없습니다. Probe 비용도 기록해야 합니다. Lock 아래의 기록 작업은 실행 순서를 바꿀 수 있습니다.
