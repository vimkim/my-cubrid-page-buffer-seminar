아직 무엇이 막혀 있는가?

풀은 여전히 가득 차 있습니다. 바이트 전달, BCB 상태 정리, 보존 정책 조정, write 속도 조절은 서로 다른 결과를 만듭니다. 네 역할의 분리는 하나의 구현 정책입니다. Worker를 합치는 대안에서도 필요한 의무는 남습니다. Wake는 재검사를 요청하고 실제 작업은 공유 조건과 queue에 남습니다.

알림은 보존된 작업이 아닙니다. Stop은 취소나 join 완료가 아닙니다. 공유 작업을 다시 발견할 수 있어야 하고 모든 worker의 접근이 끝난 뒤 자원을 회수해야 합니다.

고정 리비전의 전이

여기서 보존되는 작업은 wake 이후 작업이 검사할 때까지 공유 RAM에 남는 상태입니다. Crash 뒤에도 남는 저장장치 영속화를 뜻하지는 않습니다.

요청을 처리하는 thread가 전부 하면 안 될까?

할 수는 있습니다. 다만 S3를 읽는 경로에 S4의 변경 내용 기록까지 붙으면, S3의 요청은 자기 페이지를 읽기 전에 다른 페이지의 정리 비용도 부담합니다. 이런 일이 반복될 때 후보를 미리 준비하는 별도 thread가 도움이 됩니다. 얼마나 빨라지는지는 부하와 I/O 상황에 달려 있습니다.

  1. 요청 시점에 준비: S3 요청 → 자리 부족 확인 → S4 기록 처리 → 재사용 가능 여부 확인 → S3 읽기.
  2. 미리 준비된 후보가 있다면: 별도 thread가 S4 기록 처리 → 나중에 S3 요청 → 안전 조건 재확인 → frame 재사용.

이런 일을 맡아 반복해서 작업하고 기다리는 background thread를 여기서는 daemon이라고 부릅니다. DB 서버 안의 thread이며 별도 서버 process가 아닙니다. 요청 thread를 foreground라고 부르면, background는 요청 처리와 별도로 진행하는 실행 역할입니다.

Post-flush와 flush-control은 페이지를 다시 쓰지 않는다

File-I/O token bucket: 여러 writer가 공유하는 page 단위 credit 잔액입니다. 참여하는 writer는 OS write가 성공한 뒤 credit을 소비하고, 잔액이 없으면 계속 진행하기 전에 잠시 기다릴 수 있습니다. Flush-control은 주기적으로 잔액을 교체하므로 write 수행 허가가 아니라 soft pacing입니다. 정확한 producer, consumer, bypass rule 보기 →

각 daemon은 독립적으로 일하고 기다린다

네 daemon은 서로 다른 역할을 가진 background thread입니다. Timer나 wakeup은 실행 기회이고, 실제 작업 여부는 현재 상태를 확인한 뒤 결정합니다.

create_daemon()은 managed execution context 하나와 std::thread 하나를 만듭니다. loop는 간단합니다. task를 실행하고, cubthread::looper에게 pause 시간을 물은 뒤, 다시 task를 실행합니다. 따라서 네 이름은 하나의 dirty-page queue에서 같은 일을 꺼내는 worker가 아니라 서로 독립적인 control loop입니다.

task는 생성 직후 한 번 실행됩니다. fixed period는 start-to-start 목표입니다. looper가 직전 task 실행 시간을 빼므로 100 ms 주기가 “작업을 끝낸 뒤 항상 100 ms를 더 sleep한다”는 뜻도, 매번 유용한 작업을 한다는 보장도 아닙니다.

구성한 시작 상태: Page-flush의 타이머 주기는 0입니다. Recovery 중 실행된 작업은 닫힌 boot gate를 보고 반환했습니다. 다음 대기에 들어가기 직전 waiter는 아직 RUNNING입니다. 이때 gate가 열리고 다른 thread가 wakeup을 호출한 뒤 daemon이 대기에 들어갑니다. 이후 신호는 아직 기록되지 않았습니다.

RUNNING 중 wakeup은 다음 대기를 위해 저장되지 않습니다. 주기가 0이면 gate가 열린 사실만으로 timeout이나 자동 wake가 생기지 않습니다. 이후 SLEEPING 상태에서 받아들인 wake 또는 소스로 확인한 다른 대기 종료 사건이 필요합니다. 유한 타이머는 다음 검사 기회를 주며, flush 완료를 보장하지는 않습니다.

복구가 끝난 뒤 작업하고, pool보다 먼저 종료한다

서버는 복구 중에 thread를 만들지만 boot gate가 열리기 전에는 page-buffer 작업을 하지 않습니다. 정상 종료에서는 pool을 정리하기 전에 daemon을 멈춥니다. Stand-alone mode에서는 이 네 thread를 만들지 않습니다.

  1. 먼저 page-buffer pool, LRU, queue, monitor를 초기화합니다.
  2. server boot는 log recovery가 끝나기 전에 네 daemon thread를 만듭니다.
  3. 생성 직후 task는 boot gate가 닫힌 것을 보고 page-buffer의 유용한 작업 없이 반환합니다.
  4. recovery 뒤 boot가 gate를 엽니다. gate를 여는 동작 자체가 모든 sleeper를 wake하지는 않습니다. 이후 timer 또는 normal work wake에서 열린 gate를 관찰합니다.
  5. 정상 shutdown은 looper stop flag를 set하고 sleeper를 깨운 뒤 OS thread를 join하고 task/context를 retire하며 pointer를 비웁니다.
  6. log_final()과 pool teardown은 daemon이 모두 멈춘 뒤 실행되므로 shared state보다 오래 사는 daemon은 없습니다.

stand-alone mode에서는 이 네 thread를 만들지 않습니다. background page-flush가 없으면 관련 requester가 victim flushing을 동기적으로 수행할 수 있습니다.

자원을 해제하기 전에 thread의 join이 끝나야 합니다

Pool 구조가 daemon보다 먼저 존재합니다. Thread는 로그 복구 중에도 실행할 수 있지만 각 task는 먼저 boot gate를 검사합니다. Gate 활성화 자체가 모든 역할을 깨우지는 않습니다. Gate를 제거하면 복구 중 task가 공유 상태에 접근할 수 있습니다. 실패는 복구가 바꾸는 상태와의 충돌 조건에 달려 있으며 thread 존재 자체가 실패는 아닙니다.

종료는 stop 설정, sleeper wake, join, context·task 정리 순서입니다. 실행 중 task가 I/O에 있다면 stop은 I/O를 취소하지 않습니다. Sleeper를 깨우지 않으면 join이 진행되지 않을 수 있습니다. Stop만 설정하고 join 전에 pool을 해제하면 실행 중 task와 수명 경쟁이 생길 수 있습니다.

stop/wake/join · 복구와 gate · 종료 순서. 소스만으로 join 시간 상한을 증명할 수 없습니다.

D26 · 50 ms timer면 writer 완료를 보장할까요?

Caller가 300 ms stall을 보고했습니다. Control daemon의 명목 주기는 50 ms입니다. 반드시 여섯 번의 유효 갱신이 끝났을까요? Reviewer는 timer tick마다 writer 완료 하나를 보장한다고 해석하려 합니다.

반박을 검토한 뒤 제한된 답 보기

그렇지 않습니다. Gate, task 실행, scheduling, condition mutex, writer 경쟁이 남습니다. 갱신은 allowance를 게시하며 writer 완료를 게시하지 않습니다. 유효 진행에는 writer가 실행되고 공유 상태를 얻는 조건도 필요합니다.

후속 질문: “그럼 timer는 왜 필요합니까?” 이 역할은 producer의 알림 없이도 다음 실행 기회를 얻습니다. 다른 의존 조건까지 없애지는 않습니다.

구별할 관측: Gate, waiter 상태, task 시작·종료, 생성 allowance, writer의 condition 반환, 현재 수요를 기록합니다. Wake 횟수만으로는 작업 누락과 오래 실행 중인 task를 구분하지 못합니다. 기존 Q04–Q06의 수명 질문도 유지합니다.

일관된 대안: 하나의 nonblocking 작업 scheduler

설명용 대안입니다. 명시한 성질을 보존하며 actor의 조정 방식을 바꿉니다.

  1. 각 역할에 일시적인 wake bit 대신 보존되는 pending 상태를 둡니다.
  2. 준비된 작업을 고르고 느린 I/O 전에 continuation을 보존합니다.
  3. I/O 완료를 처리하면서 quota와 pacing 작업도 진행시킵니다.
  4. 종료 시 producer를 닫고 규칙에 따라 continuation을 완료하거나 취소한 뒤 join하고 공유 상태를 해제합니다.

설명용 대안입니다. Foreground 처리는 지연을 caller로 옮기며 blocking 통합 worker는 네 지연을 연결합니다. Nonblocking 대안에는 queue, continuation, 취소 소유권, scheduling 정책이 추가됩니다. I/O와 공정성 가정 없이 처리 시간 상한은 나오지 않습니다.

어떤 관측으로 이 설명을 반증할 수 있는가?

아직 실행하지 않은 실험 제안입니다. 결과 해석 전에 전체 고정 리비전, build, pool·log·DWB·I/O 설정과 workload를 기록합니다.

가설
명시한 wake·timer 순서에서 보존된 작업을 다시 발견한다는 가설입니다.
통제하는 변화
page_bg_flush_interval=0과 하나의 producer를 사용합니다. Sleep 직전에 멈추고 한 번 공개한 뒤 RUNNING 동안 wake하고 멈춤을 해제합니다. Post-flush terminal backoff는 별도로 검사합니다.
정확한 관측
기존 framework 통계로 loop·wake·sleep을 찾습니다. 추가 시각 기록으로 작업 공개, waiter 상태, 작업 진입, 조건을 연결합니다. Wake 횟수만으로는 부족합니다.
반증 기준과 한계
이 전제에서 pending 작업을 다시 발견할 경로가 기록되지 않으면 제안한 진행 논증에 반례가 됩니다. Scheduler 멈춤은 timing에 영향을 주며 유한 관찰만으로 영구 starvation을 증명하지는 못합니다.
