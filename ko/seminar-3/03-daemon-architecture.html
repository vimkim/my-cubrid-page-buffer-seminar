CUBRID 페이지 버퍼 데몬과 PostgreSQL 페이지 교체

자주 다시 쓰는 페이지, 대량 스캔, 변경된 페이지가 유한한 풀을 채웁니다. 각 구성 예제의 실행 순서는 독립적으로 시작합니다. 성능 설명은 소스에 근거한 추론이며 측정 결과가 아닙니다.

읽을 페이지는 있는데 담을 빈자리가 없다

새로 시작하는 예제: 데이터베이스는 데이터를 일정 크기의 묶음인 페이지로 다룹니다. 요청을 처리하는 실행 흐름을 요청 스레드라고 하겠습니다. 이 스레드가 페이지를 차례로 읽습니다. 서버는 페이지를 메모리에 모아 두는데, 이 공간을 페이지 버퍼 풀이라고 합니다. 페이지 한 장을 담는 자리인 프레임은 모두 차 있습니다.

S3는 다음에 읽을 페이지의 이름이며 아직 메모리에 없습니다. S4는 프레임 하나를 차지한 다른 페이지입니다. 지금은 아무도 사용하지 않지만, 메모리에서 변경한 내용을 아직 기록해야 합니다. 이런 상태를 dirty라고 합니다.

여기서 ‘가득 참’은 예제의 모든 프레임이 차 있다는 뜻입니다. 풀 초기화 때 프레임 수를 정하며, 등록된 기본값은 32,768페이지입니다. 10 × MAX_NTRANS보다 작으면 그 값으로 올립니다. 여기서 MAX_NTRANS = css_get_max_conn() + 1은 연결 슬롯 수에 시스템 트랜잭션 항목 하나를 더한 값입니다. 이렇게 정한 num_buffers는 이 풀을 사용하는 동안 고정되며, 관리 레코드에는 별도 메모리가 필요합니다.

등록된 페이지 수 기본값 · 초기화와 최솟값 · 최솟값 계산식 · 트랜잭션 항목 수.

S3를 담으려고 S4의 자리를 바로 덮어쓰면 변경 내용을 잃습니다. 먼저 안전한 기록 경로로 변경 내용을 보존한 뒤, 그 자리를 지금도 재사용해도 되는지 확인해야 합니다. 이 준비를 요청보다 먼저 해 두는 것이 백그라운드 작업의 한 가지 목적입니다.

기록할 사본을 보내는 일, 관리 상태를 마무리하는 일, 메모리에 남겨 둘 양을 조정하는 일, 기록 속도를 조절하는 일은 각각 다른 책임입니다.

Q&A · 모든 페이지가 네 스레드를 차례로 거치나요?

아니요. page-flush는 기록할 사본을 보내고, post-flush는 일부 프레임 관리 레코드(BCB)의 정리 작업을 넘겨받습니다. maintenance와 flush-control은 보존량과 기록 속도 정책을 조정합니다. 네 역할은 페이지의 네 처리 단계가 아닙니다.

03 · 2 / 36

요청이 오기 전에 준비하면 요청이 할 일이 줄어든다

두 실행 순서는 같은 상태에서 시작합니다. S3는 요청이 읽어야 하지만 메모리에 없는 페이지입니다. S4는 아무도 사용하지 않는 메모리의 페이지이며, 변경 내용을 아직 기록해야 합니다. 빈 프레임은 없습니다.

요청 스레드가 직접 준비하면 요청이 온 뒤 기록을 기다려야 합니다. 서버 안의 다른 스레드가 미리 준비하면 그 비용을 앞당길 수 있습니다. 요청을 처리하는 쪽을 포그라운드, 별도로 준비하는 쪽을 백그라운드라고 합니다. 여기서 데몬은 백그라운드에서 작업과 대기를 반복하는 서버 내부 스레드입니다.

두 순서 모두 마지막에 현재 재사용 조건을 확인합니다. 미리 준비한 뒤 다른 요청이 페이지를 다시 쓰거나 사용하기 시작할 수 있기 때문입니다. 필요한 순간에도 후보가 적절해야 요청의 일이 줄어듭니다. 실제 성능 이점은 부하와 기록 지연에 따라 달라집니다.

Q&A · 미리 준비한 프레임을 요청이 못 쓸 수도 있나요?

네. 준비 후 다른 요청이 페이지를 변경하거나 사용하기 시작할 수 있습니다. 이전 기록을 했어도 지금 프레임을 재사용해도 되는지는 다시 확인해야 합니다.

03 · 3 / 36

기록을 기다리는 동안 다른 관리 작업도 해야 한다

한 스레드에 모두 맡긴다고 가정해 봅시다. 이 스레드가 페이지를 기록하고, 관리 상태를 마무리하고, 메모리 보존량과 기록 속도도 조정합니다. 느린 로그나 페이지 기록을 기다리면, 그동안 나머지 일도 시작할 수 없습니다. 이런 입출력을 I/O라고 합니다.

CUBRID는 네 종류의 일을 서로 다른 백그라운드 스레드에 맡깁니다. 각 스레드가 반복해서 실행할 일을 태스크(task)라고 합니다. 한 스레드가 기록을 기다리는 동안 다른 스레드는 자기 태스크를 실행할 수 있습니다.

네 스레드가 모든 페이지를 차례로 처리하는 것은 아닙니다. 페이지 사본을 보내는 역할은 page-flush입니다. 나머지는 관리 상태나 정책을 다룹니다. 스레드를 나누어도 CPU, 잠금, 저장장치를 두고 경쟁할 수 있으므로 성능 향상은 측정해야 합니다. 기록 대기 중에도 다른 일을 실행할 수 있게 설계한다면 스레드 하나도 대안이 될 수 있습니다.

Q&A · 스레드가 네 개면 서로 기다리지 않나요?

여전히 기다릴 수 있습니다. 한 스레드의 기록 대기가 다른 세 작업의 실행을 직접 막지는 않지만, 같은 잠금이나 CPU, 저장장치를 기다릴 수 있습니다. 실제 지연은 측정해야 합니다.

03 · 4 / 36

네 스레드가 맡은 일을 구체적으로 나누어 보자

기록할 페이지부터 봅시다. S4는 메모리에 있고 아무도 사용하지 않지만 변경 내용을 아직 기록해야 하는 페이지입니다. 프레임마다 현재 페이지와 사용 상태, 기록 상태를 추적하는 관리 레코드가 있습니다. 이것을 BCB(Buffer Control Block)라고 합니다.

Page-flush

기록할 사본 보내기

페이지 상태를 확인하고 안정된 사본을 만듭니다. 필요한 로그를 먼저 보존한 뒤 사본을 기록 경로에 보냅니다. 보내는 데 성공해도 프레임 재사용에는 별도 확인이 필요합니다.

Post-flush

남은 관리 작업 맡기

일부 기록의 뒷정리를 넘겨받습니다. BCB를 잠그고 상태를 다시 확인한 뒤 이전 기록의 진행 표시를 정리하고 기다리던 스레드를 깨웁니다. 조건이 맞으면 프레임을 기다리는 요청에 제안합니다.

Maintenance

LRU의 보존 목표 조정하기

사용 활동을 보고 세션과 연결된 교체 목록인 private LRU의 보존 목표 페이지 수(quota)를 조정합니다. Private LRU와 공통 교체 목록인 shared LRU에서는 보존 우선순위가 다른 구역(zone)의 목표 크기를 조정합니다. 버퍼 풀의 전체 프레임 수는 바꾸지 않으며, 페이지 사본을 기록하지도 않습니다.

Flush-control

기록 스레드의 계속 진행 속도 조절하기

페이지 수로 계산하는 속도 조절 잔액을 새 값으로 교체합니다. 이 방식에 참여하는 스레드는 OS 기록이 성공한 뒤 잔액을 소비하고, 부족하면 다음 작업 전에 기다릴 수 있습니다.

Q&A · page-flush가 기록했으면 그 자리를 바로 쓸 수 있나요?

현재 사용자와 페이지 상태를 다시 확인해야 합니다. 기록은 변경 내용 보존을 처리하고, 완료 처리는 관리 레코드를 갱신합니다. 그 사이 새 사용이나 변경이 생겼을 수 있습니다.

03 · 5 / 36

페이지 사본을 보내는 일과 관리 상태를 정리하는 일은 다르다

페이지 사본을 보낸 뒤에도 할 일이 남습니다. 프레임의 관리 레코드인 BCB에서 이전 기록의 진행 표시를 정리하고, 그 기록을 기다리던 스레드들을 깨워야 합니다. page-flush가 직접 처리하거나 일부를 post-flush에 넘깁니다.

넘길 때는 flushed_bcbs라는 완료 처리 대기 목록에 BCB의 주소를 넣습니다. 항목을 넣고 꺼내는 이런 자료구조를 큐(queue)라고 합니다. post-flush는 주소를 꺼내 그 BCB를 정리합니다. 목록에는 페이지 데이터 사본이 들어가지 않습니다.

완료 큐에는 슬롯이 8,192개 있습니다. 컴파일된 상수 PGBUF_FLUSHED_BCBS_BUFFER_SIZE = 8 × 1024에서 정한 용량이며, 설정으로 바꾸는 기본값이 아닙니다. 포인터 삽입이 거절되면 제출한 스레드가 그 BCB를 직접 정리합니다. 동시 실행에서는 슬롯의 예약과 게시 상태도 ‘가득 참’의 의미에 영향을 줍니다. 정확한 큐 경계와 직접 처리 조건에서 이어 봅니다. 상수 · 큐 생성 · 인계 또는 직접 처리.

Q&A · post-flush에 페이지 데이터도 넘기나요?

아니요. 완료 처리 목록에는 BCB 주소가 들어갑니다. post-flush는 그 주소로 관리 레코드를 확인하고 정리하며 새로운 페이지 기록을 시작하지 않습니다.

깨어나면 먼저 지금 할 일이 있는지 확인한다

기다리는 스레드를 다시 실행시키는 방법은 두 가지입니다. 정해 둔 시간이 지나 대기를 끝내는 것이 타이머이고, 다른 스레드가 대기를 일찍 끝내 달라고 요청하는 것이 깨우기입니다. 둘 다 작업을 확인할 기회를 줍니다.

실행을 시작해도 일을 못 할 수 있습니다. 서버 복구가 끝나기 전에는 페이지 버퍼를 건드리지 못하도록 허용 여부를 나타내는 플래그를 확인합니다. 이 플래그를 부팅 게이트라고 부릅니다. 열린 뒤에도 maintenance는 재계산 시점인지, post-flush는 대기 목록에 항목이 있는지 확인합니다. flush-control의 첫 허용된 실행은 기준 시각만 기록합니다.

그림의 점은 작업을 시도할 시점을 나타냅니다. 점 하나를 기록 완료 한 번으로 세면 안 됩니다. Post-flush의 유휴 대기는 1 → 10 → 100 ms → 타이머 없음 순서로 늘어납니다. 항목을 하나 이상 꺼내면 다음 목표를 1 ms로 되돌립니다. 직전 대기가 true를 반환해도 looper가 순서를 되돌립니다. 수락된 깨우기뿐 아니라, 작업이 목표 주기를 다 써서 계산된 대기가 0인 경우도 해당합니다. 어느 경우도 페이지 기록 완료 횟수는 아닙니다. 유휴 대기와 초기화 조건 →

Q&A · 깨어났는데도 아무 일 없이 반환할 수 있나요?

네. 복구가 끝나지 않았거나, 대기 목록이 비었거나, 정책의 재계산 시점이 아닐 수 있습니다. 실행 기회를 얻는 것과 유효한 작업을 하는 것은 다릅니다.

각 스레드는 필요한 시점에 다시 확인한다

완료 처리 스레드가 할 일 없이 기다리고 있습니다. page-flush가 관리 레코드인 BCB의 주소를 flushed_bcbs 대기 목록에 넣으면 post-flush를 깨웁니다. 다른 역할들은 자기 타이머나 요청의 신호를 사용합니다.

표의 시간은 반복 실행의 시작과 다음 시작 사이의 목표 주기입니다. 실제 대기 시간은 이전 작업 시간을 뺀 값이고, CPU를 배정받거나 잠금·I/O를 기다리면 더 늦어질 수 있습니다. 깨우기 전용 대기에는 시간을 재서 대기를 끝내는 타이머가 없습니다.

설정 가능한 Page-flush 주기는 다른 역할들의 컴파일된 대기 주기와 다릅니다.

주기의 경계: 설정 내부 값은 0 이상인 정수 밀리초이며 기본값은 1,000 ms입니다. 등록된 최솟값은 0이고, 정수 저장 범위 외에 별도 최댓값은 없습니다. 0이면 무한 대기, 양수이면 max(0, period − task time)만큼 기다립니다. Page-flush는 대기할 때마다 현재 값을 읽으므로 수락된 설정 변경은 다음 대기부터 반영됩니다. 풀 크기를 바꾸거나 이미 진행 중인 대기를 끝내지는 않습니다. Post-flush의 세 타이머 목표에도 같은 시간 차감이 적용됩니다. 설정 등록 · 대기 시 값 읽기 · 대기 시간 계산.

  3. 재사용할 프레임을 기다리는 allocator 요청이 있습니다.

깨우기 요청이 지나가도 처리할 대상은 목록에 남는다

page-flush가 뒷정리를 넘기는 경우를 봅시다. 기록 경로에 페이지 사본을 보내는 데 성공했습니다. 이제 프레임의 관리 레코드인 BCB에서 기록 상태를 정리해야 합니다. 이 일을 post-flush에 맡길 때 다음 순서로 전달합니다.

  1. page-flush가 flushed_bcbs 목록에 BCB의 주소(포인터)를 넣습니다. 페이지 데이터나 새로운 기록 요청을 넣는 것이 아닙니다.
  2. 그 뒤 post-flush에 wakeup()으로 깨우기를 요청합니다. 아직 실행 중이라면 이 요청은 다음 대기를 위해 저장되지 않습니다.
  3. post-flush가 목록을 확인할 때 BCB 주소를 꺼내 남은 관리 작업을 합니다. 그러므로 처리 대상을 찾는 근거는 깨우기 횟수가 아니라 목록의 항목입니다.

이 목록이 큐입니다. 넣는 page-flush를 생산자, 꺼내 처리하는 post-flush를 소비자라고 부릅니다. 두 스레드가 같은 목록을 읽고 써야 하므로 같은 서버 프로세스 안의 메모리에 둡니다. 여기서 ‘공유’는 여러 스레드가 함께 사용한다는 뜻이며 OS의 프로세스 간 shared memory(IPC) 기능을 뜻하지 않습니다.

항목이 남는 것과 처리가 진행되는 것은 별개입니다. 항목은 꺼낼 때까지 RAM에 남지만 장애 후 복구되는 기록은 아닙니다. 처리하려면 스레드가 다시 목록을 확인해야 합니다. 특히 타이머 없이 기다리면 나중에 수락된 깨우기나 다른 대기 종료 사건이 필요할 수 있습니다. 목록만으로 즉시 처리나 처리 기한은 보장하지 않습니다.

탐색의 시작점: BCB는 메모리에 있는 프레임 하나를 관리하고, dirty는 변경 내용을 아직 기록해야 한다는 뜻입니다. 각 LRU는 링크로 이어진 교체 목록입니다. LRU3는 꼬리에 있는, 보호가 가장 약한 차가운 구역입니다. 한 번의 후보 수집에서 살펴볼 BCB 개수를 정합니다.

  1. 어느 리스트를 얼마나 볼지 정합니다. 리스트 크기와 quota(보존할 몫)를 읽어 LRU마다 방문량을 나눌 가중치인 탐색 비중을 계산합니다. 리스트 배열을 인덱스 순서로, shared 다음 private 순서로 봅니다. 비중이 0이면 건너뜁니다. 비중이 크면 더 많이 살펴보지만, 순서를 앞당기지는 않습니다.
  2. 한 리스트의 링크를 따라갑니다. 그 LRU를 잠그고 bottom에서 시작해 prev_BCB를 따라 머리 쪽으로 올라갑니다. 배정된 개수를 다 보거나, 리스트가 끝나거나, LRU3 밖의 BCB를 만나면 멈춥니다. 잠금을 풀고 다음 리스트로 갑니다.
  3. Dirty 후보를 모읍니다. Clean BCB도 방문 개수에 포함됩니다. Dirty BCB를 만나면 포인터와 페이지 식별자를 임시 후보 배열에 저장합니다.
  4. 쓰기 전에 다시 검사합니다. 나중에 저장한 BCB를 하나씩 잠급니다. 페이지 식별자가 바뀌었거나, 이미 clean이거나 flush 중이거나, LRU3를 벗어났거나, 다른 스레드가 사용 중이면 건너뜁니다. 페이지 제출 전에 필요한 WAL이 영속화되어 있어야 합니다.

작은 구성 예시: 꼬리부터 clean → dirty이지만 사용 중 → dirty이고 미사용인 BCB가 이어져 있고, 모두 LRU3라고 합시다. 방문 개수가 2이고 도중에 상태가 바뀌지 않으면 앞의 두 개만 봅니다. 두 번째는 후보에 넣지만 사용 여부 재검사에서 탈락합니다. 세 번째는 이번 탐색 범위 밖입니다.

다음 탐색과 별도 전체 flush는 어떻게 다른가요?

검사량 계산과 반복 범위는 다음 검사량 화면에서 봅니다. 다음 수집도 리스트 꼬리에서 시작하며, BCB 배열의 마지막 위치를 기억해 이어가지 않습니다. 선택적 이웃 묶음 쓰기는 가까운 페이지 식별자를 resident hash에서 찾습니다. 별도의 pgbuf_flush_all_helper()는 num_buffers 전체를 반복하는 명시적 flush 경로입니다.

탐색 비중이 0이면 이번에는 그 리스트의 BCB를 보지 않는다

탐색 비중은 이번 page-flush 후보 수집에서 리스트마다 BCB 방문량을 나누는 가중치입니다. 소스의 lru_victim_flush_priority_per_lru에 저장합니다. 0이면 그 리스트의 잠금을 잡고 BCB 링크를 따라가는 단계를 건너뜁니다. 비중을 계산하기 위한 리스트 통계는 읽습니다.

Private 리스트의 일반 계산: quota는 보존 목표, LRU3는 차가운 후보 구역입니다. 전체 리스트 크기에서 quota의 90%를 정수로 바꾼 값을 뺀 뒤, LRU3 개수와 비교해 더 작은 값을 택합니다. 소스는 이 수를 this_prv_target으로 부릅니다. 양수인 목표들에 private 전체 탐색 몫을 비례 배분합니다.

this_prv_target = min(리스트 크기 − int(quota × 0.9), LRU3 개수)

quota 100, 크기 100, LRU3 5min(100 − 90, 5) = 5Private 전체 몫이 양수이면 배정
quota 100, 크기 130, LRU3 30min(130 − 90, 30) = 30배분 목표가 앞 예제의 6배; private 몫이 양수이면 배정
quota 100, 크기 130, LRU3 0min(130 − 90, 0) = 0차가운 구역이 없어 비중 0

위 예제는 각 계산을 따로 보여 주며, 모두 같은 서버에서 관측한 상태가 아닙니다. Shared 리스트에는 shared 전체 탐색 몫을 균등하게 나눕니다. 그 전체 몫이 0이면 shared의 비중도 0입니다. 소스에는 일반 계산 대신 private LRU3 크기를 쓰는 예외적인 백업 분기도 있습니다.

비중 0은 dirty 페이지가 없다는 뜻이 아닙니다. 정책상 이번 후보 탐색에서 제외했다는 뜻입니다. 다음 수집에서 크기와 quota가 바뀌면 다시 배정될 수 있습니다. 설정 data_buffer_flush_ratio를 0으로 지정한다는 뜻도 아닙니다. 그 설정의 허용 범위는 0.01–0.95입니다.

한 번의 후보 수집에는 상한이 있지만 데몬 실행 전체에는 횟수 상한이 없다

BCB는 프레임 하나의 관리 레코드이고, LRU3는 리스트 꼬리의 차가운 구역입니다. 여기서 후보 수집 한 번은 pgbuf_flush_victim_candidates() 호출 한 번 안에서 수행하는 링크 탐색을 뜻합니다. 기본 검사량인 check_count_lru를 먼저 계산합니다.

  1. 풀의 프레임 수 × data_buffer_flush_ratio의 양수 곱에서 소수 부분을 버려 정수로 바꿉니다. 이 숨김 설정의 기본 비율은 0.01이고, 양 끝을 포함한 0.01–0.95를 허용합니다. 후보 수집 호출마다 현재 값을 읽습니다.
  2. 그 정수에 압력 보정 배수를 곱하고 다시 소수 부분을 버립니다. Checkpoint 밖의 컴파일된 배수 계산식은 min(10, max(1, 1 + 9 × sampled miss rate))입니다. 표본 miss 비율은 fix 요청 수 > victim 요청 수일 때만 victim 요청 수 ÷ fix 요청 수로 계산하고, 그 외에는 0입니다. Checkpoint 중에는 배수를 1로 고정합니다.
  3. 정수 나눗셈 200 × 1024 × 1024 / DB_PAGESIZE와 비교해 더 작은 기본 검사량을 택합니다. DB_PAGESIZE는 페이지 바이트 수입니다. 16 KiB 페이지라면 기본 검사량 상한은 12,800입니다. 이는 BCB 개수 계산을 위한 환산이며, 반드시 200 MiB를 쓴다는 뜻은 아닙니다.

리스트별 검사량 check_count_this_lru는 기본 검사량 × 해당 가중치 ÷ 가중치 합을 정수로 바꾼 값이며, 양수 가중치 리스트에는 최소 1개를 배정합니다. 기본 검사량이나 가중치 합이 0이면 링크 탐색 자체를 하지 않습니다.

전체 방문량의 정확한 예산 상한은 리스트별 배정량의 합입니다. 이상적인 비례 계산에서는 기본 검사량 + 양수 가중치 리스트 수 이내로 보수적으로 잡을 수 있습니다. 실제 정수 배정은 float 계산을 거치므로 정확한 개수는 각 배정량을 더해 구합니다. 상태가 고정된 예제에서는 각 리스트의 LRU3 크기와 배정량 중 작은 값들을 더합니다. 동시 실행 중에는 리스트 사이 이동 때문에 같은 BCB를 다시 만날 수도 있습니다.

데몬 태스크는 압력이 지속되는 동안 이 수집·제출을 반복할 수 있습니다. 한 번의 execute()에 고정된 반복 횟수나 밀리초 제한은 없습니다. 한 번의 수집 상한을 데몬 전체의 상한으로 읽으면 안 됩니다. 요청 스레드의 별도 victim 탐색에 있는 1,000개 제한도 여기에 적용되지 않습니다.

‘압력이 지속됨’에도 정확한 검사 조건이 있습니다. 프레임 대기 큐 하나라도 비어 있지 않거나, 표본 victim 요청 수 > 10과 victim requests × 1000 > fix requests를 모두 만족하면 반복합니다. 두 비교 중 하나라도 같으면 낮은 hit 비율 분기는 성립하지 않습니다. 수락된 깨우기는 이 조건이 거짓이어도 최소 한 번 호출하게 하며, 계산된 대기가 0이어도 looper의 깨우기 플래그가 설정됩니다. 기본 검사량과 가중치 합이 모두 양수인데 dirty 후보를 하나도 얻지 못하면 stop 힌트를 설정해 압력이 남아도 반복을 끝냅니다. 카운터는 관측값이며 정확성이나 지연 시간을 보장하는 조건은 아닙니다. 압력과 반복 종료 규칙 →

Maintenance는 리스트 통계를 읽고 구역 경계를 조정한다

탐색의 시작점: 각 private/shared LRU는 활동 통계와 구역별 개수를 가진 연결 리스트입니다. Quota는 private 리스트가 보존할 몫의 목표입니다. LRU1/LRU2는 더 보호하는 구역, LRU3는 차가운 구역입니다. BCB는 프레임 하나를 관리합니다.

  1. 먼저 갱신할 때인지 확인합니다. 100 ms 주기로 진입해도 리스트를 보기 전에 반환할 수 있습니다. Quota가 비활성화되어 있거나, 이미 조정 중이거나, 경과 시간이 < 1 ms인 경우입니다. 경과 시간 < 500 ms이면서 표본 unfix 수 < floor(num_buffers / 4)인 경우도 반환합니다. 프레임이 32,768개라면 활동량 기준은 unfix 8,192회입니다. 정확히 1 ms 또는 500 ms이면 해당 시간 비교만으로는 반환하지 않습니다. 컴파일된 검사 조건이며 추가 타이머는 아닙니다. 표본과 갱신 조건 →
  2. 모든 리스트의 통계를 읽습니다. 갱신이 허용되면 LRU 배열 전체를 돕니다. 표본 접근 횟수를 읽고 초기화하고, private 활동량 추정치를 갱신하고, 후보 개수를 합칩니다. 리스트별로 모아 둔 숫자를 읽는 것이며, BCB를 하나씩 찾아가 접근 여부를 조사하지 않습니다.
  3. Private, 이어서 shared를 갱신합니다. 모든 private 항목을 돌며 quota와 구역 목표 크기를 정합니다. 이어서 모든 shared 항목을 돌며 구역 목표 크기를 정합니다. 적합한 후보가 있는 리스트는 해당 victim 탐색 큐에 알립니다. Private에는 quota 조건도 적용합니다.
  4. 경계에서 넘치는 만큼 이동시킵니다. 보호 구역이 너무 크면 그 리스트를 잠급니다. LRU2의 끝에서 시작하고, LRU2가 비어 있으면 LRU1의 끝에서 시작합니다. 링크를 따라 넘치는 BCB를 LRU3로 내리고, 필요하면 LRU1도 LRU2로 줄입니다. 각 조정은 목표 크기에 도달하면 멈춥니다.

작은 구성 예시: LRU1 + LRU2에 BCB가 30개인데 새 합계 목표가 25개라면, 경계에 있는 5개를 보호 구역 밖으로 옮깁니다. Dirty 페이지를 찾으려고 모든 BCB를 검사하는 작업은 아닙니다. 목표를 크게 줄이면 이동할 BCB 수도 많아질 수 있습니다.

최대 이동 범위: 한 리스트를 잠근 조정에서는 그 시점의 LRU1/LRU2 개수 이내를 처리합니다. LRU3로 내린 BCB와 이후 LRU1에서 LRU2로 내리는 BCB는 서로 다릅니다. 풀 상태가 고정되어 있으면 전체 이동 수는 풀 프레임 수 이내입니다. 그러나 리스트들을 차례로 잠그는 동안 다른 스레드가 BCB를 다시 보호 구역으로 올리거나 다른 리스트로 옮길 수 있으므로, 동시 실행 중에는 같은 BCB의 재방문을 포함한 실제 이동 수로 비용을 계산합니다. 각 경계 루프에는 별도의 방문 개수·시간 제한이 없습니다.

리스트 수와 실제 방문량으로 시간복잡도를 읽는다

시간복잡도는 입력 개수가 커질 때 연산량이 얼마나 늘어나는지 나타냅니다. O(개수)는 그 개수에 비례하는 규모, O(1)은 풀 크기가 커져도 페이지별 반복이 추가되지 않는 규모라는 뜻입니다. 밀리초나 잠금 대기의 상한을 뜻하지 않습니다. 아래는 소스 루프에서 도출한 구조적 비용입니다.

작업 단위기본 탐색 비용얼마나 커질 수 있나요?
Page-flush 후보 수집 한 번O(리스트 수 + 방문 BCB 수)모든 리스트 항목을 읽고, 양수 가중치 리스트의 꼬리를 배정량만큼 봅니다. BCB 방문의 상한은 리스트별 배정량의 합입니다.
Maintenance의 허용된 quota 갱신 한 번O(리스트 수 + 구역 이동 BCB 수)전체 리스트 통계를 한 차례 읽고 private/shared 설정을 한 차례 갱신합니다. 구역을 크게 줄이면 풀의 프레임 수에 비례하는 이동도 가능합니다. 1,000개나 200 MiB 방문 제한은 없습니다.
Post-flush의 큐 처리 한 번O(꺼낸 BCB 수)이번 호출 중 성공적으로 꺼낸 항목 수만큼 처리합니다. 동시에 들어오는 항목도 이 수에 포함됩니다.
Flush-control의 크레딧 계산 한 번O(1)경과 시간, 잔액, 소비량, dirty 카운터로 계산합니다. Private/shared LRU와 BCB를 탐색하지 않습니다.

호출 전체의 CPU 비용에는 추가 항이 있습니다. Page-flush는 thread-entry별 fix 통계를 합산하고, maintenance는 unfix 통계를 합산하므로 O(thread-entry 수)도 더합니다. Quota 함수가 시간·활동량 조건에서 반환하더라도 활동량 확인까지 갔다면 이 통계를 읽을 수 있습니다.

Page-flush는 후보 배열을 정렬하는 설정이 기본으로 켜져 있습니다. 비교 정렬의 통상 비용 모델은 O(후보 수 × log(후보 수))이며, 소스는 qsort() 라이브러리를 호출합니다. 이 표는 그 라이브러리의 최악 시간 보장을 주장하지 않습니다. 후보 재검사, 선택적 이웃 조회, 페이지 사본 복사와 기록도 별도 비용입니다.

Post-flush와 구역 이동 중 직접 전달은 프레임을 기다리는 요청을 찾을 수 있습니다. Post-flush의 완료 알림은 해당 BCB의 대기 연결 리스트를 따라갑니다. 따라서 전체 처리는 실제로 확인한 대기 항목 수만큼 더 커질 수 있습니다. Flush-control의 pthread_cond_broadcast()도 기다리는 writer 수와 OS 구현에 따라 비용이 달라집니다. O(1)은 크레딧 계산에 대한 설명입니다.

완료 큐의 8,192개 용량은 처리 횟수 제한이 아니다

Post-flush는 이전 flush의 BCB 상태를 정리하는 스레드입니다. BCB는 프레임 하나의 관리 레코드이고, 완료 큐 flushed_bcbs는 그 포인터를 보관합니다. 컴파일된 용량은 8 × 1024 = 8,192슬롯이며 전부 사용할 수 있습니다. 설정으로 조절하는 기본값이 아닙니다. 05장에서 가득 참·예약·게시 상태의 정확한 의미를 봅니다 →

  1. 새 삽입이 없는 경우: 처음 들어 있던 항목을 처리합니다. 처음 8,192개 포인터가 모두 게시되어 있고 아직 게시 중인 생산자가 없다면, 최대 8,192개를 꺼낸 뒤 다음 consume()가 실패하면 돌아갑니다. 다음 슬롯이 예약만 되고 아직 게시되지 않았다면 더 일찍 꺼내기에 실패할 수 있습니다.
  2. 동시에 삽입되는 경우: 꺼내 비운 자리에 page-flush가 새 포인터를 넣을 수 있습니다. Post-flush는 다음 항목도 계속 꺼내므로 한 호출에서 8,192개보다 많이 처리할 수 있습니다.
  3. 따라서 고정된 호출 상한은 없습니다. 루프에는 별도의 처리 개수·시간 예산이 없습니다. 연속된 꺼내기가 계속 성공한다면 언제 돌아갈지 이 코드만으로 정할 수 없습니다.
큐 용량은 동시에 보관할 수 있는 항목 수입니다. 한 번의 실행에서 꺼낼 항목 수, 한 BCB를 잠그는 시간, 대기 스레드를 깨우는 비용의 상한은 아닙니다. 각 항목의 현재 fix·dirty·zone을 확인하며, 꺼냈다고 프레임을 반드시 전달하는 것도 아닙니다.

Flush-control은 경과 시간으로 토큰이라는 페이지 단위 크레딧 잔액을 교체합니다. 토큰이 100,000개여도 토큰별 루프를 100,000회 도는 것은 아닙니다. 숫자를 계산·대입하고 대기 writer에 broadcast합니다. 페이지 탐색량은 0이며, 잔액 계산은 일정한 규모입니다. 잠금 경쟁과 여러 writer의 깨우기 비용은 따로 남습니다.

예상 시간은 방문량과 대기 시간을 나누어 계산한다

실제 밀리초는 이 소스만으로 정할 수 없습니다. 아래는 조건을 정해 계산하는 예이며 실제 측정이나 일반적인 장비 성능값이 아닙니다. 처리 시간은 태스크 안에서 작업·대기에 쓴 시간이고, 주기는 다음 실행 기회를 정하는 목표입니다.

데몬먼저 계산·측정할 양별도로 더할 지연
Page-flush통계 합산 + 리스트 방문 + BCB 방문 + 후보 정렬·재검사·사본 처리LRU/BCB 잠금, WAL, DWB 공간, OS 기록, 토큰 대기와 반복 수집

Post-flush실제 꺼낸 항목 수 × 항목당 평균 비용 + 대기 항목 처리BCB 잠금, 직접 전달, 깨우기, 처리 중 새 삽입

산술 예제: 리스트 숫자 읽기나 BCB 한 번 방문에 각각 평균 0.5 µs가 든다고 가정합니다. 서로 다른 작업에 같은 값을 쓰는 연습용 가정입니다. 잠금·정렬·복사·I/O·깨우기 비용은 아직 포함하지 않습니다.

  • 리스트 20개의 숫자를 한 번 읽으면 10 µs입니다. 여러 차례의 리스트 루프와 thread-entry 통계 합산은 더합니다.
  • Page-flush가 BCB 12,800개를 실제 방문했다면 그 방문 비용만 6.4 ms입니다.
  • Maintenance가 구역의 BCB 100,000개를 실제 옮기고 이동당 비용도 0.5 µs라고 가정하면 이동 부분은 50 ms입니다. 실제 이동 비용은 별도로 측정해야 합니다.
  • Post-flush가 새 삽입 없이 8,192개를 처리하고 항목당 비용도 0.5 µs라고 가정하면 4.096 ms입니다. 이 값은 잠금과 대기 항목 처리까지 포함한 실측 평균으로 교체해야 합니다.

Page-flush가 실제 기록 경로에 넘기는 데이터 200 MiB를 그 경로가 실효 200 MiB/s로 처리한다고 가정하면, 바이트 처리 부분만 1초입니다. 작은 파일 쓰기가 OS 캐시에서 끝나거나 DWB에 사본을 받아 두는 경우에는 이 계산과 다른 완료 지점을 측정합니다. 사본 제출 완료를 최종 페이지 위치의 영속화 완료로 읽으면 안 됩니다.

100 ms와 50 ms는 작업 시간 보장이 아닙니다. Maintenance의 100 ms, flush-control의 50 ms는 실행 주기 목표입니다. Page-flush의 기본 1,000 ms와 post-flush의 1 → 10 → 100 ms 대기 정책도 완료 기한은 아닙니다. 실제 작업이 주기를 넘으면 다음 타이머 대기가 0이 될 수 있습니다.

이 서버의 예상 시간을 구하려면 태스크 시작·종료, 실제 방문·이동·큐 소비 개수와 잠금/I/O 대기를 같은 구간에서 측정합니다. Page-flush의 PSTAT_PB_FLUSH_COLLECT와 PSTAT_PB_FLUSH_FLUSH는 수집과 제출 경로 시간을 나누는 출발점입니다. 전체 작업 시간이나 최종 영속화 시간과 자동으로 같지는 않습니다.

완료 처리를 기다리는 스레드와 속도를 조절받는 스레드는 다르다

페이지 사본을 보내는 데 성공한 직후를 봅시다. 프레임의 관리 레코드인 BCB에는 이전 기록의 진행 표시를 정리하는 일이 남습니다. 한편 OS 기록을 끝낸 기록 스레드는 계속 진행할 속도를 조절받을 수 있습니다. 두 대기는 서로 다른 일을 기다립니다.

Post-flush가 맡는 일: 프레임을 못 구한 요청이 기다릴 때, page-flush는 BCB 주소를 완료 처리 목록에 넣어 뒷정리를 넘길 수 있습니다. post-flush가 상태를 다시 확인하고 이전 기록을 기다리던 스레드를 깨웁니다. 조건이 맞으면 프레임을 요청에 제안합니다. post-flush가 없거나 목록에 넣지 못하는 등 인계 조건이 맞지 않으면 page-flush가 직접 정리합니다. 인계 조건과 직접 처리 →

깨우기를 놓치면 필요한 작업도 잠들 수 있다

장난감을 정리하는 사람을 떠올려 봅시다. 이미 깨어 있는 사람에게 “일어나!”라고 말했습니다. 그 사람은 메모를 남기지 않고 곧 잠듭니다. 장난감 찬장의 문을 열어 줘도 잠에서 깨지는 않습니다. 다시 부르는 사람도 알람도 없다면 장난감은 그대로 남습니다. 찬장 문을 여는 것이 부팅 게이트이고, 부르는 말이 wakeup()입니다.

깨우기 요청을 기억하고 잠들기 전에 확인한다

새 설계 질문: 요청자가 page-flush의 무기한 대기 직전, 아직 깨어 있는 RUNNING 상태에서 작업 수요를 공개합니다. 워커가 그 수요를 검사할 차례라는 사실을 어떻게 기억할까요? 아래 변경은 해결책 제안이며, 고정 리비전에 구현된 동작은 아닙니다.

  1. RAM에 미처리 요청을 남기고 대기 전환과 함께 보호합니다. 생산자는 워커가 실행 중이어도 “다시 검사해야 함”을 기록합니다. 워커는 그 요청을 소비하고, 잠드는 대신 다시 실행합니다. 요청 기록, 마지막 검사, condition variable 대기 진입을 같은 mutex 같은 하나의 동기화 절차로 연결해야 합니다. 그렇지 않으면 “요청 없음”을 확인한 뒤 잠들기 전에 요청이 도착해 같은 틈이 생깁니다. 매 실행에서 현재 작업 압력을 모두 다시 확인한다면 여러 요청을 하나의 비트로 합칠 수 있으며, 모든 깨우기 횟수를 셀 필요는 없습니다.
  2. 유한한 타이머를 보조 실행 기회로 둡니다. page_flush_interval을 고정 리비전 기본값 1,000 ms처럼 양수로 두면, 이후 시간 제한 대기는 다른 생산자가 없어도 끝납니다. 태스크는 게이트와 수요를 검사하며, 제출할 페이지가 없을 수도 있습니다. 대기 정책에 시간을 정하는 것이지 스케줄링·I/O까지 포함한 응답 시간의 상한은 아닙니다. 이미 wait_inf()에 들어간 스레드는 설정만 바꿔도 깨어나지 않습니다.
  3. 게이트를 연 사건도 기억해야 할 요청으로 전달합니다. 열린 게이트를 공개한 뒤, 위의 동기화된 미처리 요청 방식으로 실행을 요청합니다. 지금의 wakeup()을 한 번 호출하는 것만으로는 RUNNING 중에 다시 버려질 수 있습니다. 시작할 때의 알림만 고쳐도 부팅 후의 틈은 남습니다.

현재 코드에서도 진행을 회복할 수 있는 경로: 이후 allocator나 victim 탐색 요청이 SLEEPING 중인 page-flush를 깨울 수 있습니다. 게이트가 열렸을 때 수락된 깨우기는 후보 flush 함수를 최소 한 번 호출하게 합니다. 타이머로 진입했을 때 allocator 수요가 큐에 있어도 실행할 이유가 생깁니다. 다른 경로가 프레임을 사용할 수 있게 만들 수도 있습니다. 이 경로들이 요청 하나만 있는 독립 사례를 정해진 시간 안에 구해 준다는 보장은 없습니다. page_buffer.c:17029–17044 · page_buffer.c:8247–8309 · page_buffer.c:15409–15417.

만들기, 작업 허용하기, 종료 기다리기는 별도 단계다

서버 시작 순서를 봅시다. 페이지를 담는 프레임, 프레임 관리 레코드인 BCB, 교체 목록과 작업 대기 목록을 먼저 준비합니다. 백그라운드 스레드들은 같은 서버 프로세스 안에서 이 메모리를 함께 사용합니다.

  1. 시작 코드는 페이지 사본을 임시 보관하는 이중 쓰기 버퍼(DWB)를 복구하고, pgbuf_daemons_init()으로 네 역할의 생성을 시도합니다. 로그 복구는 아직 끝나지 않았습니다.
  2. 먼저 실행된 스레드는 작업 허용 플래그를 확인하고 반환합니다. 복구 전 접근을 막는 이 플래그가 부팅 게이트입니다.
  3. 복구가 끝나면 게이트를 엽니다. 열기 자체는 깨우기를 보내지 않습니다. 각 스레드는 이후 타이머나 작업용 깨우기로 다시 실행될 때 허용 여부를 확인합니다.
  4. 종료할 때는 stop으로 반복 실행의 종료를 요청하고 잠든 스레드를 깨웁니다. 호출자는 join()으로 해당 스레드의 종료를 기다립니다. 실행 중인 작업과 스레드 자체 정리가 끝난 뒤에야 join이 반환합니다.

그룹은 maintenance → page-flush → post-flush → control 순서로 멈춥니다. log_final()과 풀 해제는 그 뒤입니다. 단독 실행인 stand-alone 모드에는 이 네 스레드를 만들지 않습니다. page-flush가 없으면 해당 요청 경로가 후보 기록을 직접 수행할 수 있습니다. 생성은 항상 성공하지 않으며, control은 초기화 실패로 빠질 수도 있습니다.

복구 중: 복구 코드가 페이지와 로그 상태를 고치고 있습니다. 이미 생성된 백그라운드 스레드가 이를 동시에 건드리지 않도록, 작업 허용 플래그인 부팅 게이트를 확인하고 반환합니다. 이 검사를 없애면 동시 접근이 가능해집니다. 스레드가 존재한다는 사실만으로 장애 발생을 증명하지는 않습니다.

종료 중: 반복 실행의 종료 요청인 stop은 현재 작업이나 I/O를 취소하지 않습니다. 종료 코드는 잠든 스레드를 깨우고 join()으로 종료를 기다립니다. 스레드가 작업과 자체 정리를 마치기 전에 풀이나 작업 목록을 해제하면 아직 사용하는 메모리가 사라질 수 있습니다.

재시작 실패 시: 게이트를 닫고 페이지 버퍼와 사본 임시 보관 영역인 DWB의 스레드 그룹을 종료한 뒤 log_final()을 호출합니다. 게이트는 다음 작업을 막지만 실행 중인 함수를 취소하지 않습니다.

프레임 부족을 처리하거나 목록에서 항목을 계속 꺼내는 내부 반복문이 길면 바깥의 stop 확인도 늦어집니다. stop만으로 모든 항목 처리나 정해진 시간 안의 종료를 약속할 수 없습니다. join이 확인하는 것은 해당 스레드의 종료입니다.

stop/wake/join · 복구와 게이트 · 종료 순서 · 재시작 오류 시 정리. 소스만으로 join 지연의 상한을 정할 수는 없습니다.

Q&A · 종료하면 목록의 모든 항목도 처리되나요?

stop과 join만으로는 그렇지 않습니다. 새 항목을 넣는 쪽을 언제 멈추고 남은 항목을 어떻게 처리할지 별도 규칙이 필요합니다. join은 해당 스레드의 종료를 확인합니다.

50 ms는 다음 실행을 시도할 목표입니다. 실제로 잔액을 바꾸려면 복구가 끝나 작업이 허용되고, CPU를 배정받고, 잔액을 보호하는 mutex 잠금을 얻어야 합니다. 잔액이 생긴 뒤에도 기록 스레드가 실행되어 잠금을 얻고 사용해야 합니다.

아니요. 목표 주기는 완료 횟수가 아닙니다. 이전 작업 시간, CPU 배정, 잠금 경쟁과 작업 허용 여부가 영향을 줍니다. 잔액 갱신도 스레드의 기록 완료와 다른 사건입니다.

스레드 하나로 바꾸려면 기록 대기 중에도 다른 일을 해야 한다

현재 구현과 별개인 설계 연습: 네 스레드를 하나로 바꾼다고 가정합니다. 어떤 일을 다음에 실행할지 고르는 코드를 스케줄러라고 합니다. 이 스레드가 페이지 기록이 끝날 때까지 멈춰 있으면 다른 관리 작업도 기다려야 합니다.

  1. 역할별로 아직 할 일을 기억합니다. BCB 완료 처리에는 주소 목록, 프레임 부족에는 요청 상태 등 그 역할에 맞는 기록을 둡니다. 깨우기 요청만으로 작업 내용을 대신하지 않습니다.
  2. 할 일을 고르되, 느린 I/O를 시작할 때 돌아와서 이어 할 상태와 다음 동작을 남깁니다. 이런 이어가기 기록을 continuation이라고 합니다.
  3. I/O 완료를 기다리는 동안 다른 준비된 일을 실행합니다. 완료가 도착하면 잠금 등 필요한 보호 아래 남겨 둔 지점부터 이어갑니다.
  4. 종료할 때는 새 일을 만드는 쪽을 먼저 멈춥니다. 누가 정리할지 정한 규칙에 따라 진행 중인 이어가기 기록을 끝내거나 취소합니다. 스레드를 종료하고 join()으로 종료를 확인한 뒤 필요한 메모리를 해제합니다.

이 대안에는 작업 기록의 수명, 취소와 실행 순서 규칙이 더 필요합니다. I/O 하나 때문에 모두 멈추는 문제는 줄일 수 있지만, 각 일을 공평하게 실행하는 규칙과 I/O 시간에 대한 가정 없이는 처리 시간 상한을 정할 수 없습니다.

Q&A · I/O 대기 중 다른 일을 하면 자동으로 공평해지나요?

아니요. 특정 기록 때문에 모두 멈추는 문제는 줄여도 한 작업만 계속 고를 수 있습니다. 각 작업이 실행 기회를 얻는 규칙과 I/O에 대한 가정이 따로 필요합니다.

깨우기 요청과 남은 작업을 시간 순서로 따로 기록한다

아직 실행하지 않은 실험 제안: page-flush를 새 상태에서 시작합니다. waiter는 대기와 깨우기를 관리하는 객체이며, 대기 전 상태는 RUNNING, 대기 중 상태는 SLEEPING입니다. 리비전, 빌드, 풀·로그 크기, 페이지 사본 임시 보관 영역인 DWB와 I/O 설정을 기록합니다.

확인할 설명
