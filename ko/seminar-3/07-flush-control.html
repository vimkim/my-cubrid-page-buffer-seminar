Token과 flush-control 데몬

페이지 credit의 의미, 예산 갱신, 한 writer의 진행을 살펴봅니다.

07 · 1 / 4

Token은 무엇이고 언제 소비하나요?

Token은 페이지 한 장에 해당하는 정산 단위입니다. 정산에 참여하는 파일 writer들은 token bucket이라는 정수 잔액을 공유합니다. 운영체제(OS) 쓰기가 성공한 뒤 기록한 페이지 수만큼 Token을 소비합니다. 메모리의 값을 바꾸는 것만으로는 Token을 쓰지 않습니다.

왜 이 잔액이 필요할까요? 데이터 쓰기는 읽기나 로그 쓰기와 저장 장치 사용 시간을 두고 경쟁할 수 있습니다. CUBRID는 잔액으로 writer의 이후 진행 속도를 조절합니다. 일반 writer는 남은 Token을 소비하고, 이미 기록한 페이지를 모두 정산할 만큼 Token이 없으면 기다릴 수 있습니다. Flush-control 데몬은 다음 예산을 공급하는 백그라운드 스레드이며, 직접 페이지를 쓰지는 않습니다.

이 속도 조절은 참여 경로에 적용됩니다. FILEIO_WRITE_NO_COMPENSATE_WRITE 모드는 이 정산을 건너뜁니다. 고정 리비전의 double-write buffer(DWB)는 페이지 사본을 중간에 기록하는 장치이며 이 모드를 사용합니다. 로그 진행을 보호하는 잠금인 log critical section을 가진 writer는 남은 Token을 소비하지만 부족분을 기다리지 않습니다. 따라서 Token으로 모든 저장 장치 쓰기를 제한하는 것은 아닙니다.

데몬은 Token 잔액을 어떻게 갱신하나요?

Flush-control 데몬은 공유하는 페이지 credit 잔액을 50 ms 목표 주기로 갱신합니다. 시작 과정에서 작업이 허용된 뒤 첫 실행은 시간만 기록합니다. 그다음 실행부터는 다음 순서를 따릅니다.

  1. 실제 경과 시간을 측정합니다. 직전 작업이 끝난 시점부터 잽니다. 목표 주기가 50 ms여도 실제 경과 시간이 반드시 50 ms인 것은 아닙니다.
  2. 새 예산을 계산합니다. 아래에서 설명하는 고정 속도 방식이나 adaptive 방식을 사용합니다.
  3. 잔액을 교체합니다. tb->tokens = gen_tokens에서 tb는 공유 bucket, gen_tokens는 새 예산입니다. 3개가 남았고 새 예산이 7개이면 잔액은 7개가 됩니다. 남아 있던 3개는 버립니다.
  4. 기다리는 writer들을 깨웁니다. 깨어난 writer는 새 잔액에서 아직 정산하지 못한 페이지 수만큼 Token을 다시 얻으려 합니다.

갱신과 소비는 모두 mutex라는 잠금으로 보호하여 한 번에 하나만 잔액을 바꿉니다. 기다리는 writer는 공유 알림 수단인 condition variable에서 잠들며, 그동안 mutex를 놓습니다. 깨어나면 다시 시도할 수 있지만 충분한 Token이 남아 있다고 보장받지는 않습니다.

새로 만들 Token 수는 어떻게 정하나요?

Token 예산은 한 구간에 공급하는 페이지 credit 수입니다. 그 수만큼 페이지를 쓰라는 지시는 아닙니다. adaptive_flush_control=yes가 기본값이며 adaptive 방식을 선택합니다. no이면 고정 속도 방식을 선택합니다.

고정 속도 방식

max_flush_size_per_second는 초당 바이트 수를 지정합니다. CUBRID는 I/O 페이지 한 장의 바이트 크기인 IO_PAGESIZE로 나누어 초당 페이지 수로 바꿉니다. 이후 new tokens = floor(pages/s × actual elapsed seconds)로 계산합니다. floor는 소수 부분을 버린다는 뜻입니다.

예: 고정 속도의 기본값은 초당 10,000페이지입니다. 실제로 50 ms가 지났다면 10,000 × 0.05 = 500개, 100 ms가 지났다면 1,000개를 공급합니다. 이 설정은 고정 속도 방식에서만 사용하며 adaptive 예산의 상한이 아닙니다.

Adaptive 방식 (기본값)

직전 예산은 지난번에 공급한 credit 수이고, 남은 Token은 아직 소비하지 않은 credit입니다. 버퍼 풀은 데이터베이스 페이지를 보관하는 메모리 영역입니다. Dirty 페이지는 변경 내용을 아직 기록해야 하는 페이지입니다. Dirty 증가 제안량은 dirty 개수가 풀의 절반을 넘는 정도와, 보관한 이전 개수보다 늘어난 정도를 반영합니다.

갱신 시점의 상태직전 예산을 바꾸는 방법
Token이 남고 dirty 증가 제안량이 양수직전 예산을 유지합니다.
Token이 남고 dirty 증가 제안량이 0남은 Token의 10%에서 소수 부분을 버린 값을 뺍니다.
Token이 하나도 남지 않음Dirty 증가 제안량과 직전 예산의 50% 중 큰 값을 더합니다. 50% 계산의 소수 부분은 버립니다.

마지막으로 코드에 정해진 최소 credit 공급 속도 40 MiB/s를 페이지 수로 바꾸고 실제 경과 시간에 맞춰 계산합니다. 앞의 결과가 이 최솟값보다 작으면 올립니다. 페이지 크기가 16 KiB이고 경과 시간이 50 ms이면 최솟값은 128개입니다.

예: 직전 예산이 128개이고, 남은 Token과 dirty 증가 제안량이 모두 0이면 50% × 128 = 64개를 더합니다. 다음 예산은 192개이며, 이미 최솟값 128개보다 큽니다. 이 예들은 계산을 설명하기 위한 구성 사례이며 측정한 쓰기 속도가 아닙니다.

한 writer의 예산 소비부터 대기와 갱신까지

처음부터 끝까지 이어지는 구성 사례: 첫 실행의 시간 기록을 마친 controller가 고정 속도 방식으로 초당 140페이지를 공급합니다. 각 갱신 사이의 실제 경과 시간은 50 ms이므로 매번 140 × 0.05 = 7개를 설정합니다. 일반 writer 하나가 정산에 참여하는 파일 쓰기 모드로 기록하고, 로그 진행을 보호하는 잠금인 log critical section은 갖고 있지 않으며, 각 batch의 운영체제(OS) 쓰기가 성공하면 바로 정산합니다. 다른 writer와의 Token 경쟁은 없습니다. 계산을 쉽게 보이기 위해 작은 속도를 골랐습니다.
