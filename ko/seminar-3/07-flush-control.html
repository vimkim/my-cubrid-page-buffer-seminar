쓰기 속도를 조절하는 시점과 방법

Clean 공급을 늘리면 병목이 저장장치로 옮겨갈 수 있습니다. 고정 CUBRID 경로는 OS write 이후 token을 차감합니다. 따라서 token daemon은 이미 완료한 write의 허가보다 이후 진행을 조절합니다. 회차별 교체, 누적 credit, 속도 제한 제거는 burst 양상이 다릅니다. 어느 방식도 WAL이나 보호된 재사용을 대신하지 않습니다.

매 갱신에서 token을 교체하며 자동으로 누적하지 않습니다. Condition wait가 무기한이면 열 번 반환하는 탈출 조건은 실제 시간 상한이 아닙니다. Log critical section caller의 우회도 별도로 분석해야 합니다.

07 · 3 / 13

쓴 페이지 수만큼 credit을 소비한다

bucket은 file writer가 공유하는 mutex-protected 정수 잔액입니다. FILEIO_WRITE_DEFAULT_WRITE path에서는 OS write가 성공한 뒤 fileio_compensate_flush()가 write한 page 수만큼 token을 요청합니다. 잔액이 있으면 바로 차감하고, 부족한 일반 writer는 다음 condition broadcast를 기다릴 수 있습니다. 세고 있는 write는 이미 끝났으므로 token은 그 write를 허가하는 것이 아니라 이후 진행 속도를 조절합니다.

약 50 ms마다 daemon이 새 credit 잔액으로 교체하고 대기 중인 writer를 깨웁니다. 이전 잔액에 계속 더해 쌓는 방식이 아닙니다. 이 속도 조절에는 우회 경로가 있으므로 엄격한 I/O 상한은 아닙니다.

초기화는 token 0개와 condition variable을 가진 bucket을 만듭니다. 실패하면 이 daemon이 없고 token acquisition은 no-op이 되지만 page flushing은 계속 동작합니다. 첫 gate-open task pass는 time origin만 기록합니다. 이후 pass가 elapsed time을 측정하여 첫 interval allowance를 만듭니다.

쓴 페이지 수만큼 credit을 소비한다 · 이어서

  1. token bucket을 lock합니다.
  2. consumed-token과 page-write 통계를 읽고 clear합니다.
  3. adaptive 또는 configured interval budget을 계산합니다.
  4. 새 budget을 이전 balance에 더하지 않고 tokens를 교체합니다.
  5. interval 통계를 reset하고 condition variable을 broadcast합니다.

16 KiB/page에서 adaptive 40 MiB/s floor는 2,560 page/s, 50 ms마다 약 128 token입니다. non-adaptive internal 10,000-page/s 기본값은 50 ms마다 약 500 token입니다. 실제 값은 elapsed time, integer truncation, feedback에 따라 달라집니다.

Credit은 엄격한 I/O 상한이 아니다

Credit은 성공한 OS write 뒤에 소비합니다. 참여하지 않는 write 경로와 기다리지 않는 호출자가 있으므로, 모든 write를 허가하는 장치나 엄격한 처리량 제한으로 해석하면 안 됩니다.

fileio_write()와 fileio_write_pages()는 default compensated mode에서만 successful OS write 뒤 fileio_compensate_flush()를 호출합니다. FILEIO_WRITE_NO_COMPENSATE_WRITE는 bucket을 건너뛰며 DWB 관련 write path가 이 mode를 선택할 수 있습니다. 참여하는 normal caller는 budget을 기다릴 수 있지만 최대 열 번 condition wait의 반환·재시도 뒤 탈출할 수 있습니다. 각 대기는 무기한이므로 실제 경과 시간의 상한은 아닙니다. log critical section을 가진 caller는 demand를 account하되 missing token을 기다리지 않습니다.

따라서 correctness authorization이나 strict throughput ceiling이 아니라 soft pacing입니다. CPU accounting은 O(1)이고 condition broadcast와 awakened waiter scheduling 비용은 waiter 수에 따라 커집니다.

WAL·checkpoint·DWB도 각자 역할이 있다

Log flush는 WAL을, checkpoint는 복구에 필요한 기록 진행을 담당합니다. Foreground flush와 DWB 경로도 별도로 존재합니다. 이들을 네 page-buffer daemon과 같은 작업으로 묶지 않습니다.

log-checkpoint는 기본 360초인 자체 configurable timer를 가지며 oldest_unflush_lsa로 data page를 선택합니다. log-flush는 WAL을 위해 append-log page를 durable하게 만듭니다. Foreground/WRITE-owner path는 data-page generation을 copy할 수 있습니다. DWB helper daemon은 stable image가 DWB seam을 넘은 뒤 downstream에서 동작합니다. 어느 것도 maintenance나 token-control lane에 속하지 않습니다.

D28 · 같은 quota와 열 번의 retry면 아무 일도 없었던 걸까요?

Profiler가 quota=64를 두 번 읽었지만 adjust_age는 증가했습니다. Writer 하나는 첫 condition wait에서 계속 잠들어 있습니다. Reviewer는 정책이 멈췄고 대기도 열 주기로 제한된다고 말합니다.

반박을 검토한 뒤 제한된 답 보기

수락한 epoch는 sample을 소비하고 시간·zone을 갱신하면서 quota 64를 다시 계산할 수 있습니다. Retry는 condition wait 반환 뒤에 증가합니다. 불리한 scheduling이나 알림 부재에서는 첫 untimed wait부터 오래 지속될 수 있어 열 번이 열 주기를 뜻하지 않습니다.

후속 질문: “건너뛰는 backup을 즉시 수정해야 합니까?” 먼저 지원 조건에서 producer별 영향을 분리합니다. 소스 이상과 측정한 진행 영향은 별도 주장입니다.

구별할 관측: 수락 epoch, 입력 sample, 결과 zone, producer별 배정, refill 시간, condition 반환을 기록합니다. 통제한 변화 workload에서 static/adaptive quota를 비교합니다. 기존 Q14–Q17의 정책·pacing 질문도 유지합니다.

일관된 대안: Write 전에 pacing credit 예약

설명용 대안입니다. 명시한 성질을 보존하며 actor의 조정 방식을 바꿉니다.

  1. OS write 전에 byte·page 비용을 정의해 allowance를 예약합니다.
  2. 보충이나 log 진행에 필요한 lock 밖에서만 기다립니다.
  3. 예약 후 WAL 순서를 지키는 write를 수행합니다.
  4. 제출 전 취소에는 credit을 반환하고 partial write 이후에는 정의한 오류 규칙으로 실제 작업량을 기록합니다.

설명용 대안입니다. Write 진입을 조절하지만 예약·취소 상태가 추가됩니다. Log와 credit의 의존 순환을 배제하지 않으면 deadlock이 가능합니다. 누적 credit은 저장한 burst를 허용하고 회차별 교체는 회차 allowance를 제한하며 pacing 제거는 저장장치 경쟁을 바꿉니다. 실제 장치 I/O의 엄격한 상한을 측정한 것은 아닙니다.

어떤 관측으로 이 설명을 반증할 수 있는가?

아직 실행하지 않은 실험 제안입니다. 결과 해석 전에 전체 고정 리비전, build, pool·log·DWB·I/O 설정과 workload를 기록합니다.

가설
회차별 교체가 OS write 이후 burst를 바꾸며 retry 수는 경과 시간 상한이 아니라는 가설입니다.
통제하는 변화
Write 순서와 refill 일정을 고정하고 교체, 누적 credit, pre-write 예약 대안을 비교합니다. 일반 caller와 log-CS caller를 분리합니다.
정확한 관측
OS write 반환, post-write 차감, token 교체·broadcast, condition wait 시작·반환, 탈출 이유를 관찰합니다. Compensation 통계만으로 앞선 write 지연을 알 수 없습니다.
반증 기준과 한계
관찰한 OS write보다 먼저 차감됐다면 고정 경로 주장을 반증합니다. 열 번 반환하는 경로에도 한 번의 무한 대기가 가능하면 유한 지연 정리는 나오지 않습니다. Timing은 기록된 관찰로만 사용합니다.
