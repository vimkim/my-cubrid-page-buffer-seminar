쓰기 이후의 속도 조절

CUBRID page-buffer daemon과 PostgreSQL 페이지 교체

자주 읽는 페이지 집합의 반복 접근 + 대규모 스캔 + dirty 페이지 압력. 구성한 실행 순서는 각각 독립적으로 다시 시작합니다. 기능의 이유는 소스가 의도를 명시하지 않는 한 추론(Inference)입니다.

쓰기 성공 뒤에도 writer가 기다리는 이유는?

대규모 스캔에는 빈 메모리가 필요한데, 갱신 작업 때문에 메모리에 있는 많은 페이지가 dirty 상태가 됩니다. 아직 기록해야 할 변경 내용이 남았다는 뜻입니다. 백그라운드 writer는 메모리 재사용을 준비하려고 페이지 이미지를 저장장치에 보냅니다. 설계 이유에 대한 추론(Inference): flush가 너무 느리면 할당 작업이 재사용 가능한 clean 페이지를 기다릴 수 있고, 쓰기가 몰리면 읽기나 로그 쓰기와 저장장치 사용 시간을 두고 경쟁할 수 있습니다. 속도 조절은 이 균형을 조정하는 수단이며, 지연 감소를 보장하지는 않습니다.

CUBRID는 정산에 참여하는 I/O 페이지 쓰기 한 번을 token, 즉 credit 하나로 계산합니다. 서버의 file-I/O token bucket은 참여하는 writer들이 함께 사용하는 credit의 정수 잔액입니다. Writer는 운영체제(OS)의 쓰기가 성공한 뒤에 페이지당 token 하나를 차감합니다. Credit이 부족하면 호출자가 다음 작업으로 넘어가기 전에 기다릴 수 있지만, 이미 성공한 쓰기를 막을 수는 없습니다.

Daemon의 타이머는 작업을 실행할 시점을 정하지만, 여러 writer가 쓸 페이지 수까지 정하지는 않습니다. 공유 credit으로 이들의 정산 대상 쓰기량을 합산합니다. Flush-control daemon이 다음 예산을 설정하면 일반 writer들이 이를 소비하고, 소진되면 기다릴 수 있습니다. 예산은 설정한 속도에 따른 제어 또는 dirty 페이지 상태를 반영하는 적응형 피드백으로 결정합니다.

이것이 soft pacing, 즉 느슨한 속도 조절입니다. 우회 경로가 있고 여기의 대기에는 시간 제한이 없습니다. 페이지 내용, 복구 순서, 안전한 메모리 재사용은 별도 규칙으로 보호합니다.

RAM 변경과 파일 쓰기는 서로 다른 단계입니다

페이지 버퍼는 CUBRID가 관리하는 RAM에 DB 페이지를 보관합니다. UPDATE가 메모리에 있는 값을 100에서 200으로 바꾸면 메모리 쓰기입니다. Dirty 표시는 파일에 기록할 변경이 남았다는 뜻입니다. RAM 변경과 dirty 표시만으로 DB 파일이 자동으로 바뀌거나 token이 차감되지는 않습니다.

Flush는 나중에 안정된 페이지 이미지를 저장소 쪽으로 보내는 작업입니다. pwrite(fd, buffer, size, offset)는 메모리의 바이트를 파일의 지정된 바이트 위치에 씁니다. 이미지는 출발지이고, DB 파일은 목적지입니다.

페이지 이미지를 중간에 보관하는 선택적 경로인 DWB(double-write buffer)는 비활성화된 것으로 가정합니다. Controller는 초기화되어 있고, 기본 모드의 writer는 로그 진행을 보호하는 log critical section을 보유하지 않습니다. WAL은 write-ahead logging으로, 데이터 쓰기 전에 필요한 복구 로그의 영속성을 요구합니다. Token은 참여하는 I/O 페이지 수를 세며, 행 수를 세지 않습니다.

  1. UPDATE: RAM의 바이트를 바꾸고 dirty 표시를 붙입니다.
  2. 나중의 flush: 안정된 이미지를 복사하고 필요한 WAL의 영속성을 확보합니다.
  3. 파일 쓰기: pwrite로 이미지를 DB 파일에 씁니다.
  4. 정산: token을 차감하고 부족하면 다음 작업 전에 기다릴 수 있습니다.

OS 파일 캐시를 거치더라도 CUBRID는 RAM 이미지를 파일 I/O로 전달해야 합니다. OS 쓰기와 동기화된 영속성은 별개입니다. 후자는 동기화에서 다룹니다.

어떤 작업에서 dirty 페이지를 파일에 쓰나요?

이전 트랜잭션이 변경한 페이지들이 서버의 buffer pool에 남아 있는 상황을 생각해 봅시다. SQL 작업은 변경이나 메모리 압박을 만들고, 나중에 flush를 맡은 주체가 선택된 페이지 이미지를 파일에 보냅니다. SQL 문장이 행마다 token을 직접 소비하는 것은 아닙니다.

작업 또는 상황파일 쓰기로 이어질 수 있는 이유
대량 INSERT·UPDATE·DELETEHeap과 index 페이지가 dirty 상태가 되어 나중에 이미지를 기록해야 합니다. Dirty 표시 자체는 페이지를 파일에 쓰지 않습니다.
CheckpointCheckpoint는 복구를 위해 기록할 변경이 남은 dirty 페이지를 선택해 flush 경로를 실행합니다.
대규모 읽기 스캔에 buffer 공간이 더 필요함이전 변경 때문에 dirty인 교체 후보는 페이지 하나를 담는 메모리 자리인 frame의 재사용 전에 flush가 필요할 수 있습니다. 페이지를 읽었다는 사실만으로 dirty가 되지는 않습니다.

pgbuf-page-flush daemon, checkpoint 작업, 또는 요청을 처리하는 foreground 호출자가 flush를 실행할 수 있습니다. Token 차감 여부는 선택한 파일 쓰기 모드에 달려 있습니다. Double-write buffer(DWB)는 페이지 이미지를 중간에 보관한 뒤 원래 DB 위치에 쓰는 경로입니다. DWB가 비활성화되어 있으면 페이지 버퍼의 직접 쓰기 경로는 FILEIO_WRITE_DEFAULT_WRITE를 선택해 쓰기 성공 뒤 정산합니다. 이 고정 리비전에서 활성 DWB의 staging 파일 쓰기와 원래 DB 위치(home page) 쓰기는 FILEIO_WRITE_NO_COMPENSATE_WRITE를 사용하여 이 token 정산을 건너뜁니다. 따라서 같은 SQL 작업이라도 파일 쓰기는 발생하면서 이 token 제어에는 참여하지 않을 수 있습니다.

어떤 작업이 잔액을 갱신할까요?

Flush-control daemon은 백그라운드 스레드입니다. 이 작업은 정산에 참여하는 파일 writer들이 공유하는 잔액을 새 값으로 교체합니다. 부팅 게이트(boot gate)는 공유 Boolean 플래그 boot_Enabled_flush_daemons입니다. false이면 이 태스크의 작업을 막고, true이면 허용합니다.

로그 복구 중에도 이 스레드는 이미 존재할 수 있습니다. log_initialize()가 로그 복구를 수행하고 이어지는 시작 검사가 성공하면, 서버 부팅 코드가 BO_ENABLE_FLUSH_DAEMONS()를 호출해 플래그를 true로 바꿉니다. “Gate가 열린다”는 이 작업 허용 상태로 바뀐다는 뜻입니다. 태스크는 진입할 때마다 BO_IS_FLUSH_DAEMON_AVAILABLE()로 확인하며, 닫혀 있으면 시각 기록이나 token 생성 전에 반환합니다.

열린 gate를 확인한 첫 실행은 시각만 기록하고 token을 생성하지 않은 채 반환합니다. 그다음 실행부터 경과 시간을 계산해 적응형 또는 고정 속도 분기를 선택합니다. Gate를 여는 동작 자체가 스레드를 깨우지는 않습니다. Flush-control은 이후의 주기 실행에서 열린 상태를 확인합니다. 서버 시작 전체 순서는 daemon 수명에서 이어서 설명합니다.

그림의 호출들은 bucket이 초기화된 적응형 분기에 해당합니다. 고정 속도 분기는 마지막 두 호출을 건너뜁니다.

Token 공유에는 어떤 자원이 먼저 필요할까요?

이 시작 사례는 뒤의 숫자 사례와 독립적입니다. 서버는 네 번째 page-buffer daemon 역할로 flush-control 생성을 시도합니다. 관리자가 스레드를 시작하기 전에 작업 객체가 공유 bucket 저장공간을 초기화합니다.

  1. Bucket의 mutex를 초기화합니다. 이 잠금은 writer나 갱신 작업 중 한 주체만 잔액을 수정하게 합니다.
  2. Token 잔액과 소비 카운터를 0으로 설정합니다.
  3. Condition variable을 초기화합니다. Credit이 부족한 writer가 알림을 기다리며 잠들 때 사용하는 수단입니다.
  4. Bucket 포인터를 공개한 다음, 관리자에게 컴파일된 주기 50 ms로 스레드 생성을 요청합니다.

잔액이 0이라는 사실만으로 쓰기가 발생했다고 볼 수는 없습니다. Gate가 열린 뒤 첫 실행은 시각만 기록하고, 그다음 실행이 첫 credit 예산을 만듭니다.

Q&A · mutex와 condition 초기화 후에 bucket을 게시하는 이유는 무엇인가요?

선택적인 control 생성에 실패하면 어떻게 될까요?

Bucket은 공유 페이지 credit 잔액입니다. Mutex는 한 번에 한 주체만 수정하게 하고, condition variable은 credit이 부족한 writer가 알림을 기다리게 합니다. Bucket 포인터가 공개되기 전에는 writer가 bucket을 찾을 수 없습니다. 초기화 오류가 나면 남는 자원도 오류 지점에 따라 다릅니다.

어느 초기화 오류든 반환되면 호출자는 retire()를 호출하지 않고 작업 객체를 삭제하며, control daemon을 생성하지 않습니다. Bucket 포인터가 공개되지 않았으므로 token 획득은 즉시 반환합니다. 다른 page-flush 경로들은 여전히 존재합니다.

초기화에 성공해도 사용할 실행 항목이 없으면 관리자 생성 함수가 NULL을 반환할 수 있습니다. 이 호출자는 반환값을 확인하거나 작업을 retire하지 않습니다. 메모리 할당이나 스레드 생성 예외를 처리하는 로컬 복구 코드도 없습니다. 소스에서 확인되는 정리의 한계이며, 실제 운영에서 이 실패에 도달했다는 증거는 아닙니다.

Q&A · 게시된 bucket이 없으면 writer가 token을 영원히 기다리나요?

아닙니다. bucket 포인터가 없으면 token 획득은 즉시 반환합니다. 이 우회로 pacing 부재를 설명할 수 있으며, 소스에 드러난 자원 정리 문제는 별도로 조사해야 합니다.

Writer는 쓰기 뒤 credit을 어떻게 소비할까요?

공유 bucket이 초기화되어 있고 일반 파일 writer가 쓰기를 수행하는 상황에서 시작합니다. 일반 writer는 로그 진행에 쓰이는 잠금 보호 구역인 log critical section을 소유하지 않습니다. OS 쓰기가 FILEIO_WRITE_DEFAULT_WRITE 모드로 성공했으므로 fileio_compensate_flush()에 들어갑니다.

  1. 이미 쓴 페이지마다 token 하나를 요청합니다.
  2. Bucket mutex 아래에서 사용 가능한 token을 소비하고 소비량을 기록합니다.
  3. Token이 요청량을 충족하면 잠금을 풀고 진행합니다. 부족하면 일반 writer는 condition variable에서 다음 예산을 기다릴 수 있습니다.

Condition 대기는 잠든 동안 mutex를 놓고, 반환하기 전에 다시 획득합니다. 따라서 갱신 작업이 bucket을 수정할 수 있습니다. Writer는 반환 후 mutex 아래에서 재시도합니다. 알림을 받았다는 사실만으로 token이 충분하다고 볼 수는 없습니다.

독립된 예시: Credit이 2개 남은 상태에서 이 일반 writer가 기본 모드로 페이지 3개를 한 묶음으로 쓰는 데 성공했습니다. 정산 중 다른 writer나 갱신은 끼어들지 않습니다. Token 2개를 소비하고 남은 페이지 1개의 정산을 기다릴 수 있습니다. 묶음은 이미 기록되었고, 잠든 동안 다음 작업이 늦어집니다.

즉, 쓰기 → 정산 → 부족하면 대기 → 다음 작업 순서입니다. 같은 writer가 반복해서 쓰는 경우 다음 쓰기를 늦춰 속도를 조절할 수 있습니다. 소스는 이 순서를 확인해 주지만, 최초 작성자가 왜 이를 선택했는지는 설명하지 않습니다. 쓰기 전에 credit을 예약하는 제한기는 다른 정책입니다.

Q&A · 여러 페이지를 OS 호출 한 번으로 썼다면 token도 하나만 요청하나요?

참여 경로에서는 시스템 호출당 하나가 아니라 페이지당 하나를 요청합니다. 따라서 한 번의 호출로 제출한 batch도 더 많은 credit을 요청할 수 있습니다.

Token 대기자는 공유 condition variable에서 기다린다

독립적인 대기 경로입니다. 일반 writer가 참여하는 OS 쓰기에 성공했지만, 이미 쓴 페이지를 정산할 credit이 부족합니다. TOKEN_BUCKET은 공유 credit 잔액을 담은 구조체이며, fc_Token_bucket이 가리킵니다. 함수의 tb는 그 bucket 포인터입니다. tokens는 잔액, token_mutex는 이를 보호하는 잠금, waiter_cond는 부족분을 기다리는 condition variable입니다. gen_tokens는 새 구간의 예산입니다.

/* fileio_flush_control_get_token */
pthread_cond_wait (&tb->waiter_cond, &tb->token_mutex);

/* fileio_flush_control_add_tokens: bucket mutex held */
tb->tokens = gen_tokens;
pthread_cond_broadcast (&tb->waiter_cond);

부족분을 기다리는 일반 writer는 bucket mutex를 놓고 잠듭니다. Flush-control은 같은 mutex 아래 잔액을 교체하고, 이 condition variable에서 대기 중인 writer들에게 broadcast로 재시도를 알립니다. 잠든 스레드의 등록과 깨우기는 POSIX condition-variable 구현이 맡습니다. CUBRID가 BCB의 next_wait_thrd 목록이나 direct-victim 큐에서 writer를 하나씩 꺼내는 경로가 아닙니다.

깨어난 writer들은 mutex를 다시 얻어 잔액을 검사하고 소비합니다. 다른 writer가 먼저 소비할 수 있으므로 broadcast가 모든 요청을 충족한다고 보장하지 않습니다. 이 경로는 이미 성공한 OS 쓰기 이후의 진행을 조절하며, 로그 critical section 소유자의 우회와 열 번의 대기 반환 후 탈출 조건도 유지됩니다. BCB의 flush 완료나 프레임 배정을 알리는 신호와 구분해야 합니다.

피드백은 다음 예산을 어떻게 바꿀까요?

적응형 제어는 이전에 생성한 예산에서 시작해 남은 token과 풀의 dirty 페이지 수를 확인합니다. Dirty는 메모리에 있는 페이지에 아직 기록할 변경 내용이 남았다는 뜻입니다.

  • 남은 token이 있고 dirty 압력 제안이 양수이면 이전 예산을 유지합니다. 그렇지 않으면 남은 token의 0.1배를 정수로 잘라 빼줍니다.
  • Token이 남지 않으면 dirty 압력의 제안과 이전 예산의 0.5배 중 큰 값을 더합니다.
  • 컴파일된 최저 속도 40 MiB/s를 실제 경과 시간과 I/O 페이지 크기에 맞춰 적용합니다.

Dirty 피드백은 페이지 수가 풀의 절반을 넘는 정도와, 보관한 이전 수치보다 증가한 정도에 반응합니다. 이 수치들, 잔액, 이전 예산은 실행 중 계산되는 상태입니다. 50 ms 주기, 절반이라는 목표, 최저 속도, 0.5 증가율, 0.1 감소율은 별도 운영자 설정이 없는 컴파일된 정책입니다.

누가 언제 bucket을 파괴할까요?

Control daemon이 실행 중이고 writer들이 공개된 bucket을 사용할 수 있는 상황입니다. 안전하게 정리하려면 bucket의 mutex와 condition variable을 파괴하기 전에 모든 의존 writer가 bucket 사용을 끝내야 합니다.

  1. 파괴를 요청한 호출자가 looper의 중지 플래그를 설정하고 잠든 daemon을 깨웁니다.
  2. 실행 중인 작업이 끝나면 worker가 반복문을 빠져나옵니다.
  3. Worker가 실행 context를 중지하고 retire한 뒤 작업의 retire()를 호출합니다. Control 작업이 여기서 bucket 공개를 해제하고 정리합니다.
  4. Worker 스레드가 종료합니다. 호출자의 join()이 반환한 다음 관리자가 daemon을 삭제하고 포인터를 비웁니다.

네 page-buffer 역할 중 control을 마지막으로 파괴합니다. 그룹 파괴 뒤에 풀·로그·DWB를 정리합니다. 재시작 오류에서는 먼저 boot gate를 닫고 page-buffer와 DWB 그룹을 파괴합니다. 중지 요청이나 포인터 초기화만으로 writer의 사용이 끝났다고 볼 수는 없습니다. Control 작업이 반환해야 해당 join도 끝납니다. 의존 writer의 I/O와 시간 제한 없는 token 대기는 bucket을 안전하게 파괴할 시점을 별도로 제약하며, 종료 시한을 보장하지 않습니다.

어떤 대입이 이전 예산을 버릴까요?

여기서 tb는 공유 token bucket을 가리키고, gen_tokens는 새로 계산한 예산이며, fc_Stats는 구간 정산 정보를 담습니다. 이 코드 앞에서 갱신 작업은 이미 bucket mutex를 획득했습니다.

/* initialization statistics */
fc_Stats.num_pages = 0;
fc_Stats.num_log_pages = 0;
fc_Stats.num_tokens = gen_tokens;

tb->tokens = gen_tokens;

/* signal to waiters */
pthread_cond_broadcast (&tb->waiter_cond);
pthread_mutex_unlock (&tb->token_mutex);

tb->tokens = gen_tokens는 잔액을 교체합니다. Broadcast는 잠든 writer들에게 재시도 기회를 줍니다. Writer는 mutex를 다시 획득하고 새 잔액을 검사해야 합니다. 이 대입이나 열 번 반환 후 탈출 조건 어느 것도 경과 시간이나 영속성의 보장이 되지는 않습니다.

Q&A · 깨어난 writer가 계속하기 전에 해야 할 일은 무엇인가요?

bucket mutex를 다시 얻고 공유 잔액을 확인하며, 우회·재시도 규칙에 따라 남은 요청의 credit을 소비해야 합니다. broadcast 자체는 그 writer를 위해 아무것도 예약하지 않습니다.

쓰기 전 제한에는 어떤 상태가 더 필요할까요?

독립된 설명용 대안입니다. 일반 writer가 안정된 이미지를 준비했지만 아직 제출하지 않은 상태에서 시작합니다. 쓰기 진입을 제한하려면 credit 판단을 OS 호출 앞으로 옮깁니다. 예약은 이 대기 중인 쓰기에 약속한 credit을 기록합니다.

  1. 보충 작업과 함께 사용하는 보호 아래에서 바이트·페이지 비용에 해당하는 예산을 예약합니다.
  2. 보충이나 로그 진행에 필요한 잠금 밖에서 기다리고, 면제된 호출자의 작업량을 어떻게 계산할지 정의합니다.
  3. 예약 후에도 write-ahead logging을 지킵니다. 데이터 제출 전에 필요한 복구 로그를 영속화합니다.
  4. 제출 전에 취소하면 예약한 credit을 돌려줍니다. 일부 제출이나 오류 이후에는 명시한 오류 규칙으로 실제 작업량을 기록합니다.

이 설계에는 예약과 취소 상태가 추가됩니다. Credit을 기다리면서 필요한 로그 잠금을 잡고 있으면 의존 순환이 생겨 deadlock에 빠질 수 있습니다. 남은 credit을 보관하면 나중의 집중된 쓰기에 쓸 수 있고, 교체하면 이전 예산을 버리며, 속도 조절을 제거하면 다음 작업이 즉시 진행합니다. 모두 정책 선택이며, 여기서는 장치 처리량을 측정해 우열을 매기지 않습니다.

Q&A · pre-write limiter에 취소 규칙이 필요한 이유는 무엇인가요?

writer가 credit을 예약하고도 이미지를 제출하지 않을 수 있습니다. 대안은 예약을 반환하거나 오류 시 실제 부분 작업을 집계해야 하며, WAL을 약화하거나 보충에 필요한 자원을 막아서는 안 됩니다.

카운터를 해석하려면 무엇부터 켜야 할까요?

실험을 제안하기 전에 카운터 수집과 각 사건의 시각을 기록하는 타임라인 probe를 구분합니다. 카운터를 켠다고 쓰기부터 대기까지의 이력이 새로 생기지는 않습니다.

  • extended_statistics_activation의 기본 마스크는 15입니다. Page-buffer victimization 비트 16과 daemon 비트 64는 제외됩니다. 해당 그룹 지표에 의존하기 전에 필요한 비트를 켭니다.
  • perfmon_initialize()는 시작 시 마스크를 캐시합니다. 일반 SQL 변경은 허용되지 않으므로 설정을 바꿔 효과를 내려면 재시작이나 재초기화가 필요합니다.
  • 적절한 실행 중 통계 유틸리티/API 또는 숨겨진 시작 옵션 stats_on(기본 false)을 통해 수집도 활성화해야 합니다. 시작 옵션은 가능한 방법 중 하나이지 필수 조건은 아닙니다.
  • 정산 통계는 참여하는 token 대기의 정산을 기록합니다. 앞선 OS 쓰기 지연, 우회한 작업, 페이지별 인과 타임라인을 기록하지는 않습니다.

Nonhidden으로 등록되었다는 사실만으로 안정적으로 문서화된 공개 계약이 되지는 않습니다. 일치하는 로컬 11.5 매뉴얼은 없었으며, 이 설정 설명은 확인한 고정 리비전에 한정됩니다. Probe 추가와 관측에 따른 영향 측정은 아직 제안입니다.

어떤 기록이 쓰기 뒤 정산이라는 설명을 반증할까요?

아직 실행하지 않은 독립된 실험 제안입니다. 정확한 고정 리비전과 build, 풀·로그·DWB·I/O 설정을 기록하고 시작합니다. 필요한 카운터와 수집을 활성화하고, 별도 타임라인 probe를 추가해 그 비용도 기록합니다.
