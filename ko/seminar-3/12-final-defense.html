Flush 성공만으로 정체를 설명할 수 있을까?

다시 Q로 돌아옵니다. “Flush가 성공했다”는 말만으로는 어느 이미지, 저장 경계, 현재 소유자를 관찰했는지 알 수 없습니다. 전체 여정을 잇는 프로토콜을 방어하고 최소 실행 순서로 위험한 생략을 반박한 뒤, 정체된 actor와 거절된 후보를 구별할 관측을 선택합니다. 마지막에는 전체 여정을 다시 연결합니다.

각 완료 기록은 identity, 이미지, 완료 경계를 명시해야 합니다. 현재 재사용에는 별도의 보호된 승인이 필요합니다. 진단은 입증된 사실과 관측 수단이 볼 수 없는 사실을 구분해야 합니다.

새 interleaving은 간단해 보이는 생략을 깨뜨립니다

하나의 “done” bit로 전체 여정을 설명할 수 없습니다

새 CUBRID 순서입니다. Allocator는 Q를 기다리고 F/P에는 LSA 120의 G가 있습니다. G 제출 뒤 writer가 LSA 180의 G+1을 만들고 unfix합니다. 현재 dirty 적합성 검사만 제거하고 WAL·이미지 작업은 유지합니다. 대안은 세대 완료 증거만 전달하고 재사용 권한은 따로 요청합니다.

  1. 1. G 제출

    구현된 조건
    completion pending
    단일 'done' 생략
    done=false
    구분한 증거 대안
    image(G,120) pending
    요청 / 현재 P
    Q waiting; P=G

    조건 / 가정: G의 WAL·사본 확보 전제가 충족됩니다.

    변화 / 결과: 제출은 완료 의무를 만들며 Q의 frame 소유권을 만들지 않습니다.

  2. 2. 새 writer가 P 변경

    구현된 조건
    DIRTY=1; fcnt returns to 0
    단일 'done' 생략
    old completion will imply done
    구분한 증거 대안
    image(G,120) unchanged
    요청 / 현재 P
    Q waiting; P=G+1 @180

    조건 / 가정: 사본 이후 writer가 진행할 수 있습니다. Unfix는 DIRTY를 지우지 않습니다.

    변화 / 결과: 수명 count와 세대 작업을 함께 추적해야 합니다.

  3. 3. G 완료

    구현된 조건
    clear FLUSHING; refuse dirty offer
    단일 'done' 생략
    done=true; unsafe retag
    구분한 증거 대안
    G receipt valid; reuse request rejected
    요청 / 현재 P
    Q still needs eligible frame

    조건 / 가정: 생략 모델은 이전 이미지 완료를 현재 frame 권한으로 취급합니다.

    변화 / 결과: 요청이 대기해도 안전성은 유지됩니다. 소스는 Q의 즉시 frame 확보를 약속하지 않습니다.

대안 protocol에는 명시적 증거와 비용이 필요합니다

설명용 대안: “이미지 G 수락”, “G bookkeeping 완료”, “현재 F reserve”, “이전 mapping 제거”를 구분한 receipt로 전달합니다. 각 receipt는 identity·세대·보호 구간과 취소 규칙을 명시합니다. Reservation은 새 사용자를 배제할 수 있으나 이미지 receipt를 수명 소유권으로 바꿔서는 안 됩니다.

연속 reservation은 동시성을 사용하고 방치된 예약의 정리가 필요합니다. 재검사는 metadata 읽기·동기화·retry 비용이 듭니다. Foreground completion은 CPU·I/O 대기를 요청 caller로 옮기고, background 작업은 다른 actor로 옮기는 대신 queue·수명 의존성을 만듭니다.

유효 scan, 이미지 복사, queue, 상태 전이 비용을 lock·WAL·저장장치·scheduler 지연과 따로 합산합니다. 조용한 순서의 구조 작업 상한이 동시 end-to-end 지연 상한은 아닙니다. Throughput 주장에는 통제한 workload, 저장장치 설정, pin duration, 반복 측정이 필요합니다.

D32 / D33 · 소스 경계를 지키며 방어하고 마무리합니다

Flush-completion counter가 증가하고 post-flush heartbeat도 정상인데 allocator Q가 기다립니다. 정확성을 지키는 원인 두 가지와 구분할 관측 하나를 제안해 보세요.

진단 논증 보기

완료 페이지 모두에 새 dirty 작업이 생겼거나, clean 페이지가 zone·private quota 정책을 통과하지 못할 수 있습니다. 둘 다 안전한 재사용을 지킵니다. BCB-lock snapshot과 이유별 거절 counter가 구별합니다. Heartbeat와 flush 합계만으로는 부족합니다. Wake 누락을 주장하기 전에 살아 있는 waiter 상태도 봅니다.

후속 질문: PostgreSQL도 write 수가 증가하면서 invalidation이 실패하면 re-dirty나 추가 pin일 수 있습니다. 비교하는 것은 책임 경계이며 Interface가 같다는 뜻은 아닙니다.

증거가 부족한 정체

어느 조건이 Q를 계속 막는가?

이제 G 완료는 확인했습니다. 현재 적합한 공급이 없는 경우와 Q가 제안을 받지 못한 경우가 남습니다. 두 설명을 구별할 관측을 선택합니다.

보호된 BCB 상태와 offer 사건 검사

P의 구성한 snapshot은 DIRTY=1, FLUSHING=0, fcnt=0이며 P의 offer는 공개되지 않았습니다. 완료 검사 전에 이후 writer가 dirty 의무를 만들었습니다. Q에는 다음 세대나 다른 적합한 frame이 필요합니다. Post-flush timer를 줄여도 이 의무는 없어지지 않습니다.

일관된 대안: 이미지 완료 기록과 현재 확보 분리

설명용 대안입니다. 명시한 성질을 보존하며 actor의 조정 방식을 바꿉니다.

  1. 각 기록에 이미지 identity와 정확한 수락·write·영속화 경계를 명시합니다.
  2. 이름 붙인 진행 중 이미지만 정리합니다.
  3. 현재 재사용에는 새 보호된 확보를 수행하고 새 사용이나 dirty 의무를 거절합니다.
  4. 실패하면 해당 의무를 재시도하며 기존 완료 기록을 현재 권한으로 승격하지 않습니다.

설명용 대안입니다. 명시적인 ticket·version 수명과 취소 소유권에는 metadata가 필요합니다. 연속 직렬화는 긴 배제를 선택하는 다른 대안입니다. 어떤 대체 방식도 WAL, 이미지 일관성, 새 의무, identity 수명, 발견 가능한 진행 경로를 함께 보존해야 합니다.

페이지 여정 마무리: 요청에서 프레임 재사용까지

  1. 호출자가 레코드 작업에 필요한 페이지를 찾습니다. 한 작업은 여러 페이지를 방문할 수 있습니다.
  2. 버퍼는 페이지 ID로 프레임과 BCB를 찾고, miss이면 적재합니다. Fix는 사용 기간을 보호하고, 호환되는 latch는 바이트 접근을 허용합니다.
  3. 대응하는 unfix로 사용 빚을 갚습니다. 일반적인 마지막 unfix에서 진입·재사용 정책이 갱신될 수 있지만, 곧 퇴출된다는 뜻은 아닙니다.
  4. 교체는 도메인과 후보를 고른 뒤 보호 아래 현재 안전 조건을 다시 확인합니다. Dirty 데이터는 보존해야 합니다. Background 작업은 진행을 도울 수 있지만 즉시 재사용할 프레임을 보장하지는 않습니다.
  5. 안전한 분리와 이전 매핑 제거 후에야 같은 프레임이 새 페이지 ID를 담을 수 있습니다. 주소가 같아도 이전 페이지가 계속 있다는 뜻은 아닙니다.

H1/H2가 남는지는 앞에서 확인한 재사용 순서와 정책 상태에 달려 있습니다. 다른 엔진도 재사용을 기억하지만 그 방법과 비용이 다릅니다. 이번 비교로 속도 순위를 정하지는 않았습니다.

Q23 · 다음 관찰 하나를 선택하기

구성한 시작 상태: 새로운 CUBRID 운영 사례에서 invalid frame은 없고 allocator 하나가 기다립니다. 관찰 구간의 flush 제출 성공 횟수는 20 늘었고 token 예산도 갱신됐습니다. 개별 BCB의 완료 경로, 현재 상태, 배정 기록은 없습니다. 제출 주체도 구분하지 않았습니다.

예측 질문: 다음 관찰을 하나만 추가할 수 있다면 무엇을 선택하겠습니까?

제출 주체부터 완료와 배정까지 연결한 BCB별 추적이 유용합니다. Enqueue 결과, 소비자 또는 caller 완료, 현재 flag·fix·zone·quota와 대기자·제안 결과를 함께 봅니다. Queue에 남아 있으면 소비자의 실행을, 소비됐지만 DIRTY나 fix 때문에 거절됐다면 현재 사용자와 보존 작업을 봅니다. 제출·token 합계만으로 둘을 구분할 수는 없습니다.
