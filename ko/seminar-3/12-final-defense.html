이미지가 완료돼도 할당자는 계속 기다릴 수 있습니다

Q는 프레임 할당을 기다리는 요청 스레드입니다. 프레임은 페이지 하나를 담는 메모리 슬롯이며, 풀은 가득 차 있습니다. 페이지는 저장 공간의 논리적 식별자입니다. 프레임에는 현재 바이트가 있고, BCB는 그 프레임과 짝을 이루는 고정된 메타데이터 객체입니다. 같은 주소를 재사용한다고 이전 페이지 식별자가 남아 있어서는 안 됩니다.

다른 호출자가 메모리의 페이지를 바꾸거나 계속 사용하는 동안, flush는 앞서 복사한 이미지를 완료할 수 있습니다. “Flush가 성공했다”는 말 뒤에는 세 질문이 남습니다. 어느 이미지가 완료됐는가, 지금 이 프레임을 재사용할 수 있는가, 전체 할당은 왜 기다리는가입니다.

기록에 이미지와 정확한 저장 경계를 명시합니다. 적절한 보호 아래 현재 재사용 조건을 검사합니다. 시스템 전체 정체의 원인은 가능한 여러 경로를 관찰한 뒤에 판단합니다.

경계마다 보호하는 책임이 다릅니다

호출자는 특정 주소가 아니라 논리적 페이지가 필요합니다. 메모리의 프레임에는 바이트가 있고 BCB에는 식별자와 상태가 있습니다. CUBRID의 fix와 PostgreSQL의 pin은 사용하는 동안 프레임이 재사용되지 않게 보호합니다. Latch나 content lock은 바이트 접근을 별도로 제어합니다.

  1. 호출자는 페이지를 읽거나 바꾸기 전에 사용 보호와 호환되는 바이트 접근 권한을 확보합니다.
  2. 로그를 남기는 변경은 복구 로그와 데이터 전달 작업을 만듭니다. 반납은 사용 보호를 끝내지만 그 작업까지 끝내지는 않습니다.
  3. Flush 수행자는 안정된 바이트를 해당 WAL 기준에 맞춰 제출합니다. 필요한 복구 로그를 데이터보다 먼저 보존하는 기준입니다. 완료는 그 이미지에만 해당합니다.
  4. 보호가 끊긴 구간을 지난 뒤에는 후보 선택자, 완료 소비자, 수령자가 각자의 보호 조건 아래 현재 식별자, 사용자, 남은 작업을 다시 검사합니다.
  5. 재사용 경로는 후보를 안전하게 분리하고 이전 식별자 매핑을 제거한 뒤 프레임을 다른 페이지에 연결합니다.

Writer가 반납해도 새 변경의 전달 의무는 남습니다

독립적인 CUBRID 반례입니다. Q는 프레임을 기다리는 할당자입니다. F는 논리적 페이지 P를 담는 메모리 슬롯입니다. G는 로그 위치 120에서 확보한 이미지, G+1은 이후 writer가 180에 로그를 남긴 뒤의 내용을 가리킵니다. 세대를 추론하기 위한 이름이며 저장된 카운터가 아닙니다. P의 식별자는 그대로입니다. 이 server-mode 사례의 이후 writer는 vacuum worker, 즉 더 이상 필요 없는 데이터를 정리하는 백그라운드 스레드입니다. P는 임시 볼륨이 아닌 볼륨의 영구 페이지이며, 교체에 가까운 차가운 구역인 shared LRU3에 있습니다.

BCB는 F의 고정된 메타데이터 객체입니다. Fix는 현재 사용을 보호하고 write latch는 변경을 제어합니다. DIRTY는 메모리의 내용 중 아직 전달해야 할 작업을, FLUSHING은 확보한 이미지의 미완료 작업을 나타냅니다. fcnt 필드는 fix 수를 셉니다. Vacuum worker의 unfix는 fcnt를 낮추지만 DIRTY를 지우지 않습니다. 마지막 unfix는 일반적인 LRU3 승격을 건너뜁니다. DIRTY 또는 FLUSHING은 조기 직접 제안도 막습니다. 따라서 완료 검사 때도 F는 LRU3에 남습니다. 다른 주체가 이를 옮기지 않으며, 변경 작업도 특별한 리스트 이동을 요청하지 않습니다.

Flush 수행자는 BCB mutex를 보유하고 경쟁하는 WRITE 소유자를 배제한 상태에서 안정된 바이트와 해당 로그 위치를 함께 확보합니다. WAL은 이미지 제출 전에 필요한 복구 로그를 보존합니다. 사본 확보를 위한 보호가 끝나면, 이전 사본을 제출하는 동안 이후 writer가 메모리의 바이트를 바꿀 수 있습니다.

전역 done 지름길 실행 열은 구성한 최종 재사용 프로토콜을 나타냅니다. 이전 이미지의 완료를 이전 식별자 제거 권한으로 삼고, 제안·수령·새 식별자를 연결하는 최종 retagging의 현재 DIRTY 검사를 모두 우회합니다. 이미지, WAL, 식별자, 사용, 정책에 관한 나머지 요구 조건은 유지합니다. 고정 소스에서 소비자의 DIRTY 검사 하나만 지워도 뒤쪽 경로의 DIRTY 검사는 남습니다. 아래 추적은 이 설명용 지름길을 실제 구현의 거절 경로 및 이미지와 현재 상태의 기록을 구분하는 대안과 비교합니다.

이전 이미지는 완료하고 새 dirty 작업은 유지합니다

이전 이미지의 완료와 새 메모리 작업이 만납니다

이 독립적인 실행 순서의 시작 상태로 초기화합니다. Q는 기다리는 할당자입니다. 프레임 F에는 페이지 식별자 P가 있고 고정된 BCB에는 메타데이터가 있습니다. G는 로그 위치 120의 사본, G+1은 180의 이후 메모리 작업을 가리킵니다. 추론을 위한 이름입니다. 실행 열의 P=G는 P의 내용을 뜻합니다.

시작 상태는 DIRTY=0(새 작업 없음), FLUSHING=1(이전 사본 미완료), fcnt=0(fix 없음)입니다. 사본 확보 때 BCB mutex를 보유하고 경쟁 writer를 배제했으며, 해당 복구 로그를 데이터보다 먼저 보존하는 WAL 기준을 충족했습니다. P는 임시 볼륨이 아닌 볼륨의 영구 페이지이고, 차가운 victim 구역인 shared LRU3에 있습니다. Writer는 백그라운드 정리 스레드인 server-mode vacuum worker입니다. 마지막 unfix는 일반적인 구역 승격을 건너뛰고, DIRTY/FLUSHING은 조기 제안을 막습니다. Flush 대기자를 포함해 BCB에 연결된 대기자나 다른 이동·무효화 flag는 개입하지 않습니다. Q는 별도의 할당 대기자 queue에서 중단된 상태를 유지합니다.

예측: 구성한 전역 done 지름길 프로토콜은 제안·수령·새 식별자를 연결하는 최종 retagging에 걸쳐 현재 DIRTY를 우회하며 나머지 요구 조건은 유지합니다. 고정 소스에는 각 경계의 DIRTY 검사가 있으므로 소비자 검사 하나만 삭제해서는 이 지름길을 구현할 수 없습니다. Vacuum worker가 unfix한 뒤 최종 재사용을 하면 무엇을 잃게 될까요?

  1. 1. G 제출

    구현된 조건

    전역 done 지름길
    done=false
    구분한 증거 대안

    조건 / 가정: 안정된 사본 확보와 해당 WAL-before-data를 완료한 뒤 제출에 성공했습니다.

    변화 / 결과: 완료 작업은 위치 120의 사본에 해당합니다. Q가 재사용할 프레임은 아직 없습니다.

  2. 2. Vacuum worker가 P 변경

    구현된 조건
    DIRTY=1; fcnt returns to 0
    전역 done 지름길
    old completion will imply done
    구분한 증거 대안
    image(G,120) unchanged
    요청 / 현재 P
    Q waiting; P=G+1 @180

    조건 / 가정: Vacuum worker는 P를 fix하고 write latch 아래 변경과 로그 기록을 수행한 뒤 unfix합니다. 마지막 unfix 뒤에도 shared LRU3와 DIRTY는 유지되며, 남아 있는 DIRTY/FLUSHING이 조기 제안을 막습니다.

    변화 / 결과: fcnt는 0으로 돌아가고 F는 LRU3에 남지만, 새 작업은 여전히 전달해야 합니다. 위치 120의 사본은 바뀌지 않습니다.

  3. 3. G 완료

    구현된 조건
    clear FLUSHING; refuse dirty offer
    전역 done 지름길
    done=true; unsafe retag
    구분한 증거 대안
    G receipt valid; reuse request rejected
    요청 / 현재 P
    Q still needs eligible frame

    조건 / 가정: 실제 구현의 소비자는 BCB mutex를 보유합니다. Shared LRU3, fix 없음, BCB에 연결된 대기자 없음(flush 대기자 포함), 살아 있는 Q라는 조건은 여전히 통과합니다. 완료 경로는 이전 FLUSHING을 허용합니다. 현재 DIRTY는 제안을 거절하게 하지만, 구성한 지름길은 최종 재사용까지 그 의무를 무시합니다.

    변화 / 결과: 완료는 G의 작업을 끝낼 뿐 새 작업을 끝내지 않습니다. 설명용 최종 재사용 지름길은 새 작업을 버립니다. 실제 구현과 별도 기록 대안은 Q를 계속 기다리게 합니다.

대안은 각 기록이 허용하는 행동을 명시해야 합니다

설명용 설계이며 새 실행 사례가 아닙니다. F는 페이지가 들어 있는 프레임, P는 그 안의 현재 페이지 식별자, G는 그 페이지에서 확보한 이미지입니다. BCB는 여전히 프레임의 메타데이터 객체입니다. 할당자는 F를 재사용하려 하지만, 사본 확보 보호가 끝나면 다른 호출자가 P를 사용하거나 바꿀 수 있습니다.

각 기록의 의미를 구분합니다. “이미지 G 수락”, “G의 완료 상태 정리 완료”, “현재 F 예약”, “이전 매핑 제거”입니다. 기록은 이름 붙인 사건의 증거입니다. 페이지 식별자, 이미지, 정확한 완료 경계, 보호 구간, 취소 책임자를 명시합니다.

예약이 현재 사용 권한을 부여하려면 경쟁하는 모든 조회·사용 경로가 그 배제를 따라야 합니다. 이미지 수락은 그런 배제를 제공하지 않습니다. 이후 수령자는 예약을 유지하거나, 보호 아래 현재 식별자·사용·dirty 상태를 다시 검증해야 합니다.

검사를 없애면 작업과 대기가 다른 곳으로 옮겨갑니다

같은 workload 아래 프로토콜을 비교합니다. 예약을 계속 유지하면 보호 구간 내내 새 사용자를 배제합니다. 동시성이 줄어들고, 소유자가 요청을 포기하면 예약을 정리해야 합니다. 이후 재검사를 택하면 그사이 다른 사용이 가능하지만, 메타데이터 읽기·동기화·재시도 비용을 치릅니다.

Foreground에서 완료하면 요청한 호출자가 CPU 작업과 I/O 대기를 부담합니다. Background 완료는 다른 곳에서 비용을 부담하며 queue, 스케줄링, worker 수명에 대한 의존성이 생깁니다. WAL 대기는 필요한 복구 로그를 기다리고, 저장장치 대기는 선택한 제출 또는 영속화 경계를 기다립니다.

유효한 scan, 이미지 복사, queue, 상태 전이 작업을 lock·WAL·저장장치·scheduler 지연과 구분해 셉니다. 다른 간섭이 없는 실행 순서의 작업량 상한은 동시 요청의 지연 상한이 아닙니다. 처리량 주장에는 통제한 workload, 저장장치 설정, 사용 보호 기간, 반복 측정이 필요합니다.

한 후보의 거절 이유만으로 전체 대기를 설명할 수 없습니다

기다리는 할당자에게는 적합한 프레임과 필요한 작업을 실행하는 주체가 필요합니다. 제안을 사용한다면 보호된 수령 검사 때까지 그 권한도 유지돼야 합니다.

현재 DIRTY는 메모리의 변경을 아직 전달해야 한다는 뜻입니다. Fix나 pin은 호출자가 사용 보호를 여전히 보유한다는 뜻입니다. CUBRID의 zone·private quota 검사는 보존 정책입니다. 충분히 차가운 구역과 예산을 초과한 private 리스트는 제안을 허용할 수 있지만, 정책이 안전 조건을 무시할 수는 없습니다.

앞의 표는 가설을 나열합니다. 경과 시간과 wake 횟수만으로 어느 하나를 선택할 수 없습니다. Fault injection에서는 실패시키는 경계와 유지돼야 할 상태를 명시합니다. 미완료 이미지 작업, 메모리의 dirty 작업, 이전 식별자, 사용 보호, 또는 취소된 제안 중 무엇인지 밝혀야 합니다.

D32 · 새 dirty 작업과 정책상 남겨 둔 clean 페이지를 구별합니다

독립적으로 구성한 사례입니다. Q는 프레임을 기다리는 할당자입니다. 프레임에는 페이지 바이트가 있고 BCB에는 식별자, DIRTY(전달해야 할 변경), 현재 fix(사용 보호)가 기록됩니다. 이미지 완료 합계가 증가하고 post-flush heartbeat는 작업이 실행됨을 보여 줍니다. 프레임별 거절이나 수령 이력은 없습니다.

공개된 규칙: 소비자는 BCB mutex 아래 검사합니다. 새 DIRTY나 현재 사용자는 제안을 막습니다. 추가로 전달할 변경이 없고 사용하지 않는 clean 페이지라도 zone(보존 단계)이나 private quota(교체 리스트 예산) 때문에 남겨 둘 수 있습니다. 살아 있는 할당 대기자도 필요합니다.

정확성을 유지하면서 대기를 일으키는 원인 두 가지와 이를 구별할 관측 하나를 제안해 보세요.

진단 논증 보기

완료된 모든 페이지에 새 dirty 작업이 생겼거나, clean 페이지가 zone·private quota 정책을 통과하지 못할 수 있습니다. 보호된 BCB snapshot과 이유별 거절 사건은 이를 구별하지만 heartbeat와 완료 합계는 구별하지 못합니다. 이 사건을 관찰하려면 새 probe가 필요할 수 있습니다. Wake 누락을 주장하기 전에 살아 있는 대기자 상태를 확인합니다.

후속 질문: PostgreSQL도 write 횟수가 증가하는 동안 최종 식별자 invalidation이 새 dirty 작업이나 추가 pin 때문에 거절될 수 있습니다. Pin은 재사용으로부터 사용을 보호하고, 매핑·헤더 보호는 최종 판단을 지킵니다. 각 엔진의 고유 인터페이스를 유지하면서 책임을 비교합니다.

D33 · 재검사를 없애려면 대체 보호가 필요합니다

독립적인 변경 검토 사례입니다. 선택자는 프레임 안의 페이지를 관찰한 뒤 보호를 해제하고 나중에 재사용을 시도합니다. BCB 주소는 고정돼 있어도 식별자, 현재 사용자, dirty 작업은 바뀔 수 있습니다. 제안된 최적화는 비용을 줄이기 위해 보호된 재검사 하나를 없앱니다.

안전 요구 조건은 그대로입니다. 이전 매핑을 제거하기 전에 모든 활성 사용자의 식별자와 남은 변경을 보존해야 합니다. 최적화를 받아들이려면 어떤 논증이 필요할까요?

변경 논증 보기

1단계: 완료 소비자가 실행됐나요?

새 단계적 CUBRID 사례를 시작합니다. Q는 가득 찬 풀의 유일한 할당 대기자이며, 사용하지 않는 invalid 프레임은 없습니다. F는 페이지가 들어 있는 프레임 하나이고 P는 그 논리적 페이지 식별자입니다. G는 P에서 안전하게 확보한 이미지를 가리킵니다. 세대 이름은 추론용 표기입니다. G 제출은 설정된 수락·write 경계에서 성공했고, F의 고정된 BCB 포인터가 완료 queue에 들어갔습니다. 이 전제는 원래 데이터 페이지의 저장 위치까지 동기화해 영속화했음을 뜻하지 않습니다.

BCB는 F의 메타데이터 객체입니다. FLUSHING은 미완료 이미지를, DIRTY는 메모리의 내용 중 아직 전달해야 할 작업을 나타냅니다. 완료가 진행 중인 동안 다른 호출자가 P를 fix하고 write latch 아래 바꾼 뒤 unfix할 수 있습니다. Unfix는 사용 보호를 끝내지만 DIRTY를 지우지 않습니다. Post-flush 소비자는 BCB를 잠근 뒤 이전 이미지를 완료하고 제안 여부를 판단해야 합니다.

현재까지 아는 사실은 dirty 페이지가 남아 있고 wake 횟수가 늘었다는 것입니다. Task 진입, queue 소비, 현재 BCB 상태, 제안은 기록되지 않았습니다. 소비자 미실행과 작업 완료를 구별하려면 다음에 무엇을 관찰할까요?

Task 진입과 queue 소비 관찰

구성한 사건 기록에서 post-flush는 실행됐고, G를 완료하기 위해 queue에서 F의 BCB를 꺼내 이전 FLUSHING을 해제했습니다. 이 사례에서는 G의 완료 상태 정리가 이루어졌습니다. 이 기록만으로 제안, 수령 성공, 원래 데이터 페이지의 저장 위치까지 동기화한 영속화를 입증할 수는 없습니다.

2단계: 왜 이 프레임을 제안하지 않았나요?

1단계를 그대로 이어 갑니다. 초기화하지 않습니다. Q는 여전히 할당 대기자입니다. F는 논리적 페이지 P를 담는 프레임이며 고정된 BCB에는 메타데이터가 있습니다. G는 완료된 사본입니다. G+1은 사본 확보 뒤 writer가 P를 바꿨다면 생겼을 이후 메모리 내용을 가리킵니다. 저장된 카운터가 아닌 추론용 이름입니다.

알고 있는 증거는 소비자가 실행됐고 F의 완료 항목을 소비한 뒤 이전 FLUSHING을 해제했다는 것입니다. 현재 재사용은 별도 판단입니다. BCB mutex 아래 새 DIRTY나 현재 fix·대기자는 제안을 막습니다. 보존 정책(차가운 구역, private이면 예산을 초과한 리스트)과 살아 있는 할당 대기자 조건도 통과해야 합니다. fcnt는 남아 있는 fix 수를 셉니다.

소비자가 현재 상태를 거절했을까요, 아니면 제안 후 수령이 실패했을까요? F의 두 경로를 구별할 관측을 선택해 보세요.

보호된 BCB 상태와 제안 사건 검사

구성한 snapshot은 DIRTY=1, FLUSHING=0, fcnt=0입니다. F의 제안은 게시되지 않았습니다. 연결해 기록한 writer 사건은 완료 검사 전에 G+1이 생겼음을 보여 줍니다. Writer가 fix를 반납했어도 현재 dirty 상태 때문에 거절됐다는 결론을 뒷받침합니다. Q에는 최신 내용의 전달이나 다른 적합한 프레임이 필요합니다. Post-flush timer를 줄여도 이 의무는 없어지지 않습니다.

3단계: 전체 정체를 어디까지 설명했나요?

2단계를 그대로 이어 갑니다. 초기화하지 않습니다. Q는 기다리는 할당자, F는 검사한 프레임, P는 그 안의 현재 논리적 페이지입니다. BCB mutex 아래 기록한 상태는 DIRTY=1, FLUSHING=0, fcnt=0이고 제안은 없었습니다. 이 사실은 그 검사에서 F가 거절된 이유를 설명합니다.

전체 대기 시간, 다른 후보, 이후 writer, WAL 진행, 수령 결과는 아직 모릅니다. WAL은 복구 로그이며, 영속화가 끝난 로그 위치는 각 사본이 요구하는 로그 위치까지 보존했는지를 알려 줍니다.

VS-20은 고정 리비전의 유지보수 루프 이상을 가리키는 미확정 사항 등록부의 식별자입니다. 할당자에 미치는 영향은 측정하지 않았습니다. 확인할 다른 원인 후보이며, 이 사례에서 관찰한 원인은 아닙니다. 이 프레임 하나의 결과와 시스템 전체 대기를 연결하려면 다음에 무엇을 측정해야 할까요?

검사한 전체 후보, WAL 영속화 위치, 수령 결과 연결

대기 구간 전체에서 후보 식별자와 거절 이유, 완료·배정 생산자, 필요한 로그 위치와 영속화 위치, 보호된 수령 결과를 기록합니다. 이를 연결하지 않으면 전체 정체를 P, VS-20, scheduler 공정성, 저장장치 처리량 중 하나에 돌릴 수 없습니다. 여러 설명이 여전히 가능합니다. 이 범위가 제한된 미확정 결론은 구성한 증거가 뒷받침하며, 실제 실행의 진단 기록은 아닙니다.

이미지 기록과 현재 재사용 권한을 구분합니다

진단 사례와 독립적인 설명용 대안입니다. F는 페이지 식별자 P를 담는 프레임입니다. G는 확보한 사본, G+1은 이후 변경으로 생긴 메모리 내용을 가리킵니다. 어느 세대 이름도 저장된 카운터가 아닙니다. BCB는 고정된 메타데이터 객체이며 할당자는 F를 재사용할 권한이 필요합니다.

  1. 제출한 이미지에 식별자와 세대를 명시하는 ticket을 부여합니다. 기록이 수락, write, 특정 저장 경계의 영속화 중 무엇을 뜻하는지 정합니다.
  2. 완료 시에는 해당 ticket의 미완료 작업만 끝냅니다. 이후 메모리의 dirty 작업은 유지합니다.
  3. 현재 재사용을 위해 보호를 확보하고 식별자, 사용자, dirty 작업을 새로 검사합니다. 이 조건과 선택한 정책이 허용할 때만 이전 매핑을 제거합니다.
  4. 오류나 취소가 발생하면 이전 식별자와 남은 작업을 보존하고 ticket·예약을 올바르게 해제합니다. 재시도할 수 있도록 남은 의무를 찾아낼 수 있어야 합니다.

명시적인 ticket·version 수명과 취소 책임에는 메타데이터가 추가됩니다. 연속 직렬화도 일관된 대안입니다. 모든 조회·사용 경로가 완료와 이전 식별자 제거까지 배제를 따라야 하며, 동시성과 대기 비용을 치릅니다. 어느 설계든 WAL(해당 복구 로그를 데이터보다 먼저 보존), 안정된 이미지 바이트, 이후 변경, 식별자 수명, 진행 가능한 경로를 유지해야 합니다.

어떤 관측이 이 진단 설명에 반례가 되나요?

아직 실행하지 않은 실험 제안입니다. 가득 찬 풀과 할당 대기자 하나를 두고, 안전한 사본 확보와 완료 사이에 writer를 통제해 진행시킵니다. 프레임은 논리적 페이지의 바이트를 담고 고정된 BCB는 완료와 현재 재사용 상태를 기록합니다. 두 엔진의 전체 고정 리비전, build, pool·log·DWB·I/O 설정, workload를 기록합니다. DWB는 CUBRID의 후속 double-write staging 서브시스템입니다.

가설
보호 아래 거절된 사건을 다른 사건과 연결하면 검사한 프레임이 제안되지 않은 이유를 알 수 있습니다. 완료 합계만으로는 재사용 가능한 공급을 알 수 없습니다.
통제하는 변화
위의 세 단계 화면을 사용합니다. 구성한 관측값을 공개하기 전에 관측 대상을 선택합니다. 실제 probe에서는 이후 writer의 개입 여부만 바꿉니다. CUBRID와 PostgreSQL의 실행 순서는 따로 구성합니다.
정확한 관측
제안하는 probe는 식별자, 확보한 로그 위치, 현재 사용·dirty 상태, enqueue·소비, 생산자의 배정, 보호된 수령 결과를 연결합니다. 프레임과 식별자로 사건을 맞춥니다. 빠진 기록을 만들어내지 않습니다.
반증 기준과 한계
보호된 현재 DIRTY가 적합성을 거절하는 상태에서 제안이 게시된다면 이 메커니즘 설명에 반례가 됩니다. 전체 사건 흐름에 여러 원인이 들어맞는다면 유일한 근본 원인은 입증되지 않습니다. 관찰 오버헤드, scheduler 제어, 관찰 기간은 실제 실행의 결론 범위를 제한합니다.

사용·반납·재사용을 거치는 식별자를 따라갑니다

페이지는 호출자가 요청한 논리적 객체입니다. 프레임은 현재 메모리 슬롯이고 BCB는 그 슬롯과 짝을 이루는 고정된 메타데이터 객체입니다. 이 복습은 책임의 순서이며, 새로 구성한 실행 사례가 아닙니다.

  1. 호출자는 레코드 작업에 필요한 페이지를 찾습니다. 한 작업은 여러 페이지를 방문할 수 있습니다.
  2. 버퍼는 식별자로 메모리의 프레임과 BCB를 찾고 miss이면 적재합니다. Fix는 사용 수명을 보호하고 호환되는 latch는 바이트 접근을 제어합니다.
  3. 모든 fix에 대응하는 unfix로 사용 빚을 갚습니다. 일반적인 마지막 unfix는 진입·보존 정책을 갱신할 수 있지만 퇴출이나 영속화를 약속하지 않습니다.
  4. 교체는 도메인과 후보를 고른 뒤 보호 아래 현재 안전 조건을 검사합니다. Dirty 변경은 전달해야 합니다. Background 작업은 도울 수 있지만 즉시 재사용할 프레임을 보장하지 않습니다.
  5. 안전하게 분리하고 이전 매핑을 제거하면 같은 프레임에 새 식별자를 연결할 수 있습니다. 고정된 프레임·BCB 주소가 이전 페이지를 유지하는 것은 아닙니다.

H1과 H2는 앞선 hot set에서 반복해 읽는 논리적 페이지의 이름입니다. 계속 메모리에 남는지는 재사용 순서와 정책 상태에 달려 있습니다. 비교에서는 재사용을 기억하고 비용을 나누는 서로 다른 방식을 보았으며, 속도 순위는 입증하지 않았습니다.

마지막 CUBRID 사례: 완료된 페이지를 writer가 계속 사용합니다

제출은 늘지만 할당자는 계속 기다립니다

앞선 모든 사례와 독립적인 새 CUBRID 순서입니다. B는 direct-victim 제안을 기다리는 할당자이고 A는 이후 writer입니다. 사용하지 않는 invalid 프레임은 없습니다. F는 논리적 페이지 P가 들어 있는 프레임이며 고정된 BCB에는 현재 상태가 있습니다. G는 확보한 사본, G+1은 이후 메모리 내용을 가리킵니다. 추론용 표기입니다.

Flush 수행자는 BCB mutex를 보유하고 경쟁하는 WRITE 소유자를 배제한 상태에서 G를 확보한 뒤 WAL 규칙을 지켜 제출에 성공했습니다. WAL은 데이터 제출 전에 해당 복구 로그를 보존합니다. FLUSHING이 유지된 채 BCB 포인터가 enqueue됐습니다. 소비 전에 A가 P를 fix하고 write latch 아래 바꾼 뒤 DIRTY를 설정하며 fix를 유지합니다. Fix는 현재 사용을 보호하고 DIRTY는 새 작업을 전달해야 한다는 뜻입니다.

이제 소비자가 실행돼 BCB를 잠급니다. 제안하려면 새 DIRTY와 현재 사용자가 없어야 하고, 차가운 victim 구역, private이면 예산을 초과한 리스트, 살아 있는 할당 대기자 조건도 필요합니다. Zone과 quota는 보존 정책이며 quota는 리스트의 예산입니다. 어느 이전 작업을 완료하고, 무엇이 제안을 막을까요? 소비자 미실행과 배정 거절을 구별할 관측은 무엇일까요?

마지막 PostgreSQL 사례: ring 항목을 거절해도 공유 페이지는 유지됩니다

Bulk-read가 ring을 벗어납니다

CUBRID와 독립적인 새 PostgreSQL 순서입니다. R은 dirty 영구 페이지(BM_PERMANENT)를 담는 공유 프레임과 descriptor의 이름입니다. H는 별도의 hot 공유 프레임 이름입니다. Bulk-read backend의 로컬 ring 슬롯에는 R의 Buffer ID가 있고 슬롯 자체에 페이지 바이트는 없습니다. 다른 backend가 H의 pin을 유지해 페이지 식별자가 재사용되지 않도록 보호합니다.

처음에 R에는 pin이 없고, 작은 보존 점수인 usage credit은 1입니다. Bulk-read backend는 pin으로 R 확보에 성공하고 조건부 share-exclusive content lock도 획득합니다. 페이지의 복구 로그 위치인 LSN까지는 WAL flush가 여전히 필요합니다. WAL은 영구 데이터 write 전에 보존하는 복구 로그입니다.

공개된 규칙: BULKREAD는 WAL flush가 필요하기 때문에 이 dirty 영구 ring 후보를 거절합니다. 전역 선택으로 fallback해도 현재 pin을 따라야 합니다. 최종 식별자 제거에서도 매핑·헤더 보호 아래 현재 dirty·사용 상태를 검사합니다. Ring 슬롯과 공유 R에서는 무엇이 바뀔까요? Fallback이 pin 중인 H를 덮어쓸 수 있을까요?

G는 메모리의 페이지에서 확보한 이미지 하나를, G+1은 이후 변경으로 생긴 내용을 가리킵니다. 저장된 카운터가 아닌 추론용 표기입니다. 마지막 복습이며 새 실행 사례로 초기화하지 않습니다. 프레임에는 바이트가 있고 고정된 BCB에는 현재 식별자와 상태가 기록됩니다.
