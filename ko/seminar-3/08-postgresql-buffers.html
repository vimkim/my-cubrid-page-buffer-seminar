PostgreSQL: 페이지를 메모리에 유지하고 바이트 접근을 보호하기

CUBRID 페이지 버퍼 daemon과 PostgreSQL 페이지 교체

자주 다시 읽는 페이지, 대량 스캔, 아직 기록하지 않은 변경이 있는 페이지가 유한한 버퍼 풀을 함께 사용합니다. 각 질문과 상태 추적은 독립된 시작 상태를 가집니다. 앞 사례의 사건을 다음 사례로 이어 가지 않습니다. 소스 동작은 아래 고정 리비전을 기준으로 합니다. 성능 설명은 추론이며 측정 결과가 아닙니다.

메모리의 같은 주소가 왜 계속 같은 페이지를 가리켜야 할까?

한 요청은 작은 페이지 집합을 반복해서 읽고, 대량 스캔은 새로운 페이지를 요청합니다. PostgreSQL의 공유 버퍼 풀은 가득 차 있습니다. 메모리에 있는 페이지 중에는 아직 기록하지 않은 변경이 있는 것도, 여전히 사용 중인 것도 있습니다. 없는 페이지를 적재하려면 서버가 먼저 안전하게 재사용할 프레임을 찾아야 합니다.

논리 페이지는 식별자가 있는 데이터베이스 데이터 블록입니다. 프레임은 페이지 하나의 바이트를 담는 메모리 슬롯입니다. 공유 buffer descriptor는 프레임의 현재 페이지 식별자와 제어 상태를 저장하는 메타데이터입니다. 역할상 CUBRID의 BCB(프레임별 제어 레코드)에 대응합니다. 프레임을 재사용하면 그 안의 페이지가 바뀌지만, descriptor의 배열 위치는 그대로입니다.

backend는 PostgreSQL 서버 프로세스입니다. 나중에 쓰려고 주소를 보관하고 있다면, 교체 과정이 그 주소에 다른 페이지를 넣어서는 안 됩니다. 현재 페이지의 읽기와 쓰기를 조정하는 것은 별도의 책임입니다.

Pin은 어떻게 페이지를 메모리에 유지할까?

Backend(서버 프로세스)가 공유 프레임에 이미 적재된 페이지를 사용하려 합니다. 프레임은 페이지 바이트를 담는 메모리 슬롯입니다. Backend는 pin을 획득합니다. Pin은 사용 중임을 기록하여 교체 과정이 그 프레임을 다른 페이지에 재사용하지 못하게 합니다. Content lock은 이와 별도로 페이지 바이트에 대한 연산을 조정합니다.

Backend가 앞서 획득한 pin을 반납하기 전에 같은 프레임을 다시 pin하면 사용이 중첩됩니다. Private 참조 수는 그 backend가 반납해야 할 pin의 수를 기록합니다. 일반적인 backend pin에서는 공유 참조 수에 아직 사용이 남은 backend마다 1씩 기록합니다. 아직 파일 연산이 진행 중인 비동기 I/O가 자체 수명 pin을 더할 수 있으므로, 공유 참조 수가 항상 backend 수인 것은 아닙니다. “Private”은 기록을 각 backend가 따로 관리한다는 뜻입니다. 프레임과 바이트는 계속 공유합니다.

보존 크레딧은 사용하지 않는 페이지가 교체 대상으로 선택되기 전에 추가 기회를 받게 합니다. Descriptor는 이 보존 선호를 usage_count로 저장합니다. 기본 전략에서는 backend의 private 참조 수가 0이 된 뒤 첫 pin을 획득할 때 크레딧을 1 더하며, 상한은 5입니다. 중첩 pin은 크레딧을 더하지 않습니다. 크레딧은 페이지를 사용할 권한이 아닙니다.

여러 클라이언트가 쓰는 페이지는 어떻게 보호할까?

클라이언트 요청은 PostgreSQL 서버 프로세스인 backend에서 실행됩니다. 여러 backend가 공유 프레임에 있는 같은 페이지를 사용할 수 있습니다. 프레임은 페이지 하나의 바이트를 담는 메모리 슬롯입니다. Descriptor는 그 프레임의 메타데이터이며, 공유 pin 수는 재사용을 막는 기여를 기록합니다. 각 backend는 반납 전에 다시 획득한 중첩 사용을 자신의 private 기록에 남깁니다. 공유 참조 수는 사용자의 이름을 기록하지 않고도 그 사용을 보호합니다.

버퍼 풀 전체가 공유하는 clock hand는 다음에 검사할 descriptor를 고르는 커서입니다. Pin 수는 descriptor마다 따로 있으며, 풀 전체의 pin을 카운터 하나에 모으는 것이 아닙니다. 보존 크레딧은 사용하지 않는 페이지에 추가 기회를 줍니다. Strategy ring은 대량 작업이 우선 재사용하려는 공유 프레임 ID 목록입니다. 별도의 페이지 저장 공간을 소유하지 않습니다.

이 장의 상세 메커니즘은 고정된 20devel 소스를 기준으로 합니다. PostgreSQL 18.0에도 private/shared pin, Clock, ring이 있지만 잠금과 I/O의 세부 구현은 다릅니다. 이 메커니즘들은 클라이언트의 동시 사용을 지원합니다. 이름만으로 처리량, 꼬리 지연시간, 클라이언트별 동일한 용량을 입증할 수는 없습니다.

공유 참조 수가 backend 수보다 많을 수 있는 이유는?

Backend(서버 프로세스)가 재사용을 막기 위해 공유 프레임을 pin하고 비동기 읽기를 요청 큐에 넣습니다. 프레임은 페이지 하나를 담는 메모리 슬롯입니다. 비동기 읽기는 호출자가 다른 작업을 계속하는 동안 파일에서 페이지 데이터를 적재하는 연산입니다. I/O 서브시스템은 연산이 끝날 때까지 그 프레임이 필요합니다.

I/O를 제출하기 전에 서브시스템은 자신만의 추가 수명 pin을 획득합니다. I/O가 진행 중일 때 backend에 오류가 나면 오류 정리 과정이 backend의 pin을 반납할 수 있습니다. Backend의 사용이 사라져도 추가 기여가 남아 공유 참조 수를 양수로 유지합니다. I/O가 완료되면 I/O의 pin을 반납합니다.

공유 참조 수는 수명 기여, 즉 프레임 재사용을 막는 기여를 기록합니다. I/O가 진행 중이지 않은 일반 pin 예제에서는 아직 사용이 남은 backend마다 한 번의 기여를 셉니다. 비동기 I/O에서는 추가 기여가 있으므로 참조 수가 backend 프로세스나 클라이언트 세션 수와 같지 않을 수 있습니다.

PostgreSQL 18.0도 I/O 수명 pin을 획득합니다. pinning_backends 관측 필드는 공유 참조 수를 읽으므로, 필드 이름만으로 이 예외를 배제할 수는 없습니다.

Q16 · Pin 세 번을 중첩하면 무엇이 늘어날까?

Q16 · Private 중첩과 공유 사용 기록

독립된 시작 상태: D는 이미 적재된 페이지 하나의 공유 descriptor입니다. 페이지는 기록할 변경이 없는 clean 상태입니다. A와 B는 D의 프레임을 사용할 서로 다른 PostgreSQL 서버 프로세스입니다. 둘 다 pin을 보유하지 않습니다. Pin은 사용 중임을 기록하여 프레임 재사용을 막습니다. 이 사례에는 I/O가 없으므로 공유 참조 수는 pin을 보유한 backend 수를 기록합니다. 공유 참조 수와 보존 크레딧(교체 전 추가 기회)은 모두 0에서 시작합니다.

이 사례의 규칙: 기본 전략에서 각 backend의 첫 pin은 공유 참조 수와 크레딧을 각각 1 늘립니다. 크레딧의 상한은 5입니다. 중첩 pin은 private 반납 의무만 늘립니다. 마지막 pin을 반납하면 그 backend의 공유 기여가 사라집니다. 반납은 크레딧을 소비하지 않습니다.

사건 순서: A가 반납 없이 세 번 pin합니다. 이어서 B가 첫 pin을 획득합니다. A는 자신의 pin 셋을 모두 반납합니다. 교체 스캔이 크레딧을 소비하는 일이나 다른 변경은 없습니다.

예측 질문: 각 사건 뒤 공유 참조 수, A의 private 참조 수, 보존 크레딧은 얼마일까요?

논의 후 설명 보기

A의 첫 pin 뒤에는 shared=1, A private=1, credit=1입니다. 두 중첩 pin 뒤에는 shared=1, A private=3, credit=1입니다. B의 첫 pin 뒤에는 shared=2, credit=2가 됩니다. A가 pin 셋을 모두 반납하면 shared=1, A private=0, credit=2입니다. B에게 남아 있는 pin이 계속 재사용을 막습니다. 크레딧의 상한은 5이므로 페이지 수명 전체의 호출 횟수를 세는 값일 수 없습니다.

Q17 · Pin한 주소는 바로 읽어도 될까?

Q17 · 바이트는 누가 보호할까?

독립된 시작 상태: A는 CUBRID READ fix를 대신하는 helper를 호출하는 PostgreSQL 서버 프로세스입니다. B는 공유 프레임에 적재된 같은 페이지를 pin한 다른 서버 프로세스입니다. Pin은 사용 중임을 기록하여 프레임 재사용을 막습니다. Helper는 그 프레임을 pin하고 주소를 A에게 반환하지만, 바이트 접근을 조정하는 content lock은 획득하지 않습니다.

접근 규칙: Pin은 프레임의 페이지 식별자를 유지합니다. 이 사례처럼 페이지를 처음 확인하는 일반적인 읽기에서는 shared(공유) content lock도 필요합니다. 쓰기 주체의 exclusive(배타) content lock은 바이트를 변경하는 동안 그 읽기 잠금의 획득을 막습니다.

사건: B가 exclusive content lock을 보유한 채 페이지를 변경하고 있습니다. A는 반환받은 주소를 즉시 읽기 시작합니다.

예측 질문: A가 읽기 전에 helper의 계약은 무엇을 요구해야 할까요?

논의 후 설명 보기

Helper는 바이트를 확인해도 된다는 권한을 반환하기 전에 호환되는 읽기 잠금을 획득해야 합니다. 또는 A가 읽기 전에 그 잠금을 획득하도록 의무를 명시해야 합니다. B의 exclusive 잠금 때문에 A는 기다립니다. 계약에는 잠금과 pin을 누가 반납하는지도 있어야 합니다. Pin한 주소만으로 CUBRID READ fix가 제공하는 페이지 내용 보호를 재현할 수는 없습니다.

중첩 사용은 왜 private 기록으로 충분할까?

Backend(서버 프로세스)가 이미 상주 프레임을 pin하여 재사용을 막고 있습니다. 이제 그 작업의 다른 부분에서 같은 페이지가 필요해집니다. 교체 과정에는 이 backend의 공유 기여가 이미 보입니다. 두 번째 사용을 private 기록에 더하면 두 사용이 모두 끝날 때까지 공유 기여를 유지할 수 있습니다.

따라서 private 참조 수는 남은 반납 의무, 즉 이 backend가 앞으로 반납해야 할 pin의 수를 기록합니다. Resource owner는 작업이 획득한 자원을 정리하기 위한 PostgreSQL의 기록입니다. 각 pin을 기억하므로 정상 반납이나 오류 정리 때 빠짐없이 처리할 수 있습니다.

고정 리비전의 구현은 첫 pin과 마지막 private 반납에서 공유 상태를 갱신합니다. 중첩 pin은 private 기록을 갱신합니다. 이렇게 하면 재사용을 막는 보호를 유지하면서 중첩 사용마다 공유 카운터를 다시 갱신하지 않아도 됩니다. 이 설명이 측정된 속도 향상을 입증하는 것은 아닙니다.

각 상태는 어떤 질문에 답할까?

공유 프레임에 적재된 페이지를 생각해 봅시다. 여러 backend(서버 프로세스)가 재사용을 막기 위해 pin할 수 있고, 한 backend 안에서도 여러 사용이 중첩될 수 있습니다. 교체와 바이트 접근에는 서로 다른 정보가 필요하므로 카운터 하나로 모든 질문에 답할 수 없습니다.

상태답할 수 있는 질문
Private 참조 수이 backend가 반납해야 할 pin은 몇 개인가? Resource owner의 정리 기록에도 각 획득이 남습니다.
공유 참조 수어떤 수명 기여가 남아 있는가? 일반 backend는 pin을 기여하고, 비동기 I/O도 추가 pin을 보유할 수 있습니다. 공유 참조 수가 0이 아니면 Clock은 프레임을 건너뜁니다.
usage_count사용하지 않는 페이지에 몇 번의 추가 기회를 줄 것인가? 상한이 있는 보존 크레딧이며, 사용 권한이나 정확한 접근 시각을 기록하지 않습니다.
Content lock어떤 바이트 연산이 동시에 진행할 수 있는가? 접근 경로는 pin을 유지하면서 필요한 잠금 모드를 선택합니다.

크레딧 0만으로는 왜 재사용할 수 없을까?

상주 프레임의 보존 크레딧이 0이어도 backend(서버 프로세스)가 재사용을 막는 pin을 보유할 수 있습니다. 크레딧 0은 교체 정책이 그 페이지에 추가 기회를 줄 필요가 없다는 뜻입니다. 호출자가 아직 페이지를 사용하는지는 알려 주지 않습니다.

안전 규칙: Clock은 크레딧과 관계없이 공유 참조 수가 0이 아닌 프레임을 건너뜁니다. 두 값이 모두 0일 때만 선택자가 원자적으로 자신의 pin을 더하여 후보를 확보할 수 있습니다. 후보를 확보한 뒤에도 기존 페이지 식별자를 제거하기 위한 검사가 남아 있습니다. 그 검사를 거쳐야 프레임에 다른 페이지를 담을 수 있습니다.

호출자에게 페이지 식별자가 필요한 동안 pin을 유지합니다. 각 바이트 연산에 필요한 내용 보호는 따로 획득합니다. 연산 사이에 content lock을 반납해도 호출자의 pin이 끝나는 것은 아닙니다.

동시 요청은 같은 페이지를 어떻게 찾고 사용할까?

두 backend(서버 프로세스)가 같은 페이지를 요청합니다. 그 페이지는 아직 적재 중일 수도 있습니다. Mapping table은 페이지 식별자를 그 바이트를 담는 메모리 슬롯인 공유 프레임에 연결합니다. Descriptor는 그 프레임의 현재 상태를 제어하는 메타데이터입니다.

  1. 찾기: mapping 잠금이 페이지 조회와 식별자 공개를 보호합니다. 테이블은 별도 잠금을 가진 파티션으로 나뉘어 있으므로 서로 다른 파티션은 독립적으로 진행할 수 있습니다.
  2. 유지하기: 찾은 프레임을 pin한 뒤에 mapping 잠금을 반납합니다. Pin은 프레임 재사용을 막습니다. Backend의 첫 pin이 공유 기여를 더하고, 마지막 private 반납은 그 기여만 제거합니다.
  3. 읽거나 변경하기: I/O 조정으로 호출자는 기존 읽기에 참여하거나 그 완료를 기다릴 수 있습니다. 페이지가 준비되면 해당 페이지의 content lock이 바이트 연산을 조정합니다.
  4. 교체하기: 원자적 선택으로 후보를 확보합니다. 이후 보호된 invalidation(기존 식별자 제거)을 수행하려면 기록하지 않은 변경이 없는 clean 상태여야 하며, 선택자 자신의 pin 외에 다른 pin이 없어야 합니다.

이는 20devel에서 확인한 메커니즘입니다. 자주 쓰는 descriptor에서는 여전히 원자 연산 재시도, content lock 대기, I/O 대기가 발생할 수 있습니다. 이 보호가 낮은 꼬리 지연시간이나 클라이언트별 동일한 용량을 약속하지는 않습니다.

각 backend는 얼마나 앞서 페이지를 pin해야 할까?

여러 backend(서버 프로세스)가 큰 입력을 스캔합니다. 각 backend는 앞으로 필요한 페이지를 미리 읽으려 합니다. 하지만 pin은 반납할 때까지 프레임(페이지 하나를 담는 메모리 슬롯)의 재사용을 막습니다. 너무 멀리까지 미리 읽으면 호출자가 페이지를 사용하기도 전에 많은 프레임이 묶일 수 있습니다.

Read stream은 호출자가 읽을 페이지를 큐에 넣고, 얼마나 앞서 읽을지 관리합니다. 고정된 20devel에서는 backend별 권장 pin 예산을 사용합니다. 이 권장 허용량은 공유 프레임 수인 NBuffers와 보조 프로세스를 포함한 최대 가능 backend 수에서 계산합니다.

Stream은 전략의 한도와 backend에 남은 허용량을 함께 적용합니다. 허용량이 너무 작으면 pin이 반납될 때까지 앞서 읽는 범위를 줄입니다. Stream이 현재 pin한 버퍼를 하나도 보유하지 않는다면, 남은 허용량이 0이어도 하나를 더 허용할 수 있습니다. 그래야 페이지 하나를 전달하고 진행할 수 있습니다.

이 예산은 참여하는 읽기 경로에서 아직 반납하지 않은 pin을 조절합니다. 모든 경로에 적용되는 엄격한 pin 상한이나, 모든 사용자가 같은 크기의 상주 작업 집합을 소유한다는 약속은 아닙니다. CUBRID의 private-LRU 할당량과도 다릅니다.

교체 과정에 사용자가 보이지 않으면 무엇이 깨질까?

독립된 제거 사례: A는 pin 두 개를 중첩해서 보유한 PostgreSQL 서버 프로세스입니다. 아직 끝나지 않은 두 사용이 재사용을 막습니다. H는 공유 프레임에 이미 적재된 페이지입니다. 바이트 연산 사이에 A는 content lock을 반납하지만, H가 다시 필요하므로 pin 둘은 유지합니다. I/O나 다른 사용자는 없습니다.

Clock은 clock hand라는 인덱스로 공유 descriptor 배열을 검사합니다. 인덱스는 끝에 도달하면 처음으로 돌아갑니다. 공유 참조 수가 0이 아니면 건너뜁니다. 공유 참조 수와 보존 크레딧이 모두 0일 때 CAS(compare-and-exchange)는 검사했던 상태가 여전히 일치할 때만 선택자의 pin을 더합니다.

Private 참조 수를 유지한 채 공유 기여만 제거해 봅시다. A에게 아직 H가 필요한데도 교체 과정에는 0이 보입니다. 나중에 프레임을 재사용하면 A가 보관한 주소에 다른 페이지가 들어갈 수 있습니다. 이후 content lock을 획득해도 H의 식별자는 복구되지 않습니다. 다음 상태 추적에서는 이 결함과 모든 pin을 공유 상태에 세는 설계를 비교합니다.

상태 추적 · Clock에 아직 사용자가 보일까?

두 사용이 모두 교체 과정에 보이게 하기

독립적으로 초기화합니다. 서버 프로세스 A는 상주 페이지 H에 중첩 pin(재사용을 막는 사용 기록) 둘을 보유하지만, 지금 content lock은 없습니다. Private 참조 수는 A에게 남은 사용 수, 공유 참조 수는 교체 과정에 보이는 기여 수입니다. u는 usage_count 보존 크레딧(교체 전 추가 기회)이며 여기서는 0입니다. 구현된 규칙, 공유 기여를 제거한 경우, 모든 pin을 공유 상태에 세는 대안을 비교합니다. I/O, 다른 사용자, 동시 변경은 없습니다.

  1. 1. A가 중첩 사용 둘 보유

    구현된 private/shared pin
    private=2; shared=1; u=0
    공유 수명 pin 제거
    private=2; shared=0; u=0
    Pin마다 공유 참조 수 기록
    private ledger=2; shared=2; u=0
    A / 바이트 접근
    H identity retained; no content lock now

    조건 / 가정: 바이트 연산 사이에도 A는 H가 필요합니다. 지금은 재사용을 배제하는 content lock이 없습니다.

    변경 / 결과: Private 반납 의무는 둘이며, 공유 참조 수의 사용자 한 명이 재사용을 막습니다.

  2. 2. Clock이 H 방문

    구현된 private/shared pin
    skip pinned H
    공유 수명 pin 제거
    CAS can claim H
    Pin마다 공유 참조 수 기록
    skip pinned H
    A / 바이트 접근
    A still intends later access

    조건 / 가정: 공유 참조 수가 0이 아니면 선택을 막습니다. 참조 수와 크레딧이 모두 0이면 원자적으로 후보를 확보할 수 있습니다.

    변경 / 결과: 가운데 경로는 A에게 아직 H가 필요한데도 잘못 선택을 허용합니다.

    private=1; shared=1
    공유 수명 pin 제거
    identity no longer protected
    Pin마다 공유 참조 수 기록
    private ledger=1; shared=1
    A / 바이트 접근
    one outstanding use remains

    조건 / 가정: Private 사용 하나가 남아 있습니다. 구현된 설계는 공유 기여를 유지합니다.

모든 pin이 공유 참조 수를 갱신하게 하면 어떨까?

설명용 대안: Backend(서버 프로세스)는 적재된 같은 페이지를 여러 번 사용하며, 프레임을 pin하여 재사용을 막습니다. 여러 사용을 공유 기여 하나로 압축하는 대신 각 획득을 공유 상태에 셉니다. 모든 사용자가 자신의 사용을 전부 반납할 때까지 교체 과정에 양수인 참조 수가 보여야 합니다. 선택자는 교체할 프레임을 고르는 프로세스입니다. 마지막 페이지 식별자 변경 동안에도 자신의 보호용 pin을 유지합니다.

  1. 사용을 획득하기 전에 보호된 상태에서 요청한 페이지 식별자를 찾고 다시 검증합니다.
  2. 중첩 pin을 포함하여 pin마다 공유 기여를 원자적으로 1 더합니다. 그에 대응하는 반납 의무는 private 기록에 남깁니다.
  3. 각 바이트 연산 전에 필요한 content lock을 획득합니다.
  4. 정상 반납이나 오류 때 그 획득에 해당하는 기여만 정확히 제거합니다. 페이지에 기록할 변경이 없고(clean), I/O pin을 포함하여 선택자 자신의 pin 이외에 수명 기여가 하나도 남아 있지 않을 때만 보호된 검사 아래 기존 식별자를 제거합니다. 선택자는 이 보호된 변경 내내 자신의 pin 또는 후보 확보(claim) 상태를 유지합니다.

세 번의 중첩 획득이라면 pin 셋과 반납 셋 모두에서 공유 상태를 갱신해야 합니다. PostgreSQL의 실제 설계는 그 backend의 첫 획득과 마지막 반납에서만 공유 기록을 바꿉니다. 대안은 사용 수명을 보존하지만 공유 원자 연산이 늘어납니다. Private 참조 수를 유지하면서 공유 기여를 모두 없애면 이 보호가 사라집니다.

Pin 규칙은 어떻게 검증할 수 있을까?

독립된 실험 제안이며, 실행 결과가 아닙니다: A는 이미 적재된 페이지 하나에 중첩 pin(재사용을 막는 사용 기록)을 보유한 PostgreSQL 서버 프로세스입니다. B는 교체를 위해 그 프레임을 선택하려는 다른 서버 프로세스입니다. 기록할 변경이 없는 clean 페이지, 보존 크레딧(교체 전 추가 기회) 0, I/O 없음, 다른 사용자 없음으로 시작합니다.

전체 고정 리비전, 빌드, 공유 버퍼 풀 크기, I/O와 워크로드 설정을 기록합니다. 사건 순서를 고정하고 크레딧 변화를 기록합니다. 기본 전략의 첫 pin은 크레딧을 더할 수 있으므로 선택 거부만으로 사용자의 존재를 입증할 수 없습니다.

가설
A의 공유 기여는 마지막 private 반납까지 유지됩니다.
통제하는 변화
A가 두 번 pin하고 한 번 반납합니다. B가 선택을 시도합니다. 구현된 규칙과 공유 기여만 제거한 설명용 모델을 비교합니다.

선택 거부만으로 그 원인은 알 수 없습니다. 다음 화면에서는 pin 보호를 다른 원인과 구별하는 데 필요한 보호된 전이를 명시합니다.

어떤 관측이면 pin 규칙이 틀렸다고 할 수 있을까?

앞 실험 제안을 이어 갑니다. 서버 프로세스 A는 pin 둘 중 하나를 반납했지만 상주 페이지가 아직 필요합니다. 서버 프로세스 B는 그 프레임을 선택하려 합니다. Pin은 사용 중임을 기록하여 프레임 재사용을 막습니다. 공유 기여는 A의 마지막 반납까지 남아 있어야 합니다. 페이지는 기록할 변경이 없는 clean 상태, 보존 크레딧(교체 전 추가 기회) 0, I/O 없음, 다른 사용자 없음으로 시작했으며, 이후의 크레딧 변화를 기록합니다.

정확한 관측
PinBuffer, 마지막 UnpinBufferNoOwner, Clock의 후보 확보 지점에 probe를 추가하는 계획입니다. Private 참조 수, 공유 참조 수, usage_count, 후보 확보 결과, 보호된 페이지-프레임 대응 관계를 연결하여 기록합니다. Probe의 오버헤드도 기록합니다. Content lock 대기는 바이트 접근의 조정을 관측하며, 남은 pin 반납 의무를 관측하는 것은 아닙니다.
반증 기준과 한계
A가 유효한 pin을 유지하는데 프레임이 다른 페이지 식별자에 재사용된다면 사용 수명 규칙에 어긋납니다. 선택 거부만으로는 그 원인을 알 수 없습니다. 모든 획득을 세면 공유 원자 연산량이 바뀝니다. 이 제안은 실행 시간의 이점을 입증하지 않습니다.
