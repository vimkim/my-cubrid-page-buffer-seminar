PostgreSQL의 pin과 content 보호

같은 워크로드를 PostgreSQL에 적용하되 CUBRID 필드를 일대일로 치환하지 않습니다. Descriptor는 resident identity를, private 중첩 pin은 한 backend의 사용을 나타냅니다. 공유 수명 기여는 재사용을 배제하고 content 보호는 바이트 접근을 다룹니다. usage_count는 보존 credit입니다. 각 항목이 보호하는 관계가 다릅니다.

한 backend의 중첩 private pin은 하나의 공유 수명 기여를 이용할 수 있지만 공유 보호를 없애지는 않습니다. Pin은 identity의 수명을 보호하며 임의의 동시 바이트 변경까지 보호하지는 않습니다.

PostgreSQL: 다시 쓴 페이지에 기회를 몇 번 더 준다

Buffer descriptor는 프레임 하나의 메타데이터로, 역할상 CUBRID의 BCB에 대응합니다. PostgreSQL은 descriptor를 배열에 둡니다. Clock hand는 다음에 검사할 배열 위치를 기억하고, 끝에 도달하면 처음으로 돌아갑니다. 페이지가 배열 안에서 이동하는 것은 아닙니다.

각 상주 페이지에는 작은 usage_count, 즉 재사용 크레딧이 있습니다. 기본 전략에서 backend가 처음 pin할 때 크레딧을 하나 더 받을 수 있으며 상한은 5입니다. Backend는 페이지를 사용하는 PostgreSQL 서버 프로세스입니다. Pin은 이 비교에서 CUBRID fix처럼 호출자가 사용하는 동안 프레임 재사용을 막습니다. 페이지 내용의 동시 접근을 보호하는 잠금과는 별개입니다.

Q16 · 중첩 Pin의 기록

구성한 시작 상태: 공유 descriptor D는 유효한 clean 페이지를 나타내며, 공유 refcount와 usage credit은 모두 0입니다. 기본 strategy를 사용합니다. Backend A가 D를 연속 세 번 pin한 상태에서 B가 D를 처음 pin합니다. 이후 A만 자신의 세 pin을 모두 반납합니다. Clock 방문이나 다른 변경은 없습니다.

예측 질문: 이 사건들의 순서에 따라 공유 refcount, A의 private refcount, usage credit을 어떻게 기록하겠습니까?

논의 후 설명 보기

A의 첫 pin 뒤 공유 refcount는 1, A의 private refcount는 1, credit은 1입니다. 두 중첩 pin 뒤 공유 값은 1, private은 3, credit은 1입니다. B의 첫 pin 뒤 공유 값과 credit은 각각 2입니다. A가 모두 반납하면 공유 값은 1, A private은 0, credit은 2이며 B가 D를 보호합니다. Credit의 상한은 5이고 전체 호출 횟수를 세는 값은 아닙니다.

선택 후속 질문: 최종 공유 refcount만 보았을 때 복원할 수 없는 호출 이력은 무엇인가요?

Q17 · 다른 인터페이스의 보호 책임

구성한 시작 상태: CUBRID READ fix를 사용하던 호출자를 PostgreSQL용 wrapper로 옮기는 설계입니다. Wrapper는 기존 identity의 buffer를 pin해 주소만 반환합니다. Caller는 반환 즉시 페이지 바이트를 읽습니다. 같은 페이지를 pin한 B가 content 변경을 위한 보호를 보유하고 있으며 변경 중입니다.

예측 질문: 이 wrapper가 caller의 읽기를 지원하려면 어떤 보호 책임을 인터페이스에 명시해야 할까요?

논의 후 설명 보기

Pin은 메모리 사용 수명을 보호하며 호환되는 바이트 접근까지 보장하지 않습니다. 해당 접근 경로에 필요한 content 보호의 획득·반납 주체를 명시해야 합니다. 일반 공유 버퍼 읽기에서는 바이트를 보기 전에 호환되는 content lock을 얻도록 wrapper의 반환 계약이나 caller의 의무에 넣습니다. 주소와 pin만으로 READ fix의 계약을 재현할 수 없습니다.

선택 후속 질문: 그 책임을 wrapper와 caller 중 누가 수행하게 할지 결정할 때 반환 계약을 어떻게 적겠습니까?

네 수치는 서로 다른 실수를 막습니다

Backend는 같은 buffer를 반복 사용하고 다른 backend는 바이트에 접근할 수 있습니다. Replacement는 공유된 수명 표시가 필요하며, 바이트 변경은 content 동기화가, 정책은 retention 선호가 필요합니다. 이 수치를 합치면 소유권과 인기를 혼동합니다.

수명 보호 제거는 정확성 변경입니다

Content 보호는 pin을 대신하지 못합니다

Backend A가 content-lock 구간 사이에 H를 사용하며 credit은 0입니다(u=usage_count). 가운데 경로에서 공유 수명 보호만 제거합니다. 대안은 nested pin을 모두 공유 metadata에 세고 반납도 대응시킵니다.

  1. 1. A가 nested use 두 개 보유

    구현된 private/shared pin
    private=2; shared=1; u=0
    공유 수명 pin 제거
    private=2; shared=0; u=0
    Pin마다 공유 count 대안
    private ledger=2; shared=2; u=0
    A / content 접근
    H identity retained; no content lock now

    조건 / 가정: 바이트 접근 사이에도 A는 수명 pin을 유지해야 합니다.

    변화 / 결과: Private nesting은 한 backend의 공유 기여를 압축합니다.

  2. 2. Clock이 H 방문

    구현된 private/shared pin
    skip pinned H
    공유 수명 pin 제거
    CAS can claim H
    Pin마다 공유 count 대안
    skip pinned H
    A / content 접근
    A still intends later access

    조건 / 가정: 선택은 공유 refcount가 0이 아니면 제외합니다. Credit만으로 소유권이 생기지 않습니다.

    변화 / 결과: 수명 상태를 제거하면 H가 잘못 적합해집니다. 이 구간에는 content lock이 없습니다.

  3. 3. A가 nested use 하나 반납

    구현된 private/shared pin
    private=1; shared=1
    공유 수명 pin 제거
    identity no longer protected
    Pin마다 공유 count 대안
    private ledger=1; shared=1
    A / content 접근
    one outstanding use remains

    조건 / 가정: 마지막 반납이 공유 기여를 끝냅니다. 첫 nested 반납이 아닙니다.

    변화 / 결과: 두 count 설계는 수명을 보존하지만 pin 제거는 수명을 위반합니다.

일관된 대안: 획득마다 공유 수명 기여 기록

설명용 대안입니다. 명시한 성질을 보존하며 actor의 조정 방식을 바꿉니다.

  1. 매 획득 전에 identity를 다시 검사합니다.
  2. 중첩 사용마다 공유 수명 기록을 증가시킵니다.
  3. 읽기나 변경 시 바이트를 별도로 보호합니다.
  4. 해제·오류 시 해당 획득만 정리하며 모든 기여가 없을 때만 identity를 해제합니다.

설명용 대안입니다. 중첩 획득 m번마다 공유 atomic 작업을 추가하며 private 첫·마지막 경계만 갱신하는 방식과 다릅니다. 해제 의무를 맞추기 위한 private 기록은 여전히 유용합니다. 공유 기여를 대체 없이 제거하면 수명 위반이며 동등한 빠른 pin이 아닙니다.

어떤 관측으로 이 설명을 반증할 수 있는가?

아직 실행하지 않은 실험 제안입니다. 결과 해석 전에 전체 고정 리비전, build, pool·log·DWB·I/O 설정과 workload를 기록합니다.

가설
중첩 private 사용이 backend의 마지막 해제까지 공유 수명 보호를 유지한다는 가설입니다.
통제하는 변화
Backend A가 두 번 pin하고 한 번 해제한 뒤 B가 재사용을 시도합니다. 설명용 모델에서 공유 기여만 제거한 경우와 비교합니다.
정확한 관측
추가 probe 계획: private 중첩 수, 공유 refcount 전이, 보호된 mapping identity를 기록합니다. Content-lock 대기는 바이트 접근이며 중첩 해제 의무가 아닙니다.
반증 기준과 한계
A의 보호된 사용이 남아 있을 때 재사용되면 수명 불변식을 반증합니다. 획득별 기록은 공유 atomic 비용을 바꾸며 모델만으로 timing 이득을 입증하지 않습니다.
