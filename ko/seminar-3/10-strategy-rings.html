스캔은 왜 앞서 사용한 프레임을 다시 찾을까?

스캔(scan)은 많은 데이터베이스 페이지를 순서대로 읽는 작업입니다. PostgreSQL의 backend는 그 작업을 수행하는 서버 프로세스입니다. 페이지(page)는 데이터베이스 안의 식별자를 갖습니다. 프레임(frame)은 공유 버퍼 pool에서 한 페이지를 담고 재사용할 수 있는 메모리 자리입니다.

공유 pool이 가득 찬 상태에서 시작합니다. 일부 페이지는 반복해서 읽는 동안, 큰 스캔은 여러 페이지를 한 번씩 읽으며 아직 메모리에 없는 다음 페이지를 요청합니다. 스캔에는 프레임이 필요하지만, 한 번 읽을 페이지가 다른 작업에서 다시 필요한 페이지를 밀어낼 수 있습니다. 전역 Clock은 후보를 고르면서 모든 스캔을 알아내지는 못합니다.

작업은 접근 전략(access strategy)을 선택할 수 있습니다. NORMAL은 기본 후보 선택을 사용합니다. BULKREAD는 대량 읽기, BULKWRITE는 대량 쓰기, VACUUM은 페이지 유지 관리용입니다. 뒤의 세 전략은 ring을 둘 수 있습니다. Ring은 다시 시도할 공유 프레임 ID를 제한된 개수만큼 저장하는 backend-local 배열입니다. 재사용할 후보를 선호하는 정책이며, 용량을 독점 예약하지는 않습니다.

로컬 슬롯은 공유 pool의 프레임을 가리킨다

공유 상태를 확인해야 ID로 후보를 확보할 수 있다

메모리에 없는 스캔 페이지를 요청하면 backend는 ring의 다음 슬롯을 시도합니다. 비어 있거나 적합하지 않은 항목이면 전역 Clock으로 후보를 찾습니다. 적합한 항목을 재사용하면 작은 프레임 집합 안에서 나중의 스캔 페이지가 앞선 페이지를 대체할 수 있습니다. Ring 방문은 후보를 찾는 단계입니다. pin은 backend가 사용하는 동안 프레임의 현재 페이지 식별자가 교체되지 않도록 보호합니다. 공유 refcount는 pin 보호를 기록합니다. 일반 pin은 pin을 하나 이상 가진 backend마다 한 번만 반영하며, 중첩 pin은 각 backend 안에서 따로 기록합니다. 비동기 I/O는 작업이 끝날 때까지 프레임 수명을 보호하는 별도의 pin을 더할 수 있습니다. 아래 예제의 수치에는 이 추가 pin이 없습니다. 공유 count가 0이면 이러한 보호가 모두 사라진 상태입니다.

사용 크레딧(usage credit)은 usage_count에 저장되며, 상한이 있는 값으로 재사용 관심을 나타냅니다. 페이지를 보존하려는 선호이며, 소유권이나 정확한 접근 횟수가 아닙니다. Ring은 refcount가 0이고 credit이 0 또는 1일 때만 받아들입니다. Credit이 1보다 크면 다른 작업이 페이지를 사용했음을 시사하므로 그대로 둡니다.

Backend는 compare-and-swap(CAS)을 사용합니다. 관측한 공유 상태가 여전히 같을 때만 자신의 pin을 더합니다. CAS가 실패하면 현재 상태를 다시 읽습니다. Buffer header라는 제어 metadata가 잠겨 있으면 잠금이 풀릴 때까지 기다려야 합니다. 성공하면 이전 페이지를 그대로 담은 후보를 pin한 상태로 받습니다. 실제 재사용 여부는 이후 페이지 쓰기와 식별자 매핑(identity-map) 검사로 결정합니다. 이 매핑은 데이터베이스 페이지를 상주 프레임에 연결합니다. 매핑을 바꾸려면 보호된 상태에서 선택한 backend만 pin을 갖는지, 쓰기를 기다리는 변경된 페이지 바이트가 남아 있지 않은지 확인해야 합니다.

전략을 사용한 접근은 credit이 0이면 1로 올릴 수 있습니다. 이미 더 높은 값이면 유지하며, 1보다 높게 계속 올리지는 않습니다. Ring에서 후보를 확보하는 동작 자체는 pin만 추가하고 프레임의 페이지 식별자는 바꾸지 않습니다.

일반 읽기가 스캔 페이지의 즉시 교체를 늦춘다

독립적으로 구성한 시작 상태: A는 큰 스캔을 수행하는 backend이고, B는 일반 읽기를 수행하는 backend입니다. D는 A의 스캔이 이미 읽은 유효한 페이지를 담은 clean 공유 프레임입니다. A의 ring은 여전히 D의 buffer ID를 저장합니다. 두 backend 모두 pin 없이 시작하며 D의 usage credit은 1입니다. Pin은 현재 페이지 식별자를 보호하고, credit은 보존 관심을 나타냅니다. 별도의 I/O 수명 pin은 없으며 A가 슬롯을 다시 방문하기 전까지 Clock은 credit을 낮추지 않습니다.

B가 D에 NORMAL 방식으로 자신의 첫 pin을 잡습니다. 공유 refcount는 0에서 1로, credit은 1에서 2로 늘어납니다. 이어서 B가 마지막 pin을 반납하면 refcount는 0으로 돌아오지만 credit은 2로 남습니다. A가 슬롯을 다시 방문하면 ring은 credit이 1보다 큰 D를 거절하고 전역 Clock으로 후보를 찾습니다. B가 아직 pin을 갖고 있었다면 credit과 무관하게 그 보호만으로 ring 후보 확보가 거절됩니다.

추가 credit은 일반 reader가 떠난 뒤에도 앞서 스캔한 페이지의 보존에 영향을 줄 수 있습니다. 이후 Clock 방문은 credit을 낮출 수 있습니다. Credit은 client 식별자를 저장하거나 서로 다른 과거 사용자 수를 세지 않습니다. 한 backend도 모든 pin을 반납하고 다시 첫 pin을 잡는 과정을 반복해 credit을 얻을 수 있습니다.

일반 reader에게 영구 소유권이 생기는 걸까요?

아닙니다. 로컬 ring이 소유하는 것은 ID 배열뿐이며, 후보를 확보할 때마다 현재 공유 상태를 확인합니다. Credit은 값이 낮아질 때까지 보존 선호를 주고, 보유한 pin은 사용 중 페이지 식별자를 보호합니다. 어느 쪽도 영구 예약을 만들거나 CUBRID의 private-to-shared 리스트 이동을 수행하지 않습니다.

정책의 한계: pool의 8분의 1이라는 ring 상한은 전략 객체마다 적용하며, 모든 동시 query를 합친 상한이 아닙니다. 여러 ring과 전역 fallback이 합쳐지면 큰 압력을 만들 수 있습니다. 이 상한은 client별 quota나 공정성 보장이 아닙니다. ID가 겹치면 전체 슬롯 수와 서로 다른 프레임 수도 달라집니다.

프레임 ID를 유지해도 이전 페이지가 유지되지는 않는다

CUBRID와 비교하면: ring은 한 작업에 속하며 공유 프레임 ID를 담습니다. CUBRID의 BCB는 pool이 소유하는 프레임 제어 레코드입니다. Private LRU 소속은 이 제어 레코드를 페이지 보존 정책 도메인에 배치하며, 그 도메인에는 캐시 페이지 몫의 목표인 quota가 있습니다. 어느 쪽도 페이지의 독점 접근권을 주지 않습니다. Ring의 도움을 받으려면 작업이 해당 전략을 선택해야 합니다.

Q19 · 두 ring, 하나의 프레임 ID

독립적으로 구성한 실행 순서: A와 B는 각각 자기 ring으로 스캔하는 두 backend입니다. F는 처음에 페이지 R을 담은 공유 프레임입니다. 페이지 S는 A가 요청하는, 아직 메모리에 없는 스캔 페이지입니다. 두 backend의 슬롯 모두 F의 buffer ID를 저장합니다. Pin은 현재 페이지 식별자를 보호합니다. 공유 refcount에는 일반 backend의 pin 기여분을 반영하고, credit은 보존 관심을 나타냅니다. 이 실행 순서에는 I/O 수명 pin이 없습니다.

A는 필요한 보호 절차를 거쳐 F의 페이지 R을 S로 교체한 뒤 pin을 반납합니다. B의 배열은 바뀌지 않았습니다. 이제 B가 F를 방문합니다. F는 clean(남은 페이지 쓰기 없음), refcount 0(pin 없음), credit 1입니다. Ring은 자신의 pin을 성공적으로 추가해야 이 공유 상태의 후보를 확보할 수 있습니다. 슬롯 자체가 페이지 식별자를 보존하지는 않습니다.

BULKREAD는 비용이 큰 dirty 항목에서 벗어날 수 있다

후보를 고른 backend는 pin을 보유하여 프레임의 현재 페이지 식별자를 보호합니다. 선택한 프레임은 dirty일 수 있습니다. 현재 페이지에 페이지 파일로 써야 할 변경이 있다는 뜻입니다. Backend는 먼저 share-exclusive 모드의 content lock을 대기 없이 시도합니다. 페이지를 검사하고 쓰는 동안 충돌하는 내용 변경을 막는 보호입니다. Lock을 얻지 못하면 pin을 반납하고 재시도하여 backend들이 서로 기다리는 순환이 생길 가능성을 피합니다.

선행 로그 기록(write-ahead logging, WAL)은 permanent 페이지의 변경 로그가 해당 페이지 바이트를 쓰기 전에 영속화되어야 한다는 규칙입니다. 페이지의 LSN은 이 의무를 충족해야 하는 로그 위치입니다. BM_PERMANENT는 permanent buffer를 표시합니다. Unlogged 페이지에는 실제 로그 위치를 나타내지 않는 값이 있을 수 있어 이 검사에서 제외합니다.

후보의 선택 경로(selection provenance)는 후보가 어디서 왔는지 나타냅니다. from_ring은 이번 선택에서 ring 항목을 재사용했을 때만 true이며, 전역 fallback에서는 false입니다. Ring에서 고른 dirty permanent 후보의 LSN까지 WAL flush가 아직 필요하면 StrategyRejectBuffer는 현재 슬롯이 여전히 그 후보를 가리키는지 확인한 뒤 BULKREAD만 거절합니다.

거절하면 로컬 슬롯을 InvalidBuffer로 비웁니다. 이어서 backend는 lock과 pin을 반납하고 재시도합니다. 공유 dirty 데이터와 페이지 식별자는 유지됩니다. 다음 방문은 다음 슬롯으로 이동합니다. 나중에 비운 슬롯을 만나면 전역 fallback으로 갑니다. 비용이 큰 항목을 비우면 그런 항목으로 가득 찬 ring을 끝없이 순환하는 것을 막지만, fallback에서도 WAL과 페이지 쓰기가 필요할 수 있습니다.

같은 후보를 골라도 전략에 따라 다음 동작이 달라진다

Q20 · 같은 후보 조건, 다른 전략

독립된 세 실행의 시작 상태: 프레임을 할당받으려는 각 backend가 BULKREAD, BULKWRITE 또는 VACUUM ring을 사용합니다. 각각 ring에서 dirty permanent 페이지(BM_PERMANENT)를 고릅니다. 선택 전에는 pin이 없고, 보존 선호를 나타내는 usage credit은 1입니다. 선택은 backend의 pin을 추가하여 페이지 식별자를 보호합니다. 쓰는 동안 바이트를 안정적으로 유지하는 content lock도 대기 없이 얻습니다. 다른 backend의 개입은 없으며, 예제의 수치에는 별도의 I/O 수명 pin이 없습니다.

페이지 LSN이 가리키는 로그는 아직 영속화되지 않았으므로 페이지를 쓰기 전에 WAL(write-ahead log)을 flush해야 합니다. 거절 규칙은 특정 전략에만 적용됩니다. BULKREAD는 이 로컬 ring 항목을 비우고 거절할 수 있지만 BULKWRITE와 VACUUM은 이 거절을 하지 않습니다. 이 경로들은 WAL을 flush한 뒤 페이지를 쓸 수 있습니다. 어느 경로든 이전 페이지 식별자를 제거하기 전에는 현재 상태를 확인해야 합니다.

예측 질문: 후보를 고른 뒤 세 전략의 동작은 어떻게 달라질 수 있을까요?

BULKREAD는 현재 슬롯을 InvalidBuffer로 비우고 lock과 pin을 반납한 뒤 후보 선택을 재시도합니다. 공유 페이지를 무효화하는 동작은 아닙니다. BULKWRITE와 VACUUM은 WAL 순서를 지키고 페이지를 flush한 뒤 보호된 invalidation을 시도할 수 있습니다. NORMAL에는 strategy ring이 없습니다. 쓰기가 완료되어도 자신의 pin만 남았는지, 새 dirty 변경이 없는지 확인하는 최종 검사를 대신할 수는 없습니다.

독립적으로 구성한 시작 상태: R은 backend의 ring에 ID가 들어 있는 공유 프레임이며 dirty permanent 페이지를 담고 있습니다. 앞선 실행 순서에서 R은 페이지 이름이었지만, 이 사례에서는 프레임 이름입니다. H는 다른 backend가 실행 내내 pin하는 별도 프레임입니다. 각 전략의 실행은 이 조건에서 새로 시작하며, 표시한 수치에는 별도의 I/O 수명 pin이 없습니다.

Ring 크기는 pin 반납과 I/O 완료 시간을 고려한다

Pin은 backend가 완전히 반납할 때까지 현재 페이지 식별자를 보호합니다. Ring이 너무 빨리 한 바퀴 돌면 자신의 pin이나 아직 진행 중인 읽기를 만날 수 있습니다. 슬롯을 늘리면 재방문 사이에 여유가 생기지만, 그 작업이 다시 방문할 수 있는 프레임 ID도 늘어납니다. Ring 크기는 정책 입력이며 독점 예약한 프레임 수가 아닙니다.

이 고정 리비전에서 GetAccessStrategy는 NORMAL에 ring을 주지 않습니다. BULKREAD는 256 KiB에서 시작하고, io_combine_limit과 effective_io_concurrency를 사용해 비동기 I/O용 공간을 더합니다. 이 확장은 GetPinLimit으로 제한합니다. BULKWRITE의 factory 크기는 16 MiB, VACUUM은 2 MiB입니다. 이는 factory가 고르는 값이며, 모든 호출자의 실제 ring 크기는 아닙니다.

GetAccessStrategyWithSize는 호출자가 요청한 KiB를 슬롯 수로 바꾸고, 전략 객체마다 NBuffers / 8로 제한합니다. 공유 pool의 프레임 수의 8분의 1입니다. 이 ring별 상한은 모든 query를 합쳐 제한하거나 공정성을 보장하지 않습니다. 요청이 0이면 전략 객체를 만들지 않습니다. GetAccessStrategyPinLimit은 미리 pin할 수 있는 범위를 BULKREAD에서는 전체 ring 크기, 다른 전략에서는 절반까지 허용합니다. 호출자는 이 한도와 다른 제약을 함께 적용합니다.

r은 한 backend-local 전략 객체의 슬롯 수입니다. 각 슬롯은 공유 프레임 ID를 저장합니다. r은 독점 프레임 수나 스캔이 읽는 전체 페이지 수가 아닙니다.

스캔 용량 분리에는 공유 식별자와 실패 처리 규칙이 필요하다

설명용 대안: 실제 프레임 용량을 스캔에 예약하면서 하나의 권위 있는 식별자 매핑(identity map)을 유지합니다. 이 매핑은 각 데이터베이스 페이지의 상주 프레임을 찾는 경로입니다. 용량 조정 방식을 바꾸는 대안이며, 구현된 ring protocol과는 다릅니다.

  1. 스캔을 받아들이기 전에 제한된 frame partition, 즉 스캔 용량으로 배정할 프레임 집합을 예약합니다. 안전한 용량이 없으면 기다리거나 실패합니다. Pin을 무시하거나 dirty 데이터를 덮어쓰지 않습니다.
  2. 모든 partition에서 같은 identity map을 사용합니다. 요청한 페이지가 다른 곳에 이미 상주하면 그 페이지를 사용하거나 보호된 protocol로 이동합니다. 독립적으로 수정할 수 있는 복사본을 조용히 만들지 않습니다.
  3. 이동이나 재사용 전에 기존 pin과 내용 보호를 존중합니다. Dirty 데이터를 WAL 순서에 맞춰 보존하고, identity-map 변경을 보호하면서 현재 상태를 다시 검사합니다.
  4. 스캔이 끝나면 예약을 해제하고 남는 용량을 재분배합니다. 오류나 취소 시에는 유효한 페이지 식별자와 dirty 의무를 유지한 뒤 예약을 되돌립니다.

여기서 r은 비교 대상 ring의 슬롯 수입니다. 로컬 ID r개는 독점 프레임을 예약하지 않습니다. Partition은 실제 용량을 예약하지만 예약·이동·재분배 규칙이 필요하며 유휴 공간을 묶어 둘 수 있습니다. 2Q/history 정책은 대신 queue와 기억한 페이지 식별자를 추가합니다.

어떤 관측으로 ring 설명을 반증할 수 있을까?

아직 실행하지 않은 실험 제안: 고정 PostgreSQL 리비전에서 build, pool 크기, 로그 영속성, I/O 동시성, ring 크기, pin 한도와 요청 순서를 기록합니다. CUBRID와 비교할 때는 log/DWB 설정도 기록합니다.

가설
적합한 프레임이 있으면 스캔은 제한된 로컬 ID 집합을 다시 방문할 수 있습니다. 다른 개입이나 크기 설정 때문에 fallback이 필요할 수 있습니다.
통제하는 변화
Pool과 반복 읽기·스캔 순서를 고정합니다. 기록한 설정에서 NORMAL과 지원되는 전략을 비교합니다. 두 ring이 한 프레임을 가리키는 검사는 독립된 시작 상태로 구성합니다.
정확한 관측
pg_stat_io는 I/O를 전략 context별로 묶으며 거절 이유별로 보여 주지는 않습니다. 제안하는 ring-claim, StrategyRejectBuffer, fallback probe는 슬롯 ID, 공유 pin/credit, ring 또는 전역 선택 경로와 WAL 필요 여부를 기록합니다. 슬롯 수와 서로 다른 프레임 수를 구분하고, 최종 페이지 식별자 제거를 별도로 기록합니다.
반증 기준과 한계
다른 backend의 pin이 있는데도 ring ID만으로 페이지를 교체하면 수명 보호를 반증합니다. 적합하지 않은 프레임에서의 fallback은 조건부 가설에 맞는 결과입니다. 집계 reuse 횟수로 최종 페이지 식별자 제거를 입증할 수는 없습니다.

여기서 r은 ring 슬롯 수이며, 독점 프레임 수나 스캔의 전체 I/O 수가 아닙니다. Probe 로그는 실행 시점을 바꾸므로 그 부하도 기록합니다.
