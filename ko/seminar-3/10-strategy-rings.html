스캔 ring이 가리키는 공유 frame

CUBRID 페이지 버퍼 daemon과 PostgreSQL 페이지 교체

반복 hot-set 읽기 + 대량 스캔 + dirty 압력. 구성한 실행 순서는 독립적으로 초기화합니다. 명시한 소스 의도가 없는 기능상 이유는 Inference입니다.

아직 무엇이 막혀 있는가?

큰 스캔이 많은 페이지를 한 번씩 읽었다는 이유만으로 무제한 보존을 얻어서는 안 됩니다. Access-strategy ring은 제한된 수의 공유 buffer ID를 기억합니다. ID는 재사용 기회이며 독점 frame이 아닙니다. NORMAL, BULKREAD, BULKWRITE, VACUUM은 정책과 I/O 가정이 다릅니다.

Backend-local ring이 소유하는 것은 ID 배열이며 공유 frame의 내용은 아닙니다. 다른 ring이 같은 frame을 가리켜도 공유 refcount와 credit 거절 조건을 따라야 합니다. BULKREAD의 WAL 거절은 해당 local slot을 무효화합니다.

Q19 · 두 Ring의 같은 Buffer ID

구성한 시작 상태: 서로 다른 backend A와 B의 ring slot이 같은 공유 buffer ID F를 저장합니다. F는 처음에 R을 나타냈습니다. A가 필요한 보호 절차를 거쳐 F의 identity를 S로 바꾸고 pin을 반납했습니다. B의 ring 배열에는 변경이 없었으며, B는 이제 그 slot을 방문하려고 합니다. F는 clean, refcount 0, credit 1입니다.

예측 질문: B의 slot 값이 유지됐다는 기록으로 다음 방문의 페이지 identity에 대해 어디까지 설명할 수 있을까요?

논의 후 설명 보기

Slot은 계속 F를 참조하지만 현재 F의 identity는 S입니다. Slot이 R을 소유하거나 유지하는 것은 아닙니다. B는 현재 frame에 대해 보호된 ring 선택을 시도하고 이후 필요한 identity·writeback 절차를 수행합니다. Backend의 참조 배열과 CUBRID pool이 관리하는 BCB 정책 소속을 기준으로 비교합니다.

Q20 · Strategy를 바꾼 같은 후보

구성한 시작 상태: 각각 독립된 세 실행에서 BULKREAD, BULKWRITE, VACUUM strategy의 ring으로 같은 조건의 후보를 선택했습니다. 후보는 BM_PERMANENT인 dirty 페이지이며, 필요한 content lock을 대기 없이 얻었습니다. 페이지 LSN까지 WAL flush가 필요합니다. 선택 전 refcount는 0, credit은 1이고 다른 backend의 개입은 없습니다.

예측 질문: 같은 후보의 이후 처리는 세 strategy에서 어떻게 달라질 수 있나요?

논의 후 설명 보기

BULKREAD는 이 ring 후보를 거절하고 현재 slot을 InvalidBuffer로 비운 뒤 lock과 pin을 반납하고 재시도합니다. 공유 페이지의 identity를 제거하는 분기는 아닙니다. BULKWRITE와 VACUUM은 이 bulk-read 거절 정책을 쓰지 않으며 WAL을 보존하고 flush한 뒤 보호된 invalidation으로 갈 수 있습니다. NORMAL에는 strategy ring이 없습니다. 실제 크기는 factory 정책 외에도 caller 입력, AIO·pin 한도와 NBuffers/8 상한을 확인합니다.

Scan에는 공간이 필요하지만 무제한 retention은 필요하지 않습니다

One-pass scan은 공유 pool에 많은 페이지를 통과시키지만 재사용은 적을 수 있습니다. 매 방문에 normal clock credit을 주면 반복 사용하는 working set을 밀어낼 수 있습니다. Strategy ring은 backend-local shared-buffer ID로 scan의 선호 재사용 범위를 제한합니다. 별도로 할당한 private cache가 아닙니다.

정책: 공유 refcount=0, credit≤1인 ring slot을 시도합니다. 높은 credit은 다른 사용을 시사합니다. 안전성: 공유 상태에서 claim하고 dirty data·WAL을 보존한 뒤, 보호된 현재 상태를 검사해 이전 mapping을 제거합니다.

두 local ring이 F4를 가리킬 수 있습니다. 어느 쪽도 F4를 영구 소유하지 않습니다. 한쪽 pin CAS가 성공하면 다른 쪽 slot은 일시적으로 사용할 수 없습니다. ID가 나중에는 같은 frame의 다른 페이지를 가리킬 수도 있습니다.

Local footprint와 local pool은 다른 대안입니다

Ring 없음: Normal clock과 모든 안전성 검사를 유지합니다. Scan이 normal allocation·credit 경로를 사용하므로 pollution과 metadata traffic이 늘 수 있지만 정확성은 유지할 수 있습니다. 설명용 대안: 별도 private scan pool을 할당하면 공간을 분리하지만 cached bytes를 중복 보유하며 같은 페이지를 writer·일반 reader가 사용할 때 coherence가 필요합니다. 공유 admission 정책으로 one-touch 페이지의 우선순위를 낮출 수도 있으나 분류·history 상태가 추가됩니다.

r개 slot을 가진 strategy 객체의 메모리는 O(r) ID입니다. Slot 시도는 O(1) local 작업에 공유 CAS retry가 추가되고 fallback은 clock 방문을 더합니다. r개 frame을 독점 reserve하지 않습니다. High-credit 회피는 정책이며 pinned 검사 생략은 수명 오류입니다.

Backend eviction write를 없애는 대안은 clean 공급을 보장하거나 공급이 없을 때 명시적으로 wait·fail해야 합니다. I/O를 다른 actor에게 옮겨도 I/O 자체가 없어지지는 않습니다.

아닙니다. Local ID는 소유권이 아니고 현재 credit>1은 양쪽 ring 시도를 거절합니다. Credit≤1이어도 한쪽 claim 성공은 공유 refcount를 바꾸므로 다른 쪽이 다시 판단해야 합니다. Credit gate만 제거하면 retention 정책이 바뀌며 pin gate 제거는 수명을 위협합니다.

일관된 대안: 하나의 identity map 아래 스캔 용량 분리

설명용 대안입니다. 명시한 성질을 보존하며 actor의 조정 방식을 바꿉니다.

  1. Scan admission에 제한된 frame partition을 예약합니다.
  2. Partition 전체가 하나의 권위 있는 identity map을 사용합니다.
  3. 이동이나 재사용 전에 공유 사용과 dirty 의무를 존중합니다.
  4. Scan 종료 시 예약을 해제하고 명시적인 재분배 정책으로 남는 용량을 공급합니다.

설명용 대안입니다. Local ID r개인 ring과 달리 실제 용량을 예약합니다. 재분배·coherence 규칙이 추가되고 idle 공간을 낭비할 수 있습니다. 2Q/history는 queue·history를 쓰는 다른 scan 저항 대안입니다. Ring의 local 작업은 O(1)에 공유 상태 재시도가 더해집니다. ID는 O(r) 공간을 쓰지만 전체 scan I/O나 독점 frame r개를 보장하지는 않습니다.

어떤 관측으로 이 설명을 반증할 수 있는가?

아직 실행하지 않은 실험 제안입니다. 결과 해석 전에 전체 고정 리비전, build, pool·log·DWB·I/O 설정과 workload를 기록합니다.

가설
Scan ring은 적합성과 크기 가정 아래 local 재사용 footprint를 조절한다는 가설입니다.
통제하는 변화
Hot-set·scan 요청 순서를 고정하고 pool·I/O·ring 설정을 명시해 NORMAL과 각 strategy를 비교합니다. 두 ring이 한 frame을 가리키는 경우는 별도 순서로 추가합니다.
정확한 관측
pg_stat_io에 strategy context가 있습니다. 추가 probe로 ring 허용, refcount·credit 거절, BULKREAD WAL 거절, global fallback을 구분합니다. Slot 수와 서로 다른 공유 frame 수도 구분합니다.
반증 기준과 한계
