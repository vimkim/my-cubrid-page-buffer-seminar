Lecture F2 — 캐시 정책에서 데이터베이스의 안전성으로

선행 내용은 Replacement의 기초입니다. P/R을 반복 사용하는 working set과 S/T/U scan이라는 흐름을 이어 갑니다. 이제 정책이 선호하는 victim을 실제로 제거해도 되는지 따져봅니다.

용량 문제는 같아도 허용되는 선택은 다르다

여러 시스템에서 빠른 저장 공간이 가득 찬 상태의 miss는 같은 용량 문제를 일으킵니다. 다만 캐시 단위, 배치 규칙, 관리 주체에 따라 허용되는 해결 방법이 달라집니다.

시스템과 단위관리 주체아무 victim이나 고를 수 없는 이유
OS 가상 메모리: pageOS가 하드웨어 주소 변환의 도움을 받아 가상 page를 물리 frame에 매핑합니다.회수할 때 매핑과 필요한 내용을 보존해야 합니다. Pin된 page를 임의로 회수할 수 없으며, 수정된 내용은 backing storage에 보존해야 할 수 있습니다.
CPU cache: cache line하드웨어가 tag, 배치, coherence를 관리합니다.Set-associative cache에서는 주소가 매핑된 set 안에서 경쟁합니다. 모든 line이 후보가 되는 것은 아닙니다. Dirty 상태와 coherence 의무도 제거를 제한하므로 OS page 정책과 동일하게 볼 수 없습니다.
애플리케이션 cache: 객체 또는 값애플리케이션이나 cache 라이브러리가 계약을 정합니다.객체 크기와 만료 규칙은 서로 다를 수 있습니다. 다시 계산할 수 있는 값을 버리는 것과 아직 저장하지 않은 쓰기의 유일한 사본을 버리는 것은 다릅니다. 항목을 제거해도 다른 곳의 참조가 사라지는 것은 아닙니다.
데이터베이스 buffer pool: database page데이터베이스가 residency, page 내용을 사용하는 주체, recovery를 조율합니다.사용 중인 page 보호와 dirty data가 frame 재사용을 제한합니다. Database page의 단위가 OS page나 CPU line과 같을 필요는 없습니다.

Exact LRU는 매 접근마다 metadata를 갱신합니다. 여러 사용자가 동시에 접근하면 이 관리 작업도 동기화해야 합니다. 근사 정책이나 scan에 강한 admission이 일부 비용을 줄일 수 있지만, 정책 이름이나 점근적 비용만으로 처리량을 판단할 수는 없습니다.

Dirty page 교체 전에: 무엇을 보존해야 하는가?

Pin(엔진에 따라 fix)은 사용 중인 resident page가 교체되지 않도록 보호합니다. Pin만으로 동시 읽기·쓰기가 안전해지는 것은 아닙니다. Latch는 page 내용에 대한 접근을 조율합니다. Transaction lock은 논리적 동시성 제어를 위한 별도 수단입니다. Pin을 해제해도 transaction이 commit되는 것은 아닙니다.

Dirty page에는 현재 상태를 저장 장치에 반영해야 하는 수정이 있습니다. Writeback/flush는 page image를 저장 장치에 전달하는 작업이고, eviction은 resident identity를 제거하여 frame을 다른 page에 쓸 수 있게 하는 작업입니다. Flush가 성공해도 page는 메모리에 남을 수 있습니다. Clean page도 pin되어 있으면 재사용할 수 없습니다.

Durability는 commit 성공을 알린 변경의 약속된 효과가 데이터베이스 계약에서 다루는 장애 후에도 유지된다는 뜻입니다. Recovery log는 장애 후 복구에 사용할 변경을 기록합니다. Write-ahead logging (WAL)은 수정된 data-page image보다 관련 log가 먼저 영속 저장 장치에 도달하도록 요구합니다. 일반적인 logged change에서는 recovery가 log를 재적용할 수 있으므로 durable commit이 모든 수정 page의 쓰기를 기다릴 필요는 없습니다. Page flush만으로 transaction commit을 뜻하지는 않습니다. 설정과 특수 page 종류에 따라 차이가 있으며, 이는 개념적 원칙이지 모든 API에 대한 약속은 아닙니다.

개념 설명의 근거: CMU Spring 2026 buffer-pool 강의. CUBRID의 정확한 dirty-generation/WAL protocol은 이후 Lecture 6에서 다룹니다.

Checkpoint DB-A: 가장 오래된 page가 사용 중이다

Lecture F1 강의의 어떤 마지막 행에서도 이어지지 않는, 새로 구성한 데이터베이스 모델입니다. 안정적인 세 frame의 내용은 F0=P, F1=R, F2=S이고 FIFO admission 순서는 P → R → S입니다. 모두 clean이지만 P는 다른 사용자가 pin하고 있으며 R/S에는 pin이 없습니다. 다른 I/O나 reservation은 없습니다. 이 모델은 없는 T를 반드시 적재하고, bypass/확장은 금지하며, 재사용 가능한 page 중 가장 오래된 것을 고릅니다. 자격 확인과 재사용은 원자적으로 이루어지고 pin은 FIFO 순서를 바꾸지 않습니다. 선호 page, 허용되는 victim, 적재 후 frame을 예측해 보세요.

설명과 상태 펼치기

FIFO는 P를 선호하지만 pin 때문에 재사용할 수 없습니다. 재사용 가능한 page 중 가장 오래된 것은 R입니다. F1에 T를 적재하면 P / T / S가 되고 admission 순서는 P → S → T가 됩니다. P의 frame과 내용은 보존됩니다. 이는 제약을 추가하여 구성한 FIFO 예제이며 CUBRID victim 알고리즘은 아닙니다.

정책의 선호는 어디를 살펴볼지 제안합니다. 안전한 재사용에는 보호된 상태에서 현재 상태를 확인하는 절차가 필요합니다. 다른 사용자가 page를 획득할 수 있다면 과거에 관찰한 “unpinned”만으로는 부족합니다.

Checkpoint DB-B: 쓰기와 eviction은 다르다

P / R / S와 FIFO P → R → S에서 독립적으로 다시 시작합니다. 이 분기는 DB-A의 T를 이어받지 않습니다. P는 unpinned이면서 dirty이고 R/S는 clean이지만 pinned입니다. 즉시 재사용할 수 있는 frame은 없습니다. T는 없고 bypass/확장은 계속 금지합니다. 이 분기에서는 P를 flush하며, flush 도중 새로운 pin이나 수정이 없다고 가정합니다. Writeback 성공 직후와 이후 보호된 재사용 직후의 상태를 각각 예측해 보세요.

설명과 상태 펼치기

Data page를 쓰기 전에 관련 log를 영속화합니다. Writeback 성공 직후에는 P / R / S가 그대로 남고 P가 clean·unpinned 상태입니다. 아직 P를 evict하지 않았습니다. 이후 보호된 상태에서 자격을 다시 확인하면 P를 T로 교체할 수 있습니다. 결과는 T / R / S, FIFO R → S → T입니다. Frame은 F0 그대로이며 page identity만 바뀝니다. I/O 성공과 앞서 명시한 동시 변경 부재가 전제입니다.

DB-B의 성공 결과가 아니라 DB-B에서 새로 출발하는 대안 분기: 이전 image를 쓰는 동안 다른 사용자가 P를 수정합니다. 이전 image의 쓰기 완료만으로 현재 page가 clean이라고 볼 수 없습니다. Dirty 상태와 사용 주체를 다시 확인해야 하며 추가 writeback이나 retry가 필요할 수 있습니다. 이는 추론용 schedule이며 runtime observation은 아닙니다.

안전성을 지켜도 allocation은 끝나지 않을 수 있다

Checkpoint DB-C: P / R / S에서 다시 시작하며 모두 clean·pinned입니다. T는 없고 bypass/확장은 허용하지 않습니다. Pin이 유지되는 동안 어느 frame도 재사용할 수 없습니다. 더 “좋은” recency 순위를 매기면 공간이 생길지 예측해 보세요.

설명과 상태 펼치기

어떤 순위도 pin을 해제하지는 않습니다. Frame은 P / R / S 그대로입니다. 진전하려면 사용자가 pin을 해제하는 등의 다른 사건과 이후 보호된 selection의 성공이 필요합니다. 시스템은 계약에 따라 대기·재시도하거나 요청을 실패 처리할 수 있지만, 기다리는 것 자체로 공간이 생기지는 않습니다. 이미 clean인 pinned page를 flush해도 이 상황은 해결되지 않습니다.

Safety는 사용 중인 내용을 덮어쓰거나 보존해야 할 수정을 잃는 것을 금지합니다. Progress는 어떤 사건이 있어야 대기 중인 allocation을 끝낼 수 있는지 묻습니다. 시스템이 허용하는 범위에서 다른 후보를 찾거나, dirty-page cleaning을 진행하거나, 해제를 기다리거나, 허용된 오류를 반환할 수 있습니다. 이런 동작 이름만으로 경쟁 상황에서의 최종 성공, 공정성, 완료 시각의 상한을 보장할 수는 없습니다.

두 데이터베이스가 scan traffic에 대응하는 방식

이 개념 소개는 이후 source 비교 강의와 같은 고정 revision을 사용합니다. PostgreSQL fd2b89854d93d70fe8c9a69d5b8fafd5b9302cfc 및 MySQL/InnoDB 06a5c1c99c377fc41b2eba1ea244e8b220bdc3c8. 이는 해당 revision의 Verified mechanism / Implementation policy이며 모든 release에 대한 주장이 아닙니다.

PostgreSQL: Clock hand가 descriptor를 방문하면서 pinned buffer는 건너뛰고 양수인 usage_count를 줄입니다. Unpinned이면서 credit이 0인 후보를 확보합니다. 이 count는 상한이 있는 재사용 credit이며 정확한 recency 순위가 아닙니다. Bulk-operation strategy ring은 제한된 shared-buffer ID 집합을 재사용하므로 scan이 읽을 때마다 global pool의 새로운 영역을 차지할 필요가 없습니다. Ring은 private buffer pool이 아닙니다. Clock selection 근거; Ring 재사용 근거.

InnoDB: Midpoint LRU는 resident page를 new/young 영역과 old 영역으로 나눕니다. Old 영역이 형성된 뒤에는 일반적인 disk read가 그 영역에 들어가며, 접근 후 경과 시간 조건이 young 쪽으로의 promotion을 늦출 수 있습니다. 따라서 scan의 첫 접근만으로 가장 강한 보호를 자동으로 받지 않습니다. 두 영역 모두 resident page이며 evict된 page identity의 이력이 아닙니다. Midpoint insertion 근거; Disk-read admission 근거; Promotion gate 근거.

두 엔진 모두 residency 유지 정책을 보호·writeback과 구분합니다. P/R 자체는 메모리에 들어가더라도 scan과 경쟁할 수 있습니다. Ring과 지연 promotion은 서로 다른 대응 방식일 뿐 어느 엔진이 우월하다는 증거가 아닙니다. Shared metadata, dirtying, I/O, 경쟁도 비용에 영향을 줍니다. CUBRID 경로를 익힌 뒤 Lecture 18A의 상세 비교와 canonical evidence reference로 돌아오세요.

Workload를 source에서 도출한 별도 모델로 옮기기

다음 Lecture 1에서는 CUBRID page journey를 살펴봅니다. VPID는 논리 page의 이름이고 BCB는 재사용 가능한 resident frame을 기술하며 fix/unfix는 일시적인 사용을 추적합니다. 이 교육과정의 CUBRID 설명은 다음 revision을 기준으로 합니다: f799e05d77d5300c6ea5753b4a6cc7caee6d8912.

이어 가는 것은 workload의 형태뿐입니다. 이후 예제는 구성한 32,768-frame pool에서 새로 시작하며 처음에는 INVALID frame을 가져옵니다. Runtime capture도, 가득 찬 세 frame cache도 아닙니다. CUBRID에는 별도의 정책과 보호 규칙이 있으므로 toy 모델의 hit 수나 FIFO/exact-LRU 계산을 옮겨 적용할 수 없습니다.

P/R 반복 접근과 S/T/U scan 압력구성한 32,768-frame snapshot에서 시작합니다. 처음에는 INVALID 30,768개와 resident 2,000개입니다. Runtime에서 측정한 capture가 아닙니다.

선호와 허용되는 재사용의 구분하나의 FIFO 또는 exact-LRU 순서 대신 private/shared list와 LRU1/2/3 zone을 사용합니다. 첫 admission은 INVALID frame을 사용하며 가득 찬 세 frame 중 하나를 evict하는 과정이 아닙니다.
상태 변화에는 명시된 사건이 필요기존 admission trace는 private list 32의 F43 → F42 → H1 → H2 순서로 끝납니다. 명시된 LRU1 조건에서는 P를 반복 사용해도 이동하지 않습니다. 이후 cooling/migration은 그 trace의 자체 checkpoint에서 시작합니다.

Verified mechanism: 기존 예제에서는 ignore/migration 조건에 해당하지 않으므로 고정 revision의 일반 LRU1 unfix 분기가 위치를 유지합니다. 기존 P trace에 전체 전제와 source 발췌가 있습니다. Source 분기. Toy 모델의 hit 수, FIFO 선호, 세 frame 기준의 threshold를 이 모델에 옮겨 적용하면 안 됩니다.
