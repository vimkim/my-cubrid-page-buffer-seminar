Page buffer는 무엇을 하는가?

같은 페이지를 다시 읽을 때 메모리를 재사용하고, 여러 스레드가 안전하게 접근하며, 변경된 내용을 저장하는 과정을 살펴봅니다.

페이지를 메모리에 남겨 두는 이유

기초부터 이해하는 경로 ↑

데이터베이스는 데이터를 페이지(page) 단위로 읽고 씁니다. Frame은 페이지 하나를 담는 메모리 자리이고, page buffer는 이 자리들을 관리합니다. 한 번 읽은 페이지를 메모리에 남겨 두면 다음 요청에서 다시 사용할 수 있습니다.

예를 들어 페이지 P를 읽고, 다른 일을 한 뒤 P를 다시 읽습니다. P가 메모리에 남아 있으면 hit, 없으면 miss입니다. Miss에서는 P를 담을 frame을 확보해야 합니다. 빈 자리가 없다면 다른 페이지를 안전하게 내보내야 합니다.

Hit여도 다른 스레드의 latch를 기다릴 수 있습니다. Miss여도 OS cache 등 하위 계층이 읽기를 처리할 수 있어, 반드시 물리 디스크 I/O가 발생하는 것은 아닙니다.

Fix로 사용하고 unfix로 반납하기

같은 메모리를 여러 스레드가 쓰려면 두 가지를 보장해야 합니다. 사용 중인 frame을 다른 페이지의 자리로 빼앗지 않아야 하고, 내용을 읽거나 고치는 접근도 조율해야 합니다.

  • Fix: 요청한 페이지를 준비하고, 요청한 page latch와 임시 접근 권한을 얻습니다. 성공하면 PAGE_PTR로 내용을 사용할 수 있습니다.
  • Unfix: 해당 fix로 얻은 사용 권한을 반납합니다. 그 뒤에는 반환받았던 포인터를 계속 사용하면 안 됩니다. 페이지 자체는 메모리에 남을 수 있습니다.

Page latch는 메모리의 동시 접근을 보호합니다. 트랜잭션의 논리적 잠금, 로그 기록, commit까지 대신하지는 않습니다.

소스: Contract and Objects. 소스: page_buffer.c:2260–2685, 6277–6634, 3062–3201.

페이지의 이름과 메모리 자리는 다르다

P는 페이지의 이름이고 frame은 P의 내용을 담은 자리입니다. 같은 frame에 나중에는 Q가 들어올 수 있습니다. 그 자리가 지금 누구를 담고 있고 사용 중인지 기록하는 것이 BCB입니다.

VPID는 페이지 식별자, BCB는 제어 정보, frame은 실제 데이터입니다. fcnt는 전체 fix 수이고 holder는 스레드별 fix를 기록합니다. 다음 자료구조 페이지에서 이 관계를 자세히 봅니다.

자료구조 recap: 배열과 연결 리스트

일반적인 DB 서버 프로세스 하나에는 pgbuf_Pool이 하나 있습니다. DB마다 실행되는 서버 프로세스가 각자의 pool을 관리하며, 접속이나 테이블마다 pool을 새로 만들지는 않습니다. 아래에서 N은 frame 수, S는 shared LRU 수, P는 private LRU 수입니다.

BCB와 Frame은 각각 배열이며 같은 번호의 슬롯끼리 짝을 이룹니다. Shared/private LRU는 하나의 descriptor 배열을 나눠 씁니다. buf_LRU_list[0…S−1]은 shared, buf_LRU_list[S…S+P−1]은 private입니다. 각 entry의 top/bottom이 BCB들을 가리키고, BCB 내부의 next_BCB/prev_BCB가 이중 연결 리스트를 만듭니다.

LRU 순서를 바꿀 때 BCB 배열이나 page bytes를 옮기지 않습니다. 기존 BCB의 링크를 바꿉니다. Private LRU도 별도의 frame pool이 아니며, private index는 S를 더해야 전체 배열 index가 됩니다.

몇 개이고, 메모리는 얼마나 쓸까?

구조배열 / 원소 수예시 메모리
pgbuf_Pool1648 B
BCB_table1 × N144 B × N ≈ 4.5 MiB
iopage_table1 × N(16,384 + 8 + guard) B × N
buf_LRU_list1 × (S + P)128 B × 184 = 23 KiB

위 숫자는 Linux x86-64 SERVER_MODE Debug의 구조체 크기 예시입니다. Pool 648 B는 배열을 포함한 전체 메모리가 아니라 관리 구조체 자체입니다. 기본 예시 N = 32,768, S = 32, P = 152는 max_clients = 100, HA off, LRU 개수 자동 설정을 전제로 합니다. Page bytes만 512 MiB이고, frame의 back-pointer에 256 KiB가 추가됩니다. BCB·LRU·hash·holder 등 메타데이터는 별도입니다.

개수는 고정 상수가 아닙니다. N은 buffer 설정, S/P는 LRU 설정과 서버 용량에 따라 달라집니다. Private LRU를 끄면 P = 0입니다. 각 LRU에 연결된 BCB 수는 실행 중 변하며 descriptor 수와 다릅니다. Frame의 정확한 stride는 offsetof(PGBUF_IOPAGE_BUFFER, iopage) + IO_PAGESIZE에 CUBRID_DEBUG 사용 시 guard를 더한 값입니다. 구조체 크기는 ABI와 빌드 옵션에 따라 달라집니다.

페이지 P 하나의 흐름

1

P를 요청한다

이름으로 메모리에 있는지 찾습니다.

2

없으면 자리를 마련한다

빈 frame을 쓰거나, 안전한 후보를 내보낸 자리에 P를 읽습니다.

3

접근 권한을 얻는다

Fix가 성공하면 latch로 보호되는 내용을 사용합니다.

4

읽거나 변경한다

변경 경로의 호출자는 필요한 로그와 dirty 표시를 처리합니다.

5

사용을 마친다

Unfix합니다. 이 동작이 flush나 commit을 뜻하지는 않습니다.

6

기록하고 다시 활용한다

Dirty 내용은 관련 로그를 먼저 안전하게 기록하는 WAL 순서를 지켜 저장합니다. 이후 안전 조건을 만족하면 frame을 다른 페이지에 재사용할 수 있습니다.

일반적인 기존 페이지 요청을 요약한 흐름입니다. 모든 요청이 쓰기나 교체로 끝나지는 않으며, flush는 다른 실행 흐름에서 진행될 수도 있습니다.

Miss에서 frame 확보까지: 실제 helper를 따라가기

소스 위치 펼치기

고정 소스: page_buffer.c:2416 · page_buffer.c:8392–8500 · page_buffer.c:8181–8403 · page_buffer.c:9067–9253

마지막 두 호출은 invalid list에서 자리를 얻지 못하고 선택된 victim 검색 분기가 LRU에 도달하는 경우다. 할당은 재시도하거나 기다릴 수 있다. 모든 실행이 이 그림대로 진행되지는 않는다.

사용이 끝나면 페이지도 사라질까?

P를 읽고 unfix한 직후 다른 스레드가 P를 요청합니다. 반드시 다시 읽어야 할까요?

설명 펼치기

아닙니다. P가 여전히 resident라면 같은 frame을 사용할 수 있습니다. Unfix는 한 번의 사용을 끝내는 동작이고, eviction은 메모리의 페이지 매핑을 제거하는 동작입니다. 새 요청은 다시 fix해야 합니다.
