01 · owner object 정의하기

watcher는 일반 page debt에 ordering history를 더한 것이다

PGBUF_WATCHER는 현재 page pointer/ownership state와 page 집합의 순서를 정하는 metadata를 담는다. fix debt를 대체하는 것이 아니라, multi-page protocol을 거치는 동안 debt를 옮기고 감사할 수 있게 한다.

Watcher 정보누가 제공하거나 해석하는가?
Groupaccess method가 semantic group을 제공한다. heap page에서는 heap-header VPID다.
Rankaccess method가 heap header, normal, overflow 순의 semantic order를 제공한다.
VPIDPage buffer가 마지막 ordering coordinate로 사용한다.
page_was_unfixed이 watcher가 release/refix window를 지났음을 page buffer가 알린다. caller는 관찰값을 다시 세워야 한다.

의미와 순서는 access method가 정의하고, ordered ownership transition은 page-buffer Module이 강제한다.

02 · Canonical order

Group → rank → VPID

대표 heap protocol에서는 다음 순서로 page를 비교한다.

  1. group: heap-header VPID,
  2. rank: HEAP_HDR < HEAP_NORMAL < HEAP_OVERFLOW,
  3. VPID: 같은 group/rank 안에서의 deterministic order.

group을 알 수 없는 page는 마지막에 정렬된다. 같은 page의 모든 watcher는 rank가 일치해야 한다. 이 순서는 access-method owner protocol이며 page buffer가 임의로 만든 범용 semantic ordering이 아니다.

03 · Input과 output

return value는 status를, watcher는 ownership을 전달한다

호출 형태는 개념적으로 pgbuf_ordered_fix(thread, req_vpid, fetch_mode, request_mode, req_watcher)다. 앞의 네 input은 현재 thread, page, fetch 의미, 요청 latch를 정한다. 호출 전에 caller는 PGBUF_INIT_WATCHER()로 clean watcher를 초기화한다. 이때 pgptr는 null이고, initial_rank와 필요하면 HFID에서 얻은 heap group이 access-method order를 표현한다.

결과 channel의미
Integer returnNO_ERROR 또는 error code다. page pointer가 아니다.
req_watcher성공하면 pgptr가 watched fix를 담고, watcher에는 latch mode, current rank, resolved group, holder link가 기록된다.
이미 attach된 watcherhelper가 현재 thread의 holder를 통해 찾아낸다. release/refix된 watcher는 page_was_unfixed=true와 함께 pointer를 되찾는다. partial failure 뒤에는 일부 pointer만 복구되고 나머지는 null일 수 있다.

watcher는 in/out ownership ledger다. 성공은 status와 watcher pointer를 함께 봐야 완성되고, 실패는 영향받은 watcher를 하나씩 확인해야 이해할 수 있다.

04 · Ordered refix

먼저 싸게 시도하고, 요청 순서를 어기는 것만 release한다

conditional fix가 성공하면 아무것도 release하지 않는다. conditional attempt가 실패한 뒤에만 reordering을 시작한다.

  1. 다른 watched page를 계속 hold한 채 요청 page R을 conditionally fix한다.
  2. grant되면 R을 기록하고 끝낸다. borrowed lifetime은 끊기지 않았다.
  3. reject되면 hold 중인 모든 watcher H를 R과 비교한다.
  4. H가 R보다 앞에 정렬되면 fixed 상태를 유지한다.
  5. H가 R보다 뒤에 정렬되거나 R의 group을 아직 모르면 H를 완전히 unfix한다. 동시에 avoid-deallocation을 등록하고 watcher에 unfixed 이력을 표시한다.
  6. R을 unconditionally fix한 뒤 release한 page를 정렬 순서대로 refix한다.
  7. partial failure에서는 어떤 watcher가 돌아왔고 무엇이 release 상태인지 정확히 보존하여 caller가 unwind할 수 있게 한다.

Verified mechanism: pinned ordered helper와 callback은 page_buffer.c:12268–13531에 있다.

05 · heap group 예제

0|90은 유지하고, 0|100을 0|120 앞에 넣는다

Page역할/순서conditional failure 뒤 동작
hold 중인 0|90Heap header, 첫 번째계속 fixed 상태를 유지한다.
요청한 0|100Normal, 두 번째뒤쪽 page를 release한 다음 unconditionally fix한다.
hold 중인 0|120Normal, 세 번째완전히 unfix한 뒤 0|100 다음에 refix하고 page_was_unfixed를 set한다.

최종 hold 순서는 0|90 < 0|100 < 0|120이다. 0|90에서 얻은 관찰값은 계속 보호되지만, 0|120에서 얻은 관찰값은 그렇지 않다.

06 · Revalidation 경계

pointer가 복구됐다고 지식까지 복구되는 것은 아니다

page_was_unfixed=true인 watcher마다 다음을 다시 구성한다.

  • record와 slot pointer,
  • free-space와 destination 선택,
  • page header와 type/identity에 의존하는 field,
  • 다른 hold page와의 관계,
  • 이 동작을 정당화한 access-method condition.

계속 보호된 관찰값까지 전부 버릴 필요는 없다. watcher flag가 정확한 경계를 준다. release된 watcher 뒤쪽 지식을 다시 세우고, 그에 의존한 cross-page 결론을 별도로 revalidate한다.

promotion과 같은 교훈을 더 큰 집합에 적용한다: refix 뒤 pointer 값이 같아도 이전 borrowed lifetime이 연장되는 것은 아니다. ownership을 다시 만들었으므로 지식도 다시 만들어야 한다.
07 · Partial failure

function 결과 하나가 아니라 watcher마다 audit한다

R은 성공했지만 뒤의 refix가 실패하면 held set은 혼합 상태다. 이미 복구된 watcher도 있고 release state를 가진 watcher도 있으며 R 자체가 hold 중일 수도 있다. 올바른 caller/helper unwind는 각 debt를 정확히 한 번 소비하거나 유지하고 avoid-deallocation balance를 보존해야 한다.

대표 caller 경계: heap destination/watcher ownership은 pinned heap_file.c:20493–20664에 있다. 이 caller가 generic page-buffer ordering만으로 추론할 수 없는 heap 의미를 제공한다.

08 · Retrieval 연습

watcher별 ledger를 작성한다

문제

한 heap group이 header 0|90과 normal page 0|120을 hold한다. normal page 0|100을 요청했지만 conditional attempt가 실패하고, 나중에는 0|120 refix도 실패한다.

과제: page 순서를 정하고 모든 release/acquisition을 trace하라. 살아남는 관찰값을 식별하고 partial-failure unwind가 답해야 할 최종 ownership 질문을 나열하라.

답을 chat에 붙여 넣어 보자. order ownership, selective release, observation lifetime, partial-failure debt를 확인한 뒤 Advanced 진도를 기록한다.

pinned page_buffer.c:12268–13531을 읽고 comparison coordinate, conditional attempt, selective full unfix, avoid-deallocation registration, requested-page acquisition, sorted refix, page_was_unfixed, 모든 partial-failure exit를 표시하라.
