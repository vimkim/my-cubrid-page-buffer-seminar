01 · Presenter의 역할

Model을 가르치고 catalog는 길을 안내한다

팀에 필요한 것은 모든 function의 암기가 아니다. 동작을 예측하는 model, 강한 주장을 검증하는 source route, evidence가 끝나는 지점을 솔직하게 밝히는 태도다.

하나의 page journey를 설명하고, document set으로 확장·진단·변경·검증하거나 주장 범위를 한정한다.

Pinned revision을 항상 보이게 두세요. 다른 branch에 대한 질문을 받으면 기존 주장을 조용히 옮겨 가지 말고 무엇을 다시 trace해야 하는지 말합니다.

02 · 여섯 단계

언제나 같은 causal story로 설명한다

단계전달할 핵심답할 질문
1 · Object와 boundaryVPID → BCB ↔ frame → PAGE_PTR. Pointer는 잠시 빌린 view다.“Fix가 정확히 무엇을 반환했나?”
2 · Acquire와 releaseHit와 miss는 latch grant, global/per-thread fix debt로 합류하며 성공 한 번에는 release 한 번이 필요하다.“Hit인데 왜 기다릴 수 있고 reuse는 무엇이 막나?”
3 · Caller correctnessLogical locking, validation, mutation, logging, page LSA, dirtying, 모든 exit의 cleanup은 여전히 caller 소유다.“WRITE latch만으로 왜 부족한가?”
4 · Flush generationG를 copy하고 concurrent G+1을 보존하며 page propagation 전에 WAL을 force하고 failure를 retry 가능하게 둔다.“DIRTY와 FLUSHING이 어떻게 동시에 true인가?”
5 · 안전한 replacementEligibility는 protection 아래의 hard predicate다. Policy는 eligible BCB 중에서만 고르고 안전한 detachment 뒤에만 identity를 바꾼다.“왜 fcnt==0만으로 부족한가?”
6 · Evidence에 근거한 변경Owner, state, guard, invariant, negative path, caller impact, risk-matched proof level을 밝힌다.“이 source 우려는 검증된 defect인가?”

04 · 어려운 질문에 답하는 pattern

다섯 단계로 답하고 거기서 멈춘다

  1. 짧은 답: 직접적인 한 문장.
  2. Owner/state/guard: 누가 무엇을 어떤 protection 아래에서 바꾸는지 밝힌다.
  3. Invariant와 consequence: 무엇이 계속 true여야 하며 그렇지 않으면 무엇이 깨지는지 말한다.
  4. Evidence level: contract, verified mechanism, policy, inference, runtime observation, historical evidence 중 하나.
  5. Route: Canonical 설명, source range, registry row, verification seam을 가리킨다.
반론첫 문장확장할 route
“Resident인데 왜 fix가 block되나?”Residency와 latch grant는 독립된 축이다.Acquisition concurrency와 latch queue.
“BCB 하나가 두 page 소유일 수 있나?”Stable slot 하나의 current VPID는 하나지만 protected detachment 뒤에 순차적으로 reuse할 수 있다.Replacement safety와 identity timeline.
“Statistics가 0이면 deallocate해도 되나?”Approximate diagnostic snapshot은 state transition을 허가하지 못한다.Specialized interface와 protected owner path.
“VS-12는 실제 bug인가?”Pinned source가 입증하는 것은 ordering concern이며 reachability, surviving state, impact, current status는 별개다.Registry, failure-proof ledger, target injection.
05 · 솔직한 uncertainty

“아직 모른다”도 maintainer다운 답이 될 수 있다

Fairness bound, current-branch status, metric 의미, failure consequence를 추측하지 마세요. 막연한 모름을 범위가 명확한 다음 단계로 바꿉니다.

“Pinned source는 X를 보여 주지만 Y는 입증하지 않습니다. Y는 이 registry row 또는 mechanism이 다루며, source trace, controlled schedule, fault injection, pressure test, crash boundary 중 이 검증으로 답할 수 있습니다.”

이것은 회피가 아니다. Model, implementation revision, 더 강한 주장에 필요한 evidence의 차이를 이해하고 있음을 보여 준다.

06 · Rehearsal loop

설명, 탐색, 반론 대응 순으로 연습한다

  1. 자료를 보지 않고 여섯 단계를 설명한다. 중간에 고치지 말고 녹음하거나 받아 적는다.
  2. 빠진 transition, 정의하지 않은 term, 근거 없는 claim, 끊긴 route를 모두 표시한다.
  3. Guide를 펼쳐 두고 다시 설명하며 claim 하나를 owner page와 pinned source까지 찾아간다.
  4. Core spine은 바꾸지 않은 채 섞인 counterexample 네 개에 답한다.
  5. Storage, logging/recovery, access-method teammate 한 명과 연습하고 그 질문과 수정한 답을 기록한다.

실제 발표 시간과 audience 구성이 정해지면 각 단계 안의 detail을 줄이되 causal spine 순서는 바꾸지 않는다.

07 · Presentation gate

Opening을 설명하고 반론 하나에 답한다

문제

자료를 보지 않고 opening부터 여섯 단계까지 설명하세요. 그런 다음 resident hit가 block됨, DIRTY와 FLUSHING 동시 설정, 나중에 달라진 BCB의 VPID, 0인 statistic, 사실처럼 보이는 VS-* row 중 하나의 반론에 답합니다.

할 일: 하나의 causal narrative를 유지하고 짧은 답 → owner/state/guard → invariant/consequence → evidence level → route 순서로 답하라.

Transcript를 chat에 붙여 넣으세요. 실제로 보여 준 설명만 평가하고 가장 좁은 gap을 보완하며, 가장 좋은 표현은 다음 rehearsal에 남기겠습니다.
