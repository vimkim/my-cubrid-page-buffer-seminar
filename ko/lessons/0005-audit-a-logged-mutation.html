LECTURE 5 / 변경과 durability

Caller의 correctness와 logged mutation

Fix 성공으로 접근 권한을 얻어도 logical locking, validation, logging, dirty publication과 cleanup은 caller의 책임으로 남습니다.

Logical lockWRITE latchValidateLogPage LSADIRTYCleanup
01 · Access는 필요조건이지 충분조건이 아닙니다

성공한 fix는 access 질문에만 답합니다

NULL이 아닌 PAGE_PTR는 요청한 resident page에 임시로 latched access를 얻었다는 증거일 뿐, caller의 logical operation이 올바르다는 증거는 아닙니다.

Fix 성공만으로 heap slot이 적합한지, record representation이 유효한지, transaction이 필요한 logical lock을 보유했는지, recovery payload가 올바른지, page LSA가 전진했는지, generation이 dirty인지, 모든 error path가 watcher를 release하는지는 알 수 없습니다.

review 질문: 각 condition은 어느 layer가 성립시키며, 어느 exit가 page, watcher, logical lock, overflow object 또는 recovery obligation을 아직 소유하고 있나요?
02 · 두 가지 protection

Page latch와 transaction lock은 서로의 더 강한 버전이 아닙니다

heap insert 하나에는 둘 다 필요하지만, 보호하는 객체와 release protocol이 다릅니다.

Protection보호 대상끝나는 시점제공하지 않는 것

Interface contract: page latch는 현재 in-memory bytes access를 보호합니다. Implementation policy: 이 heap insert는 page-buffer watcher ownership과 lock manager의 class/row locking을 함께 사용합니다.

03 · 대표 caller

성공 path의 여섯 step을 따라갑니다

각 row를 왼쪽부터 action, owner, exit에 남는 state 순서로 읽으세요.

  1. Prepare and lock: heap과 lock management가 logical concurrency를 성립시킵니다. 큰 record라면 먼저 overflow storage를 만들 수도 있습니다.
  2. Acquire and validate: watcher가 page latch와 fix debt를 보유하는 동안 heap은 space, slot, identity, row-lock condition을 검증합니다.
  3. Mutate: heap 및 slotted-page code가 record와 page-format invariant를 지킵니다.
  4. Log and advance LSA: caller가 recovery 의미를 선택합니다. 필요하면 log manager가 page-buffer interface를 통해 page LSA를 전진시킵니다.
  5. Publish DIRTY: pgbuf_set_dirty(..., DONT_FREE)는 ownership을 의도적으로 유지하면서 resident generation을 propagation 대상으로 표시합니다.
  6. Transfer or release: caller가 home watcher를 scan cache로 transfer하거나 ordered-unfix한 뒤 남은 watcher를 cleanup합니다.

Verified mechanism과 Implementation policy: 대표적인 success spine은 pinned heap_file.c:23120–23324에 있습니다. 이는 대표 caller의 evidence이지, 모든 page-buffer caller가 올바르다는 증명은 아닙니다.

06 · Caller knowledge

NEW_PAGE는 allocation과 buffer를 잇는 contract입니다

VPID는 이미 allocate되었지만 logical page는 아직 initialize되지 않았습니다. NEW_PAGE는 obsolete home-page image를 읽지 않고 보호된 resident storage를 materialize하라고 page-buffer Module에 알립니다.

이 이름은 두 ownership boundary를 가로지릅니다. 먼저 file 또는 disk code가 identity를 reserve합니다. 그다음 page buffer가 resident BCB/frame과 Module-owned metadata를 준비합니다. 마지막으로 owning subsystem이 page type/layout을 초기화하고 TDE와 recovery 동작을 고르며 generation을 dirty로 표시한 뒤 fix debt를 transfer하거나 갚습니다.

Miss와 hit은 의도적으로 서로 다르게 준비됩니다

상황검증된 page-buffer 작업여전히 caller가 맡는 작업
Buffer miss재사용할 BCB/frame을 claim하고 VPID를 bind합니다. DWB, home-volume read, decryption, read statistics를 건너뛰고 LSA/identity metadata를 초기화합니다. PAGE_UNKNOWN을 허용한 뒤 요청 latch 아래에서 grant하고 publish합니다.Logical payload, page type/layout을 초기화하고 TDE/recovery logging을 선택합니다. Dirty, failure 처리, ownership release/transfer도 caller 책임입니다.
Resident hit기존 mapping을 사용해 일반 fix/latch를 얻습니다. Miss 전용 metadata initialization은 다시 실행하지 않습니다. Resident PAGE_UNKNOWN image는 정상적인 reallocation case입니다.이 mode가 frame을 지웠다고 가정하지 않습니다. 같은 owner-specific initialization과 cleanup protocol을 끝까지 수행합니다.

Pinned revision의 direct creation call 열 개는 모두 file/disk owner에 있고 WRITE와 unconditional acquisition을 요청합니다. 이는 검증된 caller pattern이지 type-system restriction은 아닙니다. Zero-wait policy 때문에 conditional NULL outcome이 생길 수도 있습니다.

Representative source: pinned file_alloc()는 먼저 allocate하고 NEW_PAGE로 fix한 뒤 owner initializer를 실행하고 known type을 요구하며 TDE를 적용한 다음 transfer 또는 unfix합니다. 범위는 file_manager.c:5360–5590입니다. Miss/hit branch는 page_buffer.c:2380–2616과 8392–8634입니다.

No-read operation이 존재하는 이유

대체 제안동일하지 않은 이유
OLD_PAGEMiss이면 DWB 또는 data volume을 읽고 필요하면 decrypt하며 PAGE_UNKNOWN을 reject합니다. 의미 없는 I/O와 failure path가 늘어나고 resident deallocated image를 재사용하는 지원 경로도 깨집니다.
RECOVERY_PAGE더 넓은 allocation state를 허용하지만 miss에서는 여전히 읽습니다. 또한 creation contract가 아니라 recovery 전용 validation boundary를 우회합니다.
Cache miss에서 “new” 추론Not resident는 newly allocated와 다릅니다. Old image를 보기 전에 read 여부를 결정해야 하므로 allocation owner만 intent를 알고 있습니다.

다른 engine도 같은 내부 responsibility를 노출합니다

EngineInternal Interface 형태공통 responsibility
CUBRIDPAGE_FETCH_MODE::NEW_PAGEAllocated identity를 no-read로 resident materialize하고 caller가 WRITE를 hold한 채 initialize합니다.
PostgreSQLRBM_ZERO_AND_LOCKOld bytes를 읽지 않고 caller initialization을 위해 exclusive lock된 buffer를 반환합니다.

“Public API”에는 boundary가 필요합니다. page_buffer.h는 Server-module Interface이며 설치되는 SQL, CCI, application API가 아닙니다. 실제 design 질문은 creation을 넓게 조합할 수 있는 enum으로 유지할지, 더 좁은 internal function으로 만들지입니다.

Recommendation: semantic no-read creation operation은 유지합니다. 더 deep한 Interface가 필요하다면 WRITE를 암시하고 caller initialization obligation을 이름에 드러내는 creation function 뒤로 숨기거나 분리합니다. External sort의 specialized full-page overwrite는 allocation contract가 다르므로 별도로 유지해야 합니다.

07 · 함께 생각하기

mutation의 전체 contract를 audit합니다

문제

“WRITE fix가 성공한 뒤에도 logged mutation이 올바르려면 heap caller가 무엇을 더 증명하고 수행해야 하며, 모든 exit를 어떻게 audit해야 하나요?”

생각할 점: pgbuf_set_dirty()가 page-LSA advancement도 release도 아닌 이유를 설명하고 early exit 하나를 분석하세요.

설명 펼치기

두 protection → validate → mutate → log/page LSA → DIRTY → transfer/release → exit ledger.

필수 읽기

caller의 전체 mutation protocol을 annotate합니다

Pinned heap_file.c:23120–23324를 읽으세요. 여섯 success step과 모든 direct return 또는 goto error를 표시합니다. 각 exit마다 acquired state, cleanup/transfer owner, 남은 recovery 또는 retry 결과를 기록하세요.
