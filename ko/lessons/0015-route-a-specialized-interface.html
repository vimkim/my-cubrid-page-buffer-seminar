PAGE_PTR처럼 보인다고 fix인 것은 아니다

이 학습을 마치면 helper가 편리해 보이더라도 owner, protection, accounting, 허용 operation, 짝이 되는 cleanup을 확인하기 전에는 섣불리 재사용하지 않을 수 있다.

01 · 대체 가능성 검사

속도를 비교하기 전에 protocol부터 분류한다

두 function이 모두 page byte처럼 typed된 값을 반환해도 caller에게 주는 권한은 전혀 다를 수 있다. 하나를 다른 것으로 대체하기 전에 다음을 묻는다.

  1. Owner: 어느 subsystem이 이 protocol을 사용할 수 있는가?
  2. Location: byte가 resident frame, caller area, private copy 중 어디에 있는가?
  3. Guard: byte를 사용하는 동안 충돌하는 변경을 무엇이 막는가?
  4. Accounting: BCB fix, per-thread holder, 둘 다, 혹은 아무것도 만들지 않는가?
  5. Cleanup: 정확히 어떤 operation이 lifetime을 끝내는가?
  6. Permission: caller는 mutate, dirty, flush, invalidate할 수 있는가, 아니면 inspect만 가능한가?

Interface는 return value의 C type이 아니라 완전한 owner protocol을 보고 선택한다.

03 · Area-copy 위험

Parameter 이름만으로 지원되는 mode라고 판단할 수 없다

VS-02와 VS-03은 pinned source drift를 기록한 uncertainty-registry identifier다. Runtime error code가 아니다.

HelperPinned executable pathReview 방침
pgbuf_copy_to_area()
VS-02		Miss에서 do_fetch=true이면 READ fix, copy, unfix를 수행한다. false이면 direct-I/O body가 보통 compile out되므로 변경되지 않은 caller area를 반환할 수 있다.기존 PAGE_AREA owner 전용이다. 신뢰할 수 있는 일반 page-read abstraction으로 확대 해석하지 않는다.
pgbuf_copy_from_area()
VS-03		일반 build에서 do_fetch는 direct I/O를 선택하지 않는다. Function은 NEW_PAGE WRITE로 fix하고 page type/TDE를 설정한 뒤 copy, logging skip, dirty, free를 수행한다.기존 owner 전용이다. WAL-aware 일반 page writer로 사용하지 않는다.

Pinned revision에서 검증: page_buffer.c:4701–4912. Current status는 uncertainty registry가 소유하며 newer branch에서는 다시 확인해야 한다.

04 · Observation과 authority

Approximate signal은 조사를 제안할 뿐 operation을 허가하지 않는다

Waiter query, SHOW row, statistics는 path-specific synchronization 아래에서 diagnostic 또는 scheduling 질문에 답한다. 예를 들어 pgbuf_peek_stats()는 각 BCB를 lock하지 않고 의도적으로 flag를 copy하므로 concurrent change가 있으면 approximate snapshot이 된다.

안전한 사용: “이 count는 replacement pressure 가능성을 보여 준다. Protected path를 조사하자.”
위험한 사용: “Count가 0이므로 이 page를 deallocate하거나 reuse해도 된다.”

VS-04는 pgbuf_peek_stats()의 prototype-name drift를, VS-05는 approximate snapshot semantics를 다룬다. 어느 값도 state transition을 허가하는 mutex, latch, identity recheck, owner protocol을 대신하지 못한다.

Verified mechanism: page_buffer.c:14748–14847,17323–17530.

05 · 없거나 미완성인 interface

Declare되었다고 사용할 수 있는 것은 아니다

Pinned revision의 release header는 pgbuf_fix_without_validation_release()를 macro-map하고 declare하지만 repository-wide search에서는 definition이나 caller가 나오지 않는다. VS-01이 이 verified source fact를 기록한다.

더 빠른 bypass로 소개하면 안 된다. Target branch에 definition과 완전하고 검증된 owner protocol이 없다면 호출 시 link가 실패한다.

Interface inventory: declaration은 page_buffer.h:320–326, availability status는 VS-01이 소유한다.

07 · Retrieval 연습

안전하지 않은 네 가지 대체안을 거부한다

문제

Review에서 네 가지 shortcut을 제안했다. Temporary page에 write할 수 있는 곳에서 simple fix 사용, heap scan-copy를 mutate하고 unfix, logged update에 copy_from_area(..., false) 사용, approximate statistics에 사용자가 없으면 deallocate하는 방식이다. Patch는 release build에서 pgbuf_fix_without_validation()도 호출한다.

할 일: 각 선택의 owner, byte 위치, guard, accounting, paired cleanup, 허용 operation, evidence status를 밝혀 거부하거나 범위를 제한하라.
