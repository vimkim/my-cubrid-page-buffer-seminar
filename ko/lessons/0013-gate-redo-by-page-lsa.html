01 · 두 buffer 분리하기

log page는 자체 descriptor와 frame을 사용합니다

page_buffer.c와 log_page_buffer.c는 서로 다른 buffering subsystem이다. include와 function call은 둘을 조율하지만, log page를 data-page pool에 넣지는 않는다.

append code가 현재 log page를 “fixed”라고 부를 때가 있지만, LOG_BUFFER에는 fcnt, holder, BCB waiter queue, hash/LRU link가 없다. log append protocol이 log synchronization 아래에서 그 frame을 유지한다는 뜻이다.

WAL은 두 pool의 durability 순서를 연결한다. 한 pool의 frame을 다른 pool으로 옮기지 않는다.

02 · memory의 log page

modulo index가 hash lookup과 victim 선택을 대신한다

frame이 네 개인 예에서는 page 0–3이 slot 0–3에 들어가고 page 4는 다시 slot 0에 매핑된다. log page마다 memory 후보 slot이 정확히 하나이므로 LRU victim scan이 없다. hit이면 그 frame을 사용하고, clean collision이면 identity를 바꿔 요청 page를 읽거나 초기화한다. dirty collision은 예상 밖이며 defensive flush path가 있다.

수정된 append page는 logical order대로 toflush[]에 유지된다. usable maximum은 num_buffers - 1이며, 여기에 도달하면 modulo wrap이 unflushed page와 충돌하기 전에 append-page flush를 강제한다.

Pinned 기본값은 log_buffer_size=16,384 page다. 16 KiB log page라면 frame area는 256 MiB이고 descriptor와 보조 state는 별도다. 기본 512 MiB data page buffer와도 별개의 memory다.

03 · Append와 log flush

record를 staging한 뒤 append page에 복사하고 순서대로 durable하게 만든다

  1. LOG_PRIOR_NODE가 record를 staging하고 logical LSA를 받는다.
  2. append path가 header와 undo/redo byte를 현재 direct-mapped LOG_PAGE에 복사한다.
  3. page boundary를 넘으면 append_lsa.pageid를 전진시키고 다음 frame을 toflush[]에 넣는다.
  4. logpb_flush_all_append_pages()가 page를 묶어 쓰되, nxio_lsa가 들어 있는 boundary page를 마지막에 쓰고 active-log file을 sync한다.
  5. nxio_lsa가 아직 durable하다고 확인되지 않은 가장 낮은 주소로 전진한다.

일반 reader는 자체 LOG_PAGE storage를 건넨다. logpb_fetch_page()는 resident 또는 disk page를 보통 그곳에 copy하므로 나중에 pgbuf_unfix()할 일이 없다. 현재 pool frame을 직접 유지하고 수정하는 append writer는 별도의 특수 경로다.

04 · Logical length와 physical storage

active log는 fixed ring이고 archive가 이전 구간을 보존한다

기본 512 MiB log volume과 16 KiB page라면 active file은 32,768개의 physical page, 즉 header 하나와 data-log slot 32,767개를 갖는다. logical page ID는 계속 증가하고 physical slot은 fpageid를 기준으로 wrap한다.

slot을 재사용하기 전에 이전 logical range를 numbered archive로 copy하고 sync한다. Background archiving은 이 비용을 나누기 위해 temporary archive를 점진적으로 준비한다. data-page double-write buffer가 아니다.

Frontier의미
append_lsa현재/다음 logical append 위치
nxio_lsa아직 durable하다고 확인되지 않은 가장 낮은 log 주소

LSA는 (page ID, offset) 형식의 logical 좌표다. storage를 할당하거나 보존하지 않는다. 표현 범위는 매우 크지만 유한하며, 실제로 읽을 수 있는 history는 active ring, archive file, recovery/vacuum/HA/CDC/flashback/retention 조건에 달려 있다.

05 · 두 pool의 연결점

WAL은 변경된 data page보다 log를 먼저 durable하게 만든다

dirty data page에는 byte에 반영된 가장 최신 log change의 LSA가 있다. BCB frame을 data volume에 쓰기 전에 page buffer는 logpb_flush_log_for_wal()을 호출한다. page LSA가 nxio_lsa 이상이면 append log page를 먼저 flush하고 sync한다.

crash 뒤 recovery가 이미 disk에 도달한 모든 변경 data page를 설명하는 log record를 찾을 수 있어야 한다. 이 write order가 그 전제조건을 만든다.

06 · Checkpoint boundary

Checkpoint는 선택적인 page propagation을 조율합니다

  1. Log code가 append state를 flush하고 checkpoint 시작을 기록한다.
  2. Page buffer는 checkpoint boundary까지 조건을 만족하는 dirty page만 골라 flush하고, 남은 redo floor를 보고한다.
  3. Filesystem synchronization이 설정된 boundary를 확정한다.
  4. Log code가 active transaction/system-operation state를 기록하고 end-checkpoint/header state를 영속화한다.
  5. Permanent-volume checkpoint metadata를 기록한 뒤 설정된 DWB boundary를 거쳐 동기화한다.

Page buffer가 담당하는 것은 선택적 page propagation이다. 전체 checkpoint record, WAL, filesystem sync, volume metadata protocol까지 소유하는 것은 아니다.

Verified mechanism: pinned checkpoint coordination은 log_page_buffer.c:6901–7406에서 확인할 수 있다.

07 · Redo idempotence

적용하기 전에 비교한다

값이 같으면 이미 반영된 것이다. record LSA ≤ page LSA이면 skip한다.

  1. Recovery는 caller가 건넨 identity를 RECOVERY_PAGE, WRITE, unconditional access로 fix한다.
  2. Redo record LSA와 현재 page LSA를 비교한다.
  3. record_lsa <= page_lsa이면 unfix하고 skip한다. 해당 변경이나 그 이후 변경이 이미 page에 반영되어 있기 때문이다.
  4. 그렇지 않으면 WRITE protection 아래에서 선택된 recovery callback을 적용한다.
  5. Page LSA를 record LSA까지 전진시키고, recovery protocol이 요구하는 대로 page를 DIRTY로 표시한 뒤 모든 exit에서 release한다.

Verified mechanism: gate는 log_recovery.c:497–536, fetch semantics는 6407–6431, apply/LSA/cleanup은 log_recovery_redo.hpp:587–668에 있다.

이제 record 170을 다시 만나면 page LSA가 이미 170이므로 skip한다. 이것이 page 변경에 대한 idempotence 논리다. Page 밖에서 callback이 일으키는 임의의 side effect까지 idempotent하다고 보장하는 것은 아니다.

09 · Special fetch ownership

Recovery는 일반 caller가 모르는 allocation history를 안다

RECOVERY_PAGE, OLD_PAGE_DEALLOCATED, OLD_PAGE_MAYBE_DEALLOCATED에는 redo/undo와 allocation history에 관한 recovery의 지식이 담겨 있다. 따라서 일반 OLD_PAGE validation이라면 거부할 state를 받아들이거나 skip할 수 있다.

Log record 이후에 page가 deallocate되었다면 redo는 이를 skip할 수 있으며, 이 skip은 fix debt를 만들지 않는다. Logical allocation/deallocation의 owner는 여전히 file/disk code다. Page buffer는 그 owner가 선택한 identity를 materialize하거나 cache coherence를 지키며 invalidate한다.

일반화하면 안 된다: recovery 또는 temporary page에 적용되는 완화된 validation/logging 동작은 일반 permanent page caller가 allocation, type, logging contract를 우회해도 된다는 뜻이 아니다.
10 · Caller contract 재사용

Recovery도 logged page와 같은 방식으로 state를 전이한다

Gate가 apply를 선택하면 익숙한 ownership 순서로 돌아온다. WRITE-protected byte를 수정하고, page LSA에 가장 최근에 반영된 log action을 기록하며, DIRTY로 propagation debt를 공개하고, scope cleanup에서 모든 exit의 fix를 갚는다.

차이는 의미를 정하는 주체다. Recovery는 log record를 보고 callback과 special fetch mode를 고른다. 일반 page-buffer Module은 resident identity, byte protection, LSA interface, dirty state, release mechanics를 제공한다.

11 · Scope cleanup 해석

이 function scope가 끝날 때 stack guard가 pointer를 unfix한다

fix/gate가 redo를 계속하라고 판단한 뒤 log_rv_redo_record_sync()는 local scope_exit unfix_rcv_pgptr를 만든다. 이 guard는 thread_p와 stack-local rcv를 reference로 capture한다. Destructor는 pgbuf_unfix_and_init_after_check(thread_p, rcv.pgptr)를 호출한다.

  1. rcv.pgptr가 non-null이면 helper가 pgbuf_unfix()를 정확히 한 번 호출하고 pointer를 null로 만든다.
  2. Destructor는 정상적으로 function 끝에 도달할 때와 redo-data 추출 실패 뒤 명시적 early return을 할 때 모두 실행된다.
  3. guard가 rcv 뒤에 선언되었으므로 역순 destruction에서 rcv가 살아 있는 동안 cleanup이 먼저 실행된다.
  4. callback이 pointer를 null로 남기면 cleanup은 아무 일도 하지 않는다. guard 생성 전에 skip하는 path는 pointer가 null이라는 postcondition을 이미 assert한다.
경계: 이것은 lexical C++ RAII다. background cleanup phase, commit, delayed release가 아니다. Guard는 scope exit 시점에 남아 있는 fix만 갚으며, redo 여부 결정, page LSA 설정, DIRTY 표시는 수행하지 않는다.

Verified mechanism: guard 사용은 log_recovery_redo.hpp:601–668, null-safe unfix-and-clear helper는 page_buffer.h:64–71, guard destructor는 scope_exit.hpp:28–80에 있다.

12 · Crash evidence

Crash redo는 controlled restart evidence로 검증합니다

기존 checkpoint/backup 관찰만으로 restart redo, page별 WAL ordering, DWB recovery, torn-page handling, home-page persistence를 입증할 수 없다. Source는 의도된 gate를 보여줄 뿐이다. Crash safety에 대한 runtime evidence를 얻으려면 controlled crash point, 정확한 build/configuration, 주장하는 boundary에서의 restart 이후 state validation이 필요하다.
