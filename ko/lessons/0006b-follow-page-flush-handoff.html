Page-flush와 post-flush handoff

Clean 후보를 만드는 일과 상태 처리를 마치는 일

Dirty page에는 재사용할 때 버리면 안 되는 변경이 있다. Page-flush는 조건에 맞는 cold dirty page를 찾아 WAL 순서 조건을 지킨 뒤 사본을 제출한다. 이 background 공급이 없으면 요청자가 동기 cleaning이나 대기를 더 많이 맡을 수 있다. 명시적 flush와 foreground flush 경로 자체가 사라지는 것은 아니다.

Post-flush는 제출 이후 BCB pointer를 받아 상태 처리를 마치고, 조건이 맞으면 direct victim을 배정한다. 같은 page image를 다시 제출하는 일이 아니다. Post-flush daemon이 없을 때는 producer가 현장에서 완료 처리하는 fallback이 있다. Consumer만 제거하고 이미 전달된 일을 방치하는 것과는 다르다.

예: allocator가 frame을 기다리는 동안 flusher가 cold dirty page를 clean하게 만든다. Queue 전달 조건이 맞으면 post-flush가 BCB를 다시 확인한 뒤 배정을 시도한다. 새 fix나 더 최근 dirty generation이 있으면 바로 재사용할 수 없다. 사본 하나의 완료가 현재 frame의 clean 상태를 보장하지 않는다.

Page-flush: 사본 제출의 호출 경로

이 page-flush 경로는 neighbor flush를 거치지 않는 non-DWB write 분기다. WAL flush와 page 제출은 공통 flush helper 안에서 순서대로 수행되는 형제 작업이며, WAL helper가 page writer를 호출하는 관계는 아니다.

그 사이의 전달은 비동기이며 flushed_bcbs queue에 BCB pointer를 넣고 wake한다. Page-flush producer, 존재하는 post-flush daemon, 대기 allocator, enqueue 성공이 모두 필요하다. Wake는 중첩 함수 호출이 아니다. Enqueue와 현장 fallback.

Timer와 frame 부족이 page-flush를 깨운다

주기적인 실행과 frame 부족에 따른 wakeup이 있습니다. 깨어났다는 사실만으로 page를 썼다고 판단할 수는 없습니다. 작업은 대기 allocator와 현재 교체 압력을 확인합니다.

세부 동작과 소스 펼치기

pgbuf-page-flush는 기본 1,000 ms인 page_bg_flush_interval만큼 pause합니다. 0이면 wake가 올 때까지 무기한 기다립니다. normal victim search가 실패하거나, clean bottom 제거 뒤 dirty bottom이 드러나거나, 선택한 victim scan이 reusable BCB를 못 찾으면 allocation/victim pressure가 깨웁니다.

sleep 중 관찰된 demand wake는 pgbuf_flush_victim_candidates()를 최소 한 번 호출하게 합니다. timer timeout은 direct-victim waiter가 있거나 충분한 victim request 뒤 sampled hit ratio가 99.9% 아래일 때만 호출합니다. pressure가 남으면 task 한 번에 여러 call을 반복할 수 있고, timed pass가 page를 하나도 submit하지 않을 수도 있습니다.

후보를 모은 뒤, 현재 상태와 WAL을 확인한다

  1. pressure를 읽고 LRU별 priority와 scan budget을 계산합니다.
  2. LRU mutex를 하나씩 잡고 cold LRU3 node를 따라가며 candidate BCB pointer와 VPID를 저장합니다.
  3. LRU lock을 놓고 sequentiality를 위해 candidate를 VPID로 sort할 수 있습니다.
  4. candidate마다 BCB를 lock하고 같은 VPID, DIRTY, 현재 FLUSHING 없음, 여전히 LRU3, fix 0을 다시 확인합니다.
  5. WAL boundary가 준비되지 않았으면 skip하고 log-flush를 깨웁니다. allocator pressure에서는 필요한 log boundary를 한 번 force하고 재시도할 수 있습니다.
  6. 하나의 stable generation을 copy하여 DWB 또는 direct I/O로 submit하고 필요하면 neighbor page도 포함합니다.
후보 탐색량 계산 예제

512 MiB/16 KiB 예에서 B=32,768입니다. 기본 1% unboosted selection budget은 327개 check이고, 최대 10× boost는 3,270개로 12,800-page 200 MiB cap보다 작습니다. 이것은 inspection budget이지 write 개수 보장이 아닙니다.

Queue에는 페이지 내용이 아니라 BCB 포인터를 넘긴다

이 시점에는 stable page generation이 설정된 DWB/direct-write submission boundary를 넘었지만, BCB에는 아직 이전 flush가 진행 중이라고 기록되어 있습니다. 이 state를 clear하고 flush waiter를 깨우며 clean frame을 기다리는 allocator에 직접 줄지 판단하는 일은 CPU-side bookkeeping입니다. handoff는 이 bookkeeping 담당자만 바꾸며 page write를 반복하지 않습니다.

  1. 이동하는 것: copy한 page image가 아니라 control record를 가리키는 PGBUF_BCB * 하나입니다.
  2. 받는 곳: bounded flushed_bcbs queue를 거쳐 post-flush daemon이 받습니다.
  3. 받은 쪽이 하는 일: 현재 BCB를 lock하고 다시 확인한 뒤 이전 FLUSHING state를 clear하고 flush waiter를 깨우며, 가능하면 clean frame을 allocator에 reserve합니다.
  4. 여기서 하지 않는 일: post-flush는 새 page I/O를 시작하지 않습니다.

page-flush가 submission을 만들었고, post-flush가 존재하며, allocator가 기다리고, 8,192-entry queue가 pointer를 받아야만 delegate합니다. 조건 하나라도 맞지 않으면 page-flush가 같은 BCB bookkeeping을 직접 수행합니다.

DWB가 켜져 있으면 successful submission은 stable image가 DWB에 들어갔다는 뜻일 수 있어 home-volume write보다 앞섭니다. 따라서 이 handoff는 page-buffer submission boundary를 나타낼 뿐, 보편적인 disk durability나 transaction durability를 뜻하지 않습니다.

Post-flush가 실행될 때는 상태가 달라졌을 수 있다

Post-flush는 queue가 빌 때까지 drain합니다. pointer마다 BCB를 lock하고 fix 0, LRU3 membership, clean/eligible flag, private list라면 quota를 다시 봅니다. submission 뒤 resident page가 fix되거나 다시 dirty해지거나 hot해졌을 수 있습니다.

현재도 eligible해야 live direct-victim waiter 하나에게 reserve할 수 있습니다. 결과와 무관하게 old FLUSHING generation을 끝내고 BCB flush waiter를 깨웁니다. work를 consume하면 다음 pause는 1 ms로 reset되고, 연속 idle timeout은 10 ms, 100 ms를 거쳐 wake-only infinite sleep으로 갑니다.

Clean 페이지를 unfix하면 누가 allocator를 깨우는가?

모든 frame이 fixed라서 탐색에 실패한 allocator가 잠든 뒤, reader들이 clean 페이지를 반납하는 상황을 구성해 보자. Unfix만으로 즉시 배정을 보장하지는 않는다. 일반 LRU3 페이지의 마지막 unfix는 보통 승격이나 private→shared 이동을 수행하므로, 반납한 페이지가 계속 cold 후보로 남는 것도 아니다.

Unfix가 직접 배정하는 경로도 있다. Vacuum worker 또는 임시 볼륨의 특정 LRU3 경로와 VOID의 vacuum 경로가 해당한다. LRU 재조정으로 다른 BCB가 LRU3으로 내려갈 때도 적격성 검사, BCB trylock과 재검사를 통과하면 배정할 수 있다. 모든 unfix마다 깨우는 규칙은 아니다.

Page-flush는 후보 탐색 중 이미 clean한 BCB를 발견해 배정할 수 있다. 반면 post-flush는 flushed_bcbs 큐를 소비하며, read unfix로 생긴 모든 clean BCB를 탐색하지 않는다. 수정하지 않은 WRITE fix도 기존 페이지가 이미 clean이었다는 조건이 있어야 같은 사례가 된다.

직접 배정은 대기 allocator를 깨우지만 취소될 수 있다. VPID가 같아도 재fix로 배정이 무효화될 수 있으므로 수령자는 BCB mutex를 잡고 재사용 조건을 다시 검사한다. Maintenance backup에는 기존 VS-20 소스 문제가 있어 반드시 구제한다고 설명할 수 없다. 이 순서는 구성 사례이며 실행 관찰이나 starvation 입증이 아니다.

탐색량과 I/O 대기 시간을 구분한다

후보를 찾는 작업량과 실제 경과 시간은 다릅니다. WAL, DWB, file I/O와 lock 대기가 완료 시간에 영향을 줍니다.

세부 동작과 소스 펼치기
역할Structural workWall-time 추가 요소
Page-flushO(T + L + K + C log C + C·N)LRU/BCB contention, WAL, DWB, file I/O, scheduling
Post-flushO(Q + S + F)queue CAS, BCB/thread mutex, allocator와 flush waiter wake

T는 thread-counter shard, L은 LRU, K는 inspected node, C는 candidate, N은 neighbor span, Q는 consumed BCB pointer, S는 stale allocator wait record, F는 flush waiter입니다.

Queue에 들어간 BCB가 다시 dirty가 된 경우

Page 제출 뒤 post-flush queue에 BCB가 들어갔지만, consumer 실행 전에 다른 thread가 다시 dirty로 만들었습니다. 이 frame을 allocator에 바로 넘길 수 있을까요?

설명 펼치기

아닙니다. Consumer는 BCB를 lock하고 현재 상태를 다시 검사합니다. 이전 FLUSHING generation을 끝내고 flush waiter를 깨우는 일과, 현재 clean하고 적격인 frame을 allocator에 예약하는 일은 별개입니다. Queue의 BCB pointer가 상태의 불변을 보장하지는 않습니다.
