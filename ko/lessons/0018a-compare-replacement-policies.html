같은 네 질문으로 세 구현 비교하기

각 엔진에 같은 질문을 던진다. 새로 읽은 page는 어디에 들어가는가? 어떤 재사용 정보를 기억하는가? 후보는 어떻게 찾는가? 실제 재사용을 허용하는 조건은 무엇인가? 재사용 정보가 없으면 앞으로 쓸 가능성을 추정할 근거를 잃는다. 적격성 보호가 없으면 추정이 좋아도 사용 중이거나 dirty인 page를 덮어쓸 수 있다. 다른 정책으로도 같은 안전 책임을 지킬 수 있다.

PostgreSQL은 shared descriptor를 최근 접근 순서로 연결하는 대신 clock hand와 제한된 재사용 credit을 쓴다. InnoDB는 pool instance별 resident LRU를 young/old 영역으로 나눈다. CUBRID는 private/shared domain과 세 zone을 쓰고 후보를 보호 아래 검사한다. 이 이름만으로 어느 엔진이 더 빠른지는 알 수 없다.

PostgreSQL: 확인하고, credit을 줄이고, 건너뛰고, 확보하기

구성 예제: 동시 변경과 strategy-ring 재사용이 없고 global hand가 A를 가리킨다. 큰 pool의 일부 구간을 보는 것이다. A는 unpinned이며 usage_count가 2다. 1로 줄이고 계속 간다. B는 pinned이며 usage_count가 0이다. 건너뛴다. C는 unpinned, clean이며 usage_count가 0이다. 원자적으로 pin하여 후보로 확보한다. Invalidation에서도 상태를 재검사한다. Dirty 후보라면 조건부 lock과 flush를 수행한 뒤 다시 검증해야 할 수 있다.

소스 위치 펼치기

고정 소스: bufmgr.c:1223–1251 · bufmgr.c:2268 · bufmgr.c:2548–2671 · freelist.c:239–317

Usage credit은 시각이나 누적 hit 횟수가 아니다. 기본 경로에서 backend의 첫 pin은 이를 최대 5까지 높일 수 있지만, 같은 backend의 중첩 pin이 shared credit을 계속 높이지는 않는다. Access-strategy ring은 다른 우선 경로를 쓰며, 별도 전용 pool이 아니라 shared-buffer ID를 담는다.

InnoDB: old tail을 살핀 뒤 free list 재시도하기

구성 예제: pool instance 하나에 512개보다 긴 list와 형성된 old 영역이 있다. Free list는 비어 있고 compressed-page 대안과 동시 변경은 없다. Tail부터 A는 buffer-fixed이므로 건너뛴다. B는 dirty이므로 clean eviction에서는 건너뛴다. C는 clean이고 이동 가능하므로 내보낸다. 할당 loop가 free list로 돌아가 block을 얻는다. 동시 실행이 있으면 다른 thread가 그 block을 먼저 가져갈 수 있다.

소스 위치 펼치기

고정 소스: buf0lru.cc:517–580 · buf0lru.cc:300–382 · buf0lru.cc:956 · buf0flu.cc:476–497

Old 영역이 있으면 disk-read page는 LRU_old 바로 뒤로 들어간다. 새로 생성한 page는 young에 들어가고, 짧은 list에서는 head insertion을 쓴다. Eviction이 시작된 뒤 기본 old-page 시간 조건에서는 첫 논리 접근으로부터 적어도 1,000 ms가 지난 후 조건에 맞는 접근이 있어야 한다. 시간 경과만으로 승격하지 않는다. Old와 young 모두 ghost가 아니라 resident page를 담는다. Midpoint admission과 지연 승격이 없다면 scan pollution을 다른 정책으로 제어해야 한다.

공통 hard rule은 단순하다. Fix 또는 pin 중인 frame은 ordinary victim이 아니다. Admission, hotness memory, candidate order, dirty handling은 implementation policy다.

CUBRID: 영역을 고르고 LRU3를 살핀다

Private/shared 리스트와 세 zone으로 후보 순위를 관리합니다. 일반적인 재사용은 clean 상태와 사용·대기 상태 등의 보호된 검사를 통과해야 합니다. AOUT는 이 리비전에서 꺼져 있습니다.

세부 동작과 소스 펼치기
  1. Admission: AOUT이 꺼진 pinned baseline에서 새로 load된 VOID BCB는 final-unfix execution context에 enabled private-LRU assignment가 있으면 private S+p의 LRU1 top으로 들어가고, 없으면 shared LRU2 middle로 들어간다.
  2. Reuse: LRU1은 그대로 둔다. LRU2 page는 list-tick age가 현재 LRU2 count 절반 이상일 때만 LRU1으로 돌아간다. Ordinary LRU3 reuse는 LRU1으로 돌아간다.
  3. Victim: allocator가 advertise된 LRU index를 consume하고 그 list를 lock한 뒤 LRU3 BCB를 최대 1,000개 검사한다. 모든 candidate는 clean/unfixed/waiter-free identity revalidation을 통과해야 한다.
  4. Scale: 여러 list와 mutex가 ordering을 shard한다. Private quota의 LRU1/LRU2 threshold는 각각 5%다. Shared default는 shared target의 40%와 5%다.
Scan resistance: private/shared locality와 zone admission이 한 access stream이 다른 stream과 경쟁하는 방식을 줄인다. Source에는 AOUT ghost history가 있지만 pinned build가 ratio를 0으로 강제하므로 active 2Q behavior로 설명하면 안 된다.

Pinned CUBRID: admission과 hit transition, bounded LRU3 scan, quota adjustment.

PostgreSQL: Clock이 재사용 credit을 줄인다

고정된 최근 접근 순위 대신 제한된 usage count를 씁니다. Clock은 pinned buffer를 건너뛰고, 양수 count는 줄이며, unpinned zero-count 후보를 확보합니다. Dirty 후보는 쓰기와 재검증이 더 필요할 수 있습니다.

세부 동작과 소스 펼치기
  1. Admission: 새로 claim한 shared descriptor는 usage_count = 1을 받는다.
  2. Reuse: backend의 첫 pin이 shared usage_count를 최대 5까지 증가시킨다. 같은 backend의 nested pin은 private refcount만 바꾸므로 두 번째 shared credit을 얻지 않는다.
  3. Victim: atomic clock hand가 buffer descriptor를 진행한다. Pinned buffer는 건너뛰고 unpinned positive count는 줄이며 unpinned zero를 claim한다. 따라서 count 5는 최대 여섯 번의 full visit까지 살아남을 수 있다.
  4. Bulk scan: backend-local strategy ring이 bulk read/write와 vacuum을 위해 작은 ID 집합을 reuse한다. 그래도 shared pool의 frame을 가리키며 private buffer pool은 아니다.
LRU order가 아니다: usage_count = 2인 descriptor 둘 사이에는 “더 오래된 것을 먼저”라는 관계가 없다. Count는 clock visit이 줄이는 bounded reuse credit이지 timestamp나 linked-list rank가 아니다.

Pinned PostgreSQL: clock selection, maximum usage count 5, strategy-ring size.

InnoDB: old 영역에서 시작해 재사용을 확인한다

Old 영역이 형성된 리스트에서는 disk-read page를 old 경계에 넣습니다. 시간 조건을 만족한 재접근은 young 승격으로 이어질 수 있습니다. 새로 만든 page나 짧은 리스트에는 다른 배치 규칙이 있습니다. 시간만 지났다고 자동 승격하지는 않습니다.

세부 동작과 소스 펼치기
  1. Topology: buffer-pool instance마다 LRU, free list, flush list를 소유한다. LRU가 512 entry 이상이 되면 LRU_old가 하나의 physical list를 young/old region으로 나눈다.
  2. Admission: old region이 형성된 뒤에는 disk-read page가 그 경계 바로 뒤에 들어간다. 짧은 리스트에서는 LRU head에 들어간다. Old target default는 37%다. Memory에서 직접 만든 page는 young head에 들어간다.
  3. Reuse: old page는 보통 first access에서 innodb_old_blocks_time 이상 지난 뒤 다시 access되어야 young head로 promote된다. Default delay는 1,000ms다.
  4. Victim: allocation은 free block을 얻거나 old tail부터 clean relocatable page를 scan한다. 첫 common foreground scan은 100 entry로 제한되며 이후 pressure iteration은 LRU 전체를 scan할 수 있다.
Scan resistance: one-pass scan은 old region을 채우지만 빠른 first touch만으로 모든 page가 young으로 promote되지는 않는다. Old/new는 resident region이며 evicted identity를 기억하는 2Q ghost list가 아니다.

Pinned MySQL/InnoDB: midpoint insertion, disk-read 호출 경로, 37%와 1,000ms default, free-block pressure loop.

비슷한 이름이 같은 동작을 뜻하지는 않는다

세 엔진 모두 사용 중인 frame을 보호하지만 후보를 기억하고 찾는 방식은 다릅니다. 어느 쪽이 빠른지는 workload와 설정을 맞춘 측정이 필요합니다.

세부 동작과 소스 펼치기
유혹적인 shortcut수정된 설명
“CUBRID LRU3는 InnoDB old와 같다.”둘 다 cold region이지만 admission, domain 수, promotion gate, candidate scan이 다르다.
“PostgreSQL clock은 approximate LRU다.”usage_count는 bounded credit이며 같은 count끼리 recency order가 없다.
“PostgreSQL strategy ring은 CUBRID private LRU다.”Ring은 shared-buffer ID의 backend-local array이고 CUBRID private LRU는 pool-global linked residency/quota domain이다.
“InnoDB old/new는 2Q다.”두 region 모두 resident page를 담으며 이 path에는 general evicted-identity ghost queue가 없다.
Source shape만으로 winner를 고를 수 없다. Hit ratio와 latency는 effective pool byte, page/row layout, workload, dirtying, cleaning, checkpoint behavior, contention에도 달려 있다. 이 lecture은 measurement hypothesis를 제공하지 benchmark result를 제공하지 않는다.

이름 대신 후보 선택을 비교하기

최근 사용한 페이지라도 바로 교체 후보가 될까요? 세 엔진에서 사용 흔적과 재사용 안전 조건을 나누어 생각해 봅니다.

설명 펼치기

CUBRID는 domain과 zone, PostgreSQL은 usage credit, InnoDB는 young/old 배치로 사용 흔적을 반영합니다. 후보 순위와 실제 frame 재사용은 별개이며, 사용 중인 frame 보호와 dirty 처리도 필요합니다. 이 정책 이름만으로 성능 우위를 결론낼 수 없습니다.
