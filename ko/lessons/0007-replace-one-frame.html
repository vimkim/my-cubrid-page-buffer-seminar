00 · BCB identity 해석하기

주소가 같은 slot도 시간에 따라 다른 page를 나타낼 수 있다

BCB는 하나의 frame과 짝을 이루도록 미리 할당된 buffer-pool descriptor다. 메모리 주소는 고정되어 있지만 현재 identity는 bcb->vpid가 가리키는 resident page다. 안전한 victimization은 이 mapping을 끝내며, 이후 같은 BCB/frame slot을 다른 VPID에 연결할 수 있게 한다.

시점동일한 BCB 주소현재 identity상태
T1BCB[42]VPID A정확히 하나의 LRU list/zone에 resident 상태다.
T2BCB[42]resident VPID 없음안전하게 detach되어 재사용 가능한 invalid 상태다.
T3BCB[42]VPID B다시 bind된 뒤 하나의 LRU list/zone에 들어간다.

latch가 호환된다면 여러 thread가 현재의 같은 BCB를 fix할 수 있다. 여러 READ holder가 대표적인 예다. 이는 하나의 page identity를 공유하는 ownership이며, global fcnt와 thread별 holder에 기록된다. BCB identity가 여러 개인 것은 아니다.

하나의 BCB가 동시에 여러 LRU에 속하지는 않는다. Private LRU와 shared LRU는 서로 대안이 되는 list domain이고, LRU1/LRU2/LRU3은 현재 속한 하나의 LRU 내부 zone이다. 시간에 따라 list를 옮기거나 detach될 수는 있지만, 단일 link field로 여러 list의 일반 member가 될 수는 없다.

identity mismatch의 의미: slot이 A를 나타낼 때 보호 없이 candidate를 관찰해 두었는데, 나중에 같은 BCB 주소를 보니 B로 rebind된 경우다. A를 바탕으로 내린 stale 결정을 버리고 retry해야 한다. 일반 LRU 경로에서는 LRU mutex를 잡은 뒤 BCB protection을 획득하여 마지막 detach 중 이런 변화를 막는다. helper는 단순히 saved_vpid == bcb->vpid를 명시적으로 비교하는 함수가 아니다.

02 · Hard eligibility

관찰에서 재사용까지 다섯 가지를 증명해야 한다

  1. Identity가 안정적이다: BCB가 selection에서 확인한 VPID와 list candidate를 여전히 나타낸다.
  2. Ownership이 남아 있지 않다: global fcnt, thread별 holder, 이미 grant된 권리, 일시적 claim 어디에도 남은 fixer를 허용할 상태가 없다.
  3. Generation debt가 남아 있지 않다: DIRTY라면 아직 전파하지 않은 byte를 버리게 되고, FLUSHING이라면 copy된 generation이 이 identity를 가리키는 동안 rebind하게 된다.
  4. 충돌하는 waiter가 없다: latch waiter나 진행 중인 protocol state에는 단순한 counter read로 보이지 않는 권리가 들어 있을 수 있다.
  5. 마지막 protected revalidation이 성공한다: unlink 또는 재사용 직전에 BCB를 lock하고 identity, flag, ownership, zone, handoff 조건을 다시 확인한다.

Verified mechanism: pinned revision의 일반 LRU selection은 victim zone을 scan하고, avoid-victim flag가 있거나 fixed 상태인 frame을 제외한다. 이어 BCB를 conditional lock하고 pgbuf_is_bcb_victimizable(..., true)를 호출한 다음에야 list에서 제거한다. page_buffer.c:9293–9538을 읽어 보자.

04 · 변경 가능한 구조

eligible frame만 replacement policy로 들어간다

LRU zone과 placement, private/shared domain, quota, candidate queue나 hint, direct assignment는 locality, fairness, CPU cost, progress에 영향을 준다. 그러나 재사용이 안전한지를 새로 정의하지는 않는다.

direct-victim assignment는 revoke할 수 있다. allocator가 소비하기 전에 candidate가 다시 fixed되면 다른 candidate를 요청한다. Policy는 새로 생긴 ownership에 양보하며 재사용을 강제하지 않는다.

Implementation policy: 구체적인 zone, quota, queue priority, search order, timeout 전략은 이 revision의 선택이다. hard interface 조건은 그대로다. 성공한 fixer나 완료되지 않은 generation이 rebind 이후까지 남아서는 안 된다.

05 · lifecycle 동작 구분하기

Release, propagate, rebind, invalidate, deallocate는 서로 다른 동작이다

동작바뀌는 것대개 남는 것
Unfixcaller 한 명의 fix debt를 소비한다.resident VPID ↔ BCB/frame mapping.
Flushcopy된 dirty generation 하나를 전파한다.residency, 그리고 더 새로운 DIRTY generation이 있을 수 있다.
Victimization안전한 resident frame을 재사용하려고 detach한다.logical page는 storage에 계속 존재한다.
Invalidationcoherence/lifecycle 이유로 resident mapping을 제거하거나 거부한다.별도로 바꾸지 않았다면 logical allocation은 남는다.
Logical deallocationfile/disk ownership 관점에서 page가 더 이상 할당된 storage로 존재하지 않는다.cache된 모든 reference가 이미 사라졌다는 보장은 없다.

vacuum의 avoid-deallocation bookkeeping 자체는 일반적인 victim blocker가 아니다. 이름이 비슷한 lifecycle 구조가 LRU eligibility에도 참여한다고 추론하면 안 된다.

06 · Evidence 경계

기존 runtime 실행에서는 frame eviction이 일어나지 않았다

Source는 pinned selection mechanism을 입증한다. 기록된 workload는 eviction을 유발하지 않았고 physical victim도 식별하지 못했다.

따라서 victim order, physical-frame reuse, direct-victim revocation, pressure-path fairness를 검증할 수 없다. 이런 주장을 하려면 frame identity와 state를 관찰하는 범위가 명확한 pressure experiment가 필요하다. 끝내 가득 차지 않은 pool에서 workload가 성공했다는 사실만으로는 부족하다.
