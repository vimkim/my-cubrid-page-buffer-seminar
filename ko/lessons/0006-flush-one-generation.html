여기서 시작 · operation과 목적

Flush는 volatile buffer memory 밖으로 page image 하나를 propagate합니다

Flushing은 resident page의 안정적인 image를 capture하여, 필요한 WAL gate를 거쳐 persistent page storage 쪽으로 보내는 page-buffer operation입니다.

Database는 먼저 in-memory frame을 변경합니다. 이 resident image는 빠르게 접근할 수 있지만 volatile합니다. 이것만으로는 data volume에 있는 page의 home location이 갱신되지 않습니다. BCB에 DIRTY를 표시하는 것은 아직 끝나지 않은 propagation work를 기록하는 일이며, 이후 flush가 이 debt를 처리합니다.

질문답
무엇을 복사하나요?현재 resident page bytes를 안정적인 private image로 capture합니다. 그래서 이후 writer가 이미 submit 중인 bytes를 바꾸지 못합니다.
왜 flush하나요?Page change를 volatile buffer memory 바깥으로 propagate하고, checkpoint와 shutdown의 진행을 지원하며, clean하고 unfixed인 frame이 나중에 replacement 후보가 될 수 있게 합니다.
FLUSHING은 무엇인가요?앞서 capture한 image 하나가 현재 flush path에 있다는 in-progress state입니다. Command가 아니며 현재 resident bytes가 clean하다는 증거도 아닙니다.
무엇이 아닌가요?Flush는 transaction commit, unfix, eviction, page deallocation이 아닙니다. 이들은 서로 다른 lifecycle event입니다.

WAL rule은 ordering 질문에 답합니다. Logged non-temporary page라면 copied image를 포함하는 recovery log가 필요한 boundary에 먼저 도달한 뒤 page image를 submit해야 합니다. DWB가 enabled라면 incomplete/torn page write라는 별도의 integrity 질문에 답합니다. 어느 개념도 flush 자체의 정의는 아닙니다.

구체적인 결과: image capture 뒤 resident page를 바꾼 writer가 없고 submission이 성공하면, BCB는 DIRTY와 FLUSHING이 모두 꺼진 상태로 끝날 수 있습니다. Page는 여전히 resident이며, 이후 replacement 판단이 그 frame을 재사용할 수 있습니다.
00 · 표기법 이해하기

G는 복사된 page image에 붙인 이름이며 stored counter가 아닙니다

generation은 flush가 하나의 단위로 다루는 일관된 page bytes version에 붙인 reasoning label입니다.

flush가 시작되면 resident page를 복사합니다. 이 고정된 copy를 G라고 부르겠습니다. G를 쓰는 동안 writer가 아직 resident인 page를 다시 변경할 수 있습니다. 이렇게 더 새로워진 resident bytes를 G+1이라고 부릅니다. source에는 generation, G, G+1이라는 field가 없습니다. 같은 logical page의 두 version을 머릿속에서 분리하려고 쓰는 label입니다.

대상무엇인가예
Generation G현재 flush 중인 page-image copy의 conceptual identity.복사된 bytes에는 LSA 140까지의 logged change가 들어 있습니다.
Generation G+1G를 복사한 뒤 변경된 resident bytes의 conceptual identity.writer가 LSA 170에서 더 나중 change를 적용합니다.
Page LSApage state에 실제로 저장되는 log address로, 해당 bytes에 포함된 가장 최근 logged change를 나타냅니다.G는 140, G+1은 170을 가집니다.

generation과 LSA가 다른 이유: 여러 logged modification이 page LSA를 100에서 140으로 옮겨도 아직 복사되지 않은 같은 resident generation에 속할 수 있습니다. 반대로 새 log address로 표현되지 않는 change라도 copy 이후의 새 generation을 만들 수 있습니다. Generation은 page-image version을 구분하고, LSA는 recovery history의 위치를 가리킵니다.

DIRTY와 FLUSHING은 서로 독립적인 yes/no 질문입니다

DIRTYFLUSHING의미
00propagation을 기다리는 resident change도, in flight 상태인 copied image도 없습니다.
10resident page에 propagation debt가 있어 이후 flush가 필요합니다.
01copy G가 in flight이고, copy 뒤 resident page는 바뀌지 않았습니다.
11copy G가 in flight인 상태와 resident page의 재변경이 동시에 존재합니다. G+1도 나중에 flush해야 합니다.

DIRTY는 to-do flag입니다. 현재 resident bytes에 완료된 propagation으로 아직 처리하지 못한 change가 있다는 뜻입니다. FLUSHING은 in-progress flag입니다. 앞서 capture한 copy가 아직 flush path를 지나고 있다는 뜻입니다. FLUSHING이 resident page를 고정시키는 것은 아닙니다.

FLUSHING을 설정할 때 DIRTY를 지우는 이유는? G의 기존 debt는 in-flight operation으로 옮겨 갔습니다. DIRTY를 지우면 깨끗한 signal slot이 생깁니다. writer가 resident page를 바꾸면 DIRTY를 다시 설정합니다. 그러면 DIRTY + FLUSHING은 “이전 copy는 in flight이고, 더 새로운 resident work가 대기 중”이라는 뜻이 됩니다.
00A · 두 번째 flag가 필요한 이유

DIRTY는 pending resident work를, FLUSHING은 captured work를 조정합니다

“copy G가 in flight”와 “resident G+1을 다시 flush해야 함”은 동시에 참일 수 있습니다. Bit 하나로는 두 사실을 정확히 나타낼 수 없습니다.

FLUSHING이 필요한 이유DIRTY만 있을 때 생기는 문제
Concurrent re-dirty 보존Completion이 DIRTY를 단순히 지우면 writer가 더 새롭게 publish한 dirty state를 지울 수 있습니다. Flag가 둘이면 G completion은 FLUSHING만 지우고 G+1 DIRTY를 남깁니다.
Overlapping flush 배제두 번째 flusher가 새로 DIRTY가 된 G+1을 보고, 더 오래된 G가 in flight인 동안 submit할 수 있습니다. Storage completion 순서가 바뀌면 old G가 newer G+1을 덮어쓸 수 있습니다.
Synchronous caller 조정반드시 기다려야 하는 caller가 “propagation이 없음”과 “다른 thread가 이미 propagation을 소유함”을 구분할 수 없습니다. FLUSHING을 보면 새 flush를 시작하지 않고 BCB wait queue에서 기다립니다.
Success 또는 failure의 명시적 종료Completion 때 지울 state와 깨울 waiter가 필요합니다. Failure는 FLUSHING을 지우고 captured dirty debt/lower bound를 복구하여 retry 가능하게 만듭니다.

다음 thought experiment를 사용하세요. DIRTY=1, FLUSHING=0에서 시작합니다. Flusher F가 G를 capture하고 DIRTY=0, FLUSHING=1을 publish합니다. 이제 old debt는 F가 소유합니다. Writer W가 resident bytes를 변경하여 DIRTY=1, FLUSHING=1을 publish합니다. G는 여전히 F가 소유하고 G+1은 새 work입니다. 성공하면 F는 FLUSHING만 0으로 바꿉니다. 남은 DIRTY는 여전히 G+1을 flush해야 한다는 뜻입니다.

FLUSHING은 writer를 freeze하지 않습니다. Unsafe competing flush ownership을 막고 wait/completion을 보이게 하면서, DIRTY는 이후 resident generation을 기록할 수 있게 비워 둡니다.

Verified mechanism: safe flush가 concurrent flush를 거절하고 필요한 경우 synchronous waiter를 queue하는 동작은 pinned page_buffer.c:8809–8901에 있습니다. Source는 8839–8847에서 out-of-order old-over-new write를 명시합니다. Flag transition은 16077–16137, completion/failure wakeup은 10908–10951에 있습니다.

00B · copy와 destination 구분

Resident page를 복사한다는 말은 “DWB에 쓴다”는 뜻이 아닙니다

Flush는 먼저 private memory에 안정적인 page image를 만듭니다. DWB는 그 copied image가 갈 수 있는 destination 하나이지 copy operation 자체가 아닙니다.

pgbuf_bcb_flush_with_wal()의 page_buf는 local aligned buffer입니다. TDE가 필요하면 resident page를 이 buffer로 encrypt하고, 아니면 memcpy로 복사합니다. 이렇게 하면 BCB protection을 놓은 뒤 resident bytes가 G+1으로 바뀌어도 in-flight bytes G는 분리되어 있습니다.

Configuration 판단공통으로 일어나는 일WAL gate 뒤 copied G가 가는 곳
DWB가 created 상태이고 non-temporary pageStable image copy, LSA capture, 필요한 WAL force.dwb_add_page()가 image를 DWB slot에 받아들이고, 이후 DWB가 보호된 home-volume propagation을 조정합니다.
DWB가 disabled/not created이거나 temporary pageStable-image 분리는 그대로 일어납니다. Logged non-temporary page는 여전히 WAL gate를 지킵니다.Page-buffer path가 page의 home data-volume location에 fileio_write()를 직접 호출합니다.
DWB가 disabled라면: flush가 멈추는 것도 아니고 이 DWB mechanism에 의해 page를 두 번 쓰는 것도 아닙니다. 대신 direct-write branch를 탑니다. 없어지는 것은 DWB의 torn/incomplete page-image protection과 startup repair source입니다. WAL은 별개의 ordering과 recovery 역할을 계속 가집니다.

Pinned code는 BCB protection을 놓기 전에 uses_dwb = dwb_is_created() && !is_temp로 판단합니다. DWB에 page를 추가하는 동안 DWB가 사라지면 BCB protection을 다시 얻고 resident page를 다시 복사한 뒤 DWB 없이 retry하는 test-oriented runtime transition도 있습니다. Source comment는 live activation/deactivation에 추가 작업이 필요하다고 명시하므로 runtime toggling을 지원되는 monitoring 또는 administration protocol처럼 설명하면 안 됩니다.

Verified mechanism: local copy와 branch selection은 pinned page_buffer.c:10735–10834, WAL gating과 DWB/direct submission은 10836–10899에 있습니다. DWB recovery behavior는 별도의 startup mechanism입니다.

02A · Lower bound가 존재하는 이유

Checkpoint는 dirty generation이 어디서 시작했는지 기억해야 합니다

DIRTY는 propagation debt가 있다는 사실만 말합니다. page LSA는 resident image가 얼마나 최신인지 말합니다. oldest_unflush_lsa만 현재 갚지 않은 generation이 과거의 어디까지 걸쳐 있는지 보존합니다.

Checkpoint는 log boundary를 하나 정하고, 아직 propagate하지 않은 history가 그 boundary에 닿는 eligible dirty page를 page buffer에 flush하라고 요청합니다. 또한 남은 dirty page 중 가장 작은 lower bound가 필요합니다. Recovery가 그 지점부터 다시 redo해야 할 수 있기 때문입니다. 이는 “이 dirty generation에 boundary 이전 또는 같은 시점의 work가 있는가?”라는 range 질문이지 latest-value 질문이 아닙니다.

Checkpoint가 P를 scan할 때 P는 unfixed이고 그 밖의 flush 조건도 만족한다고 가정합니다. Boundary는 generation의 시작점으로 대상을 고르고, 복사한 page LSA는 여전히 WAL force target을 제공합니다.

이 field가 꼭 필요한 반례

  1. Disk의 P는 LSA 80까지 반영되어 있습니다. 100의 Log A가 P를 처음 dirty로 만듭니다. Latest와 oldest는 모두 100입니다.
  2. 140의 Log B가 같은 unflushed generation을 변경합니다. Latest는 140으로 움직이지만 oldest는 100에 남습니다.
  3. Checkpoint가 flush_upto_lsa = 150을 정합니다.
  4. Scan 전에 170의 Log C가 P를 다시 변경합니다. Latest는 170으로 움직이지만 A/B/C 중 어느 것도 propagate되지 않았으므로 oldest는 100에 남습니다.
Candidate test결과이유
page LSA 170 > 150이를 checkpoint predicate로 잘못 사용하면 P를 skip합니다.“이 bytes의 가장 최신 logged change는 무엇인가?”에만 답하므로 100의 unpaid A를 숨깁니다.
oldest 100 ≤ 150P를 선택합니다.아직 propagate하지 않은 generation이 checkpoint boundary 이전에 시작했습니다.

선택한 뒤 flush가 과거의 100-version을 쓰는 것은 아닙니다. A+B+C를 포함한 현재 generation을 복사하고 checkpoint accounting을 위해 oldest 100을 운반하며, image를 submit하기 전에 복사한 page LSA 170까지 WAL을 force합니다. 두 coordinate는 경쟁하지 않고 협력합니다.

03 · Ordinary success path

BCB만 보지 말고 generation을 따라갑니다

  1. Validate identity: 보호된 BCB가 여전히 의도한 page를 가리키는지 확인합니다.
  2. Open an in-flight generation: FLUSHING을 설정하고 이전 DIRTY bit를 지워 이후 mutation이 새 DIRTY generation을 publish할 수 있게 합니다.
  3. Capture stable bytes: resident image를 복사합니다. TDE를 위해 copy를 transform하고, 설정되어 있다면 DWB slot을 reserve/copy합니다.
  4. Capture recovery coordinates: page LSA와 oldest-unflush LSA를 복사하고 resident lower bound를 지웁니다.
  5. Release BCB protection: I/O 동안 resident state lock을 계속 잡고 있을 필요는 없습니다.
  6. Gate by WAL: logged non-temporary image라면 복사된 page LSA까지 WAL을 force합니다.
  7. Submit the copied image: 설정된 DWB 또는 direct data-volume write path를 사용합니다.
  8. Complete under protection: FLUSHING을 지우고 waiter를 깨우거나, pressure 상황에서 필요한 post-flush handoff를 수행합니다.

Verified mechanism: ordinary path는 pinned page_buffer.c:10723–10962에 있습니다. 설정된 endpoint를 정확히 표현해야 합니다. DWB acceptance와 이후 home-page persistence는 같은 observation이 아닙니다.

05 · Ordinary failure

Rollback은 retry할 수 있는 generation state를 복구합니다

일반 post-release path에서 DWB addition이나 direct I/O가 실패하면 code는 BCB protection을 다시 얻고 FLUSHING을 지웁니다. capture한 generation이 dirty였다면 DIRTY를 복구하고, 복사해 둔 oldest-unflush LSA도 복구한 뒤 waiter를 깨우고 failure를 반환합니다.

Review invariant: ordinary failure 뒤에도 capture된 propagation debt를 발견해 retry할 수 있어야 하며, stale FLUSHING state 뒤에 waiter가 갇혀서는 안 됩니다.

동시에 G+1이 있다면 복구된 state를 단순화하기 전에 두 generation과 실제 interleaving을 모두 설명하세요. scalar flag 하나의 이름 때문에 두 logical debt를 지워 버리면 안 됩니다.

Verified mechanism: ordinary unwind는 pinned page_buffer.c:10908–10923에 있습니다.
