00 · 표기법 이해하기

G는 복사된 page image에 붙인 이름이며 stored counter가 아닙니다

generation은 flush가 하나의 단위로 다루는 일관된 page bytes version에 붙인 reasoning label입니다.

flush가 시작되면 resident page를 복사합니다. 이 고정된 copy를 G라고 부르겠습니다. G를 쓰는 동안 writer가 아직 resident인 page를 다시 변경할 수 있습니다. 이렇게 더 새로워진 resident bytes를 G+1이라고 부릅니다. source에는 generation, G, G+1이라는 field가 없습니다. 같은 logical page의 두 version을 머릿속에서 분리하려고 쓰는 label입니다.

대상무엇인가예
Generation G현재 flush 중인 page-image copy의 conceptual identity.복사된 bytes에는 LSA 140까지의 logged change가 들어 있습니다.
Generation G+1G를 복사한 뒤 변경된 resident bytes의 conceptual identity.writer가 LSA 170에서 더 나중 change를 적용합니다.
Page LSApage state에 실제로 저장되는 log address로, 해당 bytes에 포함된 가장 최근 logged change를 나타냅니다.G는 140, G+1은 170을 가집니다.

generation과 LSA가 다른 이유: 여러 logged modification이 page LSA를 100에서 140으로 옮겨도 아직 복사되지 않은 같은 resident generation에 속할 수 있습니다. 반대로 새 log address로 표현되지 않는 change라도 copy 이후의 새 generation을 만들 수 있습니다. Generation은 page-image version을 구분하고, LSA는 recovery history의 위치를 가리킵니다.

DIRTY와 FLUSHING은 서로 독립적인 yes/no 질문입니다

DIRTYFLUSHING의미
00propagation을 기다리는 resident change도, in flight 상태인 copied image도 없습니다.
10resident page에 propagation debt가 있어 이후 flush가 필요합니다.
01copy G가 in flight이고, copy 뒤 resident page는 바뀌지 않았습니다.
11copy G가 in flight인 상태와 resident page의 재변경이 동시에 존재합니다. G+1도 나중에 flush해야 합니다.

DIRTY는 to-do flag입니다. 현재 resident bytes에 완료된 propagation으로 아직 처리하지 못한 change가 있다는 뜻입니다. FLUSHING은 in-progress flag입니다. 앞서 capture한 copy가 아직 flush path를 지나고 있다는 뜻입니다. FLUSHING이 resident page를 고정시키는 것은 아닙니다.

FLUSHING을 설정할 때 DIRTY를 지우는 이유는? G의 기존 debt는 in-flight operation으로 옮겨 갔습니다. DIRTY를 지우면 깨끗한 signal slot이 생깁니다. writer가 resident page를 바꾸면 DIRTY를 다시 설정합니다. 그러면 DIRTY + FLUSHING은 “이전 copy는 in flight이고, 더 새로운 resident work가 대기 중”이라는 뜻이 됩니다.
01 · boundary에 이름 붙이기

“썼다”라는 말 뒤에는 서로 다른 네 moment가 숨어 있습니다

더 강한 evidence 없이 claim을 이 chain의 오른쪽으로 옮기지 마세요.

flush가 완료하는 것은 복사된 generation이지, “영원히 변하지 않는 page”가 아닙니다.

02 · 두 LSA 질문

포함된 최신 change와 propagate하지 않은 가장 오래된 change는 서로 다른 coordinate입니다

복사된 generation G는 140/100을, 이후 resident generation G+1은 170/170을 가집니다.

03 · Ordinary success path

BCB만 보지 말고 generation을 따라갑니다

  1. Validate identity: 보호된 BCB가 여전히 의도한 page를 가리키는지 확인합니다.
  2. Open an in-flight generation: FLUSHING을 설정하고 이전 DIRTY bit를 지워 이후 mutation이 새 DIRTY generation을 publish할 수 있게 합니다.
  3. Capture stable bytes: resident image를 복사합니다. TDE를 위해 copy를 transform하고, 설정되어 있다면 DWB slot을 reserve/copy합니다.
  4. Capture recovery coordinates: page LSA와 oldest-unflush LSA를 복사하고 resident lower bound를 지웁니다.
  5. Release BCB protection: I/O 동안 resident state lock을 계속 잡고 있을 필요는 없습니다.
  6. Gate by WAL: logged non-temporary image라면 복사된 page LSA까지 WAL을 force합니다.
  7. Submit the copied image: 설정된 DWB 또는 direct data-volume write path를 사용합니다.
  8. Complete under protection: FLUSHING을 지우고 waiter를 깨우거나, pressure 상황에서 필요한 post-flush handoff를 수행합니다.

Verified mechanism: ordinary path는 pinned page_buffer.c:10723–10962에 있습니다. 설정된 endpoint를 정확히 표현해야 합니다. DWB acceptance와 이후 home-page persistence는 같은 observation이 아닙니다.

Verified mechanism: pinned page_buffer.c:16077–16126의 flag helper를 비교하세요.

05 · Ordinary failure

Rollback은 retry할 수 있는 generation state를 복구합니다

일반 post-release path에서 DWB addition이나 direct I/O가 실패하면 code는 BCB protection을 다시 얻고 FLUSHING을 지웁니다. capture한 generation이 dirty였다면 DIRTY를 복구하고, 복사해 둔 oldest-unflush LSA도 복구한 뒤 waiter를 깨우고 failure를 반환합니다.

Review invariant: ordinary failure 뒤에도 capture된 propagation debt를 발견해 retry할 수 있어야 하며, stale FLUSHING state 뒤에 waiter가 갇혀서는 안 됩니다.

동시에 G+1이 있다면 복구된 state를 단순화하기 전에 두 generation과 실제 interleaving을 모두 설명하세요. scalar flag 하나의 이름 때문에 두 logical debt를 지워 버리면 안 됩니다.

Verified mechanism: ordinary unwind는 pinned page_buffer.c:10908–10923에 있습니다.

06 · Evidence boundary

source와 experiment가 무엇을 입증하는지 정확히 말합니다

Label안전한 claim위험한 확대 해석
Verified mechanismpinned ordinary source path는 설명한 순서대로 snapshot, WAL gate, submission, completion, rollback을 수행합니다.모든 early failure가 ordinary rollback을 따른다고 단정하는 것.
Runtime observation기록된 experiment에서 예상한 mutation/commit state와 accepted synchronous backup boundary를 관찰했습니다.per-page WAL-before-data, DWB completion, crash recovery 또는 page-write count까지 증명했다고 보는 것.
Open finding · VS-12source inspection은 ordinary rollback 이전의 TDE/DWB preparation return에 우려를 제기합니다.실행 가능한 fault injection 없이 이 우려를 현재 production defect라고 부르는 것.

TDE는 복사된 image를 바꾸며 resident plaintext의 ownership을 바꾸지 않습니다. DWB는 page-image integrity를 보호하지만 WAL이나 recovery를 대체하지 않습니다. “page-buffer flush path가 설정된 DWB/direct-write boundary에서 완료되었다”라고 표현하세요.

07 · Retrieval practice

“page가 clean이 되었다”라고 말하지 않고 G와 G+1을 추적합니다

문제

clean page가 LSA 80에서 시작합니다. 100과 140의 log가 page를 dirty로 만듭니다. Flush generation G가 시작되고, G가 in flight인 동안 writer가 170에서 log를 남깁니다. 다음 시점의 page LSA, oldest-unflush LSA, DIRTY, FLUSHING을 예측하세요.

  1. G가 시작되기 직전,
  2. G가 image를 capture한 뒤,
  3. 170 mutation 뒤,
  4. G가 성공한 뒤,
  5. ordinary failure라면 대신 무엇을 보존해야 하는지.

할 일: 어느 state가 G에 속하고 어느 state가 G+1에 속하는지 구분하고, 각 claim에 source, runtime observation, inference 또는 open finding label을 붙이세요.

답을 chat에 붙여 넣으세요. mastery를 기록하기 전에 generation identity, flag algebra, LSA 목적, persistence 표현, evidence strength를 확인합니다.
