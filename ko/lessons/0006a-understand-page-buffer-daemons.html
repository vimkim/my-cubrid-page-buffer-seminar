왜 일부 일을 background thread가 맡는가?

여기서 daemon은 작업을 반복하고 기다리는, 관리되는 background thread다. 공통 유지보수나 cleaning을 개별 요청과 독립적으로 진행하게 한다. 별도의 DB 서버 process라는 뜻은 아니며, 네 page-buffer daemon이 모두 page를 쓰는 것도 아니다.

Background 실행이 없다면 필요한 일을 foreground 호출자나 다른 scheduler가 맡아야 한다. 요청 지연이 늘거나 미리 준비된 clean frame이 줄 수 있지만, 이것만으로 손상을 단정할 수는 없다. Queue나 대기 절차가 그대로 의존하는데 thread만 없애는 변경은 별개의 위험한 변경이다. Stand-alone mode는 동기 대안이 존재한다는 근거이지 실행 중인 서버 daemon을 끄는 방법이 아니다.

네 역할을 구분한다. Page-flush는 dirty page image를 제출한다. Post-flush는 queue에 넘긴 BCB 처리를 마친다. Maintenance는 quota와 zone을 조정한다. Flush-control은 soft I/O pacing credit을 갱신한다. 다음 강의에서 각 역할의 호출 경로와 없을 때의 영향을 확인한다.

각 daemon은 독립적으로 일하고 기다린다

네 daemon은 서로 다른 역할을 가진 background thread입니다. Timer나 wakeup은 실행 기회이고, 실제 작업 여부는 현재 상태를 확인한 뒤 결정합니다.

세부 동작과 소스 펼치기

create_daemon()은 managed execution context 하나와 std::thread 하나를 만듭니다. loop는 간단합니다. task를 실행하고, cubthread::looper에게 pause 시간을 물은 뒤, 다시 task를 실행합니다. 따라서 네 이름은 하나의 dirty-page queue에서 같은 일을 꺼내는 worker가 아니라 서로 독립적인 control loop입니다.

task는 생성 직후 한 번 실행됩니다. fixed period는 start-to-start 목표입니다. looper가 직전 task 실행 시간을 빼므로 100 ms 주기가 “작업을 끝낸 뒤 항상 100 ms를 더 sleep한다”는 뜻도, 매번 유용한 작업을 한다는 보장도 아닙니다.

복구가 끝난 뒤 작업하고, pool보다 먼저 종료한다

서버는 복구 중에 thread를 만들지만 boot gate가 열리기 전에는 page-buffer 작업을 하지 않습니다. 정상 종료에서는 pool을 정리하기 전에 daemon을 멈춥니다. Stand-alone mode에서는 이 네 thread를 만들지 않습니다.

세부 동작과 소스 펼치기
  1. 먼저 page-buffer pool, LRU, queue, monitor를 초기화합니다.
  2. server boot는 log recovery가 끝나기 전에 네 daemon thread를 만듭니다.
  3. 생성 직후 task는 boot gate가 닫힌 것을 보고 page-buffer의 유용한 작업 없이 반환합니다.
  4. recovery 뒤 boot가 gate를 엽니다. gate를 여는 동작 자체가 모든 sleeper를 wake하지는 않습니다. 이후 timer 또는 normal work wake에서 열린 gate를 관찰합니다.
  5. 정상 shutdown은 looper stop flag를 set하고 sleeper를 깨운 뒤 OS thread를 join하고 task/context를 retire하며 pointer를 비웁니다.
  6. log_final()과 pool teardown은 daemon이 모두 멈춘 뒤 실행되므로 shared state보다 오래 사는 daemon은 없습니다.

stand-alone mode에서는 이 네 thread를 만들지 않습니다. background page-flush가 없으면 관련 requester가 victim flushing을 동기적으로 수행할 수 있습니다.

Wake는 hint이며 durable event가 아닙니다. generic waiter는 sleep 중일 때만 wakeup()을 받아들입니다. task가 이미 RUNNING이면 다음 pause를 위한 event로 저장하지 않습니다. 따라서 task는 실행될 때 shared pressure 또는 queue state를 다시 확인합니다.

Post-flush와 flush-control은 페이지를 다시 쓰지 않는다

File-I/O token bucket: 여러 writer가 공유하는 page 단위 credit 잔액입니다. 참여하는 writer는 OS write가 성공한 뒤 credit을 소비하고, 잔액이 없으면 계속 진행하기 전에 잠시 기다릴 수 있습니다. Flush-control은 주기적으로 잔액을 교체하므로 write 수행 허가가 아니라 soft pacing입니다. 정확한 producer, consumer, bypass rule 보기 →
Page-flush가 completion을 post-flush에 넘김: page submission은 끝났지만 in-memory BCB bookkeeping이 남았다는 뜻입니다. allocator pressure가 있으면 page-flush는 BCB pointer만 queue에 넣어 post-flush가 마무리하게 할 수 있습니다. page byte를 넘기거나 새 write를 요청하지 않습니다. 이동하는 것, 네 조건, local fallback 보기 →

Cleaning과 상태 처리 / 정책과 속도 조절

Lecture 6B — page-flush와 post-flush: 먼저 page-flush가 stable generation 하나를 선택하고 submit하는 과정을 따라갑니다. 그다음 BCB bookkeeping을 직접 끝낼지, pointer만 queue에 넣어 post-flush가 다시 확인하고 allocator를 깨우게 할지 나뉘는 지점을 봅니다.
Lecture 6C — maintenance와 flush-control: 먼저 replacement sample이 quota와 zone으로 바뀌는 과정을 봅니다. 별도로 successful file write가 page credit을 요청하고 50 ms control loop가 shared balance를 교체하는 과정도 봅니다. 어느 control path도 page image를 전달하지 않습니다.

checkpoint, log-flush daemon, foreground/WRITE-owner flush, DWB helper daemon은 이 네 역할 밖에 있습니다. 같은 durability mechanism을 지원하거나 재사용해도 page-buffer daemon worker가 되는 것은 아닙니다.

Frame이 부족할 때 누가 어떤 일을 할까?

Dirty page가 많아 allocator가 기다립니다. 네 daemon이 모두 페이지를 쓰는 것일까요?

설명 펼치기

아닙니다. Page-flush는 조건에 맞는 page image를 제출합니다. Post-flush는 전달받은 BCB 처리를 마치고 안전할 때 allocator에 배정할 수 있습니다. Maintenance는 quota와 zone, flush-control은 성공한 OS write 이후의 pacing credit을 관리합니다.
