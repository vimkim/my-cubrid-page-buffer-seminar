01 · daemon 정의하기

daemon 하나는 task 하나를 실행하고 pause하는 thread 하나입니다

create_daemon()은 managed execution context 하나와 std::thread 하나를 만듭니다. loop는 간단합니다. task를 실행하고, cubthread::looper에게 pause 시간을 물은 뒤, 다시 task를 실행합니다. 따라서 네 이름은 하나의 dirty-page queue에서 같은 일을 꺼내는 worker가 아니라 서로 독립적인 control loop입니다.

task는 생성 직후 한 번 실행됩니다. fixed period는 start-to-start 목표입니다. looper가 직전 task 실행 시간을 빼므로 100 ms 주기가 “작업을 끝낸 뒤 항상 100 ms를 더 sleep한다”는 뜻도, 매번 유용한 작업을 한다는 보장도 아닙니다.

02 · 전체 lifecycle

생성, enable, 유용한 작업, 소멸은 서로 다른 순간입니다

  1. 먼저 page-buffer pool, LRU, queue, monitor를 초기화합니다.
  2. server boot는 log recovery가 끝나기 전에 네 daemon thread를 만듭니다.
  3. 생성 직후 task는 boot gate가 닫힌 것을 보고 page-buffer의 유용한 작업 없이 반환합니다.
  4. recovery 뒤 boot가 gate를 엽니다. gate를 여는 동작 자체가 모든 sleeper를 wake하지는 않습니다. 이후 timer 또는 normal work wake에서 열린 gate를 관찰합니다.
  5. 정상 shutdown은 looper stop flag를 set하고 sleeper를 깨운 뒤 OS thread를 join하고 task/context를 retire하며 pointer를 비웁니다.
  6. log_final()과 pool teardown은 daemon이 모두 멈춘 뒤 실행되므로 shared state보다 오래 사는 daemon은 없습니다.

stand-alone mode에서는 이 네 thread를 만들지 않습니다. background page-flush가 없으면 관련 requester가 victim flushing을 동기적으로 수행할 수 있습니다.

04 · 어려운 표현 두 개 풀어 읽기

두 mechanism 모두 같은 page를 한 번 더 write한다는 뜻이 아닙니다

File-I/O token bucket: 여러 writer가 공유하는 page 단위 credit 잔액입니다. 참여하는 writer는 OS write가 성공한 뒤 credit을 소비하고, 잔액이 없으면 계속 진행하기 전에 잠시 기다릴 수 있습니다. Flush-control은 주기적으로 잔액을 교체하므로 write 수행 허가가 아니라 soft pacing입니다. 정확한 producer, consumer, bypass rule 보기 →
Page-flush가 completion을 post-flush에 넘김: page submission은 끝났지만 in-memory BCB bookkeeping이 남았다는 뜻입니다. allocator pressure가 있으면 page-flush는 BCB pointer만 queue에 넣어 post-flush가 마무리하게 할 수 있습니다. page byte를 넘기거나 새 write를 요청하지 않습니다. 이동하는 것, 네 조건, local fallback 보기 →
05 · 다음 lesson 고르기

서로 협력하는 두 역할씩 나누어 봅니다

Lesson 6B — page-flush와 post-flush: 먼저 page-flush가 stable generation 하나를 선택하고 submit하는 과정을 따라갑니다. 그다음 BCB bookkeeping을 직접 끝낼지, pointer만 queue에 넣어 post-flush가 다시 확인하고 allocator를 깨우게 할지 나뉘는 지점을 봅니다.
Lesson 6C — maintenance와 flush-control: 먼저 replacement sample이 quota와 zone으로 바뀌는 과정을 봅니다. 별도로 successful file write가 page credit을 요청하고 50 ms control loop가 shared balance를 교체하는 과정도 봅니다. 어느 control path도 page image를 전달하지 않습니다.

checkpoint, log-flush daemon, foreground/WRITE-owner flush, DWB helper daemon은 이 네 역할 밖에 있습니다. 같은 durability mechanism을 지원하거나 재사용해도 page-buffer daemon worker가 되는 것은 아닙니다.
