빈 frame이 없는데 새 페이지를 읽어야 한다면?

발표 경로 ↑

요청을 처리하는 thread가 페이지 E를 읽으려 합니다. E는 메모리에 없고, page buffer의 frame은 이미 사용 중입니다. Frame은 페이지 한 장을 담는 메모리 자리입니다. 자리가 모두 찼다면 기존 페이지 하나를 내보내야 E를 담을 수 있습니다.

다음은 판단에 필요한 상태만 남긴 작은 예제입니다. 실제 CUBRID pool의 크기나 LRU 순서를 재현한 것은 아닙니다.

Frame의 페이지현재 상태E를 위해 바로 덮어쓸 수 있을까?
A다른 thread가 사용 중: fixed안 됩니다. 그 thread가 쓰는 메모리를 빼앗게 됩니다.
B사용이 끝났지만 변경 내용이 남음: dirty안 됩니다. 변경된 내용을 안전한 기록 경로로 보내야 합니다.
C사용이 끝났지만 변경 내용이 남음: dirtyB와 같은 준비가 필요합니다.
D다른 thread가 사용 중: fixed사용이 끝나기 전에는 재사용할 수 없습니다.

질문: 오래 안 쓴 B를 골랐으니 이제 E로 덮어써도 될까요? 오래 안 썼다는 것은 선택의 이유일 뿐입니다. 안전하게 재사용할 수 있다는 뜻은 아닙니다. B의 변경 내용부터 처리해야 합니다.

이제 네 가지 문제가 나옵니다. 재사용할 후보를 미리 준비하기, 기록 후 상태 처리를 끝내기, 작업 변화에 맞춰 보관 정책을 조정하기, 기록 속도를 조절하기. 네 daemon은 이 서로 다른 일을 맡습니다.

요청을 처리하는 thread가 전부 하면 안 될까?

할 수는 있습니다. 다만 E를 읽는 경로에 B의 변경 내용 기록까지 붙으면, E의 요청은 자기 페이지를 읽기 전에 다른 페이지의 정리 비용도 부담합니다. 이런 일이 반복될 때 후보를 미리 준비하는 별도 thread가 도움이 됩니다. 얼마나 빨라지는지는 부하와 I/O 상황에 달려 있습니다.

  1. 요청 시점에 준비: E 요청 → 자리 부족 확인 → B 기록 처리 → 재사용 가능 여부 확인 → E 읽기.
  2. 미리 준비된 후보가 있다면: 별도 thread가 B 기록 처리 → 나중에 E 요청 → 안전 조건 재확인 → frame 재사용.

이런 일을 맡아 반복해서 작업하고 기다리는 background thread를 여기서는 daemon이라고 부릅니다. DB 서버 안의 thread이며 별도 서버 process가 아닙니다. 요청 thread를 foreground라고 부르면, background는 요청 처리와 별도로 진행하는 실행 역할입니다.

질문: daemon 하나가 모든 일을 차례로 하면 되지 않을까요? 가능한 설계입니다. CUBRID는 일이 생기는 조건과 기다리는 이유가 달라 네 역할을 나눴습니다. 아래 네 역할은 항상 순서대로 통과하는 네 단계가 아닙니다. 특히 maintenance와 flush-control은 페이지를 다음 worker에게 전달하는 단계가 아닙니다.

1. Page-flush — 재사용할 후보를 누가 미리 준비할까?

질문: B가 dirty라는 이유로 매번 요청을 기다리게 한다면, 미리 할 수 있는 일은 무엇일까요? 자주 쓰지 않는 dirty page를 찾아 변경 내용의 사본을 기록 경로에 보내는 일입니다. pgbuf-page-flush가 이 일을 맡습니다.

  1. 교체 후보 영역에서 최근 사용이 뜸한 dirty page를 찾습니다.
  2. 여전히 같은 페이지인지, 사용 중이지 않은지, 이미 flush 중이지 않은지 등을 다시 확인합니다.
  3. 조건을 만족하면 안전한 사본을 만들고 필요한 WAL 순서를 지켜 기록 경로에 제출합니다. WAL은 복구에 필요한 로그를 데이터보다 먼저 기록하는 규칙입니다.
  4. 그 사이 새 변경이 없고 나머지 재사용 조건도 맞으면, 그 frame은 이후 요청에 쓰일 후보가 될 수 있습니다.

질문: B를 flush하면 B가 메모리에서 사라질까요? 아닙니다. Flush는 변경 내용의 기록 처리이고, eviction은 기존 페이지를 내보내 frame을 재사용하는 일입니다. B가 메모리에 남아 있으면 다음 B 요청은 계속 그 페이지를 사용할 수 있습니다.

없으면? 이 background 준비 경로가 사라집니다. 필요한 정리를 다른 수행자가 맡지 않으면 dirty 후보가 남아 새 frame 확보가 지연될 수 있습니다. Checkpoint와 명시적 flush도 있으므로 모든 기록이 멈추거나 즉시 데이터가 손상된다고 말할 수는 없습니다. Stand-alone mode에서는 요청자가 victim flushing을 동기적으로 수행하는 경로가 있습니다.

기록 경로가 DWB(double-write buffer)를 사용하면 제출 성공 시점에 원래 데이터 파일 위치까지 기록이 끝난 것은 아닐 수 있습니다. 또 사본을 제출한 사이 B가 다시 변경되거나 사용 중이 되면 즉시 재사용할 수 없습니다.

pgbuf_page_flush_daemon_task::execute
  → pgbuf_flush_victim_candidates
    → pgbuf_bcb_flush_with_wal

위 경로는 이웃 페이지를 함께 기록하지 않는 분기입니다. WAL이 아직 준비되지 않은 후보는 건너뛰고 log flush를 요청할 수 있습니다.

2. Post-flush — 기록 처리가 끝나면 기다리던 요청은 저절로 알까?

질문: B의 사본을 제출했습니다. 그러면 다른 thread는 “B의 flush 처리가 끝났다”는 것을 어떻게 알까요? 메모리의 관리 상태를 바꾸고 필요한 대기자를 깨우는 작업이 남습니다. 페이지마다 이런 상태를 담는 관리 객체가 BCB(Buffer Control Block)입니다. 페이지 내용과 BCB의 관리 상태는 서로 다릅니다.

평소에는 flush를 수행한 thread가 이 처리를 직접 끝낼 수 있습니다. 그런데 frame을 기다리는 요청이 있고 page-flush가 바쁘다면, 뒷정리를 다른 thread에 맡겨 다음 후보를 처리하게 할 수 있습니다. 이것이 pgbuf-page-post-flush의 역할입니다.

  1. Page-flush는 조건이 맞으면 완료 처리가 남은 BCB의 pointer를 flushed_bcbs queue에 넣습니다. 페이지 사본을 보내는 것이 아닙니다.
  2. Post-flush가 BCB를 꺼내 잠그고 현재 상태를 확인합니다. 다시 dirty가 되었거나 누군가 fix했다면 frame을 배정하면 안 됩니다.
  3. 안전 조건과 정책을 만족하면 기다리는 요청에 frame을 직접 배정할 수 있습니다. 배정 여부와 별도로 flush 진행 상태를 정리하고 flush 대기자를 깨웁니다.
없으면? Post-flush daemon이 처음부터 없거나 queue에 넣지 못하면 기존 경로가 BCB 상태 처리를 직접 끝냅니다. 따라서 이 별도 thread가 모든 flush의 필수 단계는 아닙니다. 반대로 queue에 일은 계속 넣는데 consumer만 멈추면, 넘겨진 BCB의 완료 처리와 대기자 깨우기가 남을 수 있습니다.

질문: Post-flush가 B를 한 번 더 기록하나요? 아닙니다. 전달받은 관리 상태를 처리합니다. 또 “기록한 페이지이니 무조건 배정”하지 않습니다. 제출 이후 달라진 현재 상태를 다시 확인해야 합니다.

3. Maintenance — 어제 바빴던 작업을 오늘도 똑같이 우대할까?

질문: 오전에는 작업 X가 활발했지만 오후에는 X가 조용해지고 Y가 활발해졌습니다. 페이지 보관 정책을 그대로 두어도 될까요? 예전 활동에 맞춘 보관 목표를 계속 쓰면 현재 자주 쓰는 페이지에 맞지 않을 수 있습니다.

CUBRID는 페이지를 private/shared LRU 목록으로 관리합니다. 여기서 quota는 private 목록의 보관 목표이지, 미리 잘라 독점 배정한 메모리 영역이 아닙니다. Zone은 같은 목록 안에서 더 보호할 쪽과 교체 후보 쪽을 구분하는 영역입니다. 한 페이지가 여러 zone에 동시에 들어 있는 것은 아닙니다.

  1. 일반 페이지 사용 경로가 접근 활동의 표본을 남깁니다.
  2. pgbuf-maintain이 주기적으로 조정을 시도합니다. 내부 시간·활동 조건을 통과하면 그 활동을 바탕으로 quota와 zone 경계를 갱신합니다.
  3. 이후 교체와 목록 관리가 바뀐 정책을 활용합니다. Maintenance가 페이지 내용을 기록하거나 별도 메모리를 만들어 주는 것은 아닙니다.

예를 들어 X의 활동 표본은 줄고 Y의 표본은 늘었다면, 정책은 이런 변화를 반영할 기회를 얻습니다. “X에서 정확히 두 frame을 빼서 즉시 Y에게 준다”는 식의 고정 분배를 뜻하지는 않습니다.

없으면? 이 주기적 정책 조정이 사라집니다. Private LRU 획득·반환 때의 다른 quota 조정 호출은 남지만, 지속적으로 최근 활동 변화를 반영할 기회를 잃으므로 작업 변화에 대응하기 어려워질 수 있습니다. 일반 fix/unfix나 모든 교체가 곧바로 멈춘다는 뜻은 아닙니다. 요청마다 전체 활동을 계산하는 대안도 생각할 수 있지만 요청 경로에 공통 조정 비용이 붙습니다.

4. Flush-control — 미리 기록하는 일을 무조건 빠르게 해도 될까?

질문: Dirty page를 빨리 정리하려고 writer들이 계속 기록하면 항상 좋을까요? 저장장치는 다른 읽기·쓰기 작업과도 공유합니다. Background 일을 몰아서 진행하면 다른 작업과 I/O를 놓고 경쟁할 수 있습니다. 그래서 “무엇을 기록할까?”와 별도로 “얼마나 빠르게 계속 진행할까?”를 조절합니다.

pgbuf-flush-control은 페이지 단위의 공유 credit 잔액을 주기적으로 갱신합니다. Credit은 이 속도 조절에 쓰는 계산 단위입니다. 참여하는 writer는 OS write가 성공한 뒤 기록한 page 수에 해당하는 credit을 소비하고, 부족하면 이후 진행 전에 기다릴 수 있습니다. 이를 soft pacing이라고 합니다.

  1. 예제에서 공유 잔액이 2 credit이라고 합시다. 실제 설정값을 뜻하지는 않습니다.
  2. 참여 writer가 한 page의 OS write를 마치고 1 credit을 소비하면 1이 남습니다.
  3. 다음 한 page도 write 후 소비하면 0이 됩니다.
  4. 그다음 page의 write도 이미 성공한 뒤 credit을 요청합니다. 잔액이 부족하므로 여기서 기다릴 수 있습니다.
  5. Flush-control이 잔액을 갱신하고 대기자를 깨우면 writer가 소비를 다시 시도합니다.

질문: 그러면 credit이 0이면 OS write를 시작할 수 없나요? 아닙니다. 검사 위치가 write 뒤입니다. 따라서 엄격한 사전 I/O 허가나 저장장치 전체의 속도 상한이 아닙니다. 일부 경로의 우회도 있으므로 모든 write가 같은 방식으로 기다린다고 생각하면 안 됩니다.

없으면? Token bucket 자체가 없으면 소비 경로는 우회하므로 이 pacing 효과가 사라집니다. 반면 bucket과 대기 절차는 남겨 두고 공급 daemon만 멈추면, credit을 기다리는 writer가 계속 대기할 수 있습니다. “속도 조절 기능을 없앤 설계”와 “공급자만 고장 난 상태”는 결과가 다릅니다.

Post-flush와 flush-control은 페이지를 다시 쓰지 않는다

File-I/O token bucket: 여러 writer가 공유하는 page 단위 credit 잔액입니다. 참여하는 writer는 OS write가 성공한 뒤 credit을 소비하고, 잔액이 없으면 계속 진행하기 전에 잠시 기다릴 수 있습니다. Flush-control은 주기적으로 잔액을 교체하므로 write 수행 허가가 아니라 soft pacing입니다. 정확한 producer, consumer, bypass rule 보기 →
Page-flush가 completion을 post-flush에 넘김: page submission은 끝났지만 in-memory BCB bookkeeping이 남았다는 뜻입니다. allocator pressure가 있으면 page-flush는 BCB pointer만 queue에 넣어 post-flush가 마무리하게 할 수 있습니다. page byte를 넘기거나 새 write를 요청하지 않습니다. 이동하는 것, 네 조건, local fallback 보기 →

각 daemon은 독립적으로 일하고 기다린다

네 daemon은 서로 다른 역할을 가진 background thread입니다. Timer나 wakeup은 실행 기회이고, 실제 작업 여부는 현재 상태를 확인한 뒤 결정합니다.

세부 동작과 소스 펼치기

create_daemon()은 managed execution context 하나와 std::thread 하나를 만듭니다. loop는 간단합니다. task를 실행하고, cubthread::looper에게 pause 시간을 물은 뒤, 다시 task를 실행합니다. 따라서 네 이름은 하나의 dirty-page queue에서 같은 일을 꺼내는 worker가 아니라 서로 독립적인 control loop입니다.

task는 생성 직후 한 번 실행됩니다. fixed period는 start-to-start 목표입니다. looper가 직전 task 실행 시간을 빼므로 100 ms 주기가 “작업을 끝낸 뒤 항상 100 ms를 더 sleep한다”는 뜻도, 매번 유용한 작업을 한다는 보장도 아닙니다.

복구가 끝난 뒤 작업하고, pool보다 먼저 종료한다

서버는 복구 중에 thread를 만들지만 boot gate가 열리기 전에는 page-buffer 작업을 하지 않습니다. 정상 종료에서는 pool을 정리하기 전에 daemon을 멈춥니다. Stand-alone mode에서는 이 네 thread를 만들지 않습니다.

세부 동작과 소스 펼치기
  1. 먼저 page-buffer pool, LRU, queue, monitor를 초기화합니다.
  2. server boot는 log recovery가 끝나기 전에 네 daemon thread를 만듭니다.
  3. 생성 직후 task는 boot gate가 닫힌 것을 보고 page-buffer의 유용한 작업 없이 반환합니다.
  4. recovery 뒤 boot가 gate를 엽니다. gate를 여는 동작 자체가 모든 sleeper를 wake하지는 않습니다. 이후 timer 또는 normal work wake에서 열린 gate를 관찰합니다.
  5. 정상 shutdown은 looper stop flag를 set하고 sleeper를 깨운 뒤 OS thread를 join하고 task/context를 retire하며 pointer를 비웁니다.
  6. log_final()과 pool teardown은 daemon이 모두 멈춘 뒤 실행되므로 shared state보다 오래 사는 daemon은 없습니다.

stand-alone mode에서는 이 네 thread를 만들지 않습니다. background page-flush가 없으면 관련 requester가 victim flushing을 동기적으로 수행할 수 있습니다.

Cleaning과 상태 처리 / 정책과 속도 조절

Lecture 6B — page-flush와 post-flush: 먼저 page-flush가 stable generation 하나를 선택하고 submit하는 과정을 따라갑니다. 그다음 BCB bookkeeping을 직접 끝낼지, pointer만 queue에 넣어 post-flush가 다시 확인하고 allocator를 깨우게 할지 나뉘는 지점을 봅니다.
Lecture 6C — maintenance와 flush-control: 먼저 replacement sample이 quota와 zone으로 바뀌는 과정을 봅니다. 별도로 successful file write가 page credit을 요청하고 50 ms control loop가 shared balance를 교체하는 과정도 봅니다. 어느 control path도 page image를 전달하지 않습니다.

checkpoint, log-flush daemon, foreground/WRITE-owner flush, DWB helper daemon은 이 네 역할 밖에 있습니다. 같은 durability mechanism을 지원하거나 재사용해도 page-buffer daemon worker가 되는 것은 아닙니다.

이 상황에서는 누가 필요할까?

1. B를 flush한 사이 다른 thread가 B를 다시 수정했습니다. Post-flush는 E에게 그 frame을 바로 줘도 될까요?

예측한 뒤 설명 펼치기

안 됩니다. 제출한 사본과 현재 메모리 내용은 달라졌습니다. 이전 flush의 상태 처리를 끝내더라도 새 DIRTY 상태는 남겨야 하고, 현재 재사용 조건을 다시 확인해야 합니다.

2. Post-flush thread가 없어도 완료 처리를 호출자가 직접 한다면, 반드시 별도 thread가 있어야 한다고 말할 수 있을까요?

예측한 뒤 설명 펼치기

아닙니다. 반드시 수행해야 하는 완료 처리와 그 일을 별도 thread에 분담하는 선택을 구별해야 합니다. 다만 이미 queue에 위임했다면 누군가는 그 queue를 처리해야 합니다.

3. X가 조용해지고 Y가 바빠졌습니다. 이 변화에 맞춰 보관 목표를 조정하려면 page-flush를 더 자주 깨우면 될까요?

예측한 뒤 설명 펼치기

Page-flush는 후보의 변경 내용을 기록하는 역할입니다. 활동 표본을 quota와 zone에 반영하는 역할은 maintenance입니다. 기록량과 보관 정책은 다른 문제입니다.

4. Credit이 0인데 writer가 방금 한 page를 기록했습니다. Flush-control의 규칙을 어긴 것일까요?

예측한 뒤 설명 펼치기

아닙니다. 참여 경로의 credit 소비는 OS write 성공 뒤에 옵니다. 이미 수행한 write를 취소하는 것이 아니라 이후 진행을 늦출 수 있습니다.
