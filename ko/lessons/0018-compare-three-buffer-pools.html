01 · 비교 원칙

두 가지 protection부터 본다

Replacement protection은 참조 중인 frame이 다른 logical page에 reuse되지 않게 한다. Content protection은 현재 page byte에 충돌하는 access가 들어오지 않게 한다. 모든 engine에 두 responsibility가 모두 필요하며, 가장 가까운 interface끼리도 완전한 일대일 대응은 아니다.

CUBRID

pgbuf_fix() → BCB fcnt + thread holder + requested latch → pgbuf_unfix()

PostgreSQL

Pin → private/shared refcount → 별도 content lock → 독립적인 unlock과 unpin

MySQL / InnoDB

buf_page_get_gen(..., mtr) → atomic buf_fix_count + S/SX/X memo entry → memo가 unlatch 후 unfix

CUBRID는 fix, latch, thread ownership을 결합한다. PostgreSQL은 pin과 content lock을 분리한다. InnoDB는 low-level state는 분리하지만 lifetime은 MTR memo에서 다시 묶는다.

03 · 첫 performance 가설

Replacement를 바꾸기 전에 per-thread holder lookup부터 측정한다

Verified mechanism: pgbuf_find_thrd_holder()는 target을 찾을 때까지 current thread의 singly linked held-BCB list를 순회한다. Normal latch acquisition, lock-free READ hit, unfix, dirty validation 등 ownership check에서 호출된다. Lock-free READ path는 같은 thread가 이미 BCB를 보유해도 BCB fcnt에 shared CAS를 수행한다.

Inference: worker가 서로 다른 page를 많이 동시에 보유하거나 이미 보유한 hot page를 반복 fix하면 linear holder 탐색과 shared cache-line traffic이 CPU bottleneck이 될 수 있다. PostgreSQL의 작은 private-refcount array와 overflow hash, local-only repeated-pin increment는 같은 safety responsibility를 더 저렴한 seam에 둘 수 있음을 보여 준다. 그 설계를 복사하면 CUBRID가 빨라진다는 증거는 아니다.

04 · 반증 가능한 experiment

List cost와 shared-atomic cost를 분리한다

  1. Release build와 resident working set을 사용하고 측정 구간에서 storage I/O를 제외한다.
  2. 서로 다른 H개 page를 보유한 채 target 하나를 반복 fix/unfix하며 H를 1, 4, 16, 64로 바꾼다.
  3. 한 thread로 실행한 뒤 target BCB를 공유하는 여러 thread로 실행한다. 확인한 holder node 수, CAS attempt/retry, pair당 cycle, throughput을 기록한다.
  4. Non-nested/private page, nested/private page, non-nested/shared page, nested/shared page 네 형태를 비교한다.
  5. Cost가 H에 따라 늘지 않으면 lookup hypothesis를 기각한다. Shared contention이 커지지 않거나 대표 caller의 nested re-fix가 미미하면 aggregation hypothesis를 기각한다.

Source에서 보인 기회는 workload가 실제 cost를 드러낸 뒤에야 performance finding이 된다.
