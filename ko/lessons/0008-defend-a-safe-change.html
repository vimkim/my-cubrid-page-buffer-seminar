00 · 문서 label 해석하기

VS-11과 VS-12는 code object가 아니라 registry ID다

이 guide는 불확실하거나 revision에 민감한 finding을 Unresolved or version-sensitive findings 한 문서에서 관리한다. VS-11과 VS-12는 그 registry의 안정적인 row identifier일 뿐이다. CUBRID error code, variable, page type, runtime flag가 아니다.

case packet은 registry entry, 범위를 정한 source range, prediction worksheet, proof obligation, model answer를 묶은 독립적인 review exercise를 가리키는 capstone 용어다. network packet이나 page-buffer structure가 아니다.

Case packetpinned commit에서 검증된 source fact아직 입증되지 않은 candidate consequence
A · VS-11일부 경로는 NULL을 반환할 수 있는 holder allocation보다 먼저 latch/fix state를 grant한다. 인용한 snippet에는 local rollback이 보이지 않는다.caller가 failure를 받았는데도 grant나 fcnt가 남을 수 있다.
B · VS-12Flush setup은 TDE/DWB 준비가 반환하기 전에 FLUSHING을 set하고 이전 DIRTY를 clear한다. 일반 rollback은 뒤에 있다.FLUSHING이 남거나 retry 가능한 dirty/LSA bookkeeping이 사라질 수 있다.
사실이라고 말할 수 있는가? 각 entry에는 검증된 Level 1 source-ordering fact와 Candidate consequence가 명확히 구분되어 있다. candidate 전체가 검증된 production defect는 아니다. reachability, surviving state, impact, current-branch status에는 여전히 evidence가 필요하다.
01 · Proof ladder

의심스러운 return은 첫 단에 불과하다

Level질문판단을 닫는 evidence
1 · Source-visible control flowpinned 경로가 state를 바꾸고 실패 가능한 것을 호출한 뒤 눈에 보이는 local cleanup 전에 반환하는가?정확한 symbol, range, transition, callee.
2 · Reachability지원되는 target configuration에서 이 지점의 callee가 실제로 실패할 수 있는가?target revision에서 controlled injection 또는 schedule.
3 · Surviving state주변 cleanup이 모두 끝난 뒤 어떤 ownership/generation debt가 남는가?injected return 직후 assertion/inspection.
4 · Production impact남은 state가 corruption, leak, hang, retry loss, caller-visible contract violation을 일으키는가?실제 consumer path에서 consequence 재현.
5 · Current-branch status변경 대상 branch에도 같은 mechanism과 consequence가 존재하는가?정확히 그 commit/configuration에서 다시 trace하고 실행.

강한 Level 1 논증은 조사할 가치가 있다. 그렇다고 Level 2–5를 자동으로 얻는 것은 아니다.

03 · Change-impact defense

모든 proposal이 아홉 질문에 답하게 한다

  1. Behavior: 관찰 가능한 어떤 behavior가 바뀔 수 있는가?
  2. Owners: 각 resource/decision을 어느 thread, Module, caller가 소유하는가?
  3. State: 어느 field, flag, counter, pointer, queue, LSA가 transition하는가?
  4. Guards: 어느 BCB protection, atomic order, logical lock, caller precondition이 각 transition을 보호하는가?
  5. Invariants: transition 전후에 무엇이 반드시 성립해야 하는가?
  6. Unwind: 모든 failure/restart에서 무엇을 복구, 이전, 소비하거나 깨우는가?
  7. Caller impact: return, retained ownership, retry, timing, contract change를 누가 관찰하는가?
  8. Evidence seam: source tracing은 무엇을 입증하며 어떤 controlled probe가 risk에 도달하는가?
  9. Remaining uncertainty: 무엇이 inference, version-sensitive, unreachable, unobserved 상태인가?

이 template에는 object identity, fix debt, caller correctness, flush generation, replacement eligibility, evidence grammar라는 Core가 서로 엮여 있다.

05 · 대안 packet

VS-11에는 일반 주장 하나가 아니라 injection 세 개가 필요하다

holder allocation은 NULL을 6000–6055에서 반환할 수 있다. normal hit, lock-free READ hit, awakened waiter는 holder 기록 전에 서로 다른 경로로 ownership을 grant한다. scheduling과 cleanup seam도 각각 다르다.

세 경로 모두에서 holder extension allocation failure를 따로 inject한다. atomic latch tuple, global fcnt, thread별 holder list, waiter/grant state, 반환값, 이후 acquire/release 가능 여부를 inspect한다. lock-free나 waiter 결과가 normal-hit variant까지 자동으로 입증하지 않으며 그 반대도 마찬가지다.

06 · Readiness gate

변경 준비에는 실행 가능한 evidence도 필요합니다

source packet을 만든 뒤 target revision에서 범위를 좁힌 caller regression이나 controlled runtime probe를 적어도 하나 실행한다. setup, expected transition, actual observation, 뒷받침되지 않는 conclusion, 재현 가능한 receipt를 기록하라.

implementation 준비가 끝났다고 보기 전에 다른 maintainer가 ownership ledger, 모든 negative path, risk에 맞는 test seam, remaining uncertainty를 review해야 한다. 이 과정을 거쳐 evidence packet이 단순한 문서 tour가 아니라 실제 review protocol이 된다.

07 · Retrieval 연습

방어 가능한 가장 강한 VS-12 문장을 만든다

문제

reviewer가 말한다. “source가 명백히 일찍 return하니 지금 이 flush bug를 고쳐야 합니다.”

과제: Level 1이 입증한 범위까지만 동의하고 빠진 proof level을 모두 말하라. risk에 맞는 가장 작은 probe와 정확한 postcondition을 제안하고 현재 status의 owner를 밝혀라.

답을 chat에 붙여 넣어 보자. ownership, transition ordering, proof-level discipline, test reach, claim precision을 확인한 뒤 Core 완료를 기록한다.

핵심 읽을거리

trace한 뒤 evidence 경계에서 멈춘다

pinned page_buffer.c:10795–10923과 VS-12 registry entry를 나란히 읽어라. generation setup, 각 fallible call, early exit, 일반 rollback, runtime evidence가 더 필요한 모든 주장을 표시하자.
