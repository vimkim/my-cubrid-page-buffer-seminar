02 · Grant 전후를 thread 관점에서 보기

Waiter list와 holder list는 서로 다른 구조입니다

기다리는 동안에는 BCB에서 THREAD_ENTRY로 request가 연결됩니다. Grant 뒤에는 그 thread에서 PGBUF_HOLDER로 ownership이 연결됩니다.

기다리는 thread 자체가 queue node입니다. Latch grant가 성공하기 전에는 새 holder가 생기지 않습니다.

시점Linked-list anchor와 linkNode의 의미
Incompatible unconditional waitBCB.next_wait_thrd → THREAD_ENTRY.next_wait_thrdTHREAD_ENTRY가 request_latch_mode와 request_fix_count를 담습니다. Pending request일 뿐 새 ownership은 아닙니다.
성공한 grantholder_anchor.thrd_hold_list → PGBUF_HOLDER.thrd_linkHolder가 BCB를 가리키고 이 thread의 nested fix debt를 셉니다.

Waker가 BCB latch tuple을 바꾸고 기다리던 THREAD_ENTRY를 unlink한 뒤 깨웁니다. 재개된 thread는 free list에서 재사용 가능한 holder를 pop하여 active list head에 붙입니다. BCB에는 wait-queue head가 있지만 holder 또는 transaction의 reverse list는 없습니다.

Thread ownership과 transaction policy의 차이

실행 중인 thread가 page-buffer의 두 bookkeeping을 모두 소유합니다. Thread의 tran_index를 통해 page buffer가 transaction의 wait_msecs를 읽고 transaction-aware timeout 또는 interrupt error를 보고합니다. Transaction은 wait policy에 영향을 주지만 page-buffer holder list의 node는 아닙니다.

검증된 mechanism: BCB queue head와 holder 구조는 pinned page_buffer.c:460–528, thread request field는 thread_entry.hpp:228–256, holder allocation은 page_buffer.c:5922–6086입니다.

03 · READ, WRITE, unconditional

Unconditional은 “충돌하면 기다린다”이지 “항상 기다린다”가 아닙니다

Latch 작업 전, zero-wait policy인 transaction은 unconditional fix도 conditional behavior로 바꿉니다. 그렇지 않다면 compatible request는 즉시 성공하고 incompatible request는 queue에 들어갑니다.

현재 BCB 상태READ requestWRITE request
NO_LATCHREAD와 global fcnt=1을 set하고 holder를 만듭니다.WRITE와 global fcnt=1을 set하고 holder를 만듭니다.
READ, waiter 없음즉시 grant합니다. 기존 thread holder는 증가하고 새 reader는 자기 holder를 얻습니다.이 thread가 현재 fix count 전부를 소유할 때만 즉시 promote합니다. 아니면 기다립니다.
READ, waiter 있음기존 holder는 re-enter할 수 있습니다. 새 reader는 앞지르지 않고 기다립니다.Only-reader promotion은 여전히 가능하고, 그 외에는 기다립니다.
WRITE현재 WRITE holder는 READ를 nested로 요청할 수 있고, 다른 thread는 기다립니다.현재 WRITE holder는 re-enter할 수 있고, 다른 thread는 기다립니다.

“Reader 하나 추가”만으로는 부족합니다. Writer가 기다릴 때 기존 reader와 새 non-holder reader가 서로 다른 길을 갑니다.

N reader가 있고 waiter는 없으면 READ 하나를 즉시 grant합니다. N reader와 queued writer가 있으면 새 non-holder reader는 writer 뒤로 가지만 기존 reader는 READ로 re-enter할 수 있습니다. 새 writer도 tail에 붙습니다. 현재 reader의 WRITE 요청은 모든 fix를 혼자 소유하면 promote하고, general fix path에서는 자기 READ share를 놓고 기다리며, dedicated promotion interface라면 head에 삽입됩니다.

General WRITE fix가 기다려야 하는데 이 thread가 이미 READ fix를 보유했다면, 이 thread의 READ contribution을 global fcnt에서 빼고 holder를 제거한 다음 combined count를 담은 request를 queue에 넣습니다. Dedicated blocking pgbuf_promote_read_latch()는 다른 interface이며 promoter를 queue head에 삽입합니다. 일반 conflicting fix는 tail에 append합니다.

Waiter 100명을 queue에 넣으면 O(N²)인가?

Queue가 줄지 않는 동안의 누적 insertion은 맞습니다. BCB에는 head pointer인 next_wait_thrd만 있고 tail pointer는 없습니다. 일반 append는 head부터 마지막 THREAD_ENTRY까지 걷습니다.

04 · writer 백 개

incompatible request는 ownership zero-crossing을 기다린다

serialized handoff는 source에서 확인할 수 있지만 strict fairness는 확인할 수 없다.

  1. 현재 WRITE holder가 fcnt > 0을 유지한다. incompatible unconditional WRITE request는 BCB queue 뒤에 붙는다. 단, blocking promoter는 head insertion 예외다.
  2. 각 waiter는 시간 제한과 interrupt 처리가 있는 wait로 sleep한다. conditional behavior로 전환된 request는 queue에 들어가지 않는다.
  3. 현재 holder가 unfix하여 global fcnt가 0이 되면, release하는 thread가 BCB protection을 잡은 채 queue를 순회한다.
  4. cancel된 entry는 건너뛰고, FLUSH waiter는 flush completion에 맡기며, head request에 따라 grant한다.
  5. waker가 latch mode와 요청된 fix count를 설치하고, 재개된 thread가 thread별 holder를 기록해야 success가 완성된다.

Verified mechanism: pinned grant/wait decision은 page_buffer.c:6278–6634, queue/sleep은 7041–7450, zero-crossing wakeup은 7452–7590이다.

06 · Evidence 경계

“대체로 도착 순서”는 FIFO도 starvation freedom도 아니다

Writer 백 개는 보통 queue 순서대로 zero-crossing마다 하나씩 처리됩니다. Head가 R1 → R2 → W1 → R3이면 R1과 R2를 grant한 뒤 W1에서 멈춥니다. R3는 W1을 뛰어넘지 않습니다. 그래도 다음 세 mechanism은 겉으로 보이는 처리 순서를 바꿀 수 있습니다.

  • Holder re-entry: 기존 holder는 waiter를 지나 nested ownership을 얻을 수 있다.
  • Promotion: blocking promoter는 head에 삽입된다.
  • Reader grouping: head의 연속된 compatible READ 구간을 batch로 grant할 수 있습니다.
주장하면 안 되는 것: strict FIFO, starvation freedom, wall-clock 기준 처리 보장, latch-level deadlock freedom. timed sleep이 deadlock guard 역할을 하며 정확한 시간은 revision policy다.
07 · 실패한 wait에는 debt가 남지 않는다

Timeout과 interrupt는 늦은 grant가 아니라 cleanup 경로다

timeout은 request를 reset/cancel하고 transaction wait policy에 따라 mapping된 page-latch timeout을 보고한다. interrupt된 waiter는 스스로를 제거한다. 어느 쪽도 page pointer를 반환하거나 caller가 unfix해야 할 holder를 만들지 않는다.

모든 wakeup의 양쪽을 확인해야 한다. waker의 tuple transition과 재개된 thread의 holder allocation이다. Lesson 8의 VS-11 candidate는 정확히 이 post-grant holder-recording seam에 있다. 두 ledger가 일치해야 queue success가 완성된다.

08 · Retrieval 연습

“waiter가 page를 소유한다”는 표현 없이 queue 하나를 trace한다

문제

WRITE holder의 fcnt=1이다. queue는 R1 → R2 → W1 → R3이고, 또 다른 non-holder reader가 도착한다. 이어 holder가 unfix하여 0이 된다.

과제: 새 request가 앞지를 수 있는지, 어떤 request가 grant되는지, debt가 언제 시작되는지, W1이 아직 무엇을 소유하는지 예측하라. 이 결과가 fairness를 증명하지 않는 이유와 W1의 timeout 결과도 덧붙여라.
