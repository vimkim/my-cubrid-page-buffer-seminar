01 · Resident BCB를 찾은 다음에는 무슨 일이 생길까요?

Fix 요청은 caller가 확인할 수 있는 다섯 결과 중 하나로 끝납니다

앞 lesson들은 “READ 또는 WRITE latch를 요청한다”는 데서 설명을 멈췄습니다. 이 lesson에서는 그 한 단계를 열어 봅니다. CUBRID가 resident BCB를 찾으면 요청한 latch를 현재 owner와 wait queue에 대조합니다. Compatible request는 즉시 끝날 수 있습니다. Conflicting request는 caller의 condition에 따라 바로 실패하거나 기다립니다.

아래 표는 request 하나를 caller 관점에서 따라갑니다. 확인할 질문은 간단합니다. 이 호출이 내가 이제 소유하고 나중에 unfix해야 할 page를 반환했는가?

02 · Grant 전후를 thread 관점에서 보기

Waiter list와 holder list는 서로 다른 구조입니다

기다리는 동안에는 BCB에서 THREAD_ENTRY로 request가 연결됩니다. Grant 뒤에는 그 thread에서 PGBUF_HOLDER로 ownership이 연결됩니다.

기다리는 thread 자체가 queue node입니다. Latch grant가 성공하기 전에는 새 holder가 생기지 않습니다.

Thread ownership과 transaction policy의 차이

실행 중인 thread가 page-buffer의 두 bookkeeping을 모두 소유합니다. Thread의 tran_index를 통해 page buffer가 transaction의 wait_msecs를 읽고 transaction-aware timeout 또는 interrupt error를 보고합니다. Transaction은 wait policy에 영향을 주지만 page-buffer holder list의 node는 아닙니다.

04 · READ, WRITE, unconditional

Unconditional은 “충돌하면 기다린다”이지 “항상 기다린다”가 아닙니다

Latch 작업 전, zero-wait policy인 transaction은 unconditional fix도 conditional behavior로 바꿉니다. 그렇지 않다면 compatible request는 즉시 성공하고 incompatible request는 queue에 들어갑니다.

현재 BCB 상태READ requestWRITE request
NO_LATCHREAD와 global fcnt=1을 set하고 holder를 만듭니다.WRITE와 global fcnt=1을 set하고 holder를 만듭니다.
READ, waiter 없음즉시 grant합니다. 기존 thread holder는 증가하고 새 reader는 자기 holder를 얻습니다.Nested pgbuf_fix(..., WRITE, ...)는 이 thread가 현재 fix 전부를 소유할 때만 즉시 upgrade한 뒤 새 fix debt 하나를 더합니다. 아니면 기다립니다.
READ, waiter 있음기존 holder는 re-enter할 수 있습니다. 새 reader는 앞지르지 않고 기다립니다.같은 nested-WRITE-fix rule이 적용됩니다. 이는 전용 promotion API의 contract가 아닙니다.
WRITE현재 WRITE holder는 READ를 nested로 요청할 수 있고, 다른 thread는 기다립니다.현재 WRITE holder는 re-enter할 수 있고, 다른 thread는 기다립니다.

“Reader 하나 추가”만으로는 부족합니다. Writer가 기다릴 때 기존 reader와 새 non-holder reader가 서로 다른 길을 갑니다.

N reader가 있고 waiter는 없으면 READ 하나를 즉시 grant합니다. N reader와 queued writer가 있으면 새 non-holder reader는 writer 뒤로 가지만 기존 reader는 READ로 re-enter할 수 있습니다. 새 writer도 tail에 붙습니다. “현재 reader가 WRITE를 요청한다”만으로는 부족합니다. Nested WRITE fix는 debt 하나를 새로 획득하지만, 전용 promotion은 caller가 이미 가진 fix를 변환합니다.

General WRITE fix가 기다려야 하는데 이 thread가 이미 READ fix를 보유했다면, 이 thread의 READ contribution을 global fcnt에서 빼고 holder를 제거한 다음 기존 count에 1을 더한 request를 queue에 넣습니다. Dedicated blocking pgbuf_promote_read_latch()는 기존 count를 유지하고 promoter를 queue head에 삽입합니다. 일반 conflicting fix는 tail에 append합니다.

별도의 READ-to-WRITE promotion API가 왜 필요한가?

둘 다 WRITE protection으로 끝날 수 있지만 ownership accounting contract는 다릅니다.

따라서 general helper 안의 즉시 upgrade branch는 전용 API를 대체하지 않습니다. 그 branch는 새 acquisition contract를 만족합니다. 전용 함수는 같은 debt를 변환하고, promotion 전용 policy와 queue-head continuity를 제공하며, hard-failure pointer 경계를 명시합니다. Lesson 10은 대표 B-tree caller를 따라 이 protocol을 설명합니다.

Pinned-source anomaly: ordinary immediate branch는 global fcnt=1로 만든 다음 기존 holder를 증가시킵니다. Holder count 2에서 시작하면 global count 1과 holder count 3이 남는 것으로 보입니다. 이는 안전한 promotion 대체 경로로 입증된 것이 아니라 candidate VS-18이며, focused runtime test가 더 필요합니다.

Waiter 100명을 queue에 넣으면 O(N²)인가?

04 · writer 백 개

incompatible request는 ownership zero-crossing을 기다린다

serialized handoff는 source에서 확인할 수 있지만 strict fairness는 확인할 수 없다.

  1. 현재 WRITE holder가 fcnt > 0을 유지한다. incompatible unconditional WRITE request는 BCB queue 뒤에 붙는다. 단, blocking promoter는 head insertion 예외다.
  2. 각 waiter는 시간 제한과 interrupt 처리가 있는 wait로 sleep한다. conditional behavior로 전환된 request는 queue에 들어가지 않는다.
  3. 현재 holder가 unfix하여 global fcnt가 0이 되면, release하는 thread가 BCB protection을 잡은 채 queue를 순회한다.
  4. cancel된 entry는 제거하고 FLUSH waiter는 linked 상태로 둔다. 처음 grant한 것이 WRITE이면 scan을 멈추고, READ이면 queued writer를 지나 뒤의 reader도 grant한다.
  5. waker가 latch mode와 요청된 fix count를 설치하고, 재개된 thread가 thread별 holder를 기록해야 success가 완성된다.

Verified mechanism: pinned grant/wait decision은 page_buffer.c:6278–6634, queue/sleep은 7041–7450, zero-crossing wakeup은 7452–7590이다.

05 · 번갈아 들어온 request 여섯 개

같은 wakeup scan에서 READ grant가 queued writer를 건너갈 수 있다

새 non-holder thread 여섯 개가 R1 → W1 → R2 → W2 → R3 → W3 순서로 도착한다고 가정합니다.

처음에는 owner thread만 holder(A, count=1)을 가집니다. 여섯 request는 모두 BCB A의 WRITE latch와 충돌하므로 자기 THREAD_ENTRY를 A.next_wait_thrd에 append합니다. Node에는 요청 mode와 count가 있지만, 이 여섯 requester에는 아직 PGBUF_HOLDER, page pointer, fix debt가 없습니다.

Owner가 unfix하여 0이 되면 wakeup loop는 R1을 grant하고 tuple을 READ로 바꿉니다. W1에서 멈추지 않습니다. W1은 linked 상태로 남기고 scan을 계속하여 R2를 grant하고, W2를 남기고, R3를 grant하고, W3를 남깁니다. 결과는 READ, fcnt=3, queue는 W1 → W2 → W3입니다. 깨어난 각 reader는 자기 thread list에 holder(A, count=1)을 기록합니다. 나중에 세 reader가 모두 unfix하여 0이 되면 W1을 grant하고, 이후 zero-crossing에서 W2와 W3를 하나씩 grant합니다.

Source-over-comment 세부사항: 근처 source comment는 “head”의 reader를 깨운다고 요약하지만, 실제 loop는 tuple이 READ인 동안 incompatible WRITE와 FLUSH node를 지나 계속 순회합니다. 따라서 이 mixed queue에서는 뒤쪽 READ node도 grant합니다. 축약된 comment가 아니라 control flow를 검토해야 합니다.

Queued READ 하나를 grant할 때마다 queue 전체를 처음부터 다시 scan하는가?

아닙니다. 한 번의 zero-crossing wakeup이 한 번 앞으로 순회하면서 그 scan 안에서 reader 여러 개를 grant합니다. 처음 grant 가능한 node가 READ이면 waker가 tuple을 READ로 바꾸고 현재 위치부터 계속 갑니다. Incompatible WRITE는 linked 상태로 남기고 다음 node로 이동하며, 이후 만나는 compatible READ를 모두 grant합니다. R2, R3마다 head로 돌아가지 않습니다.

Enqueue 비용은 별개입니다. 최초 WRITE owner가 계속 fixed인 동안 모든 ordinary conflicting arrival은 READ/WRITE 구분 없이 singly linked queue의 tail을 찾으려고 순회합니다. 이는 arrival마다 한 번의 O(W) append walk이며 reader-group algorithm이 아닙니다.

Queue가 WRITE로 시작하면 첫 zero-crossing은 그 writer 하나를 grant하고 멈춥니다. 그 writer가 release하면 새 head가 READ이므로 다음 한 번의 forward scan이 남은 writer를 건너 모든 READ를 grant합니다. 따라서 비용은 누적 O(N²) tail-append 작업에 한 번의 O(N) reader scan을 더한 것이지 full scan을 50번 또는 100번 하는 것이 아닙니다. 정확한 합계는 arrival가 queue를 만드는 동안 dequeue가 없다고 가정합니다.

07 · Evidence 경계

queue는 대략적인 도착 순서만 제공합니다

Writer 백 개는 보통 queue 순서대로 zero-crossing마다 하나씩 처리됩니다. Mixed queue는 다릅니다. R1 → R2 → W1 → R3은 한 번의 READ scan에서 R1, R2, R3를 grant하고 W1은 queue에 남깁니다. 따라서 다음 세 mechanism이 겉보기 service 순서를 바꿀 수 있습니다.

  • Holder re-entry: 기존 holder는 waiter를 지나 nested ownership을 얻을 수 있다.
  • Promotion: blocking promoter는 head에 삽입된다.
  • Reader grouping: READ를 선택한 뒤 scan이 queued writer를 건너 뒤의 READ request도 grant할 수 있습니다.
주장하면 안 되는 것: strict FIFO, starvation freedom, wall-clock 기준 처리 보장, latch-level deadlock freedom. timed sleep이 deadlock guard 역할을 하며 정확한 시간은 revision policy다.
08 · 실패한 wait의 cleanup

Timeout과 interrupt는 grant되지 않은 요청을 제거합니다

timeout은 request를 reset/cancel하고 transaction wait policy에 따라 mapping된 page-latch timeout을 보고한다. interrupt된 waiter는 스스로를 제거한다. 어느 쪽도 page pointer를 반환하거나 caller가 unfix해야 할 holder를 만들지 않는다.

모든 wakeup의 양쪽을 확인해야 한다. waker의 tuple transition과 재개된 thread의 holder allocation이다. Lesson 8의 VS-11 candidate는 정확히 이 post-grant holder-recording seam에 있다. 두 ledger가 일치해야 queue success가 완성된다.

09 · Retrieval 연습

queue 하나의 상태 변화를 정확히 trace합니다

문제

WRITE holder의 fcnt=1이다. queue는 R1 → R2 → W1 → R3이고, 또 다른 non-holder reader가 도착한다. 이어 holder가 unfix하여 0이 된다.

과제: 새 request가 queue 어디에 붙는지, scan이 W1을 건너 어떤 READ request를 grant하는지, debt가 언제 시작되는지, W1이 아직 무엇을 소유하는지 예측하라. 이 결과가 fairness를 증명하지 않는 이유와 W1의 timeout 결과도 덧붙여라.
