심화 역량 · 첫 원리부터 배우는 replacement

하나의 BCB가 차가워지고, victim이 되고, 새 페이지를 받는 과정을 따라갑니다

실제 기본값 수치부터 시작해서 VOID를 쉬운 말로 정의하고 BCB 하나를 끝까지 추적합니다. 공식은 구체적인 흐름을 이해한 다음에 봅니다.

01 · 한 가지 질문

page miss가 났을 때 새 페이지를 담을 frame은 어디서 올까요?

아직 쓰지 않은 BCB/frame pair가 INVALID list에 있으면 CUBRID는 그것을 꺼냅니다. 이때 resident page는 제거하지 않습니다. INVALID가 비었을 때만 LRU의 차가운 쪽에서 안전하게 교체할 resident page를 찾습니다.

Replacement는 고정된 BCB/frame pair 안의 VPID와 bytes를 바꿉니다. 새 pair를 만들거나 BCB A를 다른 frame으로 바꾸지 않습니다.

가장 짧은 흐름은 이렇습니다. INVALID에서 꺼냄 → VOID에서 load → final unfix가 LRU에 배치 → list 압력이 LRU3 쪽으로 내림 → 깨끗하고 사용되지 않는 LRU3 BCB를 detach → 이전 hash identity 제거 → 같은 pair에 새 page를 연결합니다.

02 · pinned 기본값 계산

기본 page size 16 KiB에서 512 MiB는 32,768개의 BCB/frame pair입니다

이 예시는 data_buffer_size = 512M, max_clients = 100, ha_mode = off, 기본 16 KiB I/O page를 전제로 합니다.

512 × 1,024 × 1,024 / 16,384 = 32,768 pages

normal clients 100 + admin 1 + HA 0 + system 1 = MAX_NTRANS 102
minimum buffers = 10 × 102 = 1,020, so configured 32,768 remains

shared S  = max(4, min(102, floor(32,768 / 1,000))) = 32
private P = 102 + VACUUM_MAX_WORKER_COUNT 50 = 152
all LRU descriptors L = S + P = 184

max_clients 자체는 100입니다. 내부 page-buffer 공식은 admin connection 하나와 system transaction 하나도 포함하므로 MAX_NTRANS = 102를 사용합니다. HA를 켜면 reserved connection이 추가될 수 있습니다. 512 MiB는 frame bytes의 크기이며 BCB, mutex, hash, list metadata 메모리는 별도입니다.

시작 직후: 32,768개 BCB가 모두 INVALID에 있습니다. 184개 LRU descriptor는 이미 만들어졌지만 모두 비어 있습니다. “private LRU 152개”가 owner 152명이나 미리 채운 partition 152개를 뜻하지 않습니다.

Verified defaults: system_parameter.c:1169–1189,1569–1582,2329–2342; storage_common.h:91–99; connection_globals.c:84–112,158–245; log_common_impl.h:48–52; page_buffer.c:81–84,1713–1721,5740–5766,13941–13985.

VOID BCB는 모든 management list 밖에 있습니다

04 · BCB 하나의 전체 여정

list 압력이 BCB A를 점진적으로 차갑게 만듭니다

  1. Startup: A는 frame A와 영구적으로 짝지어진 INVALID-list node입니다.
  2. Page P의 첫 miss: pgbuf_get_bcb_from_invalid_list()가 A를 꺼냅니다. A는 VOID가 되고 VPID P와 P의 bytes를 받은 뒤 fix됩니다.
  3. 첫 final unfix: global fcnt가 0이 되면 thread에 private domain이 있을 때 private LRU1 top, 없으면 shared LRU2 middle에 들어갑니다.
  4. 차가워짐: 이후 삽입으로 보호 zone이 threshold를 넘으면 pgbuf_lru_adjust_zones()가 오래된 boundary node를 LRU1 → LRU2 → LRU3로 내립니다. 시간만 흐른다고 A가 이동하지는 않습니다.
  5. Second chance: P가 다시 fix되면 LRU3에서의 final unfix는 보통 A를 LRU1으로 올립니다. A가 victim 후보가 되려면 다시 차가워져야 합니다.
  6. Victim: A가 LRU3에서 깨끗하고 사용되지 않는 상태로 남으면 선택된 scan이 A를 lock하고 protected VOID로 detach할 수 있습니다.
  7. Rebind: pgbuf_victimize_bcb()가 A를 재확인하고 resident hash에서 P를 제거한 뒤 miss path가 같은 A/frame pair에 page Q를 연결합니다.

“Candidate”, “detached”, “victimized”는 서로 다른 순간입니다. LRU3 membership은 A를 검색 가능하게 만듭니다. Detach는 LRU에서 제거하지만 이전 P가 아직 hash에서 보입니다. Victimization이 P의 identity를 제거합니다. 그 후에야 Q가 이 pair를 받을 수 있습니다.

05 · BCB A가 victim이 될까요?

LRU3에 있는 것 외에도 모든 현재 상태가 안전해야 합니다

현재 BCB A현재 결과이유
INVALIDVictimization 없이 바로 할당제거할 이전 resident page가 없습니다.
VOID, LRU1, or LRU2검사하지 않음일반 victim search는 한 LRU3 chain만 따라갑니다.
LRU3 + DIRTY건너뜀변경된 bytes를 먼저 성공적으로 flush해야 합니다.
LRU3 + FLUSHING건너뜀write generation이 아직 in flight입니다.
LRU3 + fcnt > 0 or waiter건너뜀caller가 bytes를 소유하거나 기다리고 있습니다.
LRU3 + non-NO_LATCH sample건너뜀count 0이 latch transition 중에 관찰된 값일 수 있습니다.
LRU3 + direct-victim flag일반 scan에서 건너뜀다른 allocator handoff가 A를 참조합니다.
LRU3 + BCB try-lock failure이번 visit에서 건너뜀LRU mutex를 가진 채 A를 기다리지 않습니다.
깨끗하고 사용되지 않는 LRU3, flag/waiter 없음, mutex와 protected recheck 성공A를 detachBCB mutex를 유지하며 A가 LRU3 → VOID로 바뀝니다.

pgbuf_get_victim_from_lru_list()는 이미 선택된 LRU index 하나를 받습니다. victim_hint 또는 bottom에서 시작해 prev_BCB를 따라 최대 1,000개의 BCB node를 봅니다. 1,000개 list나 모든 transaction을 순회하는 것이 아닙니다. Private threshold demotion D는 이 bounded walk 전에 일어날 수 있습니다.

Verified mechanism: page_buffer.c:221–263,9256–9538,16217–16228.

06 · Private LRU 할당과 activity

Context는 private-LRU index를 빌립니다

pgbuf_assign_private_lru()는 P개의 private descriptor를 모두 순회합니다. 먼저 session이 0인 list 중 BCB가 가장 적은 곳을 고르고, idle list가 없으면 activity가 가장 낮은 곳을 고릅니다. session_cnt[p]를 증가시키고 private-local p를 반환합니다. 실행 thread는 private_lru_index = p를 가지고, BCB는 full index S + p를 저장합니다.

이 scan은 O(P)이며 idle candidate를 동시에 빼앗긴 경우 첫 시도 뒤 최대 다섯 번 retry합니다. 매 fix가 아니라 session/vacuum context가 할당을 받을 때 실행됩니다. 여러 session이 같은 private LRU를 사용할 수 있으며 이 할당은 BCB 소유권을 주지 않습니다. 세션이 해제되면 pgbuf_release_private_lru()가 count를 줄이지만 release는 그 BCB들을 비우거나 이동시키지 않습니다.

“Activity”가 측정하는 값

일반 final unfix에서 pgbuf_bcb_register_hit_for_lru()는 한 BCB가 accepted adjustment epoch 하나에 최대 한 hit만 더하게 합니다. Accepted pgbuf_adjust_quotas()만 adjust_age를 증가시킵니다. Daemon이 100 ms마다 호출해도 early-return 조건 때문에 매번 증가하는 것은 아닙니다.

Accepted pass는 ATOMIC_TAS_32로 각 list의 lru_hits를 가져오면서 0으로 만들고, 초당 hit rate로 바꾼 뒤 10초 구간으로 private activity를 smoothing합니다. Quota는 각 private list의 activity 비율을 따르며 5,000 BCB와 N/2로 제한됩니다. LRU1과 LRU2 threshold는 각각 quota의 5%입니다. 구조적인 작업량은 O(T + L + D)입니다.

Verified mechanism: page_buffer.c:14251–14624,16594–16610,16994–17009,17146–17161; session.c:729–744; server_support.c:2069–2087.

07 · Final-unfix 이동

Private에서 shared로 이동하는 동안 list membership을 하나로 유지합니다

일반 movement는 unfix가 global fcnt를 0으로 바꿀 때만 일어납니다. pgbuf_should_move_private_to_shared()는 unfix하는 thread의 private index가 BCB의 private list와 다르거나, 같은 domain의 page가 hot하면서 충분히 오래된 경우 migration을 요청합니다.

경로는 private LRU → VOID → shared LRU2 middle입니다. Private-list mutex에서 unlink하고 그것을 놓은 뒤 pgbuf_get_shared_lru_index_for_add()로 destination을 고르고 shared-list mutex에서 link합니다. 두 list operation 사이에도 BCB mutex는 계속 유지됩니다.

알고 있는 node의 unlink/link는 O(1)이고 zone demotion D를 더하면 O(1 + D)입니다. Shared destination 선택은 amortized O(1)이며 주기적으로 O(S) balance scan을 합니다. 따라서 migration에는 lock wait를 제외한 periodic O(S + D) case가 있습니다.

Private를 access control로 이해하면 안 됩니다. 다른 transaction도 이 page를 fix할 수 있습니다. 그 transaction의 final unfix에서 domain mismatch가 생기는 것이 BCB가 shared로 이동하는 이유 중 하나입니다.
08 · 안전한 victim이 없을 때

CUBRID는 BCB가 안전해질 때까지 기다립니다

INVALID가 비었고 일반 search도 실패하면 pgbuf_allocate_bcb()는 direct-victim waiter queue에 들어가 flush daemon을 깨울 수 있습니다. Producer가 BCB를 깨끗하게 만든 뒤 예약할 수 있습니다. 소비하기 전에 다른 fix가 접근하면 reservation을 취소하고 allocator가 retry합니다.

DIRTY LRU3 BCB는 WAL-safe page write가 완료된 뒤에야 재사용할 수 있습니다. Write 중에는 FLUSHING이 replacement를 계속 막습니다. Page가 generation G+1로 다시 dirty해지면 그 새 debt가 direct assignment를 막습니다.

모든 allocation path는 assignment, retry, interrupt, timeout, explicit error 중 하나로 끝납니다. ER_PB_ALL_BUFFERS_DIRTY는 fallback error 이름이며 모든 BCB가 실제로 dirty였음을 증명하지 않습니다. Source는 특정 waiter의 wall-clock fairness를 증명하지 않습니다.

Verified mechanism: page_buffer.c:8181–8403,9067–9253,10925–10952,15420–15652,16972–17255.

10 · 이해 확인

지금 BCB A를 재사용할 수 있을까요?

기본 startup에서 시작합니다. Page P를 BCB A에 load하고 final-unfix한 뒤 LRU3까지 demote합니다. 그리고 A가 clean·idle인 경우, A가 DIRTY인 경우, scan 직전에 다른 thread가 A를 fix한 경우를 각각 생각해 보세요. 현재 list/zone, 처음 거부하는 field나 lock, A를 page Q에 rebind하기 전에 필요한 event를 말해 보세요.

Model spine: INVALID는 victimization을 피함 → VOID는 unlinked이지 free라는 뜻이 아님 → LRU3만 search → flags/owners/waiters/try-lock/final recheck가 결정 → VOID detach가 hash removal보다 먼저 → 고정된 pair가 Q를 받음.
