01 · promotion 정의하기

READ holder가 WRITE protection을 요청한다

Latch promotion은 현재 thread가 resident page 하나에 가진 protection을 READ에서 WRITE로 바꾸려는 시도다. page-buffer protocol이 안전하게 upgrade할 수 있을 때 caller가 직접 전체 unfix/refix sequence를 수행하지 않게 하는 것이 목적이다.

Promotion은 transaction-level ownership을 주거나, B-tree search 결과를 마법처럼 보존하거나, 새로운 logical fix를 만들지 않는다. 같은 page-buffer ownership을 더 강한 byte protection 아래 다시 구성할 뿐이다.

02 · 전용 API가 필요한 이유

WRITE fix 하나를 더 받는 것과 promotion은 다른 연산이다

마지막 latch mode는 같을 수 있지만 caller의 debt, wait 위치, failure contract는 다릅니다.

T가 이미 page를 READ로 두 번 hold한다고 하자. pgbuf_fix(..., WRITE, ...) 호출은 “한 번 더 acquire한다”는 뜻입니다. 성공하면 T의 holder count가 2에서 3이 되고 unfix 세 번을 갚아야 합니다. pgbuf_promote_read_latch() 호출은 “이미 가진 ownership을 강화한다”는 뜻입니다. 성공해도 count는 2이며 unfix 두 번만 갚습니다.

Blocking path도 다릅니다. General fix는 old_count + 1을 운반하고 일반 queue tail에 붙습니다. Dedicated promotion은 old_count를 운반하고 queue head의 promoter 위치를 사용하며, caller가 PGBUF_PROMOTE_ONLY_READER 또는 PGBUF_PROMOTE_SHARED_READER를 선택할 수 있게 합니다. 그 PAGE_PTR * 인자는 blocking path가 실패하면 null이 될 수 있어 caller에게 이전 pointer lifetime이 끝났음을 알립니다.

답: general fix 안의 즉시 READ-to-WRITE branch는 또 하나의 acquisition을 위한 구현 경로이지, 기존 ownership을 변환하는 public contract가 아닙니다. 전용 API는 debt와 page state를 보존하고 promotion 전용 wait와 failure 의미를 드러내기 위해 존재합니다.
Pinned-source anomaly: ordinary immediate branch는 global fcnt=1로 만든 다음 기존 holder를 증가시킵니다. Holder count 2에서 시작하면 global count 1과 holder count 3이 남는 것으로 보입니다. 이를 candidate VS-18로 추적하며, 이 branch를 전용 API의 안전한 대체물로 다루면 안 됩니다.

검증된 mechanism: ordinary nested WRITE 처리는 pinned page_buffer.c:6277–6634, dedicated promotion은 2842–3050입니다.

02A · B-tree가 사용하는 이유

READ로 낙관적으로 시작하고 구조 변경이 필요할 때만 WRITE 비용을 낸다

B-tree insertion source가 전략을 직접 설명합니다. Non-leaf traversal은 보통 구조 변경이 없다고 가정하고 READ latch를 사용합니다. Node를 검사한 뒤에야 maximum-key metadata update나 split 필요성을 알 수 있습니다. 그 순간 이미 fix한 같은 page에 WRITE가 필요합니다.

Promotion이 이 전이에 맞습니다. 경합이 없으면 같은 logical fix debt를 유지하고, 경합은 access method가 처리할 수 있는 명시적 outcome으로 만듭니다. Nested WRITE fix는 두 번째 acquisition이므로 unfix 의무를 하나 더 만들고, 기다리면 B-tree가 related page를 잡은 상태에서 ordinary queue path를 사용합니다. 이는 “현재 traversal ownership을 upgrade한다”는 의미가 아닙니다.

B-tree 상황선택한 policySource에서 확인되는 이유
Non-leaf node가 바뀌지 않을 가능성이 큼먼저 READ로 traversal합니다.변경 없는 common path에서 exclusive latch를 피합니다.

따라서 “경합이 없을 때 promotion이 더 싸다”는 말은 일부만 맞습니다. 결정적인 가치는 existing debt와 observation을 보존하고, promotion 전용 refusal/blocking policy를 제공하며, optimistic READ path를 promote할 수 없을 때 B-tree가 안전하게 restart하게 하는 의미에 있습니다.

Caller가 소유한 rationale: insertion design comment와 split path는 pinned btree.c:28307–28393과 28638–28696입니다. Delete/merge path도 같은 optimistic READ, conditional promotion, skip-or-restart policy를 31672–31866에서 적용합니다.

03 · 네 가지 outcome

Blocking success에는 내부 gap이 있지만 보호된 handoff가 있다

기다리는 동안 caller의 holder는 사라지지만, head priority가 successful grant 전에 writer나 victim이 끼어드는 것을 막습니다.

Conditional failureREAD ownership과 debt가 그대로 유지된다.READ로 계속 보호되며 algorithm상 restart 여부는 caller가 결정한다.

04 · Decision rule

“내가 유일한 fixer인가?”가 쉬운 경로를 결정한다

  1. 이 holder의 nested fix_count가 BCB의 global fcnt와 같으면 모든 fix가 이 thread의 것이다. 이미 기다리는 promoter가 없다면 latch mode를 in place로 바꿀 수 있다.
  2. 다른 reader가 있고 caller가 PGBUF_PROMOTE_ONLY_READER를 요청했다면 READ ownership을 release하지 않은 채 conditional failure로 끝난다.
  3. 다른 promoter가 이미 queue 맨 앞에 있으면 새 promotion도 conditional failure다. BCB 하나에는 promoter 하나만 기다릴 수 있다.
  4. 그 밖의 shared-reader 경로에서는 이 thread의 fix를 release하고 holder를 제거하며 promoter를 queue head에 넣고 WRITE를 기다린다.

Verified mechanism: pinned promotion은 page_buffer.c:2842–3050에 있다.

05 · Ownership accounting

저장한 fix count는 이동할 뿐 늘어나지 않는다

caller의 nested-fix count가 2라고 하자. Blocking promotion은 다음과 같이 동작한다.

  1. BCB의 global fcnt에서 2를 뺀다.
  2. 이 thread의 READ holder를 제거한다.
  3. 요청한 fix count 2를 queued promotion request와 함께 저장한다.
  4. grant되면 global tuple에 2를 복구하고 count 2인 새 WRITE holder를 만든다.

promotion 성공 전후에 caller가 갚아야 할 release는 4가 아니라 2다. 내부적으로 wait 중에는 holder가 없지만, 성공한 head handoff는 보호된 같은 page state를 반환한다.

06 · Observation continuity

성공한 promoter가 READ-side observation을 사용할 수 있는 이유

Continuity argument는 구조적입니다.

  • BCB mutex를 잡은 상태에서 promoter를 BCB queue head에 삽입합니다.
  • 남은 active owner는 READ를 hold하므로 page를 합법적으로 mutate할 수 없습니다.
  • Ordinary writer와 새 non-holder reader는 promoter 뒤에 머뭅니다.
  • 마지막 reader의 zero-crossing은 idle/victim gap 없이 head WRITE promoter를 grant합니다.
  • Single-promoter rule은 두 번째 upgrader가 page를 먼저 바꾸는 것을 막습니다.

B-tree는 이 guarantee에 의존합니다. Promotion 전에 node_header를 얻고 need_split과 max_key_len을 계산한 뒤 shared-reader promotion을 호출하며, 성공 후 그 값을 그대로 사용합니다. Promotion이 block했다는 이유만으로 다시 search하지 않습니다.

경계: thread는 promotion 함수 자체가 block된 동안 page에 접근하면 안 됩니다. Blocking이 실패하면 *pgptr_p가 null이 되고 이전 pointer lifetime은 끝납니다. Successful return과 failed return은 의도적으로 다른 contract입니다.
07 · Caller policy

성공하면 계속하고 선택한 failure에서는 restart하거나 skip한다

Module은 성공한 first promoter의 page state를 보존합니다. 따라서 B-tree는 READ-side decision을 사용해 mutation을 계속합니다. PGBUF_PROMOTE_ONLY_READER가 실패하거나 다른 promoter가 이미 있으면 B-tree는 optional merge를 skip할지 WRITE latch traversal로 restart할지 결정합니다.

Holder를 내려놓은 뒤의 hard failure는 다릅니다. Null pointer는 계속 사용하거나 unfix할 page가 없다는 뜻입니다. Caller는 error/restart path로 들어가야 합니다. 성공 뒤 blanket revalidation이 아니라 이 outcome 구분을 audit해야 합니다.

대표 caller evidence: pinned B-tree restart point는 btree.c:28365–28393과 28638–28696이다.

08 · Retrieval 연습

Continuity bridge를 증명한다

문제

Thread T가 nested READ fix 두 개를 hold하고 slot 7을 찾은 뒤 insertion 결정을 계산했다. 다른 reader도 page를 hold한다. T는 WRITE로 blocking promotion을 요청한다.

과제: 두 debt ledger를 trace하고 successful grant 전에 queued writer가 slot 7을 바꿀 수 없는 이유를 증명하라. B-tree가 그 결정을 계속 사용할 수 있는 이유를 설명한 뒤 conditional failure와 hard blocking failure를 대조하라.
