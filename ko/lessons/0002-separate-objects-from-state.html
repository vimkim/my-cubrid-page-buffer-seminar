01 · 추적하기 전에 이름 붙이기

“Page”는 객체 하나가 아닙니다

실선은 resident structure의 관계이고, 점선은 임시 borrowing 또는 debt입니다.

객체무엇인가중요한 lifetime
VPID(volid, pageid)로 이루어진 identity value.resident가 아니어도 존재할 수 있습니다. allocation validity는 page buffer 바깥의 책임입니다.
BCB현재 identity와 control state를 담는 재사용 가능한 pool control block.pool과 수명을 함께하며, 시간에 따라 다른 VPID를 나타낼 수 있습니다.
FrameBCB와 일대일로 짝지어진 page 크기의 bytes.pool과 수명을 함께하며, 내용은 현재 resident-identity generation에 속합니다.
PAGE_PTRcaller가 현재 frame에 접근할 때 보는 주소.matching unfix에서 사용 권한이 끝나는 borrowed view입니다.
Global fcnt모든 thread에 걸쳐 grant된 fix 수를 세는 BCB 단위 count.양수인 debt는 일반적인 frame 재사용을 막습니다.
Thread holderthread별 BCB reference와 중첩된 fix_count.그 thread가 마지막 nested debt를 갚을 때까지 남습니다.

Verified mechanism: holder, atomic-latch fcnt, BCB, paired frame의 정의는 pinned page_buffer.c:460–555에 있습니다. table의 일대일 pairing은 5559–5660에서 확인할 수 있습니다.

02 · 겹쳐 있는 세 lifetime

주소가 그대로여도 그 주소에 부여한 의미는 끝날 수 있습니다

1

Pool lifetime

BCB와 frame storage는 page buffer 초기화부터 종료까지 존재합니다.

2

Resident generation

invalidation이나 안전한 재사용으로 identity가 바뀌기 전까지 BCB/frame은 현재 VPID 하나를 나타냅니다.

3

Borrow lifetime

성공한 fix 하나는 matching unfix까지 debt를 전제로 PAGE_PTR를 한 번 사용할 권한을 줍니다.

!

함정

pointer 주소가 그대로라고 해서 identity가 유지되거나 release 후에도 ownership이 계속된다는 뜻은 아닙니다.

Pointer equality는 page identity가 아니고, storage lifetime은 permission lifetime이 아닙니다.

03 · scalar state 대신 tuple로 보기

서로 독립적인 네 질문을 던집니다

그림의 위치는 coordinate를 나타낼 뿐, 반드시 따라야 하는 순서가 아닙니다.

Axis답하는 질문답할 수 없는 질문
Identity / residency이 BCB/frame이 나타내는 VPID가 있다면 무엇인가?어느 thread가 소유하는지, bytes가 recoverable한지.
Ownership현재 어떤 granted fix가 일반 재사용을 막고 있는가?어떤 latch mode가 내용을 보호하는지, dirty인지.
Concurrency지금 누가 bytes를 읽거나 변경할 수 있는가?transaction visibility, ownership lifetime, durability.
Durability / propagation어느 generation을 propagate해야 하며 recovery boundary는 무엇인가?page가 resident인지, fixed인지, 안전하게 재사용할 수 있는지.
04 · 분류 예제

잘못된 두 shortcut을 드러내는 정상 state

BCB가 여전히 VPID (8, 41)을 나타내고, global fcnt == 0, latch mode는 NO_LATCH, resident generation은 DIRTY라고 가정해 봅시다.

Coordinate분류
Identity / residencyVPID (8, 41)로 resident입니다.
Ownership미지급 fix debt가 없습니다.
Concurrency이 snapshot에는 grant된 content latch가 없습니다.
Durability / propagationDIRTY입니다. 이 resident generation에는 아직 page-image propagation이 필요합니다.
버려야 할 두 결론: VPID가 여전히 resident이므로 fcnt == 0은 “evicted”를 뜻하지 않습니다. 또한 일반 재사용에는 dirty/flush, waiter, replacement-zone, protected revalidation 확인이 남아 있으므로 “eligible victim”이라는 뜻도 아닙니다.

이제 “page state”라는 말이 왜 지나치게 모호한지 알 수 있습니다. 유용한 설명은 네 coordinate로 된 tuple입니다.

05 · 성공한 fix에 적용하기

성공이 보장하는 것과 보장하지 못하는 것

정상 READ fix가 성공하면 resident identity mapping, 이 acquisition을 포함한 양수의 fix debt, grant된 READ page latch, borrowed pointer lifetime이 성립합니다. 성공만으로는 clean/dirty, durable 여부, record 존재, 올바른 transaction locking, caller correctness를 보장하지 않습니다.

matching unfix 후: 이 acquisition의 debt와 pointer 사용 lifetime은 끝납니다. BCB/frame은 계속 resident일 수 있고, 다른 fix 때문에 global fcnt가 양수로 남을 수 있습니다. ownership을 release했다고 durability state가 바뀌지도 않습니다.

Interface contract와 Verified mechanism: 정상 successful-fix postcondition과 matching release는 canonical Core 설명에서 연결합니다. pinned path는 page_buffer.c:2260–2685, 6277–6634, 3062–3201입니다.
