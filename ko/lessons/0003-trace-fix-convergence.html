Core capability · normal acquisition

hit와 miss가 하나의 fix contract로 모이는 과정 추적하기

이 lesson을 마치면 hit와 miss의 준비 과정이 어떻게 다른지, 어느 지점부터 identity를 신뢰할 수 있는지, 두 경로가 왜 caller에게 같은 ownership contract를 제공하는지 설명할 수 있습니다.

01 · 서로 독립적인 세 input

caller가 무엇을 알고 무엇을 원하는지에서 시작합니다

Choice답하는 질문중요한 결과
PAGE_FETCH_MODEcaller가 allocation 또는 residency에 관해 무엇을 아는가?OLD_PAGE는 기존 bytes를 materialize할 수 있고, NEW_PAGE는 기존 bytes를 읽지 않고 초기화하며, OLD_PAGE_IF_IN_BUFFER는 materialization을 하지 않습니다.
PGBUF_LATCH_MODEborrower가 resident bytes에 어떤 방식으로 접근할 수 있는가?READ는 compatible reader를 허용하고, WRITE는 exclusive content access를 요청합니다.
PGBUF_LATCH_CONDITIONincompatible request가 기다릴 수 있는가?Conditional은 wait path에 들어가지 않고 거절하며, unconditional은 wait path를 허용합니다.
Debt rule: 예상된 non-acquisition은 debt를 만들지 않습니다. OLD_PAGE_IF_IN_BUFFER miss나 conditional conflict는 matching unfix 의무 없이 NULL을 반환할 수 있습니다. NULL을 하나의 보편적 error로 해석하지 말고 caller가 선택한 protocol에 맞춰 해석하세요.

Interface contract: 세 choice type은 pinned page_buffer.h:172–203에서 분리되어 있습니다. Validation, zero-wait conversion, resident-only miss는 page_buffer.c:2260–2413에 있습니다.

02 · 준비는 달라도 성공의 의미는 같습니다

두 path가 하나의 postcondition으로 모입니다

여기서는 일반 mutex-protected path만 보여 줍니다. lock-free READ path는 Advanced에서 이어집니다.

H

Resident hit

hash candidate를 찾고 BCB를 보호한 뒤, 여전히 요청한 VPID를 나타내는지 다시 확인합니다.

M

Cold miss

VPID별로 준비 과정을 serialize하고 provisional BCB/frame을 확보한 뒤 bytes를 읽거나 초기화합니다.

C

Converge

보호된 상태에서 BCB identity와 page-header identity가 일치하는지 확인합니다.

G

Grant

요청한 latch를 grant하고 global 및 thread debt를 갱신한 뒤 borrowed pointer를 반환합니다.

page가 hit였다고 더 약한 contract를 받거나, miss였다고 더 강한 contract를 받는 일은 없습니다.

03 · Protected hit

hash candidate는 관찰 결과이지 증명이 아닙니다

hash chain에서 vpid가 일치해 보이는 BCB를 찾을 수 있습니다. 하지만 첫 비교는 BCB mutex로 보호되지 않습니다. thread가 mutex를 얻기 전에 victimizer가 BCB를 unlink하고, 다른 loader가 재사용 가능한 slot을 다른 VPID에 rebind할 수 있습니다.

그래서 hit path는 BCB를 lock한 뒤 VPID를 다시 비교합니다. 값이 바뀌었다면 candidate를 release하고 다시 찾습니다. table이 pool lifetime 동안 유지되므로 BCB storage 자체는 안전하게 살펴볼 수 있습니다. 바뀔 수 있는 것은 그 slot이 나타내는 identity입니다.

Stale-observation boundary: 보호된 VPID recheck를 거치면 보호되지 않은 candidate 관찰이 이 path에서 신뢰할 수 있는 resident-identity evidence로 바뀝니다.

Verified mechanism: protected hash-candidate recheck는 pinned page_buffer.c:7594–7722에 있습니다. Pool-lifetime BCB allocation은 5559–5660에서 확인할 수 있습니다.

04 · Serialized cold miss

waiter는 재시도하며 provisional BCB를 그대로 넘겨받지 않습니다

하나의 hash-anchor mutex가 in-flight load-lock chain과 resident BCB chain을 보호합니다.

  1. Thread A가 miss한 뒤 VPID load-lock record를 먼저 등록해 load owner가 됩니다.
  2. 같은 VPID에서 miss한 Thread B는 A의 record를 찾아 자신을 waiter로 연결하고 잠듭니다.
  3. A는 재사용 가능한 BCB/frame을 얻어 VPID를 지정하고, 이 provisional object를 아직 publish하지 않습니다.
  4. OLD_PAGE라면 A는 DWB를 확인한 다음 data volume을 봅니다. NEW_PAGE라면 frame을 초기화합니다.
  5. identity를 확인하고 자신의 ownership을 grant받은 뒤 A가 BCB를 publish하고 load lock을 release합니다.
  6. B는 깨어나 lookup을 재시도하고 resident hit를 찾은 뒤 별도의 grant와 debt를 얻습니다.
Evidence boundary: 이 protocol은 resident-identity 준비를 serialize합니다. “physical disk I/O가 정확히 한 번 발생한다”는 증거는 아닙니다. DWB, filesystem, OS cache, device 동작, error, retry는 별도 layer입니다.

Verified mechanism: load owner/waiter 등록과 retry는 page_buffer.c:7981–8178에 있습니다. provisional BCB allocation과 DWB/data-volume 또는 NEW_PAGE materialization은 pinned 8392–8634에 있습니다.

05 · 세 check, 세 gap

identity validation을 하나의 check로 뭉뚱그리지 마세요

각 check는 서로 다른 보호 아래 서로 다른 관찰을 검증합니다.

Check닫는 gap실패의 의미
BCB mutex 아래에서 hit candidate VPID 확인Unprotected hash observation → protected BCB재사용 slot이 rebind되었습니다. chain을 다시 찾습니다.
BCB VPID와 page-header identity 비교Prepared control state → prepared bytescontrol block과 page image가 불일치합니다. borrowed pointer를 반환하지 않습니다.
Release-time identity assertionBorrowed-use period → global decrementdebug build에서 global debt를 갚기 전에 caller/pointer identity 위반을 감지합니다.

세 번째 check는 일반 mutex-based unfix path의 debug assertion입니다. caller의 의무를 문서화하지만, release build에는 이 assertion으로 인한 runtime guard가 없습니다.

06 · 공통 contract 명시하기

네 가지 사실이 acquisition 성공을 이룹니다

  1. 요청한 VPID가 BCB/frame에 resident입니다.
  2. 요청한 page latch가 grant되었습니다.
  3. Global fcnt와 현재 thread의 holder가 이 acquisition을 기록합니다.
  4. 반환된 PAGE_PTR는 matching unfix 하나가 이 debt를 갚을 때까지 빌린 것입니다.

Publication은 cold miss 준비 과정의 일부입니다. 어느 준비 path든 성공하고 나면 caller는 위 contract를 기준으로 추론합니다.

여기서 증명하지 않는 것: waiter fairness, lock-free READ memory ordering, 모든 exceptional cleanup path, physical-device I/O count, caller logical correctness, durability.
07 · Retrieval practice

contract의 의미는 바꾸지 않고 차이를 설명합니다

문제

“일반 resident hit와 cold miss는 무엇이 다르고, 어느 postcondition이 같으며, miss protocol이 physical disk read가 정확히 한 번임을 증명하지 못하는 이유는 무엇인가요?”

권장 답변 구조: caller intent → hit protection 또는 miss serialization/materialization → 공통 identity confirmation → latch와 두 ledger → borrowed return → evidence 한계.

할 일: waiter가 owner의 provisional BCB를 받는 대신 retry하는 이유를 설명하고, hit path의 stale-observation boundary를 말하세요.

답을 chat에 붙여 넣으세요. mastery를 기록하기 전에 path 순서, ownership, identity evidence, 과도한 claim이 없는지 확인합니다.
