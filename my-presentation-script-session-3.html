01 · CONNECTION

앞선 두 세션에서 오늘로

전용 발표 장: 없는 페이지를 읽으려면 안전한 메모리 자리가 필요하다 · 기다리는 요청 스레드가 변경 보존을 맡을 수도 있다 · 요청을 실제로 막는 원인을 찾기.

페이지는 식별자를 가진 데이터 단위이고 frame은 페이지 하나를 담는 메모리 공간입니다. BCB는 frame의 현재 페이지와 사용 상태를 관리합니다. Fix는 그 frame을 다른 페이지로 바꾸지 못하게 사용을 유지하는 의무이며 unfix로 반납합니다. Dirty는 아직 전달해야 할 변경이 있다는 상태입니다. Hot set은 반복해서 읽는 페이지들의 모음입니다. 큰 스캔이 다른 페이지들을 읽는 동안 writer가 변경을 남겼고 풀의 모든 frame이 차 있다고 하겠습니다. 이때 아직 메모리에 없는 페이지 Q의 요청이 도착합니다. P는 이미 메모리에 있고 현재 사용자가 없지만 변경을 기록해야 하는 dirty 페이지입니다.

이 워크로드를 세미나 전체의 연결 질문으로 사용합니다. 실제 실행 기록은 아닙니다. 각 사례는 명시한 시작 상태에서 독립적으로 시작합니다. 같은 글자가 다른 사례에서 페이지, thread, 정책 영역을 뜻하면 그때 새로 정의합니다. 사용을 끝냈다는 사실과 변경을 보존했다는 사실을 나누어 보며 누가 재사용 가능한 frame을 준비하는지 살펴보겠습니다.

화면: 요청한 페이지는 보호된 접근 권한을 얻어야 사용할 수 있다. 요청 → fix → 사용 → unfix까지만 먼저 짚습니다.

앞선 두 세션에서는 페이지 버퍼가 왜 필요한지, 페이지 ID와 메모리 frame이 어떻게 다른지 살펴봤습니다. BCB가 무엇을 기록하고, private/shared LRU가 메모리에 올라온 페이지를 어떻게 관리하는지도 알아봤습니다. 오늘은 그 모델을 완성하겠습니다. 빈 frame이 없을 때 다음 요청을 누가 진행시키는지, PostgreSQL은 같은 문제를 어떻게 푸는지 살펴보겠습니다.

먼저 앞서 배운 내용을 하나씩 떠올려 보겠습니다. 페이지를 unfix해도 메모리에는 남아 있을 수 있습니다. 모든 사용자가 fix를 반납해도 dirty 상태는 남을 수 있습니다. LRU3는 교체 정책이 후보를 찾는 차가운 영역입니다. 그곳에 있다는 이유만으로 바로 덮어쓸 수는 없습니다. 로그가 필요한 페이지에서는 관련 로그를 페이지보다 먼저 영속화하는 WAL 순서를 지켜야 합니다. 어느 페이지인지, 남은 사용이 있는지, 바이트를 어떻게 보호하는지, 아직 보존할 변경이 무엇인지를 따로 봅니다.

먼저 질문: 버퍼 pool에 빈 frame이 없습니다. Cold 페이지 P는 아무도 fix하고 있지 않지만 dirty 상태입니다. 새 페이지 Q를 요청하면 어떤 일을 끝내야 P의 frame을 재사용할 수 있을까요?

예측 후 발표자 답 보기

먼저 필요한 로그 순서를 지키고, 해당 write 경로를 통해 P의 변경을 보존해야 합니다. 그 뒤에도 P가 다시 fix되거나 dirty 상태가 되었는지, 정책상 재사용 후보로 남아 있는지 확인해야 합니다. “cold 상태다”, “남은 fix가 없다”, “한 번 썼다”는 서로 다른 사실입니다.

이 질문을 중심으로 daemon의 역할을 살펴보겠습니다. 그 전에 dirty 페이지를 쓴다는 말이 어느 시점의 바이트를 뜻하는지부터 정리하겠습니다.

예측 질문: 이 승인 규칙을 검토할 수 있는 가장 작은 반례는 어떤 실행 순서일까요?

02 · FLUSH BRIDGE

한 페이지, 두 세대

전용 발표 장: 가득 찬 풀에서 변경된 페이지를 안전하게 기록하려면? · 사본 없는 대안은 I/O가 끝날 때까지 writer를 배제한다 · 이전 완료 전후에 이후 dirty 신호가 남는지 관찰한다.

독립적인 이미지 전달 사례로 다시 시작합니다. Q는 아직 메모리에 없는 요청 페이지이고 P는 frame에 있는 dirty 페이지입니다. Flusher는 P의 변경을 저장 경로에 전달하는 주체입니다. G는 확보한 P의 사본, G+1은 그 뒤 메모리에 생긴 변경을 가리키는 설명용 이름입니다. 실제 저장된 세대 번호가 아닙니다. Flusher가 G를 전달하는 동안 writer가 G+1을 만들 수 있다는 조건에서 무엇을 정리해야 하는지 따져봅니다.

화면 순서: Flush는 안정된 페이지 사본을 저장소 쪽으로 보낸다 → 고정된 사본이 있으면 이후 writer는 계속 진행할 수 있다 → 복구 로그가 페이지 이미지보다 먼저 살아남아야 한다 → 보호를 풀기 전에 바이트와 로그 관리 정보를 함께 확보한다 → 안정된 사본과 DWB가 해결하는 문제는 다르다 → 이전 완료 처리는 새 작업을 계속 드러내야 한다.

저장된 페이지의 값이 10이라고 하겠습니다. 메모리에서 11로 바꾸면 저장된 이미지와 메모리의 이미지가 달라집니다. DIRTY는 메모리의 이미지에 아직 저장 경로로 전달해야 할 변경이 있다는 표시입니다. Unfix로 사용을 끝내더라도 그 변경을 보존할 의무는 남습니다.

WAL의 핵심은 순서입니다. 로그가 필요한 영구 페이지에서는 변경을 설명하는 로그가 해당 데이터 페이지보다 먼저 영속화되어야 합니다. 페이지 LSA는 그 이미지가 어느 로그 위치까지의 변경을 반영하는지 나타냅니다. 로그를 먼저 보존해야 페이지 이미지를 안전하게 전달할 수 있습니다. Commit, 페이지 write, unfix는 각각 완료하는 일이 다릅니다.

Flush하는 동안에도 다른 요청은 진행해야 합니다. 안정된 이미지 11을 사본으로 확보하고 전달하는 사이, 메모리의 페이지는 12로 다시 바뀔 수 있습니다. 이때 사본 11의 세대를 G, 이후 변경의 세대를 G+1이라고 부르겠습니다. 여기서 세대, 즉 generation은 설명을 위한 이름입니다. 실제로 저장된 세대 번호나 카운터를 뜻하지는 않습니다.

사건메모리 값전달할 사본남아 있는 작업
10 → 11 변경11아직 없음11의 dirty 변경 보존
안정된 사본 확보11G = 11G의 flush 진행
다른 사용자가 12로 변경12G = 11G 진행 + G+1의 dirty 변경 보존

DWB를 쓰는 경로에서는 이미지를 DWB가 받아들인 시점과 원래 데이터 볼륨인 home volume에 실제로 쓰는 시점도 구분해야 합니다. DWB는 페이지를 쓰다가 이미지가 부분적으로만 남는 문제를 다루는 별도의 write 경로입니다. Page-flush가 성공을 반환했더라도 모든 저장 단계의 영속화가 끝났다는 뜻은 아닙니다.

이제 처음 질문을 조금 더 정확하게 바꿔 보겠습니다. 누가 G의 전달을 시작하고, 누가 G의 완료 상태를 정리할까요? 그리고 현재 메모리의 페이지가 재사용 가능한 상태인지 누가 검사할까요?

Q03 · 값이 다시 같아진 페이지

구성한 시작 상태: G의 사본에는 값 40과 페이지 LSA 120이 들어 있습니다. G가 진행되는 동안 writer가 같은 필드를 41로 바꾼 뒤 다시 40으로 바꿨고, 두 변경을 기록해 현재 페이지 LSA는 180입니다. 현재 DIRTY는 설정돼 있습니다. 이제 G의 제출이 성공했습니다.

예측 질문: 값이 40으로 같다는 관찰은 현재 DIRTY를 정리할 근거로 어디까지 사용할 수 있을까요?

값이 같다는 사실만으로 DIRTY를 지울 수 없습니다. G는 120까지의 이력을 담지만 현재 로그 작업은 180까지입니다. 완료 처리는 이전 FLUSHING만 해제하고 새로운 DIRTY와 oldest-unflush 하한은 남깁니다. 한 필드의 값 비교는 세대 완료의 근거가 되지 않습니다.

첫 화면에서는 왜 사본이 필요한지 조건부터 정합니다. 느린 write 중에도 writer를 허용하려면 제출할 바이트와 LSA가 함께 고정돼야 합니다. BCB mutex만으로 다른 WRITE owner를 막는 것은 아닙니다. Caller가 먼저 적합한 소유권과 latch 조건을 확보해야 합니다.

제거 화면은 같은 시작 상태를 세 경로로 나눕니다. 사본과 WAL은 유지하되 새 dirty 의무를 구분하지 않으면 G 완료가 G+1 작업까지 지울 수 있습니다. 반면 write 내내 writer를 배제하는 대안은 안전할 수 있습니다. 대신 저장장치 지연이 writer의 대기로 옮겨갑니다. 다음 단계에서 바뀐 필드와 결과를 확인한 뒤 초기화합니다.

사본도 WAL도 torn page의 완전한 해결책은 아닙니다. DWB는 staging write와 동기화를 home write보다 먼저 수행하고 유효한 사본을 복구에 사용합니다. 수락만으로 그 단계가 끝난 것은 아닙니다. 두 사본의 동시 손실과 무효한 storage sync는 별도 경계입니다. D25에서는 값이 같아도 header와 로그 이력, dirty 의무가 같지 않다는 점을 방어합니다.

대안의 전이: 사본 없는 대안은 I/O가 끝날 때까지 writer를 배제한다.

바이트 변경을 배제하고 일치하는 페이지 LSA를 기록합니다. 변경 배제를 유지하며 WAL을 force하고 바뀌지 않은 바이트를 제출합니다. 성공하면 해당 이미지의 의무만 정리한 뒤 다음 writer를 허용합니다. 오류이면 DIRTY와 oldest 의무를 보존하고 임시 상태와 배제를 정리합니다.

설명용 대안입니다. 별도 이미지를 줄이는 대신 로그와 저장장치 지연 내내 writer를 배제합니다. Immutable 버전 이미지는 버전 해제 protocol을 추가하는 다른 대안입니다. 어느 쪽도 저장·복구 protocol 없이 torn write를 해결하지는 못합니다.

03 · FOUR LOOPS

네 daemon은 서로 다른 일을 한다

전용 발표 장: 요청한 페이지를 담을 자리에 변경 내용이 남아 있다 · 단일 스케줄러는 I/O 중에도 다른 일을 실행할 수 있어야 한다 · 사라진 깨우기와 남아 있는 작업을 따로 기록한다.

새 페이지를 읽으려는데 풀의 모든 frame이 사용 중이라고 하겠습니다. Frame은 페이지 하나를 담는 메모리 공간이고, BCB는 그 공간의 현재 페이지와 사용 상태를 관리하는 구조입니다. S3는 읽으려는 페이지이며 아직 메모리에 없습니다. S4는 메모리에 있지만 현재 사용자가 없고, 변경 내용이 아직 기록되지 않은 dirty 후보입니다. S4를 안전하게 기록하는 것은 frame 재사용을 준비하는 일입니다. 기록 뒤에도 현재 사용 상태를 검사해야 합니다.

준비 작업을 요청 thread가 모두 수행하면 S3를 읽는 요청이 S4의 WAL·write·완료 정리를 기다릴 수 있습니다. WAL은 페이지보다 먼저 영속화해야 하는 변경 로그입니다. 네 daemon은 이미지 전달, BCB 완료 정리, 보존 정책 조정, write 이후 속도 조절을 따로 맡습니다. 이 역할 분리는 구현 정책입니다. 역할을 합치는 대안에서도 각각의 의무와 공유 상태 검사는 남습니다.

화면: 네 작업은 서로 다른 네 종류의 상태를 바꾼다 → 각 스레드는 태스크를 실행한 뒤 대기 시간을 정한다 → 복구는 작업을 허용하고 종료는 작업이 끝나기를 기다린다.

Daemon은 백그라운드에서 자신이 맡은 작업을 실행하고, 기다렸다가 다시 실행하는 주체입니다. CUBRID 서버의 페이지 버퍼 daemon은 공통 thread manager를 이용합니다. 다만 같은 작업을 네 worker에게 나누는 구조는 아닙니다. 각자 맡은 작업과 대기 방식, 참조하는 공유 상태가 다릅니다.

이 숫자가 정확한 실행 빈도를 보장하지는 않습니다. 공통 daemon 구현은 작업을 한 번 실행한 뒤 기다립니다. 정해진 주기에서 직전 작업의 실행 시간을 빼서 대기 시간을 계산합니다. 여기에 스케줄러 지연이나 I/O 시간이 더해질 수도 있습니다. 타이머가 끝났다는 사실과 실제로 유용한 일을 했다는 사실도 구분해야 합니다.

Wakeup에도 경계가 있습니다. 이 waiter는 현재 SLEEPING 상태일 때만 깨웁니다. 이미 RUNNING이면 다음 실행을 위해 wakeup 횟수를 쌓아 두지 않습니다. 따라서 작업은 공유 상태에 기록된 frame 부족 조건이나 queue를 보고 실제로 할 일을 판단해야 합니다. Wakeup만 기다리는 설정이라면 새 작업을 알리는 신호가 언제 발생하는지도 따라봐야 합니다.

생성과 작업 허용을 나누어 설명하기

먼저 pool 초기화가 BCB, LRU, quota·monitor 배열과 server queue를 마련합니다. xboot_restart_server()는 DWB에 남은 페이지를 복구한 뒤 pgbuf_daemons_init()을 호출합니다. 이 함수는 maintenance → page-flush → post-flush → flush-control 순서로 생성을 시도합니다. 이는 생성 순서입니다. 페이지가 네 역할을 차례로 통과한다는 뜻은 아닙니다.

그다음 DWB helper 생성과 log 초기화·복구, boot_after_copydb()를 거쳐 boot gate를 엽니다. Gate는 각 task가 공유 상태에 대한 본 작업을 시작해도 되는지를 나타내는 조건입니다. Thread가 존재해도 닫힌 gate를 보면 바로 반환합니다. Gate를 여는 동작 자체는 wake를 보내지 않습니다. 이후 timer나 작업 알림을 받고 다시 실행할 때 열린 gate를 확인합니다.

공통 manager는 관리할 thread entry를 예약합니다. 새 thread 안에서 실행 context를 만들고 TT_DAEMON 종류와 LOG_SYSTEM_TRAN_INDEX를 지정하며 error context도 설정합니다. 정상 구성에서 최대 네 daemon이 생깁니다. 항상 네 개가 성공한다고 가정하면 안 됩니다. Pool의 반환형 할당 오류는 pgbuf_finalize()로 정리하지만, manager가 entry 부족으로 NULL을 반환하는 경로를 역할 초기화 함수가 별도로 처리하거나 소유되지 않은 task를 retire하지는 않습니다. 이 생성 지점에는 할당·thread 생성 예외의 지역 복구 wrapper도 없습니다. 이는 소스에 보이는 정리 책임의 경계이며 운영에서 해당 실패가 발생했다는 관찰은 아닙니다. Control 초기화 실패는 07장에서 따로 설명합니다.

종료에서 누가 언제 정리하는가

종료 caller는 stop을 표시하고 sleeper를 깨운 뒤 join()으로 thread 종료를 기다립니다. Worker는 실행 중 task에서 돌아와 loop를 빠져나간 뒤 실행 context를 정리하고 task의 retire()를 호출합니다. Control의 bucket 정리도 이때 끝납니다. Worker가 종료해야 join이 반환하고 manager가 daemon을 삭제하며 포인터를 비웁니다. 따라서 join 반환은 task 정리까지 끝났음을 확인하는 시점입니다.

그동안 BCB와 queue 등 필요한 저장 공간을 유지해야 합니다. Stop은 진행 중 I/O를 취소하지 않으며 join 완료 시간의 상한도 아닙니다. 정상 종료는 이 daemon group을 멈춘 뒤 log_final()과 DWB·pool 정리를 진행합니다. Restart 오류 경로는 gate를 먼저 닫고 page-buffer와 DWB daemon group을 정리한 뒤 나머지 의존 자원을 해제합니다. Stand-alone 빌드에는 이 네 daemon group이 없습니다. 필요한 page-flush 작업은 관련 caller 경로에서 동기적으로 수행합니다.

Q05 · 실행 알림의 순서

구성한 시작 상태: Page-flush의 타이머 주기는 0입니다. Recovery 중 실행된 작업은 닫힌 boot gate를 보고 반환했습니다. 다음 대기에 들어가기 직전 waiter는 아직 RUNNING입니다. 이때 gate가 열리고 다른 thread가 wakeup을 호출한 뒤 daemon이 대기에 들어갑니다. 이후 신호는 아직 기록되지 않았습니다.

설계 논증 이어가기

확장 화면 순서: 요청한 페이지를 담을 자리에 변경 내용이 남아 있다 (EN) → 요청한 페이지를 담을 자리에 변경 내용이 남아 있다 (EN) → 큐 대신 깨우기만 쓰면 미처리 작업을 잃을 수 있다 (EN) → 요청한 페이지를 담을 자리에 변경 내용이 남아 있다 (EN) → 공유 저장 영역은 접근하는 모든 워커보다 오래 살아야 한다 (EN) → D26 · 50 ms 목표 주기로 기록 완료 횟수를 셀 수는 없다 (EN)

네 역할을 하나의 pipeline으로 보지 않겠습니다. Page-flush는 이미지 공급, post-flush는 CPU 정리와 조건부 offer, maintenance는 retention 조정, control은 write 이후 pacing 예산을 담당합니다. 역할을 foreground나 단일 worker로 옮기는 대안도 가능하지만 I/O가 다른 책임을 지연시키지 않는 실행 구조가 필요합니다.

Wake가 저장된 사건이라고 가정하면 RUNNING 중 알림에서 반례가 생깁니다. 공유 queue는 작업을 보존하지만 그 자체로 다음 실행 시각을 보장하지 않습니다. 작업 상태와 waiter 상태의 조건이 다릅니다. Timer가 실행 기회를 주더라도 gate와 scheduling, lock과 I/O 조건은 남습니다.

종료에서 stop은 취소도 join도 아닙니다. 실행 중 task가 반환하고 sleeper가 깨어나 thread를 join한 뒤 공유 자원을 해제해야 합니다. D26의 50 ms는 목표 주기이지 writer 완료 기한이 아닙니다.

대안의 전이: 단일 스케줄러는 I/O 중에도 다른 일을 실행할 수 있어야 한다.

각 역할에 일시적인 wake bit 대신 보존되는 pending 상태를 둡니다. 준비된 작업을 고르고 느린 I/O 전에 continuation을 보존합니다. I/O 완료를 처리하면서 quota와 pacing 작업도 진행시킵니다. 종료 시 producer를 닫고 규칙에 따라 continuation을 완료하거나 취소한 뒤 join하고 공유 상태를 해제합니다.

설명용 대안입니다. Foreground 처리는 지연을 caller로 옮기며 blocking 통합 worker는 네 지연을 연결합니다. Nonblocking 대안에는 queue, continuation, 취소 소유권, scheduling 정책이 추가됩니다. I/O와 공정성 가정 없이 처리 시간 상한은 나오지 않습니다.

관측과 반증: 사라진 깨우기와 남아 있는 작업을 따로 기록한다.

기존 framework 통계로 loop·wake·sleep을 찾습니다. 추가 시각 기록으로 작업 공개, waiter 상태, 작업 진입, 조건을 연결합니다. Wake 횟수만으로는 부족합니다. 이 전제에서 pending 작업을 다시 발견할 경로가 기록되지 않으면 제안한 진행 논증에 반례가 됩니다. Scheduler 멈춤은 timing에 영향을 주며 유한 관찰만으로 영구 starvation을 증명하지는 못합니다.

관측 전에 collection과 activation을 확인하기

다음은 실행 결과가 아니라 실험 제안입니다. extended_statistics_activation의 기본 mask 15에는 page-buffer victimization bit 16과 daemon bit 64가 없습니다. 이 mask는 초기화 때 cache하고 일반 SQL 변경은 거절하므로 필요한 bit는 시작 설정에 포함해야 합니다. 통계 수집도 활성 상태여야 합니다. Hidden 시작 옵션 stats_on은 기본 false이며 always-watching 수집을 켜는 한 방법입니다. 적절한 runtime 수집 utility·API를 쓰는 별도 방법도 있습니다. 이 설정들이 후보별 사건 시각을 새로 기록해 주지는 않습니다. 작업 공개, gate, waiter 상태, predicate, task 진입 시각의 probe는 추가 구현이 필요한 제안이며 observer가 timing을 바꿀 수 있습니다. 유한 기록으로 latency 상한이나 영구 starvation을 증명하지 않습니다.

04 · CREATE CLEAN SUPPLY

Page-flush: 기억한 후보를 다시 검사한다

전용 발표 장: 기억한 후보를 왜 다시 검사해야 할까? · 예약으로 보호 공백의 경쟁을 막을 수 있을까? · 오래된 후보와 지연된 쓰기를 어떤 관측으로 구분할까?.

이 장은 독립적인 후보 수집 사례로 시작합니다. P는 현재 사용자가 없고 dirty인 페이지입니다. Page-flush는 LRU list lock을 잡고 P의 BCB 포인터와 VPID를 기억합니다. VPID는 논리 페이지의 식별자입니다. Lock을 놓고 나중에 BCB를 잠그는 사이에 다른 thread가 실행할 수 있습니다. BCB의 주소가 그대로여도 현재 페이지와 사용·dirty 상태는 바뀔 수 있습니다. 앞선 관찰이 지금의 작업을 허가하지는 않습니다.

화면: 선택한 사본은 어떤 호출을 거쳐 제출될까? → Worker는 언제 필요한 작업을 찾을까? → 후보 관찰은 어떻게 flush 결정으로 이어질까?.

새 페이지를 요청한 allocator가 invalid frame도, 바로 쓸 수 있는 clean victim도 찾지 못했다고 하겠습니다. Page-flush는 cold dirty 페이지를 골라 clean 후보가 생기도록 돕습니다. 타이머가 끝날 때마다 모든 dirty 페이지를 쓰는 방식은 아닙니다. 할당을 기다리는 요청이 있는지, hit ratio가 낮은지 보고 계속할 일을 판단합니다. Boot gate를 통과한 실행에서 daemon이 wakeup으로 깨어났다고 판단하면, 후보 flush를 최소 한 번 호출합니다. 이는 소스에서 확인한 실행 조건입니다.

설정 변경은 어느 실행부터 보이는가

고정 리비전에서 등록된 이름은 page_flush_interval입니다. 기본값은 1,000 ms이고 0부터 INT_MAX ms까지 받습니다. 이전 이름 page_flush_interval_in_msecs는 deprecated alias입니다. 내부 PRM 식별자의 이름을 그대로 설정 이름으로 쓰면 안 됩니다. DBA는 SET SYSTEM PARAMETERS 'page_flush_interval=1000ms'로 서버 전체의 실행 중 registry 값을 바꿀 수 있습니다. 이 SQL은 cubrid.conf를 저장하지 않습니다. 재시작 뒤에도 유지하려면 설정 파일을 별도로 수정해야 합니다.

Looper는 다음 pause에서 새 interval을 읽습니다. 0은 daemon 제거가 아니라 timeout 없는 wake-only 대기입니다. 이미 무한 대기 중일 때 0을 양수로 바꾸어도 setter가 daemon을 깨우지는 않습니다. 별도의 작업 wake 등으로 다음 pause에 도달해야 새 값이 쓰입니다. 반복해서 읽는다는 사실, 변경 권한이 있다는 사실, 이미 대기 중인 실행을 즉시 깨운다는 사실을 구분합니다.

설정과 분류기본값·허용 범위DBA online 변경 뒤 효과

Hidden 설정도 이 pin에서는 변경 허용 flag가 있지만 공개 운영 계약과 같지는 않습니다. Interval 역시 nonhidden 등록을 확인했지만 로컬 매뉴얼에는 설명이 없습니다. 매뉴얼은 11.4, engine pin은 11.5.0입니다. 이름·변경 허용·적용 지점은 고정 소스로 확인한 내용입니다. 이 발표에서 실제 서버의 설정 변경이나 지연 측정은 하지 않았습니다.

핵심 호출은 pgbuf_flush_victim_candidates()입니다. 먼저 LRU mutex를 잡은 상태에서 cold 후보의 BCB 포인터와 VPID를 기억합니다. 그다음 list lock을 놓고 각 BCB를 검사합니다. 그 사이 다른 thread가 실행할 수 있으므로, BCB mutex를 잡은 뒤 상태를 다시 확인해야 합니다. 같은 VPID인지, 현재 dirty인지, 이미 flushing 중인지, 여전히 cold이고 남은 fix가 없는지를 봅니다.

페이지 이미지에 필요한 WAL이 아직 영속화되지 않았다면 그 후보를 당장 제출할 수 없습니다. Log-flush를 깨우거나, frame 부족을 처리하는 경로에서 필요한 로그 작업을 마친 뒤 다시 시도합니다. 제출 가능한 이미지의 안정된 사본을 만들고 공통 flush 경로로 전달합니다. 화면의 짧은 소스 추적은 이웃 페이지 묶음과 DWB를 사용하지 않는 분기 하나를 보여줍니다. 공통 helper 안에서도 WAL 처리와 페이지 write는 정해진 순서로 진행됩니다.

이미지 제출에 성공한 뒤에는 BCB의 완료 처리가 남습니다. 같은 thread가 처리할 수도 있고, post-flush에 넘길 수도 있습니다. 다음으로 그 선택 조건을 보겠습니다.

한 번의 실행이 멈추는 조건

탐색 budget과 합산 priority가 양수인 정상 scan에서 후보를 찾지 못하면 helper가 stop_iteration을 설정해 이번 내부 loop를 끝낼 수 있습니다. 내부 caller가 ratio 0을 강제로 주거나 계산된 priority가 0인 경우와 구분합니다. 일반 operator 설정의 ratio 0은 거절됩니다. Helper 오류 반환은 성공한 이미지 제출을 뜻하지 않습니다. Task는 helper 반환 코드를 소비하지 않고 stop hint와 현재 압력 조건으로 반복을 결정합니다. 이 내부 압력 loop에는 looper의 stop 검사도 없습니다. 종료 요청이 들어왔다고 후보 작업이나 진행 중 I/O가 즉시 취소되지는 않습니다.

직전 task가 interval을 모두 썼다면 다음 timed wait 길이는 0입니다. 고정 waiter는 이때 실제로 잠들지 않고 true를 반환합니다. 따라서 was_woken_up()이 true였다는 기록만으로 외부 wake를 받았다고 단정할 수 없습니다. 또 availability 함수의 non-NULL 포인터는 객체 존재만 보여줍니다. Recovery 중에는 포인터가 있어도 boot gate가 닫혀 있을 수 있으므로, 포인터만으로 유용한 작업이나 동기 fallback을 증명하면 안 됩니다.

Q07 · Identity만 다시 보는 최적화

구성한 시작 상태: 후보 수집 당시 P는 dirty, LRU3, fcnt == 0, FLUSHING 해제 상태입니다. List lock을 놓은 뒤 BCB를 잠글 때까지 VPID는 P로 유지됩니다. 변경안은 VPID 일치만 확인하고 나머지 수집 당시 상태를 그대로 사용합니다.

05 · COMPLETE AND REVALIDATE

Post-flush: 완료 처리와 frame 배정은 다르다

전용 발표 장: 쓰기가 끝나도 allocator는 왜 기다릴 수 있는가? · 완료와 예약을 별도 기록으로 나눌 수 있는가? · 완료 처리와 배정을 어떤 관측으로 구별할 수 있는가?.

이 장에서는 독립적인 완료 사례로 다시 시작합니다. P는 메모리에 있는 페이지이고 G는 제출한 P의 사본을 가리키는 설명용 세대 이름입니다. Q는 frame을 기다리는 allocator입니다. G를 제출해도 Q가 frame을 받았다는 뜻은 아닙니다. Queue는 완료 정리를 위임합니다. 소비 전에 다른 caller가 P를 fix해 사용을 유지하거나 다시 dirty로 만들 수 있고, 공개된 frame 제안도 취소될 수 있습니다.

화면: 큐로 어떤 작업을 넘기는가? → 큐에 들어간 flush는 어느 스레드가 마치는가? → 소비자는 왜 현재 상태를 다시 검사하는가? → 쓰기가 끝나도 allocator는 왜 기다릴 수 있는가?.

Queue에 들어가는 것은 PGBUF_BCB *입니다. 페이지 내용도, 이 frame을 안전하게 재사용할 수 있다는 보증도 아닙니다. 완료 처리를 넘기려면 네 조건이 모두 맞아야 합니다. 이미지를 제출한 주체가 page-flush thread여야 하고, post-flush daemon이 있어야 합니다. Direct victim을 기다리는 allocator가 있어야 하며, 용량이 제한된 queue에 포인터를 넣는 데도 성공해야 합니다. 그렇지 않으면 이미지를 제출한 thread가 BCB를 다시 잠그고 완료 처리를 합니다.

Post-flush는 queue의 소비자입니다. 포인터를 꺼내 BCB mutex를 잡고 현재 상태를 검사합니다. DIRTY를 포함해 후보 자격을 막는 flag가 있는지, fix나 BCB에 연결된 대기 thread가 남아 있는지, cold zone인 LRU3에 있는지를 봅니다. Private list라면 현재 크기가 보존 목표인 quota를 초과해야 합니다. 조건이 맞고 아직 할당을 기다리는 요청이 있으면 direct victim을 제안하고 깨울 수 있습니다. 이 시도는 기존 FLUSHING 정리보다 앞에 있습니다. 새 fix나 dirty 상태가 생겼다면 제안하지 않아도 기존 이미지의 완료 정리는 수행합니다. 여기서 BCB에 연결된 대기자는 flush 대기자도 포함합니다. 별도 queue에서 frame을 기다리는 allocator와 구분합니다.

배정을 거절하더라도 G의 완료 처리는 해야 합니다. G의 FLUSHING 상태를 해제하고, 해당 flush를 기다리는 thread를 깨워야 합니다. 반면 새 frame을 기다리는 allocator는 재사용 가능한 frame의 배정을 기다립니다. 이 두 대기를 섞으면 “flush는 끝났는데 allocator는 왜 아직 기다리지?”라는 질문의 원인을 놓치게 됩니다.

Reader가 나중에 unfix하더라도 이 queue를 통해 자동으로 배정되는 것은 아닙니다. 일반적인 LRU3의 마지막 unfix에서는 승격이나 이동이 일어날 수 있습니다. Clean 페이지의 unfix에서 직접 배정하는 것은 별도의 조건을 가진 경로입니다. Direct victim을 제안받은 allocator도 실제 사용 전에 다시 검사합니다.

대기가 늘어났다가 다시 짧아지는 이유

Queue를 처리하지 못한 유휴 회차가 이어지면 looper는 1 → 10 → 100 ms, 이후 무한 대기로 넘어갑니다. 하나라도 소비하면 allocator가 제안을 받았는지와 관계없이 pgbuf_assign_flushed_pages()가 true를 반환하고 task가 looper를 1 ms부터 다시 시작시킵니다. 이전 pause의 wake 결과도 increasing-wait 정책을 reset합니다. 소비 성공과 배정 성공은 다른 사건입니다.

이 대기 단계와 8,192-entry queue 용량은 고정 소스에 들어 있는 compiled policy입니다. 별도의 공개 post-flush interval·enable 설정은 없습니다. Queue payload는 BCB 포인터이므로, 수락한 항목의 완료 의무가 남아 있는 동안 해당 저장 공간을 유지해야 합니다. 정상 소비는 queue를 비울 때까지 진행하지만 stop이 모든 항목의 drain을 보장하는 계약은 아닙니다.

여기서 쉬어도 좋습니다. 다시 시작할 때 참가자에게 “사본 제출, BCB 완료, frame 배정”의 세 경계를 설명해 달라고 합니다.

설명용 대안입니다. 추가 식별자와 수명 기록으로 오래된 ticket을 권한과 구분합니다. 연속 예약은 새 사용을 막거나 mutex·CPU 비용을 옮깁니다. 실제 queue-full fallback은 local completion을 수행하므로 daemon 제거가 완료 정리 제거를 뜻하지는 않습니다.

Maintenance: 100 ms 시도와 quota 갱신

전용 발표 장: 가득 찬 풀에서 어떤 페이지를 더 많이 남겨 둘까? · quota를 고정해도 무엇을 계속 보호해야 할까? · 이번 호출은 새 표본을 소비했을까?.

이제 hot set과 스캔이 보존 자원을 두고 경쟁합니다. Quota와 zone은 정책상 선호이며 identity나 미전달 변경을 지울 권한이 아닙니다. Activity sampling은 선호를 어떻게 조정할지 결정합니다. Maintenance 작업 시도, 허용된 sampling 회차, 수치가 바뀐 quota는 서로 다른 관찰입니다.

Quota는 각 private LRU가 정책상 보존할 페이지 수의 목표입니다. Private는 세션과 연결된 교체 정책 영역이며 그 세션만 페이지에 접근한다는 뜻은 아닙니다. Zone은 최근 사용 정도에 따라 LRU 안의 페이지를 구분하는 구역입니다. 이 장의 별도 사례에서 A와 B는 서로 다른 정책 영역입니다. 활동이 A에서 B로 옮겨졌다고 가정하며 앞 장의 페이지·thread 이름과 이어 붙이지 않습니다.

화면: maintenance는 보존 우선순위를 어떻게 바꿀까? → maintenance를 시도해도 갱신하지 않는 이유는 무엇일까? → 보조 함수를 호출해도 프레임을 하나도 제안하지 못할까?.

앞선 세션의 private/shared LRU를, 활동에 따라 조정되는 정책으로 살펴보겠습니다. 처음 정한 quota가 계속 적절할까요? Maintenance는 최근 unfix 활동과 LRU hit 샘플을 읽고, 각 private list의 quota와 private/shared 비율, 구역별 임계값을 조정합니다. 새 임계값을 넘는 보호 구역에서는 demotion이 필요할 수 있습니다. 이것이 maintenance가 맡은 정책 작업입니다.

100 ms는 작업을 시도하는 목표 주기입니다. pgbuf_adjust_quotas()는 quota 기능이 꺼져 있거나 다른 조정이 진행 중이면 반환할 수 있습니다. 시간 간격이 너무 짧거나, 활동량이 낮고 아직 충분한 시간이 지나지 않은 경우에도 반환할 수 있습니다. 이런 조건을 통과한 갱신에서만 샘플과 quota를 처리하고, 갱신 회차를 나타내는 epoch를 진행시킵니다. Thread가 실행됐다고 해서 quota도 바뀌었다고 볼 수는 없습니다.

이 함수를 daemon만 호출하는 것도 아닙니다. Foreground의 private list 할당·반납도 pgbuf_adjust_quotas()를 호출합니다. Epoch 증가는 조건을 통과한 샘플 처리 회차를 뜻합니다. 계산 결과가 이전 quota와 같아도 회차는 진행합니다. 호출자, 허용된 회차, 수치 변화는 따로 기록해야 합니다.

설명용 대안입니다. Sampling·reset 경합을 줄이지만 용량을 낭비하거나 워크로드 변화에 늦게 대응할 수 있습니다. 정확한 기록에는 사건마다 동기화된 갱신이 필요합니다. 근사 counter는 기록 비용을 줄이며 측정된 우위나 허용 오차는 주장하지 않습니다.

관측과 반증: 이번 호출은 새 표본을 소비했을까?.

추가 probe 계획: guard 결과, adjust_age, sample 교환·reset, quota 공개를 기록합니다. Direct 배정은 producer별로 구분하며 daemon loop 수 대신 VS-20 loop 진입을 셉니다. 같은 값만으로 허용된 회차라는 가설을 배제할 수는 없습니다. VS-21 sample 오차와 VS-20 allocator 영향은 통제 관찰 전까지 미측정으로 남습니다.

Maintenance 관측에도 활성 collection과 필요한 startup activation bit가 선행합니다. 기본 mask 15는 victimization bit 16과 daemon bit 64를 제외합니다. Daemon loop 횟수만으로 accepted epoch의 호출자를 알 수 없습니다. Foreground 호출과 daemon 호출을 구분하는 추가 timeline은 아직 실행하지 않은 제안입니다.

07 · POST-WRITE PACING

Flush-control: write 이후의 속도를 조절한다

전용 발표 장: 쓰기 성공 뒤에도 writer가 기다리는 이유는? · 쓰기 전 제한에는 어떤 상태가 더 필요할까요? · 어떤 기록이 쓰기 뒤 정산이라는 설명을 반증할까요?.

Clean 공급을 늘리면 병목이 저장장치로 옮겨갈 수 있습니다. 고정 CUBRID 경로는 OS write 이후 token을 차감합니다. 따라서 token daemon은 이미 완료한 write의 허가보다 이후 진행을 조절합니다. 회차별 교체, 누적 credit, 속도 제한 제거는 burst 양상이 다릅니다. 어느 방식도 WAL이나 보호된 재사용을 대신하지 않습니다.

화면: 어떤 작업이 잔액을 갱신할까요? → Writer는 쓰기 뒤 credit을 어떻게 소비할까요? → 어떤 쓰기가 credit 부족을 우회할까요? → 다른 어떤 주체가 쓰기와 동기화를 맡을까요?.

Flush-control이라는 이름만 보면 다른 flusher에게 언제 어떤 페이지를 쓸지 지시하는 역할로 생각하기 쉽습니다. 실제로 갱신하는 것은 file_io.c의 공유 token 예산입니다. Writer는 OS write에 성공한 다음 compensation 경로에서 token을 소비하거나 기다립니다. 이 대기를 통해 이후 작업의 속도를 조절합니다.

Token은 이 공유 예산에서 I/O page 한 개에 대응하는 설명 단위입니다. Compensation은 선택된 write 경로에서 이미 쓴 양을 정산하는 후속 작업입니다. 모든 write 경로가 같은 대기를 거치는 것은 아닙니다. 이 장의 일반 writer A와 log critical section을 보유한 writer B는 새로 구성한 두 caller이며 앞 장의 정책 영역 A·B와 다릅니다.

Bucket이 없는 경우와 첫 실행

Control task는 thread 생성 전에 file-I/O bucket을 초기화합니다. Static 저장 공간에 mutex와 condition variable을 만들고 token 0으로 시작한 뒤 bucket 포인터를 공개합니다. Mutex 초기화 실패는 공개 전에 반환합니다. Condition 초기화가 실패하면 mutex는 이미 만들어졌지만 이 경로에서 지역적으로 destroy하지 않습니다. 역할 초기화 함수는 task를 retire() 없이 삭제하고 control daemon을 만들지 않습니다. 소스에 보이는 정리 경계이며 실제 발생한 누수 관찰은 아닙니다.

공개된 bucket이 없으면 token 획득 함수는 아무 일 없이 반환합니다. Bucket이 있어도 gate가 열린 첫 task 실행은 현재 시각만 기록하고 token을 만들지 않습니다. 이후 실행이 경과 시간으로 예산을 계산합니다. 종료에서는 worker의 task retire()가 bucket을 정리한 뒤 thread가 끝나고 join이 반환합니다. Bucket을 쓰는 writer의 수명도 맞춰야 하며, page-buffer daemon의 join만으로 모든 writer의 종료를 대신 증명할 수는 없습니다.

Feedback switch와 고정 rate의 차이

다음 두 공개 설정은 DBA가 서버 전체의 registry를 online으로 바꿀 수 있습니다. 표의 IO_PAGESIZE는 I/O 페이지 한 개의 byte 크기이며 bytes/s는 초당 byte 수입니다. 예를 들어 SET SYSTEM PARAMETERS 'adaptive_flush_control=no'는 다음 refresh에서 사용할 계산 분기를 바꿉니다. Bucket을 새로 만들지는 않으며 설정 파일을 저장하지도 않습니다.

설정·분류기본값·단위변경 뒤 실제 효과
adaptive_flush_control · 공개 Booleanyes다음 refresh에서 feedback 또는 고정 rate 분기 선택
max_flush_size_per_second · 공개10,000 × IO_PAGESIZE bytes/s; 최소 한 I/O page/s다음 non-adaptive refresh만 읽습니다. max_flush_pages_per_second는 deprecated page-count alias이며 adaptive ceiling은 아닙니다.

50 ms looper, adaptive 분기의 40 MiB/s floor와 증가 0.5·감소 0.1 계수는 compiled policy입니다. Token 잔량과 이전 budget·dirty feedback은 실행 중 상태입니다. DWB 설정과 sync 경계는 다음 단계의 자원·I/O 정책이며 이 네 daemon의 필수 pipeline이나 생성 switch가 아닙니다.

50 ms 목표 주기로 새 token 예산을 계산하고 기존 값을 교체한 뒤 writer를 깨웁니다. Token이 있다고 해서 페이지를 안전하게 쓸 조건까지 확보된 것은 아닙니다. WAL 순서와 BCB 보호는 각 write 경로가 지켜야 합니다. 로그 critical section을 보유한 caller는 token이 부족해도 일반 caller처럼 기다리지 않습니다. 일반 token 대기에도 반복 횟수 제한이 있습니다. 따라서 이 예산이 I/O 양의 엄격한 상한을 보장하지는 않습니다.

Log-flush는 로그를, checkpoint는 checkpoint 경계의 작업을, DWB daemon은 DWB가 이미지를 받은 뒤의 write 경로를 맡습니다. 이들은 페이지 버퍼의 네 daemon과 별도로 봐야 합니다. 여러 caller가 같은 write helper에 도달할 수 있습니다. Dirty 상태를 만든 caller가 항상 page-flush의 queue에 작업을 넣는 구조는 아닙니다.

여기까지 네 가지 결과를 구분했습니다. 이미지 제출, BCB 완료와 배정, quota 조정, writer의 속도 조절입니다. 이제 PostgreSQL에서도 누가 이 역할을 맡는지 살펴보겠습니다.

설명용 대안입니다. Write 진입을 조절하지만 예약·취소 상태가 추가됩니다. Log와 credit의 의존 순환을 배제하지 않으면 deadlock이 가능합니다. 누적 credit은 저장한 burst를 허용하고 회차별 교체는 회차 allowance를 제한하며 pacing 제거는 저장장치 경쟁을 바꿉니다. 실제 장치 I/O의 엄격한 상한을 측정한 것은 아닙니다.

관측과 반증: 어떤 기록이 쓰기 뒤 정산이라는 설명을 반증할까요?.

OS write 반환, post-write 차감, token 교체·broadcast, condition wait 시작·반환, 탈출 이유를 관찰합니다. Compensation 통계만으로 앞선 write 지연을 알 수 없습니다. 관찰한 OS write보다 먼저 차감됐다면 고정 경로 주장을 반증합니다. 열 번 반환하는 경로에도 한 번의 무한 대기가 가능하면 유한 지연 정리는 나오지 않습니다. Timing은 기록된 관찰로만 사용합니다.

08 · TRANSFER THE MODEL

PostgreSQL: pin과 credit을 먼저 나눈다

전용 발표 장: 메모리의 같은 주소가 왜 계속 같은 페이지를 가리켜야 할까? · 모든 pin이 공유 참조 수를 갱신하게 하면 어떨까? · Pin 규칙은 어떻게 검증할 수 있을까?.

PostgreSQL 사례는 새로 시작합니다. Backend는 요청을 처리하는 실행 주체입니다. Descriptor는 frame에 담긴 페이지와 사용 상태를 관리하는 구조입니다. Pin은 해당 frame을 다른 페이지로 재사용하지 못하게 하는 사용 의무이고 content lock은 바이트를 읽거나 바꿀 때 얻는 별도의 보호입니다. usage_count는 최근 사용을 제한된 숫자로 기억하는 보존 credit입니다. Pin 수와 credit은 서로 다른 조건을 나타냅니다.

화면: Pin은 어떻게 페이지를 메모리에 유지할까? → 메모리의 같은 주소가 왜 계속 같은 페이지를 가리켜야 할까?. 여기서 InnoDB 절로 이어가지 않고 다음 clock 화면 안내로 이동합니다.

PostgreSQL에도 메모리의 페이지 바이트와 이를 관리하는 descriptor가 있습니다. 여기서는 backend라는 실행 주체가 페이지를 pin합니다. Pin은 해당 frame을 다른 페이지 identity로 재사용하지 못하게 막습니다. 바이트를 읽거나 바꾸기 위한 content 보호는 별도로 얻어야 합니다. CUBRID의 fix와 latch에서 배운 책임 구분은 가져올 수 있지만, 두 엔진의 호출 인터페이스가 같다는 뜻은 아닙니다.

교체 정책에 사용할 기억도 따로 있습니다. PostgreSQL의 usage_count는 재사용 이력을 제한된 수치로 기억하는 credit입니다. 현재 pin을 나타내는 refcount와는 다른 값입니다. 접근 시각이나 LRU 위치도 아닙니다. 이 기준 리비전에서는 최대 5까지 올라갑니다.

기본 strategy에서 해당 backend가 아직 pin하지 않은 페이지를 pin하면 공유 refcount를 올립니다. Usage credit도 상한인 5에 도달하지 않았다면 올립니다. 같은 backend가 이미 pin한 페이지를 중첩해서 pin하면 backend 내부의 private refcount만 늘립니다. 따라서 중첩 호출 횟수가 그대로 공유 credit에 더해지지는 않습니다. Ring strategy의 pin은 credit이 0일 때 1로 올릴 수 있지만, 이미 높은 credit을 더 올리지는 않습니다.

Q16 · 중첩 Pin의 기록

구성한 시작 상태: 공유 descriptor D는 유효한 clean 페이지를 나타내며, 공유 refcount와 usage credit은 모두 0입니다. 진행 중인 I/O는 없습니다. 기본 strategy를 사용합니다. Backend A가 D를 연속 세 번 pin한 상태에서 B가 D를 처음 pin합니다. 이후 A만 자신의 세 pin을 모두 반납합니다. Clock 방문이나 다른 변경은 없습니다.

논의 후 설명 보기

Pin은 메모리 사용 수명을 보호하며 호환되는 바이트 접근까지 보장하지 않습니다. 해당 접근 경로에 필요한 content 보호의 획득·반납 주체를 명시해야 합니다. 일반 공유 버퍼 읽기에서는 바이트를 보기 전에 호환되는 content lock을 얻도록 wrapper의 반환 계약이나 caller의 의무에 넣습니다. 주소와 pin만으로 READ fix의 계약을 재현할 수 없습니다.

설계 논증 이어가기

확장 화면 순서: 중첩 사용은 왜 private 기록으로 충분할까? (EN) → 메모리의 같은 주소가 왜 계속 같은 페이지를 가리켜야 할까? (EN) → 교체 과정에 사용자가 보이지 않으면 무엇이 깨질까? (EN)

Private refcount는 이 backend의 nested 사용 의무이고 shared refcount는 backend의 수명 기여입니다. 첫 pin은 공유 상태를 바꾸지만 nested pin은 private 수치만 늘립니다. 마지막 반납까지 identity가 보호됩니다. Pin은 content 변경을 직렬화하지 않으며 usage_count는 소유권이 아닙니다.

수명 사례는 독립적으로 초기화합니다. H는 메모리에 있는 페이지이며 A는 H를 두 번 pin하는 backend입니다. 두 사용이 끝나기 전에 공유 수명 표시만 없애면 clock이 H를 잘못 claim할 수 있습니다. Content lock이 없는 접근 사이 구간도 pin이 보호해야 합니다. Nested pin을 모두 공유 count로 세는 대안은 대응한 반납이 있으면 안전하지만 공유 atomic 비용과 count 의미를 바꿉니다.

대안의 전이: 모든 pin이 공유 참조 수를 갱신하게 하면 어떨까?.

매 획득 전에 identity를 다시 검사합니다. 중첩 사용마다 공유 수명 기록을 증가시킵니다. 읽기나 변경 시 바이트를 별도로 보호합니다. 해제·오류 시 해당 획득만 정리하며 모든 기여가 없을 때만 identity를 해제합니다.

설명용 대안입니다. 중첩 획득 m번마다 공유 atomic 작업을 추가하며 private 첫·마지막 경계만 갱신하는 방식과 다릅니다. 해제 의무를 맞추기 위한 private 기록은 여전히 유용합니다. 공유 기여를 대체 없이 제거하면 수명 위반이며 동등한 빠른 pin이 아닙니다.

관측과 반증: Pin 규칙은 어떻게 검증할 수 있을까?.

추가 probe 계획: private 중첩 수, 공유 refcount 전이, 보호된 mapping identity를 기록합니다. Content-lock 대기는 바이트 접근이며 중첩 해제 의무가 아닙니다. A의 보호된 사용이 남아 있을 때 재사용되면 수명 불변식을 반증합니다. 획득별 기록은 공유 atomic 비용을 바꾸며 모델만으로 timing 이득을 입증하지 않습니다.

서로 다른 사용자는 어떻게 보호할까요?

추가 화면: 여러 클라이언트가 쓰는 페이지는 어떻게 보호할까? → 공유 참조 수가 backend 수보다 많을 수 있는 이유는? → 동시 요청은 같은 페이지를 어떻게 찾고 사용할까? → 각 backend는 얼마나 앞서 페이지를 pin해야 할까?.

공유 pin 기록은 pool 전체에 하나가 아니라 descriptor마다 있습니다. 각 backend는 자기 안의 중첩 pin을 따로 셉니다. 앞 질문과 독립된 사례로, 유효한 페이지 하나에 진행 중인 I/O가 없다고 합시다. Backend A가 세 번, B가 한 번 pin하면 공유 count는 2입니다. A가 세 pin을 모두 반납해도 B의 기여 1이 남으므로 frame을 재사용할 수 없습니다. 비동기 읽기는 요청한 backend가 오류로 끝나더라도 I/O 완료 전까지 frame을 지키려고 별도의 수명 pin을 더할 수 있습니다. 그래서 공유 count가 항상 실제 client 수인 것은 아닙니다.

페이지 식별자를 찾는 mapping 보호는 분할되어 있고, 페이지 바이트와 진행 중인 I/O는 buffer별로 보호합니다. 교체 후보를 확보한 뒤에도 현재 상태를 다시 검사합니다. 이것은 동시 사용을 보호하는 장치입니다. 같은 용량을 나누거나 낮은 지연을 보장하는 증거는 아닙니다. 상세 trace는 고정 20devel 소스이며, PostgreSQL 18에도 핵심 pin·credit·ring 장치가 있지만 lock의 세부 구현은 다릅니다.

Read stream은 앞으로 사용할 페이지를 미리 읽고 pin하는 경로입니다. PostgreSQL은 pool 크기와 최대 backend 수에서 backend별 권고 pin 예산을 계산합니다. 참여하는 read stream은 작업 strategy의 제한과 남은 예산을 함께 보고, 아직 사용하지 않을 페이지를 앞서 확보하는 양을 줄입니다. Stream이 현재 pin한 buffer를 하나도 보유하지 않으면 남은 예산이 0이어도 진행을 위해 하나를 더 허용합니다. 이는 미반납 pin을 조절하는 정책이며 모든 resident 페이지의 client별 quota나 모든 pin의 엄격한 상한은 아닙니다.

추가 근거와 버전 경계: 동시 client의 pin, I/O 수명, 예산에 대한 고정 소스 기록. 상세 설명은 위 장별 화면의 고정 source 링크로 확인합니다.

09 · CLOCK TRACE

Clock sweep: hand가 무엇을 바꾸는가?

전용 발표 장: 가득 찬 풀에서 스캔이 확보할 후보를 찾습니다 · 재사용 검사를 유지하면서 정확한 최근 순서를 만듭니다 · 탐색 결과를 바꾸는 사건을 관찰합니다.

Descriptor는 메모리 frame의 페이지와 사용 상태를 관리하는 구조입니다. 이번 스캔은 배열에서 다음 후보를 찾아야 합니다. Atomic hand는 여러 allocator에게 방문 위치를 나누는 공유 cursor입니다. Atomic 변경은 한 번의 나눌 수 없는 동작으로 수락합니다. CAS(compare-and-swap)는 읽었던 상태가 그대로일 때만 원하는 새 상태로 바꾸는 연산입니다. 방문 결과는 사용 중인 frame 건너뛰기, 보존 credit 감소, 자신의 pin 확보로 갈립니다. Credit 0을 읽었다고 pin을 얻은 것은 아닙니다. 상태 전이 성공이 필요합니다.

화면: Hand의 한 번 방문에는 세 가지 결과가 있습니다 → 새로 들이기, 다시 사용하기, 선택하기는 다른 상태를 바꿉니다. 다음 새 예측은 이 대본의 표로 진행합니다.

PostgreSQL의 기본 교체 경로에서는 clock hand가 공유 descriptor 배열을 따라 전진합니다. Pin 중인 descriptor는 건너뜁니다. Pin이 없고 credit이 양수라면 하나를 줄인 뒤 다음 descriptor로 갑니다. Pin이 없고 credit도 0이라면 CAS로 자신의 pin을 얻어 후보를 반환합니다. 여기까지 끝난 것은 descriptor 선택입니다. Dirty 이미지의 write나 기존 identity 제거는 이후 caller가 처리합니다.

이제 이전 화면과 독립된 새 모델로 예측해 보겠습니다. Descriptor 네 개만 두고 한 실행 주체가 순서대로 처리하는 설명용 모델입니다. 실제 PostgreSQL의 pool 설정이나 실행 캡처가 아닙니다. Hand는 F0에서 시작하고, 방문 순서는 F0 → F1 → F2 → F3입니다. 표의 refcount는 이 allocator가 선택하기 전에 다른 backend가 보유한 공유 pin 수입니다. 동시 변경이나 진행 중인 I/O는 없고 모두 clean 상태라고 가정합니다.

예측: 처음 반환하는 descriptor는 무엇일까요? 각 방문 후 credit과, 선택된 descriptor의 refcount를 적어 보세요. F2의 credit을 0으로 줄인 그 방문에서 곧바로 F2를 선택할까요?

예측 후 순서 보기
  1. F0: credit을 2 → 1로 줄이고 다음으로 이동합니다.
  2. F1: pin 중이므로 건너뜁니다. Credit은 0으로 유지됩니다.
  3. F2: credit을 1 → 0으로 줄이고 다음으로 이동합니다. 이 방문에서는 선택하지 않습니다.
  4. F3: credit이 0이고 pin이 없습니다. CAS로 자신의 pin을 얻어 refcount를 1로 바꾸고 반환합니다. 새 페이지 identity의 내용을 읽었다는 뜻은 아닙니다.

시작 상태를 바꿔 다시 예측: 표의 시작 상태에서 F3의 초기 credit만 1로 바꿉니다. 나머지 조건은 같습니다. 처음 반환하는 descriptor를 다시 구해 보세요.

다시 예측 후 답 보기

첫 순회에서 F0의 credit은 1, F2와 F3의 credit은 0이 됩니다. 다음 순회에서 F0를 1 → 0으로 줄이고 F1을 건너뛴 뒤, F2를 pin하고 반환합니다. 첫 사례를 수행한 뒤의 상태를 이어받지 않습니다.

이 모델은 exact LRU처럼 전체 접근 순서를 유지하지 않습니다. 어떤 페이지를 더 최근에 읽었는지 모두 정렬하는 대신, 제한된 credit을 기억합니다. 메타데이터 갱신과 후보 선택에 드는 작업은 비교할 수 있습니다. 다만 이 추적만으로 처리량의 우위를 판단할 수는 없습니다.

Q18 · Clock 후보의 동시 변경

구성한 시작 상태: Hand가 D의 credit을 1에서 0으로 낮추고 다음 descriptor로 갔습니다. 다시 D를 방문한 A는 refcount 0과 credit 0을 읽었습니다. A가 그 상태를 기대한 CAS로 자기 pin을 얻기 전에 B의 정상적인 첫 pin이 성공했고, B는 pin을 유지합니다. 다른 변화는 없습니다.

설명용 대안입니다. Frame n개에 O(n) 순서 metadata, 접근마다 공유 동기화 아래 O(1) list 변경, 최대 O(n) 적합성 scan이 필요합니다. History 대안은 nonresident identity 기록을 더합니다. Clock은 정확한 전역 recency 갱신을 줄이지만 CAS와 재방문 비용은 남습니다. 정확한 순서만으로 공정성이 성립하지는 않습니다.

10 · WORKLOAD STRATEGIES

Ring: 공유 frame의 ID를 작업별로 기억한다

전용 발표 장: 스캔은 왜 앞서 사용한 프레임을 다시 찾을까? · 스캔 용량 분리에는 공유 식별자와 실패 처리 규칙이 필요하다 · 어떤 관측으로 ring 설명을 반증할 수 있을까?.

이 장은 반복 읽기와 긴 scan이 경쟁하는 새 사례입니다. H1과 H2는 반복해서 읽는 hot 페이지입니다. S1, S2, S3는 scan이 한 번씩 읽을 별도의 페이지들입니다. Access-strategy ring은 이 작업이 다시 시도할 공유 buffer ID를 작은 배열에 기억합니다. ID를 기억했다고 frame을 독점하지는 않습니다. Pin은 현재 사용을 보호하고 credit은 보존 선호를 나타냅니다. NORMAL, BULKREAD, BULKWRITE, VACUUM은 서로 다른 strategy 이름입니다.

화면: 로컬 슬롯은 공유 pool의 프레임을 가리킨다. 소스의 factory 크기 계산은 질문이 있을 때 펼칩니다.

H1, H2를 반복해서 읽는 동안 긴 scan이 S1, S2, S3를 한 번씩 읽는다고 하겠습니다. Scan의 모든 miss를 전역 교체 경로에 맡기면 반복 사용하는 페이지도 교체 압력을 받을 수 있습니다. PostgreSQL은 이런 대량 작업에 buffer access strategy를 전달할 수 있습니다.

Ring은 backend 내부에 두는 작은 배열이며, 공유 buffer의 ID를 저장합니다. 다음 slot이 가리키는 frame에 pin이 없고 credit이 0 또는 1이면 재사용을 시도합니다. Slot이 비어 있거나 그 frame을 사용할 수 없다면 전역 clock에서 후보를 고르고, 선택한 buffer의 ID로 slot을 채웁니다. Ring 객체는 backend에 속하지만, 참조하는 frame은 다른 backend도 사용할 수 있습니다.

Strategy이번 세션에서 기억할 점
BAS_NORMAL기본 clock 경로. 별도의 ring 객체를 만들지 않음.
BAS_BULKREAD대량 읽기에 사용할 buffer를 재사용함. Ring에서 고른 후보가 dirty 상태인 permanent 페이지이고, 이를 쓰기 위해 WAL flush가 필요하면 ring에서 제외하고 다른 후보를 구할 수 있음.
BAS_BULKWRITE대량 쓰기에 사용할 buffer를 재사용함. Bulk-read와 동일한 dirty/WAL 후보 거절 정책을 적용하지 않음.
BAS_VACUUMVacuum 작업에 사용할 buffer를 재사용함. 필요한 dirty 페이지 write와 WAL 처리를 수행할 수 있음.

Factory 수치는 기준 리비전과 호출 경로에 따라 읽어야 합니다. 이 소스의 bulk-read 기본 크기는 256 KiB를 바탕으로 AIO에 필요한 여유분을 반영하고 pin 한도를 고려합니다. Bulk-write factory는 16 MiB, vacuum factory는 2 MiB입니다. 공통 크기 처리 경로에서는 공유 buffer 수의 1/8을 상한으로 둡니다. 실제 caller가 지정하는 크기도 확인해야 합니다. 아래의 두 slot은 설명용 모델입니다.

CUBRID의 private LRU와 PostgreSQL의 ring은 모두 대량 작업의 교체 압력과 관련되지만 구조가 다릅니다. CUBRID의 private LRU는 pool이 관리하는 BCB의 정책 영역이며 quota를 가집니다. PostgreSQL의 ring은 backend 내부에 둔 공유 buffer ID의 배열입니다. 두 구조를 독립된 buffer pool로 해석하면 실제 소유 관계를 놓칩니다.

아래 strategy 질문 전에 기록 규칙도 확인합니다. PostgreSQL의 LSN은 페이지 이미지에 필요한 로그 위치입니다. BULKREAD는 ring에서 고른 dirty permanent 페이지에 추가 WAL flush가 필요하면 자기 ring slot을 비우고 후보를 반납한 뒤 다른 경로로 재시도합니다. 공유 페이지의 dirty 내용은 지우지 않습니다. BULKWRITE나 VACUUM에서는 필요한 WAL을 보존하고 쓰기를 시도하는 별도 분기를 따를 수 있습니다. 이 규칙은 이름만 바꾼 같은 보호 조건이 아니며, 실제 caller가 고른 strategy와 pin·내용 보호를 함께 봅니다.

Ring이 없으면 normal clock을 쓰면서 안전성을 유지할 수 있습니다. Scan pollution과 경쟁 비용이 어떻게 바뀌는지는 workload에 달렸습니다. 별도 private scan pool은 공간을 분리하지만 바이트 중복과 coherence를 추가합니다. BULKREAD의 WAL 거절은 자기 slot을 비우며 공유 dirty 페이지는 보존합니다. D30을 먼저 논의하고 D31은 다음 writeback 블록에서 이어갑니다.

대안의 전이: 스캔 용량 분리에는 공유 식별자와 실패 처리 규칙이 필요하다.

Scan admission에 제한된 frame partition을 예약합니다. Partition 전체가 하나의 권위 있는 identity map을 사용합니다. 이동이나 재사용 전에 공유 사용과 dirty 의무를 존중합니다. Scan 종료 시 예약을 해제하고 명시적인 재분배 정책으로 남는 용량을 공급합니다.

설명용 대안입니다. Local ID r개인 ring과 달리 실제 용량을 예약합니다. 재분배·coherence 규칙이 추가되고 idle 공간을 낭비할 수 있습니다. 2Q/history는 queue·history를 쓰는 다른 scan 저항 대안입니다. Ring의 local 작업은 O(1)에 공유 상태 재시도가 더해집니다. ID는 O(r) 공간을 쓰지만 전체 scan I/O나 독점 frame r개를 보장하지는 않습니다.

관측과 반증: 어떤 관측으로 ring 설명을 반증할 수 있을까?.

pg_stat_io에 strategy context가 있습니다. 추가 probe로 ring 허용, refcount·credit 거절, BULKREAD WAL 거절, global fallback을 구분합니다. Slot 수와 서로 다른 공유 frame 수도 구분합니다. 다른 소유자가 있는데 ring ID만으로 사용을 승인하면 수명 보호를 반증합니다. Slot r개는 독점 frame r개나 I/O r페이지 상한을 증명하지 않으며 집계 reuse 수로 최종 해제를 입증하지 못합니다.

전용 발표 장: 요청에는 프레임이 필요하지만 기존 페이지도 보존해야 한다 · 기존 페이지를 예약해 중간 변경을 막는다 · 쓰기와 invalidation 사이의 공백을 관측하기.

이번 사례에서는 backend A가 dirty 페이지 P를 교체 후보로 pin했다고 하겠습니다. B는 같은 P를 다시 사용할 수 있는 다른 backend입니다. Dirty는 아직 전달해야 할 변경이 남았다는 뜻입니다. Pin으로 선택했다고 재사용이 끝난 것은 아닙니다. A는 기존 페이지 식별자와 frame의 연결인 mapping을 없애기 전에 바이트 보호, 필요한 WAL 보존, writeback을 수행할 수 있습니다. 바이트 보호를 푼 뒤에는 B가 새 변경을 만들 수 있습니다.

화면: 어느 엔진이 프레임을 선택해도 dirty 변경은 보존해야 한다 → 순서 관리가 줄면 세밀한 최근 사용 정보도 잃는다. Write를 맡는 주체의 자세한 구분은 아래 표와 기준 소스에서 확인합니다.

Clock은 dirty라는 이유만으로 descriptor를 제외하지 않습니다. Pin이 없고 credit이 0인 후보를 자신의 pin으로 확보한 뒤, 할당을 요청한 backend가 dirty 페이지를 쓸 수 있습니다. 이때 대기 없이 content lock 획득을 시도하고, 필요한 WAL을 먼저 보존한 다음 페이지를 씁니다. Lock을 얻지 못하거나 다른 사용 때문에 기존 identity를 제거할 수 없다면 후보를 놓고 다시 시도합니다.

선택 당시 다른 pin이 없었다고 해서 이후에도 자기 혼자 사용한다는 보장은 없습니다. 다른 backend가 pin하거나 다시 dirty 상태로 만들 수 있습니다. InvalidateVictimBuffer()는 mapping과 header를 보호한 상태에서, 현재 refcount가 자기 pin 하나뿐이고 dirty가 아닌지 확인합니다.

CUBRID에서는 list와 quota 처리 비용을, PostgreSQL에서는 sweep과 credit·pin 상태 처리 비용을 살펴볼 수 있습니다. 결과는 hot set과 scan, dirty 생성률, pin을 유지하는 시간, 저장장치에 따라 달라질 수 있습니다. 소스에서 확인한 구조만으로 성능 순위를 정할 수는 없습니다.

고정 PostgreSQL 리비전의 dirty victim은 conditional share-exclusive content lock을 요구합니다. 조건부 실패는 pin을 놓고 다시 선택해 source comment가 설명하는 wait cycle을 피합니다. 예전 shared-lock 요약을 이 리비전의 실행 사실로 옮기지 않습니다.

설명용 대안입니다. 간섭을 허용하고 재검사하는 대신 중간 사용을 배제합니다. 모든 lookup·content 경로가 예약과 lock 순서를 따라야 합니다. 저장장치 지연이 reader·writer를 막고 checkpoint와의 순서도 정의해야 합니다. 구현 경로는 병행을 유지하고 writeback 이후 재사용을 포기할 수 있습니다.

관측과 반증: 쓰기와 invalidation 사이의 공백을 관측하기.

추가 probe로 LSN, content-lock 결과, write 이후 DIRTY·refcount, mapping lock, InvalidateVictimBuffer 결과를 기록합니다. IOOP_REUSE·IOOP_EVICT는 최종 invalidation 거절보다 먼저 증가합니다. 새 DIRTY가 있는데 기존 mapping을 해제하면 미완료 작업 보존을 위반합니다. Eviction counter는 최종 mapping 해제의 성공 증거가 아닙니다. Checkpoint 영속화에는 이후 sync·log 증거가 필요합니다.

용량 경쟁을 무엇으로 기록할까요?

추가 화면: 용량 그룹과 페이지 credit은 서로 다른 정보를 기억한다 → Domain 이동과 같은 목록 안의 boost는 다르다 → 조건을 통제한 혼합 작업으로 정책을 비교하기.

CUBRID의 private replacement domain은 resident 페이지 기록과 적응형 quota를 연결합니다. Private는 독점 cache가 아니라 교체 정책 영역입니다. 같은 private list를 두 session이 배정받을 수도 있습니다. PostgreSQL의 private refcount는 아직 반납할 사용을 세고, credit은 페이지를 더 보존할 기회를 기억하며, ring은 bulk 작업이 먼저 다시 쓸 frame ID를 기록합니다. 서로 다른 역할을 같은 용량 정책으로 읽지 않습니다.

CUBRID에서도 두 종류의 promotion을 구분해야 합니다. Private에서 shared로 옮기는 해당 마지막 unfix 경로는 caller와 BCB의 private-list index 차이 또는 hot하고 충분히 오래된 상태를 검사합니다. 옮긴 BCB는 shared list의 middle에 넣습니다. 모든 서로 다른 사용자를 세는 검사가 아닙니다. Hot-zone boost는 현재 list 안의 보존 위치를 올리는 별도 작업입니다. Domain을 옮기지 않는 일반 policy 처리에서는 LRU1은 그대로 두고 LRU2는 충분히 오래됐을 때, LRU3는 boost합니다. PostgreSQL의 credit 증가나 ring 거절은 descriptor를 shared LRU로 옮기는 작업은 아닙니다.

이 구조가 어떤 혼합 workload에 유리한지는 아직 실행하지 않은 실험 질문입니다. Hot 페이지를 반복 읽는 client에 긴 scan과 writer를 더하고, client 수와 working set의 겹침, scan 양, pin 유지 시간을 바꿉니다. 데이터·query·영속성·cache byte 예산·저장장치를 맞춘 뒤 client별 처리량, read·write, CPU와 동기화 대기를 봅니다. p95/p99 지연은 요청의 95%/99%가 그 이하의 지연으로 끝나는 경계입니다. 이 tail 지연과 페이지 보존을 함께 비교해야 합니다.

PostgreSQL 18의 pg_stat_io는 작업 context별 I/O를, pg_buffercache는 개별 buffer 상태를 관찰하는 경로입니다. 완전한 client별 접근 이력은 아닙니다. pinning_backends는 공유 refcount를 그대로 보여 주므로 진행 중인 비동기 I/O의 수명 pin이 포함될 수 있고, pool 전체를 한 순간에 읽은 snapshot도 아닙니다. Hand 방문·CAS 재시도·ring 거절 원인은 추가 probe가 필요합니다. 여기서는 benchmark 결과나 용량 공정성을 증명하지 않습니다.

비교 근거와 관측 범위: CUBRID의 migration·boost와 PostgreSQL 버전별 관측 기록. 이 기록도 성능 측정 결과는 아닙니다.

사례 A · Flush 횟수는 늘었는데 allocator가 기다린다

CUBRID pool에 invalid frame이 없습니다. Allocator B는 direct victim을 기다립니다. Cold dirty 페이지 P의 G 제출에 성공했고, post-flush queue 삽입에도 성공했습니다. 소비자가 실행되기 전에 writer A가 P를 fix하고 G+1의 변경을 만들었습니다. A는 아직 fix를 반납하지 않았습니다. 이후 소비자가 실행되어 해당 BCB를 꺼냈습니다.

왜 이 사건만으로 B를 바로 진행시킬 수 없을까요? G의 어떤 처리는 마쳐야 할까요? “Post-flush가 실행되지 않았다”와 “실행했지만 배정을 거절했다”를 구분하려면 무엇을 관찰할까요?

A의 현재 fix와 새 DIRTY가 재사용을 막습니다. G의 FLUSHING 상태를 해제하고 flush를 기다리는 thread는 깨웁니다. 하지만 G+1의 dirty 상태와 현재 fix의 보호는 유지해야 합니다. 소비자의 실행과 queue 소비, BCB의 flag와 fix 상태, 현재 zone과 quota, direct-victim 대기 요청과 배정 여부를 시간 순서대로 봅니다. Flush 횟수 증가만으로 queue 소비나 배정 성공을 판단할 수는 없습니다. 이 사례는 특정 버그나 starvation을 실제 실행에서 입증한 기록이 아닙니다.

사례 B · Ring이 있어도 scan이 전역 clock으로 간다

PostgreSQL bulk-read strategy의 다음 ring slot은 dirty 상태인 permanent 페이지 R을 가리킵니다. 여기서 permanent는 BM_PERMANENT로 구분하는 페이지 범주입니다. R을 처음 선택할 때 pin은 없었고 credit은 1이었습니다. 대기 없이 content lock을 얻는 데도 성공했습니다. 아직 R의 페이지 LSN까지 WAL flush가 필요합니다. 같은 시점에 별도의 hot 페이지 H는 다른 backend가 pin하고 있습니다.

Q24 · 이름이 다른 모듈의 검토

구성한 시작 상태: 설명용 모듈의 문서에는 Acquire(P) → Use → Release(P)와 SubmitImage(P) → Complete(ticket) → Offer(frame) → Retag(frame, Q)라는 두 경로가 적혀 있습니다. Submit은 사본을 전달하고 ticket을 반환합니다. Complete와 Offer의 보장 범위, Retag가 현재 상태를 검사하는지는 아직 정의하지 않았습니다. 이는 실제 엔진 API가 아닌 인터페이스 검토 사례입니다.

확장 화면 순서: 이미지가 완료돼도 할당자는 계속 기다릴 수 있습니다 (EN) → 경계마다 보호하는 책임이 다릅니다 (EN) → 이전 이미지는 완료하고 새 dirty 작업은 유지합니다 (EN) → 대안은 각 기록이 허용하는 행동을 명시해야 합니다 (EN) → 일어나지 않은 첫 전이를 찾습니다 (EN) → D32 · 새 dirty 작업과 정책상 남겨 둔 clean 페이지를 구별합니다 (EN)

기존 Q23/Q24의 새 사례를 마친 뒤 더 강한 질문으로 연결합니다. G 완료 counter가 증가하고 post-flush heartbeat가 정상이어도 새 DIRTY 때문에 offer가 없거나 zone·quota 정책에서 거절할 수 있습니다. D32는 보호된 현재 상태와 이유별 counter로 두 원인을 구별하는 관측을 요구합니다.

별도로 초기화한 제거 모델: 이전 이미지는 완료하고 새 dirty 작업은 유지합니다.

이 trace의 Q는 대기 중인 allocator, F는 메모리 frame, P는 그 frame의 영구 페이지입니다. G는 로그 위치 120의 사본이고 G+1은 이후 180까지 반영한 메모리 변경입니다. 모두 설명용 표기입니다. G는 writer를 배제하고 안정되게 확보했으며 일치하는 WAL 순서를 지켜 제출했습니다. 시작할 때 P는 shared LRU3에 있고 DIRTY=0, FLUSHING=1, fcnt=0입니다. BCB에 연결된 대기자는 flush 대기자를 포함해 없습니다. Q는 별도의 allocator queue에서 기다립니다. 명시한 vacuum worker만 P를 변경하고 필요한 로그를 남긴 뒤 마지막 fix를 반납합니다. 이 특수 unfix 분기는 cold 영역을 유지하지만 일반 unfix는 승격할 수 있으므로 같은 사례로 대체하면 안 됩니다.

제거 모델은 소비자와 수신자 등을 포함한 최종 재사용의 현재 DIRTY 의무를 모두 과거 완료 boolean으로 대신합니다. 다른 조건은 유지한다고 가정합니다. 실제 코드의 소비자 검사 한 줄만 지워도 수신자의 DIRTY 검사와 assertion이 남습니다. 따라서 한 줄 삭제만으로 unsafe retag가 발생한다는 소스 주장은 아닙니다. 독립적으로 구성한 최종 재사용 모델이 새 변경 의무를 잃는 이유를 설명합니다.

D33에서는 검사 하나를 없앤 변경을 방어합니다. 어떤 구간을 제거했고 어떤 actor가 그 사이 조건을 바꿀 수 있는지, 대체 보호와 실패·취소 정리가 무엇인지 설명해야 합니다. 연속 reservation과 재검사는 비용을 다른 곳에 씁니다. 측정 없이 빠르다고 결론 내리지 않습니다.

마지막에는 요청부터 identity·수명, 바이트 보호, 변경·WAL, 반납, 이미지 전달, 현재 적합성, 이전 identity 제거, 재사용까지 다시 말해 봅니다. 거절된 생략 하나와 안전한 대안 하나를 넣어 전체 논증을 완성합니다. 이 지점에서 마지막 세미나를 종료하고 유지보수 자료로 연결합니다.

마지막 연결 질문

한 페이지를 요청한 순간부터 같은 frame을 다른 페이지 identity로 재사용할 때까지의 여정을 설명해 보겠습니다. 먼저 identity를 찾고, 메모리에 페이지를 담을 공간을 마련합니다. 사용을 보호할 fix나 pin을 얻고, 바이트 접근에 필요한 보호도 얻습니다. 페이지를 변경한 caller는 필요한 로그를 남기고 dirty 상태를 기록합니다. 사용을 반납한 뒤에도 페이지는 메모리에 남을 수 있고, dirty 상태도 별도로 남습니다. 이후 정책이나 caller에 따라 이미지 전달을 시작하고 완료 상태를 정리합니다. 마지막으로 현재의 보호 상태와 재사용 조건을 다시 확인한 뒤 identity를 바꿉니다.

Daemon이나 정책의 이름이 바뀌어도 확인할 질문은 같습니다. 지금 어느 페이지를 나타내고 있을까요? 누가 사용하고 있을까요? 어느 시점의 이미지가 보존됐을까요? 다음 단계를 진행할 책임은 누구에게 있고, 어떤 조건을 통과해야 할까요? CUBRID와 PostgreSQL의 차이는 이 질문에 답하는 구체적인 상태와 경로에서 찾을 수 있습니다.

각 기록에 이미지 identity와 정확한 수락·write·영속화 경계를 명시합니다. 이름 붙인 진행 중 이미지만 정리합니다. 현재 재사용에는 새 보호된 확보를 수행하고 새 사용이나 dirty 의무를 거절합니다. 실패하면 해당 의무를 재시도하며 기존 완료 기록을 현재 권한으로 승격하지 않습니다.

설명용 대안입니다. 명시적인 ticket·version 수명과 취소 소유권에는 metadata가 필요합니다. 연속 직렬화는 긴 배제를 선택하는 다른 대안입니다. 어떤 대체 방식도 WAL, 이미지 일관성, 새 의무, identity 수명, 발견 가능한 진행 경로를 함께 보존해야 합니다.

관측과 반증: 어떤 관측이 이 진단 설명에 반례가 되나요?.

현재 사용·dirty 상태, queue 소비, producer 배정, 수신 결과를 연결합니다. 관측이 없으면 기록을 만들어내지 않고 필요한 probe를 제안합니다. 여러 원인이 관측과 일치하면 유일한 근본 원인이라는 답을 지지할 수 없습니다. Observer 비용, scheduler 제어, 제한된 관찰 시간이 runtime 결론을 제한합니다.
