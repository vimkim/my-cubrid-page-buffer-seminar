앞선 두 세션에서 오늘로

화면 안내: 전용 발표 장: 없는 페이지를 읽으려면 안전한 메모리 자리가 필요하다 · 기다리는 요청 스레드가 변경 보존을 맡을 수도 있다 · 요청을 실제로 막는 원인을 찾기.

먼저 오늘 사용할 말을 짚고 시작하겠습니다. 페이지는 식별자가 있는 데이터 단위입니다. Frame은 페이지 하나를 담는 메모리 공간입니다. BCB는 그 frame에 지금 어느 페이지가 들어 있는지, 누가 사용하고 있는지를 관리하는 구조입니다. 스레드가 페이지를 fix하면 사용하는 동안 그 frame을 다른 페이지로 바꿀 수 없습니다. 스레드는 사용을 마칠 때 unfix로 그 사용 권한을 반납합니다. Dirty는 페이지의 변경 내용을 아직 저장 경로로 전달해야 한다는 상태입니다. Hot set은 반복해서 읽는 페이지들의 모음입니다.

이제 상황을 하나 만들겠습니다. 큰 스캔이 여러 페이지를 읽는 동안 writer, 즉 페이지를 변경하는 스레드가 변경 내용을 남겼습니다. 버퍼 pool의 모든 frame에는 이미 페이지가 들어 있습니다. 이때 스레드가 메모리에 없는 페이지 Q를 요청합니다. 페이지 P는 이미 메모리에 있습니다. 지금 P를 사용하는 스레드는 없지만, P에는 아직 기록해야 할 dirty 변경이 남아 있습니다.

이 상황을 세미나 전체를 연결하는 질문으로 사용하겠습니다. 각 실행 사례는 해당 절에 적힌 시작 상태에서 따로 시작합니다. 실제 서버에서 계속 이어진 하나의 실행 기록은 아닙니다. 같은 글자를 다른 사례에서 페이지나 스레드, 정책 영역의 이름으로 사용하면 그 역할을 다시 설명하겠습니다.

오늘은 두 사건을 따로 따라가겠습니다. 스레드가 페이지 사용을 끝내는 사건과, 변경 내용을 저장 경로에 기록하는 사건입니다. 이 둘을 구분하면서 어떤 스레드가 다음 요청에 쓸 frame을 준비하는지 살펴보겠습니다.

화면 안내: 화면: 요청한 페이지는 보호된 접근 권한을 얻어야 사용할 수 있다. 요청 → fix → 사용 → unfix까지만 먼저 짚습니다.

앞선 두 세션에서는 페이지 버퍼가 왜 필요한지, 페이지 ID와 메모리 frame이 어떻게 다른지 살펴봤습니다. BCB가 무엇을 기록하고, private/shared LRU가 메모리에 올라온 페이지를 어떻게 관리하는지도 알아봤습니다. 오늘은 그 모델을 완성하겠습니다. 빈 frame이 없을 때 다음 요청을 누가 진행시키는지, PostgreSQL은 같은 문제를 어떻게 푸는지 살펴보겠습니다.

앞서 배운 내용을 하나씩 떠올려 보겠습니다. 스레드가 페이지를 unfix해도 페이지는 메모리에 남아 있을 수 있습니다. 모든 스레드가 fix를 반납한 뒤에도 기록하지 않은 변경이 있으면 페이지는 dirty 상태입니다.

LRU3는 교체 정책이 후보를 찾는 차가운 영역입니다. 페이지가 LRU3에 있다는 사실만으로 그 내용을 덮어쓸 수는 없습니다. 로그가 필요한 페이지에서는 관련 로그를 페이지보다 먼저 영속화해야 합니다. 이것이 WAL 순서입니다. 영속화는 서버가 종료되더라도 필요한 기록이 남도록 저장하는 일입니다.

따라서 재사용을 판단할 때는 질문을 나누어야 합니다. 지금 frame에 어느 페이지가 들어 있습니까? 아직 그 페이지를 사용하는 스레드가 있습니까? 페이지 내용을 읽거나 바꾸는 스레드 사이의 접근은 어떻게 보호합니까? 저장 경로에 기록해야 할 변경이 남아 있습니까?

먼저 질문: 버퍼 pool에 빈 frame이 없습니다. 차가운 영역의 페이지 P를 fix한 스레드는 없지만 P는 dirty입니다. 새 페이지 Q를 요청한 스레드가 P의 frame을 사용하려면, 먼저 어떤 작업과 검사를 끝내야 할까요?

예측 후 발표자 답 보기

먼저 P의 변경에 필요한 로그를 페이지보다 앞서 영속화해야 합니다. 그리고 선택한 write 경로를 통해 P의 변경 내용을 기록해야 합니다. 그 사이 다른 스레드가 P를 다시 fix하거나 변경할 수 있습니다. 그러므로 재사용을 맡은 스레드는 현재 사용 상태와 dirty 상태를 다시 검사해야 합니다. P가 지금도 정책상 재사용 후보인지도 확인해야 합니다. P가 차가운 영역에 있다는 사실, fix가 남아 있지 않다는 사실, 이전 내용을 한 번 썼다는 사실은 각각 다른 검사에 답합니다.

이 질문을 중심으로 daemon의 역할을 살펴보겠습니다. 그 전에 dirty 페이지를 쓴다는 말이 어느 시점의 바이트를 뜻하는지부터 정리하겠습니다.

Q01 · 재사용 승인 규칙

구성한 시작 상태: 앞 사례와 별도로, 마지막 unfix 직후의 규칙을 바꾸는 제안을 살펴보겠습니다. fcnt == 0이면 외부에 reusable = true라는 알림을 보내자는 제안입니다. Fcnt는 남아 있는 fix의 수입니다. Allocator는 새 페이지를 담을 frame을 찾는 실행 주체입니다. 제안된 allocator는 이 알림만 믿고 frame에 담긴 페이지의 식별 정보인 identity를 바꿉니다. 이 알림 경로에서는 다른 기존 검사를 수행하지 않습니다.

예측 질문: Fcnt가 0이라는 이유만으로 재사용을 승인하면 어떤 실행 순서에서 문제가 생길까요? 가장 짧은 반례를 구성해 보세요.

논의 후 설명 보기

Writer가 페이지 P를 변경하고 dirty로 표시했다고 하겠습니다. 그 뒤 writer가 마지막 fix를 unfix로 반납합니다. 이제 fcnt는 0이지만, P의 변경 내용은 아직 기록하지 않았습니다. 이때 allocator가 frame의 identity를 바꾸고 새 페이지에 사용하면 P의 변경 내용을 잃습니다.

실제 재사용 경로에서는 다른 스레드의 상태 변경과 충돌하지 않도록 필요한 보호를 잡고 검사해야 합니다. 현재 flag와 identity, 대기 스레드, 정책 조건을 함께 확인합니다. Unfix는 스레드의 페이지 사용을 끝냅니다. 페이지 이미지를 저장 경로에 전달하는 작업은 기록해야 할 변경을 처리합니다.

화면 안내: 확장 화면 순서: 없는 페이지를 읽으려면 안전한 메모리 자리가 필요하다 (EN)

오늘은 각 메커니즘의 필요성을 설계 심사에서 설명한다고 생각해 보겠습니다. 먼저 어떤 문제를 해결하는지 보겠습니다. 그다음 특정 검사나 기록을 제거했을 때 어느 실행 순서에서 결과가 달라지는지 따져 보겠습니다. 다른 설계가 같은 요구를 안전하게 충족할 수도 있습니다. 그런 대안을 제시할 때는 추가로 필요한 상태와 동기화를 설명해야 합니다. 어떤 스레드가 더 오래 기다리게 되는지도 함께 설명해야 합니다.

안전성, 요청의 진행, 교체 정책의 품질, 성능은 각각 확인해야 합니다. 잘못된 재사용을 안전하게 거절했더라도 요청은 계속 기다릴 수 있습니다. 소스 구조를 보고 설명한 기능적 이유는 Inference, 즉 근거가 있는 추론으로 구분하겠습니다. 그것만으로 원저자가 당시 어떤 의도로 설계했는지 확인할 수는 없습니다. 오늘 구성한 실행 순서는 성능 측정이나 crash 실험의 결과가 아닙니다.

화면 안내: 대안의 전이: 기다리는 요청 스레드가 변경 보존을 맡을 수도 있다.

이번에는 frame을 기다리는 요청 스레드가 필요한 쓰기를 직접 맡는 대안을 가정하겠습니다. 요청 스레드는 먼저 후보의 페이지 식별 정보와 현재 사용 상태를 검사합니다. 후보 페이지가 dirty라면 적합한 페이지 내용이 바뀌지 않도록 필요한 보호를 확보합니다. 스레드는 그 내용에 필요한 로그를 먼저 영속화하고 페이지 이미지를 씁니다.

쓰기와 완료 처리를 마친 뒤에는 후보의 현재 상태를 다시 검사합니다. 그 상태를 바탕으로 frame 획득을 다시 시도합니다. 쓰기가 실패하면 다시 기록해야 할 변경이 있다는 dirty 정보를 유지합니다. 요청 처리에 사용한 임시 자원은 정리합니다.

이것은 요청을 처리하는 foreground 경로에서 쓰기를 맡기는 설계 대안입니다. CUBRID의 모든 server fallback이 정확히 이 순서로 동작한다고 주장하는 설명은 아닙니다. 이 설계에서는 로그와 저장장치 I/O 시간이 요청의 대기 시간에 포함됩니다. 쓰기를 끝낸 뒤에도 스레드는 frame 재사용에 필요한 동기화를 확보해야 합니다. 그 상태에서 현재 조건에 적합한 clean frame을 얻어야 합니다.

화면 안내: 관측과 반증: 요청을 실제로 막는 원인을 찾기.

이제 실제 원인을 구분하기 위한 관측을 계획하겠습니다. 요청 스레드가 frame 할당을 기다리기 시작한 시각과 끝낸 시각을 기록합니다. 후보의 적합성은 필요한 보호를 잡은 상태에서 확인합니다. 그리고 어떤 공급자, 즉 frame을 준비하는 실행 주체가 실제 배정을 수행했는지 연결해서 기록합니다.

Pool 전체에 clean 페이지가 몇 개 있다는 숫자만으로 이 요청이 받을 frame이 있다고 판단할 수는 없습니다. 이 요청에 배정할 수 있는 적합한 frame이 있는데도 요청 스레드가 다른 곳에서 기다린다면, 변경 기록이 요청을 막는다는 설명을 다시 검토해야 합니다. 이 관측 계획만으로 요청 사이의 공정성이나 전체 처리량을 입증할 수는 없습니다.

02 · FLUSH BRIDGE

한 페이지, 두 세대

화면 안내: 전용 발표 장: 가득 찬 풀에서 변경된 페이지를 안전하게 기록하려면? · 사본 없는 대안은 I/O가 끝날 때까지 writer를 배제한다 · 이전 완료 전후에 이후 dirty 신호가 남는지 관찰한다.

이번 장의 사례는 앞 사례와 독립적으로 시작합니다. 요청 스레드는 아직 메모리에 없는 페이지 Q를 읽으려 합니다. 페이지 P는 메모리의 frame에 있고 dirty 상태입니다. Flusher는 P의 내용을 저장 경로로 보내는 실행 주체입니다. Writer는 P를 변경하는 실행 주체입니다.

Flusher가 확보한 P의 사본을 G라고 부르겠습니다. 사본을 확보한 뒤 writer가 메모리의 P에 새 변경을 남기면 그 이후 변경을 G+1이라고 부르겠습니다. G와 G+1은 실행 순서를 설명하기 위한 이름입니다. 실제로 저장된 세대 번호는 아닙니다. Flusher가 G를 전달하는 동안 writer가 새 변경을 남길 수 있을 때, 완료 처리가 어떤 상태를 지워도 되는지 살펴보겠습니다.

화면 안내: 화면 순서: Flush는 안정된 페이지 사본을 저장 경로에 제출한다 → 고정된 사본이 있으면 이후 writer는 계속 진행할 수 있다 → 복구 로그가 페이지 이미지보다 먼저 살아남아야 한다 → 보호를 풀기 전에 바이트와 로그 관리 정보를 함께 확보한다 → 안정된 사본과 DWB가 해결하는 문제는 다르다 → 이전 완료 처리는 새 작업을 계속 드러내야 한다.

저장된 페이지의 값이 10이라고 하겠습니다. Writer가 메모리의 값을 11로 바꾸면 저장된 내용과 메모리의 내용이 달라집니다. Writer는 아직 저장 경로로 보내야 할 변경이 있다는 뜻으로 DIRTY를 설정합니다. Writer가 unfix로 페이지 사용을 끝내더라도, 값 11을 기록해야 하는 작업은 남아 있습니다.

WAL에서 핵심은 로그와 페이지를 쓰는 순서입니다. 로그가 필요한 영구 페이지를 다룬다고 하겠습니다. 그 페이지의 변경을 설명하는 로그가 데이터 페이지보다 먼저 영속화되어야 합니다. 페이지 LSA는 해당 페이지 내용이 어느 로그 위치까지의 변경을 반영하는지 나타냅니다. Flusher는 필요한 로그가 먼저 보존됐는지 확인하고 페이지 이미지를 전달합니다. 트랜잭션의 commit, 페이지 write, 페이지 사용을 끝내는 unfix는 서로 다른 작업을 완료합니다.

앞서 값이 11이 된 페이지에서 이어가겠습니다. Flusher가 값 11을 담은 안정된 사본을 확보했다고 하겠습니다. Flusher가 사본을 전달하는 사이, writer가 메모리의 값을 12로 바꿀 수 있습니다. 이때 제출하는 사본 11을 G라고 부릅니다. 사본 확보 뒤 메모리에 생긴 변경을 G+1이라고 부릅니다. Generation, 즉 세대라는 말은 두 작업을 구분하기 위한 설명입니다. 엔진에 그 세대 번호나 카운터가 저장돼 있다는 뜻은 아닙니다.

여기서 flush는 flusher가 안정된 페이지 사본을 페이지 저장 경로에 제출하는 일입니다. DWB는 double-write buffer입니다. DWB를 사용하는 경로에서는 메모리 slot에 사본을 접수하는 것만으로 페이지 버퍼 flush가 성공할 수 있습니다. 하지만 그 사본이 영속화되기 전에 crash가 나면 사본도 메모리와 함께 사라집니다.

로그가 기록된 영구 페이지를 복구할 때는 먼저 영속화한 WAL과 살아남은 홈 페이지를 사용합니다. 제출한 사본 자체가 남아 있다는 사실과, 로그를 사용해 변경을 복구할 수 있다는 사실을 구분해야 합니다.

DWB는 이미지를 접수한 뒤 중간 저장 파일에 쓰고 동기화합니다. 원래 데이터 볼륨인 home volume에 쓰고 동기화하는 단계는 별도로 있습니다. 유효한 중간 저장 이미지가 보존돼 있으면 DWB 복구 절차가 일부만 쓰인 홈 페이지를 수리할 수 있습니다. 따라서 page-flush의 성공 반환만으로 이 쓰기와 영속화 단계들이 모두 끝났다고 말할 수는 없습니다.

이제 처음 질문을 조금 더 정확하게 바꿔 보겠습니다. 누가 G의 전달을 시작하고, 누가 G의 완료 상태를 정리할까요? 그리고 현재 메모리의 페이지가 재사용 가능한 상태인지 누가 검사할까요?

Q02 · 사본의 로그 기준

구성한 시작 상태: 별도의 로그 순서 사례입니다. 로그가 필요한 영구 페이지에서 안정된 사본 G와 그 사본의 페이지 LSA 120을 함께 확보했습니다. 이후 writer가 메모리의 페이지를 더 변경해 현재 페이지 LSA는 180이 됐습니다. WAL은 140까지 영속화됐습니다. Flusher는 아직 사본 G를 제출하지 않았습니다.

예측 질문: 사본 G에 필요한 WAL을 어디까지 영속화해야 할까요? 사본의 120, 현재 페이지의 180, 영속화된 WAL의 140을 각각 어떤 판단에 사용하겠습니까?

논의 후 설명 보기

제출할 사본 G의 LSA는 120입니다. WAL은 이미 140까지 영속화됐으므로 G에 필요한 로그는 보존돼 있습니다. 현재 메모리 페이지의 LSA 180은 사본 확보 뒤의 변경에 속합니다. G의 내용은 그대로 두면서 180까지의 WAL을 기다리게 하면 이 사본에는 필요하지 않은 로그 작업까지 기다리게 됩니다.

구현의 검사 지점도 나누어 보겠습니다. 후보 선택의 사전 검사는 그때 메모리에 있는 페이지의 LSA를 봅니다. 공통 helper, 즉 공통 처리를 맡은 함수는 자신이 확보한 사본의 LSA를 전달합니다.

선택 후속 질문: 사본 G를 제출하면서 현재 메모리 페이지의 LSA를 기준으로 기다리게 하면, 어떤 로그 작업을 추가로 기다리게 되나요?

Q03 · 값이 다시 같아진 페이지

구성한 시작 상태: 앞 사례와 독립적으로 시작합니다. 사본 G에는 값 40과 페이지 LSA 120이 들어 있습니다. G의 쓰기가 진행되는 동안 writer가 메모리의 같은 필드를 41로 바꿉니다. Writer는 그 값을 다시 40으로 바꾸고 두 변경을 모두 로그에 기록합니다. 현재 메모리 페이지의 LSA는 180이고 DIRTY는 설정돼 있습니다. 이제 사본 G의 제출이 성공했습니다.

예측 질문: 현재 값이 다시 40이 됐다는 이유로 완료 처리에서 DIRTY를 지워도 될까요? 그 값 비교로 확인할 수 있는 범위는 어디까지일까요?

논의 후 설명 보기

현재 값과 G의 값이 모두 40이어도 완료 처리는 현재 DIRTY를 지울 수 없습니다. G에는 LSA 120까지의 내용이 들어 있습니다. Writer가 그 뒤에 기록한 변경의 로그 위치는 180까지입니다. 따라서 완료 처리는 이전 G에 해당하는 FLUSHING만 해제합니다. 새 변경의 DIRTY와, 아직 기록하지 않은 변경의 가장 오래된 로그 위치인 oldest-unflush 하한은 남깁니다. 한 필드의 값이 같은지만 비교해서 두 쓰기 작업이 모두 끝났다고 판단할 수는 없습니다.

선택 후속 질문: 아직 기록해야 할 변경이 있는지 설명하려면 필드 값 외에 어떤 로그 이력과 상태를 확인해야 하나요?

Q04 · 완료 기록의 범위

구성한 시작 상태: 별도의 완료 기록 사례입니다. 구성한 로그에는 DWB가 사본 G를 받아들였다는 기록과 BCB의 FLUSHING이 해제됐다는 기록만 있습니다. 그 뒤 페이지에 새 변경은 없습니다. Home volume에 대한 write와 fsync, 재시작 뒤 복구 결과는 기록하지 않았습니다.

예측 질문: 이 기록으로 어떤 작업이 끝났다고 말할 수 있나요? 확인하지 않은 저장 단계까지 포함하지 않고 가장 강한 주장을 적어 보세요.

논의 후 설명 보기

이 기록으로는 DWB가 flusher가 제출한 사본 G를 받아들였고 페이지 버퍼의 완료 처리가 끝났다고 말할 수 있습니다. Home volume에도 전달됐다고 말하려면 이후의 write를 확인해야 합니다. 재시작 후에도 내용이 보존됐다고 말하려면 저장 동기화인 synchronization과 해당 recovery 결과를 추가로 확인해야 합니다.

선택 후속 질문: Home volume에도 내용이 영속화됐다고 말하려면 어떤 사건을 추가로 기록해야 하나요?

화면 안내: 상태 변화 화면: 이전 사본을 완료해도 이후 dirty 신호는 남긴다. 시작 상태를 확인하고 다음 단계에서 달라지는 필드를 예측합니다. 이 사례는 독립적으로 초기화합니다.

근거: flush의 기준 설명. 자세한 소스 위치는 준비 계획의 소스 추적 경로에 있습니다.

화면 안내: 확장 화면 순서: 가득 찬 풀에서 변경된 페이지를 안전하게 기록하려면? (EN) → 호출자의 보호 조건이 사본을 신뢰할 수 있게 한다 (EN) → Dirty bit 하나로 처리하면 이후 writer의 작업을 지울 수 있다 (EN) → 안전한 대안은 바이트를 고정하고 해당 작업만 완료해야 한다 (EN) → 로그 순서를 지켜도 페이지 쓰기가 원자적이 되는 것은 아니다 (EN) → D25 · 데이터 값이 같으면 다음 flush를 생략해도 될까? (EN)

첫 화면에서는 사본을 만드는 이유부터 살펴보겠습니다. 느린 페이지 write 중에도 writer가 계속 변경하도록 허용하려면, flusher가 제출할 페이지 바이트와 그 내용의 LSA를 함께 고정해야 합니다. 먼저 caller, 즉 함수를 호출하는 스레드가 적합한 소유권과 latch 조건을 확보해야 합니다. BCB mutex만 잡았다고 이미 WRITE 권한을 가진 다른 스레드의 변경까지 막는 것은 아닙니다.

검사를 제거하는 화면에서는 같은 시작 상태를 세 경로에 사용합니다. 첫 경로는 사본과 WAL 순서를 유지하면서 이후 변경을 구분하는 기록만 제거합니다. 그러면 G의 완료 처리가 G+1의 기록해야 할 변경까지 지울 수 있습니다. 다른 경로에서는 페이지 write가 끝날 때까지 writer의 변경을 막습니다. 이 대안은 안전할 수 있지만 writer가 저장장치 지연을 기다려야 합니다. 각 단계에서 바뀐 필드와 결과를 확인하고, 다음 경로를 시작할 때 상태를 초기화하겠습니다.

Torn page는 쓰기가 중간에 끊겨 페이지의 일부만 기록된 상태입니다. 안정된 사본을 만들거나 WAL 순서를 지키는 것만으로 이 문제를 모두 해결할 수는 없습니다. DWB는 먼저 중간 저장 영역에 staging write를 수행하고 동기화합니다. 그 뒤 home write를 수행하며, 복구할 때 유효한 사본을 사용합니다. DWB가 이미지를 수락한 사건만으로 이 단계들이 끝났다고 판단할 수는 없습니다. 두 사본이 함께 손실되거나 저장장치의 storage sync가 필요한 보존을 수행하지 못한 상황은 별도로 검토해야 합니다. D25에서는 필드 값이 같아도 header, 로그 이력, 남아 있는 dirty 기록 작업은 다를 수 있다는 점을 설명하겠습니다.

화면 안내: 대안의 전이: 사본 없는 대안은 I/O가 끝날 때까지 writer를 배제한다.

이번에는 페이지 사본을 만들지 않는 대안을 생각해 보겠습니다. 쓰기를 맡은 스레드는 먼저 다른 writer가 페이지 내용을 바꾸지 못하도록 필요한 보호를 확보합니다. 쓰기 스레드는 제출할 페이지 내용을 변경되지 않는 상태로 유지합니다. 그 내용에 대응하는 페이지 LSA를 확인합니다. 그런 다음 필요한 로그를 먼저 영속화하는 WAL force를 수행합니다. 페이지 내용을 저장 경로에 제출하는 동안에도 다른 writer의 변경을 계속 막습니다.

쓰기가 성공하면 스레드는 이번에 기록한 내용에 대한 완료 처리를 마칩니다. 그 뒤 다른 writer가 페이지를 변경하도록 허용합니다. 쓰기가 실패하면 나중에 다시 기록할 수 있도록 DIRTY와 oldest-unflush 정보를 남깁니다. 임시 상태를 정리하고 변경을 막던 보호를 해제합니다.

이것은 설명을 위해 구성한 대안입니다. 별도 이미지를 줄이는 대신 다른 writer가 로그와 저장장치 I/O를 기다려야 합니다. Immutable 버전 이미지, 즉 확보 뒤 내용이 바뀌지 않는 버전을 유지하는 대안도 있습니다. 그 대안에는 버전을 언제 해제할지 정하는 protocol이 추가로 필요합니다. 어느 대안이든 torn write를 처리하려면 저장과 복구 protocol을 따로 갖춰야 합니다.

화면 안내: 관측과 반증: 이전 완료 전후에 이후 dirty 신호가 남는지 관찰한다.

이제 관측 지점을 추가하는 probe 계획을 보겠습니다. 사본의 LSA와 현재 페이지의 LSA를 각각 기록합니다. 사본 확보 전, writer의 새 변경 후, 이전 사본의 완료 후에 DIRTY와 FLUSHING을 기록합니다. DWB 수락, staging sync, home sync의 시각도 각각 기록합니다. 이전 완료 처리가 이후 변경의 기록까지 지운다면 새 변경을 남긴다는 설명에 반례가 됩니다. Crash 복구 결과를 해석하려면 오류를 넣은 fault 지점과 storage 가정이 필요합니다. Flag 기록만으로 영속화를 증명할 수는 없습니다.

03 · FOUR LOOPS

네 daemon은 서로 다른 일을 한다

화면 안내: 전용 발표 장: 요청한 페이지를 담을 자리에 변경 내용이 남아 있다 · 단일 스케줄러는 I/O 중에도 다른 일을 실행할 수 있어야 한다 · 사라진 깨우기와 남아 있는 작업을 따로 기록한다.

이번 장은 새 페이지 요청에서 따로 시작합니다. Pool의 모든 frame에 페이지가 들어 있습니다. 읽으려는 페이지 S3는 아직 메모리에 없습니다. 다른 페이지 S4는 메모리에 있지만 지금 사용하는 스레드는 없습니다. S4에는 아직 기록하지 않은 dirty 변경이 남아 있습니다. Frame은 페이지 하나를 담는 메모리 공간이고, BCB는 그 공간의 현재 페이지와 사용 상태를 관리하는 구조입니다. 먼저 S4의 변경을 안전하게 기록하면 frame 재사용을 준비할 수 있습니다. 쓰기를 마친 뒤에도 재사용을 맡은 스레드는 현재 사용 상태를 다시 검사해야 합니다.

S3를 요청한 스레드가 준비 작업을 모두 직접 맡는다고 생각해 보겠습니다. 그 스레드는 S4에 필요한 WAL을 보존하고, 페이지를 쓰고, BCB의 완료 처리를 마칠 때까지 기다릴 수 있습니다. WAL은 페이지보다 먼저 영속화해야 하는 변경 로그입니다.

CUBRID의 네 daemon은 이와 관련된 일을 따로 맡습니다. 페이지 이미지 전달, BCB 완료 처리, 페이지를 얼마나 보존할지 정하는 정책 조정, write 이후의 속도 조절입니다. 역할을 나누는 방식은 구현 정책입니다. 다른 설계에서 역할을 합쳐도 필요한 기록 작업과 공유 상태 검사는 수행해야 합니다.

Quota는 private LRU가 보존할 페이지 수의 목표입니다. Direct victim은 frame을 기다리는 allocator에게 직접 제안하는 후보입니다. 그 제안을 받은 뒤에도 실제 재사용 전의 검사는 필요합니다.

화면 안내: 화면: 네 작업은 서로 다른 네 종류의 상태를 바꾼다 → 각 스레드는 태스크를 실행한 뒤 대기 시간을 정한다 → 복구는 작업을 허용하고 종료는 작업이 끝나기를 기다린다.

Daemon은 백그라운드 스레드입니다. 맡은 작업을 실행하고, 대기한 뒤 다시 작업을 실행합니다. CUBRID 서버의 페이지 버퍼 daemon들은 공통 thread manager를 이용합니다. 네 스레드가 같은 작업을 나누어 처리하는 구조는 아닙니다. 각 daemon은 자기 작업, 대기 방식, 확인할 공유 상태를 따로 갖습니다.

여기서 탐색한다고 할 때 무엇을 훑는지 나누어 보겠습니다. Page-flush는 BCB 배열 전체를 순서대로 보는 방식이 아닙니다. 먼저 각 LRU의 크기와 quota를 읽고 탐색 비중을 계산합니다. 대상 LRU 하나를 잠그고 꼬리에서 BCB 링크를 따라 올라갑니다. LRU3 구역에서 배정된 개수만큼만 봅니다. Clean BCB도 방문 개수에 포함됩니다. Dirty 후보를 저장한 뒤에는 BCB를 잠그고 현재 상태를 다시 확인해야 합니다. 계속 압력이 있으면 다음 후보 수집도 꼬리에서 시작합니다.

Maintenance는 갱신 조건을 통과하면 모든 private/shared LRU의 통계 숫자를 읽습니다. 이어서 private의 quota와 구역 목표 크기를 갱신하고, shared의 구역 목표 크기를 갱신합니다. 보호 구역이 넘치는 리스트에서는 경계의 BCB만 필요한 만큼 내립니다. 목표를 크게 줄이면 이동할 BCB도 많아질 수 있습니다. 이 quota 경로와 별도로 직접 후보를 제안하려는 백업 함수는 기준 리비전에서 루프 본문을 건너뜁니다. Post-flush는 완료 큐에서 BCB 포인터를 꺼내고, flush-control은 시간과 크레딧 상태를 읽습니다.

표에 적힌 주기는 실제 실행 횟수를 보장하는 숫자가 아닙니다. 공통 daemon 구현은 먼저 작업을 한 번 실행합니다. 그다음 정해진 주기에서 직전 작업에 쓴 시간을 빼고 남은 시간만큼 기다립니다. 실제 실행에는 스케줄러 지연이나 I/O 시간도 영향을 줍니다. 따라서 타이머가 끝났다는 사건과, daemon이 필요한 작업을 실제로 마쳤다는 사건을 따로 기록해야 합니다.

Wakeup은 대기 중인 스레드를 깨우는 알림입니다. 여기서 waiter는 daemon의 대기 상태를 관리하는 객체입니다. Waiter가 SLEEPING 상태일 때만 wakeup이 대기를 깨웁니다. RUNNING 상태에서 받은 wakeup은 다음 대기를 위한 횟수로 저장하지 않습니다.

그러므로 daemon의 작업은 공유 상태에 남아 있는 frame 부족 조건이나 queue를 보고 할 일을 판단해야 합니다. Wakeup만 기다리는 설정에서는 새 작업이 생긴 뒤 어떤 스레드가 언제 깨우는지도 확인해야 합니다.

생성과 작업 허용을 나누어 설명하기

생성 순서를 따라가겠습니다. Pool 초기화는 BCB와 LRU, quota·monitor 배열, 서버용 queue를 먼저 마련합니다. 서버를 재시작하는 xboot_restart_server()는 DWB에 남은 페이지를 복구합니다. 그 뒤 pgbuf_daemons_init()을 호출합니다. 이 함수는 maintenance, page-flush, post-flush, flush-control 순서로 생성을 시도합니다. 이것은 daemon을 만드는 순서입니다. 페이지가 이 네 역할을 같은 순서로 통과하는 실행 경로를 뜻하지는 않습니다.

서버 초기화는 이어서 DWB helper를 생성하고 로그 초기화와 복구를 수행합니다. boot_after_copydb()를 거친 뒤 boot gate를 엽니다. Boot gate는 각 task가 공유 상태를 다루는 본 작업을 시작해도 되는지 나타내는 조건입니다.

Daemon 스레드가 이미 있어도 task가 닫힌 gate를 확인하면 본 작업 없이 반환합니다. Gate를 여는 동작은 그 자체로 wakeup을 보내지 않습니다. Daemon이 이후 타이머나 작업 알림으로 다시 실행할 때 열린 gate를 확인합니다.

공통 manager는 스레드를 관리할 thread entry를 예약합니다. 새 스레드 안에서는 실행 context를 만듭니다. 스레드 종류를 TT_DAEMON으로, 트랜잭션 인덱스를 LOG_SYSTEM_TRAN_INDEX로 지정합니다. Error context도 설정합니다. 정상 구성에서 최대 네 daemon을 만들 수 있습니다.

생성이 항상 성공한다고 가정해서는 안 됩니다. Pool 할당이 오류 반환으로 실패하면 pgbuf_finalize()가 관련 자원을 정리합니다. 하지만 manager가 entry 부족으로 NULL을 반환하는 경로에는 다른 경계가 있습니다. 역할 초기화 함수는 그 실패를 별도로 처리하지 않으며, manager가 소유하지 못한 task를 retire하지도 않습니다. 이 생성 지점에는 할당이나 스레드 생성 예외를 지역적으로 복구하는 wrapper도 없습니다.

이 설명은 고정 소스에서 확인한 정리 책임의 범위입니다. 운영 서버에서 해당 실패가 발생했다는 관측은 아닙니다. Control 초기화 실패는 07장에서 따로 설명하겠습니다.

종료에서 누가 언제 정리하는가

종료 순서는 누가 무엇을 하는지 나누어 보겠습니다. 종료를 요청하는 caller는 stop을 표시합니다. 대기 중인 daemon을 깨운 뒤 join()으로 스레드 종료를 기다립니다. Worker는 실행 중인 task에서 돌아와 loop를 빠져나갑니다. 이어서 실행 context를 정리하고 task의 retire()를 호출합니다. Control이 사용하는 bucket도 이때 정리합니다.

Worker가 종료한 뒤 join이 반환합니다. 그다음 manager가 daemon을 삭제하고 포인터를 비웁니다. 따라서 join이 반환한 시점에는 해당 task의 정리도 끝났다고 확인할 수 있습니다.

종료를 기다리는 동안에는 BCB와 queue처럼 daemon이 접근할 저장 공간을 유지해야 합니다. Stop은 실행 중인 I/O를 취소하지 않습니다. Join이 얼마 안에 끝난다는 시간 상한도 주지 않습니다.

정상 종료는 이 daemon group을 멈춘 뒤 log_final()과 DWB·pool 정리를 수행합니다. Restart 오류 경로는 boot gate를 먼저 닫습니다. 그 뒤 page-buffer와 DWB daemon group을 정리하고 나머지 의존 자원을 해제합니다. Stand-alone 빌드에는 이 네 daemon group이 없습니다. 필요한 page-flush는 해당 작업을 호출한 스레드가 동기적으로 수행합니다.

화면 안내: 확장 화면 순서: 요청한 페이지를 담을 자리에 변경 내용이 남아 있다 (EN) → 요청한 페이지를 담을 자리에 변경 내용이 남아 있다 (EN) → 큐 대신 깨우기만 쓰면 미처리 작업을 잃을 수 있다 (EN) → 요청한 페이지를 담을 자리에 변경 내용이 남아 있다 (EN) → 공유 저장 영역은 접근하는 모든 워커보다 오래 살아야 한다 (EN) → D26 · 50 ms 목표 주기로 기록 완료 횟수를 셀 수는 없다 (EN)

네 역할을 다시 연결해 보겠습니다. Page-flush는 페이지 이미지를 저장 경로에 보냅니다. Post-flush는 CPU에서 BCB 완료 처리를 하고 조건이 맞을 때 frame을 제안합니다. Maintenance는 메모리에 얼마나 보존할지 조정합니다. Control은 write 이후의 속도 조절에 사용할 예산을 마련합니다. 네 역할이 하나의 pipeline에서 차례대로 실행되는 것은 아닙니다. 역할을 요청 스레드나 하나의 worker로 옮기는 대안도 가능합니다. 그때는 느린 I/O가 다른 역할의 실행을 막지 않도록 실행 구조를 설계해야 합니다.

Wakeup이 나중에 처리할 사건으로 항상 저장된다고 가정해 보겠습니다. Waiter가 RUNNING일 때 받은 알림이 그 가정의 반례가 됩니다. 공유 queue에는 미처리 작업을 남길 수 있습니다. 하지만 queue에 작업이 있다는 사실만으로 다음 task의 실행 시각이 정해지지는 않습니다. 작업이 남아 있다는 조건과 waiter가 대기를 끝낼 수 있다는 조건을 따로 확인해야 합니다. 타이머가 실행 기회를 주더라도 boot gate, 스케줄링, lock 획득, I/O 조건은 여전히 확인해야 합니다.

종료 caller가 stop을 표시한 뒤에도 실행 중인 task는 반환해야 합니다. 대기 중인 스레드는 깨어나야 합니다. Caller는 join으로 worker의 종료를 확인한 뒤 공유 자원을 해제해야 합니다. D26에서 다루는 50 ms는 목표 주기입니다. Writer의 쓰기가 50 ms 안에 끝나야 한다는 기한은 아닙니다.

화면 안내: 대안의 전이: 단일 스케줄러는 I/O 중에도 다른 일을 실행할 수 있어야 한다.

이번에는 하나의 스케줄러가 여러 역할을 실행하는 대안을 구성하겠습니다. 스케줄러는 각 역할에 아직 처리하지 않은 일을 나타내는 pending 상태를 둡니다. 일시적인 wake bit만으로 작업을 기억하지 않습니다. 스케줄러는 준비된 작업을 선택합니다. 느린 I/O를 시작하기 전에는 완료 뒤 이어서 할 일을 continuation으로 남깁니다. I/O 완료를 처리하는 동안 quota와 pacing 작업도 실행할 수 있게 합니다.

종료 시에는 새 작업을 넣는 producer를 먼저 닫습니다. 정해진 규칙에 따라 continuation을 끝내거나 취소합니다. 그 뒤 worker를 join하고 공유 상태를 해제합니다.

이것은 설명용 대안입니다. Foreground가 직접 처리하면 기다리는 시간이 caller의 지연으로 들어갑니다. 하나의 통합 worker가 blocking I/O를 수행하면 그 대기가 나머지 역할도 늦출 수 있습니다. 기다리는 동안 다른 일을 실행하는 nonblocking 대안에는 queue와 continuation, 취소를 맡는 주체, 스케줄링 정책이 추가로 필요합니다. I/O와 공정성에 관한 가정 없이 전체 처리 시간의 상한을 계산할 수는 없습니다.

화면 안내: 관측과 반증: 사라진 깨우기와 남아 있는 작업을 따로 기록한다.

먼저 기존 framework 통계로 loop 실행, wake, sleep 사건을 찾겠습니다. 추가 기록에는 작업을 공유 상태에 올린 시각, waiter 상태, task 진입 시각, 당시 실행 조건을 연결하겠습니다. Wake 횟수만 세면 어떤 작업을 처리했는지 알 수 없습니다. 이 사례의 전제에서 남아 있는 pending 작업을 다시 발견할 경로가 기록되지 않는다면, 제안한 진행 설명에 반례가 됩니다. 스케줄러가 멈춘 상황은 관측 시간에 영향을 줍니다. 유한한 기록만으로 영구적인 starvation, 즉 요청이 끝없이 처리 기회를 얻지 못하는 상태를 증명할 수는 없습니다.

Page-flush: 기억한 후보를 다시 검사한다

화면 안내: 전용 발표 장: 기억한 후보를 왜 다시 검사해야 할까? · 예약으로 보호 공백의 경쟁을 막을 수 있을까? · 오래된 후보와 지연된 쓰기를 어떤 관측으로 구분할까?.

이번 장은 후보를 수집하는 독립적인 사례입니다. 페이지 P는 dirty이고 지금 사용하는 스레드는 없습니다. Page-flush 스레드는 LRU list lock을 잡습니다. P를 관리하는 BCB의 포인터와 P의 VPID를 기억합니다. VPID는 논리 페이지의 식별자입니다.

Page-flush는 list lock을 놓은 뒤 나중에 BCB를 잠급니다. 그 사이 다른 스레드가 실행될 수 있습니다. BCB의 주소가 같아도 그 frame에 담긴 페이지나 사용 상태, dirty 상태는 바뀔 수 있습니다. 따라서 후보를 수집할 때 본 상태를 지금의 작업을 허가하는 근거로 그대로 사용할 수는 없습니다.

화면 안내: 화면: 선택한 사본은 어떤 호출을 거쳐 제출될까? → Worker는 언제 필요한 작업을 찾을까? → 후보 관찰은 어떻게 flush 결정으로 이어질까?.

새 페이지를 요청한 allocator가 빈 invalid frame도, 바로 사용할 clean victim도 찾지 못했다고 하겠습니다. Page-flush는 차가운 dirty 페이지를 골라 기록하면서 clean 후보가 생기도록 돕습니다. 타이머가 끝날 때마다 모든 dirty 페이지를 쓰지는 않습니다. 할당을 기다리는 요청이 있는지, hit ratio가 낮은지 확인해 계속할 일이 있는지 판단합니다. Boot gate를 통과한 실행에서 daemon이 wakeup으로 깨어났다고 판단하면 후보 flush를 최소 한 번 호출합니다. 이 호출 조건은 고정 소스에서 확인한 내용입니다.

화면 안내: Flush 대기자와 프레임 대기자는 어디서 생길까? → 두 종류의 대기자는 왜 다른 결과를 기다릴까?.

먼저 누가 왜 기다리는지 구별하겠습니다. Flush 대기자는 dirty 페이지를 동기 flush하려다가 이미 진행 중인 flush를 기다리는 스레드입니다. 프레임 할당 대기자는 메모리에 없는 페이지를 읽으려는데 빈 자리도 교체할 자리도 구하지 못한 스레드입니다. Page-flush와 post-flush는 이들의 진행을 도울 작업을 합니다. 이전 사본의 완료 처리가 끝나도 메모리에 새 dirty 변경이 남아 있으면 그 프레임을 다른 페이지에 줄 수 없습니다.

설정 변경은 어느 실행부터 보이는가

설정을 바꾸는 사례도 보겠습니다. 고정 리비전에 등록된 이름은 page_flush_interval입니다. 기본값은 1,000 ms입니다. 허용 범위는 0부터 INT_MAX ms까지입니다. 이전 이름 page_flush_interval_in_msecs는 사용을 권하지 않는 deprecated alias입니다. 내부 PRM 식별자와 실제 설정 이름을 구분해야 합니다.

DBA는 SET SYSTEM PARAMETERS 'page_flush_interval=1000ms'로 서버 전체가 사용하는 실행 중 registry 값을 바꿀 수 있습니다. 이 SQL은 cubrid.conf 파일을 저장하지 않습니다. 재시작 뒤에도 값을 유지하려면 설정 파일을 따로 수정해야 합니다.

Looper는 daemon의 반복 실행과 대기를 관리합니다. 다음 pause, 즉 대기 시간을 정하는 지점에서 새 interval을 읽습니다. Interval을 0으로 설정하면 timeout 없이 wakeup만 기다립니다. Daemon 객체를 제거하는 설정은 아닙니다.

이미 무한 대기 중인 daemon의 interval을 0에서 양수로 바꿨다고 하겠습니다. Setter, 즉 설정값을 바꾸는 처리는 daemon을 깨우지 않습니다. 별도의 작업 wakeup 등으로 daemon이 다시 진행해 다음 pause에 도달해야 새 값을 사용합니다. 값을 반복해서 읽는지, DBA가 바꿀 수 있는지, 현재의 대기를 즉시 끝내는지는 서로 다른 질문입니다.

핵심 함수는 pgbuf_flush_victim_candidates()입니다. Page-flush 스레드는 LRU mutex를 잡은 상태에서 차가운 후보의 BCB 포인터와 VPID를 기억합니다. 그다음 list lock을 놓고 각 후보의 BCB를 검사합니다.

다른 스레드가 중간에 실행할 수 있으므로 page-flush는 BCB mutex를 잡은 뒤 현재 상태를 다시 확인합니다. VPID가 기억한 페이지와 같은지 확인합니다. 지금 dirty인지, 이미 flushing 중인지도 확인합니다. 아직 차가운 후보인지, 남아 있는 fix가 없는지도 검사합니다.

선택한 페이지 이미지에 필요한 WAL이 아직 영속화되지 않았다고 하겠습니다. Page-flush는 그 후보를 당장 제출할 수 없습니다. Log-flush를 깨워 로그 작업이 진행되게 합니다. 또는 frame 부족을 처리하는 경로에서 필요한 로그 작업을 마친 뒤 다시 시도합니다.

제출 조건을 만족하면 스레드는 페이지의 안정된 사본을 만들고 공통 flush 경로로 전달합니다. 화면의 짧은 소스 추적에서는 이웃 페이지 묶음과 DWB를 사용하지 않는 분기 하나를 따라갑니다. 공통 helper 안에서도 필요한 WAL 처리와 페이지 write는 정해진 순서를 지킵니다.

페이지 이미지 제출에 성공해도 BCB의 완료 처리는 남아 있습니다. 제출한 스레드가 직접 처리할 수 있습니다. 조건이 맞으면 post-flush 스레드에 넘길 수도 있습니다. 다음 장에서는 어느 조건에서 넘기는지 살펴보겠습니다.

한 번의 실행이 멈추는 조건

한 번의 후보 탐색이 끝나는 조건도 나누어 보겠습니다. 탐색 budget과 합산 priority가 양수인 정상 scan에서 후보를 찾지 못하면 helper는 stop_iteration을 설정할 수 있습니다. 이 값은 이번 내부 loop를 끝내라는 힌트입니다. 내부 caller가 ratio를 강제로 0으로 준 경우나 계산된 priority가 0인 경우와 구분해야 합니다. 일반 운영 설정에서는 ratio 0을 거절합니다.

Helper가 오류를 반환했다고 해서 이미지 제출에 성공한 것은 아닙니다. Task는 그 반환 코드를 사용해 반복 여부를 판단하지 않습니다. Stop hint와 현재 frame 부족 등의 압력 조건을 보고 반복을 결정합니다. 이 내부 압력 loop에는 looper의 stop 검사도 없습니다. 따라서 종료 요청을 보냈다고 후보 작업이나 진행 중인 I/O가 즉시 취소되지는 않습니다.

직전 task가 interval만큼의 시간을 이미 사용했다고 하겠습니다. 다음 timed wait의 길이는 0이 됩니다. 고정 waiter는 이때 실제로 잠들지 않고 true를 반환합니다. 따라서 was_woken_up()이 true였다는 기록만 보고 외부 스레드가 wakeup을 보냈다고 결론 내릴 수는 없습니다.

Availability 함수가 non-NULL 포인터를 반환하는 경우도 구분하겠습니다. 그 포인터는 daemon 객체가 존재한다는 사실을 보여줍니다. 복구 중에는 객체가 있어도 boot gate가 닫혀 있을 수 있습니다. 포인터 하나만으로 daemon이 필요한 작업을 수행한다거나 동기 fallback이 실행된다고 입증할 수는 없습니다.

05 · COMPLETE AND REVALIDATE

Post-flush: 완료 처리와 frame 배정은 다르다

화면 안내: 사본을 전달했는데, 왜 후속 처리가 남을까?.

프레임은 페이지 한 개를 담는 메모리 칸입니다. 이번 flush를 위해 복사한 페이지 바이트를 쓰기 경로에 전달했고, 그 호출은 성공했다고 하겠습니다. 그래도 프레임의 제어 기록에는 FLUSHING 표시가 남아 있습니다. 이 flush의 완료 처리를 아직 해야 한다는 뜻입니다.

남은 표시를 정리하고, 그 flush의 완료를 기다리는 스레드가 있으면 깨워야 합니다. Post-flush는 page-flush 대신 이 후속 작업을 맡을 수 있는 백그라운드 스레드입니다. 프레임을 기다리는 요청이 있을 때, 제출 뒤의 작업 일부를 다른 스레드로 넘깁니다. 전달 호출의 성공만으로 최종 볼륨에 쓰기가 끝났거나 영속성이 확보됐다고 판단하지는 않습니다. DWB라는 중간 저장 영역에 사본을 받아둔 단계일 수 있습니다.

화면 안내: 두 대기자가 원하는 결과는 서로 다르다.

여기서 두 종류의 대기를 구분하겠습니다. Flush 대기자는 이미 시작한 flush의 완료 처리를 기다립니다. Allocator는 다른 페이지를 담을 프레임을 찾는 요청 스레드입니다. Flush 대기자는 프레임의 제어 기록인 BCB에 연결되고, allocator는 별도의 프레임 대기 큐에 등록됩니다. 완료 처리를 위해 BCB 포인터를 넘기는 큐도 따로 있습니다.

Flush 대기자를 깨우는 사건과 allocator가 프레임을 확보하는 사건은 다릅니다. 깨어났다는 알림만으로 I/O 성공, 영속성, 프레임 수신을 판단할 수도 없습니다.

화면 안내: 1. Page-flush가 남은 완료 처리를 넘긴다.

먼저 성공 사례 하나만 따라가겠습니다. P는 프레임에 있는 페이지입니다. 사본을 성공적으로 제출한 직후에 현재 P는 clean입니다. 이후의 수정으로 다시 써야 할 바이트가 없습니다. 남은 fix가 없어 프레임 사용을 보호하는 호출자도 없습니다. BCB에 연결된 대기자와 다른 방해 플래그가 없고, 페이지는 차가운 영역인 shared LRU3에 있습니다. Allocator는 별도 큐에서 기다립니다. Post-flush가 있고 완료 큐에 공간도 있습니다. 이 성공 사례에서는 다른 호출자가 끼어들지 않습니다.

Page-flush는 BCB 포인터를 완료 큐에 넣고 post-flush를 깨웁니다. 포인터가 가리키는 것은 프레임의 제어 기록입니다. 페이지 바이트를 이 큐에 넣는 것은 아닙니다. Wake는 다른 스레드의 실행 기회를 주는 일입니다. 그 자리에서 post-flush를 호출하지는 않습니다. 지금은 완료 처리를 위임했을 뿐이고, FLUSHING은 남아 있으며 allocator도 기다립니다.

화면 안내: 2. Post-flush가 프레임을 검사하고 제안을 게시한다.

이제 같은 사례를 이어갑니다. Post-flush가 포인터를 꺼내 BCB mutex를 잡습니다. 이 잠금 아래에서 현재 플래그와 fix, 연결된 대기자, 차가운 영역에 있는지를 검사합니다. Shared list이므로 private quota 검사는 필요하지 않습니다. 이 사례의 조건은 그대로라서 검사를 통과합니다.

Post-flush는 선택한 allocator가 여전히 기다리는지 확인합니다. 그 뒤 보호된 연산으로 이 프레임을 그 요청의 후보로 게시하고 깨웁니다. 게시와 wake의 정확한 순서는 뒤의 분석에서 살펴보겠습니다.

성공하는 제안 분기에서는 직접 제안 표시를 설정하면서 FLUSHING도 함께 해제합니다. 이후 공통 완료 경로에서 이전 FLUSHING이 해제됐는지 확인하고 flush 대기자가 있는지 살펴봅니다. 이번 사례에는 그런 대기자가 없습니다. BCB 잠금을 풀어도 allocator가 이미 프레임을 수신한 것은 아닙니다.

화면 안내: 3. Allocator가 검사한 뒤 제안한 프레임을 받는다.

Allocator가 실행을 재개하면 전달 슬롯에서 포인터를 꺼내고 BCB를 잠급니다. 제안이 취소되지 않았는지 확인하고, 제안 표시를 제거한 뒤 현재 교체 적격성을 다시 검사합니다. 통과하면 BCB를 교체 목록에서 제거하고 잠금을 유지한 채 반환합니다. 할당 경로는 그 뒤에도 이전 페이지 P의 lookup 매핑을 제거해야 합니다. 그 절차가 끝난 뒤 요청한 페이지 식별자로 프레임을 확보합니다.

이번에는 이전 flush의 완료 처리와 allocator의 프레임 확보가 모두 성공했습니다. 다음 사례는 이 실행의 다음 단계가 아닙니다. 매번 시작 상태를 새로 잡겠습니다.

화면 안내: Flush 대기자가 깨어나도 allocator 제안은 없을 수 있다.

이번에는 제출한 P의 BCB가 큐에 들어 있고, 그 BCB에 flush 대기자 하나가 연결돼 있다고 하겠습니다. P는 clean이고 fix가 없으며 shared LRU3에 있습니다. Allocator는 별도로 기다립니다. 연결된 대기자 자체가 post-flush의 직접 제안을 막습니다. 따라서 이번 회차에서는 프레임을 제안하지 않습니다. 그래도 이전 FLUSHING을 해제하고 flush 대기자를 제거해 깨운 뒤 잠금을 풉니다. 완료 대기는 이어갈 수 있지만 allocator에게 프레임을 준 것은 아닙니다.

화면 안내: 큐가 가득 차면 누가 완료 처리를 하는가?.

Q09 · Queue 인계 실패

구성한 시작 상태: 별도의 queue 인계 실패 사례입니다. Page-flush 스레드가 사본 G를 성공적으로 제출했습니다. Post-flush daemon이 있고 direct victim을 기다리는 allocator도 있습니다. 하지만 queue가 가득 차 BCB 포인터를 넣지 못했습니다. G의 FLUSHING은 아직 설정돼 있고 그 flush를 기다리는 스레드도 남아 있습니다.

예측 질문: Queue 삽입이 실패한 이 실행에서 어느 스레드가 G의 BCB 완료 처리를 맡아야 하나요?

논의 후 설명 보기

G를 제출한 page-flush 스레드가 완료 처리를 맡습니다. 이 스레드는 BCB mutex를 다시 잡고 기존 FLUSHING을 해제합니다. 이어서 해당 flush를 기다리는 스레드를 깨웁니다. Queue 삽입에 실패했으므로 post-flush 소비자에게 이 항목을 맡길 수 없습니다.

같은 사본을 checkpoint 스레드가 제출했다면 is_page_flush_thread 조건부터 거짓입니다. 그 경우에도 제출한 caller가 일반 완료 분기에서 직접 처리합니다.

선택 후속 질문: 같은 사본을 checkpoint 스레드가 제출했다면 어떤 조건에서 완료 처리 주체가 정해지나요?

화면 안내: 큐 삽입에 실패하면 호출자에게 완료 책임이 남는다.

Queue가 가득 찬 사례에서도 제출한 사본은 그대로입니다. 큐에 BCB 포인터를 넣지 못했으므로 제출한 스레드가 잠금을 다시 잡고 완료 처리를 직접 수행합니다. 이 직접 완료 분기는 allocator에게 프레임을 제안하지 않습니다.

화면 안내: 이전 완료 처리가 끝나도 새 dirty 작업은 남는다.

다시 초기화하겠습니다. P는 프레임의 페이지이고, G는 이미 제출한 안정된 사본입니다. G는 저장된 카운터가 아니라 설명용 이름입니다. BCB 포인터를 큐에 넣은 뒤, 소비 전에 writer가 P를 fix하고 수정합니다. Writer는 아직 fix를 유지합니다. G+1은 그 새 바이트를 가리키는 설명용 이름입니다. DIRTY는 새 수정의 보존 작업이 남았다는 표시입니다.

Post-flush는 현재 DIRTY와 사용 보호를 보고 프레임을 제안하지 않습니다. 그래도 G의 이전 FLUSHING을 정리하고 flush 대기자를 깨웁니다. G+1의 DIRTY는 남습니다. 이전 사본의 완료 처리를 끝낸 것이 새 수정의 쓰기까지 끝냈다는 뜻은 아닙니다.

화면 안내: Reader가 allocator 제안을 취소할 수 있는가?.

Q11 · Direct-victim 제안 이후

구성한 시작 상태: 별도의 수신 재검사 사례입니다. Post-flush 소비자가 clean 페이지 P의 BCB를 allocator B에게 direct victim으로 배정했습니다. B가 실제로 frame을 재사용하기 전에 reader A가 P를 정상적으로 fix했습니다. A는 아직 fix를 반납하지 않았습니다. 이제 B가 실행 기회를 얻었습니다.

예측 질문: Allocator B가 실제 frame 재사용 전에 다시 확인해야 할 현재 상태는 무엇인가요?

논의 후 설명 보기

Allocator B는 실제 재사용 전에 필요한 보호를 잡고 수신 검사를 통과해야 합니다. VPID가 그대로 P이어도 새 fix가 생기면 제안은 취소될 수 있습니다. B는 reader A가 사용하는 frame을 덮어쓸 수 없습니다. pgbuf_get_direct_victim은 BCB mutex를 잡고 현재 flag, fix, 대기 스레드를 검사합니다. 거절하면 사용할 제안을 반환하지 않습니다. 나중에 A가 unfix하더라도 같은 제안을 다시 받거나 즉시 성공한다는 보장은 없습니다.

선택 후속 질문: A가 나중에 unfix한 뒤 B가 성공한다고 설명하려면 현재 상태와 배정 경로에 관한 어떤 전제가 더 필요한가요?

화면 안내: 되짚기: 완료, wake, 제안, 수신은 서로 다른 사건이다.

완료 처리, wake, 프레임 제안, 보호된 수신을 따로 보겠습니다. 이전 완료 처리를 마쳐도 새 DIRTY 작업은 남을 수 있습니다. Wake는 실행 기회를 줍니다. 제안은 수신할 후보를 게시하며 취소될 수 있습니다. Allocator는 현재 상태를 검사해 수신한 뒤에도 실제 재사용 전에 이전 페이지 식별자를 제거해야 합니다. 이제 전체 분기 그림에서 각 사건이 어디에 있는지 찾아보겠습니다.

화면 안내: 전체 그림에서 위임과 직접 완료를 따라간다.

화면 안내: 유지보수 분석: 완료 처리 경로를 찾는다.

여기서부터 유지보수를 위한 분석입니다. 성공 경로와 독립적인 실패 사례를 이해한 뒤, 실제 호출 경로와 대기자 저장 구조, wake 순서, 현재 상태 검사, 추가 공급자, 대안과 비용을 살펴봅니다. 상세 호출 목록은 펼쳐 볼 수 있습니다.

스레드를 깨우는 소스 순서를 확인하겠습니다. Post-flush는 allocator의 스레드 잠금을 잡고 signal을 먼저 보낸 뒤 BCB 포인터를 전달 슬롯에 저장합니다. 이후 그 잠금을 풉니다. 깨어난 스레드는 같은 잠금을 다시 잡아야 wait에서 돌아오므로, 돌아올 때는 포인터가 게시돼 있습니다.

화면 안내: 새 quota가 프레임 제안을 막을 수 있는가?.

Q10 · 소비 전의 정책 변화

구성한 시작 상태: 별도의 quota 변화 사례입니다. Private LRU의 페이지 P가 사본 G의 제출을 마쳤고, P의 BCB 포인터가 queue에 들어갔습니다. Post-flush가 실행될 때 P는 clean이며 LRU3에 있습니다. 남아 있는 fix와 BCB에 연결된 대기 스레드는 없습니다. 여기서 BCB 대기자에는 flush 대기자도 포함합니다. List의 현재 크기는 80입니다. 그 사이 quota는 60에서 100으로 바뀌었습니다. 별도 queue의 allocator는 계속 frame을 기다리고, 다른 배정 방해 flag는 없습니다.

예측 질문: Post-flush가 P를 frame 후보로 제안할지 결정할 때, 바뀐 quota 100은 어떤 조건에 사용되나요?

논의 후 설명 보기

Post-flush는 현재 quota인 100을 사용합니다. List의 크기 80은 100을 초과하지 않습니다. 따라서 P가 clean이고 fix가 없어도 private-list 조건에서 직접 배정을 거절합니다. 그래도 post-flush는 G의 기존 FLUSHING을 해제하고 flush 대기자를 깨우는 완료 처리를 마칩니다. 이전 flush를 완료한 결과와 allocator에게 frame을 배정하지 않은 결과를 각각 기록해야 합니다.

선택 후속 질문: G의 완료 처리와 allocator의 frame 배정이 각각 성공했는지 어떤 사건으로 기록하겠습니까?

대기가 늘어났다가 다시 짧아지는 이유

Post-flush가 queue 항목을 처리하지 못한 유휴 실행을 반복한다고 하겠습니다. Looper는 대기를 1 ms, 10 ms, 100 ms로 늘립니다. 그 뒤에는 wakeup을 기다리는 무한 대기로 들어갑니다.

항목을 하나라도 꺼내 처리하면 pgbuf_assign_flushed_pages()는 true를 반환합니다. Allocator가 frame 제안을 받았는지와는 별개입니다. Task는 이 반환을 보고 looper를 다시 1 ms 대기부터 시작시킵니다. 이전 pause의 wake 결과도 대기를 늘리는 increasing-wait 정책을 초기화합니다. 따라서 queue 항목을 소비한 사건과 allocator에게 배정한 사건을 따로 봐야 합니다.

이 대기 단계와 queue의 8,192-entry 용량은 고정 소스에 컴파일된 정책입니다. 별도로 공개된 post-flush interval이나 enable 설정은 없습니다. Queue가 BCB 포인터를 전달하므로, 받아들인 항목의 완료 처리가 남아 있는 동안에는 BCB 저장 공간을 유지해야 합니다. 정상 소비는 queue가 빌 때까지 진행합니다. 하지만 stop 요청이 들어왔다는 사실만으로 모든 항목을 drain, 즉 끝까지 꺼내 처리한다고 보장할 수는 없습니다.

발표자 안내: 여기서 쉬어도 좋습니다. 다시 시작할 때 참가자에게 사본 제출, BCB 완료 처리, frame 배정이 각각 어떤 사건인지 설명해 달라고 합니다.

화면 안내: 상태 변화 화면: 이전 완료 처리가 끝나도 새 dirty 작업은 남는다. 시작 상태를 확인하고 다음 단계에서 달라지는 필드를 예측합니다. 이 사례는 독립적으로 초기화합니다.

화면 안내: 상태 변화 화면: 큐 삽입에 실패하면 호출자에게 완료 책임이 남는다. 시작 상태를 확인하고 다음 단계에서 달라지는 필드를 예측합니다. 이 사례는 독립적으로 초기화합니다.

화면 안내: 상태 변화 화면: Quota 거절과 제안 취소는 각각 새 상태에서 시작한다. 시작 상태를 확인하고 다음 단계에서 달라지는 필드를 예측합니다. 이 사례는 독립적으로 초기화합니다.

근거: 완료 처리 인계 조건 · 소비자의 검사와 완료 처리 · Clean 페이지를 반납하면 allocator가 깨어나는가?.

설계 논증 이어가기

화면 안내: 확장 화면 순서: 사본을 전달했는데, 왜 후속 처리가 남을까? (EN) → D27 · 과거의 clean 상태로 현재 재사용을 승인할 수 있는가? (EN)

배정 거절의 이유를 구분하겠습니다. 아직 dirty이거나 현재 사용자가 있으면 안전성 때문에 거절합니다. Hot zone과 private quota는 메모리에 어떤 페이지를 얼마나 보존할지 정하는 정책 조건입니다. 현재 frame을 기다리는 유효한 waiter가 없으면 배정하지 않습니다. 어느 이유로 거절하든 이전 이미지의 완료 처리와 flush 대기자 wakeup은 별도로 수행해야 합니다.

Queue가 가득 차 삽입에 실패하면 producer, 즉 이미지를 제출한 스레드가 완료 처리를 직접 합니다. 이미 queue에 넣은 작업이 있는데 consumer를 중지하는 상황과는 다릅니다. D27에서는 reviewer가 제안한 clean-at-enqueue boolean을 살펴봅니다. 이 값은 queue에 넣을 당시 clean이었다는 사실을 기록합니다. 이 값을 현재 재사용의 승인으로 쓰려면 그 사이 상태 변경을 막았다는 증명이 필요합니다.

화면 안내: 대안의 전이: 완료와 예약을 별도 기록으로 나눌 수 있는가?.

이번에는 완료 기록과 재사용 예약을 나누는 대안을 구성하겠습니다. 완료 ticket은 이전 이미지를 식별합니다. 처리를 맡은 스레드는 그 ticket을 한 번만 완료합니다. 재사용 예약은 필요한 보호를 잡고 현재 상태를 검사한 뒤에만 발급합니다. 이후 새 사용이 생기면 재사용 예약을 취소합니다. 그 사건 때문에 이전 flush의 완료까지 취소하지는 않습니다. 수신 스레드는 유효한 예약을 원자적으로 소비하거나 다시 시도합니다. 취소와 종료 때는 ticket의 정리를 마친 뒤 저장 공간을 회수합니다.

이것은 설명용 대안입니다. 추가 식별자와 수명 기록으로 과거의 완료 ticket을 현재의 재사용 승인과 구분합니다. 계속 유지하는 예약은 새로운 사용을 막을 수 있습니다. 또는 mutex와 CPU 처리 비용을 다른 지점으로 옮길 수 있습니다. 현재 구현에서 queue가 가득 찼을 때는 제출한 스레드가 완료 처리를 직접 수행합니다. 따라서 post-flush daemon을 제거하는 대안에서도 완료 처리를 맡을 주체는 필요합니다.

화면 안내: 관측과 반증: 완료 처리와 배정을 어떤 관측으로 구별할 수 있는가?.

기존 통계에는 frame을 배정한 producer별 counter가 있습니다. 추가 기록에서는 BCB와 identity별로 enqueue와 dequeue를 연결하겠습니다. 기존 FLUSHING 해제, 각 거절 분기, frame 제안의 공개와 취소, allocator의 수신 결과도 연결하겠습니다. 일반 배정을 거절한 뒤 이전 FLUSHING이 남는다면 완료 처리를 수행한다는 설명에 반례가 됩니다. Queue가 비어 있지 않다는 사실이나 배정 횟수가 있다는 숫자만으로 allocator의 수신 성공을 입증할 수는 없습니다.

Producer별 통계를 읽기 전에 통계 수집이 활성 상태인지 확인하겠습니다. 시작 시 activation bit도 확인해야 합니다. Victimization bit 16과 daemon bit 64는 기본 mask 15에 없습니다. 합계 배정 횟수는 개별 allocator가 frame을 받았다는 증거가 아닙니다. Enqueue, 거절, 제안, 수신을 개별 사건으로 연결하는 기록은 아직 추가해야 할 probe 제안입니다.

06 · POLICY ADAPTATION

Maintenance: 100 ms 시도와 quota 갱신

화면 안내: 같은 페이지를 다시 읽는데, 왜 디스크에서 또 가져올까? → 처음 정한 보존 목표를 계속 사용해도 될까? → quota는 무엇의 목표일까?.

12개 프레임이 모두 찬 교육용 예제로 시작하겠습니다. 같은 네 페이지를 반복해서 읽는 요청과 다른 페이지를 차례로 가져오는 스캔이 함께 실행됩니다. 스캔에 자리를 내주면서 곧 다시 쓸 페이지를 내보내면, 반복 조회는 디스크에서 그 페이지를 다시 가져와야 합니다. 그 요청이 나중에 여덟 페이지를 돌아가며 읽으면, 처음 정한 목표가 바뀐 작업에 맞는지도 다시 검토해야 합니다. 이 숫자는 실제 CUBRID quota 계산이 아닙니다.

교체 목록은 같은 버퍼 풀 안의 페이지를 정책에 따라 묶습니다. Private 목록은 세션과 연결되지만 페이지 접근을 독점하지 않으며, 여러 세션이 같은 목록을 쓸 수도 있습니다. Shared 목록이 스캔 페이지를 뜻하는 것도 아닙니다. Quota는 목록에 남기려는 페이지 수의 목표입니다. 예약해 둔 칸 수나 즉시 재사용을 허용하는 값은 아닙니다.

Fix는 호출자가 페이지를 사용하는 동안 프레임의 재사용을 막습니다. Final unfix는 마지막 fix를 해제합니다. Maintenance는 일부 final-unfix 경로에서 수집한 대략적인 활동 표본으로 목표와 영역별 크기 기준을 다시 계산합니다. Thread별로 집계한 final unfix 수는 갱신할 만큼 활동이 쌓였는지 검사하는 입력입니다. 목록별 hit 표본은 목표 계산에 쓰는 별도의 입력입니다. 같은 프레임의 반복 기여를 억제하는 집계가 있으므로, 반복 조회의 읽기 횟수가 늘었다고 quota가 반드시 늘지는 않습니다.

LRU1은 오래 남기는 영역이고, LRU2는 중간 영역이며, LRU3는 교체 후보를 공급합니다. BCB는 프레임의 제어 레코드이고 mutex는 변경을 보호하는 잠금입니다. Allocator는 프레임을 구하는 요청 thread입니다. Private 목록은 LRU1과 LRU2의 합이 새 quota를 넘을 때 영역 조정을 호출합니다. 작은 기준값을 저장하는 것만으로 모든 항목을 이동시키지는 않습니다. 조정 조건을 통과하면 목록 mutex를 잡고 초과한 항목을 후보 영역 쪽으로 내립니다. 직접 제안하지 않은 페이지는 계속 메모리에 있습니다. 이동 중 allocator에 직접 제안할 수도 있지만, BCB를 잠그고 현재 상태를 다시 검사해야 합니다. 받는 allocator도 제안을 확인합니다.

화면 안내: maintenance는 어떤 활동을 관찰할까? → 활동 표본은 어떻게 교체 정책에 반영될까? → 보존 목표가 줄면 무엇이 달라질까? → 교체 후보가 되어도 바로 재사용할 수 없는 이유는?.

Dirty는 저장 경로에 반영할 변경이 남았다는 뜻이고, flushing은 이전 이미지의 쓰기 작업이 진행 중이라는 뜻입니다. 보존 목표가 작아져도 이 의무는 사라지지 않습니다.

화면 안내: maintenance를 호출할 때마다 목표를 갱신할까? → 갱신이 허용되어도 quota 숫자가 같을 수 있을까?.

Maintenance의 100 ms는 작업을 시도하는 목표 간격입니다. 실제 시작은 스케줄링과 작업 시간에 따라 달라집니다. Quota 조정 함수인 pgbuf_adjust_quotas()는 기능이 켜져 있는지, 다른 조정이 진행 중인지, 충분한 시간이나 활동이 쌓였는지 검사합니다. 조건을 통과한 호출만 표본을 소비하고 목표를 다시 계산합니다. 요청 thread도 private 목록을 배정하거나 해제할 때 이 함수를 호출합니다.

허용된 표본 갱신 한 번을 epoch라고 하며 adjust_age가 그 횟수를 기록합니다. Quota 숫자가 바뀌지 않아도 갱신 회차는 진행할 수 있습니다. 호출을 시도한 사건, 새 표본을 처리한 사건, allocator가 프레임을 받은 사건을 각각 확인해야 합니다.

Q12 · 갱신 회차의 기록

구성한 시작 상태: 별도의 갱신 회차 사례입니다. Epoch는 조건을 통과한 quota 갱신 회차입니다. 처음 adjust_age는 8이고 관찰할 private list의 quota는 60페이지입니다. 여섯 번 호출한 함수 중 네 번은 조기 반환합니다. 두 번만 갱신을 끝까지 수행하며, 두 갱신 뒤에도 quota는 60입니다. 다른 갱신이나 동시 조정은 없습니다. 숫자가 표현 범위를 넘어 돌아가는 wrap도 없습니다.

예측 질문: 마지막 adjust_age는 얼마인가요? Quota가 그대로 60이라는 사실과 갱신 회차를 어떻게 구분하겠습니까?

논의 후 설명 보기

Adjust_age는 10이 됩니다. 처음 값 8에서 두 번의 갱신 회차가 진행됐고, 다른 갱신이나 wrap은 없기 때문입니다. Quota가 계속 60이어도 샘플 처리와 갱신은 수행됐을 수 있습니다. 따라서 quota 숫자와 함께 조건 통과 여부, 샘플 처리, adjust_age의 변화를 확인해야 합니다.

선택 후속 질문: Quota 숫자만 기록하면 이번 호출이 조기 반환했는지 갱신을 마쳤는지 구분할 수 있나요? 어떤 기록이 더 필요한가요?

화면 안내: 두 번 갱신해도 quota는 60일 수 있다. Q12의 시작 상태로 되돌려 독립적으로 추적합니다. 네 번의 조기 반환 뒤 허용된 두 갱신만 age를 8에서 10으로 진행시킵니다.

화면 안내: 이제 maintenance에 관해 무엇을 설명할 수 있을까? → 어떤 조건에서 새 표본의 갱신을 허용할까? → 활동이 적은 풀은 언제 갱신 조건을 통과할까? → hit 표본으로 보존 용량의 몫을 어떻게 계산할까? → 새 보존 목표에는 어떤 한계가 있을까?.

이제 정확한 계산을 붙이겠습니다. 1 ms 이전에는 반환합니다. 집계한 활동이 풀 크기의 4분의 1 미만이고 500 ms도 지나지 않았다면 반환합니다. 갱신을 허용한 뒤의 낮은 활동량 분류는 비율 계산을 바꾸며, 허용된 갱신을 취소하지 않습니다. 목록 hit를 시간으로 나누고 이전 기록과 평활화해 보존 목표를 구합니다. 앞의 12개 프레임 그림에 이 수식과 실제 한계값을 그대로 적용하지는 않습니다.

시작 설정과 매 회차 계산값을 나누기

표의 설정은 pool과 list를 초기화할 때 읽습니다. IO_PAGESIZE는 실행 중 I/O 페이지 한 개의 byte 크기입니다. 이 고정 소스의 설정 등록에는 일반적인 실행 중 변경을 허용하는 USER_CHANGE flag가 없습니다. 따라서 DBA가 SET SYSTEM PARAMETERS로 바꾸려 하면 거절합니다. 설정 파일을 수정한 뒤 재시작해 관련 구조를 초기화해야 새 값이 반영됩니다. RELOADABLE은 loader에서 사용하는 분류입니다. 이 분류만으로 살아 있는 pool을 재구성하거나 SQL 변경을 허용한다고 해석할 수는 없습니다.

VS-20과 VS-21은 불확실성 목록의 항목 번호입니다. 목록은 소스에서 확인한 사실과 아직 확인하지 않은 운영 영향을 나누어 기록합니다. 다른 리비전의 참고 사례인 eb0a4cd7b003defec83c7f5f0e2d1f392c139a81에는 명시적으로 순회하면서 배정 budget을 사용하는 수정이 있습니다. 이 commit은 오늘 설명하는 고정 소스와 다릅니다. 그 수정이 있다는 사실만으로 발표 기준이 바뀌지는 않습니다. 다른 branch에 merge나 배포됐는지, 실제 지연이 줄었는지도 각각 별도의 확인이 필요합니다.

Q13 · 소스상 이상 징후의 영향

구성한 시작 상태: 별도의 진단 사례입니다. 고정 소스에서 maintenance의 보조 반복문 본문이 실행되지 않는 조건을 확인했습니다. 운영자는 낮은 활동량에서 allocator의 지연을 보고했습니다. 같은 시간에 다른 direct-victim 공급자가 실행됐는지, 어떤 frame을 배정했는지는 아직 기록하지 않았습니다.

예측 질문: 보조 반복문의 미실행이 보고된 allocator 지연의 원인인지 확인하려면 어떤 관측을 설계하겠습니까?

같은 시간축에 allocator의 대기 구간을 기록하겠습니다. 다른 frame 공급자의 실행과 현재 후보 조건을 함께 기록합니다. 배정이 성공했는지, 이후 취소됐는지도 연결하겠습니다. Workload와 구성을 고정한 비교에서 보조 경로가 진행에 기여하는지 확인할 수 있습니다. VS-20에서 확인한 것은 반복문 본문에 진입하지 않는다는 소스 사실입니다. 보고된 지연의 원인으로 판단하려면 추가 증거가 필요합니다. 다른 공급자가 allocator에게 frame을 배정한 사건은 모든 진행이 멈췄다는 주장에 반례가 됩니다.

07 · POST-WRITE PACING

Flush-control: write 이후의 속도를 조절한다

화면 안내: 전용 발표 장: 쓰기 성공 뒤에도 writer가 기다리는 이유는? · 쓰기 전 제한에는 어떤 상태가 더 필요할까요? · 어떤 기록이 쓰기 뒤 정산이라는 설명을 반증할까요?.

Clean frame을 더 많이 준비하면 요청의 병목이 저장장치로 옮겨갈 수 있습니다. 이번 장에서는 write 속도를 어떻게 조절하는지 보겠습니다. 고정 CUBRID 경로는 OS write를 수행한 뒤 token을 차감합니다. 따라서 token daemon이 조절하는 것은 이미 끝난 write의 허가가 아니라 이후 작업의 진행 속도입니다. 회차마다 예산을 교체하는 정책과 credit을 누적하는 정책은 순간적인 burst가 다릅니다. 속도 제한을 제거한 경우도 비교할 수 있습니다. 어느 정책에서도 WAL 순서와 보호된 재사용 검사는 수행해야 합니다.

화면 안내: 화면: 어떤 작업이 잔액을 갱신할까요? → Writer는 쓰기 뒤 credit을 어떻게 소비할까요? → 어떤 쓰기가 credit 부족을 우회할까요? → 다른 어떤 주체가 쓰기와 동기화를 맡을까요?.

Flush-control이라는 이름을 보면 어떤 페이지를 언제 쓰라고 다른 flusher에게 지시하는 역할을 떠올릴 수 있습니다. 실제로 이 daemon이 갱신하는 것은 file_io.c의 공유 token 예산입니다. 해당 write 경로의 writer는 OS write에 성공한 다음 compensation으로 쓴 양을 정산합니다. Token을 소비하거나 부족하면 기다립니다. 이 대기가 이후 작업의 속도를 조절합니다.

Token은 공유 예산에서 I/O page 한 개에 대응하는 설명 단위입니다. Compensation은 선택한 write 경로에서 이미 쓴 양을 정산하는 후속 작업입니다. 모든 write가 같은 대기 경로를 사용하는 것은 아닙니다. 이번 장에서는 일반 writer를 A라고 부르겠습니다. 로그 critical section을 보유한 다른 writer를 B라고 부르겠습니다. Critical section은 관련 공유 상태를 보호하는 구간입니다. A와 B는 앞 장의 정책 영역 이름과 다른, 새로 구성한 caller입니다.

Bucket이 없는 경우와 첫 실행

Control task는 스레드를 생성하기 전에 file-I/O bucket을 초기화합니다. Bucket은 token 예산과 대기 상태를 관리합니다. 초기화는 static 저장 공간에 mutex와 condition variable을 만들고 token을 0으로 설정합니다. 그 뒤 다른 스레드가 사용할 bucket 포인터를 공개합니다.

Mutex 초기화에 실패하면 포인터 공개 전에 반환합니다. Condition 초기화에 실패하는 경로에서는 mutex가 이미 만들어져 있지만 지역적으로 destroy하지 않습니다. 역할 초기화 함수는 task를 retire() 없이 삭제하고 control daemon을 만들지 않습니다. 이 설명은 소스에서 확인한 정리 책임의 경계입니다. 실제로 누수가 발생했다는 관측은 아닙니다.

공개된 bucket이 없으면 token 획득 함수는 별도 작업 없이 반환합니다. Bucket이 있고 boot gate가 열렸어도 첫 task 실행은 현재 시각만 기록합니다. 첫 실행에서는 token을 만들지 않습니다. 이후 task 실행이 경과 시간을 사용해 예산을 계산합니다.

종료 시에는 worker가 task의 retire()에서 bucket을 정리합니다. 그 뒤 스레드가 끝나고 join이 반환합니다. Bucket을 사용하는 writer가 언제까지 접근하는지도 함께 맞춰야 합니다. Page-buffer daemon을 join했다는 기록만으로 모든 writer도 종료했다고 판단할 수는 없습니다.

Feedback switch와 고정 rate의 차이

다음 두 공개 설정은 DBA가 서버 전체 registry에서 실행 중 바꿀 수 있습니다. 표의 IO_PAGESIZE는 I/O 페이지 한 개의 byte 크기이고, bytes/s는 초당 byte 수입니다. 예를 들어 SET SYSTEM PARAMETERS 'adaptive_flush_control=no'를 실행하면 다음 refresh에서 사용할 계산 분기가 바뀝니다. 이 SQL이 bucket을 새로 만들거나 설정 파일을 저장하지는 않습니다.

설정·분류기본값·단위변경 뒤 실제 효과

50 ms looper와 adaptive 분기의 40 MiB/s floor는 컴파일된 정책입니다. 예산을 늘리는 0.5 계수와 줄이는 0.1 계수도 같은 분류입니다. Token 잔량, 이전 budget, dirty feedback은 실행 중 변하는 상태입니다. DWB 설정과 sync 경계는 이후 저장 경로의 자원과 I/O 정책으로 따로 봐야 합니다. 네 page-buffer daemon을 차례로 통과해야 한다는 pipeline이나 이들을 생성하는 switch로 해석하지는 않겠습니다.

Control은 50 ms 목표 주기로 새 token 예산을 계산합니다. 기존 token 값을 새 값으로 교체한 뒤 기다리는 writer를 깨웁니다. Token이 있다는 사실만으로 페이지 쓰기의 안전 조건이 충족되지는 않습니다. 각 write 경로가 WAL 순서와 BCB 보호를 지켜야 합니다.

로그 critical section을 보유한 caller는 token이 부족해도 일반 caller처럼 기다리지 않습니다. 일반 token 대기에도 재시도 횟수 제한이 있습니다. 따라서 이 예산을 실제 I/O 양의 엄격한 상한으로 사용할 수는 없습니다.

다른 write 주체도 구분하겠습니다. Log-flush는 로그를 기록합니다. Checkpoint는 checkpoint 경계의 작업을 처리합니다. DWB daemon은 DWB가 받은 이미지의 후속 write 경로를 처리합니다. 이들은 페이지 버퍼의 네 daemon과 별도의 역할입니다. 여러 caller가 공통 write helper를 호출할 수 있습니다. 페이지를 dirty로 만든 caller가 항상 page-flush queue에 작업을 넣는 구조는 아닙니다.

여기까지 네 결과를 따라왔습니다. 페이지 이미지 제출, BCB 완료 처리와 frame 배정, quota 조정, writer의 속도 조절입니다. 이제 새로운 PostgreSQL 사례에서 각 작업을 누가 맡는지 살펴보겠습니다.

구성한 시작 상태: 별도의 두 writer 사례입니다. 일반 writer A와 로그 critical section을 보유한 writer B가 각각 OS write에 성공했습니다. 두 writer는 그 뒤 token compensation 경로에 도착했고, 모두 token 부족을 만났습니다. B는 계속 로그 critical section을 보유합니다. 추가 token 갱신은 아직 없습니다.

예측 질문: Token이 부족한 두 caller가 이후 같은 방식으로 기다릴까요? 어떤 보유 조건을 검사해 분기를 나누나요?

논의 후 설명 보기

LOG_CS_OWN 분기가 로그 critical section을 보유한 caller인지 검사합니다. 일반 writer A는 token condition에서 기다리고 재시도할 수 있습니다. 열 번의 재시도 뒤에는 진행하는 경로가 있습니다. Writer B는 수요를 기록하고 부족한 token을 기다리지 않습니다. 두 writer의 OS write는 이미 성공했습니다. 따라서 이 기능은 이후 진행 속도를 부드럽게 조절하는 soft pacing으로 설명해야 합니다. 쓰기 전 허가나 영속화 보장으로 읽을 수는 없습니다.

선택 후속 질문: 두 writer의 차이를 포함하면 이 속도 조절 기능이 무엇을 조절하고 무엇을 보장하는지 어떻게 표현해야 할까요?

화면 안내: 상태 변화 화면: 이미 끝난 쓰기는 credit을 어떻게 소비할까요?. 시작 상태를 확인하고 다음 단계에서 달라지는 필드를 예측합니다. 이 사례는 독립적으로 초기화합니다.

근거: write 이후의 호출 · token 소비, 대기, 갱신.

설계 논증 이어가기

화면 안내: 확장 화면 순서: 남은 credit을 저장하면 집중된 쓰기는 어떻게 달라질까요? (EN) → 쓰기 성공 뒤에도 writer가 기다리는 이유는? (EN) → D28 · 같은 quota나 열 번의 재시도로 정체를 판단할 수 있을까요? (EN)

시작점을 다시 확인하겠습니다. 해당 경로에서는 OS write가 이미 끝난 뒤 token을 정산합니다. 별도의 비교에서 기존 token 2개와 새 예산 3개가 있다고 하겠습니다. 값을 교체하는 경로에서는 갱신 뒤 3개가 남습니다. 누적하는 대안에서는 5개가 남습니다. 이 차이는 이후 burst를 얼마나 허용할지에 관한 정책입니다. 이미 쓴 바이트의 안전 조건이나 WAL 순서를 바꾸는 것은 아닙니다.

열 번이라는 제한은 condition wait가 반환한 뒤의 retry 횟수입니다. 첫 wait에도 timeout이 없습니다. 따라서 열 번을 50 ms 목표 주기와 곱해 500 ms 같은 대기 상한을 만들 수는 없습니다. Log-CS를 보유한 caller는 token 부족분을 기다리지 않습니다.

Write 전에 제한하는 pre-write limiter를 대안으로 제시하려면 진입을 허용하는 admission 위치와 capacity cap을 새로 정해야 합니다. Log-holder가 계속 진행할 조건도 설계해야 합니다. D28에서는 quota 값과 epoch를 구분하듯 retry 횟수와 실제 시간을 구분하겠습니다.

화면 안내: 대안의 전이: 쓰기 전 제한에는 어떤 상태가 더 필요할까요?.

이번에는 OS write 전에 예산을 예약하는 대안을 구성하겠습니다. Writer는 byte나 page의 비용을 정의하고 필요한 allowance, 즉 허용량을 예약합니다. 예산 보충이나 로그 진행에 필요한 lock을 보유한 채로는 기다리지 않게 합니다. 예약한 뒤 WAL 순서를 지켜 write를 수행합니다. 제출 전에 취소하면 예약한 credit을 돌려줍니다. 일부만 쓴 partial write 이후에는 미리 정한 오류 규칙에 따라 실제 작업량을 기록합니다.

이것은 설명용 대안입니다. Write 진입을 조절하려면 예약과 취소 상태를 추가로 관리해야 합니다. 로그 진행과 credit 보충이 서로 기다리는 의존 순환을 막지 못하면 deadlock이 생길 수 있습니다. Credit을 누적하면 이전에 모아 둔 양만큼 burst를 허용합니다. 회차마다 교체하면 그 회차의 allowance를 사용합니다. Pacing을 제거하면 저장장치에 대한 경쟁이 달라질 수 있습니다. 이 비교는 실제 장치 I/O의 엄격한 상한을 측정한 결과가 아닙니다.

화면 안내: 관측과 반증: 어떤 기록이 쓰기 뒤 정산이라는 설명을 반증할까요?.

관측에서는 OS write가 반환한 시각과 그 뒤 token을 차감한 시각을 연결하겠습니다. Token 교체와 broadcast, condition wait의 시작과 반환, 대기를 끝낸 이유도 기록하겠습니다. Compensation 통계만으로 그 앞의 write가 얼마나 걸렸는지 알 수는 없습니다. 관측한 경로에서 token 차감이 OS write보다 앞섰다면 고정 경로에 대한 설명의 반례가 됩니다. Control 통계를 볼 때도 수집 활성 상태와 필요한 시작 시 activation bit를 확인하겠습니다. 기본 mask 15에는 daemon bit 64가 없습니다. 수집 설정만 켜면 OS write, token wait, broadcast의 인과관계가 자동으로 기록되는 것은 아닙니다. 추가 probe와 사용한 build·설정을 기록해야 합니다. 관측이 실행에 미친 observer effect도 기록해야 합니다. Retry 횟수로 시간 상한을 대신 계산하지는 않겠습니다.

08 · TRANSFER THE MODEL

PostgreSQL: pin과 credit을 먼저 나눈다

화면 안내: 전용 발표 장: 메모리의 같은 주소가 왜 계속 같은 페이지를 가리켜야 할까? · 모든 pin이 공유 참조 수를 갱신하게 하면 어떨까? · Pin 규칙은 어떻게 검증할 수 있을까?.

PostgreSQL 사례는 앞의 CUBRID 실행과 독립적으로 시작합니다. Backend는 요청을 처리하는 실행 주체입니다. Descriptor는 frame에 담긴 페이지와 사용 상태를 관리하는 구조입니다. Backend가 페이지를 pin하면 사용하는 동안 그 frame을 다른 페이지에 재사용할 수 없습니다. 페이지 바이트를 읽거나 바꿀 때는 content lock이라는 별도의 보호를 얻습니다. usage_count는 최근 사용을 제한된 수치로 기억하는 교체 정책 값입니다. 이 값을 보존 credit이라고 부르겠습니다. 현재 pin이 있는지와 보존 credit이 높은지는 서로 다른 질문입니다.

화면 안내: 화면: Pin은 어떻게 페이지를 메모리에 유지할까? → 메모리의 같은 주소가 왜 계속 같은 페이지를 가리켜야 할까?. 여기서 InnoDB 절로 이어가지 않고 다음 clock 화면 안내로 이동합니다.

PostgreSQL도 페이지 바이트와 관리용 descriptor를 나누어 둡니다. Backend는 사용하려는 페이지를 pin합니다. 그 pin이 남아 있는 동안 frame을 다른 페이지 identity로 바꾸어 재사용하지 못합니다. Backend가 페이지 바이트를 읽거나 변경하려면 해당 접근에 필요한 content 보호를 따로 확보해야 합니다. CUBRID의 fix와 latch에서 배운 책임 구분을 비교에 사용할 수 있습니다. 다만 두 엔진의 함수 호출 인터페이스가 같다는 뜻은 아닙니다.

교체 정책이 최근 사용을 기억하는 값도 보겠습니다. PostgreSQL의 usage_count는 페이지를 얼마나 더 남길지 판단하는 제한된 credit입니다. 현재의 pin을 기록하는 refcount와는 다른 값입니다. 마지막 접근 시각이나 LRU list의 위치를 저장하지도 않습니다. 이 고정 리비전에서 usage_count는 최대 5까지 올라갑니다.

기본 strategy에서 backend가 아직 pin하지 않은 페이지를 처음 pin한다고 하겠습니다. Backend는 공유 refcount를 올립니다. Usage credit도 상한 5에 도달하지 않았다면 올립니다. 같은 backend가 그 pin을 유지한 채 같은 페이지를 다시 pin하면, 자기 안의 private refcount만 늘립니다. 이 중첩 pin의 호출 횟수만큼 공유 credit을 계속 올리지는 않습니다.

작업이 다시 사용할 공유 buffer ID를 작은 배열에 기억하는 ring strategy도 있습니다. 이 strategy에서 pin하는 경우에는 credit이 0이면 1로 올릴 수 있습니다. 이미 높은 credit을 더 올리지는 않습니다.

Q16 · 중첩 Pin의 기록

구성한 시작 상태: 별도의 pin 수치 사례입니다. 공유 descriptor D는 유효한 clean 페이지를 관리합니다. 공유 refcount와 usage credit은 모두 0입니다. 진행 중인 I/O는 없고 기본 strategy를 사용합니다. Backend A가 D를 세 번 연속 pin하고 모두 유지합니다. 그 상태에서 backend B가 D를 처음 pin합니다. 이후 A만 자기의 세 pin을 모두 반납합니다. 중간에 교체 후보를 찾는 Clock이 방문하거나 다른 상태를 바꾸는 사건은 없습니다.

예측 질문: A의 첫 pin, 두 번의 중첩 pin, B의 첫 pin, A의 전체 반납을 차례로 따라가 보세요. 각 단계의 공유 refcount와 A의 private refcount, usage credit은 얼마인가요?

논의 후 설명 보기

A의 첫 pin 뒤에는 공유 refcount가 1입니다. A의 private refcount도 1이고 credit도 1입니다. A가 같은 페이지를 두 번 더 pin하면 private refcount는 3이 됩니다. 공유 refcount와 credit은 계속 1입니다. 이후 B가 처음 pin하면 공유 refcount와 credit은 각각 2가 됩니다.

A가 자기 pin을 모두 반납하면 A의 private refcount는 0입니다. 공유 refcount는 B의 사용을 나타내는 1이 남습니다. Credit은 2를 유지합니다. B의 pin이 남아 있으므로 D의 frame을 다른 페이지에 재사용할 수 없습니다. Credit의 상한은 5이며 모든 pin 호출 횟수를 세는 값은 아닙니다.

선택 후속 질문: 마지막 공유 refcount만 보면 A가 그 전에 몇 번 중첩 pin했는지 알 수 있을까요? 어떤 호출 이력을 복원할 수 없나요?

Q17 · 다른 인터페이스의 보호 책임

구성한 시작 상태: 별도의 인터페이스 이전 설계입니다. 기존 caller는 CUBRID READ fix로 페이지를 읽었습니다. 새 PostgreSQL wrapper는 같은 identity의 buffer를 pin하고 주소만 반환합니다. Caller는 반환받자마자 페이지 바이트를 읽습니다. 다른 backend B도 같은 페이지를 pin한 상태입니다. B는 content 변경에 필요한 보호를 잡고 페이지를 변경하고 있습니다.

예측 질문: Caller가 안전하게 읽도록 하려면 누가 어떤 content 보호를 확보하고 반납하는지 wrapper의 계약에 어떻게 적어야 할까요?

논의 후 설명 보기

Pin은 caller가 사용하는 동안 frame을 다른 페이지로 재사용하지 못하게 합니다. 하지만 다른 backend의 페이지 변경과 읽기 접근이 충돌하지 않는다는 보장까지 주지는 않습니다. 따라서 wrapper의 계약에는 누가 content 보호를 획득하고 반납할지 적어야 합니다. 일반 공유 버퍼 읽기에서는 caller가 바이트를 보기 전에 호환되는 content lock을 얻어야 합니다. Wrapper가 그 보호를 확보해 반환할지, caller가 별도로 확보할지를 명시해야 합니다. 주소와 pin만 반환해서는 기존 READ fix의 계약을 재현할 수 없습니다.

선택 후속 질문: Wrapper가 content 보호까지 확보해 반환할지, caller가 따로 확보할지 선택할 때 각각의 반환 계약을 어떻게 적겠습니까?

화면 안내: 상태 변화 화면: 상태 추적 · 어느 backend가 아직 재사용을 막고 있을까?. 시작 상태를 확인하고 다음 단계에서 달라지는 필드를 예측합니다. 이 사례는 독립적으로 초기화합니다.

근거: PinBuffer · 최대 credit.

설계 논증 이어가기

화면 안내: 확장 화면 순서: 중첩 사용은 왜 private 기록으로 충분할까? (EN) → 메모리의 같은 주소가 왜 계속 같은 페이지를 가리켜야 할까? (EN) → 교체 과정에 사용자가 보이지 않으면 무엇이 깨질까? (EN)

Private refcount는 한 backend 안에서 같은 페이지를 몇 번 pin하고 아직 반납하지 않았는지 셉니다. Shared refcount는 그 페이지의 frame을 계속 유지해야 하는 공유 사용 기록입니다. Backend의 첫 pin은 공유 상태를 바꿉니다. 이미 pin한 페이지의 중첩 pin은 private 수치만 늘립니다. 그 backend의 마지막 pin 반납까지 페이지 identity를 재사용으로부터 보호합니다. Pin 자체가 다른 backend의 content 변경을 직렬화하지는 않습니다. Usage_count도 페이지를 소유한 주체를 표시하는 값은 아닙니다.

다음 수명 사례는 따로 시작합니다. 페이지 H는 메모리에 있습니다. Backend A가 H를 두 번 pin한 상태입니다. A의 두 사용이 끝나기 전에 공유 사용 기록을 없애는 변경을 가정하겠습니다. 그러면 Clock이 사용 중인 H를 후보로 잘못 확보할 수 있습니다. Content lock을 잠시 잡지 않는 두 접근 사이에도 pin은 frame 재사용을 막아야 합니다.

중첩 pin마다 공유 count를 올리는 다른 대안도 가능합니다. 각 획득에 맞추어 반납하면 안전할 수 있습니다. 대신 공유 atomic 갱신의 비용과 count가 나타내는 의미가 달라집니다.

화면 안내: 대안의 전이: 모든 pin이 공유 참조 수를 갱신하게 하면 어떨까?.

이번에는 중첩 획득을 모두 공유 기록에 더하는 대안을 구성하겠습니다. Backend는 획득 전에 현재 identity를 다시 검사합니다. 획득할 때마다 공유 사용 기록을 증가시킵니다. 읽거나 변경할 때는 바이트 접근을 따로 보호합니다. 반납하거나 오류가 나면 그 획득에 대응하는 기록만 정리합니다. 모든 사용 기록이 없어졌을 때만 identity를 재사용할 수 있게 합니다.

이것은 설명용 대안입니다. 중첩 획득이 m번이면 공유 atomic 작업도 그때마다 추가됩니다. Private 사용의 첫 획득과 마지막 반납에만 공유 기록을 바꾸는 방식과 비용이 다릅니다. 각 획득에 맞추어 반납하기 위해 private 기록을 유지하는 것은 여전히 유용합니다. 공유 사용 기록을 없애려면 같은 수명을 보장하는 대체 보호가 필요합니다. 그 보호 없이 기록만 제거하면 사용 중인 frame을 재사용할 수 있으므로 안전한 빠른 pin 대안이 아닙니다.

화면 안내: 관측과 반증: Pin 규칙은 어떻게 검증할 수 있을까?.

추가할 probe에서는 backend 안의 private 중첩 수와 공유 refcount의 변화를 기록하겠습니다. Mapping을 보호한 상태에서 현재 페이지 identity도 기록합니다. Content lock을 기다리는 것은 페이지 바이트 접근을 위한 대기입니다. 중첩 pin을 반납하는 기록과는 구분해야 합니다. A의 유효한 사용이 남아 있는데 frame이 재사용되면 수명 보호에 반례가 됩니다. 매 획득마다 공유 사용 기록을 갱신하는 대안은 공유 atomic 비용을 바꿉니다. 구성한 모델만으로 실행 시간이 줄어든다고 입증하지는 않겠습니다.

서로 다른 사용자는 어떻게 보호할까요?

화면 안내: 추가 화면: 여러 클라이언트가 쓰는 페이지는 어떻게 보호할까? → 공유 참조 수가 backend 수보다 많을 수 있는 이유는? → 동시 요청은 같은 페이지를 어떻게 찾고 사용할까? → 각 backend는 얼마나 앞서 페이지를 pin해야 할까?.

공유 pin 기록은 pool 전체의 숫자 하나가 아닙니다. 각 descriptor에 따로 있습니다. Backend마다 자기 안의 중첩 pin도 따로 셉니다. 앞 질문과 독립적인 사례로, 유효한 페이지 하나에 진행 중인 I/O가 없다고 하겠습니다. A가 그 페이지를 세 번 pin하고 B가 한 번 pin하면 공유 count는 2입니다. A가 자기의 세 pin을 모두 반납해도 B의 공유 사용 기록 1이 남습니다. 따라서 frame을 재사용할 수 없습니다.

이 고정 20devel 소스의 비동기 읽기에서는 I/O가 frame을 계속 사용해야 하는 경우도 있습니다. 요청한 backend가 오류로 끝나더라도 읽기가 완료될 때까지 frame을 지키려고 별도의 수명 pin을 추가할 수 있습니다. 그래서 공유 count가 항상 실제 client 수와 같다고 일반화해서는 안 됩니다.

여러 backend가 같은 페이지를 찾고 사용하는 보호도 보겠습니다. 페이지 식별자를 찾는 mapping 보호는 분할돼 있습니다. 페이지 바이트와 진행 중인 I/O는 buffer별로 보호합니다. 교체 후보를 확보한 뒤에도 현재 상태를 다시 검사합니다. 이 장치들은 동시 사용을 보호합니다. 모든 client가 같은 용량을 받거나 낮은 지연을 얻는다는 보장은 별도로 확인해야 합니다.

여기서 자세히 따라가는 trace는 고정된 20devel 소스입니다. PostgreSQL 18에도 핵심 pin·credit·ring 장치가 있지만 lock의 세부 구현은 다릅니다.

Read stream은 곧 사용할 페이지를 미리 읽고 pin하는 경로입니다. PostgreSQL은 pool 크기와 최대 backend 수를 바탕으로 backend별 권고 pin 예산을 계산합니다. 이 예산을 사용하는 read stream은 작업 strategy의 제한과 남은 예산을 함께 확인합니다. 이를 바탕으로 아직 사용하지 않을 페이지를 미리 확보하는 양을 줄입니다.

Stream이 현재 pin한 buffer를 하나도 보유하지 않는 경우에는 예외가 있습니다. 남은 예산이 0이어도 작업이 진행하도록 하나를 더 허용합니다. 이 정책은 아직 반납하지 않은 pin의 양을 조절합니다. 모든 resident 페이지를 나누는 client별 quota나 모든 pin의 엄격한 상한은 아닙니다.

Clock sweep: hand가 무엇을 바꾸는가?

화면 안내: 전용 발표 장: 가득 찬 풀에서 스캔이 확보할 후보를 찾습니다 · 재사용 검사를 유지하면서 정확한 최근 순서를 만듭니다 · 탐색 결과를 바꾸는 사건을 관찰합니다.

이번 장에서는 descriptor 배열에서 다음 교체 후보를 찾겠습니다. Descriptor는 frame의 현재 페이지와 사용 상태를 관리하는 구조입니다. 여러 allocator가 탐색할 때 공유 cursor인 atomic hand가 각자 방문할 위치를 나누어 줍니다. Atomic 연산은 한 번의 나눌 수 없는 변경으로 처리됩니다. CAS는 compare-and-swap입니다. 앞서 읽은 상태가 그대로일 때만 원하는 새 상태로 바꾸는 연산입니다.

Allocator는 방문한 frame이 사용 중이면 건너뜁니다. 사용 중이지 않지만 보존 credit이 있으면 credit을 줄입니다. 조건이 맞으면 자신의 pin을 확보합니다. Credit 0을 읽었다는 관찰만으로 pin을 얻은 것은 아닙니다. Pin을 만드는 상태 변경에 성공해야 후보를 확보한 것입니다.

화면 안내: 화면: Hand의 한 번 방문에는 세 가지 결과가 있습니다 → 새로 들이기, 다시 사용하기, 선택하기는 다른 상태를 바꿉니다. 다음 새 예측은 이 대본의 표로 진행합니다.

기본 교체 경로에서 allocator는 clock hand가 가리키는 공유 descriptor를 방문합니다. 다른 사용의 pin이 있으면 건너뜁니다. Pin이 없고 credit이 양수이면 credit을 하나 줄이고 다음 descriptor로 갑니다. Pin이 없고 credit도 0이면 CAS로 자신의 pin을 얻습니다. 이 변경에 성공하면 후보를 반환합니다.

이 시점에 끝난 것은 descriptor 선택입니다. 페이지가 dirty라면 이후 caller가 필요한 쓰기를 처리합니다. 기존 페이지 identity를 제거하는 작업도 이후에 있습니다.

이제 앞 화면과 독립적인 작은 모델로 예측해 보겠습니다. Descriptor를 네 개만 두고 한 실행 주체가 차례로 방문합니다. 실제 PostgreSQL의 pool 설정이나 실행 캡처는 아닙니다. Hand는 F0에서 시작합니다. 방문 순서는 F0, F1, F2, F3입니다. 표의 refcount는 이 allocator가 선택하기 전에 다른 backend가 보유한 공유 pin 수입니다. 동시 변경과 진행 중인 I/O는 없고, 네 페이지는 모두 clean이라고 가정합니다.

예측: Allocator가 처음 반환할 descriptor는 무엇일까요? 방문할 때마다 credit이 어떻게 바뀌는지 적어 보세요. 선택한 descriptor의 refcount도 적어 보세요. F2의 credit을 0으로 줄인 방문에서 곧바로 F2를 선택할까요?

예측 후 순서 보기
  1. F0: credit을 2 → 1로 줄이고 다음으로 이동합니다.
  2. F1: pin 중이므로 건너뜁니다. Credit은 0으로 유지됩니다.
  3. F2: credit을 1 → 0으로 줄이고 다음으로 이동합니다. 이 방문에서는 선택하지 않습니다.
  4. F3: credit이 0이고 pin이 없습니다. CAS로 자신의 pin을 얻어 refcount를 1로 바꾸고 반환합니다. 새 페이지 identity의 내용을 읽었다는 뜻은 아닙니다.

시작 상태를 바꿔 다시 예측: 첫 사례의 결과를 이어받지 않습니다. 표의 처음 상태로 돌아가되 F3의 초기 credit만 1로 바꿉니다. 나머지 조건은 그대로입니다. 처음 반환할 descriptor를 다시 구해 보세요.

다시 예측 후 답 보기

첫 순회에서 allocator는 F0의 credit을 1로 줄입니다. F2와 F3의 credit은 각각 0으로 줄입니다. 다음 순회에서 F0의 credit을 1에서 0으로 줄이고 F1은 pin이 있으므로 건너뜁니다. 그다음 F2를 방문하면 pin도 없고 credit도 0입니다. Allocator는 F2에 자신의 pin을 얻고 반환합니다. 이 계산은 바꾼 시작 상태에서 따로 수행합니다. 첫 사례를 마친 뒤의 상태를 사용하지 않습니다.

이 모델은 모든 접근의 정확한 최근 순서를 유지하지 않습니다. Exact LRU는 어느 페이지를 더 최근에 사용했는지 전체 순서를 관리합니다. Clock은 제한된 credit을 기억하고 탐색 중에 줄입니다. 따라서 두 정책이 메타데이터를 갱신할 때와 후보를 찾을 때 어떤 일을 하는지 비교할 수 있습니다. 이 작은 추적만으로 어느 쪽의 처리량이 더 높은지 판단하지는 않겠습니다.

Q18 · Clock 후보의 동시 변경

구성한 시작 상태: 별도의 동시 pin 사례입니다. Hand는 D의 credit을 1에서 0으로 줄인 뒤 다음 descriptor로 갔습니다. 이후 allocator A가 D를 다시 방문하고 refcount 0과 credit 0을 읽었습니다. A는 그 상태를 기대하는 CAS로 자기 pin을 얻으려 합니다. 하지만 CAS 전에 backend B의 정상적인 첫 pin이 성공했고 B는 그 pin을 유지합니다. 다른 상태 변화는 없습니다.

예측 질문: A가 D를 반환할 수 있는지 결정하는 것은 앞서 읽은 0인가요, 이후 CAS의 결과인가요? 이 실행 순서에서 이유를 설명해 보세요.

논의 후 설명 보기

B가 먼저 pin을 얻었으므로 A가 읽은 상태는 더 이상 현재 상태가 아닙니다. A의 CAS는 실패합니다. A가 다시 읽으면 B의 pin이 남아 있습니다. 따라서 이 방문에서는 D를 반환할 수 없습니다. 상태 0을 읽는 것은 관찰입니다. CAS에 성공해야 실제로 pin의 보호를 확보합니다.

동시 변경이 없는 경우에도 두 방문을 구분해야 합니다. 양수 credit을 0으로 줄인 방문에서는 다음 descriptor로 이동합니다. 나중에 credit 0인 상태로 다시 방문했을 때 후보를 선택합니다.

설계 논증 이어가기

화면 안내: 확장 화면 순서: 정확한 LRU는 접근 순서 유지 비용을 냅니다 (EN) → 동시 변경 없는 풀에서는 방문 상한을 구할 수 있습니다 (EN) → D29 · usage_count≤5이면 여섯 순회가 보장될까요? (EN)

Exact LRU에서 이미 위치를 아는 항목을 list에서 옮기는 splice 자체는 O(1)입니다. Clock과 비교할 때는 작업을 어디에 배치하는지 봐야 합니다. LRU는 hit 때 공유 사용 순서를 갱신하는 동기화가 필요합니다. Clock은 allocation 때 descriptor를 방문하고 credit을 줄이는 aging을 수행합니다. Credit만 제거하는 정책 대안도 pin, WAL, mapping 규칙을 유지하면 안전할 수 있습니다. 교체 선호를 바꾸는 것과 사용 보호를 제거하는 것을 구분해야 합니다.

Credit의 최댓값 5를 보고 동시 실행에서도 여섯 pass 안에 성공한다고 말할 수는 없습니다. 그런 방문 상한은 allocator 하나만 있고, pin 상태가 고정돼 있고, 새 credit이 더해지지 않으며, CAS에 성공한다는 가정 아래에서 계산합니다. 다른 backend가 credit을 올리거나 pin하면 그 가정이 깨집니다. Trycounter는 credit 감소 CAS가 성공해도 reset됩니다. D29에서는 descriptor 방문, credit 감소, 후보 확보인 claim, 간섭에 따른 retry를 각각 세겠습니다.

Ring: 공유 frame의 ID를 작업별로 기억한다

화면 안내: 전용 발표 장: 스캔은 왜 앞서 사용한 프레임을 다시 찾을까? · 스캔 용량 분리에는 공유 식별자와 실패 처리 규칙이 필요하다 · 어떤 관측으로 ring 설명을 반증할 수 있을까?.

이번 장은 반복 읽기와 긴 scan이 경쟁하는 새로운 사례입니다. H1과 H2는 반복해서 읽는 hot 페이지입니다. S1, S2, S3는 scan이 한 번씩 읽을 별도의 페이지입니다. Access-strategy ring은 이 작업이 다음에 다시 사용할 후보의 공유 buffer ID를 작은 배열에 기억합니다. ID를 기억한 backend가 해당 frame을 독점하는 것은 아닙니다. 현재 사용은 pin으로 보호합니다. Credit은 얼마나 보존할지 정하는 선호입니다. NORMAL, BULKREAD, BULKWRITE, VACUUM은 서로 다른 strategy의 이름입니다.

화면 안내: 화면: 로컬 슬롯은 공유 pool의 프레임을 가리킨다. 소스의 factory 크기 계산은 질문이 있을 때 펼칩니다.

앞서 정한 시작 상태에서 반복 읽기와 scan을 함께 실행한다고 생각해 보겠습니다. 한 작업은 H1과 H2를 반복해서 읽습니다. 긴 scan은 S1, S2, S3를 한 번씩 읽습니다. Scan의 모든 miss가 전역 교체 경로에서 후보를 고르면 반복해서 사용하는 페이지도 교체 압력을 받을 수 있습니다. PostgreSQL은 이런 대량 작업의 caller에게 buffer access strategy를 사용할 수 있게 합니다.

Ring은 backend 안에 있는 작은 배열입니다. 각 slot에 공유 buffer의 ID를 저장합니다. Backend는 다음 slot이 가리키는 frame의 현재 상태를 검사합니다. Pin이 없고 credit이 0 또는 1이면 그 frame의 재사용을 시도합니다. Slot이 비어 있거나 가리키는 frame을 사용할 수 없으면 전역 Clock에서 후보를 찾습니다. 새로 선택한 buffer의 ID를 그 slot에 넣습니다.

Backend가 소유하는 것은 ring 배열입니다. 배열이 가리키는 frame은 공유 pool에 있으며 다른 backend도 사용할 수 있습니다.

Strategy이번 세션에서 기억할 점
BAS_NORMAL기본 clock 경로. 별도의 ring 객체를 만들지 않음.
BAS_BULKREAD대량 읽기에 사용할 buffer를 재사용함. Ring에서 고른 후보가 dirty 상태인 permanent 페이지이고, 이를 쓰기 위해 WAL flush가 필요하면 ring에서 제외하고 다른 후보를 구할 수 있음.

Ring 크기는 고정 리비전의 factory와 실제 caller를 함께 읽어야 합니다. 이 소스에서 bulk-read 기본 크기는 256 KiB를 바탕으로 계산합니다. AIO, 즉 비동기 I/O에 필요한 여유분과 pin 한도를 반영합니다. Bulk-write factory는 16 MiB이고 vacuum factory는 2 MiB입니다. 공통 크기 처리에서는 공유 buffer 수의 1/8을 상한으로 둡니다. Caller가 별도의 크기를 지정하는지도 확인해야 합니다. 아래 두 slot은 설명용 모델이며 실제 factory의 크기가 아닙니다.

CUBRID private LRU와 PostgreSQL ring은 모두 대량 작업의 교체 압력을 다룹니다. 하지만 관리하는 객체가 다릅니다. CUBRID private LRU는 pool이 관리하는 BCB의 정책 영역이고 quota가 있습니다. PostgreSQL ring은 backend 내부의 공유 buffer ID 배열입니다. 두 구조를 각각 독립된 buffer pool이라고 설명하면 실제 frame을 누가 관리하고 사용하는지 놓치게 됩니다.

다음 strategy 질문은 새로운 쓰기 조건에서 시작하겠습니다. BULKREAD backend가 자기 ring에서 dirty 영구 페이지를 후보로 골랐습니다. 그 페이지를 쓰려면 필요한 로그를 추가로 영속화해야 합니다. PostgreSQL의 페이지 LSN은 이 페이지 내용에 필요한 로그 위치를 나타냅니다.

이 조건에서 BULKREAD backend는 자기 ring slot에 저장된 후보의 buffer ID를 지웁니다. 후보를 확보하면서 얻은 pin을 반납합니다. 그 뒤 다른 후보를 찾는 경로로 다시 시도합니다. 공유 페이지의 DIRTY 표시와 변경 내용은 그대로 남깁니다.

BULKWRITE와 VACUUM은 필요한 WAL을 먼저 보존하고 페이지 쓰기를 시도하는 별도 분기를 따를 수 있습니다. 따라서 strategy 이름만 바꾸어 같은 처리라고 설명해서는 안 됩니다. 실제 caller가 선택한 strategy와 각 경로의 pin·내용 보호를 함께 확인해야 합니다.

Ring을 사용하지 않고 normal Clock으로 후보를 찾는 대안도 안전성 검사를 유지할 수 있습니다. 긴 scan이 자주 사용하는 페이지를 밀어내는 scan pollution과 경쟁 비용이 얼마나 달라지는지는 workload에 달려 있습니다. 별도의 private scan pool은 실제 공간을 나누는 대안입니다. 대신 같은 데이터의 바이트 중복과 사본 사이의 일관성인 coherence를 관리해야 합니다. BULKREAD가 WAL 조건 때문에 후보를 거절할 때는 자기 ring slot만 비우고 공유 dirty 페이지를 남깁니다. D30을 먼저 논의하겠습니다. D31은 다음 writeback 설명에서 이어가겠습니다.

이번에는 writeback 동안 후보 예약을 유지하는 대안을 구성하겠습니다. 재사용을 맡은 스레드는 모든 lookup·pin 경로가 확인하는 예약을 설치합니다. 다른 writer의 변경을 막고, 제출할 내용과 일치하는 로그 위치를 확인합니다. 필요한 WAL을 먼저 보존한 뒤 안정된 바이트를 씁니다.

Mapping을 보호한 상태에서 자기만 사용하는 조건과 clean 상태가 계속 유지되는지 확인합니다. 조건을 만족하면 기존 mapping을 해제합니다. 오류나 취소 때는 기존 identity와 아직 기록할 변경을 남겨야 합니다. 예약과 사용 소유권은 정해진 순서로 해제합니다.

이것은 설명용 대안입니다. 다른 사용을 허용한 뒤 현재 상태를 재검사하는 대신 예약으로 중간 사용을 막습니다. 모든 lookup·content 경로가 예약과 lock 순서를 따라야 합니다. 저장장치 I/O가 지연되는 동안 reader와 writer도 기다릴 수 있습니다. Checkpoint와 어떤 순서로 실행할지도 정해야 합니다. 현재 구현은 병행 사용을 허용하며, 그 결과 writeback 뒤에 재사용을 포기할 수 있습니다.

화면 안내: 관측과 반증: 쓰기와 invalidation 사이의 공백을 관측하기.

추가할 probe에서는 페이지 LSN과 content-lock 획득 결과를 기록하겠습니다. Write 뒤의 DIRTY와 refcount, mapping lock 획득, InvalidateVictimBuffer의 결과도 연결하겠습니다. IOOP_REUSE와 IOOP_EVICT는 최종 invalidation의 현재 상태 검사보다 먼저 증가합니다. 그 뒤 InvalidateVictimBuffer가 재사용을 거절할 수 있습니다. 따라서 eviction counter만으로 이전 mapping이 실제로 해제됐다고 판단할 수는 없습니다. 새 DIRTY가 남아 있는데 mapping을 해제했다면 기록하지 않은 변경을 보존한다는 조건에 반례가 됩니다. Checkpoint의 영속화까지 설명하려면 이후 sync와 log의 증거도 필요합니다.

여러 client의 사용을 비교할 때 private라는 말의 대상을 확인하겠습니다. CUBRID private replacement domain은 메모리에 있는 페이지 기록과 적응형 quota를 연결하는 교체 정책 영역입니다. 독점 cache가 아니며 두 session이 같은 private list를 배정받을 수도 있습니다.

PostgreSQL의 private refcount는 backend가 아직 반납하지 않은 사용 횟수를 셉니다. Credit은 페이지를 더 보존할 기회를 기억합니다. Ring은 bulk 작업이 먼저 다시 사용할 공유 frame ID를 기억합니다. 이 세 역할을 CUBRID의 같은 용량 정책으로 해석하지는 않겠습니다.

CUBRID의 promotion도 두 종류로 나누어 보겠습니다. Private에서 shared로 옮기는 해당 마지막 unfix 경로는 caller의 private-list index와 BCB의 index가 다른지 검사합니다. 또는 페이지가 hot이고 충분히 오래됐는지 확인합니다. 이동하면 BCB를 shared list의 middle에 넣습니다. 이 검사가 페이지를 사용한 모든 서로 다른 사용자의 수를 세는 것은 아닙니다.

Hot-zone boost는 현재 list 안에서 페이지의 보존 위치를 올리는 별도 작업입니다. Domain을 옮기지 않는 일반 policy 처리에서는 LRU1을 그대로 둡니다. LRU2는 충분히 오래됐을 때 boost합니다. LRU3도 boost합니다. PostgreSQL이 credit을 올리거나 ring 후보를 거절하는 작업은 descriptor를 shared LRU로 옮기는 작업과 구분해야 합니다.

어느 구조가 혼합 workload에 유리한지는 아직 실행하지 않은 실험 질문입니다. Hot 페이지를 반복해서 읽는 client에 긴 scan과 writer를 더하겠습니다. Client 수, working set이 서로 겹치는 정도, scan 양, pin 유지 시간을 각각 바꿔 보겠습니다. 비교할 때 데이터와 query, 영속성 조건, cache의 byte 예산, 저장장치를 맞춰야 합니다.

관측할 값은 client별 처리량, read와 write, CPU 사용, 동기화 대기입니다. p95와 p99는 요청의 95%와 99%가 각각 그 이하의 지연으로 끝나는 경계입니다. 이런 tail 지연과 hot 페이지가 얼마나 남아 있는지를 함께 비교해야 합니다.

PostgreSQL 18의 pg_stat_io로 작업 context별 I/O를 관찰할 수 있습니다. pg_buffercache는 개별 buffer 상태를 관찰하는 경로입니다. 두 경로가 모든 client의 전체 접근 이력을 제공하는 것은 아닙니다.

pinning_backends는 공유 refcount를 그대로 표시합니다. 따라서 진행 중인 비동기 I/O가 frame을 보호하는 수명 pin도 포함될 수 있습니다. Buffer를 차례로 관측하므로 pool 전체를 같은 순간에 읽은 snapshot도 아닙니다. Hand 방문, CAS 재시도, ring 후보 거절의 원인은 추가 probe가 필요합니다. 이 설명에서 benchmark 결과나 client별 용량 공정성을 입증하지는 않겠습니다.

사례 A · Flush 횟수는 늘었는데 allocator가 기다린다

사례 A는 따로 시작합니다. CUBRID pool에 invalid frame이 없습니다. Allocator B는 direct victim을 기다립니다. Cold dirty 페이지 P의 사본 G 제출이 성공했습니다. P의 BCB 포인터를 post-flush queue에 넣는 데도 성공했습니다. Post-flush가 항목을 꺼내기 전에 writer A가 P를 fix합니다. A는 P에 G+1의 변경을 남기고 fix를 유지합니다. 그 뒤 post-flush가 실행해 해당 BCB를 꺼냈습니다.

A의 fix가 남아 있고 새로운 DIRTY도 설정돼 있습니다. 이 둘이 현재 frame의 재사용을 막습니다. Post-flush는 이전 G의 FLUSHING을 해제하고 그 flush를 기다리는 스레드를 깨웁니다. G+1의 DIRTY와 A의 현재 사용 보호는 유지해야 합니다.

관측에서는 소비자의 실행과 queue 항목 소비를 먼저 연결하겠습니다. 그 시점의 BCB flag와 fix, zone과 quota를 기록합니다. Direct victim을 기다리는 요청이 있었는지, 제안이나 배정이 발생했는지도 시간 순서로 연결합니다. Flush 횟수 증가만으로 queue 소비나 배정 성공을 판단할 수는 없습니다. 이 사례는 특정 버그나 starvation을 실제 서버에서 입증한 기록이 아닙니다.

사례 B · Ring이 있어도 scan이 전역 clock으로 간다

사례 B는 PostgreSQL에서 독립적으로 시작합니다. Bulk-read strategy의 다음 ring slot은 dirty 영구 페이지 R을 가리킵니다. Permanent는 BM_PERMANENT로 구분하는 페이지 범주입니다. R을 처음 선택할 때 다른 pin은 없었고 credit은 1이었습니다. Backend는 필요한 content lock을 기다리지 않고 얻었습니다. 하지만 R의 페이지 LSN까지 WAL flush를 더 수행해야 합니다. 같은 시점에 별도의 hot 페이지 H는 다른 backend가 pin하고 있습니다.

이 조건에서는 BAS_BULKREAD의 ring 후보를 거절할 수 있습니다. StrategyRejectBuffer가 현재 slot을 InvalidBuffer로 비웁니다. Caller는 pin과 lock을 반납하고 다른 후보를 구합니다. 그 거절만으로 메모리에 있는 페이지 R의 identity를 제거하지는 않습니다. 전역 Clock도 pin이 남아 있는 H는 건너뜁니다.

Q24 · 이름이 다른 모듈의 검토

구성한 시작 상태: 마지막은 설명용 모듈의 인터페이스 검토 사례입니다. 실제 엔진 API가 아닙니다. 문서에는 Acquire(P) → Use → Release(P)라는 사용 경로와 SubmitImage(P) → Complete(ticket) → Offer(frame) → Retag(frame, Q)라는 쓰기·재사용 경로가 있습니다. P는 사용하려는 페이지이고, Q는 같은 frame에 나중에 담을 페이지입니다. Submit은 사본을 전달하고 그 작업을 가리키는 ticket을 반환합니다. Complete와 Offer가 어디까지 보장하는지, Retag가 현재 상태를 검사하는지는 아직 정하지 않았습니다.

예측 질문: 이 문서만으로 안전한 재사용을 설명하려면 각 함수가 무엇을 보장하고 누가 검사하는지 어떤 계약부터 정해야 할까요?

논의 후 설명 보기

먼저 Acquire와 Release가 어떤 페이지 identity에 대한 사용을 확보하고 반납하는지 정의해야 합니다. Submit에는 어떤 안정된 이미지를 전달하는지 적어야 합니다. Complete에는 어떤 저장 단계까지 마쳤다는 뜻인지 적어야 합니다. Offer에는 제안을 받은 주체의 권한과, 이후 상태 변화로 취소될 수 있는지를 명시해야 합니다.

Retag는 필요한 보호를 잡고 현재의 재사용 조건을 검사해야 합니다. 이전 mapping을 어떻게 제거하는지도 정해야 합니다. 각 단계가 실패했을 때 누가 무엇을 정리할지 함께 명시해야 합니다. CUBRID와 PostgreSQL은 서로 다른 필드와 호출 경로로 이 책임을 수행합니다. API 이름만 읽어서 보장 범위를 정할 수는 없습니다.

Q23과 Q24의 새 사례를 마친 뒤 원인 구분을 더 이어가겠습니다. G의 완료 counter가 늘고 post-flush heartbeat가 정상이더라도 frame 제안이 없을 수 있습니다. 새 DIRTY 때문에 거절했을 수 있고, 현재 zone이나 quota 정책에서 거절했을 수도 있습니다. D32에서는 필요한 보호를 잡고 본 현재 상태와 이유별 counter를 이용해 이 원인들을 구분할 관측을 고르겠습니다.

화면 안내: 별도로 초기화한 제거 모델: 이전 이미지는 완료하고 새 dirty 작업은 유지합니다.

이 trace도 앞 사례와 별도로 시작합니다. Q는 기다리는 allocator입니다. F는 메모리 frame이고 P는 그 frame에 있는 영구 페이지입니다. G는 로그 위치 120에 대응하는 사본입니다. G+1은 사본 확보 뒤 로그 위치 180까지 반영한 메모리 변경입니다. 이 이름들은 모두 설명용 표기입니다.

Flusher는 G를 확보하는 동안 writer가 페이지를 변경하지 못하도록 필요한 보호를 확보했습니다. 그 상태에서 G를 안정되게 확보했습니다. 사본에 맞는 WAL 순서를 지켜 제출했습니다. 처음 P는 shared LRU3에 있습니다. DIRTY=0, FLUSHING=1, fcnt=0입니다. BCB에 연결된 대기자는 없으며 여기에는 flush 대기자도 포함합니다. Q는 별도의 allocator queue에서 기다립니다.

이 사례에서는 명시한 vacuum worker만 P를 변경합니다. 필요한 로그를 남기고 마지막 fix를 반납합니다. 이 특수 unfix 분기는 페이지를 cold 영역에 유지합니다. 일반 unfix에서는 페이지를 승격할 수 있으므로 같은 사건으로 바꾸면 시작 조건과 결과도 달라질 수 있습니다.

검사를 제거하는 모델은 현재 DIRTY에 대한 최종 재사용 검사를 모두 과거의 완료 boolean으로 대체합니다. 소비자와 수신자를 포함해 현재 DIRTY를 검사할 다른 지점도 같은 방식으로 대체한다고 가정합니다. 나머지 조건은 유지합니다.

이 모델은 실제 코드에서 소비자 검사 한 줄만 지우는 변경과 다릅니다. 그 한 줄만 지워도 수신자의 DIRTY 검사와 assertion은 남습니다. 따라서 한 줄 삭제만으로 안전하지 않은 retag가 발생한다고 주장하지는 않겠습니다. 독립적으로 구성한 최종 재사용 모델에서 왜 이후 변경의 기록 작업을 잃는지 설명하겠습니다.

D33에서는 검사 하나를 제거하는 변경을 검토하겠습니다. 먼저 어떤 보호 구간이나 검사를 제거했는지 명시해야 합니다. 그 사이 어떤 actor가 상태를 바꿀 수 있는지도 설명해야 합니다. 검사 대신 사용할 보호와 실패·취소 시의 정리 주체를 함께 제시해야 합니다. 계속 유지하는 reservation과 현재 상태 재검사는 비용을 서로 다른 지점에서 사용합니다. 측정 없이 어느 대안이 더 빠르다고 결론 내리지는 않겠습니다.

마지막에는 전체 페이지 여정을 다시 연결하겠습니다. 요청한 identity를 찾고 사용 수명을 확보하는 단계부터 시작합니다. 바이트 보호, 변경과 WAL, 사용 반납, 이미지 전달을 차례로 설명합니다. 현재 후보의 적합성을 검사한 뒤 이전 identity를 제거하고 frame을 재사용하는 단계까지 이어갑니다. 안전하지 않아 거절한 생략 하나와 안전한 대안 하나를 포함해 설명을 완성하겠습니다. 여기서 마지막 세미나를 마치고 유지보수 자료로 연결하겠습니다.

마지막 연결 질문

한 스레드가 페이지를 요청한 순간부터 같은 frame을 다른 페이지에 재사용하는 순간까지 따라가겠습니다. 먼저 스레드는 요청한 identity를 찾습니다. 메모리에 없으면 페이지를 담을 공간을 마련합니다. 스레드는 fix나 pin으로 사용하는 동안의 frame을 보호합니다. 바이트 접근에 필요한 보호도 확보합니다.

페이지를 변경하는 caller는 필요한 로그를 남기고 dirty 상태를 기록합니다. Caller가 사용을 반납해도 페이지는 메모리에 남을 수 있습니다. 아직 기록하지 않은 변경이 있으면 dirty 상태도 남습니다. 이후 정책이나 caller의 필요에 따라 쓰기를 맡은 주체가 이미지를 전달하고 완료 상태를 정리합니다. 마지막으로 재사용을 맡은 주체가 frame 재사용에 필요한 동기화를 확보합니다. 그 상태에서 현재 사용 상태와 재사용 조건을 다시 검사합니다. 조건을 만족한 뒤 페이지 identity를 바꿉니다.

Daemon이나 정책 이름이 달라도 확인할 질문은 같습니다. Frame에 지금 어느 페이지가 들어 있습니까? 어떤 스레드가 사용하고 있습니까? 어느 시점의 이미지가 어느 저장 단계까지 기록됐습니까? 다음 단계를 누가 맡고, 그 주체가 어떤 조건을 확인해야 합니까? CUBRID와 PostgreSQL은 이 질문에 답하는 구체적인 필드와 실행 경로가 다릅니다. 그 차이를 기준으로 소스를 비교할 수 있습니다.

이번에는 완료 기록을 명시적으로 다루는 대안을 구성하겠습니다. 각 기록에 어떤 페이지 이미지인지 적습니다. 이미지를 수락한 단계, write한 단계, 영속화한 단계를 각각 명시합니다. 완료 처리는 그 기록이 가리키는 진행 중 이미지만 정리합니다.

현재 frame을 재사용하려면 새로 필요한 보호를 잡고 적합성을 확인해야 합니다. 새 사용이나 아직 기록하지 않은 dirty 변경이 있으면 재사용을 거절합니다. 실패한 기록 작업은 해당 작업을 다시 시도합니다. 이전 완료 기록을 현재 재사용의 승인으로 사용하지는 않습니다.

이것은 설명용 대안입니다. Ticket과 version을 언제까지 유지할지 기록하고 취소를 맡는 주체를 정해야 합니다. 그만큼 metadata가 필요합니다. 모든 단계를 계속 직렬화하는 방식은 오랫동안 다른 접근을 막는 또 다른 대안입니다. 어느 방식에서도 WAL 순서, 이미지 일관성, 이후 변경의 기록, identity의 사용 수명을 보존해야 합니다. 남은 작업을 다시 발견해 진행할 경로도 갖춰야 합니다.

관측에서는 현재 사용과 dirty 상태를 queue 소비에 연결하겠습니다. Frame을 준비한 producer의 배정과 allocator의 수신 결과도 연결하겠습니다. 관측하지 않은 사건은 실제 기록처럼 만들지 않고 필요한 probe를 제안하겠습니다. 여러 원인이 같은 관측과 일치하면 유일한 근본 원인을 찾았다고 말할 수 없습니다. Observer가 추가한 비용, 스케줄러 제어, 제한된 관찰 시간도 runtime 결론의 범위를 제한합니다.
