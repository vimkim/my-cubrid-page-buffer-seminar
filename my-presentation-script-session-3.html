01 · CONNECTION

앞선 두 세션에서 오늘로

화면: 한 페이지의 여정. 요청 → fix → 사용 → unfix까지만 먼저 짚습니다.

앞선 두 세션에서는 페이지 버퍼가 왜 필요한지, 페이지 ID와 메모리 frame이 어떻게 다른지 살펴봤습니다. BCB가 무엇을 기록하고, private/shared LRU가 메모리에 올라온 페이지를 어떻게 관리하는지도 알아봤습니다. 오늘은 그 모델을 완성하겠습니다. 빈 frame이 없을 때 다음 요청을 누가 진행시키는지, PostgreSQL은 같은 문제를 어떻게 푸는지 살펴보겠습니다.

먼저 앞서 배운 내용을 하나씩 떠올려 보겠습니다. 페이지를 unfix해도 메모리에는 남아 있을 수 있습니다. 모든 사용자가 fix를 반납해도 dirty 상태는 남을 수 있습니다. LRU3에 있다는 이유만으로 바로 덮어쓸 수 있는 것도 아닙니다. 어느 페이지인지, 남아 있는 fix가 있는지, 바이트 접근은 어떻게 보호되는지, 아직 보존해야 할 변경은 무엇인지를 따로 봐야 합니다.

먼저 질문: 버퍼 pool에 빈 frame이 없습니다. Cold 페이지 P는 아무도 fix하고 있지 않지만 dirty 상태입니다. 새 페이지 Q를 요청하면 어떤 일을 끝내야 P의 frame을 재사용할 수 있을까요?

예측 후 발표자 답 보기

먼저 필요한 로그 순서를 지키고, 해당 write 경로를 통해 P의 변경을 보존해야 합니다. 그 뒤에도 P가 다시 fix되거나 dirty 상태가 되었는지, 정책상 재사용 후보로 남아 있는지 확인해야 합니다. “cold 상태다”, “남은 fix가 없다”, “한 번 썼다”는 서로 다른 사실입니다.

이 질문을 중심으로 daemon의 역할을 살펴보겠습니다. 그 전에 dirty 페이지를 쓴다는 말이 어느 시점의 바이트를 뜻하는지부터 정리하겠습니다.

02 · FLUSH BRIDGE

한 페이지, 두 세대

화면 순서: DIRTY → 사본이 필요한 이유 → 로그와 페이지의 경계 → 한 세대의 flush 단계 → DWB 경로 → 다시 dirty가 된 경우.

저장된 페이지의 값이 10이라고 하겠습니다. 메모리에서 11로 바꾸면 저장된 이미지와 메모리의 이미지가 달라집니다. DIRTY는 메모리의 이미지에 아직 저장 경로로 전달해야 할 변경이 있다는 표시입니다. Unfix로 사용을 끝내더라도 그 변경을 보존할 의무는 남습니다.

WAL의 핵심은 순서입니다. 로그가 필요한 영구 페이지에서는 변경을 설명하는 로그가 해당 데이터 페이지보다 먼저 영속화되어야 합니다. 페이지 LSA는 그 이미지가 어느 로그 위치까지의 변경을 반영하는지 나타냅니다. 로그를 먼저 보존해야 페이지 이미지를 안전하게 전달할 수 있습니다. Commit, 페이지 write, unfix는 각각 완료하는 일이 다릅니다.

Flush하는 동안에도 다른 요청은 진행해야 합니다. 안정된 이미지 11을 사본으로 확보하고 전달하는 사이, 메모리의 페이지는 12로 다시 바뀔 수 있습니다. 이때 사본 11의 세대를 G, 이후 변경의 세대를 G+1이라고 부르겠습니다. 여기서 세대, 즉 generation은 설명을 위한 이름입니다. 실제로 저장된 세대 번호나 카운터를 뜻하지는 않습니다.

사건메모리 값전달할 사본남아 있는 작업
10 → 11 변경11아직 없음11의 dirty 변경 보존
안정된 사본 확보11G = 11G의 flush 진행
다른 사용자가 12로 변경12G = 11G 진행 + G+1의 dirty 변경 보존

예측: 사본 G의 제출이 성공했습니다. 현재 메모리 값은 무엇이고, 어느 세대의 변경을 더 보존해야 할까요?

예측 후 답 보기

메모리 값은 12입니다. 제출한 이미지는 11이므로, 12를 반영하는 G+1의 dirty 상태는 남아야 합니다. G의 FLUSHING 상태를 해제해도 현재 DIRTY까지 지우면 안 됩니다.

DWB를 쓰는 경로에서는 이미지를 DWB가 받아들인 시점과 원래 데이터 볼륨인 home volume에 실제로 쓰는 시점도 구분해야 합니다. DWB는 페이지를 쓰다가 이미지가 부분적으로만 남는 문제를 다루는 별도의 write 경로입니다. Page-flush가 성공을 반환했더라도 모든 저장 단계의 영속화가 끝났다는 뜻은 아닙니다.

이제 처음 질문을 조금 더 정확하게 바꿔 보겠습니다. 누가 G의 전달을 시작하고, 누가 G의 완료 상태를 정리할까요? 그리고 현재 메모리의 페이지가 재사용 가능한 상태인지 누가 검사할까요?

03 · FOUR LOOPS

네 daemon은 서로 다른 일을 한다

화면: 네 가지 책임 → 실행과 대기 → 시작과 종료.

Daemon은 백그라운드에서 자신이 맡은 작업을 실행하고, 기다렸다가 다시 실행하는 주체입니다. CUBRID 서버의 페이지 버퍼 daemon은 공통 thread manager를 이용합니다. 다만 같은 작업을 네 worker에게 나누는 구조는 아닙니다. 각자 맡은 작업과 대기 방식, 참조하는 공유 상태가 다릅니다.

이름맡은 결과기준 소스의 대기 방식
pgbuf-page-flushCold dirty 페이지의 이미지 전달기본 1,000 ms 타이머와 frame 부족 시 wakeup. 주기가 0이면 wakeup만 기다림.
pgbuf-page-post-flushBCB 완료 정리, 조건부 direct-victim 배정유휴 상태에서 1 → 10 → 100 ms, 이후 wakeup만 기다림
pgbuf-maintain활동량에 맞춘 quota와 LRU 구역 조정100 ms 목표 주기로 작업 시도
pgbuf-flush-controlWriter가 사용할 새 token 예산50 ms 목표 주기

이 숫자가 정확한 실행 빈도를 보장하지는 않습니다. 공통 daemon 구현은 작업을 한 번 실행한 뒤 기다립니다. 정해진 주기에서 직전 작업의 실행 시간을 빼서 대기 시간을 계산합니다. 여기에 스케줄러 지연이나 I/O 시간이 더해질 수도 있습니다. 타이머가 끝났다는 사실과 실제로 유용한 일을 했다는 사실도 구분해야 합니다.

Wakeup에도 경계가 있습니다. 이 waiter는 현재 SLEEPING 상태일 때만 깨웁니다. 이미 RUNNING이면 다음 실행을 위해 wakeup 횟수를 쌓아 두지 않습니다. 따라서 작업은 공유 상태에 기록된 frame 부족 조건이나 queue를 보고 실제로 할 일을 판단해야 합니다. Wakeup만 기다리는 설정이라면 새 작업을 알리는 신호가 언제 발생하는지도 따라봐야 합니다.

Thread가 만들어지는 시점과 실제 flush 작업이 허용되는 시점도 다릅니다. 이 daemon은 recovery 전에 만들어집니다. 하지만 작업 실행을 허용하는 boot gate가 닫혀 있으면 해당 작업은 바로 반환합니다. Recovery가 끝난 뒤 gate가 열립니다. 종료할 때는 stop → wake → join을 마친 다음 daemon이 사용하는 자원을 해제해야 합니다. Stand-alone 빌드에는 이 네 daemon이 없습니다.

질문: Thread 목록에 page-flush가 보인다는 사실만으로 recovery 중에도 페이지를 쓸 수 있다고 말할 수 있을까요? 타이머가 한 번 끝났다면 quota도 반드시 바뀌었을까요?

예측 후 답 보기

첫 질문은 boot gate를 확인해야 답할 수 있습니다. 두 번째는 해당 작업이 quota 갱신 조건을 통과했는지 확인해야 합니다. 객체가 존재하는 것, 실행 기회를 얻는 것, 유용한 결과를 만드는 것은 서로 다릅니다.

04 · CREATE CLEAN SUPPLY

Page-flush: 기억한 후보를 다시 검사한다

화면: 이미지 제출 호출 경로 → 타이머와 frame 부족 조건 → 후보 수집과 재검사.

새 페이지를 요청한 allocator가 invalid frame도, 바로 쓸 수 있는 clean victim도 찾지 못했다고 하겠습니다. Page-flush는 cold dirty 페이지를 골라 clean 후보가 생기도록 돕습니다. 타이머가 끝날 때마다 모든 dirty 페이지를 쓰는 방식은 아닙니다. 할당을 기다리는 요청이 있는지, hit ratio가 낮은지 보고 계속할 일을 판단합니다. Boot gate를 통과한 실행에서 daemon이 wakeup으로 깨어났다고 판단하면, 후보 flush를 최소 한 번 호출합니다. 이는 소스에서 확인한 실행 조건입니다.

핵심 호출은 pgbuf_flush_victim_candidates()입니다. 먼저 LRU mutex를 잡은 상태에서 cold 후보의 BCB 포인터와 VPID를 기억합니다. 그다음 list lock을 놓고 각 BCB를 검사합니다. 그 사이 다른 thread가 실행할 수 있으므로, BCB mutex를 잡은 뒤 상태를 다시 확인해야 합니다. 같은 VPID인지, 현재 dirty인지, 이미 flushing 중인지, 여전히 cold이고 남은 fix가 없는지를 봅니다.

페이지 이미지에 필요한 WAL이 아직 영속화되지 않았다면 그 후보를 당장 제출할 수 없습니다. Log-flush를 깨우거나, frame 부족을 처리하는 경로에서 필요한 로그 작업을 마친 뒤 다시 시도합니다. 제출 가능한 이미지의 안정된 사본을 만들고 공통 flush 경로로 전달합니다. 화면의 짧은 소스 추적은 이웃 페이지 묶음과 DWB를 사용하지 않는 분기 하나를 보여줍니다. 공통 helper 안에서도 WAL 처리와 페이지 write는 정해진 순서로 진행됩니다.

예측: 후보를 수집할 때 BCB는 P를 가리켰습니다. List lock을 놓은 사이 다른 thread가 실행되어 같은 BCB가 Q를 나타내게 됐습니다. BCB 주소는 같으니 P의 flush 후보로 계속 처리해도 될까요?

예측 후 답 보기

VPID를 다시 검사할 때 이 후보를 제외해야 합니다. BCB의 저장 공간이 계속 유지되더라도 그 공간이 나타내는 페이지는 달라질 수 있습니다. 포인터를 기억하는 것과 현재 페이지의 identity를 확인하는 것은 서로 다른 작업입니다.

이미지 제출에 성공한 뒤에는 BCB의 완료 처리가 남습니다. 같은 thread가 처리할 수도 있고, post-flush에 넘길 수도 있습니다. 다음으로 그 선택 조건을 보겠습니다.

05 · COMPLETE AND REVALIDATE

Post-flush: 완료 처리와 frame 배정은 다르다

화면: queue로 완료 처리 넘기기 → 소비자 호출 경로 → 현재 상태 검사 → 다시 dirty가 된 BCB.

Queue에 들어가는 것은 PGBUF_BCB *입니다. 페이지 내용도, 이 frame을 안전하게 재사용할 수 있다는 보증도 아닙니다. 완료 처리를 넘기려면 네 조건이 모두 맞아야 합니다. 이미지를 제출한 주체가 page-flush thread여야 하고, post-flush daemon이 있어야 합니다. Direct victim을 기다리는 allocator가 있어야 하며, 용량이 제한된 queue에 포인터를 넣는 데도 성공해야 합니다. 그렇지 않으면 이미지를 제출한 thread가 BCB를 다시 잠그고 완료 처리를 합니다.

Post-flush는 queue의 소비자입니다. 포인터를 꺼내 BCB mutex를 잡고, 현재 상태를 검사합니다. DIRTY를 포함해 후보 자격을 막는 flag가 있는지, fix가 남아 있는지, LRU3에 있는지, private list라면 quota를 초과했는지를 봅니다. 조건이 맞고 아직 할당을 기다리는 요청이 있다면 direct victim을 배정하고 깨울 수 있습니다. 그 사이 reader나 writer가 다시 fix했거나 페이지가 dirty 상태가 됐다면 배정을 거절합니다.

배정을 거절하더라도 G의 완료 처리는 해야 합니다. G의 FLUSHING 상태를 해제하고, 해당 flush를 기다리는 thread를 깨워야 합니다. 반면 새 frame을 기다리는 allocator는 재사용 가능한 frame의 배정을 기다립니다. 이 두 대기를 섞으면 “flush는 끝났는데 allocator는 왜 아직 기다리지?”라는 질문의 원인을 놓치게 됩니다.

새 실행 순서: G 제출 성공 → BCB 포인터를 queue에 넣음 → reader A가 P를 READ fix하고 계속 사용 → post-flush가 포인터를 꺼냄. 여기서 마쳐야 할 일과 보류해야 할 일은 각각 무엇일까요?

예측 후 답 보기

G의 완료 상태를 정리하고 flush를 기다리는 thread를 깨우는 일은 진행합니다. 현재 A의 fix가 P의 frame을 보호하므로 allocator에게 재사용할 frame으로 배정하지 않습니다. Queue에 포인터를 넣었을 때의 상태가 아니라, 지금의 보호 상태를 기준으로 판단합니다.

Reader가 나중에 unfix하더라도 이 queue를 통해 자동으로 배정되는 것은 아닙니다. 일반적인 LRU3의 마지막 unfix에서는 승격이나 이동이 일어날 수 있습니다. Clean 페이지의 unfix에서 직접 배정하는 것은 별도의 조건을 가진 경로입니다. Direct victim을 제안받은 allocator도 실제 사용 전에 다시 검사합니다.

여기서 쉬어도 좋습니다. 다시 시작할 때 참가자에게 “사본 제출, BCB 완료, frame 배정”의 세 경계를 설명해 달라고 합니다.

근거: 완료 처리 인계 조건 · 소비자의 검사와 완료 처리 · clean unfix의 공급 경로.

06 · POLICY ADAPTATION

Maintenance: 100 ms 시도와 quota 갱신

화면: 정책 호출 경로 → quota와 구역 → 소스에서 확인되는 한계.

앞선 세션의 private/shared LRU를, 활동에 따라 조정되는 정책으로 살펴보겠습니다. 처음 정한 quota가 계속 적절할까요? Maintenance는 최근 unfix 활동과 LRU hit 샘플을 읽고, 각 private list의 quota와 private/shared 비율, 구역별 임계값을 조정합니다. 새 임계값을 넘는 보호 구역에서는 demotion이 필요할 수 있습니다. 이것이 maintenance가 맡은 정책 작업입니다.

100 ms는 작업을 시도하는 목표 주기입니다. pgbuf_adjust_quotas()는 quota 기능이 꺼져 있거나 다른 조정이 진행 중이면 반환할 수 있습니다. 시간 간격이 너무 짧거나, 활동량이 낮고 아직 충분한 시간이 지나지 않은 경우에도 반환할 수 있습니다. 이런 조건을 통과한 갱신에서만 샘플과 quota를 처리하고, 갱신 회차를 나타내는 epoch를 진행시킵니다. Thread가 실행됐다고 해서 quota도 바뀌었다고 볼 수는 없습니다.

소스를 읽을 때 주의할 예외도 있습니다. Maintenance의 direct-victim 보조 경로는 주석에 목적이 적혀 있습니다. 하지만 이 기준 리비전에서는 시작 index와 비교 조건 때문에 두 반복문의 본문에 진입하지 않습니다. 이 소스상의 이상 징후는 불확실성 목록의 VS-20에서 추적합니다. Quota 조정은 이 문제와 별개로 봐야 합니다. 다른 공급 경로를 함께 확인하지 않고 전체 allocator의 진행이 멈춘다고 결론 내릴 수도 없습니다.

질문: 100 ms가 지났고 daemon 작업이 호출됐습니다. Quota가 그대로라면 어떤 조건부터 확인할까요? 보조 경로의 주석만 보고 “대기 중인 요청을 반드시 진행시킨다”고 설명해도 될까요?

예측 후 답 보기

Quota 조정 기능이 켜져 있는지, 다른 조정이 진행 중인지, 경과 시간과 활동량 조건을 통과했는지 확인합니다. 보조 경로는 실제 반복문의 조건과 불확실성 목록의 증거 수준을 확인해야 합니다. 한 번의 실행에서 갱신이 없었다는 관찰만으로 고장이라고 판단할 수는 없습니다.

근거: quota 갱신을 허용하는 조건 · 불확실성 목록의 VS-20 / VS-21.

07 · POST-WRITE PACING

Flush-control: write 이후의 속도를 조절한다

화면: token 예산 갱신 경로 → write 후 token 소비 → 속도 조절의 한계 → 별도의 작업 주체.

Flush-control이라는 이름만 보면 다른 flusher에게 언제 어떤 페이지를 쓸지 지시하는 역할로 생각하기 쉽습니다. 실제로 갱신하는 것은 file_io.c의 공유 token 예산입니다. Writer는 OS write에 성공한 다음 compensation 경로에서 token을 소비하거나 기다립니다. 이 대기를 통해 이후 작업의 속도를 조절합니다.

50 ms 목표 주기로 새 token 예산을 계산하고 기존 값을 교체한 뒤 writer를 깨웁니다. Token이 있다고 해서 페이지를 안전하게 쓸 조건까지 확보된 것은 아닙니다. WAL 순서와 BCB 보호는 각 write 경로가 지켜야 합니다. 로그 critical section을 보유한 caller는 token이 부족해도 일반 caller처럼 기다리지 않습니다. 일반 token 대기에도 반복 횟수 제한이 있습니다. 따라서 이 예산이 I/O 양의 엄격한 상한을 보장하지는 않습니다.

예측: Writer가 OS write에 성공한 뒤 token을 기다립니다. “Token이 없으니 페이지 write가 아직 시작되지 않았다”는 해석은 맞을까요? 이 대기는 어느 단계의 진행을 늦출까요?

예측 후 답 보기

이 경로의 OS write는 이미 성공했습니다. 대기는 caller가 그 이후 경로를 거쳐 다음 작업으로 진행하는 속도를 늦춥니다. OS write 성공만으로 fsync나 모든 영속화 단계까지 완료됐다고 말할 수는 없습니다.

Log-flush는 로그를, checkpoint는 checkpoint 경계의 작업을, DWB daemon은 DWB가 이미지를 받은 뒤의 write 경로를 맡습니다. 이들은 페이지 버퍼의 네 daemon과 별도로 봐야 합니다. 여러 caller가 같은 write helper에 도달할 수 있습니다. Dirty 상태를 만든 caller가 항상 page-flush의 queue에 작업을 넣는 구조는 아닙니다.

여기까지 네 가지 결과를 구분했습니다. 이미지 제출, BCB 완료와 배정, quota 조정, writer의 속도 조절입니다. 이제 PostgreSQL에서도 누가 이 역할을 맡는지 살펴보겠습니다.

근거: write 이후의 호출 · token 소비, 대기, 갱신.

08 · TRANSFER THE MODEL

PostgreSQL: pin과 credit을 먼저 나눈다

화면: descriptor 모델 → credit이 변하는 경우. 여기서 InnoDB 절로 이어가지 않고 다음 clock 화면 안내로 이동합니다.

PostgreSQL에도 메모리의 페이지 바이트와 이를 관리하는 descriptor가 있습니다. 여기서는 backend라는 실행 주체가 페이지를 pin합니다. Pin은 해당 frame을 다른 페이지 identity로 재사용하지 못하게 막습니다. 바이트를 읽거나 바꾸기 위한 content 보호는 별도로 얻어야 합니다. CUBRID의 fix와 latch에서 배운 책임 구분은 가져올 수 있지만, 두 엔진의 호출 인터페이스가 같다는 뜻은 아닙니다.

교체 정책에 사용할 기억도 따로 있습니다. PostgreSQL의 usage_count는 재사용 이력을 제한된 수치로 기억하는 credit입니다. 현재 pin을 나타내는 refcount와는 다른 값입니다. 접근 시각이나 LRU 위치도 아닙니다. 이 기준 리비전에서는 최대 5까지 올라갑니다.

기본 strategy에서 해당 backend가 아직 pin하지 않은 페이지를 pin하면 공유 refcount를 올립니다. Usage credit도 상한인 5에 도달하지 않았다면 올립니다. 같은 backend가 이미 pin한 페이지를 중첩해서 pin하면 backend 내부의 private refcount만 늘립니다. 따라서 중첩 호출 횟수가 그대로 공유 credit에 더해지지는 않습니다. Ring strategy의 pin은 credit이 0일 때 1로 올릴 수 있지만, 이미 높은 credit을 더 올리지는 않습니다.

질문: usage_count가 0인데 다른 backend가 pin하고 있습니다. “credit이 없으니 바로 victim으로 고르면 된다”는 추론에서 빠진 조건은 무엇일까요?

예측 후 답 보기

현재 pin이 없어야 합니다. Credit은 페이지를 얼마나 더 유지할지 판단하는 정책 값이고, pin은 현재 사용을 보호합니다. 같은 descriptor에 함께 기록돼 있어도 맡은 역할은 다릅니다.

근거: PinBuffer · 최대 credit.

09 · CLOCK TRACE

Clock sweep: hand가 무엇을 바꾸는가?

화면: clock 구성 사례 → 소스의 동작 원리. 다음 새 예측은 이 대본의 표로 진행합니다.

PostgreSQL의 기본 교체 경로에서는 clock hand가 공유 descriptor 배열을 따라 전진합니다. Pin 중인 descriptor는 건너뜁니다. Pin이 없고 credit이 양수라면 하나를 줄인 뒤 다음 descriptor로 갑니다. Pin이 없고 credit도 0이라면 CAS로 자신의 pin을 얻어 후보를 반환합니다. 여기까지 끝난 것은 descriptor 선택입니다. Dirty 이미지의 write나 기존 identity 제거는 이후 caller가 처리합니다.

이제 이전 화면과 독립된 새 모델로 예측해 보겠습니다. Descriptor 네 개만 두고 한 실행 주체가 순서대로 처리하는 설명용 모델입니다. 실제 PostgreSQL의 pool 설정이나 실행 캡처가 아닙니다. Hand는 F0에서 시작하고, 방문 순서는 F0 → F1 → F2 → F3입니다. 표의 refcount는 이 allocator가 선택하기 전에 다른 backend가 보유한 공유 pin 수입니다. 동시 변경은 없고 모두 clean 상태라고 가정합니다.

DescriptorIdentityRefcountUsage credit
F0H102
F1S110
F2S201
F3S300

예측: 처음 반환하는 descriptor는 무엇일까요? 각 방문 후 credit과, 선택된 descriptor의 refcount를 적어 보세요. F2의 credit을 0으로 줄인 그 방문에서 곧바로 F2를 선택할까요?

예측 후 순서 보기
  1. F0: credit을 2 → 1로 줄이고 다음으로 이동합니다.
  2. F1: pin 중이므로 건너뜁니다. Credit은 0으로 유지됩니다.
  3. F2: credit을 1 → 0으로 줄이고 다음으로 이동합니다. 이 방문에서는 선택하지 않습니다.
  4. F3: credit이 0이고 pin이 없습니다. CAS로 자신의 pin을 얻어 refcount를 1로 바꾸고 반환합니다. 새 페이지 identity의 내용을 읽었다는 뜻은 아닙니다.

시작 상태를 바꿔 다시 예측: 표의 시작 상태에서 F3의 초기 credit만 1로 바꿉니다. 나머지 조건은 같습니다. 처음 반환하는 descriptor를 다시 구해 보세요.

다시 예측 후 답 보기

첫 순회에서 F0의 credit은 1, F2와 F3의 credit은 0이 됩니다. 다음 순회에서 F0를 1 → 0으로 줄이고 F1을 건너뛴 뒤, F2를 pin하고 반환합니다. 첫 사례를 수행한 뒤의 상태를 이어받지 않습니다.

이 모델은 exact LRU처럼 전체 접근 순서를 유지하지 않습니다. 어떤 페이지를 더 최근에 읽었는지 모두 정렬하는 대신, 제한된 credit을 기억합니다. 메타데이터 갱신과 후보 선택에 드는 작업은 비교할 수 있습니다. 다만 이 추적만으로 처리량의 우위를 판단할 수는 없습니다.

근거: StrategyGetBuffer.

10 · WORKLOAD STRATEGIES

Ring: 공유 frame의 ID를 작업별로 기억한다

화면: access-strategy ring. 소스의 factory 크기 계산은 질문이 있을 때 펼칩니다.

H1, H2를 반복해서 읽는 동안 긴 scan이 S1, S2, S3를 한 번씩 읽는다고 하겠습니다. Scan의 모든 miss를 전역 교체 경로에 맡기면 반복 사용하는 페이지도 교체 압력을 받을 수 있습니다. PostgreSQL은 이런 대량 작업에 buffer access strategy를 전달할 수 있습니다.

Ring은 backend 내부에 두는 작은 배열이며, 공유 buffer의 ID를 저장합니다. 다음 slot이 가리키는 frame에 pin이 없고 credit이 0 또는 1이면 재사용을 시도합니다. Slot이 비어 있거나 그 frame을 사용할 수 없다면 전역 clock에서 후보를 고르고, 선택한 buffer의 ID로 slot을 채웁니다. Ring 객체는 backend에 속하지만, 참조하는 frame은 다른 backend도 사용할 수 있습니다.

Strategy이번 세션에서 기억할 점
BAS_NORMAL기본 clock 경로. 별도의 ring 객체를 만들지 않음.
BAS_BULKREAD대량 읽기에 사용할 buffer를 재사용함. Ring에서 고른 후보가 dirty 상태인 permanent 페이지이고, 이를 쓰기 위해 WAL flush가 필요하면 ring에서 제외하고 다른 후보를 구할 수 있음.
BAS_BULKWRITE대량 쓰기에 사용할 buffer를 재사용함. Bulk-read와 동일한 dirty/WAL 후보 거절 정책을 적용하지 않음.
BAS_VACUUMVacuum 작업에 사용할 buffer를 재사용함. 필요한 dirty 페이지 write와 WAL 처리를 수행할 수 있음.

Factory 수치는 기준 리비전과 호출 경로에 따라 읽어야 합니다. 이 소스의 bulk-read 기본 크기는 256 KiB를 바탕으로 AIO에 필요한 여유분을 반영하고 pin 한도를 고려합니다. Bulk-write factory는 16 MiB, vacuum factory는 2 MiB입니다. 공통 크기 처리 경로에서는 공유 buffer 수의 1/8을 상한으로 둡니다. 실제 caller가 지정하는 크기도 확인해야 합니다. 아래의 두 slot은 설명용 모델입니다.

새 ring 실행 순서: slot 0은 F4를, slot 1은 F5를 가리킵니다. 다음 방문은 slot 0입니다. F4는 clean, refcount 0, credit 1입니다. F5는 clean, refcount 0, credit 2입니다. 동시 변경 없이 두 miss를 차례로 처리하고, 첫 번째 pin은 다음 miss 전에 반납합니다. 두 번째 miss에서는 전역 clock으로 넘어가 clean 상태이며 credit이 0인 F6을 선택한다고 가정합니다. 두 slot은 어떻게 바뀔까요?

예측 후 답 보기

첫 miss에서는 F4를 pin해 재사용할 수 있으므로 slot 0의 ID는 F4로 유지됩니다. 두 번째 miss에서는 F5의 credit이 2라서 ring에서 재사용하지 않고 전역 경로로 넘어갑니다. 선택한 F6의 ID를 slot 1에 기록합니다. F5는 공유 pool에 남아 있고 ring slot의 참조만 바뀝니다. 이 모델에서도 페이지 identity를 교체하려면 선택 이후에 필요한 보호 절차를 거쳐야 합니다.

CUBRID의 private LRU와 PostgreSQL의 ring은 모두 대량 작업이 주는 교체 압력과 관련이 있지만, 구조는 다릅니다. CUBRID의 private LRU는 pool이 관리하는 BCB의 정책 영역이며 quota를 가집니다. PostgreSQL의 ring은 backend 내부에 둔 공유 buffer ID의 참조 배열입니다. 둘 다 private이라는 말로 독립된 pool처럼 설명하면 실제 소유 관계를 놓치게 됩니다.

근거: strategy factory · ring 재사용과 slot 교체 · bulk-read의 후보 거절.

11 · WRITEBACK OWNERS

Clock이 dirty 페이지를 골랐다면 누가 쓰는가?

화면: dirty 페이지의 처리와 진행 → PostgreSQL과 CUBRID의 설계 선택. Write를 맡는 주체의 자세한 구분은 아래 표와 기준 소스에서 확인합니다.

Clock은 dirty라는 이유만으로 descriptor를 제외하지 않습니다. Pin이 없고 credit이 0인 후보를 자신의 pin으로 확보한 뒤, 할당을 요청한 backend가 dirty 페이지를 쓸 수 있습니다. 이때 대기 없이 content lock 획득을 시도하고, 필요한 WAL을 먼저 보존한 다음 페이지를 씁니다. Lock을 얻지 못하거나 다른 사용 때문에 기존 identity를 제거할 수 없다면 후보를 놓고 다시 시도합니다.

선택 당시 다른 pin이 없었다고 해서 이후에도 자기 혼자 사용한다는 보장은 없습니다. 다른 backend가 pin하거나 다시 dirty 상태로 만들 수 있습니다. InvalidateVictimBuffer()는 mapping과 header를 보호한 상태에서, 현재 refcount가 자기 pin 하나뿐이고 dirty가 아닌지 확인합니다.

주체목적따라볼 경로
할당을 요청한 backend자신의 miss를 진행하기 위해 dirty victim을 처리GetVictimBuffer가 dirty 분기에서 FlushBuffer를 호출한 뒤 InvalidateVictimBuffer를 호출
Background writer향후 할당에 쓸 clean 후보를 미리 확보BgBufferSync → SyncOneBuffer, 현재 pin과 credit 조건을 고려
CheckpointerCheckpoint 경계에 필요한 dirty 페이지 처리와 저장 작업BufferSync와 checkpoint 처리. Cold 상태이고 credit이 0인 victim만을 고르는 작업은 아님.

Background writer가 있어도 요청을 처리하는 backend의 write가 사라지지는 않습니다. Checkpointer는 교체 후보만 처리하는 worker도 아닙니다. 앞서 CUBRID의 page-flush, log-flush, checkpoint, DWB를 구분했듯이 PostgreSQL에서도 각 주체의 목적과 완료 경계를 보면 역할을 이해할 수 있습니다.

예측: Backend A가 dirty victim을 flush했습니다. 기존 identity를 제거하기 직전에 B가 같은 페이지를 pin했습니다. A가 이미 썼으니 frame을 다른 페이지로 바꿔도 될까요?

예측 후 답 보기

현재 공유 refcount가 A의 pin 하나보다 많으므로 identity 제거를 거절하고 다시 선택해야 합니다. Write가 끝났더라도 현재 사용 중인 B의 pin은 남아 있습니다. B가 다시 dirty 상태로 만들었다면 현재 dirty 검사에서도 재사용을 거절합니다.

설계를 비교할 때는 조건도 함께 봐야 합니다. CUBRID는 LRU의 정책 영역과 zone, quota로 페이지 유지와 교체 압력을 다룹니다. PostgreSQL은 제한된 credit과 clock, 작업별 ring을 사용합니다. CUBRID에서는 list와 quota 처리 비용을, PostgreSQL에서는 sweep과 credit·pin 상태 처리 비용을 살펴볼 수 있습니다. 결과는 hot set과 scan, dirty 생성률, pin을 유지하는 시간, 저장장치에 따라 달라질 수 있습니다. 소스에서 확인한 구조만으로 성능 순위를 정할 수는 없습니다.

근거: 요청 backend의 write · identity 제거 전 재검사 · 백그라운드의 clean 후보 준비 · checkpoint의 선택 기준.

12 · FINAL WORKSHOP

새 실행 순서에 적용하고, 페이지 버퍼 세미나를 마친다

화면: 먼저 이 절의 두 새 질문을 사용합니다. 답을 논의한 뒤 한 페이지의 전체 여정을 열어 마무리합니다.

이제 배운 역할과 조건을 새로운 실행 순서에 적용해 보겠습니다. 각 사례에서 시작 상태, 사건 하나, 그 이후 상태를 적어 주세요. 이어서 전이를 결정하는 조건과 다음에 확인할 증거를 적어 주세요. 필요한 소스는 참고해도 좋습니다. 예시 답은 먼저 열지 않습니다.

사례 A · Flush 횟수는 늘었는데 allocator가 기다린다

CUBRID pool에 invalid frame이 없습니다. Allocator B는 direct victim을 기다립니다. Cold dirty 페이지 P의 G 제출에 성공했고, post-flush queue 삽입에도 성공했습니다. 소비자가 실행되기 전에 writer A가 P를 fix하고 G+1의 변경을 만들었습니다. A는 아직 fix를 반납하지 않았습니다. 이후 소비자가 실행되어 해당 BCB를 꺼냈습니다.

왜 이 사건만으로 B를 바로 진행시킬 수 없을까요? G의 어떤 처리는 마쳐야 할까요? “Post-flush가 실행되지 않았다”와 “실행했지만 배정을 거절했다”를 구분하려면 무엇을 관찰할까요?

논의 후 예시 답 보기

A의 현재 fix와 새 DIRTY가 재사용을 막습니다. G의 FLUSHING 상태를 해제하고 flush를 기다리는 thread는 깨웁니다. 하지만 G+1의 dirty 상태와 현재 fix의 보호는 유지해야 합니다. 소비자의 실행과 queue 소비, BCB의 flag와 fix 상태, 현재 zone과 quota, direct-victim 대기 요청과 배정 여부를 시간 순서대로 봅니다. Flush 횟수 증가만으로 queue 소비나 배정 성공을 판단할 수는 없습니다. 이 사례는 특정 버그나 starvation을 실제 실행에서 입증한 기록이 아닙니다.

사례 B · Ring이 있어도 scan이 전역 clock으로 간다

PostgreSQL bulk-read strategy의 다음 ring slot은 dirty 상태인 permanent 페이지 R을 가리킵니다. 여기서 permanent는 BM_PERMANENT로 구분하는 페이지 범주입니다. R을 처음 선택할 때 pin은 없었고 credit은 1이었습니다. 대기 없이 content lock을 얻는 데도 성공했습니다. 아직 R의 페이지 LSN까지 WAL flush가 필요합니다. 같은 시점에 별도의 hot 페이지 H는 다른 backend가 pin하고 있습니다.

R과 ring slot은 어떻게 처리할 수 있을까요? 전역 경로로 넘어갈 수 있다는 사실이 H의 pin 보호를 없앨까요? 후보 거절과 pin 보호의 조건을 소스에서 각각 어디서 확인할까요?

논의 후 예시 답 보기

이 조건에서는 BAS_BULKREAD의 ring 후보를 거절할 수 있습니다. StrategyRejectBuffer가 slot을 InvalidBuffer로 비우면, caller는 pin과 lock을 반납하고 다른 후보를 구합니다. 이 거절만으로 메모리에 있는 R의 identity를 제거하지는 않습니다. 전역 clock도 pin 중인 H는 건너뜁니다. GetVictimBuffer의 permanent/from_ring/WAL 조건과 StrategyRejectBuffer의 bulk-read 조건을 함께 읽고, pin 보호는 StrategyGetBuffer의 refcount 검사에서 확인합니다. Ring에서 전역 경로로 넘어가더라도 pin으로 보호된 hot frame을 덮어쓸 수는 없습니다.

마지막 연결 질문

한 페이지를 요청한 순간부터 같은 frame을 다른 페이지 identity로 재사용할 때까지의 여정을 설명해 보겠습니다. 먼저 identity를 찾고, 메모리에 페이지를 담을 공간을 마련합니다. 사용을 보호할 fix나 pin을 얻고, 바이트 접근에 필요한 보호도 얻습니다. 페이지를 변경한 caller는 필요한 로그를 남기고 dirty 상태를 기록합니다. 사용을 반납한 뒤에도 페이지는 메모리에 남을 수 있고, dirty 상태도 별도로 남습니다. 이후 정책이나 caller에 따라 이미지 전달을 시작하고 완료 상태를 정리합니다. 마지막으로 현재의 보호 상태와 재사용 조건을 다시 확인한 뒤 identity를 바꿉니다.

Daemon이나 정책의 이름이 바뀌어도 확인할 질문은 같습니다. 지금 어느 페이지를 나타내고 있을까요? 누가 사용하고 있을까요? 어느 시점의 이미지가 보존됐을까요? 다음 단계를 진행할 책임은 누구에게 있고, 어떤 조건을 통과해야 할까요? CUBRID와 PostgreSQL의 차이는 이 질문에 답하는 구체적인 상태와 경로에서 찾을 수 있습니다.

이것으로 세 번의 페이지 버퍼 세미나를 마치겠습니다. 앞으로 실제 변경이나 장애를 만날 때는 오늘 살펴본 상태의 소유자와 전이 조건을 기준으로 소스를 찾아가면 됩니다. 모든 세부사항을 한 번에 외우기보다, 근거를 찾아 자신의 설명을 검증하는 방법을 가져가시면 좋겠습니다.
