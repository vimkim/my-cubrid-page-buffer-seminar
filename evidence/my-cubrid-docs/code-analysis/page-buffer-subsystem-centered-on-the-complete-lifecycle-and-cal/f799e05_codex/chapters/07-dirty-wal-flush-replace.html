07. Dirty는 durable이 아니다

학습 목표와 concrete scenario

dirty generation, WAL-before-data, checkpoint/recovery와 replacement eligibility/policy를 설명한다.

질문: flush가 snapshot을 쓴 동안 writer가 같은 BCB를 다시 dirty하게 만들면 completion이 무엇을 지워야 하는가?

직관: 한 page journey를 identity, ownership, concurrency, durability, release 순서로 따라가며 각 abstraction을 exact state와 guard로 교체한다.

세 durability moment

  1. Memory: WRITE holder가 bytes와 page LSA를 바꾸고 dirty/oldest-unflush-LSA를 세운다.
  2. Log: flusher가 stable page copy의 LSA를 읽어 logpb_flush_log_for_wal()로 log를 먼저 force한다.
  3. Data: TDE/DWB 또는 direct file write가 page image를 제출하고 completion한다.

flush start는 FLUSHING을 set하면서 이전 dirty를 clear한다. 그래서 I/O 중 writer가 resident BCB를 다시 dirty로 만들 수 있다. old snapshot write success와 current BCB DIRTY가 동시에 참인 것은 lost update가 아니라 generation separation이다. ordinary I/O error는 pre-flush dirty와 oldest LSA를 복원한다.

10000-row update는 generation 1과 length violation 0, dirty calls 58430를 만들었고 owned backupdb -C -r가 성공했다. rebind-exp4의 per-session log append/WAL/data-page iowrite counter는 0이었으므로 individual WAL ordering 또는 physical victim을 runtime에서 보았다고 말하지 않는다.

allocation은 invalid list, private/shared victim, direct-victim pressure 순으로 진전한다. 모든 candidate가 fixed/dirty이면 flush daemon을 깨우고 wait하거나 ER_PB_ALL_BUFFERS_DIRTY로 실패한다. clean eviction에는 바로 앞 data write가 필요하지 않다.

Failure audit. TDE encrypt 및 DWB-slot error가 FLUSHING/old DIRTY 설정 뒤 common rollback 전에 return하는 경로는 defect candidate다. reachability test와 callee side-effect audit가 끝나기 전 guarantee로 승격하지 않는다.

이 장의 요약과 다음 전환

Memory, log, data durability와 victim eligibility를 분리했다. 다음 장에서는 source mechanism을 runtime counter로 어디까지 관찰했는지 검증한다.
