05. Latch, holder, wait와 pgbuf_unfix()

학습 목표와 concrete scenario

protected state, latch matrix, nested holder, wait/wakeup과 unfix의 happens-before를 설명한다.

질문: BCB fcnt=3이고 현재 thread holder fix_count=2일 때 한 번과 마지막 unfix는 무엇이 다른가?

직관: 한 page journey를 identity, ownership, concurrency, durability, release 순서로 따라가며 각 abstraction을 exact state와 guard로 교체한다.

Mode와 condition은 다른 축이다

CUBRID grant matrix
Existing Request Conditional Unconditional
idle READ/WRITE grant, fcnt=1, holder 생성
READ/no waiter READ share; nested holder 가능
READ + others WRITE promotion fail own reads drop, front queue, later restore
incompatible READ/WRITE immediate NULL/error timed queue; timeout/interrupt 가능

waiter_exists가 있으면 새 reader barging을 막지만 existing holder reentry는 허용한다. 이는 starvation과 nested-operation liveness 사이의 policy다. page-latch timeout은 transaction-lock deadlock proof가 아니다.

Rare allocation failure — CUBRID-C012. Lock-free READ뿐 아니라 normal idle, compatible new-holder와 blocked-request grant도 latch/fcnt를 먼저 commit한 뒤 holder를 할당한다. Allocation failure는 assert 후 NULL/ER_FAILED를 반환하지만 committed latch/fcnt를 backout하지 않는다. Hardened 재구현은 holder reserve-first 또는 explicit latch/fcnt rollback을 사용한다.

pgbuf_unfix()가 실제로 하는 일

  1. PAGE_PTR→BCB를 찾고 current-thread holder를 검사한다.
  2. holder의 nested fix_count를 낮추거나 제거한다.
  3. shared READ/no-waiter fast path면 atomic fcnt만 낮춘다.
  4. full path의 마지막 fcnt면 NO_LATCH로 전환한다.
  5. VOID를 LRU에 넣거나 zone을 boost하고, waiter를 깨우며 deferred flush를 처리한다.

unfix ≠ flush ≠ commit ≠ eviction. unfix는 borrowed lifetime을 끝낸다. dirty, flushing, waiter, direct-victim flag, LRU zone 조건이 남으면 victim이 아니다.

Empty read는 promotion 0이었다. 10000-row insert는 promotion success 689, dirty calls 102125, heap/B-tree HOLDER_DIRTY WRITE/MIXED unfix를 만들었다. 이는 holder metadata의 runtime signature이지 실제 contention schedule의 증거가 아니다.
발표자 노트. “BCB fcnt=3, 내 holder fix_count=2”를 주고 한 번 unfix와 마지막 unfix의 차이를 청중에게 계산시킨다.
