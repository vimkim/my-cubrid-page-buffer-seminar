1. 버퍼 풀은 왜 존재하는가 — 도서관과 책상의 물리학

🎨 비유 당신은 거대한 도서관(디스크)에서 일하는 연구원이다. 서고에서 책 한 권을 가져오는 데는 몇 분이 걸리지만, 일단 책상(메모리) 위에 올려 둔 책은 몇 초 만에 펼칠 수 있다. 책상은 좁아서 몇십 권밖에 못 올린다. 그렇다면 전략은 자명하다 — 자주 보는 책은 책상에 두고, 안 보는 책부터 서고로 돌려보낸다. 버퍼 풀은 정확히 이 책상이고, page buffer 코드는 이 책상을 관리하는 사서다.

수치로 보면 이 비유는 과장이 아니다. DRAM 접근은 ~100ns, NVMe SSD 랜덤 읽기는 ~100μs(1,000배), HDD라면 ~10ms(100,000배)다. 디스크를 한 번 읽을 시간에 메모리는 수천~수만 번 읽는다. 그래서 모든 디스크 기반 DBMS는 예외 없이 "디스크의 데이터를 메모리에 캐시하고, 가능한 한 메모리에서만 논다"는 구조를 갖는다.

이때 캐시의 단위가 중요하다. 버퍼 풀이 캐시하는 것은 "쿼리 결과"도 "행(row)"도 아닌 페이지(page) — 디스크 파일을 일정 크기(CUBRID 16KB, PostgreSQL 8KB, InnoDB 16KB)로 자른 블록이다. 한 페이지에는 보통 수십~수백 개의 행이 들어 있다. 디스크와의 모든 입출력은 페이지 단위로 일어난다.

2.2 왜 그냥 OS 페이지 캐시를 쓰지 않나?

OS도 파일 캐시를 갖고 있다. 그런데 왜 DBMS는 굳이 자체 버퍼 풀을 만들까? (1) 쓰기 순서 제어 — WAL 규칙(7장)처럼 "로그가 먼저, 데이터가 나중" 순서를 OS 캐시는 보장해 주지 않는다. (2) 교체 정책 제어 — DBMS는 "이건 인덱스 루트라 계속 쓴다", "이건 풀스캔이라 한 번 보고 만다"를 알지만 OS는 모른다. (3) fix/latch 같은 동시성 규약은 페이지가 항상 같은 주소에 고정되어 있어야 성립한다. 그래서 세 엔진 모두 direct I/O 또는 자체 버퍼 풀 + OS 캐시 조합으로 스스로 관리한다.

3. CUBRID 해부학 ①: pgbuf_Pool의 구조물들

🎨 비유 책상(버퍼 풀)을 자세히 보자. 책마다 대출 카드(BCB)가 붙어 있어 "누가 보는 중인지, 낙서(수정)했는지"를 기록한다. 책 제목으로 카드를 바로 찾는 카드 색인함(hash table)이 있고, 책상 위 책들은 인기순으로 여러 줄(LRU 리스트)로 정렬되어 있다. 빈 자리 목록(invalid list)과, 사서 보조 알바 4명(daemon)도 있다.

CUBRID의 버퍼 풀 전체는 단 하나의 전역 구조체 pgbuf_Pool에 담긴다 (PGBUF_BUFFER_POOL, page_buffer.c:755-832; 인스턴스는 :845). 주요 구성물:

3.1 BCB — 페이지마다 붙는 대출 카드

프레임(16KB 실물)과 1:1로 짝지어진 관리 구조체가 PGBUF_BCB다 (page_buffer.c:511-543). 배열 인덱스가 같으므로 BCB↔프레임 변환은 조회가 아니라 포인터 산술이다 (CAST_PGPTR_TO_BFPTR, :148-169). 카드에 적히는 것들:

  • vpid — 어느 볼륨의 몇 번 페이지인가 (Volume + Page ID).
  • atomic_latch — 이 트리의 백미. latch_mode(16b) + waiter_exists(16b) + fcnt(32b)를 한 개의 64-bit atomic에 패킹했다 (:499-508). 거의 모든 전이가 CAS 루프라서, 읽기 fix/unfix는 mutex 없이 처리된다(4.3절). ※ 로컬 커밋(CBRD-26941 등)의 설계 — stock 11.5는 셋이 분리된 필드다.
  • flags — 32-bit int 하나에 플래그 7개 + zone(4종) + 소속 LRU 리스트 번호(16b)를 전부 패킹 (:224-241, :178-216). dirty, flushing-to-disk, victim-direct 등이 여기 산다. 부팅 때 마스크가 안 겹치는지 검사하고 겹치면 abort()한다 (:16777-16798).
  • oldest_unflush_lsa — 이 페이지가 dirty가 된 후 첫 수정의 로그 위치. checkpoint가 "어디까지의 수정이 아직 디스크에 없나"를 계산하는 근거다(7장).
  • count_fix_and_avoid_dealloc — int 하나에 카운터 2개: 상위 16b는 fix 누적 횟수(64에서 포화 — "hot 페이지" 판정용), 하위 16b는 "vacuum아, 이 페이지 지우지 마" 참조 수 (:267-269, :533-538).

3.2 해시 테이블 — 항상 1,048,576 버킷

VPID로 BCB를 찾는 해시는 풀 크기와 무관하게 항상 220 = 1M 버킷이고, 버킷마다 pthread mutex가 하나씩 있다 (HASH_SIZE_BITS 20, page_buffer.c:295-296; :5631-5642). 버킷 구조체는 mutex + BCB 체인 + buffer lock 체인으로 구성된다 (:575-582). buffer lock 체인은 "지금 이 VPID를 디스크에서 읽는 중"이라는 팻말이다 — 같은 페이지를 두 스레드가 동시에 읽어오는 낭비를 막는다(4.2절 miss 경로).

⚠️ 알아두면 좋은 사실 1M개의 mutex는 x86-64 glibc 기준 대략 56MiB를 항상 차지한다. 16M짜리 미니 풀(퀴즈 환경)에서도 그렇다. 또한 해시 탐색 1차 시도는 버킷 mutex 없이 체인을 걷고, BCB를 잠근 뒤 VPID를 재검증한다 (pgbuf_search_hash_chain, :7544-7667) — 락 비용을 아끼는 낙관적 패턴.

3.3 프레임 — 페이지 실물과 머리/꼬리 도장

프레임에 담기는 FILEIO_PAGE는 3부분이다 (file_io.h:186-193): 머리의 시스템 영역 prv(마지막 수정 LSA, pageid, volid, 페이지 타입 등), 사용자 데이터 영역, 그리고 페이지 맨 끝의 prv2 — prv.lsa의 복사본이다. 머리와 꼬리의 LSA가 다르면 그 페이지는 쓰다가 만 것(torn page)이다. CUBRID에는 페이지 checksum이 없고, 이 머리/꼬리 LSA 워터마크가 유일한 torn 감지 수단이다(8장).

4. CUBRID 해부학 ②: fix/unfix — 페이지 하나를 빌리는 일

🎨 비유 연구원이 책을 보려면: ① 색인함에서 카드를 찾고(없으면 서고에서 가져오고), ② 대출 도장을 찍고(fix), ③ "읽는 중" 또는 "수정 중" 팻말을 세우고(latch), ④ 다 보면 팻말을 내리고 도장을 지운다(unfix). 이 왕복 한 번이 Num_data_page_fetches 1이다. 쿼리 하나가 이 왕복을 수백~수만 번 한다.

모든 것의 입구는 pgbuf_fix (thread_p, &vpid, fetch_mode, latch_mode, condition) (pgbuf_fix_release, page_buffer.c:2211)이다. 인자의 의미:

  • fetch_mode — OLD_PAGE(보통), NEW_PAGE(디스크 읽기 생략 — 새로 할당한 페이지), OLD_PAGE_IF_IN_BUFFER(있을 때만) 등 (page_buffer.h:172-187).
  • latch_mode — PGBUF_LATCH_READ(공유) / PGBUF_LATCH_WRITE(배타).
  • condition — UNCONDITIONAL(잠들어서라도 기다림) / CONDITIONAL(못 잡으면 바로 포기).

4.1 HIT — 이미 책상에 있는 경우

해시에서 BCB를 찾으면 latch를 요청한다. 부여 규칙 (pgbuf_latch_bcb_upon_fix, :6246-6583):

  • READ 요청 + 현재 READ latch → waiter가 없으면 합류 허용(fcnt++). 대기 중인 WRITE가 있으면 새 READ는 줄을 선다(writer 기아 방지) — 단, 이미 이 페이지를 잡고 있는 스레드는 예외(자기-데드락 방지) (:6326-6349).
  • WRITE latch를 쥔 스레드의 재요청 → 항상 허용 (재귀 fix) (:6356-6360).
  • 충돌 → pgbuf_block_bcb로 대기 큐에 들어가 잠든다 (:6995-7114).
⚠️ 페이지 latch에는 데드락 감지기가 없다 행 락(lock)은 wait-for graph로 데드락을 찾지만, 페이지 latch는 타임아웃이 유일한 해결책이다. 소스의 자백: "We do not guarantee that there is no deadlock between page latches... the request will be waken up by timeout... treated as a victim" (:7093-7100). 기본 타임아웃은 5분(pgbuf_latch_timeout_msecs = 300,000ms, :107)이고 트랜잭션의 wait_msecs와는 무관하다 (:7250-7262). 그래서 여러 페이지를 잡을 땐 순서가 생명이다 — heap 코드가 쓰는 pgbuf_ordered_fix는 (그룹, 랭크, VPID) 순으로 정렬해서 잡고, 순서가 꼬이면 이미 잡은 페이지를 놓았다가 다시 잡는다 (:12185-13014).

4.2 MISS — 서고에서 가져오는 경우

그림 3의 오른쪽 경로다. 핵심 디테일 셋: (1) buffer lock — 같은 VPID를 읽는 두 번째 스레드는 팻말을 보고 잠들며, 깨어나면 페이지를 건네받는 게 아니라 처음부터 재시도한다(이제는 해시에서 발견됨) (:7935-8033, PGBUF_LOCK_WAITER). (2) 빈 BCB는 invalid list에서, 없으면 victim 선택(6장)으로 확보한다. (3) 디스크를 읽기 전에 반드시 DWB부터 확인한다 (:8454) — 디스크의 원위치가 구버전일 수 있기 때문(8장).

4.3 이 트리의 특기: 무잠금 읽기 fast path

READ + OLD_PAGE + UNCONDITIONAL 조합(전체 fix의 대부분)은 pgbuf_lockfree_fix_ro (:7669-7732)로 들어간다: 버킷 mutex 없이 체인을 걷고, latch_mode==READ && !waiter_exists && fcnt!=0이면 64-bit latch 워드를 CAS 한 번으로 fcnt++하고 끝. BCB mutex도, LRU 조작도 없다. unfix 쪽 짝은 pgbuf_lockfree_unfix_ro (:7751-7774)인데, fcnt != 1 조건이 묘수다 — 마지막으로 놓는 스레드만 느린 경로로 보내 LRU 정리(5장)가 반드시 실행되게 한다. (이 fast path 전체가 이 브랜치의 로컬 설계다.)

4.4 unfix — 반납의 순간이 정책의 순간

pgbuf_unfix (:3024)는 fcnt를 내리고, 0이 되는 순간에만 일이 커진다 (pgbuf_unlatch_bcb_upon_unfix, :6605-6832): LRU zone별 결정(5장), 대기자 깨우기, 비동기 flush 요청 처리. 재미있는 최적화 — 대기자가 있으면 LRU 정리를 전부 건너뛰고 페이지를 최대한 빨리 넘긴다 (:6674-6680).

5. 교체 정책: LRU zone, private/shared 리스트, quota, AOUT

🎨 비유 책상 위 책들을 한 줄로 세우면(전역 LRU) 두 가지 문제가 생긴다. ① 모두가 같은 줄을 만지느라 줄 자체가 병목이 되고, ② 한 명이 전집 1,000권을 훑기 시작하면 모두의 애독서가 밀려난다. CUBRID의 답: 줄을 여러 개로 쪼개고(리스트 샤딩), 연구원마다 개인 책꽂이(private list)를 주되 칸 수 제한(quota)을 건다. 전집을 훑는 사람은 자기 책꽂이만 넘치고, 남의 책은 안전하다.

5.1 한 리스트의 내부: 3개의 zone

각 LRU 리스트는 위에서부터 zone 1(hot) / zone 2(완충) / zone 3(victim 후보)로 나뉜다. 설계 주석 (page_buffer.c:188-196)이 의도를 명확히 말한다:

핵심 규칙 — "매번 top으로"는 순진한 교과서 LRU다. CUBRID의 boost 규칙 (pgbuf_lru_boost_bcb :10072-10137; unfix 분기 :6691-6799):

  • zone 1: 아무것도 하지 않는다. 어차피 victim이 될 수 없는데 리스트 mutex를 잡고 포인터 수술을 할 이유가 없다.
  • zone 2: 리스트에 들어온 뒤 충분히 시간이 지난 경우에만(PGBUF_IS_BCB_OLD_ENOUGH, 나이차 ≥ count_lru2/2 :1004-1009) top으로 boost. "연속 두 번 fix"로는 승격되지 않는다.
  • zone 3: 살아있다는 신호가 오면 무조건 구출(boost).

5.2 리스트는 왜 여러 개인가 — shared와 private

리스트 수 (:5693-5749, :13884-13922): shared는 기본적으로 max_clients에서 출발해 "리스트당 최소 1,000페이지" 조건으로 줄이고(최소 4개), private는 MAX_NTRANS + vacuum worker 50개를 만든다. private 리스트는 세션마다 하나씩 배정되고 (세션 생성 시 pgbuf_assign_private_lru, session.c:740), 그 세션을 처리하는 워커 스레드로 전파된다. vacuum 워커도 저마다 하나씩 갖는다.

5.3 quota — 개인 책꽂이의 칸 수 제한

private 리스트가 무한정 크면 한 세션이 풀을 독식한다. 그래서 quota가 있다 (PGBUF_PAGE_QUOTA, :716-736). 100ms마다 도는 pgbuf-maintain 데몬이 pgbuf_adjust_quotas (:14195-14447)로 재계산한다:

  • 각 리스트의 활동량(activity)을 히트 수로 측정하되, 같은 BCB는 조정 주기당 1히트만 인정한다 (:16534-16544) — 한 페이지를 백만 번 두드려도 1점. 즉 quota는 접근 빈도가 아니라 워킹셋의 넓이를 따라간다.
  • 전체 private 몫 = 풀 × (private 히트 비율), 각 리스트 몫 = 활동량 비례 배분. 상한: 5,000페이지 또는 풀의 절반 (:14384-14386).
  • quota 초과분은 zone 3으로 강등되어 victim 후보가 된다 (:14393-14400).
  • private 리스트의 zone 1/2는 quota의 5%씩으로 고정이다 (:14390-14391) — lru_hot_ratio(기본 0.4)는 shared 리스트에만 적용된다. private 리스트는 사실상 90%가 victim 지대다.

6. victim 선택과 direct victim — 프레임이 없을 때 벌어지는 일

🎨 비유 새 책을 올릴 자리가 없다. 규칙: ① 자기 책꽂이가 규정 초과면 자기 것부터 반납. ② 남의 초과분, ③ 공용 서가 순서. 그런데 반납 후보가 전부 낙서된 책(dirty)이라면? 당신은 접수대에서 번호표를 뽑고 기다리고, 사서 알바(flush daemon)가 낙서를 정서(flush)한 책을 당신 손에 직접 쥐여준다. 이것이 direct victim이다.

6.1 3단계 탐색 순서

pgbuf_get_victim (:9020-9197)의 설계 주석 (:9037-9057) 그대로:

  1. 자기 private 리스트 — 단, quota를 넘겼을 때만 (:9067-9068). 게다가 초과 스레드는 남의 리스트 사용이 제한된다(restrict_other :9091-9099) — 폭식한 세션은 남의 것을 빼앗지 못하고 자기 것을 게워 낸다.
  2. 다른 스레드의 (큰) private 리스트 — lock-free 순환 큐에서 꺼낸다.
  3. shared 리스트 — 역시 lock-free 큐 경유.

리스트 안에서의 탐색 (pgbuf_get_victim_from_lru_list, :9267-9482): victim_hint(또는 bottom)에서 위로 최대 1,000개(MAX_DEPTH)를 걷는다. dirty / flush 중 / 이미 배정됨 → 건너뜀. fix됨 → 후보로만 기록. 깨끗하고 한가한 BCB → trylock 성공 시 리스트에서 떼어 반환. 실패로 끝나면 flush daemon을 깨운다 (:9473) — "victim이 없다 = dirty가 너무 많다"이기 때문.

6.2 direct victim — 번호표와 배급

그래도 victim이 없으면 스레드는 direct_victims.waiter_threads_high/low_priority 큐에 자신을 넣고 잠든다 (:8192-8300). vacuum 스레드와 btree 루트급 hot 페이지를 쥔 스레드는 high 우선순위. 이후 깨끗한 BCB가 생기는 모든 곳에서 배급이 일어난다 (:15364-15421 pgbuf_assign_direct_victim; 배급처 목록은 8.4절 팩트시트): flush를 마친 페이지(post-flush 데몬), zone 3으로 떨어지는 깨끗한 페이지, vacuum이 놓아주는 페이지 등이 대기 스레드의 전용 슬롯(bcb_victims[thread_index])에 직접 꽂힌다.

기아 방지 장치들: 매 4번째 배급은 low 큐 우선 (:15508-15514), low 큐가 꽉 차면 high로 승격 (:8224-8233), 최후엔 5분 타임아웃. ER_PB_ALL_BUFFERS_DIRTY 에러는 flush daemon이 없는 환경(SA mode)에서나 도달하는 마지막 수단이다 (:8326-8330).

7. dirty 페이지, WAL 규칙, flush, checkpoint

🎨 비유 연구원이 책에 수정 메모를 붙였다(dirty). 원본(서고 사본)에 바로 반영하러 뛰어가지 않는다 — 대신 수정 일지(WAL log)에 "몇 쪽을 이렇게 고쳤다"를 적고 일지만 금고에 넣는다(COMMIT). 책 자체는 나중에 사서 알바가 한가할 때 서고에 반영한다. 단 철칙이 하나 있다: 책을 서고에 반영하기 전에, 그 수정의 일지가 반드시 금고에 먼저 들어가 있어야 한다. 이것이 Write-Ahead Logging의 'Ahead'다.

7.1 dirty의 탄생

페이지를 고친 코드는 pgbuf_set_dirty (:4874)를 불러 BCB의 dirty 플래그를 세운다 — WRITE latch를 쥔 채로만 가능하다(디버그 빌드에서 assert) (:11599-11610). 동시에 log manager가 pgbuf_set_lsa로 페이지 머리의 LSA를 갱신하고, dirty가 된 후 첫 수정이면 oldest_unflush_lsa를 기록한다 (:4944-5031).

디스크에 쓰나?보장 수단
COMMIT 시데이터 페이지 ❌ / 로그 ⭕ (commit LSA까지)durability = 로그가 책임 (no-force)
수정 도중flush daemon이 커밋 전에도 쓸 수 있음 ⭕UNDO 로그가 있어 안전 (steal)

CUBRID는 steal / no-force 조합이다 — 그래서 REDO와 UNDO 로그가 모두 필요하다. 실측(quizzes/03·04): 2,000행 UPDATE + COMMIT 직후 → dirties +9,669, data iowrites 0. 1,000행 INSERT + COMMIT → log_append_records +2,052, log_page_iowrites +21, data iowrites 0. 커밋이 디스크에 남기는 것은 로그뿐이다.

7.2 WAL 규칙의 강제 지점 — 모든 페이지 쓰기의 단일 관문

버퍼에서 디스크로 나가는 모든 데이터 페이지는 단 하나의 함수를 지난다: pgbuf_bcb_flush_with_wal (:10671-10898). 순서가 전부다:

  1. BCB에 flushing-to-disk 플래그를 세우고 dirty를 미리 끈다 (:10739, :16018-16033) — 쓰는 동안 다른 스레드가 또 수정하면 그 수정이 새로 dirty를 켜므로 유실되지 않는다.
  2. 페이지를 스택 버퍼로 복사한다 (:10744-10758) — 디스크에 나가는 것은 사본이다. (DWB 사용 시 사본이 곧장 DWB 슬롯으로 들어간다.)
  3. BCB mutex를 풀고 (:10779) —
  4. WAL 규칙 집행: logpb_flush_log_for_wal(페이지의 현재 LSA) (:10786; log_page_buffer.c:4162). 이 페이지의 마지막 수정 로그까지 디스크에 없으면 로그부터 내린다. 이때 Num_log_wals가 1 오른다.
  5. 그 다음에야 실제 쓰기: DWB 경유(8장) 또는 fileio_write (:10811-10837).
📌 두 개의 부등식으로 외우기 ① log flush ≥ commit LSA — COMMIT 응답 전에 (durability)
② log flush ≥ 페이지의 LSA — 데이터 페이지 flush 전에 (WAL 규칙, 위 4단계)
②가 없으면 "로그에 없는 미래"가 데이터 파일에 존재하게 되어 크래시 복구의 전제가 깨진다.

7.3 누가 언제 flush하나 — 데몬의 경제학

page flush daemon(pgbuf-page-flush)이 주역이다. 깨어나는 조건: 1초 주기(기본) + victim을 기다리는 스레드가 있을 때 + 히트율이 낮을 때(기준이 무려 99.9% (:16568-16579)). 본체 pgbuf_flush_victim_candidates (:3818-4119)는:

  • 각 LRU 리스트의 바닥(zone 3)에서 dirty 후보를 모은다 — flush 우선순위는 quota 초과분이 많은 리스트일수록 높다 (pgbuf_compute_lru_vict_target, :14062-14185).
  • (volid, pageid)로 정렬해 물리적 순차 쓰기로 만든다 (:3954-3957).
  • 로그가 아직 안 내려간 페이지는 건너뛰고(Num_data_page_skipped_flush_need_wal) log flush daemon을 깨운다 (:4013-4028).
  • 쓰기 속도는 토큰 버킷으로 제한된다(pgbuf-flush-control 데몬이 50ms마다 토큰 충전, adaptive 모드에선 "풀의 절반이 dirty"를 목표로 부족분의 제곱에 비례해 가속 (:14788-14821)). 단, 로그 쓰기는 토큰을 무시한다 — LOG_CS를 쥔 스레드는 면제 (file_io.c:771-812).

7.4 checkpoint — 복구 시간의 상한을 사는 비용

checkpoint가 없다면 한 달 뒤 크래시의 복구는 한 달치 로그 재생이다. checkpoint는 주기적으로 (기본 6분 / checkpoint_interval) dirty 페이지들을 내려서 REDO 시작점(redo LSA)을 앞으로 당긴다. pgbuf_flush_checkpoint (:4133-4264)의 특징:

  • LRU가 아니라 BCB 테이블 전체를 인덱스 순으로 스캔한다 (:4172).
  • 수집 기준은 oldest_unflush_lsa ≤ flush_upto_lsa — checkpoint 시작 시점 이전의 수정만 책임진다. 진행 중 새로 생긴 dirty는 다음 checkpoint 몫(그래서 "그 순간을 얼리는" 것이 아니다).
  • 여기도 (volid,pageid) 정렬 + 초당 1,000페이지 페이스 제어(burst 16장 단위) (:4275-4362).
  • flush하지 못한 페이지들의 최소 oldest_unflush_lsa가 다음 redo LSA가 되어 로그 매니저에 반환된다 (log_page_buffer.c:7010-7030).
  • victim flusher와 서로 양보한다: checkpoint는 victim flush 중 최대 1.5초/interval 대기 (:4331-4337), victim flusher는 checkpoint 중 ×10 부스트를 끈다 (:3905-3916).

8. Double Write Buffer — 반쪽 페이지와의 전쟁

🎨 비유 16KB 페이지를 디스크에 쓰는 도중 정전이 나면? 디스크가 원자성을 보장하는 단위는 섹터(0.5~4KB)라서, 앞 4KB만 새 내용이고 뒤는 옛 내용인 반쪽짜리 페이지(torn page)가 남을 수 있다. 수정 일지(WAL)도 소용없다 — REDO는 "온전한 옛 페이지" 위에서만 성립하니까. CUBRID의 답: 서고에 반영하기 전에 복사본을 먼저 안전 금고(DWB 파일)에 넣고 확인 도장(fsync)을 받는다. 원본 반영 중 정전이 나도 금고의 사본으로 복구하면 된다.

8.1 쓰기 경로 — 순서가 생명

구성: 기본 2MB 버퍼를 2블록으로 나눠 사용(블록당 64페이지) (dwb 파라미터, :769-811). 읽기 경로가 디스크보다 DWB를 먼저 확인하는 것 (page_buffer.c:8454)은 최적화가 아니라 정합성 요건이다 — ②와 ③ 사이에는 원위치가 구버전이기 때문.

8.2 복구 — 재기동 때 벌어지는 일

부팅 시 dwb_load_and_recover_pages (dwb:3199-3403)가 <db>_dwb 파일을 읽어 각 사본의 원위치 페이지를 검사한다: 머리/꼬리 LSA 워터마크가 일치하면 sane — 절대 덮어쓰지 않는다(버전 복원은 REDO의 몫, DWB는 torn 수리만) (:3155-3161). 불일치(torn)면 DWB 사본으로 교체. 둘 다 깨져 있으면 복구 불능으로 실패한다 (:3163-3176).

⚠️ 반(反)직관 3연발 ① <db>_dwb 파일 크기는 buffer_size가 아니라 블록 1개 크기다(기본 1MB) — 모든 블록 flush가 offset 0에 덮어쓴다 (:1193, :2329). ② torn 감지는 checksum이 아니라 LSA 워터마크이고, 이 검사는 DWB 복구 때만 수행된다 — 일반 읽기 경로는 검사하지 않는다(수리 수단이 있는 곳에서만 검사한다는 일관성). ③ DWB가 켜져 있으면 Num_data_page_iowrites는 페이지당 2회 집계된다(DWB 쓰기+원위치 쓰기) (dwb:2339, :2115, :2150) — 퀴즈 10의 "+206 ≈ 103페이지 × 2"의 정체.
🧪 실습 — Quiz 11 quizzes/11-double-write-buffer: 같은 워크로드를 DWB on/off로 실행. off일 때 iowrites가 페이지당 1회로 떨어지고 DWB 카운터가 사라지는 것을 비교 관측한다. (double_write_buffer_size=0이 off 스위치.)

9. PostgreSQL은 어떻게 푸는가 (20devel)

⚠️ 버전 주의 분석한 트리는 master(20devel, fd2b89854d9)다. 릴리스판 PG와 크게 다르다: freelist 삭제, content lock을 LWLock에서 자체 구현으로 교체(모드 3개), AIO 읽기 기본화 (io_method=worker), BM_JUST_DIRTIED 폐지 등. "PG 상식"과 다른 부분은 그때그때 표시한다.

9.1 구조 한눈에

  • BufferDesc — CUBRID의 BCB에 해당. 20devel의 특징: refcount(18b) + usage_count(4b) + 플래그(12b) + content lock 상태(20b)까지 하나의 64-bit atomic에 패킹 (buf_internals.h:33-86). CUBRID 이 브랜치의 64-bit atomic_latch와 발상이 정확히 같다 — 두 코드베이스가 독립적으로 같은 결론(한 워드 + CAS)에 도달했다는 점이 흥미롭다.
  • lookup — 공유 해시를 128개 파티션으로 나눠 파티션당 LWLock 하나 (NUM_BUFFER_PARTITIONS, lwlock.h:83). CUBRID의 "버킷마다 mutex 1M개"보다 락은 훨씬 적고 굵다.
  • pin — 백엔드-로컬 참조 카운트 배열(8칸+해시)로 같은 페이지 재-pin 시 공유 atomic을 건드리지 않는다 (bufmgr.c:230-269). CUBRID의 per-thread holder 장부와 같은 역할.

9.2 교체: 리스트가 없다 — clock-sweep

PG에는 LRU 리스트 자체가 없다. 버퍼마다 usage_count(0~5)만 두고, 시계 바늘 (nextVictimBuffer, 락 없는 단조 증가 카운터 mod NBuffers)이 배열을 돌며 "usage_count > 0이면 1 깎고 통과, 0이면 victim" (ClockSweepTick freelist.c:109-166; StrategyGetBuffer :183-317). pin 시 usage_count는 5까지 증가 (bufmgr.c:3338).

📌 20devel 뉴스: freelist가 아예 삭제됐다 "빈 버퍼는 freelist에서, 없으면 clock-sweep"이 오랜 상식이었지만, 이 트리에서 freelist는 코드째 사라졌다 (commit 2c789405275 "Remove freelist, always use clock-sweep"; freelist.c:32-56). 갓 부팅한 서버의 버퍼는 전부 usage 0이라 첫 sweep이 즉시 찾아낸다 — cold-start와 steady-state가 같은 경로가 됐다. CUBRID의 invalid list(빈 BCB 목록)는 여전히 존재한다는 점과 대조적.

LRU 근사 수준 비교 — usage_count 4비트는 CUBRID의 리스트 순서보다 훨씬 거친 근사다. 그 대신 접근 시 어떤 전역 자료구조도 조작하지 않는다(atomic 하나). CUBRID는 zone 1 무이동 정책으로 같은 목표(핫 패스에서 리스트 조작 제거)를 리스트를 유지한 채 달성한다.

9.3 scan resistance: ring buffer

대량 스캔은 ring buffer를 배정받는다: seq scan 256KB(+AIO 여유분), VACUUM 2MB, 대량쓰기 16MB (GetAccessStrategy, freelist.c:425-501). 스캔은 이 링 안의 버퍼만 돌려쓰고, usage_count를 1 이상으로 올리지 못한다 (bufmgr.c:3344-3346). 링 버퍼가 다른 백엔드에 의해 재사용되면(usage>1) 말없이 링에서 제외되어 일반 풀로 승격된다 (freelist.c:664-666). CUBRID의 private quota가 "세션"을 격리 단위로 쓰는 반면, PG는 "스캔의 종류"를 단위로 쓴다.

9.4 dirty와 WAL — 같은 규칙, 다른 배선

FlushBuffer (bufmgr.c:4526-4642): LSN 읽기 → XLogFlush(recptr)(WAL 규칙!) → checksum 계산 → smgrwrite. CUBRID의 pgbuf_bcb_flush_with_wal과 1:1로 대응한다. 쓰는 주체는 셋: 아무 백엔드나(victim이 dirty일 때 자기 손으로 flush — CUBRID처럼 데몬에 위임하지 않는다!), bgwriter(시계 바늘 앞을 미리 청소, 풀 전체를 최소 120초에 한 바퀴 (bufmgr.c:4051)), checkpointer.

checkpoint는 dirty를 (tablespace, relfile, block) 순으로 정렬하고 tablespace 간 라운드로빈으로 써서 여러 디스크를 동시에 굴린다 (BufferSync, bufmgr.c:3575-3840). checkpoint_completion_target(0.9)으로 다음 checkpoint 직전까지 시간을 발라 쓴다 — CUBRID의 고정 페이스(초당 1,000장)보다 정교한 스케줄링.

9.5 torn page: doublewrite가 없다 — full_page_writes

PG의 소스에 doublewrite는 한 글자도 없다. 대신 checkpoint 후 첫 수정인 페이지는 WAL 레코드에 페이지 전체 이미지(FPI)를 태워 보낸다 — 판정은 page_lsn <= RedoRecPtr 한 줄 (XLogRecordAssemble, xloginsert.c:678-700). 복구는 디스크의 (어쩌면 torn인) 페이지를 쳐다보지도 않고 WAL의 이미지에서 재구성한다. 비용의 위치가 다르다: CUBRID/InnoDB는 데이터 쓰기 2배, PG는 WAL 볼륨 증가(checkpoint 직후 폭증).

9.6 20devel의 새 물건: AIO 읽기

읽기는 기본적으로 io worker 프로세스가 수행하며(io_method=worker (aio.h:42)), read stream이 최대 io_combine_limit(16블록=128KB)씩 묶어서 비동기 발행한다. 같은 페이지를 읽는 두 번째 백엔드는 CV에서 자는 게 아니라 남의 AIO 핸들에 합류해 기다린다 (bufmgr.c:7304-7310). CUBRID의 buffer lock(팻말+재시도)과 목적은 같고 수단이 다르다. 쓰기는 아직 전부 동기다.

10. InnoDB는 어떻게 푸는가 (MySQL 26.7)

10.1 구조 한눈에

  • 버퍼 풀이 여러 개 — innodb_buffer_pool_instances(기본 auto, 최대 64)개의 독립 인스턴스로 쪼개고, page id의 하위 6비트를 버린 해시로 배정해 64페이지 extent가 같은 인스턴스에 모이게 한다 (buf0buf.ic:823-832). 전역 mutex는 존재하지 않는다 — 인스턴스당 7개의 전문 mutex(LRU_list, free_list, flush_list...)로 분해됐다 (buf0buf.h:2288-2313).
  • buf_page_t / buf_block_t — 관리 데이터(BCB 상당)와 프레임 포인터. fix는 atomic buf_fix_count, 내용 보호는 블록별 rw-latch(S/SX/X).
  • free list가 있다 — PG(삭제), CUBRID(invalid list는 부팅 직후용)와 달리 InnoDB는 상시 free list를 유지하고, page cleaner가 LRU 꼬리를 flush/evict해서 미리 채워 놓는다.

10.2 교체: midpoint LRU — "37% 지점에 꽂는다"

리스트는 하나(인스턴스당)지만 중간점(LRU_old)이 있어 young(앞 ~63%)/old(뒤 ~37%) 두 구역으로 나뉜다. 새로 읽힌 페이지는 head가 아니라 old 구역의 머리에 꽂힌다 (buf_LRU_add_block_low, buf0lru.cc:862-908). 그 페이지가 young으로 승격되는 조건이 정교하다 (buf_page_peek_if_too_old, buf0buf.ic:180-203):

  1. 워밍업 게이트: 아직 아무도 쫓겨난 적 없으면(freed_page_clock==0) 승격 자체를 안 한다 — 새 서버에서 "Pages made young 0"은 정상이다.
  2. innodb_old_blocks_time(기본 1초): 첫 접근 후 1초 안의 재접근은 무시. 풀스캔이 한 페이지를 연달아 만지는 것은 승격 사유가 아니다 — 이것이 InnoDB scan resistance의 핵심.
  3. 승격 스로틀: 이미 young이면, 풀의 ~16%만큼 eviction이 지나기 전엔 재승격하지 않는다 — 핫 페이지가 LRU mutex를 반복해서 잡는 것을 막는다.
📌 상식 교정 "old 구역은 3/8"이라는 유명한 숫자는 상수가 아니라 sysvar 기본값이고, 실제로는 innodb_old_blocks_pct=37 → 378/1024 ≈ 36.9%다 (ha_innodb.cc:23091-23093). 또 old 구역 자체가 리스트 512페이지 미만에서는 아예 생기지 않는다 (BUF_LRU_OLD_MIN_LEN). 26.7에는 Page_fetch::SCAN이라는 호출자 선언형 스캔 힌트도 있다(승격+random read-ahead 억제) (buf0buf.h:61-64) — CUBRID/PG에는 없는 API 레벨 장치.

10.3 dirty: flush list와 fuzzy checkpoint

InnoDB는 LRU와 별도로 dirty 페이지만의 flush list를 유지한다 — oldest_modification LSN 순서(느슨하게: 최대 2MiB LSN 어긋남 허용 (buf0flu.h:410-417)). 덕분에 checkpoint는 페이지를 쓸 필요가 없다: flush list 꼬리의 최소 LSN이 곧 checkpoint LSN이다 (fuzzy checkpoint — log_checkpointer 스레드가 주기적으로 기록만 한다). CUBRID·PG의 "checkpoint = dirty 일괄 flush 이벤트"와 가장 크게 갈리는 지점이다. 대신 redo 로그 공간이 차오르면 page cleaner가 강제로 낮은 LSN 페이지들을 flush해 checkpoint를 전진시킨다(sync flush).

WAL 규칙의 집행 지점은 물론 여기도 있다: 페이지를 쓰기 직전 persist_smaller_than(newest_modification) — 26.7에서 log_write_up_to를 대체한 인터페이스다 (buf0flu.cc:985-993).

page cleaner는 코디네이터+워커 구조로, 매 틱마다 (a) LRU 꼬리 청소(free list 충전)와 (b) flush list flush(redo 생산 속도·dirty 비율 기반 adaptive 산정)를 수행한다. 기준 처리량 innodb_io_capacity의 기본이 26.7에서 10,000(8.0의 50배!)이라는 점은 튜닝 상식을 뒤집는다 (ha_innodb.cc:22234).

10.4 torn page: doublewrite 파일

CUBRID DWB와 동일한 원리: 페이지를 #ib_16384_N.dblwr 파일들에 먼저 쓰고 fsync 후 원위치에 쓴다. 차이: 감지가 checksum 기반이고(CUBRID는 LSA 워터마크), 인스턴스×2개의 병렬 dblwr 파일 + 배치/단일 세그먼트 분리 등 동시성 구조가 크고, DETECT_ONLY 모드(16바이트 요약만 기록, 수리는 포기하고 감지만)라는 절충안이 있다 (buf0dblwr.cc:2772-2924, buf0dblwr.h:260-295). O_DIRECT 계열에선 dblwr 파일 fsync를 생략한다 (:872-876).

10.5 "전부 dirty" 상황의 답

free block이 없으면 사용자 스레드는: free list → LRU 꼬리 100개 스캔 → 자기 손으로 single page flush (동기, 재시도 상한 없음 (buf0lru.cc:630, buf0flu.cc:1896-1971)) → 20회 반복 후엔 매회 10ms 슬립. CUBRID의 "파킹+배급"(6장)과 정반대로 요청자가 직접 값을 치르는 모델이다. 극단 상황에선 ER_IB_BUFFER_POOL_FULL로 서버가 의도적으로 죽기도 한다 (buf0lru.cc:465-471).

11.1 "왜"의 관점에서 다시 보기

  • CUBRID의 설계는 "다중 리스트 + 세션 격리"로 요약된다. 정확한 LRU 순서를 유지하면서도 핫패스 비용을 zone-1 무이동·무락 fast path로 상쇄한다. 대가는 복잡도다 — victim 탐색 3단계, 배급 큐, quota 조정 데몬이 서로 맞물린 정교한 기계이고, 실제로 사문화 코드(AOUT 등)가 남을 만큼 진화 흔적이 많다.
  • PostgreSQL은 "자료구조 최소주의"다. 리스트도 free list도 없이 카운터 하나(usage)와 바늘 하나로 승부한다. 근사는 거칠지만 경합 지점이 가장 적고, 코드가 가장 작다. 스캔 격리도 별도 정책이 아니라 "링이 usage를 1 이상 못 올린다"는 규칙 하나로 해결한다.
  • InnoDB는 "전문화"다. dirty에는 flush list, 빈 프레임에는 free list, 교체에는 midpoint — 목적별 자료구조를 다 만들고 mutex도 목적별로 쪼갰다. fuzzy checkpoint는 그 보상이다: dirty가 LSN 순으로 정리되어 있으니 checkpoint가 공짜에 가깝다.
📌 하나만 기억한다면 세 엔진 모두 같은 불변식 위에 서 있다: "fix/pin된 페이지는 쫓아낼 수 없다", "dirty는 로그가 먼저 내려간 뒤에만 쓴다", "커밋은 로그만 기다린다". 나머지 전부 — 리스트냐 시계냐, 링이냐 quota냐, DWB냐 FPI냐 — 는 이 불변식을 지키면서 경합과 I/O를 어디로 옮길 것인가에 대한 서로 다른 선택이다.

12.4 Grill 준비 체크리스트

리포트와 퀴즈를 마친 뒤, 아래 질문에 막힘없이 답할 수 있으면 grill 준비 완료다.

  1. fix / latch / 트랜잭션 lock의 차이를 수명과 보호 대상으로 설명할 수 있다.
  2. miss 경로에서 buffer lock 팻말이 무엇을 막고, 깨어난 대기자가 왜 "재시도"하는지 안다.
  3. BCB flags 워드에 무엇 무엇이 패킹되어 있는지 나열할 수 있다.
  4. zone 1/2/3의 boost 규칙 세 가지와 그 이유(비용)를 말할 수 있다.
  5. 새로 읽힌 페이지가 (이 빌드에서) 정확히 어디에 꽂히는지, AOUT이 살아 있었다면 어떻게 달랐을지 안다.
  6. quota가 접근 "빈도"가 아니라 워킹셋 "넓이"를 추적하는 이유(히트의 epoch 중복 제거)를 설명할 수 있다.
  7. victim 탐색 3단계 순서와 restrict_other의 의미를 안다.
  8. "모든 후보가 dirty"일 때의 전체 협업(파킹→flush→배급)을 그릴 수 있다.
  9. pgbuf_bcb_flush_with_wal의 5단계 순서(플래그→복사→unlock→WAL→쓰기)를 재현할 수 있다.
  10. checkpoint가 반환하는 redo LSA가 정확히 무엇의 최소값인지 안다.
  11. DWB의 쓰기 순서(②fsync가 왜 ③보다 먼저인가)와 복구 규칙("sane이면 절대 덮지 않는다")을 안다.
  12. 세 엔진의 scan resistance 격리 단위(세션/스캔종류/나이)를 비교할 수 있다.
  13. PG 20devel에서 freelist가 사라진 뒤 cold-start가 어떻게 동작하는지 안다.
  14. InnoDB fuzzy checkpoint가 왜 flush list의 존재 덕분에 가능한지 안다.
  15. DWB on/off에 따라 iowrites 카운터 해석이 어떻게 달라지는지 안다.
