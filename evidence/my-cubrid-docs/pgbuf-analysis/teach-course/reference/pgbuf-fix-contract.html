pgbuf_fix() contract card

코드 리뷰와 발표 중 한 장으로 확인하는 identity → residency → concurrency → ownership → release.

Pinned: f799e05OfflineSource-confirmed

입력 5개

  • thread_p: holder/accounting과 wait context
  • vpid: (volid, pageid) identity
  • fetch_mode: 어떤 page 상태가 허용되는가
  • request_mode: READ 또는 WRITE latch
  • condition: 기다릴 수 있는가

성공 postcondition

  • 요청한 VPID가 올바른 resident frame에 대응한다.
  • 요청과 호환되는 latch 권한이 부여되었다.
  • thread holder와 BCB fix accounting에 소유가 기록되었다.
  • 반환된 PAGE_PTR는 matching unfix까지 접근 가능하다.

Hit와 miss는 어디에서 합쳐지는가?

resident 여부는 경로를 바꾸지만 성공 계약은 바꾸지 않는다.

다섯 질문

  1. Identity — 어느 VPID인가?
  2. Residency — 이미 frame에 있는가?
  3. Concurrency — 어떤 latch를 언제 얻는가?
  4. Ownership — 누가 몇 번 fix했는가?
  5. Release — 언제 replacement 가능해지는가?

경계선

  • fix는 durability 자체가 아니다.
  • 수정자는 WRITE latch 아래에서 logging/dirty protocol을 지킨다.
  • unfix는 보통 disk write가 아니다.
  • fcnt == 0은 replacement eligibility의 필요조건이지 즉시 eviction 명령이 아니다.
