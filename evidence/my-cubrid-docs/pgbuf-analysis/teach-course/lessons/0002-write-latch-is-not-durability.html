00 · Important correction

Commit은 dirty data page를 기다리지 않는다

정정: “data page가 storage에 기록되어야 transaction이 crash-durable하다”는 표현은 너무 강하다. 필요한 WAL과 commit record가 durable하면, data page가 아직 dirty인 상태에서 crash가 나도 redo가 page를 재구성할 수 있다.

WRITE latch는 지금 memory를 바꿀 권리다. Durable WAL은 crash 뒤 변화를 재현할 능력이다. Data-page flush는 그 변화를 page image에 나중에 전파하는 일이다.

01 · Three separate moments

한 번의 update에는 세 개의 clock이 있다

Data page는 commit 시점보다 늦게 기록될 수 있다. 이것이 WAL이 random page writes를 commit latency에서 분리하는 이유다.

02 · Caller completes the mutation contract

Heap과 B-tree는 log와 DIRTY를 연결한다

/* representative heap pattern */
log_append_undoredo_data (..., addr.pgptr, ...);
pgbuf_set_dirty (thread_p, addr.pgptr, DONT_FREE);

/* representative B-tree pattern */
log_append_redo_data (..., new_page_ptr, ...);
pgbuf_set_dirty (thread_p, *new_page_ptr, DONT_FREE);

Logging API는 page address를 받아 log position과 page recovery state를 연결한다. Caller는 수정된 resident image를 DIRTY로 표시한다. Exact call ordering에는 page type과 temporary/unlogged 예외가 있으므로 이 두 줄을 모든 caller의 문자 그대로인 template으로 일반화하면 안 된다.

Release-build safeguard: pgbuf_set_lsa()는 page LSA를 설정하고, release build에서는 dirty도 설정한다. Source comment는 missing dirty call을 방어하면서도 그런 caller bug를 찾아 고쳐야 한다고 명시한다.

Evidence: heap heap_file.c:2867–2868; B-tree btree.c:4071–4073; LSA/dirty safeguard page_buffer.c:5038–5079.

03 · Flush one generation safely

Flusher가 하는 일은 commit과 다르다

  1. BCB protection 아래에서 FLUSHING을 set하고 기존 DIRTY를 clear한다.
  2. Page image, page LSA, oldest_unflush_lsa를 snapshot한다.
  3. BCB를 놓은 뒤 snapshot의 page LSA까지 logpb_flush_log_for_wal()로 WAL을 force한다.
  4. DWB 또는 data-volume write path로 snapshot을 제출한다.
  5. 성공하면 FLUSHING만 clear한다. 그 사이 writer가 다시 set한 DIRTY는 남는다.
  6. 일반 write 실패면 이전 DIRTY와 oldest_unflush_lsa를 복원한다.

Flush 시작 때 old DIRTY를 clear하는 이유는 “clean이라고 선언”하기 위해서가 아니다. I/O 중 새 수정이 생기면 그것을 별도 generation으로 다시 set할 수 있게 하기 위해서다.

Evidence: snapshot/WAL/write/error restore page_buffer.c:10723–10961; generation flags page_buffer.c:16077–16125; WAL force log_page_buffer.c:4150–4189. Claim CUBRID-C004.

05 · Model-visible mastery check

현재 질문

Question

성공적으로 WRITE latch를 얻은 것만으로 수정된 page가 durable해집니까? Data page를 commit 전에 flush하지 않아도 되는 이유까지 설명하세요.

Model/recommended answer: 아니다. WRITE fix는 exclusive in-memory access만 부여한다. Caller는 recovery log와 page LSA 관계를 만들고 page를 DIRTY로 표시한다. 필요한 WAL과 commit record가 durable하면 data page가 아직 dirty여도 redo로 복구할 수 있다. 이후 flusher는 page LSA까지 WAL을 먼저 force하고 page image를 기록하여 해당 generation을 storage에 전파한다.

Why correct: latch는 memory concurrency, durable WAL은 crash recoverability, page flush는 page-image propagation을 담당한다. WAL이 commit과 random data-page write를 분리한다.

Your task: Model을 반복하지 말고 failure matrix에서 두 행을 골라, 왜 그 결과가 생기는지 causal chain으로 설명하세요.
