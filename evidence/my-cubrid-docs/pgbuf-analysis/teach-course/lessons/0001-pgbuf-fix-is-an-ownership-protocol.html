01 · Reframe

“Get page”는 절반만 맞다

호출자는 논리 주소인 VPID와 접근 정책을 넘긴다. 성공하면 byte pointer만 얻는 것이 아니라, 해당 frame을 안전하게 사용할 수 있는 시간 제한 소유권을 얻는다.

pgbuf_fix()는 page identity를 resident frame에 결속하고, latch와 fix ownership을 부여한 뒤, 그 권리가 기록된 상태에서만 PAGE_PTR를 반환한다.

발표 함정: PAGE_PTR 자체가 독립적인 ownership token은 아니다. 실제 protocol state는 BCB의 atomic latch/fix count와 thread holder 쪽에 추적된다. pointer는 그 계약 아래에서 쓰는 접근 수단이다.

Evidence: page_buffer.c:2246–2516; public macro boundary: page_buffer.h:275–330.

02 · One contract, two residency paths

Hit와 miss의 차이는 준비 작업이다

찾는 방법은 다르지만 성공의 의미는 같다.

1

Locate

READ 조건이 맞으면 lock-free read fast path를 먼저 시도하고, 아니면 buffer hash에서 BCB를 찾는다.

2

Materialize

miss이면 victim/replacement와 I/O가 포함될 수 있는 BCB claim/load 경로를 탄다.

3

Grant

올바른 page인지 검증하고 compatible latch와 holder/fix accounting을 만든 뒤 반환한다.

Evidence: lock-free attempt 2362–2376; hash/miss split 2380–2439; latch grant 2485–2516.

03 · The sentence to defend

성공 반환 시 무엇이 참인가?

축성공 postcondition왜 필요한가
IdentityVPID가 BCB/frame의 page와 일치한다.잘못 재사용된 frame을 읽지 않는다.
Residencypage가 buffer frame에 있고 반환 pointer로 접근 가능하다.disk identity를 memory address로 바꾼다.
Concurrency요청한 READ/WRITE access와 호환되는 latch가 부여됐다.동시 접근의 허용 범위를 정한다.
Ownershipthread holder와 global fix accounting이 이 보유를 추적한다.release와 replacement safety를 연결한다.
Lifetimecaller는 matching pgbuf_unfix()까지 계약을 유지한다.frame이 사용 중 재활용되는 것을 막는다.
중요한 경계: durability는 이 성공 조건에 들어가지 않는다. 수정 경로는 별도로 logging, page LSA, dirty marking, WAL-before-data flush 규칙을 지켜야 한다. 따라서 “WRITE fix를 했으니 crash-safe하다”는 답은 틀리다.
04 · Close the lifetime

unfix()가 계약을 닫는다

PAGE_PTR pg = pgbuf_fix (...);
if (pg == NULL) { /* fetch/latch failure policy */ }

/* read or modify only within the granted latch contract */

pgbuf_unfix (thread_p, pg);  /* release exactly this acquisition */

pgbuf_unfix()는 page pointer에서 BCB를 되찾고, thread holder를 줄이며, fast read라면 lock-free release를 시도하고, 아니라면 BCB latch/fix accounting을 갱신한다. 마지막 보유가 사라지면 그 frame은 replacement 대상이 될 수 있지만, unfix가 즉시 eviction이나 disk write를 명령하는 것은 아니다.

Evidence: page_buffer.c:3062–3203. The source comment states the page becomes subject to replacement if no other thread fixes it.

05 · Retrieval practice

소스를 닫고 30초 답변을 써라

Question

“pgbuf_fix()가 단순 page lookup이 아닌 이유와 성공 시 보장되는 것을 설명해 보세요.”

Model / recommended answer: pgbuf_fix()는 VPID라는 logical identity를 resident BCB/frame에 연결하고, 요청과 호환되는 latch를 획득하며, thread holder와 global fix count에 ownership을 기록한 뒤 PAGE_PTR를 반환한다. 따라서 반환 pointer는 matching pgbuf_unfix()까지 그 contract 아래에서만 유효하다. 다만 fix 자체가 logging이나 durability를 보장하지는 않는다.

Your task: 위 답을 복사하지 말고, 각 보장이 빠지면 어떤 failure가 가능한지 자신의 말로 설명하세요.

자동 점검은 단어 포함 여부만 보는 얕은 feedback이다. 진짜 mastery check는 답을 이 채팅에 붙여 넣는 것이다. 그러면 정확성, 빠진 invariant, 위험한 표현을 공격적으로 검토한다.
