One BCB, many lists

01 · Metadata / data split

BCB는 page의 관리 카드, frame은 실제 bytes

Pool은 시작할 때 같은 크기의 배열 두 개를 만든다: BCB_table(관리 카드)과 iopage_table(실제 page bytes). 카드와 frame은 1:1로 짝지어져 서로를 가리킨다.

BCB(PGBUF_BCB) = "이 frame에 지금 어떤 page가 살고 있고(vpid), 누가 쓰고 있으며(atomic_latch, fix count), 어떤 상태인가(flags: DIRTY/FLUSHING, oldest_unflush_lsa)"를 담는 per-frame 관리 레코드.

PGBUF_IOPAGE_BUFFER는 disk에 그대로 기록되는 FILEIO_PAGE iopage(page LSA인 prv.lsa 포함)와 BCB 역포인터만 담는다. Lesson 0002에서 flusher가 memcpy한 대상이 바로 이 iopage이고, DIRTY/FLUSHING flag 연산의 대상은 BCB의 flags다. PAGE_PTR는 이 iopage 내부를 가리키므로, CAST_PGPTR_TO_BFPTR 같은 macro가 pointer 산술로 카드↔bytes를 오간다.

Evidence: page_buffer.c:513–545 (BCB), 548–557 (iopage buffer), 764–767 (두 table). 라인은 lab tracer branch(1daa9d2) 기준이며 구조체 자체는 pinned f799e05와 동일하다.

02 · The picture

같은 BCB가 세 색인에 동시에 꿰여 있다

BCB 안의 링크 field들(hash_next, prev_BCB/next_BCB)이 곧 색인이다. 별도의 node를 만들지 않는다 — intrusive linked list.

핵심 문장: BCB 하나는 (a) hash chain — "이 VPID가 어디 있나", (b) LRU list — "무엇을 쫓아낼까", (c) 어떤 thread의 holder list — "내가 지금 뭘 쥐고 있나"에 동시에 속할 수 있다. 세 질문은 서로 다른 lock(각 bucket의 hash_mutex, 각 LRU의 mutex, BCB 자신의 mutex)으로 보호된다.
03 · The directory

hash table: VPID → resident BCB

buf_hash_table은 bucket 배열이고, 각 bucket(PGBUF_BUFFER_HASH)은 hash_mutex 하나와 두 chain 앵커를 가진다:

  • hash_next chain — 이 bucket에 사는 resident page들의 BCB chain. pgbuf_fix()의 lookup이 걷는 곳.
  • lock_next chain (PGBUF_BUFFER_LOCK) — "지금 이 VPID를 disk에서 적재하는 중"이라는 자리표. miss가 나면 loader가 lock을 걸어 두고, 같은 page를 원하는 다른 thread는 중복 disk read를 하는 대신 여기서 기다린다. lock table 크기가 thread 수로 고정된 이유: thread당 동시에 한 page만 적재할 수 있기 때문.

Evidence: page_buffer.c:577–584 (hash entry), 559–571 (buffer lock, "# of buffer lock records is fixed as the total # of threads").

04 · The clock

LRU lists + AOUT: 무엇을 쫓아낼 것인가

Replacement는 source 주석이 직접 명명한다: "The page replacement algorithm is LRU + Aout of 2Q". 전역 LRU 하나가 아니라 여러 개의 PGBUF_LRU_LIST(shared + private)를 두어 mutex 경합을 나눈다. 각 list는:

  • zone 1|2|3 — top이 가장 뜨겁고, zone 3(bottom 쪽)이 victim 후보 구역. bottom_1/bottom_2가 경계.
  • victim_hint — victim 탐색 시작점 캐시. 주석에 개발자의 솔직한 TODO("there must be a logic error somewhere")까지 남아 있다.
  • tick_list/tick_lru3 — BCB의 tick_lru_list/tick_lru3와 비교해 "충분히 오래됐으니 top으로 승격"을 판단하는 나이 계산기.

buf_AOUT_list는 2Q의 두 번째 축: victim으로 쫓겨난 page의 VPID만 FIFO로 기억하는 이력이다(frame 없음). 다시 fix되는 page가 AOUT에 있으면 "최근에 쫓아냈던 놈"이므로 더 뜨거운 위치로 넣는다. buf_invalid_list는 deallocate된 page의 BCB들이 쉬는 free list다.

Evidence: page_buffer.c:587–625 (LRU list), 637–668 (2Q comment + AOUT), 628–635 (invalid list).

05 · The ledger

holder: "이 thread가 지금 쥔 것" 장부

Lesson 0001의 "holder accounting"의 실체: pgbuf_Pool.thrd_holder_info[]는 thread당 하나의 PGBUF_HOLDER_ANCHOR이고, 그 안의 thrd_hold_list가 이 thread가 현재 fix 중인 BCB들의 PGBUF_HOLDER(BCB pointer + fix_count) 목록이다. fix/unfix마다 갱신되므로 cache line 하나(64B)에 padding까지 맞춰 놓았다 — false sharing 방지.

이 장부 덕분에: 재귀적 fix(fix_count 증가)가 가능하고, debug build는 "unfix 없이 끝난 thread"를 적발하며, Lesson 0002에서 본 flush의 안전장치 assert("I must be the owner")도 바로 이 thrd_hold_list를 걷는다.

Evidence: page_buffer.c:463–492 (holder + anchor + cache-line static_assert), flush assert 10870–10888.

발표 함정: "DIRTY page 목록이 따로 있다"고 말하지 마라. CUBRID에는 dirty page 전용 list가 없다 — DIRTY는 BCB flags의 bit이고, flusher는 LRU list들을 훑어 victim 후보 중 dirty를 골라낸다(count_vict_cand, victim_cand_list). PostgreSQL의 clock-sweep이나 InnoDB의 flush_list와 다른 지점.
07 · Retrieval practice

소스를 닫고 지도를 다시 그려라

Question

"Buffer pool 내부 자료구조를 지도처럼 설명해 보세요. 각 구조가 없으면 어떤 질문에 답할 수 없게 됩니까?"

Model / recommended answer: pool은 BCB_table(관리 카드)과 iopage_table(실제 bytes)의 1:1 쌍이 본체다. buf_hash_table의 bucket chain이 VPID→BCB directory를 제공하고, 같은 bucket의 buffer lock chain이 "적재 중" 자리표로 중복 disk read를 막는다. 여러 PGBUF_LRU_LIST(zone 1|2|3 + victim_hint)와 buf_AOUT_list(쫓겨난 VPID 이력, 2Q)가 victim 선택에 답하고, thrd_holder_info[]의 per-thread holder list가 "내가 지금 뭘 쥐었나"에 답한다. 이 색인들은 별도 node가 아니라 BCB 안의 링크 field(hash_next, prev_BCB/next_BCB)로 꿰인다.

Your task: model을 반복하지 말고, 구조 하나를 골라 그것이 사라진 세계를 서술하세요 (예: buffer lock table이 없다면 miss 두 개가 동시에 오면 무슨 일이 생기는가?).

자동 점검은 단어 포함만 본다. 진짜 검사는 답을 채팅에 붙여 넣는 것 — 그러면 잘못된 소유권 서술이나 빠진 lock 경계를 공격적으로 짚는다.
