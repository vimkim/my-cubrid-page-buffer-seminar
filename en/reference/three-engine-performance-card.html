Performance-opportunity funnel

  1. Observe: measure held-list depth, nodes inspected, shared CAS attempts/retries, and cycles per fix/unfix.
  2. Localize: vary held-set size separately from thread count and target-page sharing.
  3. Low-risk prototype: accelerate per-thread holder lookup while preserving global fcnt.
  4. Higher-risk prototype: aggregate nested ownership locally only if shared CAS is proven material.
  5. Prove: preserve promotion, waiter ordering, zero-crossing wakeup, last-unfix LRU work, and victim exclusion.
Current conclusion: source-backed opportunity, not measured improvement. Existing evidence does not compare latency or throughput across the three engines.

Thirty-second answer

CUBRID's distinctive seam is that a normal fix combines residency protection, a per-thread holder, and the requested page latch. PostgreSQL makes pin and content lock independent and keeps repeated pins backend-local after the first shared contribution. InnoDB keeps fix count and latch state separate but records their lifetime in an MTR memo. The first CUBRID performance bet is to measure linear holder lookup as held-set depth grows; only if shared atomic traffic dominates should nested-fix aggregation be considered.
