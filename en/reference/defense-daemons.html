1 / 6 · Problem and invariant

Independent outputs explain independent roles

A full pool couples four different problems: dirty candidates need safe submission; submitted images leave CPU bookkeeping; workload changes make old retention budgets unsuitable; many writers compete for storage. One event does not solve all four.

Page-flushSubmitted cold images; decouple clean supply from one blocked allocator.
Post-flushBCB completion and conditional offers; offload CPU completion under pressure.
MaintenanceUpdated quotas/zones; adapt retention to sampled activity.
Flush-controlReplacement token allowance; distribute post-write pacing across writers.

2 / 6 · Mechanism and evidence

The task predicate is stronger evidence than the wake

Page-flush runs at least once after an explicit sleeping wake, then tests current pressure. Post-flush drains queued BCB pointers. Maintenance attempts quota updates. Flush-control samples elapsed time and replaces a shared allowance; its first useful call only establishes the time origin.

The nominal pauses are configurable page-flush, escalating 1/10/100 ms then wake-only post-flush, 100 ms maintenance and 50 ms control. Execution time and scheduling affect actual intervals. Wake while RUNNING returns without retaining a future event; wake while SLEEPING changes waiter state and notifies.

4 / 6 · Alternatives and costs

Move a role only with its ownership obligations

Teaching alternatives: Foreground callers can submit dirty pages safely through the same WAL/image protocol, but the allocator pays that I/O latency. Local completion already replaces post-flush when handoff cannot occur; it retains completion/wakeup semantics but consumes producer CPU. A single worker could perform all four tasks, if it separately tracks every work predicate and policy cadence; blocking page I/O could delay all other duties.

Static quotas remove adaptation, affecting policy under shifting workloads. Caller-driven token refresh would need shared elapsed-time accounting and notification; simply removing the refresh leaves token waiters dependent on escape paths or other wakes.

Four daemons add four managed execution contexts, threads, stacks and waiter/looper state when created. Per-call useful work is not O(1): candidate scans, queue drain and policy updates have their own costs. Separation may reduce coupling; it is not a measured speedup.

Removal schedules: With all searched frames dirty, no foreground/checkpoint flush and no other cleaning producer, deleting page-flush leaves the waiting allocator without new clean supply. If post-flush is absent before submission, local fallback completes; stopping it after enqueue can strand that queued obligation. Removing periodic maintenance leaves quiet intervals dependent on existing foreground updates. Removing refill while keeping an ordinary deficit wait can strand it on an untimed condition; removing the pacing wait instead changes burst behavior. These are different removal scopes.

5 / 6 · Concurrency and failure boundaries

Stop must reach a joined thread before resource release

Pool structures exist before the daemon group. Threads can already run during log recovery, but every task first tests the boot gate. Enabling the gate is not itself a wake of every role. Removing the gate allows task accesses during recovery; the resulting failure depends on the shared state being changed by recovery, rather than merely on a thread existing.

Destruction sets stop, wakes a sleeper, joins, then retires context/task. If a working task is in I/O, stop does not cancel that I/O. If a sleeper is never awakened, join can fail to progress. Freeing the pool after setting stop but before join can race a still-working task and cause a lifetime violation.

6 / 6 · Defense and falsifiability

D26 · Does a 50 ms timer prove a waiting writer will finish?

A caller reports a 300 ms stall. The control daemon has a 50 ms nominal period. Must six useful refreshes have completed? A reviewer proposes treating each timer tick as one guaranteed writer completion.

Challenge, then reveal the bounded answer

No. Gate, task execution, scheduling, condition mutex and writer competition remain. A refresh publishes an allowance, not a writer completion. Useful progress also requires the writer to be scheduled and obtain the relevant shared state.

Follow-up: “Then why have a timer?” It supplies another execution opportunity without requiring a work producer to notify this role; it does not eliminate dependency conditions.

Discriminating observation: Record gate, waiter status, task start/end, generated allowance, writer condition returns and current demand. A wake count alone cannot distinguish missed work from a long-running task. Keep Q04–Q06 as the existing lifecycle challenges.
