Part 1 · Boundary and objects

What exists, and who owns correctness?

EssentialPGBUF-QB-001Lesson 1

1. What does the page-buffer Module own—and what remains with its callers?

Show model answer

Spoken answer: The Module maps a page identity to resident bytes and temporarily protects those bytes through fix, latch, dirty/flush, and replacement protocols. It does not know whether the caller chose the right page or made a logically valid change. Allocation knowledge, logical locking, page-layout validation, recovery meaning, retry, and complete cleanup remain with the caller and neighboring modules.

Defend with: Successful fix proves an access contract; it does not prove caller correctness.

Canonical answer and source anchors · Lesson 1

EssentialPGBUF-QB-003Lessons 1–2

2. How do VPID, BCB, frame, PAGE_PTR, and holder differ?

Show model answer

Spoken answer: A VPID is the logical page identity. A BCB is volatile control state for one currently resident identity, paired with a frame that stores the bytes. A PAGE_PTR is only a borrowed view into those bytes; it is not the page’s identity or ownership record. Global fcnt protects the frame from reuse, while each thread’s holder records its own matching release debt.

Defend with: The pointer can repeat while identity changes, and identity can remain while the frame address changes.

Canonical answer and source anchors · Lesson 2

CounterexamplePGBUF-QB-004Lesson 2

3. Can a page be resident, unfixed, and dirty at the same time?

Show model answer

Spoken answer: Yes. Residency, fix ownership, latch state, dirty/flush state, and victim eligibility are independent axes. A caller can unfix a modified page while it remains resident and dirty for later propagation. It is not safe to victimize merely because fcnt==0; dirty, flushing, waiter, transient-owner, and identity conditions still matter.

Defend with: “Resident” describes location, “fixed” describes reuse protection, and “dirty” describes propagation debt.

Part 2 · Acquisition and ownership

Why do successful-looking paths still recheck?

Expected challengePGBUF-QB-009Lesson 3

4. Why check BCB identity again after finding a victim or hash candidate?

Show model answer

Spoken answer: The first lookup produces only a candidate. Before the thread obtains the protection needed to fix, release, remove, or reuse it, another thread may change the resident mapping. The protected identity check proves that the BCB still represents the expected VPID at the transition that matters.

Defend with: It is not checking whether the same BCB address still exists; it is checking whether that stable slot still has the same current identity.

Canonical answer and source anchors · Lesson 7

Expected challengePGBUF-QB-015Lesson 4

5. Can several threads share one BCB? Does that put it in several LRUs?

Show model answer

Spoken answer: Several compatible readers can fix the same BCB concurrently. They share one resident BCB and one global fcnt, but each thread has a separate holder entry and nested release debt. That does not duplicate the BCB across LRU lists: LRU membership is replacement-policy placement for the single BCB, not per-thread ownership.

Defend with: Per-thread holder ledgers answer “who owes release?”; LRU state answers “where should replacement search?”

Canonical answer and source anchors · Ownership debt card

EssentialPGBUF-QB-013Lesson 5

6. Why does a caller need a transaction lock if it already has a page latch?

Show model answer

Spoken answer: A page latch serializes short physical access to one in-memory page image. A transaction lock protects a logical database object across transaction conflict and visibility rules. A heap mutation may need both because protecting bytes does not establish logical permission, and logical permission does not protect the bytes while they are edited.

Defend with: The mechanisms have different objects, owners, and lifetimes.

Canonical answer and source anchors · Lesson 5

Part 3 · Mutation and durability

Which generation became durable?

EssentialPGBUF-QB-023Lesson 5

7. What is the correct mutation, logging, page-LSA, dirty, and release order?

Show model answer

Spoken answer: The caller first establishes logical permission and validates the destination, then mutates through the page owner, appends the recovery record, advances the page LSA when required, marks the resident generation dirty, and finally transfers or releases every watcher on both success and error paths.

Defend with: A WRITE latch alone supplies none of the recovery meaning, dirty publication, or all-exit cleanup.

Canonical answer and source anchors · Caller mutation card

Expected challengePGBUF-QB-028Lesson 6

8. What are generation G and G+1, and why can DIRTY and FLUSHING both be set?

Show model answer

Spoken answer: “Generation” is a reasoning label for one snapshot of the page bytes and LSAs selected for flushing; it is not a stored version number. The flusher copies G and marks that work FLUSHING. If a writer changes the resident page afterward, those newer bytes are G+1 and set DIRTY again. G can finish successfully while G+1 remains dirty, so FLUSHING and DIRTY may overlap without contradiction.

Defend with: FLUSHING means an older copied image has in-flight work; DIRTY means the current resident image still owes propagation.

Canonical answer and source anchors · Flush-generation card

EssentialPGBUF-QB-027Lesson 6

9. Where does WAL-before-data happen, and does successful flush mean the home page is durable?

Show model answer

Spoken answer: Before submitting the copied page image, page-buffer flush asks log management to force WAL through that image’s page LSA. The image then follows the configured DWB or direct data-volume path. Success at this boundary may mean DWB acceptance or direct-write return; it does not automatically prove physical home-page persistence.

Defend with: WAL is the recovery-ordering gate, DWB protects page-image propagation, and physical durability is a lower boundary.

Canonical answer and source anchors · Lesson 6

Part 4 · Replacement and progress

Eligibility first; policy second

EssentialPGBUF-QB-029Lesson 7

10. What makes a BCB safe to victimize?

Show model answer

Spoken answer: LRU policy may nominate a candidate, but reuse requires a protected final gate: the BCB must be unfixed, clean and not flushing, free of disqualifying waiters or transient ownership, conditionally protectable, and still bound to the expected identity. Neither fcnt==0 nor LRU position is sufficient by itself.

Defend with: Policy chooses where to search; hard predicates authorize destructive reuse.

Canonical answer and source anchors · Replacement-safety card

AdvancedPGBUF-QB-040Lesson 12

11. What happens when no free BCB is immediately available?

Show model answer

Spoken answer: The allocator enters a progress protocol: search invalid or eligible victim state, trigger flush or background progress, wait for or consume a direct-victim reservation, and retry. Timeout, interrupt, or an all-buffers-dirty condition can provide bounded exits. An empty free list is pressure, not proof of deadlock or starvation.

Defend with: Safety is established by eligibility; liveness depends on producers, wakeups, retries, and bounded exits.

Part 5 · Advanced mechanisms

What changes across a temporary ownership gap?

AdvancedPGBUF-QB-035Lesson 11

12. Why can ordered fixing release pages first, and what becomes stale?

Show model answer

Spoken answer: To avoid acquiring a multi-page set in a conflicting order, the helper may release watchers, sort the required order, and refix. Refix restores ownership of the identities, but it does not restore observations made before release. Page-local pointers, slots, offsets, comparisons, and traversal decisions must be recomputed when page_was_unfixed reports the gap.

Defend with: Same VPID after refix does not mean same bytes or same derived decision.

Canonical answer and source anchors · Ordered-watcher card

AdvancedPGBUF-QB-046Lesson 13

13. How does redo use page LSA to avoid applying a record twice?

Show model answer

Spoken answer: Redo fixes the recovery page under WRITE and compares the log record LSA with the page LSA. If the page already represents that record, redo skips it and releases ownership. Otherwise it applies the recovery function, advances the page LSA, marks the page dirty as required, and releases through scope cleanup.

Defend with: This proves page-image idempotence at the LSA gate; it does not automatically prove arbitrary callback side effects idempotent.

Canonical answer and source anchors · Lesson 13

Evidence disciplinePGBUF-QB-055Lessons 8 and 16

14. Are VS-10, VS-11, and VS-12 packets true statements that defects exist?

Show model answer

Spoken answer: No. A VS-* packet is a version-sensitive evidence record for a concern, not a verdict. It packages the candidate’s source path, current evidence level, missing proof, and status owner. Promotion requires exact control flow, supported reachability, surviving-state evidence, caller or production impact, and a target-branch recheck. Different packets may already sit at different evidence levels.

Defend with: “Source-visible early return” is weaker than “reachable state leak,” which is weaker than “demonstrated production defect.”

Maintainer defensePGBUF-QB-070Lessons 8 and 16

15. What test actually proves a page-buffer change is safe?

Show model answer

Spoken answer: There is no universal test. Choose the seam that crosses the risk: a representative caller regression for an Interface change, deterministic interleaving for an ordering race, named fault injection plus state assertions for unwind, controlled pressure for replacement policy, and crash/recovery evidence for durability. Then state exactly what remained untested.

Defend with: More repetitions are not stronger evidence if execution never crosses the risky transition.
