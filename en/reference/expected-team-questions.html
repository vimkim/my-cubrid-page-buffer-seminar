Part 1 · Boundary and objects

What exists, and who owns correctness?

EssentialPGBUF-QB-001Lesson 1

1. What does the page-buffer Module own—and what remains with its callers?

Show model answer

Model answer: The Module maps a page identity to resident bytes and temporarily protects those bytes through fix, latch, dirty/flush, and replacement protocols. It does not know whether the caller chose the right page or made a logically valid change. Allocation knowledge, logical locking, page-layout validation, recovery meaning, retry, and complete cleanup remain with the caller and neighboring modules.

Defend with: Successful fix proves an access contract; it does not prove caller correctness.

Canonical answer and source anchors · Lesson 1

EssentialPGBUF-QB-003Lessons 1–2

2. How do VPID, BCB, frame, PAGE_PTR, and holder differ?

Show model answer

Model answer: A VPID is the logical page identity. A BCB is volatile control state for one currently resident identity, paired with a frame that stores the bytes. A PAGE_PTR is only a borrowed view into those bytes; it is not the page’s identity or ownership record. Global fcnt protects the frame from reuse, while each thread’s holder records its own matching release debt.

Defend with: The pointer can repeat while identity changes, and identity can remain while the frame address changes.

Canonical answer and source anchors · Lesson 2

CounterexamplePGBUF-QB-004Lesson 2

3. Can a page be resident, unfixed, and dirty at the same time?

Show model answer

Model answer: Yes. Residency, fix ownership, latch state, dirty/flush state, and victim eligibility are independent axes. A caller can unfix a modified page while it remains resident and dirty for later propagation. It is not safe to victimize merely because fcnt==0; dirty, flushing, waiter, transient-owner, and identity conditions still matter.

Defend with: “Resident” describes location, “fixed” describes reuse protection, and “dirty” describes propagation debt.

Part 2 · Acquisition and ownership

Why do successful-looking paths still recheck?

Expected challengePGBUF-QB-009Lesson 3

4. Why check BCB identity again after finding a victim or hash candidate?

Show model answer

Model answer: The first lookup produces only a candidate. Before the thread obtains the protection needed to fix, release, remove, or reuse it, another thread may change the resident mapping. The protected identity check proves that the BCB still represents the expected VPID at the transition that matters.

Defend with: It is not checking whether the same BCB address still exists; it is checking whether that stable slot still has the same current identity.

Canonical answer and source anchors · Lesson 7

Expected challengePGBUF-QB-015Lesson 4

5. Can several threads share one BCB? Does that put it in several LRUs?

Show model answer

Model answer: Several compatible readers can fix the same BCB concurrently. They share one resident BCB and one global fcnt, but each thread has a separate holder entry and nested release debt. That does not duplicate the BCB across LRU lists: LRU membership is replacement-policy placement for the single BCB, not per-thread ownership.

Defend with: Per-thread holder ledgers answer “who owes release?”; LRU state answers “where should replacement search?”

Canonical answer and source anchors · Ownership debt card

EssentialPGBUF-QB-013Lesson 5

6. Why does a caller need a transaction lock if it already has a page latch?

Show model answer

Model answer: A page latch serializes short physical access to one in-memory page image. A transaction lock protects a logical database object across transaction conflict and visibility rules. A heap mutation may need both because protecting bytes does not establish logical permission, and logical permission does not protect the bytes while they are edited.

Defend with: The mechanisms have different objects, owners, and lifetimes.

Canonical answer and source anchors · Lesson 5

Part 3 · Mutation and durability

Which generation became durable?

EssentialPGBUF-QB-023Lesson 5

7. What is the correct mutation, logging, page-LSA, dirty, and release order?

Show model answer

Model answer: The caller first establishes logical permission and validates the destination, then mutates through the page owner, appends the recovery record, advances the page LSA when required, marks the resident generation dirty, and finally transfers or releases every watcher on both success and error paths.

Defend with: A WRITE latch alone supplies none of the recovery meaning, dirty publication, or all-exit cleanup.

Canonical answer and source anchors · Caller mutation card

Expected challengePGBUF-QB-028Lesson 6

8. What are generation G and G+1, and why can DIRTY and FLUSHING both be set?

Show model answer

Model answer: “Generation” is a reasoning label for one snapshot of the page bytes and LSAs selected for flushing; it is not a stored version number. The flusher copies G and marks that work FLUSHING. If a writer changes the resident page afterward, those newer bytes are G+1 and set DIRTY again. G can finish successfully while G+1 remains dirty, so FLUSHING and DIRTY may overlap without contradiction.

Defend with: FLUSHING means an older copied image has in-flight work; DIRTY means the current resident image still owes propagation.

Canonical answer and source anchors · Flush-generation card

EssentialPGBUF-QB-027Lesson 6

9. Where does WAL-before-data happen, and does successful flush mean the home page is durable?

Show model answer

Model answer: Before submitting the copied page image, page-buffer flush asks log management to force WAL through that image’s page LSA. The image then follows the configured DWB or direct data-volume path. Success at this boundary may mean DWB acceptance or direct-write return; it does not automatically prove physical home-page persistence.

Defend with: WAL is the recovery-ordering gate, DWB protects page-image propagation, and physical durability is a lower boundary.

Canonical answer and source anchors · Lesson 6

Part 4 · Replacement and progress

Eligibility first; policy second

EssentialPGBUF-QB-029Lesson 7

10. What makes a BCB safe to victimize?

Show model answer

Model answer: LRU policy may nominate a candidate, but reuse requires a protected final gate: the BCB must be unfixed, clean and not flushing, free of disqualifying waiters or transient ownership, conditionally protectable, and still bound to the expected identity. Neither fcnt==0 nor LRU position is sufficient by itself.

Defend with: Policy chooses where to search; hard predicates authorize destructive reuse.

Canonical answer and source anchors · Replacement-safety card

AdvancedPGBUF-QB-040Lesson 12

11. What happens when no free BCB is immediately available?

Show model answer

Model answer: The allocator enters a progress protocol: search invalid or eligible victim state, trigger flush or background progress, wait for or consume a direct-victim reservation, and retry. Timeout, interrupt, or an all-buffers-dirty condition can provide bounded exits. An empty free list is pressure, not proof of deadlock or starvation.

Defend with: Safety is established by eligibility; liveness depends on producers, wakeups, retries, and bounded exits.

Canonical answer and source anchors · Lesson 12

Part 5 · Advanced mechanisms

What changes across a temporary ownership gap?

AdvancedPGBUF-QB-035Lesson 11

12. Why can ordered fixing release pages first, and what becomes stale?

Show model answer

Model answer: To avoid acquiring a multi-page set in a conflicting order, the helper may release watchers, sort the required order, and refix. Refix restores ownership of the identities, but it does not restore observations made before release. Page-local pointers, slots, offsets, comparisons, and traversal decisions must be recomputed when page_was_unfixed reports the gap.

Defend with: Same VPID after refix does not mean same bytes or same derived decision.

Canonical answer and source anchors · Ordered-watcher card

AdvancedPGBUF-QB-046Lesson 13

13. How does redo use page LSA to avoid applying a record twice?

Show model answer

Model answer: Redo fixes the recovery page under WRITE and compares the log record LSA with the page LSA. If the page already represents that record, redo skips it and releases ownership. Otherwise it applies the recovery function, advances the page LSA, marks the page dirty as required, and releases through scope cleanup.

Defend with: This proves page-image idempotence at the LSA gate; it does not automatically prove arbitrary callback side effects idempotent.

Canonical answer and source anchors · Lesson 13

Evidence disciplinePGBUF-QB-055Lessons 8 and 16

14. Are VS-10, VS-11, and VS-12 packets true statements that defects exist?

Show model answer

Model answer: No. A VS-* packet is a version-sensitive evidence record for a concern, not a verdict. It packages the candidate’s source path, current evidence level, missing proof, and status owner. Promotion requires exact control flow, supported reachability, surviving-state evidence, caller or production impact, and a target-branch recheck. Different packets may already sit at different evidence levels.

Defend with: “Source-visible early return” is weaker than “reachable state leak,” which is weaker than “demonstrated production defect.”

Maintainer defensePGBUF-QB-070Lessons 8 and 16

15. What test actually proves a page-buffer change is safe?

Show model answer

Model answer: There is no universal test. Choose the seam that crosses the risk: a representative caller regression for an Interface change, deterministic interleaving for an ordering race, named fault injection plus state assertions for unwind, controlled pressure for replacement policy, and crash/recovery evidence for durability. Then state exactly what remained untested.

Defend with: More repetitions are not stronger evidence if execution never crosses the risky transition.

Reader implementation questions

Fourteen direct answers from the pinned source

LookupReader Q1Lesson 3

1. What hashing algorithm maps a VPID toward a BCB?

Show direct answer

Answer: The resident lookup uses bucket = (pageid ^ (reverse8(volid & 0xff) << 12)) & 0xfffff. It reverses the low eight volume-id bits into the high portion of a 20-bit value, XORs the page id, and selects one of 2^20 anchors. The bucket contains a chain, so lookup still locks a candidate and compares the complete VPID. pgbuf_hash_vpid() is a separate generic/AOUT hash, not this resident-table formula.

Pool lifetimeReader Q2Lesson 2

2. Does a lookup miss create a new BCB?

Show direct answer

Answer: No. Startup allocates a fixed BCB array and a one-to-one frame array. data_buffer_pages determines num_buffers—32,768 by default at this baseline, subject to the page-buffer minimum—and every slot initially has no resident identity. A miss claims an invalid/free slot or reuses a victim. The code says “allocate a BCB,” but it means allocate from this existing pool; “create a new BCB” is misleading after initialization.

PressureReader Q3Lessons 7 and 12

3. What happens when the BCB pool is full?

Show direct answer

Answer: The allocator searches for a safe LRU victim. If none is immediately eligible, server mode can request flush progress and wait for a direct victim; stand-alone or recovery paths flush synchronously and retry. Assignment, retry, interrupt, timeout, and ER_PB_ALL_BUFFERS_DIRTY are bounded outcomes. Selection never overrides the hard gate: an unsafe fixed, dirty, flushing, waited-on, transient, or identity-changed BCB cannot be reused.

LRU policyReader Q4Lesson 12

4. How many private and shared LRUs exist, and what do their quotas mean?

Show direct answer

Answer: The counts are configuration- and mode-dependent. Auto shared count derives from MAX_NTRANS, targets roughly 1,000 buffers per list, and has a floor of four; explicit count is capped at 1,000. In server mode, private count -1 derives from transaction plus vacuum capacity, 0 disables private quotas, and a positive count has a floor of four. One BCB belongs to one list. Quotas guide placement and search; they do not cap fixes or authorize reuse.

Answer: Shared LRU1/LRU2 defaults are 40%/5%; private quota targets reserve 5%/5%. Activity-weighted private quotas are smoothed, capped at 5,000 pages and half the pool, while the shared remainder has a minimum target of 50 per list. All numbers are pinned policy, not Interface contract.

OwnershipReader Q5Lessons 3 and 4

5. What do fix and unfix mean?

Show direct answer

Answer: A successful fix makes the requested page resident, grants the requested page latch, increments global BCB fix ownership, records the current thread’s nested holder debt, and lends a PAGE_PTR. The matching unfix repays one debt. When the global count reaches zero it releases the latch and may place, boost, flush, or offer the BCB to replacement. Unfix is not commit, flush, eviction, or deallocation.

Source: src/storage/page_buffer.c:2260-2685,3062-3201,6277-6883

Background progressReader Q6Lesson 12

6. How many page-buffer daemons exist, and what do they do?

Show direct answer

Answer: Server mode nominally registers four: maintenance every 100 ms for quota/direct-victim work; page flush on demand or at the 1,000 ms default interval; post-flush with adaptive 1/10/100 ms waits; and flush control every 50 ms for I/O tokens. Recovery gating, configuration, and failed flush-control initialization qualify that count. Stand-alone mode has no page-buffer daemons and uses synchronous progress.

Victim orderReader Q9Lesson 12

9. How is victim priority determined?

Show direct answer

Answer: There is no single priority number. The order is layered: domain pressure chooses own over-quota private, other private, shared, then own under-quota private; only LRU3 is scanned from its hint or oldest end for at most 1,000 candidates; then the final safety gate may reject the preferred candidate. A separate high/low queue prioritizes direct-victim waiters, not BCB eligibility.

Holder lifetimeReader Q10Lesson 4

10. How does a holder entry live, and can it make unfix slow?

Show direct answer

Answer: Initialization reserves seven entries per thread; exhaustion grows storage in sets of ten. First fix binds one free entry to one BCB and prepends it to that thread’s hold list. Nested fixes reuse it by increasing fix_count. Final matching unfix removes the binding and returns the entry to that thread’s free list, but backing memory remains until page-buffer finalization.

Performance judgment: a bottleneck is plausible, not automatic. Find is linear in the distinct BCBs held by that thread, and final removal may walk the singly linked list again. Small or LIFO hold sets are cheap; unfavorable order can accumulate quadratic traversal. Many threads on one BCB can instead contend on its shared atomic latch, while nested fixes of one page by one thread do not lengthen the holder list. Profile these separately from zero-count LRU work, wakeups, and flush.

Source: src/storage/page_buffer.c:86-94,438-500,5922-6275,6298-6634,7807-7835

Replacement safetyReader Q11Lessons 7 and 12

11. Why does victim selection need a protected handoff?

Show direct answer

Handoff: the LRU scan only nominates a pointer. Its pre-lock “all clear” reads can become stale when ownership, flags, waiter state, or list state changes. BCB try-lock plus a current recheck authorizes detach; removal changes membership to PGBUF_VOID_ZONE and returns the BCB still locked, preventing an A-based decision from acting after rebind to B.

Safety: fcnt > 0, next_wait_thrd != NULL, non-idle latch/transient protocol state, DIRTY, FLUSHING, and direct-victim flags block ordinary reuse. DIRTY protects unpropagated current bytes; FLUSHING protects completion still associated with an older snapshot and identity.

Pressure: a nonresident materialization first tries the invalid list and searches victims only when no free slot exists. If every BCB is fixed, none is stolen: server mode waits for a future unfix or exits by timeout/interrupt/shutdown; the no-daemon path retries synchronously and fails if no victim appears.

One LRU: one BCB has one link pair and one encoded list index/zone. Private-to-shared movement removes it to VOID before adding it to the new list. LRU objects live for the pool; context assignments and BCB membership are shorter-lived.

Source: src/storage/page_buffer.c:499-623,8181-8403,9265-9538,9695-10415,14513-14650,15900-16030

Cross-private LRUReader Q12Lesson 12

12. How does one transaction find victims in another private LRU?

Show direct answer

Discovery: it does not inspect transaction objects or walk every private list. Over-quota private lists with LRU3 candidates advertise their integer indices in lock-free circular queues. The victimizer consumes the big-private queue first, then the regular queue when allowed, and maps the index directly to buf_LRU_list[lru_idx].

Locking: it locks only that selected list, scans at most 1,000 LRU3 entries, and try-locks BCBs. Contention on a concentrated hot list is possible, but there is no all-private-LRU mutex sweep; severe bottleneck requires measured evidence.

Zones: new private BCBs normally enter LRU1 top, new shared BCBs LRU2 middle. Threshold pressure demotes LRU1→LRU2→LRU3. An old-enough LRU2 hit and an ordinary LRU3 hit boost to LRU1. Private LRU1/LRU2 targets are 5%/5% of quota; shared defaults are 40%/5% of the shared target.

Source: src/storage/page_buffer.c:9330-9538,9695-10353,14251-14511,15674-15728,16370-16506

Ordered ownershipReader Q13Lesson 11

13. What are the inputs, outputs, and internal steps of ordered fix?

Show direct answer

Input: thread_p, requested VPID, fetch mode, latch mode, and a clean in/out watcher. The caller initializes the watcher with its access-method rank and optional heap group; pgptr must be null. Already-held watchers are not passed as a separate array—the helper discovers them through the current thread’s holder list.

Output: the function returns an integer status. On success, req_watcher.pgptr is the requested watched fix and the watcher records latch/rank/group/link state. Existing watchers that crossed a release/refix gap regain pointers with page_was_unfixed=true. On partial failure, earlier watchers may be restored while later ones remain null, so inspect each watcher.

Internal path: try the request conditionally while other pages are held; if it succeeds, attach the watcher and finish. If it rejects, validate the watched holders, leave pages that sort before the request fixed, register avoid-deallocation and fully unfix pages that sort after it, resolve an unknown heap group if needed, sort by group→rank→VPID, and acquire the request plus released pages unconditionally in that order. Rebuild fix counts and watcher chains, balance avoid-deallocation, and unwind the requested fix on error.

Source: src/storage/page_buffer.h:90-164,205-258,282-352; src/storage/page_buffer.c:12186-13063

Redo cleanupReader Q14Lesson 13

14. What does “redo releases through scope cleanup” mean?

Show direct answer

Answer: after the redo fix/gate, log_rv_redo_record_sync() creates a stack scope_exit guard. When that lexical function scope ends—normal fall-through or a later explicit early return—the guard’s destructor calls pgbuf_unfix_and_init_after_check(thread_p, rcv.pgptr). If the pointer is non-null, the helper unfixes once and clears it; if null, it does nothing. The guard is declared after rcv, so cleanup runs while the captured object is still alive.

Boundary: this is C++ RAII, not a background phase, commit, dirtying step, or delayed callback. Paths that skip before guard construction already leave rcv.pgptr null.

Source: src/transaction/log_recovery_redo.hpp:601-668; src/storage/page_buffer.h:64-71; src/base/scope_exit.hpp:28-80
