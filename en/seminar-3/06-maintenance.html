Maintenance adjusts quotas and zones

It attempts adjustment on a 100 ms schedule, but updates only after time and activity gates pass. It performs no page copy, WAL force or file I/O. The source note below records limitations in the backup direct-victim path.

The task has a fixed 100 ms start-to-start target and no ordinary explicit wake. On each gate-open pass it calls pgbuf_adjust_quotas(), then the intended low-activity backup pgbuf_direct_victims_maintenance().

Quota adjustment returns early when private quota is disabled, another adjustment is active, less than 1 ms elapsed, or both activity is below B/4 and less than 500 ms elapsed. Only an accepted pass resets unfix shards, increments adjust_age, consumes LRU hit counters, smooths activity, computes quotas, changes zone thresholds, and demotes overflow beyond those thresholds.

For B=32,768, the high-activity threshold is 8,192 counted final unfixes. Fewer than 81 unfixes on an accepted pass is the low-activity case. With low activity, the executable 500 ms guard normally admits roughly the first 100 ms attempt at or after 500 ms, subject to scheduling.

Cost is O(T) for a normal timing/activity check and O(T + L + D) for an accepted adjustment, plus LRU mutex waits. It performs no page copy, WAL force, or file I/O.

Do not turn an approximate policy into a safety proof

The executable quota guard has 1 ms and 500 ms comparisons, despite a five-minute comment. Hit increments, reset synchronization, reused BCB hit_age and signed-wrap handling require the separate VS-21 investigation. No measured sampling error or intended error bound is established here.

VS-20 is narrower: both maintenance backup loop indices start equal to their saved start, and their initial condition requires inequality. Thus neither body enters in this pinned source. It removes this backup producer's work, while page-flush, zone adjustment and other producers still exist. It does not prove runtime starvation.

backup loop guards · VS-20 / VS-21 owner · sampling evidence. Candidate signals remain hints; protected reuse checks decide safety.

06 · 10 / 13

Account for policy work separately

Let T count unfix-counter shards, L count private/shared LRU descriptors and D count demoted BCBs. Early feature/busy/timing rejection is O(1); summing shards is O(T). An accepted quota pass adds O(L+D) metadata work and LRU mutex waits. No byte copy or page write occurs in quota adjustment. Static quotas remove sampling work but change responsiveness; exact hit accounting adds shared synchronization at access events.

06 · 12 / 13

A coherent replacement: Static quotas with unchanged safety checks

Teaching alternative. Preserve the stated property while changing how actors coordinate.

  1. Assign a fixed share to each active policy domain.
  2. Apply zone and retention policy using that share.
  3. Keep all protected identity, use, dirty and flush checks.
  4. Release a departing domain’s accounting explicitly; leave quota changes to a separate administrative epoch.

Teaching alternative: removes sampling/reset contention but may strand capacity or react poorly to workload shifts. Exact accounting instead requires synchronized per-event updates. Approximate counters reduce bookkeeping; no measured winner or accepted error bound is asserted.
