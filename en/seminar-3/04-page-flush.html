Page-flush: write changes and prepare for reuse

CUBRID page-buffer daemons and PostgreSQL page replacement

Follow one successful page journey first. Later competing schedules each start afresh. This is a source-grounded explanation; inference and unexecuted experiments are marked separately.

04 · 1 / 10

Why write changed pages ahead of reuse?

A database stores data in pages. A page is one piece of that data. To read or change it, the database brings it into memory. A frame is a memory slot that holds one page. The collection of these slots is the buffer pool.

Starting state: P is a page already in memory. A task changed its value from 10 to 20. That change still needs to reach storage. We call a page with changes still to write dirty. Q is another page that a request now needs to read. It is absent from memory.

Assume the request finds neither an empty frame nor a frame it can reuse immediately. It needs a slot for Q. Overwriting P with Q now would discard P’s changes before writing them. P’s changes therefore need a write first.

Page-flush is a background server thread that helps do this writing ahead of reuse. A thread is an execution path inside the server. The requesting thread and page-flush run separately. We will follow a case in which page-flush chooses P as a candidate.

The basic journey is choose a candidate → check its current state → make a copy → write the required log first → request the copy’s write → finish the old work → check permission to reuse the frame. An actual run may choose another page, or another thread may find a frame for Q first.

Who manages the page and its memory slot?

Continue the same case. P is the resident dirty page. Q is the page to read next. F is the address of the control record for P’s frame. This record is a BCB (buffer control block).

ObjectPlain meaning
Page PThe data we want to read or change.
FrameThe memory slot that holds the data.
BCBThe record of which page occupies the slot and which uses or writes remain.
VPIDA page identity made of volume and page numbers. The BCB holds the current page’s VPID.
AllocatorThe code obtaining a frame for the requested page.

The BCB storage lasts while the buffer pool exists, even when its frame is reused for another page. The same address F can therefore describe a different page later. The address tells us where to look. The VPID tells us which page is there.

Several threads can access the same control information. A mutex is a lock allowing one thread at a time to access that information. The replacement list and each BCB have different mutexes. Page-flush releases the list lock after collection, then locks a BCB to check again.

Keep three objects separate: the page is the data, the frame is its slot, and the BCB is the slot’s control record. A surviving record still needs checks of its current page identity and use state.

When does page-flush get a chance to work?

Continue the basic case: Q is absent from memory. The allocator waits after failing to find a frame for Q. This frame waiter can request a page-flush wake. A wake asks a background thread to get a chance to check for work.

Page-flush is created during startup. It does not process candidates until recovery permits that work. This permission check is the boot gate. After it opens, an accepted wake or a timer can provide the next check opportunity.

A wake reported by the waiter causes at least one candidate-helper call once the gate is open. A timer-driven opportunity first checks for frame waiters or high sampled replacement pressure. A timer timeout does not mean a page is written.

Details: first execution, pressure loop and stopping

Imagine a dishwashing helper looking for dishes to wash because clean dishes are running short. If someone is waiting, the helper keeps looking. But if the helper finds nothing to wash in the places checked this time, it steps aside so others can look for clean dishes.

In this analogy, the helper is page-flush. A page, represented by a dish, is a chunk of data; a frame is its place in memory. A dirty page has changes that still need writing toward storage. Page-flush finds and writes these pages. First, server recovery must allow the work. The helper can exist before it is allowed to start.

  1. Look once to start. If the wait result says “work now,” call the candidate-search function once. Another thread waking the worker can produce this result, but so can a wait lasting zero time.
  2. Look again if help is still needed. Repeat if a request is waiting for a frame, or recent request samples show frequent searches for space to hold pages absent from memory. If neither condition holds, end this repetition.
  3. Stop for now if the search found no candidates. If there was both a positive amount to check and eligible lists to search, but no dirty candidates were found, end the repetition even if requests are still waiting. This gives those requests a chance to look again for reusable frames. Having no check allowance or no eligible lists does not produce this stop signal.
Ending this search does not mean all the work is done. It does not establish that every page has been written, that a usable frame is ready, or that the helper itself has shut down. A shutdown request does not immediately interrupt this inner repetition either.
How does the code express these conditions?
  • Permission to work: During recovery, a closed boot gate makes the task return immediately. A non-null daemon pointer means the object exists. That alone establishes neither useful progress nor that a requester takes the synchronous fallback.
  • First call and repetition: When was_woken_up() is true, force_one_run forces one call to pgbuf_flush_victim_candidates(). This result also occurs when task execution consumes the configured period, leaving zero time to wait. Afterward, pgbuf_keep_victim_flush_thread_running() checks for frame waiters or a low sampled hit ratio. The exact integer comparisons are shown above. They estimate replacement pressure from request counters; the 99.9% target is policy rather than a measured probability.
  • No candidates: If check budget check_count_lru and summed list priority lru_sum_flush_priority are both positive but the candidate count is zero, set stop_iteration and break. If either value is not positive, zero candidates alone does not produce this signal.
  • Write success and shutdown: The task ignores the candidate function’s error return. Entering or returning from the function does not establish successful page-image submission. This inner repetition does not check the daemon’s shutdown stop flag. The task must return to the outer loop before the worker can stop; locks, recovery-log forcing and page I/O can delay that return. No shutdown completion deadline is guaranteed.

Setting: what does page_flush_interval change?

A DBA is a database administrator. The online SQL SET SYSTEM PARAMETERS 'page_flush_interval=1000ms' changes the running server’s value. It does not edit cubrid.conf. The deprecated alias page_flush_interval_in_msecs accepts a number of milliseconds.

The interval targets the spacing of execution starts. Task time is subtracted from the next wait. Zero selects wake-only waiting and does not remove the daemon. Changing zero to a positive interval does not wake an already indefinite wait. After an accepted work wake, the next pause reads the new value. A shutdown request instead ends the worker; a stopped looper does not read new wait settings.

The interval determines check opportunities. It determines neither the number of pages written nor a completion deadline. Candidate state, log readiness and I/O still determine each execution’s result.

Source evidence: system_parameter.c:L259-L273 · system_parameter.c:L1806-L1829 · page_buffer.c:L16971-L17049

Q&A · Does interval zero turn page-flush off?

No. It selects wake-only waiting. The worker still exists, and a later accepted wake can give it another task opportunity; useful work also requires the gate and current candidate checks.

Q&A · Will every timer timeout inspect candidates?

Not necessarily. A timer-driven entry needs the relevant allocator pressure or sampled replacement-pressure condition before entering the candidate helper. A timer is an opportunity to check those conditions.

Q&A · Why stop when requests are still waiting?

This search found no candidates to write in the places it checked. Instead of immediately repeating the search just because a request is waiting, let requests look again for reusable frames. That does not guarantee they will find one. Dirty pages may still exist elsewhere.

Q&A · Does an online interval change persist in cubrid.conf?

The described SQL assignment updates running-server parameter values. It does not edit the configuration file, and the new value affects a subsequent looper read rather than retroactively changing the current wait.

Which pages does page-flush inspect first?

Continue the basic case. P still needs its changes written. In this case no request currently uses P, and replacement policy gives it low retention priority. We call that priority cold. It does not mean the page will never be used again.

Replacement policy tracks retention order in LRU lists. LRU3 is their low-priority zone. Page-flush starts at the tail of a selected list and follows this zone, collecting dirty pages.

It first reads pressure and list priorities to divide the inspection budget. It holds one list mutex at a time. Starting at bottom, it follows prev_BCB while inside LRU3 and within the list’s budget. It records each candidate’s BCB address and VPID in an array.

Settings: inspection budget and candidate order

The scan budget determines how many control records to inspect. Sorting determines the processing order of collected candidates. Neither is a count of actual writes.

When sorting is true, qsort() orders the array by volid, then pageid: volume and page numbers. Candidates collected as 90 → 12 → 51 in one volume become 12 → 51 → 90. False omits this array sort. A new order reserves no page and guarantees no write performance.

These two hidden settings are server-wide internal policy inputs. At the pinned revision, a DBA can change the running values online. They take effect when subsequent code reads them and do not edit the configuration file. They are not documented administrator contracts.

Details: why inspection count differs from write count

Example configuration, independent of the page journey: a 512 MiB pool with 16 KiB pages has 32,768 frames. MiB is 1,048,576 bytes; KiB is 1,024 bytes. The default 0.01 ratio yields int(32768 × 0.01) = 327. The compiled boost ceiling is 10, so its ceiling calculation is 327 × 10 = 3270, below the base limit 209715200 / DB_PAGESIZE. Here DB_PAGESIZE is the usable size after subtracting reserved header and trailer areas from the full 16,384 bytes. Input origins and when they change → For ordinary positive samples the ratio is strictly below 1, so boost is below 10 before floating-point rounding. The actual allowance uses the sampled boost and a second truncation; per-list minimum-one rounding still applies afterward. A checkpoint uses boost 1.

At helper entry, the victim-request counter is atomically exchanged with zero and fix shards are summed/reset. The continuation test instead reads the current counters without resetting them. The two checks can therefore see different samples. Startup allocates num_buffers candidate-array entries, one per resident frame; this scratch capacity is distinct from the nominal per-call allowance.

For the ordinary priority calculation, let the actual private fraction be 1 − shared_pages / num_buffers. Its flush share is min(1, actual_private_fraction × (1 − (private_quota_fraction − actual_private_fraction))); shared lists divide the remainder equally, while private lists divide their share in proportion to positive targets. If all private targets are zero and shared pages are at most int(shared_list_count × 50 × (ratio_lru1 + ratio_lru2)), an available invalid frame makes priority computation return early. Without an invalid frame, an assertion-enabled build stops at the assertion; with assertions disabled its fallback uses private LRU3 sizes with private share 1 and target int(private_pages × (1 − 2 × 0.05)). These are source-visible implementation policies, not a fairness guarantee.

What are a clean page and a replacement list?

Imagine copying one notebook page onto a sheet on your desk, then reading or editing that sheet. A page is that unit of data; a frame is its space in memory. If you add a note to the copy, those changes need to reach the storage path before you give its space to another copy.

TermSimple meaning and actual state
Dirty pageA copy with new notes still to send. Its BCB, the frame's control record, has DIRTY set.
Clean pageA page whose DIRTY flag is currently clear. A page that was only read can be clean. A clean page still contains data.
LRU listA linked list using recent-use information to decide “whose space should we give up first?” BCBs are connected by links; CUBRID has several private/shared lists.
List end · tailThe last BCB in the selected LRU list, called bottom. Replacement searches this list's cold zone, LRU3, when the tail is in that zone.
Clean means neither empty nor permission to reuse. Current users, waiters and an earlier copy's ongoing flush also need checking. A clear DIRTY flag alone cannot establish durable disk storage.

Why does taking a clean page leave a dirty page at the end?

Independent starting example: The new page is absent from memory and no free frame (page-sized memory slot) remains. The LRU list, which orders replacement choices, ends in the cold zone LRU3 shown below. Dirty means changes still need writing; clean means DIRTY is clear. Neither page is in use, has waiters or is flushing; the clean candidate passes the protected recheck. No other thread intervenes in this sequence.

Only the selected list's last two entries are shown. The right end is the tail.
MomentEnd of the list
Before removal… → dirty page → clean page (current tail)
After taking the clean candidate… → dirty page (new tail)
  1. The request thread searches. The server thread requesting the new page runs the allocator (code obtaining a frame) to find space that can safely be given up.
  2. It takes the clean candidate. It detaches that BCB (frame control record) from the LRU, securing the frame to return for this request. It releases memory space for the new page without deleting the database page.
  3. It wakes page-flush. The same request thread checks the current tail. If it is dirty and the daemon object exists, it calls wake. The page-flush daemon, a separate background thread, looks for dirty candidates to write and helps prepare later frame supply.
The dirty page was already dirty. Taking the clean entry makes it the new last entry. The clean candidate for this request is already secured. Sending a wake does not make the dirty page immediately written or reusable.

Actual search can also select a candidate away from the tail. The wake condition is a dirty current tail after removal. Remove → check tail → wake → return · Daemon's dirty candidate search

Q&A · Does sorting candidates by VPID reserve those pages?

No. Sorting changes processing order and can favor sequential writes. It adds no protection against fixes, identity changes or other flushes after collection.

Q&A · Will increasing the flush ratio proportionally increase completed writes?

It increases the candidate search budget at the next read. Current guards, WAL readiness, list priority and downstream capacity still determine submissions, so completed writes need not rise proportionally.

Q&A · Can a helper submit more pages than its collected candidate count?

Neighbor batching can add suitable nearby pages. Conversely, many collected candidates can be rejected. Counts of inspected nodes, saved candidates and submitted images measure different work.

Reading the descriptor array differs from following BCB links within one selected list. Read from bottom on the right toward the head through prev_BCB. Clean entries count as visits; remembered candidates are not reservations.

Why check a remembered page again?

Next step in the basic case: P is the chosen dirty page. F is its frame’s BCB address. Page-flush has released the list lock and acquired F’s BCB mutex. It checks the state now, rather than trusting the earlier observation.

Other threads can run while the list lock is released. Another page might occupy the slot. A thread might start using P or begin another flush. The candidate record prevents none of these changes.

A fix records a caller’s use and prevents the frame being reused during that use. The caller returns it with unfix. fcnt counts remaining fixes. The latch state protecting access to page contents also matters.

The BCB’s DIRTY marks changes still to write. FLUSHING marks an earlier image still needing completion handling. The two marks describe different outstanding work.

Question about the presentRequired condition and reason
Is this the chosen page?Saved and current VPIDs must agree: another page can occupy the same address.
Are there still changes to write?DIRTY must be set: another path may already have handled the candidate.
Is an earlier flush outstanding?FLUSHING must be absent: do not start overlapping old and new flush work.
Is its retention priority still low?It must remain in LRU3. Coldness is a policy condition for this candidate path.
Does current use or waiting block it?There must be no fix, connected BCB waiter or blocking latch state.

The basic case passes all these conditions. It next checks the required recovery log and captures an image. During copying, a conflicting writer must be prevented from changing those bytes. Protecting control information with the BCB mutex alone does not automatically provide content protection.

A current fix makes page-flush skip this candidate attempt. It does not take the reader’s permission away. Other flush paths can handle a fixed page with the necessary content protection. These candidate-path conditions are not a blanket prohibition on every flush.

pgbuf_is_bcb_fixed_by_any(bufptr, false) returns true for a positive fix count or a connected BCB waiter. With this call’s false argument, a latch other than PGBUF_NO_LATCH also makes it true. Checking only fcnt=0 is insufficient.

The following branch skips a candidate for a changed VPID, absent DIRTY or outstanding FLUSHING. All three increment num_skipped_already_flushed. Despite its name, it includes identity mismatch and cannot be read as a count of already-written pages.

Inference: releasing the list lock leaves room for other list operations during BCB or storage waits. The implementation handles intervening changes by checking again. This is not a measured claim that every contention cost decreases.

Q&A · Why can fcnt=0 still fail the use check?

The helper also considers attached waiters and blocking latch state. Zero outstanding fixes answers only one part of current eligibility; it is not a complete capture or reuse permission.

Q&A · Why is the counter name insufficient to identify an already-flushed page?

The same increment covers identity mismatch, no longer dirty and already flushing. To diagnose one nomination, observe the actual failing premise under the protected check.

Q&A · Why not keep the list mutex until the write finishes?

Keeping the list lock would block other threads from that list while waiting for the BCB lock or data writing. Multiple locks also need a valid acquisition order. The current design releases the list lock and later checks for changes made in between.

04 · 6 / 10

Why capture a copy and write the log first?

Continue the basic case. P is the dirty page that passed the current checks. Page-flush copies P’s bytes into separate storage. The image is this copy of the page contents. Later changes to the original cannot change that image.

A logged page change also creates a record needed for recovery. That record is the log. WAL (write-ahead log) requires the log to be preserved before the page image is submitted. For logged changes, records through this image’s log position must first be durable.

An LSA (log sequence address) identifies a position in the log. Capturing the page also captures its matching LSA. Matching copied bytes to the correct log position is necessary for recovery ordering.

  1. Protect the bytes against a conflicting writer during copying.
  2. Capture a stable copy and its matching log position.
  3. Make the required WAL durable for a logged image.
  4. Then pass the image to its configured write path. This is submission. Its return result must also be checked.
Requesting a write, getting a successful result and clearing the BCB’s completion state are separate events. On a DWB path, success can mean acceptance into an intermediate buffer. A success return alone proves neither a home-volume write nor physical-device persistence.

A neighbor batch collects suitable adjacent pages around the chosen page. With a stable setting, the default width 8 includes the chosen page plus at most 7 additions; the valid inclusive range is 0–32. Zero or one takes the single-page route. Clean bridging defaults to false. These configurable server-wide policies are read online by the candidate and neighbor helpers; repeated reads within one batch do not form a configuration snapshot. A width limits selected pages, not time spent waiting or the number of batches in one task. The compiled helper has 2 × 32 − 1 = 63 BCB-pointer/VPID positions to address either direction; those positions do not authorize a 63-page batch.

Q&A · Does entering fileio_write prove that the write succeeded?

No. Function entry identifies the attempted route. Its result, later completion bookkeeping and any storage synchronization are separate events that need separate observations.

Q&A · Why might a batch include a clean neighbor?

The optional policy can bridge dirty neighbors with a suitable clean page. It is a batching choice, not evidence that the clean neighbor has a new dirty obligation, and all required current checks still apply.

04 · 7 / 10

Can the frame be reused as soon as the write succeeds?

First finish the basic case. P is the page whose copy was just submitted. Q is the new page waiting for a frame. In this successful case submission succeeded, no one subsequently used or changed P, no other state blocks reuse, and P remains in LRU3 of a shared list used by multiple tasks.

The BCB’s FLUSHING mark says this flush still needs completion handling. That work clears the mark and wakes any thread waiting for this flush. Page-flush can handle it directly. When its branch conditions hold, it can instead queue a BCB pointer for post-flush. Assume post-flush exists and its completion queue accepts the pointer in this successful case, permitting delegation. Chapter 05 defines that queue’s capacity, enqueue failure and local-completion fallback. A queue stores items for later processing; this queue holds control-record addresses, not page bytes.

Post-flush can check present conditions and offer the frame to a waiting request. The recipient also locks the BCB and checks present reuse eligibility. In this successful case the conditions remain valid: the recipient gets the frame and can use it for Q after the old-page removal protocol. The next chapter’s successful case follows offer and receipt in detail.

Check separately for successful old-image submission, completion of that flush, current frame eligibility, an offer and a successful receiving check. Actual code can combine an offer-state change with clearing FLUSHING in one operation. Observing one event does not prove all the others succeeded.

First distinguish the result each waiter needs

Compare two independent requests. A flush waiter (request thread waiting for flush completion) requested a synchronous flush of a dirty page but found another thread already flushing it. A frame-allocation waiter (allocator waiting for a frame) could not find a slot for a new page. An allocator (frame-allocation request thread) obtains a frame to hold a page. The first needs completion of the ongoing flush. The second needs a frame it can use now, even one previously holding another page.

Reset the case to examine a new change

New starting state. G is the earlier copy captured from P and submitted. A writer then changed the resident P again. We call this newer content G+1. G/G+1 are teaching names, not stored source-code generation counters.

The source sets FLUSHING and clears old DIRTY when starting the flush that captures the copy. DIRTY being zero therefore does not prove writing has finished. A later writer can set DIRTY again. Old-image completion clears FLUSHING and leaves this newer DIRTY intact.

Clean means there is no new dirty-change mark. An earlier flush may still be outstanding, so clean alone does not authorize reuse. With new changes or a retained fix, old-flush waiters can wake while Q’s frame waiter continues waiting. Clean is not used here to assert equality of disk and memory.

Details: current reasons to reject offering or reuse

An offer identifies a frame that might be usable now. It does not reserve guaranteed receipt by a particular request. A private list’s quota is the target number of pages retained in that policy domain, not exclusive ownership. This offer check rejects list_count <= quota; only list_count > quota passes that policy gate. Equality is rejected.

Details: why queue capacity does not bound completion time

Queue capacity limits BCB pointers held at one moment. A producer can add more while a consumer removes them, so capacity bounds neither total work in one execution nor elapsed time. The producer inserts items; the consumer removes them.

Count processed completion items, stale allocator records and visited flush waiters separately. CAS (compare-and-swap) changes a shared value only if its old value matches the expected one. CAS retries, BCB/thread mutexes and scheduling add delays. Earlier WAL and page-I/O waits also contribute to total latency.

Q&A · Can an allocator receive a frame from another page instead?

Yes. It needs any currently eligible frame for the missing page. Its registration is separate from a particular BCB’s flush-wait list, so another supplier can satisfy it first.

Q&A · Should completion be undone if the allocator cannot receive the frame?

Failure to offer or receive does not undo successful old-image submission. Completion must still retire the old flush bookkeeping and preserve any current obligations; allocation can retry separately.

Q&A · Can the flush waiter succeed while the allocation waiter keeps waiting?

Yes. Old-image completion can satisfy the first while newer dirtiness, a retained fix or policy rejection blocks frame reuse for the second.

Q&A · Would a larger completion queue guarantee shorter allocation waits?

No. More capacity can retain more outstanding items, but consumers still need scheduling, locks and eligible receivers. Producers may refill it, and an item’s completion may yield no reusable frame.

A private list is a kind of replacement list assigned to work contexts. Its quota is the target number of pages to retain there. It is a retention-policy input used when deciding whether to offer a frame.

Q&A · Is a private-list quota an exclusive ownership claim?

No. It is a retention target for a replacement domain. It can affect whether a cold frame is offered, but does not give one session exclusive access to its page.

Design alternative: what else does reservation require?

This is a teaching alternative. A reservation installed during collection could make competing uses or reuse wait until the decision. It is a new protocol to design, not the pinned implementation.

  1. Reserve the identity under list and BCB protection. Every competing path must check it.
  2. Keep the reservation and required object lifetime while releasing the list lock.
  3. Protect contents, capture matching image/log state, and submit in WAL order.
  4. On cancellation or failure, preserve outstanding write/recovery information. Clear the reservation before releasing the object’s lifetime reference.

Fix, lookup, reuse, retry, cancellation and shutdown paths must all follow the protocol. A long reservation can increase access latency. Sorting storage and comparison work also remain. Holding the list mutex during I/O is another alternative requiring lock-order and contention analysis.

Q&A · If the reader later unfixes, can the saved candidate be trusted again?

It may become eligible again, but that requires another protected current check. The intervening use does not restore all the earlier observations or reserve the page for this flusher.

Q&A · What if the reader changes no bytes?

Its retained fix still changes current use state, so this candidate path rejects it. Dirty-state preservation and caller-use protection are independent reasons for the guards.

Q&A · Does removing only the identity check prove byte corruption?

No. In this constructed variant the remaining current guards can still protect the new page’s image. The demonstrated result is acting on a different page under a stale nomination; stronger damage needs additional evidence.

Q&A · Could a reservation be added only to page-flush?

No coherent reservation follows unless competing fix, reuse, cancellation and teardown paths obey it too. Preserving identity also leaves content protection, WAL and failure cleanup as separate obligations.

What must wait when the required log is late?

Independently of the previous two cases, examine late log progress. WAL is the recovery log that must be preserved before the page image. An LSA identifies its position. The following ordered positions are teaching values, not runtime measurements.

Q08 · The required log position has not been reached

New starting state: recovery has opened the boot gate. An allocator waits for a reusable frame. Page-flush accepts a wake while SLEEPING and starts one pgbuf_flush_victim_candidates() call.

The image needs log records through LSA 300. Durable log currently reaches only 250, short of 300. Observation ends before the helper returns, with zero images submitted so far. Which thread and event should be checked next?

Think, then reveal the explanation

Follow-up: does reaching log position 300 alone prove that a frame for the new page has been obtained?

Log readiness is the next required condition. Current candidate checks, submission, completion and frame receipt still need their own progress afterward.

Compiled retry limit: within one helper call there is at most one synchronous force-and-repeat, only if a direct-victim allocator waits, victim_count > 0, and count_need_wal == victim_count. The second pass checks the same array again. Any other skip reason blocks this all-candidates-WAL condition. The outer task can invoke the helper again; this one-repeat limit supplies no task-wide retry or elapsed-time bound.

The exact log gate is nxio_lsa <= PageLSA: equality still needs WAL; the next-to-write log position must advance past the required PageLSA. This position is not the “last durable record” position used in the scenario above.

How do we check how far the work progressed?

Finish by asking how far this work progressed. “The daemon woke” shows an opportunity to inspect. “Candidates were collected” shows targets for later checks. “Submission succeeded” shows the configured write path’s acceptance boundary. None substitutes for successful present-frame reuse.

  1. Which page was selected?
  2. Which present condition passed or failed?
  3. Which image and log position were used for the write attempt?
  4. What were the submission result and completion events?
  5. Which request was offered which frame, and did it receive it?

Connect these events to distinguish a changed candidate being skipped from waiting on late log or writing. Existing skip totals combine multiple causes. A number alone cannot determine one request’s waiting cause.

Q&A · Is enabling the detailed statistics mask enough to obtain useful counters?

The relevant families must be enabled and collection must be active. Even then, these counters do not create the per-candidate identity and event correlation required for causal attribution.

Q&A · Can high skip totals explain one request’s long wait?

They suggest work was rejected, but mix causes and pages. Connect the request’s allocator wait to candidate identity, rejection, submission and receiving events before assigning the cause.

Q&A · Why intervene on identity, fix count and DIRTY in separate runs?

Each changes a different premise. Isolating them identifies which guard caused rejection and avoids attributing a combined intervention to the wrong condition.
