Why must a saved candidate be checked again?

A request needs a page that is absent from memory, but every frame is occupied. A frame is a memory slot holding one page’s bytes. Page-flush, a background server thread, looks for modified pages it can write so that their frames may later become reusable.

Starting example: P names one resident logical page. Its frame contains modified bytes that still need writing: the page is dirty. F names the address of its buffer control block (BCB), the pool-owned record that tracks this frame’s identity and state. The record’s VPID identifies the logical page currently in the frame.

Page-flush saves the address and page identity while protecting a replacement list with a mutex. A mutex allows one thread at a time to inspect or change the protected state. Page-flush releases the list mutex before taking the BCB mutex. Another thread can use the page or reuse the frame during that gap.

The saved address answers “which control record?” The saved identity answers “which page did we select?” A fresh check under the BCB mutex answers “may we act on its current state?” Keeping the BCB storage alive preserves only the first fact.

Pinned collection and recheck

Q&A · Why not keep the list mutex until the write finishes?

That would extend list exclusion across BCB locking, WAL and storage waits, and requires a valid lock order. The shown design releases list protection and pays for that gap with current-state revalidation.

Which calls can submit the selected image?

Start with a cold dirty page—a modified resident page still needing a write—that has passed the current eligibility checks. Cold means replacement policy gives it low retention priority. The following branch writes one page directly, with neighbor batching and the double-write buffer (DWB) absent. DWB is an optional downstream staging path for page images.

The common helper captures a stable image: copied page bytes that later writers cannot change. For logged changes, it first makes the necessary write-ahead log (WAL) records durable so recovery can interpret the page. It then submits the image to the page writer.

Submission means the image reaches its configured direct-write or DWB acceptance boundary. Entering a helper does not establish success; submission still does not establish that the resident frame is currently reusable.

When does the worker look for useful work?

An allocator is the code trying to obtain a frame for a requested page. When its search finds no reusable frame, it can wait for a direct victim: an eligible frame offered by another thread. Page-flush can wake to help prepare that supply.

The worker runs its task once before its first pause, but a boot gate blocks useful work until recovery permits it. Later, a timer or accepted wake gives another task opportunity. With the gate open, a wake reported by the waiter forces at least one candidate-helper call. A timer timeout enters the helper only if an allocator waits or sampled replacement pressure is high: more than ten victim requests and a hit ratio below the 99.9% policy target.

page_flush_interval defaults to 1,000 ms; zero means waiting indefinitely for a wake. Allocation/victim code calls wake when normal search fails, when removing a clean list bottom exposes a dirty one, or when a selected scan finds no reusable frame control record (BCB).

A wake asks the worker to check; the gate permits task work; current candidate guards permit an image capture. None of these events alone proves submission.

Interval and task guards · Zero-duration wait result

Q&A · Does interval zero turn page-flush off?

No. It selects wake-only waiting. The worker still exists, and a later accepted wake can give it another task opportunity; useful work also requires the gate and current candidate checks.

Q&A · Will every timer timeout inspect candidates?

Not necessarily. A timer-driven entry needs the relevant allocator pressure or sampled replacement-pressure condition before entering the candidate helper. A timer is an opportunity to check those conditions.

Look again, or stop for now?

Imagine a dishwashing helper looking for dishes to wash because clean dishes are running short. If someone is waiting, the helper keeps looking. But if the helper finds nothing to wash in the places checked this time, it steps aside so others can look for clean dishes.

In this analogy, the helper is page-flush. A page, represented by a dish, is a chunk of data; a frame is its place in memory. A dirty page has changes that still need writing toward storage. Page-flush finds and writes these pages. First, server recovery must allow the work. The helper can exist before it is allowed to start.

  1. Look once to start. If the wait result says “work now,” call the candidate-search function once. Another thread waking the worker can produce this result, but so can a wait lasting zero time.
  2. Look again if help is still needed. Repeat if a request is waiting for a frame, or recent request samples show frequent searches for space to hold pages absent from memory. If neither condition holds, end this repetition.
  3. Stop for now if the search found no candidates. If there was both a positive amount to check and eligible lists to search, but no dirty candidates were found, end the repetition even if requests are still waiting. This gives those requests a chance to look again for reusable frames. Having no check allowance or no eligible lists does not produce this stop signal.
Ending this search does not mean all the work is done. It does not establish that every page has been written, that a usable frame is ready, or that the helper itself has shut down. A shutdown request does not immediately interrupt this inner repetition either.
How does the code express these conditions?
  • Permission to work: During recovery, a closed boot gate makes the task return immediately. A non-null daemon pointer means the object exists. That alone establishes neither useful progress nor that a requester takes the synchronous fallback.
  • First call and repetition: When was_woken_up() is true, force_one_run forces one call to pgbuf_flush_victim_candidates(). This result also occurs when task execution consumes the configured period, leaving zero time to wait. Afterward, pgbuf_keep_victim_flush_thread_running() checks for frame waiters or a low sampled hit ratio. Hit ratio estimates the proportion of requests whose pages were in memory from recent request counters. The low-ratio condition requires more than ten victim requests and a hit ratio below 99.9%.
  • No candidates: If check budget check_count_lru and summed list priority lru_sum_flush_priority are both positive but the candidate count is zero, set stop_iteration and break. If either value is not positive, zero candidates alone does not produce this signal.
  • Write success and shutdown: The task ignores the candidate function’s error return. Entering or returning from the function does not establish successful page-image submission. This inner repetition does not check the daemon’s shutdown stop flag. The task must return to the outer loop before the worker can stop; locks, recovery-log forcing and page I/O can delay that return. No shutdown completion deadline is guaranteed.

Q&A · Why stop when requests are still waiting?

This search found no candidates to write in the places it checked. Instead of immediately repeating the search just because a request is waiting, let requests look again for reusable frames. That does not guarantee they will find one. Dirty pages may still exist elsewhere.

How does an observation become a flush decision?

Start with a full pool containing cold dirty pages. A dirty page has modified resident bytes still needing a write. The page-flush daemon (pgbuf-page-flush) looks for dirty pages to write so their frames can later become clean reuse candidates. An LRU list orders pages for retention; LRU3 is its cold victim zone.

A BCB is the control record for one frame; its VPID identifies the logical page currently held there. The daemon calls pgbuf_flush_victim_candidates(), which collects dirty candidates through pgbuf_get_victim_candidates_from_lru(). A saved address locates that record without freezing its later identity or state.

  1. Choose search work. Read pressure, calculate each list’s priority, and divide a scan budget among the lists with positive priority.
  2. Remember possibilities. Hold one LRU mutex at a time. Start at that list’s tail (bottom) and follow prev_BCB while still in LRU3 and within that list’s scan budget. Save each dirty candidate’s BCB address and VPID in a candidate array.
  3. Leave list protection. Release the mutex. The collected array may be sorted by volume and page number before checking candidates individually; no reservation spans this gap.
This search collects dirty candidates for page-flush. Collection supplies possibilities; the next protected check must still establish current eligibility before any image is captured. The policy settings below distinguish scan work from candidate ordering.

Q&A · Does sorting candidates by VPID reserve those pages?

No. Sorting changes processing order and can favor sequential writes. It adds no protection against fixes, identity changes or other flushes after collection.

Which current conditions permit capture?

Continue the collection path: list protection has ended, and page-flush now locks one candidate’s BCB, the frame’s control record. VPID names its current page; DIRTY marks a resident write still owed; FLUSHING marks an earlier image still awaiting completion.

A fix protects a caller’s continued use; fcnt counts fixes. LRU3 is the cold replacement zone. WAL is the recovery log, which must be durable through this image’s log position before its data is submitted.

  1. Check the present. Lock each BCB. Require the saved identity, current DIRTY state, no outstanding FLUSHING, and current cold-zone membership. The fixed-by-any helper also rejects current fixes, attached waiters, or a blocking latch state; raw fcnt=0 alone is insufficient.
  2. Check the recovery log. If the required WAL is not durable, skip the candidate and wake log-flush. In server mode, with an allocator waiting for a direct victim and every collected candidate skipped for WAL, force through their greatest log position once in this helper call, then recheck the same candidates.
  3. Capture and submit. The common flush protocol preserves one stable image and its matching log boundary. It submits through the optional DWB page-image staging buffer or direct I/O, possibly grouping suitable nearby pages into a neighbor batch.
The BCB mutex protects metadata checks. The common helper’s caller-eligibility protocol also excludes a conflicting content writer during capture; a metadata lock alone does not replace that obligation.

Why does the current fix reject this saved candidate?

A reader changes use while identity stays the same

Independent reset: P names a dirty resident page; F is the address of its BCB, the control record for its frame. A names a reader thread that will acquire and retain a fix. Q names a different page used only in the final identity-change comparison.

The page starts in the cold LRU3 victim zone with no fixes (fcnt=0) and no prior flush (FLUSHING=0). Page-flush drops the list mutex before taking the BCB mutex. The reader acts in between. A fix protects continued use; DIRTY=1 means a resident write is still owed.

Here, a fix grants the reader permission to use the page. The reader returns that permission with unfix when its use ends. fcnt counts fixes that have not yet been returned. While the reader retains its fix, the frame cannot be reused for a different page.

“Reject the candidate” means page-flush skips writing this candidate on this attempt. It does not reject the reader’s fix request or revoke the reader’s permission. Why save both an address and a page identity?

Independent illustration: F names a pool-owned BCB address, the control record for one frame. P names the logical page initially held there; Q names a different page that might later occupy the frame. The BCB storage remains allocated while the pool exists, even when the frame’s page identity changes.

Saving F/P records where to look and what page was observed. Later, F/Q would have the same control-record address but a different VPID, so identity comparison rejects the stale nomination. Even F/P can now have a caller fix, a newer dirty image, a hotter zone, or another outstanding flush.

Safety checks protect current callers and outstanding write work. Retention policy prefers cold-zone pages and, at the later direct-offer stage, respects private-list quota. A quota is a target number of pages to retain for a replacement domain; it does not grant exclusive page ownership. Coldness does not certify durability.

Inference: Releasing the list mutex before BCB work limits how long list operations are blocked. The implementation pays for this shorter protected interval by revalidating the candidate later. A saved observation does not reserve its future state.

Q&A · Is a private-list quota an exclusive ownership claim?

No. It is a retention target for a replacement domain. It can affect whether a cold frame is offered, but does not give one session exclusive access to its page.

Which settings change candidate search and sorting?

The page-flush daemon (pgbuf-page-flush) has passed its boot gate, which permits work after recovery, and calls pgbuf_flush_victim_candidates(). It scans the tail of selected LRU replacement lists within their cold victim zone, LRU3, collecting dirty pages that still need a write. The settings below control how much it scans and the order in which it processes the collected candidates.

LRU collection order follows retention policy and can differ from page-location order. A VPID identifies a page by volume number (volid) and page number (pageid). With data_buffer_sequential_victim_flush=true, qsort() orders the candidate array by volume, then page number, before individual rechecks. In an independent example, candidates in one volume collected as 90 → 12 → 51 become 12 → 51 → 90. These numbers are page IDs; sorting changes the processing order without guaranteeing write counts or I/O performance.

04 · 17 / 24

Why is a search budget different from a write count?

Independent size example: A 512 MiB pool with 16 KiB pages contains 32,768 frames. MiB and KiB are binary units: 1,048,576 bytes and 1,024 bytes respectively. The default 1% search ratio first gives an integer budget of 327 checks. A pressure boost can multiply that by at most ten, giving 3,270, still below the 200 MiB cap of 12,800 pages. Checkpoint activity suppresses the boost.

These numbers budget candidate inspection. A checked node can be clean, already flushing, currently in use, warmer than before, or waiting for WAL; it need not produce a submitted image. An LRU list orders a policy domain’s pages for retention. Per-list priority divides the work, and optional neighbor batching can write additional suitable pages.

Q&A · Can a helper submit more pages than its collected candidate count?

Neighbor batching can add suitable nearby pages. Conversely, many collected candidates can be rejected. Counts of inspected nodes, saved candidates and submitted images measure different work.

04 · 18 / 24

Why does queue capacity fail to bound completion time?

After accepted submission, post-flush may consume BCB pointers from a completion queue. Each pointer locates a frame’s control record; it carries bookkeeping work rather than page bytes. A stale allocator record names a request that no longer waits; a flush waiter still waits for its image completion.

The structural work grows with the completion entries actually consumed, stale allocator records examined, and flush waiters visited. Queue capacity limits entries stored at one moment. A producer can refill the queue during a drain, so capacity does not bound the total entries consumed in that execution.

A compare-and-swap (CAS) operation changes shared state only if its expected old value still matches. CAS retries, BCB/thread-mutex contention, and wakeup scheduling add cost beyond those counts. Separately, page-flush’s WAL and page I/O waits add time before completion work becomes available.

Count the work performed and measure the waiting intervals separately. A small candidate budget or bounded queue does not prove a short request latency.
Q&A · Would a larger completion queue guarantee shorter allocation waits?

No. More capacity can retain more outstanding items, but consumers still need scheduling, locks and eligible receivers. Producers may refill it, and an item’s completion may yield no reusable frame.

04 · 21 / 24

Could a reservation prevent the protection-gap race?

Teaching alternative: Start at candidate collection. Instead of saving only an observation, install a reservation: shared state that competing fix and reuse paths must obey until the flush decision ends. This is a proposed protocol, not the pinned implementation.

  1. Under list and BCB protection, reserve the selected identity. Every competing path must recognize that reservation before changing the identity or admitting conflicting use.
  2. Release list protection while retaining the reservation and a lifetime reference that keeps the required objects alive.
  3. Obtain the necessary protection against content writers. Capture one stable image and its matching WAL boundary, then submit it.
  4. On cancellation or failure, preserve or restore pending write/recovery bookkeeping. Clear the reservation before releasing the lifetime reference, so no path observes a reservation on reclaimed storage.

The reservation preserves identity across the gap, but still needs content protection, WAL ordering, and correct completion. Lookup, retry, cancellation, and teardown must all follow the new protocol. Longer exclusion can delay accesses to frequently used pages; the current implementation instead permits intervening changes and checks again.

Optional sorting still needs candidate storage and comparisons growing as candidate count times its logarithm. Holding an LRU mutex while waiting for BCB protection or I/O is a different alternative with lock-order and contention costs; a reservation does not justify that shortcut.

Q&A · Could a reservation be added only to page-flush?

No coherent reservation follows unless competing fix, reuse, cancellation and teardown paths obey it too. Preserving identity also leaves content protection, WAL and failure cleanup as separate obligations.

Protected current checks reject a nomination whose identity or eligibility changed; rejected nominations and slow accepted writes produce different evidence.
Controlled change

Exact observation
Existing skip counters group rejection causes. Add a proposed per-candidate probe for saved/current VPID, the exact rejecting branch, captured LSA (the image’s log position), durable WAL position, and actual submission result.
Falsifier and limit
If the retained identity comparison accepts a different current VPID, the identity claim fails. Removing only that comparison may show wrong selection attribution, while other current guards remain; that result alone establishes no byte corruption.

Enable the relevant statistics collection before interpreting existing counters. The proposed event correlation is additional instrumentation, not information those counters already provide.
