A scan ring names shared frames

CUBRID page-buffer daemons and PostgreSQL page replacement

Repeated hot-set reads + large scan + dirty-page pressure. Constructed schedules reset independently. Functional rationale is Inference unless explicit source intent establishes it.

10 · 1 / 17

Why should a scan revisit its own frames?

A scan reads many database pages in order. A PostgreSQL backend is the server process carrying out that work. A page has a database identity; a frame is a reusable memory slot that holds one page in the shared buffer pool.

Start with a full pool. Some pages are read repeatedly, while a large one-pass scan asks for its next absent page. The scan needs a frame, but its one-time pages may displace pages that the other work needs again. The global clock chooses candidates without recognizing every scan.

An operation can choose an access strategy: NORMAL uses default selection; BULKREAD is for bulk reading, BULKWRITE for bulk writing, and VACUUM for page maintenance. The last three can keep a ring: a bounded backend-local array of shared-frame IDs to try again. This is a reuse preference, not exclusive capacity.

10 · 3 / 17

An ID becomes a claim only after shared checks

For an absent scan page, the backend tries its next ring slot; an empty or unsuitable entry falls back to the global clock. Reusing eligible entries lets later scan pages replace earlier ones within that small set. A ring visit needs a candidate. A pin protects a frame's current page identity from replacement while a backend uses it. The shared refcount records pin protection. Ordinary pins contribute once per backend with any pin; nested pins are tracked privately. Asynchronous I/O can add a separate lifetime pin until that operation ends. The constructed counts below exclude those extra pins. A zero shared count means none of this protection remains.

Usage credit, stored as usage_count, records bounded reuse interest. It is a retention preference, not ownership or an exact access count. The ring accepts only refcount 0 and credit 0 or 1. Credit above 1 suggests other work has used the page, so the ring leaves it alone.

The backend uses compare-and-swap (CAS): add its shared pin only if the observed state still matches. A failed CAS rereads current state; a locked buffer header (its control metadata) must be allowed to unlock before the claim. Success returns a pinned candidate, still holding its old page. Separate page writes and identity-map checks decide later reuse: the map links a database page to its resident frame, and changing it needs protected checks that only the selector is pinned and no dirty work remains: no changed page bytes awaiting a write.

A strategy access can raise zero credit to 1; it preserves an already higher value. It does not keep raising credit above 1. The ring claim itself adds a pin without changing the frame's page identity.

10 · 4 / 17

Normal reuse makes a scanned page less replaceable

Independent constructed reset: A is the backend running a large scan; B is a backend doing an ordinary read. D is a clean shared frame holding a valid page already read by A's scan. A's ring still stores D's buffer ID. Both backends start without pins, and D has usage credit 1. A pin protects the current page identity; credit records retention interest. No I/O lifetime pins are present, and no Clock aging occurs before A revisits the slot.

B takes its first NORMAL pin on D. Shared refcount rises from 0 to 1, and credit from 1 to 2. B then releases its last pin: refcount returns to 0, but credit stays 2. When A revisits its slot, the ring rejects D because credit is above 1 and falls back to global Clock selection. If B still held a pin, that protection would reject the ring claim regardless of credit.

The extra credit can protect this formerly scanned page even after the ordinary reader leaves. Later Clock visits can age it. Credit does not store client identities or count distinct past users: one backend can also earn it through repeated release and first-pin cycles.

Does this give the ordinary reader permanent ownership?

No. The local ring owns only its ID array, and current shared state controls each claim. Credit gives retention preference until it ages; a held pin protects the page identity for the duration of use. Neither gives a permanent reservation or a CUBRID private-to-shared list migration.

Policy limit: the one-eighth-of-pool ring cap applies to each strategy object, not all concurrent queries together. Multiple rings and global fallback can create substantial combined pressure. The cap is neither a per-client quota nor a fairness guarantee; overlapping IDs also make total slot counts differ from distinct frame counts.

10 · 5 / 17

Retaining a frame ID does not retain its old page

Compared with CUBRID: a ring belongs to one operation and holds shared-frame IDs. A CUBRID BCB is a pool-owned control record for a frame; private LRU membership places BCBs in a retention domain with a quota target for its share of cached pages. Neither gives exclusive page access. Ring help depends on the operation choosing that strategy.

Q19 · Two rings, one frame ID

Independent constructed schedule: A and B are two backends, each running a scan with its own ring. F is one shared frame, initially holding page R. Page S is the absent scan page that A wants. Both backends' slots store F's buffer ID. A pin protects the current page identity; ordinary backend pin contributions make the shared refcount, and credit records retention interest. This schedule has no I/O lifetime pins.

A completes the protected replacement of R with S in F, then releases its pin. B's array has not changed. B now visits F: it is clean (no pending page write), has refcount 0 (no pins), and credit 1. A ring accepts that shared state only by successfully adding its pin; the slot itself preserves no page identity.

Prediction: What does B's unchanged slot say about the current identity?

Discuss, then reveal

It still refers to frame F, which now holds page S. It cannot promise that page R remains. B can attempt the current frame's protected ring claim, then perform any required writeback and identity replacement. Its unchanged array does not undo A's work.

10 · 6 / 17

BULKREAD can escape a costly dirty ring entry

The selecting backend holds a pin, protecting the frame's current page identity. The selected frame may be dirty: its current page has changes that still need a page-file write. The backend first tries a share-exclusive content lock without waiting. This prevents conflicting content changes while it inspects and writes the page. If the lock is unavailable, it releases the pin and retries, avoiding a possible cycle of backends waiting on one another.

Write-ahead logging (WAL) requires the log describing a permanent page's changes to be durable before writing those page bytes. The page's LSN is the log position through which that obligation must be met. BM_PERMANENT marks a permanent buffer; unlogged pages can carry fake LSNs, so this test excludes them.

Selection provenance says where the candidate came from. from_ring is true only when this selection reused a ring entry; global fallback sets it false. For a dirty permanent ring candidate whose LSN still needs WAL flushing, StrategyRejectBuffer rejects only BULKREAD, after verifying that its current slot still names the candidate.

Rejection sets the local slot to InvalidBuffer (empty), then the backend releases lock and pin and retries. Shared dirty data and page identity remain. The next visit advances to the next slot; encountering an emptied slot later forces global fallback. Clearing costly entries prevents a ring full of them from endlessly cycling, but fallback can still require WAL and a page write.

10 · 7 / 17

The strategy changes what follows the same selection

Q20 · Same candidate, different strategy

Reset to three independent runs: each allocating backend uses a BULKREAD, BULKWRITE or VACUUM ring. Each selects a dirty permanent page (BM_PERMANENT) from its ring. Before selection it has no pins and usage credit 1, a retention preference. Selection adds the backend's pin, protecting page identity. The content lock, which stabilizes bytes during the write, is acquired without waiting. No other backend intervenes; the modeled counts exclude separate I/O lifetime pins.

The page's LSN identifies log records that are not yet durable, so writing the page requires a WAL (write-ahead log) flush first. The visible rule is specific: BULKREAD can clear and reject this local ring entry; BULKWRITE and VACUUM do not take that rejection. Those paths may flush WAL, then write the page. All still need current-state checks before removing its old identity.

Prediction: How can the three strategies differ after selection?

Discuss, then reveal

BULKREAD empties its current slot with InvalidBuffer, releases lock and pin, and retries selection. It does not invalidate the shared page. BULKWRITE and VACUUM can preserve the WAL order and flush the page, then attempt protected invalidation. NORMAL has no strategy ring. A completed write still cannot replace the final checks for a sole pin and no newly dirty work.

What does each dirty-candidate run start with?

Independent constructed reset: R is a shared frame whose ID is in a backend's ring; it holds a dirty permanent page. This R is a frame label, unlike the page name in the earlier schedule. H is another frame, pinned by a different backend throughout. Each strategy run starts with its own copies of these premises; no separate I/O lifetime pins contribute to the shown counts.

The backend claims R from initial refcount 0 and credit 1, then obtains the content lock without waiting. A pin protects the page identity; the content lock stabilizes its bytes and LSN, the required log position. The WAL log is not yet durable through that LSN.

Only BULKREAD rejects this dirty permanent ring candidate. It releases lock and pin after setting its local slot to InvalidBuffer (empty). BULKWRITE and VACUUM can flush WAL, then write the page and attempt protected identity removal. That final attempt still requires a sole pin and no dirty work.

A retry advances to the next ring slot. Clearing one slot therefore does not guarantee immediate global fallback. The next trace's terminal BULKREAD lane describes fallback when an emptied slot is encountered again. Clearing each costly entry prevents endless rejection of a ring full of them.

10 · 11 / 17

Ring size must allow time to release and finish I/O

A pin protects the current page identity until its backend fully releases it. A ring that cycles back too quickly can encounter its own backend's pins or reads still in progress. More slots provide separation, but also leave more frame IDs available for the operation to revisit. Ring size is a policy input, not a count of exclusively reserved frames.

At this pin, GetAccessStrategy returns no ring for NORMAL. BULKREAD starts at 256 KiB, adds space for asynchronous I/O using io_combine_limit and effective_io_concurrency, and limits that expansion using GetPinLimit. BULKWRITE's factory size is 16 MiB; VACUUM's is 2 MiB. These are factory choices, not every caller's actual ring size.

GetAccessStrategyWithSize converts the caller's requested KiB to slots and caps each strategy object at NBuffers / 8, one eighth of the shared pool's frame count. This per-ring cap does not limit all queries together or establish fairness. A zero request creates no strategy object. GetAccessStrategyPinLimit allows look-ahead pins up to the full BULKREAD ring, or half for other strategies; callers combine it with their other limits.

10 · 12 / 17

Other scan policies move the costs elsewhere

Remove only the ring: the scan uses normal global clock allocation and credit rules. Retain pin, content, WAL and identity checks. A scan larger than the pool can displace pages used between scan passes, producing later misses. This is possible cache pollution, not evidence of corruption or a universal slowdown.

Teaching alternative: separate private scan pool. Reserve different memory for scan page bytes. That isolates capacity but can cache the same database page twice. Writers and normal readers then need a coherence rule so the two copies cannot disagree; idle private capacity may be wasted.

Teaching alternative: shared admission/history policy. Classify one-touch pages and give them less retention. A policy such as 2Q remembers repeat use through queues and page-identity history. It can help without per-operation hints, but requires extra state and synchronized updates. No measurements here rank these alternatives for this workload.

10 · 13 / 17

A bounded ID array does not bound all allocation work

Let r be the number of slots in one backend-local strategy object. Each slot stores a shared-frame ID; r does not count exclusive frames or all pages read by the scan.

The local array uses O(r) ID memory. Advancing, reading or replacing one slot takes O(1) local work. Claiming its frame can add shared compare-and-swap retries (the observed state must still match) or waits for a locked control header to unlock. An unsuitable slot adds global clock visits; a dirty fallback candidate can add content-lock retries, WAL flushing and page writes.

Removing only the high-credit rejection changes retention policy. Removing the pin check allows replacement during another backend's protected use. Those changes have different consequences even though both remove a ring gate.

To eliminate page writes from the allocating backend, another actor must guarantee clean supply, or the request must wait or fail when supply is absent. Moving the write to a background actor still leaves the I/O obligation. Neither r slots nor ring success proves a latency bound.

Credit can reject a frame even with no pins

Independent reset: F4 is a shared frame whose ID appears in two backends' local rings. It now has no pins protecting its current page identity, and usage credit 2 records retention interest. A local ring entry grants no ownership, and a ring claim requires current refcount 0 and credit at most 1.

D30 · Prediction: Can both rings reuse F4 because their IDs are local?

Reveal the ring argument

No. Current credit above 1 rejects both ring attempts. If credit were at most 1, one successful shared-state CAS claim would add a pin; the other backend would have to re-evaluate the changed refcount. Removing only the credit gate changes retention policy; removing the pin gate threatens another user's protected lifetime.

Follow-up: BAS_BULKREAD WAL rejection empties its own current slot so repeated costly dirty entries eventually lead to global selection. The guard requires a dirty permanent candidate from the ring whose LSN needs WAL flushing. It neither clears the shared dirty page nor changes every strategy's policy.

10 · 16 / 17

A scan partition needs shared identity and failure rules

Teaching alternative: reserve actual frame capacity for scans while keeping one authoritative identity map, the lookup from each database page to its resident frame. This changes capacity coordination; it is not the implemented ring protocol.

  1. Reserve a bounded frame partition (a set of frames assigned scan capacity) before scan admission. If no safe capacity is available, wait or fail rather than bypassing a pin or overwriting dirty data.
  2. Use the same identity map across partitions. When a requested page already resides elsewhere, use that resident identity or migrate it through a protected protocol; do not silently create an independent writable copy.
  3. Before migration or reuse, respect existing pins and content protection, preserve dirty data with its WAL order, and recheck current state while protecting the identity-map change.
  4. On scan exit, release the reservation and rebalance idle capacity. On error or cancellation, preserve valid page identities and dirty obligations before undoing reservations.

Here r is the number of slots in a ring used for comparison. Those r local IDs reserve no exclusive frames. A partition reserves real capacity, but adds reservation, migration and rebalance rules and may strand idle space. A 2Q/history policy instead adds queues and remembered page identities.

What would refute the ring argument?

Unexecuted experiment proposal: at the pinned PostgreSQL revision, record build, pool size, log durability, I/O concurrency, ring size, pin limits and request order. A CUBRID comparison also records log/DWB settings.

Hypothesis
Eligible frames let a scan revisit a bounded local set of IDs. Interference or sizing can force fallback.
Controlled change
Fix pool and repeated-read/scan sequence. Compare NORMAL with supported strategies under recorded settings. Test two rings naming one frame as an independent reset.
Exact observation
pg_stat_io groups I/O by strategy context, not each rejection reason. Proposed ring-claim, StrategyRejectBuffer and fallback probes record slot ID, shared pins/credit, ring-versus-global provenance and WAL need. Compare slots with distinct frames; record final identity retirement separately.
Falsifier and limit
Replacing a page on a ring ID alone despite another backend's pin refutes lifetime protection. Fallback from unsuitable frames fits the conditional hypothesis. Aggregate reuse counts do not prove final retirement.

Here r counts ring slots, not exclusive frames or all scan I/O. Probe logging changes timing; record its overhead.
