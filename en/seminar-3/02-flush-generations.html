DIRTY records the gap between memory and disk · continued

A flush pays that propagation debt. It helps a checkpoint limit recovery work, helps shutdown move dirty pages out, and makes a clean unfixed frame eligible for replacement. Flush is not commit, unfix, eviction, or page deletion. A successfully flushed page may remain in memory.

Shortest mental model: DIRTY means “there is page work to do.” FLUSHING means “a copied version is doing that work now.”
02 · 5 / 31

The writer must be allowed to continue

The flush copies the current resident bytes into private memory. We call that frozen copy G. After the copy is made, another writer may change the resident page again. We call the newer resident bytes G+1.

G and G+1 are reasoning labels, not counters stored in the BCB.

02 · 7 / 31

Two facts can be true at the same time

When flush starts, it marks FLUSHING and clears the old DIRTY. This does not lose the work: the flusher now owns copy G. The cleared DIRTY bit becomes an empty signal slot for the next writer.

  1. G starts: DIRTY=0, FLUSHING=1.
  2. A writer changes the resident page: DIRTY=1, FLUSHING=1.
  3. G succeeds: clear only FLUSHING.
  4. The surviving DIRTY=1 correctly says G+1 still needs a flush.

FLUSHING also blocks a second competing flush. Otherwise an older write G could finish after a newer write G+1 and overwrite it. A synchronous caller can wait for the current flusher instead of starting another one.

Verified mechanism: concurrent-flush exclusion and waiting are at pinned page_buffer.c:8809–8901; the flag helpers are at 16077–16126.

02 · 8 / 31

Log durability and page propagation are different

A transaction can commit before every changed page reaches its home location. WAL makes that safe.

A flush is about the page image. WAL is about the log needed to explain that image. For a logged non-temporary page, the log must be forced far enough before the copied page image is submitted.

One says “how new”; the other says “how far back” · continued

Example: disk has P through 80. P changes at log 100, then 140, then 170 without any completed flush. Its page LSA moves 100 → 140 → 170. Its oldest_unflush_lsa stays 100, because the change at 100 is still not represented by a completed page propagation.

Memory aid: page LSA is the right edge of the copied image's log history. Oldest-unflush is the left edge of the unpaid dirty history.
02 · 11 / 31

The boundary selects work by its beginning

Suppose the checkpoint boundary, named flush_upto_lsa, is 150. The checkpoint asks: “Does this still-unpropagated dirty run reach back to 150 or earlier?”

P is selected because 100 ≤ 150. It writes the current image, not a historical image from 100.

  1. oldest_unflush_lsa=100 ≤ 150: this checkpoint should try to flush P.
  2. The current copy contains changes through page LSA 170.
  3. Before writing that copy, force WAL through 170.

What if oldest_unflush_lsa > flush_upto_lsa?

That is not a violation. If oldest is 200 and the checkpoint boundary is 150, this dirty run began after the checkpoint's chosen boundary. The checkpoint may skip it. Another background or pressure-driven flush may still write it early; that is safe extra work if the normal WAL rule is followed.

Checkpoint selection and WAL ordering use different values. “Newer than the checkpoint boundary” does not mean “unsafe to flush.”

Eight source steps, four human-sized actions

  1. Claim the job: validate the BCB, set FLUSHING, clear the old DIRTY.
  2. Freeze G: copy the bytes, copied page LSA, and oldest-unflush LSA; clear the resident lower bound so G+1 can get its own.
  3. Send G safely: release BCB protection, force WAL through the copied page LSA, then use DWB or direct write.
  4. Close the job: reacquire protection, clear FLUSHING, and wake waiters. Do not erase a newer DIRTY.

DWB changes the physical write route

The private copy isolates G from later writers. DWB is an optional protected destination for that copy. When DWB is unavailable or the page is temporary, the page-buffer path uses direct fileio_write() instead. Flush still happens, and logged non-temporary pages still obey WAL.

02 · 21 / 31

Finish G without losing G+1

On success, completion clears only FLUSHING. If a writer created G+1, its DIRTY bit and new oldest-unflush value remain for the next flush.

On ordinary DWB/direct-I/O failure, the path clears FLUSHING, restores the captured DIRTY debt and oldest-unflush lower bound, wakes waiters, and returns failure. The work remains visible and retryable.

Review question: after every success or failure exit, which generation owns DIRTY, which operation owns FLUSHING, and what lower bound must checkpoint still see?

The copied bytes and their log boundary travel together

The helper assumes its caller has established eligibility and holds the BCB mutex. It marks FLUSHING, clears the old DIRTY, captures the image and its page LSA under protection, saves/clears the oldest-unflush bound, and unlocks before WAL and submission. 02 · 25 / 31

Safe alternatives move the cost

Teaching alternatives: Hold exclusive byte access through WAL and page write: coherent image, one generation at a time, but writers now wait for storage. Or use immutable/versioned page images and an explicit generation acknowledgement: preserve overlap, but manage version lifetimes and retire only acknowledged debt.

For page size B and k concurrent flushes, copying requires O(B) byte work per image and O(kB) staging space across active calls, with stack or DWB-slot ownership depending on the branch. WAL latency, encryption, DWB capacity and I/O time are additional costs. Exclusive serialization saves staging but adds an I/O-length protected interval; that is not a measured latency comparison.

Removal with no replacement: If a device reads mutable bytes while a writer changes two related fields, it may observe a mixed image. Keeping byte exclusion through the transfer is a valid replacement. Removing WAL ordering instead permits a data image whose explaining log is absent after a crash.

02 · 26 / 31

Safe alternatives move the cost · continued

Removing only competing-flush exclusion also changes ordering: submit old G, submit newer G+1, let G+1 finish first and G finish last at the same home page. With no ordering replacement, old bytes can win. Serializing flushes or a version-aware ordered-write protocol avoids this constructed schedule.

02 · 27 / 31

WAL and DWB cover different failures

WAL orders recovery information before the logged page image. It does not by itself make a multi-sector page write atomic. Under a torn-write assumption, direct home writing can leave a page made of old and new sectors. DWB supplies a staged recovery image through its own write/recovery protocol; disabling DWB is not automatically incorrect if storage atomicity or another repair mechanism supplies that requirement.

DWB acceptance, completed home-volume writing, OS write return and durable storage are distinct boundaries. Neither the copied image nor FLUSHING certifies device persistence. Concurrent identity reuse must remain excluded while this protocol owns P.

Ordinary I/O failure restores dirty/oldest-LSA bookkeeping; early TDE/DWB-slot returns are the separate candidate VS-12, not a proven universal rollback. DWB ownership and pinned evidence.

02 · 28 / 31

WAL and DWB cover different failures · continued

Downstream mechanism: DWB staging write and synchronization precede home writes; acceptance need not flush a partial block; recovery requires a valid staged image. Loss of both images or ineffective storage synchronization remains outside this argument. Full-page WAL images are a primary-source alternative torn-page repair technique with extra WAL volume.

02 · 30 / 31

A coherent replacement: Exclude writers through propagation

Teaching alternative. Preserve the stated property while changing how actors coordinate.

  1. Acquire byte exclusion and record the matching page LSA.
  2. Keep exclusion while forcing WAL and submitting the unchanged bytes.
  3. On success, retire only that image’s debt before admitting the next writer.
  4. On error, preserve DIRTY and its oldest obligation, release temporary state, then release exclusion.

Teaching alternative: saves a separate image but extends writer exclusion through log/storage latency. Versioned immutable images are another choice with explicit version retirement. Neither solves torn writes without a storage/recovery protocol.
