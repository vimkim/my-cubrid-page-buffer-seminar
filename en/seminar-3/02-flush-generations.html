One page, two generations

CUBRID page-buffer daemons and PostgreSQL page replacement

Repeated reads, a large scan and writes compete for a finite pool of memory frames. Each constructed schedule below has its own starting state. Source explains mechanisms; performance benefits remain workload-dependent.

02 · 1 / 33

A full pool needs a safe way to write changed pages

Starting situation: A request thread needs page Q, which is absent from memory. Every frame—a memory slot for one page—is occupied. Page P is already in a frame. Nobody is using it, but its memory contents include changes that have not yet been sent to page storage: it is dirty.

A flusher is the thread that sends those changes toward storage. A writer is a thread that modifies the memory contents. The difficulty is that a writer may change the page again while the flusher is sending an earlier copy.

Writing the earlier copy must preserve the newer work. A later reuse decision must still check the frame's current identity, use, waiters, flags and replacement policy.

This is a constructed starting situation. The examples below restart from their own stated values; they do not form one continuous execution.

A flush sends a stable page copy toward storage

Starting state: A writer has changed a page in memory. The page's stored contents have not caught up. Losing memory now would lose those bytes unless recovery can reconstruct them.

A flush captures a stable page image—a copy of the page bytes at one protected moment—and sends that image toward persistent page storage.

Writing a page and releasing a page finish different jobs

Starting state: A modified resident page still needs propagation. Its BCB records this with DIRTY. A flush works on a copied image; FLUSHING records that the image's page-buffer flush operation is outstanding.

A checkpoint records a recovery boundary and tries to propagate relevant dirty work so restart has less log history to replay. Shutdown also tries to move dirty pages toward storage. Under replacement pressure, successful flush bookkeeping can make a clean, unused frame a candidate for later reuse.

Unfix releases a caller's granted use; commit completes a transaction's durability protocol; eviction removes a page from its frame. Flush completes a different job, so a flushed page may remain in memory. Cleanliness alone does not authorize reuse.

Clearing the old dirty signal makes room for a new one

Independent schedule: A resident page starts dirty, with no flush underway. G will name its protected copy; G+1 will name the writer's later resident change. DIRTY tracks resident work and FLUSHING tracks the copied-image operation.

  1. The flusher claims G: it sets FLUSHING=1 and clears the old DIRTY. The stable copy now carries the old work.
  2. After capture protection ends, the writer changes the resident page and sets DIRTY=1 again. Both flags are now set.
  3. G's submission succeeds. Under BCB protection, completion clears FLUSHING only.
  4. The remaining DIRTY=1 keeps G+1 visible for a later flush.

The flusher also prevents a second competing flush. Without ordering, an old image could finish after a newer image and overwrite it. A synchronous caller—a caller that needs to wait—can wait for the current flush instead of starting another.

02 · 8 / 33

The recovery log must survive before its page image

Starting situation: A transaction changes a permanent page and records information needed to recover that change in a log. Memory can disappear in a crash, so the log must survive before the database allows the logged page image to reach page storage.

WAL means write-ahead logging: make the corresponding recovery log durable before submitting the logged page image. Durable means retained across the stated crash and storage assumptions. An operating-system write return alone does not establish it.

Commit completes a transaction's durability protocol, including its required log. The home pages may still be older; recovery can replay their logged changes after a crash. Page propagation is a later, separate job.

Before a logged non-temporary image is submitted, the flusher forces WAL through its copied page LSA—the position of the latest logged change included in that image.

Checkpoint rechecks keep unfinished work in recovery’s view

Starting situation: The checkpoint collected a dirty page, but the page may change before the checkpoint reaches it again. A collection result is an observation, not permission to use stale state.

Under the BCB's metadata mutex, the checkpoint rechecks the page identity, current DIRTY flag and oldest_unflush_lsa. After waiting for a flush, it checks whether new work still reaches its boundary and may flush again. That minimum keeps recovery's redo start—the position where replay begins—from claiming more progress than page propagation supports.

02 · 21 / 33

FLUSHING does not track fsync progress

Independent starting state: G is a stable image captured from a dirty permanent page. DWB (double-write buffer) will accept it into a memory slot; the home volume is its normal data file. The WAL is the recovery log, which must be durable through G's log position before submission. Successful dwb_add_page(), after that WAL requirement, establishes acceptance; copying into a reserved slot alone does not.

FLUSHING tracks the page-buffer job. It is a flag in the buffer control block (BCB), the frame's management record. It is set before image capture and WAL forcing, then cleared when the configured submission succeeds and BCB completion runs, locally or through post-flush. It does not track entry into or return from fsync() or fdatasync(), operating-system calls requesting file synchronization.

FLUSHING=0 does not certify home-volume synchronization. With DWB, BCB completion can clear it before either staging or home writes occur. Conversely, WAL synchronization or a synchronous full-block DWB flush can occur while FLUSHING is still 1. The flag and the syscall therefore have no one-to-one relationship. The synchronization wrapper selects fsync() when metadata is required and fdatasync() otherwise.

Verified mechanism: capture, WAL, submission and BCB completion · DWB acceptance and synchronous full-block fallback · WAL synchronization · synchronization wrapper.

02 · 27 / 33

A safe replacement must keep bytes stable and acknowledge the right work

Independent design choice: A flusher wants to write a changed resident page while other threads want to modify it. The implemented stable copy permits overlap. If we remove that copy, we need another way to keep one internally consistent image during the transfer.

Serialize writers: Hold exclusive byte access through WAL forcing and the page write. One image stays unchanged, but writers wait through log and storage latency. This can save a separate staging image at the cost of a longer protected interval.

Versioned images: Publish immutable page versions with matching log metadata. Keep each version alive until its I/O ends, and acknowledge only that version's work. This retains overlap but adds lifetime and retirement bookkeeping.

Copying costs work proportional to page bytes; staging memory grows with page size and the number of simultaneous flushes. Stack buffers or DWB slots own the images depending on the branch. Encryption, WAL waiting, slot capacity and I/O add costs; no latency ranking was measured.

Removal without replacement: I/O consuming mutable bytes can read one field before a writer changes it and another field afterward, producing a mixed image. Keeping exclusion through the transfer repairs that problem. Removing WAL ordering creates a different failure: after a crash, data can survive without its explaining log.

DWB first preserves staging, then propagates home pages

Independent downstream walkthrough: DWB (double-write buffer) has accepted a captured page image into a slot. A slot is a staging position; a block groups slots for writing. Acceptance can return while a partial block still waits for flushing.

  1. The block flush writes the staging file and requests synchronization.
  2. After staging synchronization, it writes the home pages and synchronizes the affected volumes through its flush/helper protocol.
  3. On recovery, it replaces a corrupted home page only when a valid retained staging image is available.

This argument assumes effective storage synchronization and a valid retained repair image. Losing both images is outside it. A different repair technique stores full-page images in WAL, adding log volume.

A no-copy alternative keeps writers excluded through I/O

Independent teaching alternative: A permanent resident page is dirty, no competing flush exists, and another writer wants access. Replace the separate snapshot with exclusive byte access held throughout WAL forcing and page submission. This is a design proposal, not a claim that CUBRID uses this protocol.

  1. Acquire content exclusion and record the page LSA that matches the unchanged resident bytes.
  2. Keep writers excluded while forcing WAL through that LSA and submitting those bytes.
  3. On success, retire that image's obligation before admitting another writer.
  4. On error, preserve DIRTY and its earliest unfinished log position, release temporary state, then release exclusion.

On every exit, the design needs a defined owner for cleanup and waiter release. It saves a separate image but makes writers wait for log and storage latency. Immutable versions are another option with explicit version retirement. Both still need a storage/recovery protocol for torn writes.
