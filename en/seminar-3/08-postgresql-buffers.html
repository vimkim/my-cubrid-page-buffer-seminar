PostgreSQL: keep pages resident and protect their bytes

CUBRID page-buffer daemons and PostgreSQL page replacement

Frequently reread pages share a finite pool with a large scan and pages with unwritten changes. Each constructed question or trace starts independently; its events do not carry into the next example. Source behavior is pinned below. Performance explanations are reasoning, not measurements.

08 · 1 / 17

Why must a resident page stay the same page?

A request repeatedly reads a small set of pages while a large scan asks for new ones. PostgreSQL’s shared pool is full. Some resident pages have unwritten changes, and some are still in use. Before loading a missing page, the server must find a frame it can safely reuse.

A logical page is a named block of database data. A frame is a memory slot holding one page’s bytes. The shared buffer descriptor, metadata comparable in role to a CUBRID BCB (per-frame control record), stores that frame’s current page identity and control state. Reuse changes which page occupies the frame; the descriptor’s array position stays the same.

A backend is a PostgreSQL server process. If it keeps an address for later use, replacement must not put a different page at that address. Coordinating reads and writes to the current page is a separate responsibility.

08 · 2 / 17

How does a pin keep the page resident?

A backend (server process) wants to use a page already loaded in a shared frame, the memory slot for its bytes. It acquires a pin: a recorded use that prevents replacement from reusing that frame for a different page. A content lock separately coordinates operations on the page’s bytes.

If the backend pins the same frame again before releasing its earlier pin, the uses nest. Its private reference count records how many releases it owes. For ordinary backend pins, the shared reference count records one contribution from each backend with outstanding uses. Asynchronous I/O, a file operation still running, can add its own lifetime pin, so the shared count is not always a backend count. “Private” describes the bookkeeping; the frame and its bytes remain shared.

Retention credit gives an unused page extra chances before selection. The descriptor stores this preference as usage_count. Under the default strategy, a backend’s first pin after its private count reaches zero adds one credit, up to 5. Nested pins add no credit. Credit grants no right to use the page.

08 · 3 / 17

How can one page stay protected for several clients?

A client request runs in a backend, a PostgreSQL server process. Several backends can use one page in a shared memory frame. Its descriptor is the metadata record for that frame, and its shared pin count records contributions preventing reuse. Each backend privately records its own nested uses. The shared count protects owners without naming them.

The pool-wide clock hand is a shared cursor choosing the next descriptor to inspect. The pin count belongs to each descriptor; it is not one count for the whole pool. Retention credit gives an unused page extra chances. A strategy ring is a bulk operation’s preferred list of shared-frame IDs to reuse; it does not own separate page storage.

Our detailed mechanisms use the pinned 20devel source. PostgreSQL 18.0 also has private/shared pins, Clock and rings, but its locking and I/O details differ. These mechanisms support concurrent clients; their names do not establish throughput, tail latency or equal capacity per client.

08 · 4 / 17

Why can the shared count exceed the number of backends?

A backend (server process) pins a shared frame, the memory slot for one page, and queues an asynchronous read. This file operation loads page data while the caller can continue other work. The I/O subsystem needs that frame until the operation ends.

Before submitting the I/O, the subsystem takes an extra lifetime pin of its own. If the backend fails while the I/O runs, cleanup may release the backend’s pins. The extra contribution keeps the shared count positive after that use disappears. Completion releases the I/O pin.

Shared reference count records lifetime contributions. With no I/O in progress, our ordinary pin examples count one contribution per backend with outstanding uses. During asynchronous I/O, an extra contribution means the count need not equal the number of backend processes or client sessions.

PostgreSQL 18.0 also takes an I/O lifetime pin. Its pinning_backends observation field reads the shared count, so its name alone does not remove that qualification.

Q16 · What do three nested pins add?

Q16 · Private nesting and shared owners

Independent starting state: D is the shared descriptor for one loaded, clean page. A and B are different PostgreSQL server processes that will use D’s frame. Neither holds a pin, a recorded use preventing frame reuse. No I/O occurs in this schedule, so the shared count records pinning backends. It and retention credit (extra chances before replacement) start at zero.

Rules for this schedule: Each backend’s first pin adds one shared contribution and one credit under the default strategy, with credit capped at 5. Its nested pins add only private release obligations. Its final release removes its shared contribution; release does not spend credit.

Events: A pins three times without releasing. B then pins for its first time. A releases all three pins. No replacement scan spends credit, and no other change occurs.

Prediction: After each event, what are the shared count, A’s private count and retention credit?

Discuss, then reveal

After A’s first pin: shared=1, A private=1, credit=1. After its two nested pins: shared=1, A private=3, credit=1. B’s first pin gives shared=2 and credit=2. After A releases all three: shared=1, A private=0, credit=2. B’s outstanding pin still prevents reuse. Credit is capped at 5; it cannot count all calls over the page’s lifetime.

Q17 · Does a pinned address permit reading?

Q17 · Who protects the bytes?

Independent starting state: A is the PostgreSQL server process calling a helper that replaces a CUBRID READ fix. B is another server process that pins the same loaded page in a shared frame. The helper pins that frame and returns its address to A; it acquires no content lock.

Access rules: A pin preserves the frame’s page identity. For the ordinary initial page inspection in this example, a reader also needs a shared content lock. A writer’s exclusive content lock excludes that read lock while it changes the bytes.

Event: B holds the exclusive content lock and is changing the page. A immediately starts reading the returned address.

Prediction: What must the helper’s contract require before A reads?

Discuss, then reveal

The helper must obtain the compatible read lock before returning permission to inspect bytes, or explicitly require A to obtain it before reading. B’s exclusive lock makes A wait. The contract must also name who releases the lock and pin. A pinned address alone does not reproduce the page-content protection supplied by CUBRID READ fix.

08 · 8 / 17

Why can nesting stay private?

A backend (server process) already pins a resident frame to prevent reuse, then a second part of its operation needs the same page. Replacement already sees this backend’s shared contribution. Recording the second use privately is enough to keep that contribution until both uses finish.

The private reference count therefore records release debt: how many pin releases this backend still owes. The resource owner is PostgreSQL’s cleanup record for resources acquired by an operation; it remembers each pin so normal release or error cleanup can account for it.

The pinned implementation updates shared state on the first pin and final private release. A nested pin updates private bookkeeping instead. This avoids another shared counter update on each nested use while preserving the replacement exclusion. It does not establish a measured speedup.

Which state answers which question?

Consider a loaded page in a shared frame. Several backends (server processes) may pin it to prevent reuse, and one backend may have several nested uses. Replacement and byte access need different facts, so no single counter can answer every question.

StateQuestion it answers
Private reference countHow many releases does this backend owe? Its resource-owner cleanup record also remembers each acquisition.
Shared reference countWhich lifetime contributions remain? Ordinary backends contribute pins, and asynchronous I/O can hold an extra pin. A nonzero count makes Clock skip the frame.
usage_countHow many extra chances should an unused page receive? This bounded retention credit records neither ownership nor an exact access time.
Content lockWhich byte operations may proceed together? The access path chooses the required lock mode while keeping its pin.
08 · 10 / 17

Why is zero credit insufficient for reuse?

A resident frame can have zero retention credit while a backend (server process) still holds a pin that prevents reuse. Zero credit says that the replacement policy owes the page no extra chance. It says nothing about whether a caller still uses that page.

Safety rule: Clock skips a frame with a nonzero shared reference count, regardless of its credit. Only when both values are zero may the selector atomically add its own pin and claim a candidate. Claiming precedes the later checks that remove the old page identity so the frame can hold a different page.

Keep the pin while the caller needs the page identity. Acquire the content protection required for each byte operation. Releasing a content lock between operations does not end the caller’s pin.
08 · 11 / 17

How do concurrent requests find and use the same page?

Two backends (server processes) request the same page, which may still be loading. A mapping table connects each page identity to a shared frame, the memory slot for its bytes. The descriptor controls that frame’s current state.

  1. Find it: mapping locks protect page lookup and identity publication. The table is split into partitions with separate locks, so different partitions can proceed independently.
  2. Keep it: pin the found frame before releasing the mapping lock. A backend’s first pin adds its shared contribution; its final private release removes that contribution only.
  3. Read or change it: I/O coordination lets callers join or wait for an existing read. Once the page is ready, its own content lock coordinates byte operations.
  4. Replace it: atomic selection claims a candidate. Protected invalidation later requires clean state (no unwritten changes) and no pin beyond the selector’s own pin.

These are verified mechanisms at 20devel. A hot descriptor can still suffer atomic retries, content-lock waits or I/O waits. The protections do not promise low tail latency or equal capacity per client.

08 · 12 / 17

How far ahead should each backend pin pages?

Several backends (server processes) scan large inputs. Each wants to read future pages early, but a pin prevents a frame (the memory slot for one page) from being reused until released. Reading too far ahead can tie up many frames before the caller consumes their pages.

A read stream queues pages for a caller and manages this look-ahead. In pinned 20devel, it uses an advisory per-backend pin budget: a suggested allowance derived from the shared-frame count, NBuffers, and the maximum possible backend population, including auxiliary processes.

The stream combines its strategy limit with the backend’s remaining allowance. If the allowance is too small, it reduces look-ahead until pins are released. When the stream holds no pinned buffers, it can allow one more even with zero remaining allowance, so it can deliver a page and continue.

This controls outstanding pins in participating read paths. It is not a universal hard pin cap or a promise that every user owns an equal resident working set. It is different from a CUBRID private-LRU quota.

What breaks if replacement cannot see the owner?

Independent removal example: A is a PostgreSQL server process with two nested pins, meaning two outstanding uses that prevent reuse. H is the page already resident in the shared frame. Between byte operations, A releases its content lock but keeps both pins because it needs H again. No I/O or other owner is present.

Clock examines the shared descriptor array with a wrapping index called the clock hand. It skips nonzero shared reference counts. At shared count zero and retention credit zero, CAS (compare-and-exchange) adds the selector’s pin only if the state still matches what it inspected.

Remove only the shared contribution while retaining private counts. Replacement now sees zero even though A still needs H. A later reuse can put a different page at A’s retained address. Acquiring a content lock later cannot restore H’s identity. The next trace compares this defect with a design that counts every pin in shared state.

Could every pin update the shared count?

Teaching alternative: A backend (server process) needs the same loaded page several times and pins its frame to prevent reuse. Instead of compressing those uses into one shared contribution, count each acquisition in shared state. Replacement must still see a positive count until every user releases its uses. The selector is the process choosing a replacement frame; it keeps its own protective pin during the final identity change.

  1. Find and revalidate the requested page identity under protection before acquiring a use.
  2. Atomically add one shared contribution for every pin, including nested pins. Record the matching release obligation privately.
  3. Acquire the required content lock before each byte operation.
  4. On release or error, remove exactly the contribution for that acquisition. Retire the old identity under protected checks only when it is clean and no lifetime contribution beyond the selector’s own pin remains, including any I/O pin. The selector keeps its own pin or claim through this protected change.

Three nested acquisitions now require shared updates for all three pins and releases. PostgreSQL’s implemented design changes shared accounting only at that backend’s first and final boundaries. The alternative preserves lifetime but adds shared atomic work. Keeping private counts while removing all shared contributions loses that protection.

How would we test the pin rule?

Independent proposal, not an executed result: A is a PostgreSQL server process with nested pins (uses preventing reuse) on one loaded page. B is another server process trying to select that frame for replacement. Start with a clean page, zero retention credit, no I/O and no other owner.

Record the full pinned revision, build, shared-pool size, I/O and workload settings. Hold the event order fixed and record credit changes. A first default-strategy pin may add credit, so rejection alone cannot prove ownership.

Hypothesis
A’s shared contribution remains until its final private release.
Controlled change
A pins twice and releases once. B attempts selection. Compare the implemented rule with a teaching model that removes only the shared contribution.

Rejection alone does not identify its cause. The next screen specifies the protected transitions needed to distinguish pin protection from other reasons.

Which observation would disprove the pin rule?

Continue the proposed experiment: server process A has released one of its two pins and still needs the resident page. Server process B tries to select its frame. A pin is a use preventing frame reuse; the shared contribution should remain until A’s final release. The page starts clean with zero credit, no I/O and no other owner; record any later credit changes.

Exact observation
Propose probes at PinBuffer, final UnpinBufferNoOwner and the Clock claim. Correlate private count, shared count, usage_count, claim result and the protected page-to-frame mapping. Record probe overhead. A content-lock wait observes byte coordination rather than pin-release debt.
Falsifier and limit
Reuse for a different page identity while A retains a valid pin would contradict the lifetime rule. Selection rejection alone does not identify its cause. Counting every acquisition changes shared atomic work; this proposal establishes no timing advantage.
