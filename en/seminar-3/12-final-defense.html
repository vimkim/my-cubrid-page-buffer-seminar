A completed image can leave the allocator waiting

Q is the request thread waiting to allocate a frame: one memory slot that can hold a page. The pool is full. A page is a logical storage identity; its frame holds the current bytes, and a BCB is the stable metadata object paired with that frame. Reusing the same addresses must not preserve the old page identity by accident.

A flush may finish an earlier copied image while another caller changes the resident page or keeps using it. “The flush succeeded” leaves three questions: which image completed, whether this frame is reusable now, and why the overall allocation waits.

Name the image and exact storage boundary in a receipt. Check current reuse under the appropriate protection. Attribute a system-wide stall only after observing the competing paths.

12 · 2 / 22

Each boundary protects a different responsibility

A caller needs a logical page, not merely an address. Its resident frame stores bytes; the BCB stores identity and state. A fix in CUBRID, or a pin in PostgreSQL, protects use against frame reuse. A latch or content lock separately controls access to the bytes.

  1. The caller acquires use protection and compatible byte access before reading or changing the page.
  2. A logged mutation creates recovery-log and data-propagation work. Release ends use protection; it does not finish that work.
  3. The flusher submits stable bytes with the matching WAL boundary: required recovery log before data. Completion covers that image alone.
  4. After a gap in protection, selectors, completion consumers and receivers recheck the current identity, users and pending work under their own guards.
  5. The reuse path safely detaches the candidate and removes the old identity mapping before binding the frame to another page.

A writer's release leaves its new update pending

Independent CUBRID counterexample. Q is the allocator waiting for a frame. F is a memory slot holding logical page P. G names the image captured at log position 120; G+1 names contents after a later writer logs at 180. These names describe generations for reasoning, not stored counters. P's identity remains the same. For this server-mode case, the later writer is a vacuum worker: a background thread that cleans up obsolete data. P is a permanent page, in a nontemporary volume, in shared LRU3, the cold replacement zone.

The BCB is F's stable metadata object. A fix protects current use; a write latch controls mutation. DIRTY records resident work still needing propagation; FLUSHING records the outstanding captured image. The field fcnt counts fixes. The vacuum worker's unfix lowers fcnt but does not clear DIRTY. Its final unfix skips the ordinary LRU3 boost; DIRTY or FLUSHING also prevents an early direct offer. Thus F remains in LRU3 for the completion check. No other actor moves it, and the edit requests no special list movement.

The flusher captures stable bytes and their matching log position while holding the BCB mutex and excluding competing WRITE owners. WAL preserves the required recovery log before image submission. After capture protection ends, a later writer can change the resident bytes while the old copy is submitted.

The Global “done” lane models a constructed final-reuse protocol: old-image completion authorizes retirement while bypassing current DIRTY checks at offer, receiving and final retagging. All other image, WAL, identity, use and policy requirements remain. Deleting only the consumer's DIRTY check in the pinned source still encounters downstream DIRTY guards. The trace compares this modeled shortcut with the implemented rejection and separate image/current-state receipts.

Teaching design; no new execution. F names an occupied frame, P its current page identity, and G the captured image of that page. The BCB remains the frame's metadata object. The allocator wants to reuse F, but another caller can still use or change P after capture protection ends.

Give each receipt a distinct meaning: “image G accepted,” “G completion bookkeeping finished,” “current F reserved,” or “old mapping retired.” A receipt is evidence of the named event. Record the page identity, image, exact completion boundary, protected interval and cancellation owner.

A reservation can authorize current use only if every competing lookup/use path obeys its exclusion. Image acceptance grants no such exclusion. A later receiver must either retain that reservation or revalidate current identity, use and dirty state under protection.

12 · 6 / 22

Removing a check moves work and waiting elsewhere

Compare protocols under the same workload. Holding a reservation continuously keeps new users out through the protected interval. It reduces concurrency and needs cleanup if its owner abandons the request. Rechecking later allows intervening use, but pays for metadata reads, synchronization and retries.

Completing work in the foreground makes the requesting caller pay the CPU and I/O wait. Background completion pays elsewhere and adds queue, scheduling and worker-lifetime dependencies. WAL waits for the required recovery log; storage waits for the chosen submission or persistence boundary.

Count useful scan, image-copy, queue and state-transition work separately from lock, WAL, storage and scheduler delay. A quiet-schedule work bound does not bound concurrent request latency. Throughput claims need a controlled workload, storage configuration, use-protection durations and repeated measurements.

Keep image receipts separate from current reuse claims

Teaching replacement, independent of the diagnostic case. F is a frame holding page identity P. G is a captured copy; G+1 names resident contents after a later change. Neither generation label is a stored counter. The BCB remains the stable metadata object, and the allocator needs permission to reuse F.

  1. Give the submitted image a ticket naming identity and generation. Specify whether its receipt means accepted, written, or durable at a named storage boundary.
  2. On completion, retire only that ticket's outstanding work. Keep any later resident dirty work.
  3. For current reuse, acquire protection and check identity, users and dirty work anew. Retire the old mapping only when these conditions and the chosen policy permit it.
  4. On error or cancellation, preserve the old identity and pending work, release the ticket/reservation correctly, and make the remaining obligation discoverable for retry.

Explicit ticket/version lifetimes and cancellation ownership add metadata. Continuous serialization is another coherent choice: every lookup/use path must obey exclusion through completion and retirement, at a concurrency and wait cost. Either design must preserve WAL (matching recovery log before data), stable image bytes, later updates, identity lifetime and a path to progress.

Follow the identity through use, release and reuse

A page is the logical object requested by the caller. A frame is its current memory slot; a BCB is the stable metadata object paired with that slot. This recap is a responsibility sequence, not another constructed execution.

  1. The caller finds the page needed for a record operation. One operation may visit several pages.
  2. The buffer resolves that identity to a resident frame and BCB, loading on a miss. Fix protects use lifetime; a compatible latch controls access to bytes.
  3. Matching unfixes repay every fix. Ordinary final unfix can update admission or retention policy; it promises neither eviction nor persistence.
  4. Replacement chooses a domain and candidate, then checks current safety under protection. Dirty changes need propagation. Background work can help without guaranteeing an immediately reusable frame.
  5. Safe detachment and old-mapping removal allow the same frame to carry a new identity. Stable frame/BCB addresses do not preserve the old page.

H1 and H2 name the repeatedly read logical pages of the earlier hot set. Their continued residency depends on the reuse schedule and policy state. The comparisons showed different ways to remember reuse and distribute costs; they established no speed ranking.

Every current reuse decision needs its own guard

WAL preserves the matching recovery log before data submission. The complete journey is request → identity lookup → protected acquisition → use or logged mutation → release → image/WAL propagation → current eligibility → protected reuse.

Daemons help move work forward. Clocks and rings help find or retain candidates. None of these replaces the guard that protects the current page identity, active users and pending updates at reuse.
