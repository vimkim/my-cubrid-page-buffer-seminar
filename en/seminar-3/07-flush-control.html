Tokens and the flush-control daemon

Page credits, their refresh, and one writer’s progress.

07 · 1 / 4

What is a token, and when is it spent?

A token is one page of accounting credit. Participating file writers share an integer balance called the token bucket. They charge one token per page after the operating-system (OS) write succeeds. Changing a value in memory does not spend a token.

Why keep this balance? Data writes can compete with reads and log writes for storage time. The balance lets CUBRID pace later writer progress: an ordinary writer uses available tokens and may wait when it cannot account for all the pages it already wrote. The flush-control daemon is a background thread that supplies the next allowance; it does not write the pages.

This is soft pacing on participating paths. FILEIO_WRITE_NO_COMPENSATE_WRITE skips this accounting; the pinned double-write buffer (DWB), a page-image staging mechanism, uses that mode. A writer holding the log critical section, a lock protecting log progress, consumes available tokens but does not wait for a deficit. Tokens therefore do not impose a limit on all storage writes.

How does the daemon refresh the balance?

The flush-control daemon refreshes the shared page-credit balance on a nominal 50 ms schedule. Once startup permits its work, the first execution only records a timestamp. Each later execution:

  1. Measures actual elapsed time since the previous task finished. A nominal 50 ms period does not guarantee 50 ms of elapsed time.
  2. Calculates the allowance using fixed-rate or adaptive control, described below.
  3. Replaces the balance: tb->tokens = gen_tokens. Here tb is the shared bucket and gen_tokens is the new allowance. If 3 tokens remain and the new allowance is 7, the balance becomes 7; the remaining 3 are discarded.
  4. Wakes waiting writers. They retry their outstanding charges against the new balance.

A mutex, a lock allowing one balance update at a time, protects both refresh and consumption. Waiting writers sleep on a condition variable, a shared notification mechanism; sleeping releases the mutex. Waking gives a writer another chance to obtain tokens, not a promise that enough remain.

How many tokens does it generate?

A token allowance is the number of page credits published for an interval, not an instruction to write that many pages. adaptive_flush_control=yes selects adaptive mode and is the default; no selects fixed-rate mode.

Fixed-rate mode

max_flush_size_per_second supplies a byte rate. CUBRID converts it to pages/s using IO_PAGESIZE, the size in bytes of one I/O page. It then calculates new tokens = floor(pages/s × actual elapsed seconds); floor discards the fractional part.

Example: the default fixed rate is 10,000 pages/s. An actual 50 ms interval gives 10,000 × 0.05 = 500 tokens. An actual 100 ms gives 1,000. This setting is used only in fixed-rate mode; it does not cap the adaptive allowance.

Adaptive mode (default)

The previous allowance is the number of credits generated last time; unused tokens are the credits still unspent. A buffer pool is the memory area holding database pages. A dirty page is one whose changes still need writing. The dirty-page suggestion reflects how far their count exceeds half the pool and how much it has risen above a retained earlier count.

State at refreshChange to the previous allowance
Unused tokens remain; dirty suggestion is positiveKeep the allowance.
Unused tokens remain; dirty suggestion is zeroSubtract 10% of the unused tokens, rounded down.
No tokens remainAdd the larger of the dirty suggestion or 50% of the previous allowance, rounded down.

Finally, raise the result if necessary to the compiled 40 MiB/s minimum credit rate, converted to pages and scaled by actual elapsed time. At 16 KiB/page and 50 ms this floor is 128 tokens.

Example: with a previous allowance of 128, zero unused tokens, and a zero dirty suggestion, add 50% × 128 = 64. The next allowance is 192; it already exceeds the 128-token floor. These are constructed calculations, not measured write rates.

One writer, from allowance to waiting and refill

One continuous constructed schedule: a controller that has passed its timestamp-only execution uses fixed-rate mode at 140 pages/s, so each actual 50 ms refresh sets 140 × 0.05 = 7 tokens. One ordinary writer uses the participating file-write mode, holds no log critical section (the lock protecting log progress), and charges promptly after each successful operating-system (OS) batch. No other writer competes for tokens. This small rate is chosen to show the arithmetic.

  1. 1. 0 ms: the daemon sets seven tokens

    Result: The writer consumes 2 of the new 7 tokens; 5 remain.

The shortage begins after all nine pages have been written. Waiting delays later work; it does not undo those writes.
