When and how to pace writes

Cleaning can move the bottleneck to storage. The pinned CUBRID path charges tokens after an OS write; the token daemon therefore paces subsequent work rather than admitting that completed write. Interval replacement, accumulated credit and no pacing have different burst behavior. None replaces WAL or protected reuse.

Tokens are replaced each update, not automatically accumulated. A ten-return escape is not a wall-clock bound when the underlying condition wait is untimed. Log-critical-section callers need their own bypass analysis.

Consume credits for pages already written

The bucket is a mutex-protected integer balance shared by file writers. On the FILEIO_WRITE_DEFAULT_WRITE path, after a successful OS write, fileio_compensate_flush() requests as many tokens as pages written. A writer spends available tokens immediately; an ordinary writer that is short may wait for the next condition broadcast. The write being counted has already happened, so a token controls subsequent progress rather than authorizing that write.

About every 50 ms, the daemon replaces the credit balance and wakes waiting writers. It does not accumulate credits by adding to the old balance. Bypasses make this soft pacing rather than a strict I/O ceiling.

Initialization creates the bucket with zero tokens and a condition variable. If it fails, this daemon is absent and token acquisition becomes a no-op; page flushing still works. The first gate-open task pass records the time origin only. A later pass measures elapsed time and creates the first interval allowance.

Consume credits for pages already written · continued

  1. Lock the token bucket.
  2. Read and clear consumed-token plus page-write statistics.
  3. Compute an adaptive or configured interval budget.
  4. Replace tokens; do not accumulate the new budget onto the old balance.
  5. Reset interval statistics and broadcast the condition variable.

At 16 KiB/page, the adaptive 40 MiB/s floor is 2,560 pages/s, about 128 tokens per 50 ms. The non-adaptive internal 10,000-page/s default would be about 500 tokens per 50 ms. Actual values depend on elapsed time, integer truncation, and feedback.

07 · 6 / 13

Credits are not a strict I/O ceiling

Credits are consumed after successful OS writes. Some write paths bypass compensation and some callers do not wait, so credits are neither universal write authorization nor a strict throughput ceiling.

fileio_write() and fileio_write_pages() call fileio_compensate_flush() after a successful OS write only in the default compensated mode. FILEIO_WRITE_NO_COMPENSATE_WRITE skips the bucket; DWB-related write paths can choose this mode. A normal participating caller may wait for budget but can escape after at most ten condition-wait returns/retries. Each wait is untimed, so this does not bound elapsed time. A caller holding the log critical section accounts demand without waiting for missing tokens.

This is soft pacing rather than correctness authorization or a strict throughput ceiling. CPU accounting is O(1); condition broadcast and the scheduling of awakened waiters scale with their count.

Q15 · Different callers after a write

Constructed starting state: Ordinary writer A and writer B holding the log critical section each succeed at OS writing, then reach compensation with insufficient tokens. B keeps the critical section and no new budget has arrived.

Prediction: Which branch determines how their progress differs?

Discuss, then reveal

LOG_CS_OWN separates the paths. A can wait on the token condition and retry, with a ten-retry escape. B accounts demand and returns without waiting for missing tokens. Both writes already happened. This is soft pacing of later progress, not write authorization or a durability contract.

07 · 8 / 13

WAL, checkpoints and DWB have separate roles

Log flush handles WAL, while checkpointing advances recovery-related writeback. Foreground flush and DWB paths also exist separately. They are not additional instances of the four page-buffer daemon roles.

log-checkpoint has its own configurable timer, 360 seconds by default, and selects data pages using oldest_unflush_lsa. log-flush makes append-log pages durable for WAL. Foreground and WRITE-owner paths can copy a data-page generation. DWB's helper daemons operate downstream after a stable image crosses the DWB seam. None belongs to the maintenance or token-control lane.

D28 · Can unchanged quota and ten retries prove “nothing happened”?

A profiler samples quota=64 twice, adjust_age advances, and one writer remains asleep after its first condition wait. A reviewer calls the policy frozen and the wait bounded by ten periods.

Challenge, then reveal the bounded answer

An accepted epoch can reproduce quota 64 while consuming samples and updating time/zones. A retry increments only after condition wait returns. The first untimed wait can last arbitrarily long under adverse scheduling or absent notification, so ten is not ten periods.

Follow-up: “Should we repair the skipped backup immediately?” First attribute impact by producer under supported conditions. Source anomaly and measured progress impact are separate claims.

Discriminating observation: Record accepted epochs, input samples, resulting zones, assignments by producer, refill times and condition returns. Compare static/adaptive quotas with a controlled changing workload. Existing Q14–Q17 preserve the prior policy and pacing challenges.

A coherent replacement: Reserve pacing credit before writing

Teaching alternative. Preserve the stated property while changing how actors coordinate.

  1. Before OS writing, reserve an explicitly priced byte/page allowance.
  2. Wait only outside locks needed by replenishment or log progress.
  3. Perform the WAL-respecting write after reservation.
  4. On cancellation before submission, return credit; after a partial write, account actual work under a defined error rule.

Teaching alternative: can constrain admission but adds reservation and cancellation state; a log/credit dependency cycle can deadlock unless excluded. Accumulated credit permits saved bursts, interval replacement bounds each epoch’s allowance, and absent pacing shifts storage competition. None is a measured strict device-I/O ceiling.

What observation could refute this explanation?

Unexecuted experiment proposal. Record the full pinned revision, build, pool/log/DWB/I/O settings and workload before interpreting a result.

Hypothesis
Interval replacement changes bursts after OS write; retries do not bound elapsed time.
Controlled change
Keep write sequence and refill schedule fixed; compare replacement, accumulated-credit and pre-write reservation teaching designs. Separate ordinary and log-CS callers.
Exact observation
Observe OS write return, post-write consume, token replacement/broadcast, condition wait start/return and exit reason. Compensation stats alone omit preceding write latency.
Falsifier and limit
Charging before the observed OS write would contradict this pinned-path claim. Ten returns with one unbounded wait provide no finite latency theorem; use timing only as a recorded observation.
