01 · 1 / 6

How can a full pool serve a new request?

Repeated reads keep a hot set useful; a large scan asks for new identities; writers leave dirty pages. The finite pool is full when request Q arrives. This is the recurring workload, not one recorded execution. Every interleaving starts from its own stated checkpoint. The first two sessions established BCBs, fix debt and private/shared LRU; now we ask who can turn those objects into usable supply.

Safety preserves identity, active use and logged dirty obligations. Progress requires an actor able to discharge the blocking predicate. Retention and pacing optimize costs under stated workloads. A policy score cannot substitute for a safety guard.

01 · 2 / 6

A page identity is different from its memory slot

P is a page identity; a frame is the slot holding its contents. Later, the same frame can hold Q. Its BCB records which page it currently represents and whether it is in use.

VPID identifies the page, the BCB holds control information, and the frame holds data. fcnt counts granted fixes across threads; holders record each thread’s fixes. The structures page develops these relationships.

One request for page P

1

Request P

Look up whether P is resident.

2

Make room on a miss

Use an unused frame, or safely remove a candidate and read P into its slot.

3

Obtain access

After fix succeeds, use the contents with the granted latch.

4

Read or modify

A modifying caller handles the required logging and dirty marking.

5

Finish using it

Unfix the page. This does not itself mean flush or commit.

6

Write back and reuse

Dirty contents are written with WAL ordering: make the corresponding log durable first. Once safe, the frame can be reused for another page.

This summarizes an ordinary request for an existing page. Not every request writes or evicts it, and flushing can occur in another execution context.

One request for page P · continued

Q01 · Permission to reuse

Constructed starting state: A proposed change publishes reusable=true immediately after final unfix makes fcnt=0. Its allocator retags the frame without any other checks.

Prediction: What is the smallest schedule that challenges this approval rule?

Discuss, then reveal

A writer logs a change and marks P dirty, then performs its final unfix. fcnt becomes zero while the preservation debt remains. Retagging now loses that debt. A protected reuse decision must also check current flags, identity, waiters and policy eligibility. Release ends use; generation propagation ends a different obligation.

Optional follow-up: Which event ends use, and which ends preservation work?

01 · 5 / 6

A coherent replacement: Serialized foreground acquisition

Teaching alternative. Preserve the stated property while changing how actors coordinate.

  1. Keep identity and use checks.
  2. When supply is dirty, select a protected eligible image and satisfy its WAL obligation.
  3. Write and complete that image, recheck current state, then retry acquisition.
  4. On failure, retain dirty debt and release the request’s temporary resources.

This teaches a coherent foreground design, not a promise that every server fallback has this exact path. I/O moves into request latency; the need for a clean protected frame remains.

01 · 6 / 6

What observation could refute this explanation?

Unexecuted experiment proposal. Record the full pinned revision, build, pool/log/DWB/I/O settings and workload before interpreting a result.

Hypothesis
Dirty supply rather than request count explains this constructed full-pool stall.
Controlled change
Keep pool size and request sequence fixed; vary whether an eligible dirty frame has an actor able to propagate it.
Exact observation
Correlate allocation wait entry/exit with protected eligibility and actual producer assignment; aggregate clean count cannot certify an available frame.
Falsifier and limit
Falsify attribution if the waiter is blocked elsewhere while useful eligible supply exists. This does not prove fairness or workload-wide throughput.
