Four roles, four progress obligations

CUBRID page-buffer daemons and PostgreSQL page replacement

Repeated hot-set reads + large scan + dirty-page pressure. Constructed schedules reset independently. Functional rationale is Inference unless explicit source intent establishes it.

03 · 1 / 20

What remains blocked?

The pool is still full. Propagating bytes, completing BCB state, adapting retention, and pacing writes produce different outputs. Four roles are one implementation policy; the necessary obligations survive even if a replacement design combines the workers. A wake requests another check, while shared predicates and queues describe the work.

Notification is not retained work. Stop is not cancellation or joined termination. Shared work must remain discoverable, and every worker must stop accessing its resources before they are reclaimed.

Pinned transition

Retained work here means shared RAM state that survives a wake until a task checks it. It does not mean crash-durable storage.

03 · 2 / 20

Could the request thread do everything itself?

It could. But if reading S3 also requires writing S4 first, context B pays for another page’s preparation before its own read can proceed. A separate thread can prepare candidates ahead of demand. The performance benefit depends on workload and I/O conditions.

  1. Prepare on demand: request S3 → find no free slot → handle S4’s write → recheck reuse safety → read S3.
  2. If a candidate was prepared earlier: another thread handles S4’s write → the request for S3 arrives later → recheck safety → reuse the frame.

A background thread that repeatedly performs and waits for such work is a daemon here. It runs inside the DB server, not as a separate server process. Foreground means the request thread; background describes execution separate from that request.

Could the request thread do everything itself? · continued

Question: could one daemon do all the work in sequence? That is a possible design. CUBRID separates four responsibilities with different work triggers and waiting conditions. They are not four stages that every page traverses. In particular, maintenance and flush-control do not pass pages to the next worker.

Four questions distinguish the responsibilities · continued

Wake is a hint, not a durable event: the generic waiter accepts wakeup() only while it is sleeping. If the task is already running, the call is not stored for its next pause. Each task therefore rechecks shared pressure or queue state when it executes.
03 · 9 / 20

Post-flush and flush-control do not write the page again

File-I/O token bucket: a shared balance of page-sized credits. Participating writers spend credits after a successful OS write; when the balance is empty they may pause before continuing. Flush-control periodically replaces the balance, so this is soft pacing rather than permission to perform the write. See the exact producer, consumer, and bypass rules →
Page-flush hands completion to post-flush: page submission has finished, but in-memory BCB bookkeeping remains. Under allocator pressure, page-flush may queue only the BCB pointer for post-flush to finish; it does not pass page bytes or request another write. 03 · 10 / 20

Each daemon works and waits independently

The four daemons are background threads with distinct roles. A timer or wakeup provides an execution opportunity; current state determines whether useful work follows.

create_daemon() creates one managed execution context and one std::thread. Its loop is simple: execute the task, ask its cubthread::looper how long to pause, then execute again. The four names are therefore four independent control loops, rather than interchangeable workers pulling dirty pages from one queue.

The task runs once immediately after construction. A fixed period is a start-to-start target: the looper subtracts the previous execution time. A 100 ms period does not mean “finish work, then always sleep another 100 ms,” and it does not guarantee useful work on every pass.

03 · 12 / 20

Work starts after recovery and stops before pool teardown

The server creates the threads during recovery, but useful page-buffer work waits for the boot gate. Normal shutdown stops them before pool teardown. Stand-alone mode does not create these four threads.

  1. The page-buffer pool, LRUs, queues, and monitors are initialized first.
  2. Server boot creates the four daemon threads before log recovery finishes.
  3. Their immediate task calls see the boot gate closed and return without useful page-buffer work.
  4. Boot opens the gate after recovery. Opening it does not itself wake every sleeper; a later timer or ordinary work wake lets each role observe the open gate.
  5. Normal shutdown sets each looper's stop flag, wakes a sleeper, joins the OS thread, retires its task/context, and clears the pointer.
  6. log_final() and pool teardown happen after the page-buffer daemons have stopped, so no daemon outlives the shared state it touches.

Stand-alone mode creates none of these four threads. When background page-flush is unavailable, the relevant requester can perform victim flushing synchronously.

Q06 · Stop is not yet join

Constructed starting state: A shutdown proposal frees BCB and queue storage immediately after setting stop, then wakes and joins. It does not check whether a daemon is inside its task body.

Prediction: What fact must be proved to approve this resource lifetime?

Discuss, then reveal

No daemon may still access the storage when it is freed. Setting stop only asks the loop to end; a running task can still touch shared state. Wake releases a sleeper, and join establishes that its thread has ended. Keep required shared storage alive through join and task/context retirement.

03 · 17 / 20

Stop must reach a joined thread before resource release

Pool structures exist before the daemon group. Threads can already run during log recovery, but every task first tests the boot gate. Enabling the gate is not itself a wake of every role. Removing the gate allows task accesses during recovery; the resulting failure depends on the shared state being changed by recovery, rather than merely on a thread existing.

Destruction sets stop, wakes a sleeper, joins, then retires context/task. If a working task is in I/O, stop does not cancel that I/O. If a sleeper is never awakened, join can fail to progress. Freeing the pool after setting stop but before join can race a still-working task and cause a lifetime violation.

stop/wake/join · recovery and gate · shutdown ordering. No source-only upper bound on join latency.

03 · 18 / 20

D26 · Does a 50 ms timer prove a waiting writer will finish?

A caller reports a 300 ms stall. The control daemon has a 50 ms nominal period. Must six useful refreshes have completed? A reviewer proposes treating each timer tick as one guaranteed writer completion.

Challenge, then reveal the bounded answer

No. Gate, task execution, scheduling, condition mutex and writer competition remain. A refresh publishes an allowance, not a writer completion. Useful progress also requires the writer to be scheduled and obtain the relevant shared state.

Follow-up: “Then why have a timer?” It supplies another execution opportunity without requiring a work producer to notify this role; it does not eliminate dependency conditions.

Discriminating observation: Record gate, waiter status, task start/end, generated allowance, writer condition returns and current demand. A wake count alone cannot distinguish missed work from a long-running task. Keep Q04–Q06 as the existing lifecycle challenges.

03 · 19 / 20

A coherent replacement: One nonblocking work scheduler

Teaching alternative. Preserve the stated property while changing how actors coordinate.

  1. Give every role retained pending state, not one disposable wake bit.
  2. Choose a ready task and preserve its continuation before issuing slow I/O.
  3. Complete the I/O continuation while allowing quota and pacing tasks to run.
  4. At stop, close producers, finish or cancel continuations under explicit rules, join, then free shared state.

Teaching alternative: foreground work shifts latency to callers; a blocking unified worker couples all four delays. The nonblocking alternative adds queues, continuations, cancellation ownership and scheduling policy. No bounded service time follows without I/O and fairness assumptions.
