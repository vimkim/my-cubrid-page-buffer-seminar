Four background jobs help a full pool move

CUBRID page-buffer daemons and PostgreSQL page replacement

Frequently reused pages, a large scan, and changed pages fill a finite pool. Each constructed schedule starts independently. Performance explanations are source-based reasoning, not measured results.

03 · 1 / 28

A missing page needs a frame occupied by dirty work

Independent constructed starting state: A request is reading a large scan, but the page buffer—the server's collection of pages in memory—is full. A frame is one memory slot that holds one database page.

In this example, S3 and S4 name two different database pages. S3 is the scan page the request needs next; it is absent from memory. S4 is a different page already in a frame. Nobody is using it now, but its memory contents have changed: it is dirty, so those changes still need to reach page storage.

The server cannot simply overwrite the dirty page's frame. It must preserve the changes through a safe write path, then check whether the frame is still unused and safe to reuse. Background jobs can help with this preparation before another request runs out of space.

Preparing page bytes, finishing in-memory state, choosing retention targets, and slowing writers are different jobs. Moving them to other threads does not remove their safety conditions.

Q&A · Does every dirty page have to pass through all four daemons?

No. They handle different responsibilities, not a four-stage page pipeline. Page-flush submits images; post-flush may finish bookkeeping; maintenance and flush-control adjust policy and pacing.

03 · 2 / 28

Preparing a frame early can reduce work on the request path

Same starting snapshot, two alternative schedules: S3 is the requested page missing from memory. S4 is an unused resident page with dirty changes that still need preservation. Every frame—the memory slot for one page—is occupied.

A daemon here is a background thread inside the database server that repeatedly works and waits. Foreground means the thread serving the request; background means a separate execution thread.

The request thread can do all this work. The second schedule moves preparation away from its read path, if a suitable frame is ready when needed. The performance benefit depends on the workload and storage delays.

Q&A · Can background preparation become wasted work?

A prepared page can be changed or used again before demand arrives. Its old flush still fulfilled a preservation job, but the frame may no longer be available to the waiting request.

03 · 3 / 28

One blocking worker would make unrelated jobs wait

Design question: Suppose one background thread writes a dirty page, finishes its management state, adjusts retention targets, then updates writer pacing. While that thread waits for a slow log or page write, the other three jobs cannot run on it.

CUBRID gives these jobs separate daemons: background threads inside the server, each with its own task and wait policy. This lets one role run while another is waiting. It is a design choice, not a measured performance guarantee.

The four roles are not four stages every page must visit. Only page-flush submits page images. Maintenance changes retention policy; flush-control changes how participating writers wait. A single worker remains a possible alternative if its scheduling preserves these responsibilities.

Q&A · Do four threads guarantee that the four jobs never block each other?

No. Separate execution avoids one blocking task monopolizing a single worker, but the jobs can still contend for shared locks, CPU or storage. Their actual overlap and latency require observation.

03 · 4 / 28

Four jobs change four different kinds of state

Starting point: S4 is an unused page in memory whose changed contents still need writing. Its BCB is the frame's management record: it tracks the current page identity, use and flush state.

Page-flush

Submit page bytes

Check the dirty page, copy stable bytes, and send the copy through the safe write path. Submission alone does not authorize frame reuse.

Post-flush

Finish the record

Recheck the BCB after submission, finish the old flush state, and wake waiting threads. It may offer a suitable frame to a waiting request.

Maintenance

Change retention targets

Use activity samples to adjust quotas (target shares of the pool) and zones (groups with different retention preferences).

Flush-control

Slow continuing writers

Replace a shared balance of page-sized credits. Participating writers spend them after successful OS writes and may then wait.

Q&A · Which role makes a dirty candidate safe to reuse?

No role grants that permission alone. Preservation removes an old write obligation, completion updates metadata, and the allocator still needs a protected decision about the frame’s current state.

03 · 6 / 28

A timer gives a chance to check, not a completed job

Each daemon is a background thread that performs its task, then waits. A timer ends that wait after a target period; a wake is another thread's request to end the wait early. Neither proves that useful work happened.

Before work, every task checks the boot gate, a shared flag that permits page-buffer work after recovery. Maintenance may reject a recalculation of retention targets, called a quota epoch. Post-flush starts with short waits, then backs off when idle; consumed work or an accepted wake resets it to 1 ms. Flush-control's first gate-open pass only records time.

Q&A · Why can a daemon wake and do no useful work?

Task entry can encounter a closed boot gate, no pending item, or a policy guard that rejects an update. A wake provides an opportunity to inspect state; it does not certify output.

Q&A · Why does post-flush eventually wait without a timer?

Its increasing waits reduce idle polling, while producers can wake it when they enqueue work. That policy relies on retained queue state and a valid wake/check sequence; it supplies no completion deadline.

Q&A · Then who wakes post-flush?

During ordinary work, the page-flush daemon requests the wake directly. The producer in the preceding answer is the page-flush thread submitting the page image and delegating completion work through the queue. After successful image submission in pgbuf_bcb_flush_with_wal(), all of these conditions must hold.

  1. The call comes from the page-flush path (is_page_flush_thread == true).
  2. The post-flush daemon exists.
  3. An allocator request is waiting for a reusable frame.
  4. pgbuf_Pool.flushed_bcbs->produce(bufptr) successfully inserts the BCB pointer into the queue.

It then calls pgbuf_Page_post_flush_daemon->wakeup(). The order is publish queue work → request a wake. If any condition fails, the submitting thread completes that BCB's bookkeeping locally. An allocator unable to find a frame wakes page-flush; page-flush wakes post-flush if the conditions above hold. These are two separate wake calls.

During server shutdown, the shared daemon shutdown code requests a wake. When pgbuf_daemons_destroy() destroys post-flush, daemon::stop_execution() sets stop, calls wakeup(), then join(). This wake supports worker exit; it does not guarantee that every pending queue item is processed.

A wake sent while the thread is running is not saved as a notification for its next wait. Retaining work in the queue and getting another execution opportunity are separate facts. Follow that sequence in the limits of a wake just before sleep.

03 · 8 / 28

Shared state keeps work after a wake is lost

A producer creates work; a consumer processes it. A queue keeps pending items in shared memory. A predicate is a condition the task checks, such as whether a request still needs a frame. This retained state survives an early wake until checked; it is RAM state, not crash-durable storage.

A wake is only a hint: wakeup() wakes a sleeping waiter. While the thread is running, it saves no signal for the next wait. On its next task entry, the consumer must check the queue or pressure again.
Q&A · If the queue retains work, can a lost wake still delay it?

Yes. Retention prevents forgetting the item, but processing still needs another task entry. At a wake-only wait, a later accepted signal or other supported wait exit matters.

Q&A · Can a quota or token balance replace a BCB safety check?

No. Quotas guide retention and tokens pace participating writers. Neither proves current identity, absence of users, completed preservation, or permission to overwrite a frame.

03 · 11 / 28

Page-flush follows links from each target LRU tail

Search starting point: A BCB manages one resident frame; dirty means its changes still need writing. Each LRU is a linked replacement list. Its LRU3 is the cold, least-protected zone at the tail. A visit allowance limits how many BCBs to inspect in one collection pass.

  1. Decide where to look. Read list sizes and quotas (target retained shares) to compute a flush weight per LRU. Walk the list array in index order, shared entries then private entries. Skip a list whose weight is zero; a larger weight gives a larger visit allowance, not an earlier turn.
  2. Follow one list's links. Lock that LRU, start at bottom, and follow prev_BCB toward the head. Stop when the allowance is used, the list ends, or the walk reaches a BCB outside LRU3. Unlock before considering the next list.
  3. Save dirty candidates. Every BCB visited consumes allowance, including a clean BCB. Save each dirty BCB's pointer and page identity in a temporary candidate array.
  4. Recheck before writing. Later lock each saved BCB. Skip it if its page identity changed, it is now clean or already flushing, it left LRU3, or someone is using it. Required WAL must already be persistent before page submission.

Small constructed example: Three BCBs appear from the tail toward the head: clean → dirty and in use → dirty and unused, all in LRU3. With an allowance of 2 and no concurrent changes, the pass visits only the first two. It saves the second, then rejects it at the use recheck. The third is beyond this pass's allowance.

How the allowance is calculated, and when another pass runs

The base allowance uses pool size × configured flush ratio, a pressure adjustment, and a cap equivalent to 200 MiB of page bytes. Each positive-weight list gets its proportional integer share, with a minimum of 1 visit. Integer truncation and the minimum mean the base allowance is not an exact global visit cap. It is not the 1,000-node cap used by the foreground victim helper.

Under continuing pressure the daemon can collect again; each collection starts at list tails again, without a saved BCB-array cursor. A stop hint can end the inner loop. 03 · 12 / 28

Maintenance visits list statistics, then adjusts zone boundaries

Search starting point: Each private/shared LRU is a linked replacement list with activity counters and zone sizes. A quota is a private list's target retained share; LRU1/LRU2 are its more-protected zones, and LRU3 is the cold zone. A BCB manages one frame.

  1. First decide whether to update. A 100 ms task attempt can return from quota adjustment before list traversal, for example when quotas are disabled or the time/activity gate rejects the update.
  2. Read every list's counters. On an accepted update, walk the whole LRU array. Read and reset sampled-hit counters, update private activity estimates, and sum candidate counts. These are per-list numbers; there is no BCB-by-BCB activity search.
  3. Update private lists, then shared lists. Visit all private entries to set quotas and zone thresholds. Then visit all shared entries to set their zone thresholds. Advertise lists with eligible candidates to the corresponding victim-discovery queues, subject to the private quota condition.
  4. Move only the excess at boundaries. If a list's protected zones are too large, lock that list. Start at the end of LRU2 (or LRU1 if LRU2 is empty), follow links and demote excess BCBs to LRU3; then shrink LRU1 into LRU2 if needed. Stop each adjustment when its threshold is met.

Small constructed example: If LRU1 + LRU2 contain 30 BCBs and their new combined threshold is 25, move the 5 boundary BCBs out of those protected zones. This is not a scan of every BCB looking for dirty pages. A large threshold reduction can still move many BCBs.

Q&A · Why can a flush waiter wake while a writer still waits for tokens?

They wait on different conditions. One needs old-image completion bookkeeping; the other needs pacing credit after an OS write. Satisfying either condition does not satisfy the other.

03 · 14 / 28

Each thread executes its task before deciding how long to wait

A daemon is a background thread inside this server. Its task is the job it executes; its looper chooses the pause, and its waiter handles that pause and wake requests.

A successful create_daemon() starts one std::thread and provides a managed execution context—the server state used by that thread. It immediately runs the task, asks cubthread::looper how to pause, then repeats. Each of the four roles has its own loop.

For later fixed-period passes, the loop subtracts the previous task's execution time. If a task consumes 70 ms of a 100 ms period, the remaining target wait is 30 ms. If it consumes the whole period, the timed wait can be zero. These are scheduling opportunities; task guards may still reject work.

Execution time is subtracted at the pause.

Q&A · What if the task takes longer than its nominal period?

The looper can leave no timed pause for that pass. It cannot recover the elapsed time or guarantee immediate scheduling, and task guards still decide whether the next entry performs work.

03 · 16 / 28

Recovery permits useful work; shutdown waits for it to end

Boot starting state: The page-buffer pool and its management records, replacement lists, queues and monitors exist before the background jobs start. The boot gate is a shared flag that blocks useful page-buffer work while recovery establishes the required state.

  1. After double-write-buffer (DWB) recovery, server boot calls pgbuf_daemons_init() to attempt creation of the four roles, before log recovery finishes.
  2. A created worker runs its task immediately. A task entry during recovery sees the closed gate and returns.
  3. After recovery, boot opens the gate. Each role sees it on a later task entry from its own timer or work wake; opening the gate sends no wake itself.
  4. At normal shutdown, the caller sets stop and wakes a sleeper. A running task must return. The worker then retires its execution context and task, exits, and the caller's join() returns. The manager clears the daemon pointer.
  5. The group stops in maintenance → page-flush → post-flush → control order, before log_final() and later pool teardown.

Stand-alone mode creates none of these four threads. When background page-flush is unavailable, the relevant request path can flush victims synchronously. Creation is not unconditional: flush-control may be absent after initialization failure.

Q&A · Why start the workers before opening their recovery gate?

Creation establishes their execution contexts; the gate separately prevents premature page-buffer work. A created thread may enter its task during recovery and return without useful work.

Q&A · Are these daemons separate operating-system processes?

Here each successfully created role is a thread within the database server. It has a managed context but shares pool storage, so thread termination and shared-resource lifetime must be coordinated.

Boot creates workers before it permits page-buffer work

Boot starting state: The page-buffer pool already exists. Recovery reconstructs the database's required page and log state; a shared boot gate keeps these background tasks from using it too early.

  1. pgbuf_initialize() has prepared frames, BCBs (frame management records), replacement lists, quota/activity arrays and queues.
  2. xboot_restart_server() loads and recovers DWB pages. DWB is the optional staging buffer used to protect page images.
  3. pgbuf_daemons_init() attempts maintenance → page-flush → post-flush → flush-control creation. This is creation order, not a page pipeline.
  4. Boot creates the separate DWB helper group, then runs log_initialize() and log recovery.
  5. After boot_after_copydb(), boot opens the gate with BO_ENABLE_FLUSH_DAEMONS(). Opening the flag itself sends no wake.

A successfully created worker can already enter its task while the gate is closed. That entry returns before useful page-buffer work; only a later entry can observe permission.

No. It orders startup attempts. Once created, workers have independent loops, and a page need not visit all roles or follow their creation order.

Creation failure and restart failure need different cleanup

Creation boundary: The server attempts up to four page-buffer daemon roles; successful creation is not guaranteed. If pool initialization returns an allocation error, it calls pgbuf_finalize() and aborts that initialization.

The generic manager can return NULL when it has no available thread entry. The role initializers do not check that return or retire the task left without a worker on this path. Independent constructed starting state: A daemon may still be inside its task, reading a BCB (a frame's management record) or a shared queue. A proposed shutdown frees those objects immediately after setting stop, then wakes the worker and calls join() to wait for its thread to end.

03 · 22 / 28

Join confirms worker cleanup has already finished

Lifecycle map: The pool is the shared page storage in memory. The gate controls when tasks may use it. At shutdown, the caller requests stop and wakes a sleeper; the worker finishes any active task, retires its context and task, then exits. Only then can the caller's join() return and the manager clear its pointer.

The pool and queues stay alive through this sequence. Flush-control's task-owned token bucket is cleaned up inside its worker's retirement, before that worker exits.

Q&A · Can join return while the worker is still retiring its token bucket?

Not on the successful worker-exit sequence shown here. The control task retires its bucket before thread exit, and join returns after that exit. Other users’ lifetime obligations still need the shutdown protocol.

03 · 24 / 28

Shared storage must outlive every worker that touches it

Recovery boundary: A created background thread can execute while log recovery is running. Its boot gate is the shared flag that rejects page-buffer work until recovery finishes. Removing that check permits concurrent accesses to state recovery is changing; the thread's mere existence does not establish a failure.

Shutdown boundary: Stop requests the outer loop to end; it does not cancel I/O in an active task. The caller wakes a sleeper and waits in join(). The worker finishes its task, retires its context and task, and exits before join returns. Freeing pool or queue storage earlier can race a worker still using it.

On restart failure, cleanup first closes the gate, then destroys the page-buffer and double-write-buffer (DWB) daemon groups before log_final(). Closing the gate blocks later task work; it cannot cancel a helper already executing. An inner pressure or queue-drain loop may delay the outer stop check. Stop alone promises neither queue draining nor a time limit for termination.

stop/wake/join · recovery and gate · shutdown ordering · restart-error cleanup. No source-only upper bound on join latency.

Q&A · Does shutdown necessarily drain every pending queue item?

Stop alone promises neither draining nor a time bound. A safe shutdown needs explicit producer, pending-work and resource-retirement rules; joining establishes worker exit, not a generic queue-drain policy.

D26 · A 50 ms target cannot count writer completions

Independent constructed starting state: A writer reports a 300 ms stall. Flush-control is the background job that replaces a shared balance of page-sized credits; an empty balance may pause a participating writer after its OS write. The control loop has a 50 ms target period.

A useful balance refresh requires scheduling and an open recovery gate—the flag permitting useful work. Updating the balance requires its mutex—the lock protecting shared credits—and the writer must later run and obtain that lock to consume them. A period is an execution opportunity, not a completed refresh or writer operation.

Challenge: Does the 300 ms stall prove that six useful refreshes completed, or that six writers must have finished?

Challenge, then reveal the bounded answer

No. A nominal period cannot count completed work. Gate, task duration, scheduling, the balance mutex and writer competition can all matter. A refresh publishes an allowance, not a writer completion.

Follow-up: “Then why have a timer?” It provides another task opportunity without requiring a producer to notify this role. The other conditions still apply.

03 · 26 / 28

A single scheduler must let other jobs run during I/O

Independent teaching alternative: Replace the four background threads with one scheduler. A naive blocking worker would stop all four jobs while waiting for a page write. The goal is to preserve each job's pending work and let the other jobs run during that wait.

  1. Keep a shared queue or pending-work record for each role. A wake only prompts the scheduler to check it.
  2. Choose a ready job. Before starting slow I/O, save a continuation: the state and next action needed when that I/O finishes.
  3. While I/O is outstanding, run ready completion, retention or pacing work. When I/O finishes, resume its continuation under the required protection.
  4. At shutdown, stop new producers, then finish or cancel outstanding continuations under explicit ownership rules. End the worker, join it, then free shared state.

This alternative adds queues, continuation lifetimes, cancellation rules and scheduling policy. Foreground preparation puts its cost on requests; one blocking worker makes the jobs wait together. A nonblocking scheduler avoids that particular coupling, but no bounded service time follows without I/O and fair-scheduling assumptions.

Q&A · Would one nonblocking scheduler automatically be fair?

No. Saving continuations avoids blocking all roles on one I/O, but fairness also needs scheduling and I/O assumptions. Retaining pending work does not bound when each job receives service.

Enable the counters before relying on their output

Observation starting state: A daemon experiment needs both active statistics collection and the selected categories enabled. An empty counter without this setup cannot show that no work happened.

extended_statistics_activation is a startup-cached bitmask: each bit selects one statistics category. Its default value 15 enables categories 1, 2, 4 and 8. It excludes page-buffer victimization (16) and daemon detail (64). Enable the categories needed by the experiment before startup or reinitialization; a normal SQL change does not update this cached setting.

Collection must also be running. stats_on (hidden, default false) is one startup option for always-on collection; an appropriate statistics API or utility is another route. Framework counters can show loop, wake and sleep activity, but cannot supply a per-item timeline.

Publication time, waiter state, task entry and the work predicate still need proposed probes. A predicate is the shared condition being checked, such as whether an allocator still needs a frame. These probes are a plan, not recorded runtime evidence.
