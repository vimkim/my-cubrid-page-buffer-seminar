Four background jobs help a full pool move

CUBRID page-buffer daemons and PostgreSQL page replacement

Frequently reused pages, a large scan, and changed pages fill a finite pool. Each constructed schedule starts independently. Performance explanations are source-based reasoning, not measured results.

03 · 1 / 36

The next page needs a frame, but every frame is occupied

Fresh teaching example: A database handles data in fixed-size units called pages. A request thread is an execution flow handling a request. It reads pages in sequence. The server keeps pages in memory in its page-buffer pool. Every frame, a memory slot for one page, is occupied.

S3 names the next page to read; it is absent from memory. S4 names another page occupying a frame. Nobody uses it now, but its memory contents changed and still need to be written. This state is called dirty.

Putting S3 into S4's frame now would lose those changes. First preserve them through the safe write path, then check whether the frame is still safe to reuse. Preparing it before a request needs it is one purpose of background work.

Sending a page copy, finishing its management state, adjusting how much memory to retain, and controlling write speed are separate responsibilities.

Q&A · Does every page pass through all four threads?

No. Page-flush sends copies; post-flush receives selected frame-management-record (BCB) bookkeeping. Maintenance and flush-control adjust retention and write pacing. These roles are not four stages for every page.

03 · 2 / 36

Preparing a frame before the request can reduce its work

Both schedules start from the same state. S3 is the page the request needs, absent from memory. S4 is an unused resident page whose changes still need a write. No frame is empty.

If the request thread prepares the frame itself, the request must wait for that work. Another thread inside the server can do the preparation earlier. The request path is the foreground; separate preparation is background work. A daemon here is a server thread that repeats work and waits.

Both schedules check the current reuse conditions at the end. Another request may change or start using the page after preparation. Earlier work helps only if the candidate is still suitable when needed. The actual performance benefit depends on workload and write latency.

Q&A · Can a prepared frame become unsuitable?

Yes. Another request can change or start using the page. The earlier write does not replace the current reuse check.

03 · 3 / 36

Other management work must continue during a write wait

Suppose one thread does everything. It writes pages, finishes management state, adjusts memory retention, and controls write speed. While it waits for a slow log or page write, it cannot start the other jobs. These input/output operations are called I/O.

CUBRID gives four kinds of work to separate background threads. The work each thread repeatedly executes is its task. While one thread waits for a write, another can execute its own task.

Every page does not pass through all four threads. Page-flush sends page copies; the others handle state or policy. Separate threads can still compete for CPU, locks, and storage, so any performance gain needs measurement. One thread is also a possible alternative if its design lets other jobs run during I/O waits.

Q&A · Can four threads still wait for each other?

Yes. One thread waiting for a write need not directly block the other jobs, but they can still compete for locks, CPU, or storage. Actual delays require measurement.

03 · 4 / 36

Identify the concrete job of each thread

Start with a page that needs a write. S4 is in memory and unused, but its changes still need writing. Each frame has a management record that tracks its current page, users, and flush state. This record is its BCB (Buffer Control Block).

Page-flush

Send a copy for writing

Check the page and make a stable copy. Preserve required log records first, then send the copy to the write path. Successful submission still requires a separate reuse check.

Post-flush

Take over remaining bookkeeping

Receive selected completion work. Lock and recheck the BCB, finish the old flush state, and wake waiting threads. If suitable, offer the frame to a request waiting for one.

Maintenance

Adjust LRU retention targets

Use activity samples to adjust the target page count (quota) of session-associated replacement lists, the private LRUs. Adjust target sizes of retention-priority regions (zones) in both private LRUs and common replacement lists, the shared LRUs. Total buffer-pool frame capacity stays unchanged; no page copies are written.

Flush-control

Control how fast writers continue

Replace a pacing balance measured in pages. Participating threads consume it after a successful OS write and may wait before continuing if it is insufficient.

Q&A · Can the frame be reused immediately after page-flush writes?

Current users and page state must be rechecked. Writing preserves changes; completion updates the management record. New use or changes may occur in between.

03 · 5 / 36

Sending page copies and finishing bookkeeping are different jobs

Work remains after a page copy is submitted. The frame's management record, its BCB, needs its old flush state finished, and threads waiting for that flush must be woken. Page-flush does this itself or hands selected work to post-flush.

For a handoff, it adds the BCB's address to a completion-work list named flushed_bcbs. A data structure where items are added and removed this way is a queue. Post-flush takes an address and finishes the BCB it points to. The list does not contain page-data copies.

No. The completion list holds BCB addresses. Post-flush uses them to check and finish management state, without starting a new page write.

03 · 6 / 36

After waking, check whether work is currently allowed and needed

There are two ways to resume a waiting thread. A timer ends the wait after a chosen duration. A wake asks the thread to end its wait early. Both give it an opportunity to check for work.

Execution can still find no work to do. Before touching the page buffer, each task checks a flag that disallows work until server recovery finishes. This flag is called the boot gate. After it opens, maintenance checks whether recalculation is due, and post-flush checks its pending list. Flush-control's first allowed execution only records a reference time.

Dots in the diagram mark opportunities to attempt work, not completed writes. Post-flush extends its idle waits. Processing an item or receiving an accepted wake before timeout resets its next target wait to 1 ms.

Q&A · Can a thread wake and return without useful work?

Yes. Recovery may be incomplete, the list empty, or policy recalculation not due. An execution opportunity is different from useful work.

Q&A · Why does post-flush eventually wait without a timer?

It reduces repeated empty-list checks. Page-flush adds work and requests a wake. Retained items and the wake/check sequence must both be handled; this does not guarantee a deadline.

Q&A · Then who wakes post-flush?

During ordinary work, the page-flush daemon requests the wake directly. The producer in the preceding answer is the page-flush thread submitting the page image and delegating completion work through the queue. After successful image submission in pgbuf_bcb_flush_with_wal(), all of these conditions must hold.

  1. The call comes from the page-flush path (is_page_flush_thread == true).
  2. The post-flush daemon exists.
  3. An allocator request is waiting for a reusable frame.
  4. pgbuf_Pool.flushed_bcbs->produce(bufptr) successfully inserts the BCB pointer into the queue.

It then calls pgbuf_Page_post_flush_daemon->wakeup(). The order is publish queue work → request a wake. If any condition fails, the submitting thread completes that BCB's bookkeeping locally. An allocator unable to find a frame wakes page-flush; page-flush wakes post-flush if the conditions above hold. These are two separate wake calls.

During server shutdown, the shared daemon shutdown code requests a wake. When pgbuf_daemons_destroy() destroys post-flush, daemon::stop_execution() sets stop, calls wakeup(), then join(). This wake supports worker exit; it does not guarantee that every pending queue item is processed.

A wake sent while the thread is running is not saved as a notification for its next wait. Retaining work in the queue and getting another execution opportunity are separate facts. Follow that sequence in A wake sent before sleep is not saved for later.

03 · 8 / 36

The pending target stays in the list even if a wake is missed

Consider a completion handoff from page-flush. It successfully sent a page copy through the write path. The frame's BCB management record still needs its flush state finished. When handing this work to post-flush, it follows this sequence.

  1. Page-flush adds the BCB address (pointer) to flushed_bcbs. It does not add page data or a new write request.
  2. It then requests a wake with wakeup(). If post-flush is still running, that request is not saved for its next wait.
  3. When post-flush checks the list, it takes the BCB address and finishes the bookkeeping. The list item, not the number of wake requests, identifies the work.

This list is the queue. Page-flush adds items as its producer; post-flush removes and processes them as its consumer. Both threads need the same list, so it lives in memory inside the same server process. Shared here means used by multiple threads, not an OS shared-memory IPC facility between processes.

Retaining an item and making progress are separate. The item remains in RAM until taken; it is not a crash-recoverable record. Processing requires another list check. A thread waiting without a timer may need a later accepted wake or another wait-ending event. The list alone guarantees neither immediate processing nor a deadline.
Q&A · Can processing be delayed even with a retained item?

Yes. The address preserves the work target, but processing requires another check. A wait without a timer may need a later accepted wake or another event ending the wait.

03 · 9 / 36

Check work lists, page state, and policy separately

The four threads check different things. Page-flush checks frame shortage and write candidates; post-flush checks its completion-work list. Maintenance adjusts private-LRU target page counts (quotas) and private/shared LRU retention-priority region (zone) size thresholds. Flush-control replaces a pacing balance; one unit of this balance is a token.

In the diagram, a BCB is a frame's management record, a fix registers current use, and a mutex locks checks and changes. LRU3 is the cold region searched for reuse candidates. WAL requires the relevant log records to be preserved before submitting the page copy. DWB is an optional staging area that receives the copy first. DWB acceptance does not prove the final page-location write has finished.

Q&A · What if another thread fixes a candidate after page-flush selects it?

If that fix is still held just before writing, page-flush skips the candidate. Page state can change after selection, so page-flush locks the BCB mutex and rechecks the current page identity, use, and other conditions before deciding whether to write.

03 · 11 / 36

Page-flush follows links from each target LRU tail

Search starting point: A BCB manages one resident frame; dirty means its changes still need writing. Each LRU is a linked replacement list. Its LRU3 is the cold, least-protected zone at the tail. A visit allowance limits how many BCBs to inspect in one collection pass.

  1. Decide where to look. Read list sizes and quotas (target retained shares) to compute a flush weight per LRU. Walk the list array in index order, shared entries then private entries. Skip a list whose weight is zero; a larger weight gives a larger visit allowance, not an earlier turn.
  2. Follow one list's links. Lock that LRU, start at bottom, and follow prev_BCB toward the head. Stop when the allowance is used, the list ends, or the walk reaches a BCB outside LRU3. Unlock before considering the next list.
  3. Save dirty candidates. Every BCB visited consumes allowance, including a clean BCB. Save each dirty BCB's pointer and page identity in a temporary candidate array.
  4. Recheck before writing. Later lock each saved BCB. Skip it if its page identity changed, it is now clean or already flushing, it left LRU3, or someone is using it. Required WAL must already be persistent before page submission.

Small constructed example: Three BCBs appear from the tail toward the head: clean → dirty and in use → dirty and unused, all in LRU3. With an allowance of 2 and no concurrent changes, the pass visits only the first two. It saves the second, then rejects it at the use recheck. The third is beyond this pass's allowance.

How do another collection and a separate flush-all differ?

See the following budget screen for arithmetic and repetition scope. Another collection starts at list tails again; it does not resume a saved position in the BCB array. Optional neighbor batching looks up nearby page identities in the resident hash. The separate pgbuf_flush_all_helper() is an explicit flush path that iterates over all num_buffers entries.

03 · 13 / 36

One collection has a budget; a daemon execution has no fixed iteration limit

A BCB manages one frame; LRU3 is a list’s cold tail zone. Here, one candidate collection means the link search within one call to pgbuf_flush_victim_candidates(). First compute the base inspection budget, check_count_lru.

  1. Convert pool frame count × data_buffer_flush_ratio to an integer. The default ratio is 0.01.
  2. Multiply that integer by the pressure boost, then convert to an integer again. The boost is 1–10, and is 1 during a checkpoint.
  3. Take the smaller budget and 200 × 1024 × 1024 / DB_PAGESIZE. DB_PAGESIZE is the page size in bytes. With 16 KiB pages this cap is 12,800. It converts bytes into a BCB count; it does not mean that 200 MiB will be written.

The per-list inspection budget, check_count_this_lru, converts base budget × list weight ÷ weight sum to an integer, with a minimum of one for each positive-weight list. If the base budget or weight sum is zero, no link search runs.

The daemon task can repeat collection and submission while pressure persists. One execute() has no fixed iteration count or millisecond budget. A collection cap is not a cap on the whole execution. The separate foreground victim-search limit of 1,000 visits does not apply here.

03 · 14 / 36

Maintenance visits list statistics, then adjusts zone boundaries

Search starting point: Each private/shared LRU is a linked replacement list with activity counters and zone sizes. A quota is a private list's target retained share; LRU1/LRU2 are its more-protected zones, and LRU3 is the cold zone. A BCB manages one frame.

  1. First decide whether to update. A 100 ms task attempt can return from quota adjustment before list traversal, for example when quotas are disabled or the time/activity gate rejects the update.
  2. Read every list's counters. On an accepted update, walk the whole LRU array. Read and reset sampled-hit counters, update private activity estimates, and sum candidate counts. These are per-list numbers; there is no BCB-by-BCB activity search.
  3. Update private lists, then shared lists. Visit all private entries to set quotas and zone thresholds. Then visit all shared entries to set their zone thresholds. Advertise lists with eligible candidates to the corresponding victim-discovery queues, subject to the private quota condition.
  4. Move only the excess at boundaries. If a list's protected zones are too large, lock that list. Start at the end of LRU2 (or LRU1 if LRU2 is empty), follow links and demote excess BCBs to LRU3; then shrink LRU1 into LRU2 if needed. Stop each adjustment when its threshold is met.

Small constructed example: If LRU1 + LRU2 contain 30 BCBs and their new combined threshold is 25, move the 5 boundary BCBs out of those protected zones. This is not a scan of every BCB looking for dirty pages. A large threshold reduction can still move many BCBs.

Maximum movement scope: Under one list’s lock, an adjustment processes no more than its LRU1/LRU2 population at that point. BCBs demoted to LRU3 are distinct from those subsequently moved from LRU1 to LRU2. In a fixed-state pool, total moves do not exceed the pool frame count. Between successive list locks, other threads can promote a BCB again or move it to another list, so concurrent cost uses actual moves including revisits. The boundary loops have no separate visit or time budget.

03 · 16 / 36

The 8,192-slot completion queue does not cap a drain’s item count

Post-flush finishes a previous flush’s BCB state. A BCB manages one frame, and the completion queue flushed_bcbs stores its pointer. Queue capacity is 8 × 1024 = 8,192 items.

  1. Without new insertions: Process the initial contents. An initially full queue allows at most 8,192 successful consumes before the next consume() fails and the call returns.
  2. With concurrent insertions: Page-flush can insert new pointers into slots freed by the consumer. Post-flush continues consuming, so one call can process more than 8,192 items.
  3. There is consequently no fixed per-call cap. The loop has no separate item or time budget. If the queue stays sufficiently populated, this code alone does not determine when the call returns.
Queue capacity bounds simultaneously stored items. It does not bound items consumed in one execution, time to acquire a BCB lock, or waiter-notification cost. Each item’s current fix, dirty and zone state is rechecked; consuming it does not guarantee a frame offer.

Flush-control replaces a page-credit balance, called tokens, using elapsed time. A balance of 100,000 tokens does not run 100,000 token iterations. It calculates and assigns numbers, then broadcasts to waiting writers. Page-search visits are zero; balance calculation has constant scale. Lock contention and waking several writers still add cost.

03 · 18 / 36

Flush-completion waits and writer pacing waits have different purposes

Consider the moment after successful page-copy submission. The frame's BCB still needs its old flush state finished. Separately, a writer that completed an OS write may have to slow down before continuing. These waits concern different work.

Post-flush's job: When requests are waiting for frames, page-flush may add a BCB address to the completion list and hand over bookkeeping. Post-flush rechecks state and wakes threads waiting for the old flush. If suitable, it offers the frame to a request. If handoff conditions fail, including no post-flush thread or a rejected enqueue, page-flush finishes locally. Handoff conditions and local completion →
Flush-control's job: After a successful OS write, participating writers consume a pacing balance measured in pages. This balance is called the token bucket. Insufficient balance may make them wait before continuing. Flush-control replaces the balance and wakes waiting writers. Bypass paths make this a soft limit. Balance use and bypass rules →

Successful submission means success at the selected write-path boundary. With DWB staging, this differs from completing the write at the final page location. Post-flush starts no new page write in either path.

Q&A · Can a writer still wait after a flush waiter is woken?

Yes. One waits for old-flush bookkeeping; the other waits for a pacing balance after its OS write. These different conditions do not guarantee each other’s progress.

The thread runs its task once, then waits

Start when the background thread is created. Successful create_daemon() starts one std::thread inside the server. It also prepares server state the thread needs, including error handling. This state is its execution context.

  1. The thread executes its work, the task, first. It does not begin by waiting.
  2. After the task returns, a wait-policy object, the looper, selects the wait duration.
  3. A wait-and-wake object, the waiter, handles the wait. Once it ends, the thread executes its task again unless stop was requested.

A fixed period targets the time between task starts. A 70 ms task in a 100 ms period leaves a target wait of 30 ms. A task taking at least 100 ms can leave zero timer wait. Neither CPU scheduling time nor useful work is guaranteed; the task checks current conditions again.

Execution time is subtracted at the pause.

Q&A · What if the task takes longer than the period?

The next timer wait can be zero. Elapsed time cannot be recovered, and immediate CPU scheduling is not guaranteed. The next execution still checks work conditions.

Remember the request before deciding to sleep

New design question: A caller publishes demand while page-flush is awake (RUNNING), just before its infinite pause. How can the worker remember to inspect that demand? The following changes are proposals; they are not implemented at the pinned revision.

  1. Keep a pending request in RAM, and coordinate it with sleeping. The producer records “check again” even while the worker is running. The worker consumes that request instead of sleeping. The request update, final check and transition into condition waiting must use one synchronization protocol, such as the same mutex. Otherwise the request can arrive between “nothing pending” and sleep, reopening the gap. A coalescing bit can suffice if each pass rechecks all current pressure; it need not count every wake.
  2. Use a finite timer as a fallback opportunity. A positive page_flush_interval, such as the pinned default 1,000 ms, lets a future timed pause end without another producer. The task still checks the gate and demand; it may submit nothing. This limits the wait policy, not total response time under scheduling or I/O. Changing the setting does not wake a thread already in wait_inf().
  3. Treat opening the gate as a request that must be remembered. After publishing the open gate, request a pass through the coordinated pending protocol. A single call to today's wakeup() can arrive while RUNNING and be lost again. Startup notification alone also leaves the after-boot window unresolved.

Paths that can restore progress today: A later allocator or victim-search request can call wake after page-flush is SLEEPING. An accepted wake forces at least one candidate-flush call when the gate is open. A timed task entry with queued allocator demand also has a reason to run. Other paths may make a frame available. Creating a thread, allowing work, and waiting for exit are separate steps

Follow server startup. Prepare page frames, their BCB management records, replacement lists, and pending-work lists first. Background threads use this memory together inside the same server process.

  1. Startup recovers the double-write buffer (DWB), which stages page copies, then attempts four roles through pgbuf_daemons_init(). Log recovery has not finished.
  2. An early thread execution checks the work-permission flag and returns. This flag, the boot gate, blocks access before recovery.
  3. Recovery completion opens the gate. Opening it sends no wake. Each thread checks permission on a later execution prompted by its timer or work wake.
  4. Shutdown requests an end to repeated execution with stop and wakes a sleeping thread. The caller uses join() to wait for that thread to exit. Join returns only after active work and the thread's own cleanup finish.

The group stops in maintenance → page-flush → post-flush → control order, before log_final() and pool destruction. Stand-alone mode creates none of these four threads. Without page-flush, the relevant request path can write candidates itself. Creation can fail; control can also be omitted after initialization failure.

Prepare memory first and allow work after recovery

Database recovery runs during server startup. Recovery reconstructs page and log state, so other threads must not use it too early. Background tasks first check a work-permission flag called the boot gate.

  1. pgbuf_initialize() prepares page frames, BCB management records, replacement lists, target-share (quota) and activity arrays, and queues.
  2. xboot_restart_server() reads and recovers pages from DWB, the optional page-copy staging area.
  3. pgbuf_daemons_init() attempts maintenance → page-flush → post-flush → flush-control creation. This is thread-creation order.
  4. Startup creates separate DWB helpers, then runs log_initialize() and log recovery.
  5. After boot_after_copydb(), BO_ENABLE_FLUSH_DAEMONS() allows work. This flag change does not wake threads.

A thread created earlier can execute during recovery but returns at the closed gate before useful work. A later execution must observe the open gate. Thread-creation order is not a page-processing sequence.

Prevent access during recovery and after memory is freed

During recovery: Recovery code is changing page and log state. An already-created background thread checks the boot gate work-permission flag and returns instead of touching it. Removing the check permits concurrent access. Thread existence alone does not prove a failure occurred.

During shutdown: Stop requests an end to repeated execution; it does not cancel active work or I/O. Shutdown wakes a sleeper and uses join() to wait for exit. Freeing the pool or work list before the thread finishes work and cleanup can remove memory it still uses.

After restart failure: Close the gate, end the page-buffer and DWB page-staging thread groups, then call log_final(). The gate blocks later work but does not cancel a function already executing.

An inner loop handling frame shortage or continually taking list items can delay the outer stop check. Stop alone promises neither processing every item nor exit within a fixed time. Join confirms the particular thread has exited.

One-thread alternatives must let other jobs run during write waits

Design exercise, separate from the current implementation: Suppose one thread replaces four. Code choosing the next job is the scheduler. If this thread blocks until a page write finishes, other management jobs must wait too.

  1. Remember pending work in a form appropriate to each role: BCB addresses for completion, request state for frame shortage, and so on. Wake requests cannot replace the work record.
  2. Choose ready work. Before starting slow I/O, save the state and next action needed to resume afterward. This resume record is a continuation.
  3. Run other ready jobs while I/O is outstanding. When completion arrives, resume from the saved point under the required locks and protection.
  4. At shutdown, stop sources of new work first. Finish or cancel outstanding resume records under explicit cleanup-ownership rules. End the thread, confirm exit with join(), then free the necessary memory.

This alternative adds lifetime, cancellation, and execution-order rules for work records. It can reduce coupling to one I/O wait, but bounded service time still requires fair scheduling and assumptions about I/O duration.

Q&A · Does running other jobs during I/O automatically ensure fairness?

No. Avoiding a shared I/O stall still allows one job to monopolize selection. Fair execution rules and I/O assumptions remain necessary.
