Writeback precedes protected identity retirement

CUBRID page-buffer daemons and PostgreSQL page replacement

A few pages are read repeatedly while a large scan and pending page writes fill the pool. Each constructed schedule starts independently. Explanations of purpose and cost are inferences unless the source states its intent.

11 · 1 / 21

The request needs a frame; the old page still matters

A database request needs a page that is absent from a full buffer pool. A frame is one memory slot holding one page; its descriptor stores the current page identity and shared state. The backend, the server process handling this request, has selected a dirty frame to make room.

A dirty page has changes that still need writing to its data file. A pin keeps the frame's current page identity available to its holder. It permits other backends to pin or change that same page under the required content lock.

Writeback writes the old page's bytes to its data file. Invalidation later removes the old page-to-frame mapping. A successful write prepares for reuse; only the protected check of current pins and dirty state can authorize invalidation. Asynchronous I/O can hold its own lifetime pin, protecting the frame until storage work finishes.

11 · 3 / 21

Protect the bytes, then write the log before the page

Fresh write attempt: the requesting backend holds a pin on a dirty permanent page, a page whose changes are recorded for crash recovery. The pin keeps its identity available. A content lock separately protects its bytes against incompatible mutations.

WAL means write-ahead logging: recovery-log records must reach durable storage before the data-file changes they describe. The page's LSN, its log sequence number, identifies the log position required for this image. FlushBuffer reads that position while holding at least share-exclusive content protection, forces WAL for a permanent page, then writes the stable bytes.

Finishing the write can mark the page clean. The bulk-read strategy is BULKREAD; bulk-write is BULKWRITE; maintenance uses VACUUM. For a dirty permanent candidate from a BULKREAD ring, the backend can instead reject it when WAL forcing is needed. Rejection empties that local slot and releases lock/pin; it preserves the shared page identity and dirty work. BULKWRITE and VACUUM do not take this rejection.

11 · 4 / 21

The old mapping remains usable until protected retirement

Continue after a successful page write: the requesting backend still holds its pin, but has released the content lock. A pin protects page identity; the content lock had protected bytes during writing. The old page-to-frame mapping is still present, so another backend can find it and acquire its own pin.

Invalidation removes this old lookup entry. InvalidateVictimBuffer takes the mapping partition lock to protect lookup and the header lock to inspect current descriptor state. It rejects if another pin remains or if the page is dirty, meaning a data-file write is pending. Only a sole pin and clean state together allow retirement.

If another backend keeps its pin, the extra shared refcount rejects reuse. If it changes the page and leaves, refcount can return to one while the dirty flag rejects reuse. The next case isolates that second failure.

11 · 5 / 21

The other backend left; its new change did not

Fresh constructed case: A is the backend seeking a reusable frame. B is another backend that changes pages. R is the permanent, logged page currently in A's selected frame. A has written R and still holds its pin; the old mapping remains. No I/O is in progress.

The content lock protects page bytes during a write or mutation. After A releases it, B can pin R, take mutation protection, log a new change, mark R dirty, and leave. Here the shared refcount counts ordinary backend pin references; B's departure returns it to one, while the dirty flag still records B's pending change.

Q21 · What does the remaining pin prove?

Prediction: A now holds the only pin, but R is dirty again. Is refcount=1 enough to retire R's mapping?

Discuss, then reveal

No. It proves that A is the sole shared pin holder at the check. It says nothing about unwritten changes. InvalidateVictimBuffer requires both refcount=1 and no BM_DIRTY under mapping and header locks. A's earlier write cannot include B's later change, so A releases this candidate and retries.

11 · 6 / 21

A reusable-page budget cannot replace checkpoint work

A background writer prepares clean pages for likely future allocations. A checkpoint establishes a recovery boundary: its selected dirty pages must be written, followed by storage synchronization and log work. These actors choose work for different reasons.

Fresh constructed case: P and Q are two dirty resident pages with no pins or in-progress I/O. P is selected for this checkpoint and has usage credit 3. Q has usage credit 0. Usage credit is a small retention counter recording recent use; it influences replacement preference, rather than writing obligations.

Q22 · Which work must each actor finish?

Proposal: Skip checkpoint page processing because the background writer is running. It can consider Q, while its normal cleaning policy skips credited P. Does that cover the checkpoint's required output?

Discuss, then reveal

No. The background writer scans within its budget for unpinned, zero-credit pages such as Q. Checkpoint processing covers selected work such as P even when credit is positive. A write by a backend or the background writer can satisfy a selected page's checkpoint write, but merely running that actor cannot do so. The checkpoint also needs its later synchronization and log steps.

Optional follow-up: Which comparable workload and completion boundary would you measure before comparing engine write latency?

11 · 8 / 21

The three writers aim at different results

Return to a full pool with dirty resident pages; this is a role comparison, not the next event in the preceding race. Each writer uses content protection and the page's logging rule, but successful writing has a different purpose.

Allocating backend

The process handling a request selects and pins a dirty victim, tries the content lock, writes it, then attempts protected invalidation. Failure releases that candidate and retries.

Background writer

This worker cleans unpinned, zero-credit pages within its scan/write budget. Usage credit records retention preference. Cleaning prepares likely future candidates without reserving them for one request.

Checkpointer

This worker handles dirty pages selected for a recovery boundary. Positive usage credit does not cancel their required writes; later synchronization and log work complete the boundary.

11 · 9 / 21

Capacity groups and page credit remember different things

Start a new policy comparison: several client sessions, their server-side work contexts, reread pages while a bulk scan fills the same pool. A frame is one memory slot holding a page. Which policy records how these workloads compete for capacity?

CUBRID's replacement domain is a policy group of resident frames. A quota is its target capacity share. Private domains associate sessions with accounting; shared domains hold common policy membership. A private domain grants no exclusive page access, and several sessions can share one private list.

PostgreSQL's ordinary global Clock searches shared descriptors using bounded usage credit, a retention counter that aggregates qualifying accesses without storing the users' identities. Backend-private refcounts record outstanding pins, which protect current page identity; they are use bookkeeping rather than residency quotas. A ring is a bulk operation's local array of shared frame IDs.

Inference: CUBRID's explicit capacity accounting may help a mixed workload, while maintaining quotas, queues and list movements also costs work. Neither pins nor rings promise general per-client capacity fairness; more policy state proves no throughput or hit-ratio advantage.

11 · 10 / 21

Moving between domains differs from boosting within a list

Fresh CUBRID example: a caller releases the page's last outstanding fix, the protection keeping it available for use. The page's BCB, its buffer-control metadata, records a private policy list and zone: LRU1 is hot, LRU2 middle, LRU3 cold. A list is a capacity-accounting group, not exclusive page ownership.

Domain migration: on the eligible final-unfix path, CUBRID compares the caller's private-list index with the BCB's list, or tests whether the BCB is hot and old enough. If migration is chosen, it removes the BCB from the private list and inserts it in the shared list's middle. This tests association, not distinct-user count. Two sessions sharing one private list need not trigger the index-mismatch branch.

Zone boost: when ordinary policy handling does not migrate, it keeps LRU1 in place, boosts LRU2 only when old enough, and boosts LRU3 toward the hot end of its existing list. This changes retention preference; it does not authorize reuse.

PostgreSQL's normal first pin, which protects page identity, can add bounded usage credit, a retention counter. A ring, a local array of shared frame IDs, skips credit above one. Credit changes retention preference without moving the shared descriptor (page metadata) into a shared LRU.

Less ordering work trades away fine recency information

H1 and H2 are frequently reread pages in a small working set. A large scan reads many other pages once. The pool is full, so these workloads compete for frames, the memory slots holding their pages. These are structural trade-offs at the pins, not measured speed rankings.

Remembering reuse
PostgreSQL keeps bounded usage credit, a small retention counter, instead of an ordinary-buffer recency list. It loses exact access order and may need repeated clock passes. CUBRID groups frames into list domains and hot-to-cold zones. Ordinary reuse in the hot LRU1 zone also avoids a list move, so it is not exact LRU on every hit.
A scan beside H1/H2
A PostgreSQL ring is a per-operation array of shared frame IDs. Recycling eligible entries limits the operation's footprint. It helps only when the operation chooses that strategy and entries remain reusable. CUBRID's domains are policy groups; their quotas are target capacity shares. They govern competition across accesses, with more policy state to maintain.
11 · 12 / 21

A short search path does not guarantee a short wait

Start with a full pool and a request waiting for one reusable frame. A frame is a memory slot; its descriptor carries state. Usage credit is a small retention counter. PostgreSQL's global clock visits shared descriptors and ages unpinned credited entries before selecting a zero-credit candidate.

The clock searches without first choosing a policy group or its target capacity share (a quota), but it may revisit many descriptors. CUBRID first chooses a replacement list and bounds one scan of its cold LRU3 zone. That bound covers one search, while retries and dirty-page writes can still delay allocation.

PostgreSQL spends less state on detailed order and adds an explicit bulk-operation ring. CUBRID spends more state on group and zone policy. Neither choice proves lower overhead or a limit on a request's total waiting time.

11 · 14 / 21

The ring can supply a pin, then the write path can reject it

Start a new selection attempt. A backend is a server process handling a request. Its ring is a local array of shared frame IDs; each frame is a memory slot, not private page storage. Usage credit records retention preference, while a pin protects current identity.

The backend advances to the next slot. An empty slot, any existing pin, or credit above one sends it to the global clock; the selected ID replaces that slot. A successful ring claim already gives this backend a pin, but has not retired the page identity.

For a dirty page, the backend tries a share-exclusive content lock without waiting. This lock protects the page's bytes against mutation during writing. Failure releases the pin and retries; waiting could form a deadlock with another backend that holds this lock while waiting for pages held by the selector.

Ring sizes and strategy choices at this revision

BAS_NORMAL has no ring. BULKREAD, BULKWRITE and VACUUM use source-selected sizes. Bulk-read starts at 256 KiB, adds room for configured I/O concurrency, then applies its pin-limit cap. Every created ring is capped at NBuffers/8 entries. “Always 256 KiB” is therefore incorrect at this pin.

11 · 17 / 21

Checkpoint completion needs more than page writes

Suppose selected checkpoint pages have been written. Durable storage means the required data survives a crash; a write accepted by the operating system may still be in memory. OS writeback scheduling asks the system to push those bytes onward, without itself proving durability.

The checkpoint is the recovery boundary. After its page writes, PostgreSQL processes queued fsync requests, which synchronize storage. It later inserts the checkpoint log record and forces that record to durable WAL, the write-ahead recovery log.

Safe frame reuse is a separate current-state decision. A pin protects the current page identity. InvalidateVictimBuffer requires shared refcount one, its own pin, and no BM_DIRTY under mapping/header locks. New pins or changes after the page write can make this fail. Repeated changes and contention give no source-only bound on total waiting time.

Defend the check that preserves the later change

Fresh constructed case: A is the allocating backend; B is another backend; R is the permanent logged page in the selected frame. A wrote R, released content protection and kept its pin. B then pinned R, protected and logged a mutation, marked R dirty, and released its pin. No I/O is in progress.

A pin protects the current identity; releasing it does not write page bytes. Refcount counts pin references; ordinary backend pins contribute one per backend. DIRTY marks pending data-file work. At the protected invalidation check, which removes the old mapping, refcount is one and DIRTY is set.

Reveal the retirement argument

Refcount alone is insufficient. The proposal must exclude intervening changes or preserve their image through another protocol. Current BM_DIRTY makes the implemented path reject reuse. Separately record ring claims, global fallback visits, content-lock failures, bulk-read WAL rejection, and dirty/refcount invalidation failures. That distinguishes search pressure from write-path races. No cross-engine performance winner follows from this constructed case.

11 · 20 / 21

Reserve the old identity to prevent the intervening change

Teaching alternative, independently reset: a backend has selected a dirty page for reuse; no other backend or I/O holds a pin. A pin protects page identity. A new reservation would stop other lookups from pinning this old identity until retirement, rather than letting them intervene and checking afterward.

  1. Store a reservation with an owner and cancellation state. Every lookup/pin path must consult it under an agreed lock order.
  2. Hold a content lock to exclude mutations while bytes are written. Read the page's log position and force the matching write-ahead log (WAL) to durable storage.
  3. Write the stable bytes. Under mapping protection, verify sole ownership and clean state, then remove the old mapping before releasing the reservation.
  4. On error or cancellation, keep the old identity discoverable and retain pending dirty work. Clear the reservation before releasing its owner's pin.

This prevents the later-change race, but storage delays now block new readers and writers. All lookup/content paths and checkpoint interactions need consistent ordering and cleanup. The implemented protocol permits intervening use, then may abandon reuse even after writing successfully.
