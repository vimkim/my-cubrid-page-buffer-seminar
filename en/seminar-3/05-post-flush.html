Finishing a flush does not claim its frame

CUBRID page-buffer daemons and PostgreSQL page replacement

Repeated reads compete with a large scan for a finite set of memory slots. Modified pages also need to be written safely. Each constructed schedule starts independently; these examples are not recorded executions.

05 · 1 / 19

Why can an allocator still wait after a write?

Start a fresh example. Page P is a logical database page already held in a frame, a memory slot for one page. G names a stable copy of its bytes submitted for writing; this is reasoning notation, not a stored generation counter. Another request needs a frame, but no reusable frame has reached it.

The BCB (buffer control block) records which page occupies the frame and its current state. Its FLUSHING flag still records unfinished work for the submitted image. The flush waiter waits for that work to finish. An allocator waits for a frame it can reuse. Finishing one wait need not finish the other.

Track three separate actors: page-flush submits the image; post-flush may finish its BCB bookkeeping and offer the frame; the allocator must check the offer when it receives it. An offer can be withdrawn before reuse.

Which thread finishes a queued flush?

Assume page-flush has successfully submitted a page image and queued its BCB, the frame's control record. Page-flush is the producer because it inserts the pointer; the consumer is the post-flush daemon, a separate background thread that removes it. The wake gives that thread a chance to run; it is not a call into that thread.

Source: page_buffer.c:17072–17080 · page_buffer.c:15496–15556

The asynchronous boundary is flushed_bcbs, a bounded queue of BCB pointers. Delegation requires a page-flush producer, an existing post-flush daemon, a waiting allocator, and successful insertion. If any condition fails, the submitting thread finishes locally. Enqueue and local fallback.

05 · 3 / 19

What work crosses the queue?

Continue from successful image submission. The page bytes have entered either the DWB (double-write buffer, a separate staging area before the home-volume write) or the direct-write path. The BCB, the frame's control record, still needs completion bookkeeping: FLUSHING marks that unfinished work and flush waiters wait for it to finish. Page-flush is the submitting thread; post-flush is the background consumer; an allocator is a request thread needing a frame. LRU3 is the cold replacement zone; a private-list quota is its policy target for retained pages. Those current conditions affect a possible offer.

The queue carries one PGBUF_BCB *: an address of the frame's control record, with no page bytes. Post-flush locks that record, may offer a currently eligible frame, then finishes the old FLUSHING bookkeeping and wakes flush waiters. It starts no new page I/O. The pool owns this queue and the BCB storage; a queued pointer requires its record to remain alive. Old FLUSHING prevents ordinary victim reuse while completion is queued. The 8,192-entry capacity is compiled policy, not an operator setting.

Who finishes when the queue is full?

Q09 · The completion queue is full

Independent constructed starting state: Page P occupies a frame; G is its stable copied image, a reasoning label rather than a stored counter. Page-flush successfully submits that image. Its BCB, the frame's control record, still has FLUSHING=1 and flush waiters. Post-flush exists and an allocator waits, but the completion queue is full. Failed insertion leaves completion with the submitter.

With DWB (double-write buffer) enabled, submission may mean acceptance into staging before the home-volume write. This is a page-buffer submission boundary, not proof of transaction or disk durability.

Prediction: Which thread must finish the BCB bookkeeping for this submission?

Discuss, then reveal

The submitting page-flush thread reacquires the BCB mutex, clears the old FLUSHING state and wakes flush waiters locally. No pointer was published, so post-flush has no completion item for this submission. This fallback does not directly assign a frame to the waiting allocator.

The checkpoint submitter also takes this ordinary caller completion branch: is_page_flush_thread is false. The checkpoint is separate work that advances the database's recovery boundary.

05 · 6 / 19

Why does the consumer check current state?

Assume a BCB pointer was successfully queued after image submission. The BCB is a stable control record, but the page's current state can change before post-flush runs. Each fix protects a caller's use of the frame; fcnt counts outstanding fixes. DIRTY means modified bytes still need preservation. LRU3 is the cold replacement zone; a private-list quota is a retention target.

Post-flush removes a pointer and takes the BCB mutex, which protects the decision. Invalid flags, current fixes or any BCB-attached waiters block assignment. This waiter check conservatively includes attached flush waiters too. Moving to a hotter zone or a private list that is no longer over quota also rejects it. If all checks pass and a live allocator still waits, post-flush can publish a direct-victim offer: a reservation the allocator must later validate.

Whether or not it offers the frame, the consumer finishes old FLUSHING bookkeeping and wakes flush waiters. It drains until the queue is empty. Consuming any item resets the next pause to 1 ms, even when no allocator receives a frame; the looper's prior wake result also resets backoff. Idle waits progress through 1, 10 and 100 ms, then wake-only sleep. These are compiled policy values, not deadlines. There is no independent public post-flush enable or period setting.

Independent constructed starting state: Page P is resident; G labels its submitted stable image, not a stored counter. Its BCB, the frame's control record, is queued for post-flush. This list has 80 pages; quota changes from 60 to 100 before consumption.

At consumption the page is clean, in the cold LRU3 zone, has no fixes (outstanding protected uses), no BCB-attached waiters and no other blocking flag. An allocator still waits. The consumer uses the current quota and offers private-list frames only when the list is over it.

Prediction: How does the new quota affect the offer and the old completion?

Discuss, then reveal

The current list is no longer over quota: 80 does not exceed 100. This retention-policy check rejects direct assignment even though the frame is clean and unfixed. Post-flush still clears old FLUSHING and checks whether flush waiters need waking. This quota-only reset has no attached waiters; if they existed, the earlier waiter check would already block assignment.

Can a reader revoke an allocator offer?

Q11 · An offer can be revoked

Independent constructed starting state: Page P is resident and clean. B is an allocator waiting for a reusable frame; A is a reader about to use that same page. Post-flush has published a direct-victim offer for the frame to the allocator. This reservation is revocable. Before the allocator receives it, the reader fixes the page and retains that fix, protecting its use of the frame.

The BCB is the frame's control record. Its VPID identifies the resident page; identity can remain unchanged while use protection changes. The receiving allocator must lock the BCB and validate the offer and current eligibility.

Prediction: What must the allocator verify before reusing the frame?

Discuss, then reveal

pgbuf_get_direct_victim takes the offered slot, locks the BCB and checks for invalidation. One normal new fix can invalidate the offer without changing VPID. The helper also checks current victim eligibility, including flags and fixes/waiters. The allocator must not overwrite the reader's held frame; rejection returns no usable offer and leads to a retry.

Does releasing a clean page wake an allocator?

Start an independent constructed schedule. Every frame (memory slot for one page) is fixed: readers still have protected uses of it. An allocator has failed to find a reusable frame and sleeps. Readers then unfix clean pages, releasing their uses. Clean means no pending dirty write; unfixed means no remaining fix. Neither alone promises an immediate offer.

LRU3 is the cold replacement zone. On ordinary final unfix, a page there is usually boosted or moved from a session-associated private list to a shared list. It need not remain cold. Specific vacuum-worker or temporary-volume paths can assign an LRU3 frame directly; a vacuum path can also assign from VOID, outside LRU zones. Vacuum is background cleanup of obsolete database data.

Zone adjustment may offer a different BCB, the frame's control record, as it enters LRU3. That path checks eligibility, attempts the BCB mutex without waiting (trylock), then rechecks. Page-flush can also offer an already-clean candidate during its scan. Post-flush only consumes flushed_bcbs; it does not search all pages released by readers. The WRITE fix without modification fits this example only if the page was already clean.

Why is a later unfix still no promise of reuse?

Continue the clean-release example: readers have released clean pages and an allocator needs a frame. The direct-victim offer reserves a candidate for that allocator and wakes it, but is revocable. A new fix protects another reader's use and can invalidate the offer while VPID, the resident page identity, stays the same. The receiver takes the BCB (frame-control-record) mutex and checks current state before claiming it.

VS-20 identifies an entry in the uncertainty registry. At the pinned revision, both loops in the maintenance backup skip their bodies as written, so that backup is no guaranteed rescue. Other suppliers still exist. This constructed schedule neither records a runtime stall nor proves starvation, which would mean indefinite denial of progress.

Which event gives an allocator authority to reuse?

Review an independent candidate example. F is a frame, a memory slot with a stable BCB control record. P is the page originally nominated for writing; Q is another page that could later occupy that slot. VPID is the resident page identity. Remembering the frame's address does not preserve its identity or state.

After candidate collection and sorting, page-flush locks each BCB and compares the saved VPID with the current one. It also checks DIRTY (pending modified bytes), no existing FLUSHING, current use and cold-zone eligibility, then WAL for this logged-page path: the log records required to recover the copied image must be durable before page propagation. Even the same identity can gain a new fix, a new flush or a hotter zone across the gap.

Successful submission leaves completion bookkeeping. Page-flush may delegate it through the queue if a post-flush daemon and allocator waiter exist and insertion succeeds; otherwise it completes locally. Post-flush checks current eligibility, may publish an offer, and finishes old FLUSHING/wakeups. The allocator then performs its own protected receiving check. Only successful reception supplies a usable frame; later victimization still removes the old identity before reuse.

Verified mechanism: page_buffer.c:4040–4088 · page_buffer.c:15487–15660 · conditional delegation and fallback.

Remove only identity comparison: the remembered slot may now hold the other page, which could be flushed under the original nomination. Keeping all current flush guards shows incorrect selection attribution; it does not alone prove corruption. Removing current use or dirty checks creates a different safety counterexample.

Could a reservation remove the receiving race?

Start a teaching alternative with F, a frame holding a clean eligible page. An allocator needs that frame. The implemented offer allows another caller to fix (protect its use of) the page before receiving, so the allocator must recheck. The continuous reservation would instead exclude new users until the allocator consumes or cancels it.

Reserve the frame before leaving the protected interval. Transfer a token that names the reservation and keeps its BCB control record alive. Every lookup/fix path must respect the reservation; cancellation, abandoned waiters and shutdown must release it safely. It avoids this race by making new readers wait. Holding an LRU list mutex over I/O would also make unrelated list operations wait for storage.

This is a teaching design, not the pinned implementation. The implemented local fallback answers a different problem: unavailable post-flush or a full queue. The submitting thread still finishes old completion bookkeeping and wakes flush waiters; it need not offer the frame then. Removing the daemon does not require deleting completion.

05 · 16 / 19

Which work grows as more completions arrive?

Compare CPU work with waiting time. One page-flush pass scans replacement lists, sorts candidates when enabled and may examine neighbors. Post-flush instead consumes control-record pointers, skips stale allocator records and wakes flush waiters. These are structural operation counts; lock contention, atomic retries, scheduling and storage latency add elapsed time.

For the scan estimate, T counts separate thread-counter pieces whose values are combined, L counts replacement lists visited, K counts linked-list entries inspected, C counts candidates sorted, and N is the number of neighboring pages possibly examined per candidate. Reading, scanning, sorting and neighbor checks give O(T + L + K + C log C + C·N) work on the stated sorted/neighbor path.

For the queue estimate, Q counts BCB completion entries actually consumed, S counts stale allocator wait records skipped, and W counts flush waiters processed. Their work adds O(Q + S + W). The producer can refill the queue during consumption, so queue capacity does not bound a continuously refilled drain.

An observed fcnt=0 means no counted fixes; it still does not certify eligibility. pgbuf_is_bcb_fixed_by_any also checks waiting users. The control-record mutex protects the actual decision. The drain loop does not poll the daemon stop flag; requesting stop alone promises neither a time bound nor that every queued item will be drained.

D27 · Can old cleanliness authorize current reuse?

D27 · Queued facts can become stale

Independent constructed starting state: Page P is clean when its BCB (frame control record) is queued. The reviewer proposes storing “clean at enqueue” to replace consumer and receiving checks. The consumer decides whether to offer the frame; the allocator later decides whether to receive it. Between enqueue and consume, the page becomes hot, a writer fixes it, dirties it and unfixes. Prediction: Which checks express retention policy, and which omissions threaten safety?

Discuss, then reveal

Cold-zone/private-quota checks enforce retention policy. Current dirty and fix/invalid-victim checks protect pending work and ownership. Zero fixes after the writer leaves does not remove its dirty bytes. The queued boolean describes a past state.

05 · 18 / 19

Could completion and reservation have separate records?

Start a teaching redesign after an image has been accepted for writing. The submitting thread still owes completion bookkeeping; an allocator separately needs a reusable frame. The completion ticket would identify the old image and keep its control record alive. The distinct reuse reservation would record permission to claim the frame, subject to current protected checks.

  1. Acknowledge each completion ticket once, even if reuse is rejected.
  2. Grant a reservation only after checking the current frame under protection.
  3. Let new use cancel the reservation without cancelling old flush completion.
  4. Let the receiver atomically consume a valid reservation or retry. On cancellation or shutdown, drain tickets before reclaiming their storage.

These are requirements of the alternative, not guarantees of the pinned queue. Extra image/reservation identifiers and lifetime accounting keep stale records from becoming authority. The continuous reservation can instead block new use, with different contention costs. The actual queue-full path already finishes locally; completion can remain correct without this daemon.

Hypothesis
Completion can finish while the allocator receives no frame; failure to assign and failure to complete are different causes to investigate.
Controlled change
Keep image submission successful. Vary only the queue-full, new-dirty-write or later-fix event in its independently reset schedule.
Exact observation
Producer-specific assignment counters exist when enabled. Additional proposed probes correlate enqueue/dequeue, old FLUSHING clear, rejection reason, offer publication/revocation and protected receiving result by BCB and identity.
