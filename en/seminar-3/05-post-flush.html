Why a successful write does not immediately free a memory slot

From writing one page to safely reusing its memory

Follow the normal path of one memory slot first. Each later case resets to its stated starting conditions. All are constructed from source, not observed executions.

05 · 1 / 29

The page was written. Why can the memory slot still be unavailable?

A database reads and writes data in blocks called pages. The page in this story is P. P occupies one memory slot. A slot that holds one page is called a frame.

A request changed P and finished using it. A background worker copied the changed contents and sent the copy to the write path. That call succeeded. Sending memory contents to the write path is called a flush.

Another request needs a slot to read a new page. A successful write call does not empty P's slot automatically. The slot still contains P, and the program still has work to finish.

What remains? Finish this flush. Check whether the slot can be handed over now. Let the receiving request make its final check. We will follow these steps one at a time.

Here, “write success” means that the write-path call succeeded. An intermediate storage area may have accepted the copy, so this does not certify durable storage at the final disk location.

These examples are constructed from source, not measured executions. Read the normal path first, then compare three other situations. Source and policy details can be expanded in the later detailed explanation.

05 · 2 / 29

“Finish this write” and “Give me a slot”

Beside each frame is a record of its page, its users, and its unfinished work. This control record is called the BCB (buffer control block).

The BCB's FLUSHING marker means that this flush still needs completion handling. Even after the write call succeeds, the responsible worker must clear the marker.

A thread is an execution flow that performs work within the program. Waiting threads need different results.

Who waits?What do they need?
Flush waiter (request thread waiting for flush completion)“I am waiting for this page's ongoing flush to finish.” Completion handling must finish so it can continue its wait procedure.
Allocator (frame-allocation request thread)“Give me a frame to load another page into.” A frame it can receive and use.

The post-flush daemon handles completion for a queued BCB and wakes its flush waiters. It separately checks whether it can offer the frame to an allocator. Waking a flush waiter and giving the allocator a slot are separate actions. A wakeup is a notification that gives a thread a chance to run again. The notification alone proves neither write success nor receipt of a slot.

The next normal example has no waiter attached to this frame. An attached flush waiter would block a direct offer in this check. We examine that separate case after the normal path.

1. The write call for the page copy succeeds

Start of the normal example. Page P occupies one frame. The background thread that writes copies of changed pages is called page-flush. Another request, the allocator, is waiting for a slot. No competing request changes P during this example.

What happened: Page-flush sent P's copy to the write path, and the call succeeded. P has no later changes needing another write. This state is called clean.

What remains: P still occupies the slot. Its control record, the BCB, still has FLUSHING=1. The value 1 means that completion handling for this flush remains.

Result so far: The write call for the copy succeeded. Completion handling is unfinished, and the allocator has not received a slot. Follow the same slot in the next step.

05 · 4 / 29

2. Pass the slot record to the completion worker

Continue the same normal example. The write for page P's copy succeeded. Its slot's control record, the BCB, has FLUSHING=1, meaning completion handling remains. The allocator still waits for a slot.

A separate background thread called post-flush can help finish this work. The threads pass pending items through a queue named flushed_bcbs.

What is passed: Page-flush puts a BCB pointer in the queue. The pointer identifies the slot record to process. The queue does not carry another copy of the page contents.

In this example, post-flush exists, an allocator is waiting, and the queue has room. The submitter is page-flush. All four conditions hold, so delegation succeeds. If any condition fails, the submitting thread finishes the work itself.

Page-flush wakes post-flush. This gives it a chance to run; it does not call the post-flush function directly. The queued pointer records the pending work.

Result so far: Responsibility has passed to another worker. Completion handling remains, and the allocator still waits. Post-flush starts no new page write while processing this item.

05 · 5 / 29

3. Check the slot now, then offer it and finish completion handling

Continue the same normal example. The pointer to page P's control record, the BCB, is queued. P has no new changes and no current user. No attached waiter or other marker blocks reuse. P is in the replacement-candidate region, and current policy permits handing over this slot. The allocator is still waiting.

Why check again? Another request could use or change the page after insertion. Write success concerns an earlier copy. It does not guarantee the current state of the memory slot.

Post-flush removes the pointer from the queue and locks the BCB to check its current state. This lock, a mutex, protects the state check and decision together.

The checks pass in this example. Post-flush records an offer for one allocator that is still waiting and notifies it: “Try receiving this slot.” The offer can later be revoked.

The actual source order: Check current state first. The successful-offer branch sets the offer marker and clears FLUSHING together. The common completion tail ensures the marker is clear, wakes any flush waiters, and unlocks the BCB. This example has no attached waiter.

Result so far: Completion handling for the earlier flush has finished, and the slot has been offered. The allocator has not received it yet. The receiver's check remains.

Show the exact replacement policy for this example

P is in shared LRU3. LRU lists organize replacement order; LRU3 is their cold replacement-candidate region. A shared list does not require the private-list quota check, which applies a retention target. There is also no outstanding fix protecting a caller's use.

05 · 6 / 29

4. The receiver checks, then removes the old page identity before reuse

End of the same normal example. Post-flush offered page P's slot to the allocator and unlocked its BCB. P has no new changes or users, no waiter is attached, and the offer has not been revoked.

Why check once more? Another request could use P between offer and receipt. “Offered” and “received” happen at different times.

  1. The allocator takes its offered pointer. It locks the slot's BCB and checks that the offer has not been revoked.
  2. It rechecks current replacement conditions. They pass here. The allocator removes the BCB from the replacement list and returns it to the allocation path with its lock held.
  3. The allocation path removes the previous page identity. It deletes the old mapping that directed lookups for P to this slot. The slot can then be claimed for the requested new page.

Final result: The allocator obtained a usable slot. Write success, completion handling, a current-state check, an offer, receipt checks, and removal of the previous identity all took place.

The following cases do not continue this success. Each starts from its own reset state.

One wait can end while the request for a slot still waits

Separate starting state. The write for page P's copy succeeded, and its BCB pointer is in the completion queue. P has no later changes or user. Policy and other markers permit an offer. This time, a thread waiting for flush completion is attached to the BCB. The allocator waits for a slot separately.

What happens: Post-flush locks and checks the BCB. The attached flush waiter blocks an offer to the allocator in this check.

Work it still does: Post-flush clears the earlier FLUSHING marker, removes the flush waiter from the list, wakes it, and unlocks the BCB.

Result: The flush waiter can continue its wait procedure. The allocator received no offer in this pass. It needs a later opportunity or another supplier.

A thread waiting for one page's flush and an allocator seeking a slot use different registration paths. A notification to the flush waiter does not establish that the allocator received a slot.

Other situation 1: finish locally when the queue is full

Q09 · No room to pass work to another worker

Reset for a new case. Page-flush wrote page P's copy, and the call succeeded. Its BCB still has FLUSHING=1 and an attached flush waiter. Post-flush exists and an allocator waits, but the completion queue is full.

Problem: The BCB pointer cannot be inserted. Without posting the item, responsibility for completion does not pass to post-flush.

Required action: The submitting page-flush thread locks the BCB itself and clears the earlier FLUSHING marker. It wakes the flush waiter itself. It does not postpone completion until the queue has room.

Result: The successful write of the copy remains successful. Completion finishes, but this local branch does not directly assign a slot to the allocator.

05 · 9 / 29

Other situation 2: the page changes again after its copy was written

Reset for a new case. The write for page P's copy succeeded, and its BCB pointer was queued. Another thread changes P and keeps using it. P now contains changes absent from the earlier copy. A thread waiting for this flush's completion is also attached to the BCB. The allocator waits for a slot separately.

Why cannot the slot be handed over? The earlier copy lacks the new changes. Overwriting the slot could lose them and violate the current user's rights. A page with changes still needing preservation is called dirty.

What post-flush does: It locks the BCB and sees the current dirty state and use protection. It makes no offer. It still finishes completion handling for the earlier copy, clears FLUSHING, and wakes the attached flush waiter.

Result: The earlier work finished. The new changes remain dirty, and current use remains protected. The allocator did not receive this slot. Finishing the earlier work does not mean that the new changes were written.

05 · 10 / 29

Other situation 3: another request uses the page before receipt

Q11 · State can change after an offer

Reset for a new case. Page P occupies a frame and is clean, with no changes needing another write. B is the allocator offered this slot. A is a thread that wants to read P. Completion handling for the earlier flush has finished.

Before B receives the slot, A acquires the right to use P. This protection against reuse during a caller's use is called a fix. A retains its fix. Such a new fix can revoke B's offer.

Why check at receipt? A may be using P even though its name and contents are unchanged. Overwriting based only on the earlier offer would violate A's use.

Required action: B must lock the BCB and check revocation and current replacement conditions. It rejects this offer and seeks another candidate. A's later release does not automatically restore the old offer.

Think about it: Does “the page has not changed” mean “nobody is using it”?

Show the explanation

No. A read request also protects its use with a fix. The receiver must check current use and revocation as well as page identity. The source helper pgbuf_get_direct_victim performs the receiving check.

Find the source: enqueue, consume, or finish locally

The detailed explanation starts here. Page-flush can delegate remaining completion work after write success. Post-flush is a separate thread in the same server process. The inserting side is the producer; the removing side is the consumer.

The actual work-transfer boundary is the flushed_bcbs queue. Wakeup is a notification; the queue item records which BCB needs processing. The notification function does not directly call the consumer function.

BCB storage must remain valid until consumption. The buffer pool owns the queue and BCB storage. The outstanding FLUSHING marker blocks ordinary frame reuse.

Three structures hold different things

“Remove it from the queue and wake it” leaves the object and location unclear. Distinguish these three structures. A thread's management record is THREAD_ENTRY; a frame's control record is its BCB.

The last queue stores neither sleeping threads nor page bytes. It stores BCB pointers. When it is full, the submitter finishes locally.

Expand structure names and circular-queue internals

The first list starts at BCB.next_wait_thrd; each THREAD_ENTRY.next_wait_thrd links to the next item. The allocator queues are direct_victims.waiter_threads_high_priority and waiter_threads_low_priority, storing THREAD_ENTRY *.

The completion queue has type lockfree::circular_queue<PGBUF_BCB *>. It reuses positions in a fixed array in a circle. PGBUF_FLUSHED_BCBS_BUFFER_SIZE = 8 * 1024 permits 8,192 simultaneous pointers. This is compiled policy, not an operator setting.

m_data is the storage array. Atomic m_produce_cursor and m_consume_cursor manage insertion and removal positions. m_index_mask wraps positions around the array. Per-slot m_blocked_cursors prevent consumption of a pointer still being recorded. Checking a removed BCB's state requires a separate BCB mutex.

A writer lacking rate-control tokens waits separately on the shared bucket's condition variable. A condition variable is a synchronization tool for waiting for notification of a condition change.

Offer a slot and wake the request waiting for it

An allocator unable to find a slot registers in a separate wait queue, not a page's BCB list. A supplier searches that queue for a request still waiting. It skips records whose wait has already ended.

The supplier records an offered BCB pointer and notifies the request under the request's lock. Source calls notification before storing the pointer, but the receiver must reacquire that same lock to return from its wait. It cannot proceed to receipt before publication finishes.

Remaining check: The awakened allocator takes its pointer and locks the BCB to check revocation and current conditions. Notification does not itself establish frame receipt.

Expand wait functions, priorities, and offer storage

pgbuf_allocate_bcb registers with produce(thread_p) and waits in THREAD_ALLOC_BCB_SUSPENDED. thread_suspend_timeout_wakeup_and_unlock_entry waits on the thread's wakeup_cond using pthread_cond_timedwait. The wait has a timeout.

pgbuf_get_thread_waiting_for_direct_victim normally tries the high-priority queue first. Every fourth lookup tries the low-priority queue first. This selection policy alone proves no bound on waiting time or fairness.

pgbuf_assign_direct_victim locks the target entry and checks its waiting state. It notifies through thread_wakeup_already_had_mutex and records THREAD_ALLOC_BCB_RESUMED. It then sets the offer marker and clears FLUSHING, stores the pointer in direct_victims.bcb_victims[waiter_thread->index], and unlocks the entry.

The receiver, pgbuf_get_direct_victim, atomically empties its pointer slot and locks the BCB. Rejection makes the allocation path seek another candidate.

05 · 17 / 29

The queued record is from the past; permission depends on current state

Queueing a BCB pointer does not freeze page state. Another request may use or change it before post-flush consumes the item. Post-flush therefore decides from current state with the BCB locked.

  • New changes needing preservation or another blocking marker prevent an offer.
  • A fix protecting use or an attached BCB waiter prevents an offer. This includes a flush waiter.
  • Current replacement region and list-retention policy must allow an offer.
  • Even after passing the checks, an allocator must actually still be waiting.

Rejected offers still receive completion handling. Clear the earlier FLUSHING marker and wake any flush waiters. Preserve later dirty changes.

Expand check names and daemon waiting intervals

DIRTY marks changes still needing preservation. fcnt counts outstanding fixes. pgbuf_is_bcb_fixed_by_any(bcb, true) conservatively includes attached waiters. LRU3 is the cold replacement-candidate region. A private list must currently exceed its retention target, or quota.

The consumer removes items until the queue is empty. Consuming any item resets the next wait to 1 ms regardless of allocator receipt. A wake accepted by the looper also resets the increase. Idle waits progress through 1, 10, and 100 ms, then wait indefinitely for a wake.

These intervals are compiled policy, not completion deadlines. There is no independent public setting to enable, disable, or set the period of post-flush alone. Resetting the wait interval is not evidence of frame receipt.

Why does B receive no frame here?

B is a request thread waiting for a reusable frame. The flush waiters are waiting for P's existing flush to finish. These are different requests, registered in different places. Waking the flush waiters does not wake B or give B the frame.

  1. Failed insertion leaves no completion item for P. Post-flush may process other queued items, but it cannot consume a pointer that was never inserted. The submitting page-flush thread must finish this completion locally.
  2. The local branch finishes only the flush bookkeeping. Inside pgbuf_bcb_flush_with_wal, it locks the BCB, calls pgbuf_bcb_mark_was_flushed to clear FLUSHING, and calls pgbuf_wake_flush_waiters. That wake function visits the BCB's attached waiters and removes only requests for PGBUF_LATCH_FLUSH. B's separate allocator wait queue is not examined.
  3. Frame assignment needs another operation. pgbuf_assign_direct_victim selects a still-waiting allocator, stores the offered BCB in that thread's bcb_victims slot, and wakes it through the allocator protocol. The local completion branch never calls this function. Even a successful offer still needs the allocator's protected receiving check before reuse.

“Still waiting” describes this branch's result. It does not mean P can never be offered to B. Clearing FLUSHING removes one obstacle to reuse; it neither establishes every eligibility condition nor publishes an offer. This fallback creates no deferred post-flush item for P.

Local completion · Flush-waiter selection · Separate allocator assignment

Q&A · Is failed enqueue a failed page submission?

No in this scenario: submission has already succeeded. Enqueue failure decides who finishes the remaining BCB bookkeeping; it does not turn the accepted image into an I/O failure.

Q&A · Could page-flush assign the frame after waking the flush waiters?

A submitting thread is not inherently forbidden from supplying a frame. The pinned fallback simply has no assignment step. Adding one would need current clean-state, fix and attached-waiter checks, replacement-policy checks, and the allocator's publication/wake protocol. Calling a wake function alone would not supply a frame. Even post-flush checks assignment before waking flush waiters; an attached flush waiter blocks that offer, and the same consumer pass does not retry assignment after removing it.

Conservative attached-waiter check · Consumer checks, then completion and wake

Q&A · How can B obtain a frame later?

A later page-flush candidate scan can directly offer a frame that is now clean and reusable. Another post-flush item may also supply an eligible frame. These paths call pgbuf_assign_direct_victim only when their checks pass. A supplier must find a live allocator waiter, and B must validate any offer it receives. P need not be that frame; this example promises neither a later offer for P nor a deadline for B.

A released page does not automatically go to another request

Separate starting state. Every frame has an outstanding fix protecting use. The allocator cannot obtain a slot and waits. Later, read requests release their page use. This release is called unfix.

A page with no changes awaiting preservation is clean. A page with no outstanding fix is unfixed. Even if both hold, releasing use and handing the slot to another request are separate actions.

An ordinary final unfix can change replacement order or move the page between lists. The released page need not remain a cold candidate. Post-flush handles only the completion queue; it does not search all released clean pages.

Expand other suppliers and their exact conditions

An ordinary unfix in LRU3, the cold candidate region, normally boosts the page or moves it from a private list to a shared list. Private is a session-associated policy category.

Specific vacuum-worker and temporary-volume paths can offer LRU3 frames directly. Vacuum is background cleanup of obsolete database data. Its worker path can also offer from VOID, outside replacement regions.

Region adjustment may offer another frame entering LRU3. This path checks conditions, attempts the BCB mutex without waiting using trylock, and rechecks. Page-flush can also offer an already-clean candidate found during traversal.

Releasing an unchanged WRITE fix belongs to this case only if the page was already clean.

Later release does not automatically restore a revoked offer

Continue the release case. Users have released their fixes on clean pages. The allocator still needs a slot. If an earlier offer was revoked, the receiver must check revocation and follow the acquisition procedure again. An unchanged page name or lower fix count does not validate the old offer.

Another supplier may make a new offer. Establish which path resolved this wait from its actual execution and current conditions.

The same memory address need not mean the same page

Separate candidate example. F is a memory slot, or frame. P was the page originally selected for writing. Q is another page that could later occupy the same slot. The BCB storage address may remain stable while the slot's page and state change.

The current page identity is its VPID. A record of P at selection does not establish P later. Before writing, page-flush locks the BCB and compares the saved identity with its current identity.

Even unchanged identity leaves more checks: current use, changes needing preservation, an existing flush, and the current replacement region. For logged page paths, the WAL rule requires preservation of necessary recovery log before the page write.

Checks also follow the write. Post-flush decides whether to offer the current slot. The allocator rechecks at receipt. Before loading a new page, the old lookup mapping for P must be removed.

Consider removing only the identity comparison

With other checks retained but identity comparison removed, a slot now holding Q could be processed as the original candidate P. This counterexample shows a mismatch in selection identity. It is not an observed corruption result. Removing dirty or use-protection checks produces a different safety counterexample.

What extra responsibilities come with a retained reservation?

Reset for a design alternative. F is a frame holding a clean page that passes offer checks. Another request can fix it before allocator receipt, so the implementation rechecks.

An alternative is a retained reservation blocking new users until handoff. Excluding a new reader avoids this race. The reader must instead wait or retry its lookup.

New responsibilities: Every lookup and fix path must respect the reservation. Someone must release it if the receiver cancels, disappears, or the server shuts down. The reservation must also retain the lifetime of its referenced BCB.

Compare lock cost and the local completion branch

Holding an LRU-list lock throughout write I/O makes unrelated list operations wait for storage. Reservation needs its own design for which operations it blocks and for how long.

The actual local completion branch solves another problem. When delegation is unavailable, the submitter finishes the flush and wakes its waiters without needing to offer a slot. Completion can remain correct without post-flush, but this branch itself does not assign that frame.

05 · 27 / 29

Why queue capacity does not determine processing time

Simultaneous queue capacity differs from the total items processed in one pass. Page-flush can insert more items while post-flush consumes them. Queue capacity is therefore not a bound on total work or completion time.

Skipping stale allocator records, waking flush waiters, lock contention, and scheduling add cost. The formulas below describe structural operation counts, not measured time.

In the traversal formula, T counts per-thread counter shards read, L lists visited, and K list entries inspected. C counts candidates sorted; N counts possible neighbor pages inspected per candidate.

In the queue formula, Q counts BCB items actually consumed, S stale allocator records skipped, and W flush waiters processed. Here Q is a cost variable, separate from the earlier page name.

Expand operation counts and stopping conditions

A traversal path with sorting and neighbor inspection costs O(T + L + K + C log C + C·N) operations. Queue and waiter work adds O(Q + S + W). Atomic retries and storage delay also affect elapsed time.

fcnt=0 observes no outstanding fixes; it does not certify waiter or other eligibility checks. The BCB mutex protects the actual decision. The queue-consumption loop does not check the daemon stop flag, so a stop request establishes neither a completion deadline nor processing of every item.

An alternative also separates completion responsibility from reuse permission

Reset for a design alternative. The copy's write call succeeded. The submitter has completion responsibility; the allocator needs a usable slot. Suppose separate records manage these two jobs.

A completion ticket records which earlier copy needs completion handling. A reuse reservation records permission to claim a slot after current checks. Both must retain the lifetime of the BCB they reference.

  1. Process each completion record exactly once even when the slot cannot be offered.
  2. Create a reservation only after protected current-state checks.
  3. New use may cancel a reservation without cancelling completion of the earlier write.
  4. The receiver atomically consumes a valid reservation or retries. Cancellation and shutdown require an owner to clean up records and storage.

These are requirements for a teaching alternative. They do not describe tickets and reservations implemented by the pinned queue. The actual implementation already has a local completion path for failed delegation.
