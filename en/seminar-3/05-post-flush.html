Finishing a flush does not claim its frame

CUBRID page-buffer daemons and PostgreSQL page replacement

Repeated reads compete with a large scan for a finite set of memory slots. Modified pages also need to be written safely. Each constructed schedule starts independently; these examples are not recorded executions.

05 · 1 / 28

The copy was submitted. What remains?

A frame is a memory slot that holds one page. Page-flush has submitted a copy of the page's bytes for this flush. The submission call succeeded, but the frame's control record still has a FLUSHING flag recording unfinished completion work.

CUBRID must clear that flag and wake any threads waiting for this flush's completion. Post-flush is a background thread that can take over this remaining work from page-flush. This moves some post-submission work to another thread while requests are waiting for frames.

If a request needs a frame, post-flush may also inspect the current state and offer this frame. The offer can be revoked, so the receiving request must check again.

Finishing the old flush's completion work and another request acquiring the frame are separate events.

Successful submission alone does not establish completion at the page's final disk location or durable storage. The write path may first accept the copy into the DWB (double-write buffer), a staging area before the home-volume write.

Conditional delegation and local completion

First follow one successful handoff. Then compare three independent failures before the maintainer analysis.

Q&A · What is missing between a successful write and a usable frame?

Old-flush bookkeeping must finish, current offer checks must pass, and the allocator must receive a still-valid offer. A newer dirty write or caller fix can prevent the last steps.

05 · 2 / 28

Two waiters ask for different results

A frame holds a database page. Its BCB (buffer control block) is the control record for the frame's identity and state. A flush waiter is a thread waiting for an existing flush's completion work. An allocator is a request thread looking for a frame to hold a page.

Waiting threadWhat must happen
Flush waiter: “Finish this flush.”The thread handling completion clears the old FLUSHING state and wakes flush waiters attached to this BCB. Waking a thread lets it resume its wait protocol; the notification alone proves neither I/O success nor durability.
Allocator: “Give me a reusable frame.”A supplier offers an eligible frame. The allocator wakes and checks the offer under the BCB mutex, which protects the state decision. Successful receipt is followed by removal of the old page identity before reuse.

The flush waiter registers on the BCB. The allocator registers in a separate frame-wait queue. A third queue carries BCB pointers for post-flush completion work. We will inspect these structures later.

Example boundary: the successful handoff below has no BCB-attached waiter. A flush waiter attached to this frame would block its direct offer in that consumer pass. Its completion gets a separate example.

2. Post-flush checks the frame and publishes an offer

Continue the successful example. Page P is still clean, with no caller's fix, no BCB-attached waiter and no other blocking flag. It remains in shared LRU3, the cold zone. The BCB is the frame's control record; its pointer is queued with FLUSHING=1, meaning old completion work remains. The allocator still waits in its separate queue.

  1. Post-flush removes the pointer and locks the BCB. The BCB mutex gives it exclusive access for this state decision. It checks current flags, protected uses, attached waiters and cold-zone membership. This shared-list frame needs no private-quota check.
  2. The checks pass; post-flush publishes an offer and wakes the allocator. It verifies that the selected allocator still waits, then publishes the candidate and wakes it in a protected operation. In this successful branch the flag update marks the direct offer and clears FLUSHING together. The allocator has not received the frame yet.
  3. Post-flush finishes the completion pass and unlocks the BCB. It ensures old FLUSHING is clear and checks for flush waiters to wake. This starting state has none. The allocator's receiving check must acquire this BCB mutex before proceeding.

State now: FLUSHING=0; an offer is published; the old page identity is still P. The offer grants no permission to overwrite the frame without the receiving checks.

3. The allocator checks and receives the offered frame

Continue the successful example. The allocator is a request thread needing a frame. Post-flush has finished the old flush's completion work and offered the frame holding page P. Its BCB (frame control record) is unlocked. P is still clean and unfixed, no BCB waiter has appeared, and no reader or writer has cancelled the offer.

  1. The allocator resumes and takes its offered pointer. A wake only provides an opportunity to run. The allocator takes the pointer offered to it and locks the BCB.
  2. The allocator validates current permission. It checks whether another caller revoked the offer, removes the offer flag and rechecks whether the frame is a valid reuse candidate. On success it removes this BCB from the replacement list and returns it still locked.
  3. The allocation path removes the old page identity before reuse. It performs victimization: another protected check and deletion of P's old lookup mapping. Only then can the frame be claimed for the requested page identity.

Successful result: the old completion is finished and the allocator has obtained a frame through the protected path. The next examples restore their own starting states; they do not continue this reuse.

Why does B receive no frame here?

B is a request thread waiting for a reusable frame. The flush waiters are waiting for P's existing flush to finish. These are different requests, registered in different places. Waking the flush waiters does not wake B or give B the frame.

  1. Failed insertion leaves no completion item for P. Post-flush may process other queued items, but it cannot consume a pointer that was never inserted. The submitting page-flush thread must finish this completion locally.
  2. The local branch finishes only the flush bookkeeping. Inside pgbuf_bcb_flush_with_wal, it locks the BCB, calls pgbuf_bcb_mark_was_flushed to clear FLUSHING, and calls pgbuf_wake_flush_waiters. That wake function visits the BCB's attached waiters and removes only requests for PGBUF_LATCH_FLUSH. B's separate allocator wait queue is not examined.
  3. Frame assignment needs another operation. pgbuf_assign_direct_victim selects a still-waiting allocator, stores the offered BCB in that thread's bcb_victims slot, and wakes it through the allocator protocol. The local completion branch never calls this function. Even a successful offer still needs the allocator's protected receiving check before reuse.

“Still waiting” describes this branch's result. It does not mean P can never be offered to B. Clearing FLUSHING removes one obstacle to reuse; it neither establishes every eligibility condition nor publishes an offer. This fallback creates no deferred post-flush item for P.

Q&A · Is failed enqueue a failed page submission?

No in this scenario: submission has already succeeded. Enqueue failure decides who finishes the remaining BCB bookkeeping; it does not turn the accepted image into an I/O failure.

Q&A · Could page-flush assign the frame after waking the flush waiters?

A submitting thread is not inherently forbidden from supplying a frame. The pinned fallback simply has no assignment step. Adding one would need current clean-state, fix and attached-waiter checks, replacement-policy checks, and the allocator's publication/wake protocol. Calling a wake function alone would not supply a frame. Even post-flush checks assignment before waking flush waiters; an attached flush waiter blocks that offer, and the same consumer pass does not retry assignment after removing it.

Q&A · How can B obtain a frame later?

A later page-flush candidate scan can directly offer a frame that is now clean and reusable. Another post-flush item may also supply an eligible frame. These paths call pgbuf_assign_direct_victim only when their checks pass. A supplier must find a live allocator waiter, and B must validate any offer it receives. P need not be that frame; this example promises neither a later offer for P nor a deadline for B.

The old copied job can finish separately. Its completion preserves the newer DIRTY obligation, which another flush must handle; joining both would erase the distinction this protocol maintains.

Recap: completion, wake, offer and receipt are separate

A submitted image is the copy of page bytes chosen for one write. A frame holds the current resident page; its BCB is its control record. The old FLUSHING flag records outstanding completion work. A flush waiter needs that work finished; an allocator needs a reusable frame. A direct-victim offer is a revocable offer to the allocator, whose protected receiving check still remains.

The submitting thread completes locally when delegation cannot be used. When delegation succeeds, the consumer completes the old flush even if current state prevents an offer. An attached flush waiter itself blocks the offer during that pass. Each failure example above starts independently.

Q&A · What keeps a queued BCB pointer from naming reclaimed pool memory?

The pool must outlive the consumer and its queued work. The pointer itself is not a lifetime guarantee. Old FLUSHING also excludes ordinary victim reuse until the delegated completion is processed.

The asynchronous boundary is flushed_bcbs, a bounded queue of BCB pointers. Delegation requires a page-flush producer, an existing post-flush daemon, a waiting allocator, and successful insertion. If any condition fails, the submitting thread finishes locally. Enqueue and local fallback.

  3. thread_wakeup_already_had_mutex() signals the target's condition variable and records THREAD_ALLOC_BCB_RESUMED. Then store the BCB pointer in pgbuf_Pool.direct_victims.bcb_victims[waiter_thread->index] before releasing the entry mutex.

The source signals before storing the pointer, but the awakened thread must reacquire that same entry mutex before its wait returns. The pointer is therefore published before that return. pgbuf_get_direct_victim() atomically empties its slot to obtain the pointer, locks the BCB, and checks offer cancellation and current reuse conditions. A rejected offer sends the allocator back to seek a candidate.

Waking flush waiters and offering a frame to an allocator thus use different lists, states and receiving procedures.

Q&A · Why is signaling before storing the offered pointer safe in this sequence?

Both happen while holding the target entry mutex. The awakened wait must reacquire that mutex before returning, so it cannot return past publication while the producer still holds the lock.

05 · 17 / 28

Why does the consumer check current state?

Assume a BCB pointer was successfully queued after image submission. The BCB is a stable control record, but the page's current state can change before post-flush runs. Each fix protects a caller's use of the frame; fcnt counts outstanding fixes. DIRTY means modified bytes still need preservation. LRU3 is the cold replacement zone; a private-list quota is a retention target.

Post-flush removes a pointer and takes the BCB mutex, which protects the decision. Invalid flags, current fixes or any BCB-attached waiters block assignment. This waiter check conservatively includes attached flush waiters too. Moving to a hotter zone or a private list that is no longer over quota also rejects it. If all checks pass and a live allocator still waits, post-flush can publish a direct-victim offer: a reservation the allocator must later validate.

Whether or not it offers the frame, the consumer finishes old FLUSHING bookkeeping and wakes flush waiters.

Consumed-work reset · Wake reset · Compiled pauses

Daemon pause policy and reset conditions

It drains until the queue is empty. Consuming any item resets the next pause to 1 ms, even when no allocator receives a frame; the looper's prior wake result also resets backoff. Idle waits progress through 1, 10 and 100 ms, then wake-only sleep. These are compiled policy values, not deadlines. There is no independent public post-flush enable or period setting.

Q&A · Does backoff reset mean an allocator received a frame?

No. Consuming a completion item resets backoff even if current checks reject assignment or no live allocator is found. An accepted wake can also reset it.

Q&A · Can an attached flush waiter itself block a direct offer?

Yes. The consumer’s conservative attached-waiter check includes flush waiters. It can reject assignment, then still finish the old flush and wake those waiters.

Does releasing a clean page wake an allocator?

Start an independent constructed schedule. Every frame (memory slot for one page) is fixed: readers still have protected uses of it. An allocator has failed to find a reusable frame and sleeps. Readers then unfix clean pages, releasing their uses. Clean means no pending dirty write; unfixed means no remaining fix. Neither alone promises an immediate offer.

LRU3 is the cold replacement zone. On ordinary final unfix, a page there is usually boosted or moved from a session-associated private list to a shared list. It need not remain cold. Specific vacuum-worker or temporary-volume paths can assign an LRU3 frame directly; a vacuum path can also assign from VOID, outside LRU zones. Vacuum is background cleanup of obsolete database data.

Zone adjustment may offer a different BCB, the frame's control record, as it enters LRU3. That path checks eligibility, attempts the BCB mutex without waiting (trylock), then rechecks. Page-flush can also offer an already-clean candidate during its scan. Post-flush only consumes flushed_bcbs; it does not search all pages released by readers. The WRITE fix without modification fits this example only if the page was already clean.

Q&A · Does every final unfix of a clean page directly wake an allocator?

No. Ordinary release can boost or move the page instead. Direct offers depend on particular producer paths and current eligibility; post-flush does not scan every newly unfixed clean page.

Could a reservation remove the receiving race?

Start a teaching alternative with F, a frame holding a clean eligible page. An allocator needs that frame. The implemented offer allows another caller to fix (protect its use of) the page before receiving, so the allocator must recheck. The continuous reservation would instead exclude new users until the allocator consumes or cancels it.

Reserve the frame before leaving the protected interval. Transfer a token that names the reservation and keeps its BCB control record alive. Every lookup/fix path must respect the reservation; cancellation, abandoned waiters and shutdown must release it safely. It avoids this race by making new readers wait. Holding an LRU list mutex over I/O would also make unrelated list operations wait for storage.

This is a teaching design, not the pinned implementation. The implemented local fallback answers a different problem: unavailable post-flush or a full queue. The submitting thread still finishes old completion bookkeeping and wakes flush waiters; it need not offer the frame then. Removing the daemon does not require deleting completion.

Q&A · What happens if a continuously reserved allocator abandons its request?

The alternative needs an explicit cancellation owner to release the reservation and lifetime reference safely. Otherwise new users can remain excluded even though no allocator will consume the frame.

Which work grows as more completions arrive?

Compare CPU work with waiting time. One page-flush pass scans replacement lists, sorts candidates when enabled and may examine neighbors. Post-flush instead consumes control-record pointers, skips stale allocator records and wakes flush waiters. These are structural operation counts; lock contention, atomic retries, scheduling and storage latency add elapsed time.

For the scan estimate, T counts separate thread-counter pieces whose values are combined, L counts replacement lists visited, K counts linked-list entries inspected, C counts candidates sorted, and N is the number of neighboring pages possibly examined per candidate. Reading, scanning, sorting and neighbor checks give O(T + L + K + C log C + C·N) work on the stated sorted/neighbor path.

For the queue estimate, Q counts BCB completion entries actually consumed, S counts stale allocator wait records skipped, and W counts flush waiters processed. Their work adds O(Q + S + W). The producer can refill the queue during consumption, so queue capacity does not bound a continuously refilled drain.

An observed fcnt=0 means no counted fixes; it still does not certify eligibility. pgbuf_is_bcb_fixed_by_any also checks waiting users. The control-record mutex protects the actual decision. The drain loop does not poll the daemon stop flag; requesting stop alone promises neither a time bound nor that every queued item will be drained.

Could completion and reservation have separate records?

Start a teaching redesign after an image has been accepted for writing. The submitting thread still owes completion bookkeeping; an allocator separately needs a reusable frame. The completion ticket would identify the old image and keep its control record alive. The distinct reuse reservation would record permission to claim the frame, subject to current protected checks.

  1. Acknowledge each completion ticket once, even if reuse is rejected.
  2. Grant a reservation only after checking the current frame under protection.
  3. Let new use cancel the reservation without cancelling old flush completion.
  4. Let the receiver atomically consume a valid reservation or retry. On cancellation or shutdown, drain tickets before reclaiming their storage.

These are requirements of the alternative, not guarantees of the pinned queue. Extra image/reservation identifiers and lifetime accounting keep stale records from becoming authority. The continuous reservation can instead block new use, with different contention costs. The actual queue-full path already finishes locally; completion can remain correct without this daemon.

Q&A · Why acknowledge completion separately from reservation cancellation?

Cancelling reuse permission does not undo successful image submission. Separate records let old completion finish exactly once while a stale or unsuitable reuse reservation is rejected.
