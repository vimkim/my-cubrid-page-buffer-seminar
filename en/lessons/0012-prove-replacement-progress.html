01 · The one question

A page miss needs a frame; where does that frame come from?

If an unused BCB/frame pair exists on the INVALID list, CUBRID pops it. No resident page is removed. Only after INVALID is empty does CUBRID search the cold end of an LRU for a resident page that is safe to replace.

Replacement changes the VPID and bytes inside a fixed BCB/frame pair. It does not manufacture a new pair and does not swap BCB A to another frame.

The short route is: INVALID pop → load in VOID → final unfix places the BCB in an LRU → list pressure demotes it toward LRU3 → a clean idle LRU3 BCB may be detached → its old hash identity is removed → the same pair is rebound.

02 · Pinned defaults, calculated

512 MiB means 32,768 BCB/frame pairs at the default 16 KiB page size

This example assumes data_buffer_size = 512M, max_clients = 100, ha_mode = off, and the default 16 KiB I/O page.

512 × 1,024 × 1,024 / 16,384 = 32,768 pages

normal clients 100 + admin 1 + HA 0 + system 1 = MAX_NTRANS 102
minimum buffers = 10 × 102 = 1,020, so configured 32,768 remains

shared S  = max(4, min(102, floor(32,768 / 1,000))) = 32
private P = 102 + VACUUM_MAX_WORKER_COUNT 50 = 152
all LRU descriptors L = S + P = 184

max_clients is still 100. The internal page-buffer formulas use MAX_NTRANS = 102 because they also include one admin connection and one system transaction. HA can add more reserved connections. The 512 MiB covers frame bytes; BCBs, mutexes, hashes, and list metadata are additional memory.

Startup snapshot: all 32,768 BCBs are on INVALID. The 184 LRU descriptors already exist but are empty. “152 private LRUs” does not mean 152 owners or 152 prefilled partitions.

Verified defaults: system_parameter.c:1169–1189,1569–1582,2329–2342; storage_common.h:91–99; connection_globals.c:84–112,158–245; log_common_impl.h:48–52; page_buffer.c:81–84,1713–1721,5740–5766,13941–13985.

03 · Five list-membership states

VOID means the BCB is outside every management list

StatePlain meaningVictim search?
INVALIDOn the global free/invalid singly linked list; no resident VPID.Allocation pops it directly in O(1).
VOIDOn neither INVALID nor any LRU. It may be loading, fixed before first placement, moving, or detached under protection.No LRU scan can see it.
LRU1Hot protected part of one LRU.No.
LRU2Protected second-chance part.No.
LRU3Cold part and the only ordinary victim-search zone.Yes, but safety checks may reject every node.

A newly loaded resident page can remain VOID during its entire first fix. Its VPID may already be in the resident hash and its fcnt may be positive. VOID says nothing about identity, ownership, dirty state, or whether overwriting is legal. It says only that prev_BCB/next_BCB do not currently link the BCB into INVALID or an LRU.

Verified mechanism: page_buffer.c:174–216,5559–5667,6636–6994,8904–8952,15860–15986.

04 · One BCB's complete trip

BCB A can age without a clock ticking it down

  1. Startup: A is an INVALID-list node paired permanently with frame A.
  2. First miss for page P: pgbuf_get_bcb_from_invalid_list() pops A. A becomes VOID, receives VPID P, loads P's bytes, and is fixed.
  3. First final unfix: when global fcnt reaches zero, A enters private LRU1 top when the thread has a private domain; otherwise it enters shared LRU2 middle.
  4. Cooling: later insertions make protected zones exceed their thresholds. pgbuf_lru_adjust_zones() demotes old boundary nodes LRU1 → LRU2 → LRU3. Time alone does not move A.
  5. Second chance: if P is fixed again, a final unfix from LRU3 normally boosts A to LRU1. A must cool again.
  6. Victim: if A stays clean and idle in LRU3, a selected scan may lock and detach it to protected VOID.
  7. Rebind: pgbuf_victimize_bcb() rechecks A, removes P from the resident hash, and the miss path binds the same A/frame pair to page Q.

“Candidate,” “detached,” and “victimized” are different moments. LRU3 membership makes A searchable. Detach removes it from the LRU but old P is still hash-visible. Victimization removes P's identity. Only then can Q own the pair.

pgbuf_get_victim_from_lru_list() receives one already selected LRU index. It starts at victim_hint or bottom and follows prev_BCB through at most 1,000 BCB nodes. It does not scan 1,000 lists or all transactions. Private threshold demotions D can happen before this bounded walk.

06 · Private LRU assignment and activity

A context borrows a private-LRU index

pgbuf_assign_private_lru() scans all P private descriptors: first choose a zero-session list with the fewest BCBs; if none is idle, choose the least-active list. It increments session_cnt[p] and returns private-local p. The executing thread carries private_lru_index = p; a BCB stores the full index S + p.

The scan is O(P), with one initial attempt and up to five retries if an idle candidate is stolen concurrently. It runs when a session/vacuum context receives an assignment, not on every fix. Multiple sessions can use the same private LRU. When a session releases the assignment, pgbuf_release_private_lru() decrements its count; release does not empty or move its BCBs.

What “activity” measures

On an ordinary final unfix, pgbuf_bcb_register_hit_for_lru() lets one BCB contribute at most one hit in one accepted adjustment epoch. Only an accepted pgbuf_adjust_quotas() increments adjust_age; a daemon call every 100 ms does not necessarily increment it because early-return conditions can reject the pass.

An accepted pass uses ATOMIC_TAS_32 to take and reset each list's lru_hits, converts hits to a per-second rate, and smooths private activity over ten seconds. Quota follows each private list's activity share, capped at 5,000 BCBs and N/2. LRU1 and LRU2 thresholds are each 5% of that quota. The structural work is O(T + L + D).

Verified mechanism: page_buffer.c:14251–14624,16594–16610,16994–17009,17146–17161; session.c:729–744; server_support.c:2069–2087.

07 · Final-unfix movement

Private → shared preserves single-list membership

Ordinary movement happens only when an unfix changes global fcnt to zero. pgbuf_should_move_private_to_shared() requests migration when the unfixing thread's private index differs from the BCB's private list, or when a same-domain page is both hot and old enough.

The path is private LRU → VOID → shared LRU2 middle. The source unlinks under the private-list mutex, releases it, chooses a destination with pgbuf_get_shared_lru_index_for_add(), and links under the shared-list mutex. The BCB mutex remains held between the two list operations.

A known-node unlink/link is O(1), plus D zone demotions: O(1 + D). Shared destination choice is amortized O(1) and has a periodic O(S) balance scan, so migration has a periodic O(S + D) case, excluding lock wait.

Do not read “private” as access control. A different transaction can fix the page. Domain mismatch on its final unfix is exactly one reason the BCB migrates to shared.
08 · When no safe victim exists

CUBRID waits until a BCB becomes safe to reuse

If INVALID is empty and normal search finds nothing, pgbuf_allocate_bcb() can enter a direct-victim waiter queue and wake the flush daemon. A producer may clean and reserve a BCB. If another fix reaches it before consumption, the reservation is revoked and the allocator retries.

A DIRTY LRU3 BCB becomes reusable only after WAL-safe page write completion. During the write, FLUSHING still blocks replacement. If the page is dirtied again as generation G+1, that newer debt prevents direct assignment.

Every allocation path ends in assignment, retry, interrupt, timeout, or explicit error. ER_PB_ALL_BUFFERS_DIRTY is a fallback error name and does not prove that every BCB was literally dirty. The source does not prove wall-clock fairness for one waiter.

Verified mechanism: page_buffer.c:8181–8403,9067–9253,10925–10952,15420–15652,16972–17255.

The explicit private-list parameter can reach 4,050. The automatic formula MAX_NTRANS + 50 is derived separately and is not clamped by the shared-list 1,000 limit. Victim search still consumes an advertised list index; it does not enumerate those descriptors on every miss.

10 · Check your model

Can BCB A be reused now?

Start with default startup. Load page P into BCB A, final-unfix it, demote it to LRU3, then consider three variants: A is clean and idle; A is DIRTY; another thread fixes A just before the scan. For each variant, name the current list/zone, the first rejecting field or lock, and the event required before A can be rebound to page Q.

Model spine: INVALID avoids victimization → VOID is unlinked, not free → only LRU3 is searched → flags/owners/waiters/try-lock/final recheck decide → detach to VOID precedes hash removal → the fixed pair receives Q.
