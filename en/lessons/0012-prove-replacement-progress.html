01 · Keep the layers

Policy finds candidates; eligibility authorizes reuse

Replacement progress decides where to search, who should flush, whether an allocator waits, and how a candidate reaches it. None of those choices weakens Lesson 7’s hard gate: stable identity, no owner/waiter conflict, no DIRTY/FLUSHING debt, and protected final revalidation.

A fast candidate hint and a direct reservation are search results—not permission to rebind a frame.

02 · Objects and lifetime

LRUs are created at pool initialization; transactions only borrow a private-list assignment

N BCB/frame slots and S + P LRU objects have pool lifetime. A resident BCB is linked into exactly one doubly linked LRU only after its first zero-crossing unfix.

  1. Startup: pgbuf_initialize_bcb_table() chains all N = num_buffers BCBs through next_BCB. invalid_top points at BCB 0 and invalid_cnt = N. Every shared/private LRU object already exists but has null top/bottom/boundaries and zero counts.
  2. First miss: allocation pops the invalid head in O(1), loads a page into that fixed BCB/frame slot, and leaves it in VOID while fixed. The BCB and its frame remain the same array-index pair for pool lifetime; the page identity stored in that pair changes after legal victimization.
  3. First unfix to zero: with the pinned default AOUT-disabled path, a private-domain page joins that private LRU1 top; a page without a private domain joins a shared LRU2 middle.
  4. Heavy pressure: the invalid list can reach zero. Resident BCBs occupy the LRU zones, dirty LRU3 pages require flush progress, clean eligible LRU3 pages are advertised as candidates, and allocators search or wait. There is no second hidden reserve of BCB/frame pairs.
Three lifetimes: the LRU array lives from page-buffer initialization to finalization; a context-to-private-LRU assignment lives from assignment to release and can be shared by several contexts; a BCB's list membership changes on placement, boost, demotion, removal, and reuse.

Verified mechanism: BCB chain page_buffer.c:5590–5650; invalid-list initialization/pop 5907–5920,8923–8950; LRU array initialization 5744–5800; placement 6636–7040.

Worked private-list example: if quota adjustment gives one private list Q = 1,000, its LRU1 threshold is 50 and LRU2 threshold is 50. If the list currently contains 1,000 resident BCBs, roughly 900 positions remain in LRU3 after adjustment. If it contains 1,150, quota does not reject 150 pages; it makes the list over quota and therefore an earlier victim source.

Quota adjustment normally returns early before doing this work unless enough activity/time has accumulated. When it runs, it traverses all L = S + P LRU descriptors and may demote the current excess of LRU1/LRU2 nodes. Therefore its structural cost is O(L + D), where D is the number of nodes demoted in that adjustment—not O(1).

05 · Other-private discovery

Consume a list index; do not enumerate transactions

Candidate producers advertise integer LRU indices. A victimizer locks only the selected list, scans bounded LRU3 state, and uses BCB try-locks.

  1. An eligible clean LRU3 BCB increases count_vict_cand. An over-quota private list atomically enlists its index in private_lrus_with_victims; quota adjustment can republish it.
  2. pgbuf_lfcq_get_victim_from_private_lru() consumes big_private_lrus_with_victims first, then the regular queue when allowed. It maps the integer directly to buf_LRU_list[lru_idx]; the caller never walks another transaction’s object.
  3. pgbuf_get_victim_from_lru_list() locks that one LRU mutex, scans at most 1,000 LRU3 entries, and try-locks each BCB before the final safety recheck.
  4. If candidates and quota still justify another search, the index is requeued. Otherwise its enlistment flag is cleared so a later candidate can advertise it again.
The 2,000-transaction answer: victim search does not inspect 2,000 transaction entries or 2,000 private-LRU descriptors. It consumes one advertised integer index in O(1), locks that one list, then walks at most 1,000 BCB nodes in its LRU3. A hot selected-list mutex, repeated failed try-locks, or many 1,000-node attempts can cost CPU, but the cost is not O(number of open transactions). The separate, infrequent pgbuf_assign_private_lru() operation does linearly inspect all P private-list descriptors—O(P), up to five retries after an assignment race—when a context receives an assignment.

06 · Read the same page twice

Reuse changes zone/position conditionally; it does not store “frequency = 2”

The meaningful event is the ordinary unfix that returns the BCB's fix count to zero. Its current zone and age decide the movement.

pgbuf_bcb_register_hit_for_lru() can count one hit for the containing LRU per quota.adjust_age: if bcb->hit_age is older, it increments monitor.lru_hits[lru_idx] and advances that BCB's hit age. Quota adjustment consumes those per-list hits to estimate activity. This is deliberately not an ever-growing, per-BCB read-frequency score used to sort victims.

A second, separate signal is the high half of count_fix_and_avoid_dealloc. The general fix path increments this approximate hotness counter up to 64; the overlapping-reader fast path bypasses that registration, so it is not an exact successful-read count. Reaching 64 participates only in the old private-to-shared migration rule—it is not compared by the LRU3 victim scan. The counter resets when the BCB returns to the invalid list.

LRU1Keep its current position; register list activity when eligible.Already outside the victim zone; no extra boost is needed.
LRU2, too youngStay in LRU2. “Old enough” means list tick distance at least half the current LRU2 count.An immediate reread does not automatically earn LRU1 protection.

So the concise answer is: sometimes. A later read can make the page less victimizable through position/zone, and its hit can influence the containing private LRU's future quota. Two rapid reads while the page is young in LRU2 may leave its placement unchanged. AOUT would add ghost-history behavior, but the analyzed default forces its ratio to zero.

08 · No free BCB

The allocator enters a progress loop with explicit exits

  1. Take invalid/free BCB: immediate reusable storage; no resident mapping needs flush or victim proof.
  2. Search LRUs: follow pinned private/shared/quota order; every chosen resident candidate still passes protected eligibility.
  3. Wait for direct victim: in server mode with a flush daemon, enqueue the allocator, wake the producer, and sleep with a bounded/interrupt-aware wait.
  4. Revalidate assignment: lock the assigned BCB. If a worker fixed it again, revoke the reservation and retry—normally with elevated priority.
  5. No daemon: during stand-alone/recovery conditions, flush synchronously and search again.
  6. Terminate: return a frame, retry, report interrupt/timeout, or emit explicit no-buffer error. Failure returns no page pointer.

Verified mechanism: allocation loop page_buffer.c:8181–8403; victim search order 9067–9265; direct-victim consumption/revocation 15592–15660.

09 · Revocable direct victim

Reservation loses to newly acquired ownership

A producer can reserve an eligible BCB for a waiting allocator. Between assignment and consumption, another active worker may fix the resident page. That new ownership invalidates the reservation.

MomentWhat is trueWhat the allocator may do
Producer assignsCandidate was eligible at producer’s protected check.Wake waiter with a reservation.
Worker fixes before consumptionCandidate now has ownership and is unsafe to reuse.Mark/revoke direct assignment.
Allocator consumesProtected revalidation detects invalid assignment.Release reservation state and request another candidate.

Forcing reuse would violate the fix contract. Retrying is not wasted correctness; it is the mechanism honoring a newer, stronger fact.

10 · Flush coordination

Old-generation completion cannot victimize G+1

Under pressure, victim flush can propagate copied generation G and hand the BCB toward post-flush assignment. Post-flush must recheck that the resident page is still clean, unfixed, in the victim zone, and policy-eligible.

If a writer created DIRTY generation G+1 while G was in flight, the direct-victim handoff must fail. Completing old bytes does not authorize discarding newer resident bytes.

Verified mechanism: flush handoff page_buffer.c:10925–10952; post-flush assignment 15489–15556.
