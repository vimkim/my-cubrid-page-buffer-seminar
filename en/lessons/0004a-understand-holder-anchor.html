Separate the holder anchor from a holder entry

By the end, you can show exactly how one thread recognizes a repeated fix of BCB A, why no list position is remembered, and when a holder entry moves between active and free lists.

01 · One sentence first

The anchor owns lists; an entry records one thread–BCB relationship

PGBUF_HOLDER_ANCHOR is one thread's small directory. A PGBUF_HOLDER is one reusable record saying “this thread currently owes N unfixes to this BCB.”

The anchor does not represent a page. It gives one thread access to its active and free holder-entry lists.

ObjectCardinality and fieldsMeaning
PGBUF_HOLDER_ANCHOROne per thread index: thrd_hold_list, thrd_free_list, num_hold_cnt, num_free_cnt.Routes that thread to active and reusable entries. It has no BCB pointer and no nested-fix count.
PGBUF_HOLDERZero or more per thread: bufptr, fix_count, thrd_link/next_holder, statistics, watchers.When active, binds this thread to one BCB and counts this thread's nested debts for it.
02 · Read the snapshot

Two active entries can represent four successful fixes

In the diagram, Thread 17 has fixed BCB X three times and BCB Y once. Its anchor therefore has num_hold_cnt = 2, because it owns two distinct active entries. The sum of their nested debts is 3 + 1 = 4.

Do not equate the counters: num_hold_cnt is the active-list length; it is not the sum of holder fix_count values.

Thread 18 can also fix BCB X. That produces a separate holder under Thread 18's separate anchor. BCB X's global fcnt combines grants from both threads, while each holder stores only its own thread's share.

03 · Answer the lookup question

It scans by BCB address; it does not remember a position

For another fix of BCB A, pgbuf_find_thrd_holder(thread_p, bufptr_A) walks the current thread's active list and compares holder->bufptr == bufptr_A.

  1. Resolve the current thread's anchor. thread_p->m_holder_anchor lazily caches &pgbuf_Pool.thrd_holder_info[thread_p->index].
  2. Start at m_holder_anchor->thrd_hold_list.
  3. Compare each active entry's bufptr with BCB A's pointer.
  4. Follow thrd_link until a match or NULL.
  5. On a match, a successful repeated grant increments that same entry's fix_count. On no match, a successful first grant obtains a free entry, prepends it to the active list, stores BCB A in bufptr, and sets fix_count = 1.
CaseHolder resultAccounting result after grant
Same thread, same BCB ASame matching entry.Entry count increments; active-list length does not.
Same thread, different BCB BNew active entry under the same anchor.Both active-list length and BCB B debt grow.
Different thread, same BCB ASeparate entry under that thread's anchor.BCB A global fcnt includes both threads.
What is absent: there is no remembered numeric position, per-thread holder hash table, or BCB-owned reverse list of holder threads in this path. The lookup is linear in the number of distinct BCBs currently held by that thread.

Verified mechanism: the exact traversal is pinned page_buffer.c:6090–6126. Normal fix looks up at 6319, increments a match at 6494–6510, and allocates a first entry at 6511–6531. The resident READ fast path repeats the match-or-allocate decision at 7753–7782.

04 · Why the thread needs a ledger

Global fcnt protects residency; the holder attributes debt to its owner

The BCB can say “three fixes exist,” but it cannot say that Thread A owns two, Thread B owns one, and Thread C owns none. The holder supplies that missing attribution.

The two ledgers are deliberately redundant in total but different in meaning: global replacement safety versus caller-specific ownership.

Question the code must answerWhat global state can sayWhat the holder adds
May this BCB be victimized?fcnt > 0 says some ownership remains, so no.No owner identity is needed for this global gate.
Does this caller have debt for A?fcnt > 0 says only that somebody owns debt.A matching bufptr proves this thread owns debt; no match lets the helper report an ownership error.
How many nested fixes does this caller owe?fcnt mixes all threads.fix_count lets one unfix consume exactly one of this thread's grants.
Is this reader the only owner during promotion?The global total alone cannot isolate the caller's share.Comparing global fcnt with this holder's fix_count reveals whether other readers exist.
What must ordered multi-page fixing revisit?A BCB-by-BCB pool scan would not preserve this thread's watcher, rank, and owner grouping.The thread list enumerates precisely its outstanding BCB bindings and attached watcher state.

Important: the holder is not a complete release-build misuse guard

If a caller omits unfix, the holder and global debt remain; the mistake is not prevented at the call site. In a release build, pgbuf_unfix_all() uses the thread list as a request-end cleanup safety net. Debug builds instead assert and report outstanding holders. Until cleanup, the leaked fix can keep a BCB ineligible for replacement.

An extra or wrong-thread unfix is even more important to distinguish. pgbuf_unlatch_thrd_holder() notices a missing entry and returns ER_PB_UNFIXED_PAGEPTR, but the pinned ordinary release path is not fail-closed: the lock-free READ release does not consume that status, and the protected release decrements global fcnt before checking it. After the final valid unfix, the old PAGE_PTR is contractually invalid and may already name reused storage. Therefore the holder exposes ownership information, but it does not make double-unfix safe or reliably stop its state mutation at this revision.

Precise conclusion: holder fields exist and drive normal release-build behavior; only extra debug tracking and assertions are debug-only. Misuse prevention is a separate, incomplete property routed as VS-17.

Does the BCB reverse-reference its holders?

No. The BCB stores global atomic_latch.fcnt, latch/wait state, flags, and page identity, but no authoritative holder-thread list. A fix call already has thread_p and bufptr, so pgbuf_find_thrd_holder(thread_p, bufptr) starts from that thread's thrd_hold_list and compares holder->bufptr == bufptr. The arrow points from thread-owned entry to BCB. Victimization needs only the global “any fixes remain?” answer and therefore reads global fcnt instead of enumerating owners.

Could owner identity be moved into the BCB?

Yes; that is a legitimate redesign. A write_owner_thread_id would be enough to identify the sole WRITE owner, and the BCB's global fcnt could also be that owner's nested total while WRITE is exclusive. This would remove the holder lookup for that case.

READ is the harder case. Many threads may hold the same BCB at once. Distinguishing an existing reader from a new reader therefore requires a BCB-side set, not one owner ID. If nested fixes remain legal, each reader needs its own count: after Thread A fixes twice and unfixes once, the set must know A is still an existing reader; after its second unfix, it must remove A. The natural BCB-side record is therefore <thread_id, fix_count>—the same core information as PGBUF_HOLDER, stored and indexed in the reverse direction.

The code already has a holder-free counterexample

pgbuf_simple_fix() and pgbuf_simple_unfix() update only global fcnt. Their source warning limits the protocol to temporary-file reads, says a write can make it unsafe, and forbids mixing it with general FIX/latch use. This proves a holder is not intrinsically required merely to keep one frame resident. It also shows what must be surrendered: general READ/WRITE latch ownership, re-entry/promotion semantics, ordered watchers, and owner attribution.

Codebase-reviewed conclusion: global fcnt is sufficient for the narrow trusted latchless temporary-read protocol. The current general fix API needs per-owner state because of the semantics it promises. That state could move or change shape; it cannot be deleted while those semantics stay unchanged.
The narrow answer: existing-reader versus new-reader is one important use, but not the only one. The same per-owner state supplies READ-to-WRITE promotion and nested membership lifetime. Ordered watcher handling also uses the forward list. pgbuf_unfix_all() is only a legacy request-end safety net documented by its own source comment; it is not the primary justification for holders.

Verified mechanism: grant, re-entry, waiter barging, and promotion use caller ownership at pinned page_buffer.c:6312–6537; missing-holder detection and nested decrement are at 6128–6184; the ordinary unfix flow is pgbuf_unfix() plus global decrement at 6636–6703. Holder-free simple fix is restricted at page_buffer.c:2688–2811; progress classification is at 11705–11785. The legacy cleanup comment and enumeration are at pgbuf_unfix_all(); ordered fixing consumes the same thread list and watcher records beginning at pgbuf_ordered_fix().

05 · Two list roles

The same entry storage changes lists and link fields

Entry stateOwning listLink usedBCB meaning
Activethrd_hold_listthrd_link; next_holder == NULLbufptr and positive fix_count describe live debt.
Reusablethrd_free_listnext_holderNo current thread–BCB ownership relationship.

Allocation pops the free-list head and prepends it to the hold-list head. This constant-time insertion explains why a holder has no stable ordinal position: later first-time fixes can put new entries before it.

06 · Storage lifetime versus binding lifetime

Final unfix removes the binding, not the backing allocation

The entry is recycled; one logical thread–BCB binding is temporary.

Initialization gives every thread seven reserved free entries. If a thread exhausts its free list, allocation obtains an entry from shared extension sets of ten. A first successful fix activates one entry. Each repeated successful fix increments it. Each matching unfix decrements it; when it reaches zero, removal unlinks it from the active list and pushes it onto that thread's free list. Watchers must already be detached.

Verified mechanism: initialization and allocation are at page_buffer.c:5922–6086; final-debt removal and recycling are at 6128–6275. Backing holder storage is reclaimed during page-buffer finalization, not by an ordinary unfix.

07 · Unfix and cost

Can this become very slow? Yes, when one thread holds many distinct pages

Let H be the number of distinct BCBs currently held by this thread—not the buffer-pool size, lifetime fix count, or sum of nested debts. Because the active list has no BCB-to-holder index, position determines the work:

OperationHolder-list costReason
First fix of a new distinct BCBUp to O(H)The lookup must reach NULL to prove there is no existing entry, then allocation prepends one.
Repeated fix of an already held BCBBetween O(1) and O(H)The entry is reused, but it still has to be found. Only a head entry is immediately cheap.
Unfix with debt remainingUp to O(H)The same linear lookup finds the entry before decrementing it.
Final unfix of a non-head entryUp to two scansLookup finds the entry; removal may start at the head again to find its predecessor.

Worst-case accumulation

Fixing distinct pages A, B, C, …, N without releasing earlier pages performs 0, 1, 2, …, N−1 failed comparisons before each new entry is created. The total is N(N−1)/2, therefore O(N²). This acquisition cost exists even if the pages are later released in favorable LIFO order.

Order still changes release cost because each new entry is prepended. LIFO release repeatedly removes the head and is favorable. Releasing the oldest entries first, or repeatedly accessing an older entry while newer entries remain, repeatedly crosses a long list and can add another quadratic pattern.

Why this is not automatically the production bottleneck

  • The list is thread-local, so its traversal is CPU/cache work rather than cross-thread list-lock contention.
  • When H is small, a linear scan is short. The seven reserved entries per thread are consistent with an expected common shape of few simultaneous distinct holds, but they are not a hard limit or performance proof; extension sets provide more entries.
  • Nested fix of one head BCB does not grow the list and is O(1). The same BCB can become expensive to find only after newer distinct entries are prepended before it.
  • I/O, BCB atomic-latch contention, BCB mutex waits, wakeups, LRU work, and flush may dominate elapsed time.
Performance verdict: this is a source-proven linear-search hot-path shape and a mechanically valid scalability risk. It becomes a measured bottleneck only when a profile shows large per-thread H, unfavorable ordering, and substantial samples in pgbuf_find_thrd_holder() or pgbuf_remove_thrd_holder(). Many threads fixing one BCB instead create a different hypothesis: contention on that BCB's shared atomic latch.

Verified mechanism, inferred cost: find/decrement/remove are at page_buffer.c:6090–6275; normal fix calls find and takes the match-or-allocate branches at 6319,6494–6531. The complexity follows from that singly linked control flow. This document has no Runtime observation proving it dominates a production workload.
