LECTURE 5 / Mutation and durability

Caller correctness and logged mutation

A successful fix grants access. The caller still owns logical locking, validation, logging, dirty publication, and cleanup.

Logical lockWRITE latchValidateLogPage LSADIRTYCleanup
01 · Complete the contract after access

Successful fix answers only the access question

A non-NULL PAGE_PTR proves temporary, latched access to the requested resident page—not that the caller's logical operation is correct.

Fix success does not prove that a heap slot is suitable, a record representation is valid, the transaction holds the required logical lock, the recovery payload is correct, the page LSA was advanced, the generation is dirty, or every error path will release its watcher.

Review question: which layer establishes each condition, and which exits still own a page, watcher, logical lock, overflow object, or recovery obligation?
02 · Two protections

Page latches and transaction locks protect different domains

One heap insert needs both, on different objects and with different release protocols.

ProtectionProtectsEndsNever gives
Page latchResident bytes of one BCB/frameWith matching unfix or watcher transfer/releaseRow/class ownership or transaction isolation
Transaction lockLogical class or row identityUnder the transaction protocolSafe access to resident page bytes

Interface contract: a page latch protects current in-memory byte access. Implementation policy: this heap insert composes page-buffer watcher ownership with class/row locking from the lock manager.

03 · Representative caller

Follow the six-step success spine

Read each row left to right: action, owner, then the state an exit leaves.

  1. Prepare and lock: heap and lock management establish logical concurrency; a large record may first create overflow storage.
  2. Acquire and validate: a watcher carries page latch and fix debt while heap proves space, slot, identity, and row-lock conditions.
  3. Mutate: heap and slotted-page code preserve record and page-format invariants.
  4. Log and advance LSA: the caller chooses recovery meaning; the log manager advances the page LSA through the page-buffer interface when required.
  5. Publish DIRTY: pgbuf_set_dirty(..., DONT_FREE) marks the resident generation for propagation while intentionally retaining ownership.
  6. Transfer or release: the caller transfers the home watcher to scan cache or ordered-unfixes it, then cleans the remaining watchers.

Verified mechanism and Implementation policy: the representative success spine is pinned heap_file.c:23120–23324. It is representative caller evidence, not a proof that every page-buffer caller is correct.

04 · Keep adjacent transitions distinct

Mutation, recovery evidence, dirtying, and release are four events

EventWhat becomes trueWhat is still not true
Physical mutationResident bytes contain the new heap record under WRITE latch.No recovery meaning or propagation obligation follows automatically.
Log append + page LSAThe caller's recovery action is recorded; the page LSA advances when the recovery index requires it.The page is not dirty merely because its LSA changed.
pgbuf_set_dirty(..., DONT_FREE)The current resident generation needs page-image propagation.The watcher debt remains; the page is not thereby flushed or durable at every boundary.
Transfer or unfixThe caller moves or repays ownership debt.Release is not commit, flush, or eviction.

WRITE latch → mutate → recovery log/page LSA → DIRTY → transfer or release.

Do not rewrite this as “dirtying sets the page LSA.” The caller chooses recovery meaning, the log append can advance the page LSA, and dirty publication is a separate later transition.

06 · Caller knowledge

NEW_PAGE is the allocation-to-buffer contract

The VPID is already allocated; the logical page is not initialized yet. NEW_PAGE asks the page-buffer Module to materialize protected resident storage without reading an obsolete home-page image.

The name crosses two ownership boundaries. File or disk code first reserves the identity. Page buffer then establishes a resident BCB/frame and its metadata. Finally, the owning subsystem initializes the page type and layout, chooses TDE and recovery behavior, marks the generation dirty, and transfers or repays the fix debt.

Miss and hit have deliberately different preparation

SituationVerified page-buffer workWork still owned by the caller
Buffer missClaim and bind a reusable BCB/frame; skip DWB, home-volume read, decryption, and read statistics; initialize LSA/identity metadata; accept PAGE_UNKNOWN; grant and publish under the requested latch.Initialize logical payload, page type, and layout; choose TDE/recovery logging; mark dirty; handle failure; release or transfer ownership.
Resident hitUse the existing mapping and acquire the ordinary fix/latch. Do not repeat miss-only metadata initialization. A resident PAGE_UNKNOWN image is an expected reallocation case.Do not assume the mode erased the frame. Complete the same owner-specific initialization and cleanup protocol.

All ten direct creation calls at the pinned revision are in file/disk owners and request WRITE plus unconditional acquisition. That is a verified caller pattern, not a type-system restriction; zero-wait policy can still produce a conditional NULL outcome.

Representative source: pinned file_alloc() allocates first, fixes NEW_PAGE, runs the owner initializer, requires a known type, applies TDE, then transfers or unfixes at file_manager.c:5360–5590. The miss/hit branches are at page_buffer.c:2380–2616 and 8392–8634.

Why the no-read operation exists

Proposed substituteWhy it is not equivalent
OLD_PAGEA miss reads DWB or the data volume, decrypts as needed, and rejects PAGE_UNKNOWN. It adds irrelevant I/O and failure paths and breaks the supported resident-deallocated-image case.
RECOVERY_PAGEIt accepts broader allocation states but still reads on a miss and bypasses recovery-specific validation, not creation-specific validation.
Infer “new” from a cache missNot resident does not mean newly allocated. The decision to read must happen before the old image can reveal anything; only the allocation owner knows the intent.

Other engines expose the same internal responsibility

EngineInternal Interface shapeShared responsibility
CUBRIDPAGE_FETCH_MODE::NEW_PAGEAllocated identity; no-read resident materialization; caller initializes while holding WRITE.
PostgreSQLRBM_ZERO_AND_LOCKDo not read old bytes; return the buffer exclusively locked for caller initialization.
MySQL/InnoDBbuf_page_create()Use a separate creation function that publishes and latches a new buffer-pool page without a normal read.
“Public API” needs a boundary: page_buffer.h is a Server-module Interface. It is not an installed SQL, CCI, or application API. The useful design question is whether creation should remain a broadly composable enum value or become a narrower internal function.

Recommendation: retain the semantic no-read creation operation. If maintainers want a deeper Interface, hide or split it behind a creation function that implies WRITE and names the caller's initialization obligation. Keep the specialized external-sort full-page overwrite separate; it shares the no-read mechanism but not the allocation contract.
