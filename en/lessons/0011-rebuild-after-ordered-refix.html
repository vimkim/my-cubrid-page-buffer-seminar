Advanced capability · ordered ownership

Why ordered fix releases pages before waiting

By the end, you can explain the deadlock it prevents, distinguish its cheap and reorder paths, locate the holder/watcher/temporary-array state, and rebuild knowledge after a real protection gap.

WatcherGroupRankConditional fixRefixpage_was_unfixed
01 · Start with the deadlock

Two individually valid fixes can form a cycle

Assume the canonical order is A < B. T1 already holds B and requests A; T2 already holds A and requests B. If both requests sleep while retaining what they hold, T1 waits for T2 and T2 waits for T1.

The conditional attempt stays awake. Before T1 sleeps for earlier page A, it releases later page B, allowing T2 to finish.

A thread may wait for a later page while retaining earlier pages. Before it waits for an earlier page, it releases every reorderable page it holds later in the canonical order.

02 · Separate the fast and slow paths

The common path attaches a watcher without reordering

Situation at entryFirst attemptWhat follows?
No other BCB is held, or the only holder names this VPIDUnconditional ordinary fixAttach the requested watcher and return.
Other pages are held; requested latch is compatible nowConditional ordinary fixAttach the watcher. No old page is released.
Conditional attempt gets a terminal error or zero-wait rejectionConditional ordinary fixReturn without reordering and sleeping.
Conditional attempt would block and waiting is allowedConditional, then reorder pathSelect later pages, release them, sort a temporary array, and reacquire.

The conditional first attempt is the performance shortcut. It avoids list validation, full unfix, qsort(), and refix whenever the new latch is immediately available.

03 · Locate the state

A watcher is normal page debt plus ordering history

PGBUF_WATCHER carries the current page pointer/ownership state and metadata used to order a set of pages. It does not replace fix debt; it makes the debt movable and auditable across a multi-page protocol.

The active-holder list is not kept in canonical page order. Only the slow path copies facts into a temporary array and sorts that array.

Watcher informationWho supplies or interprets it?
GroupThe access method supplies the semantic group—for heap pages, the heap-header VPID.
RankThe access method supplies semantic order: heap header before normal before overflow.
VPIDPage buffer uses it as the final ordering coordinate.
page_was_unfixedPage buffer reports that this watcher crossed a release/refix window; the caller must rebuild observations.

A holder is one aggregate per thread/BCB pair in a head-inserted singly linked list. Each holder owns a doubly linked watcher chain; appending uses its tail and is O(1). On the reorder path, every fix debt of a released page must be represented by a watcher, because the helper must reconstruct every pointer and count after the full unfix.

The access method defines meaning and order. The page-buffer Module enforces the transition using watcher metadata and a temporary sorted array—not a sorted holder list.

04 · Canonical order

Group → rank → VPID

Within the representative heap protocol, pages compare by:

  1. group: heap-header VPID,
  2. rank: HEAP_HDR=0 < HEAP_NORMAL=1 < HEAP_OVERFLOW=2, then
  3. VPID: deterministic order within the same group/rank.

Pages without a known group sort last. Every watcher for the same page must agree on rank. This order is an access-method owner protocol, not a universal semantic ordering invented by page buffer.

05 · Input and output

The return value reports status; the watcher carries ownership

The call is conceptually pgbuf_ordered_fix(thread, req_vpid, fetch_mode, request_mode, req_watcher). The first four inputs identify the current thread, page, fetch semantics, and requested latch. Before the call, the caller initializes a clean watcher with PGBUF_INIT_WATCHER(): pgptr is null, while initial_rank and an optional heap group derived from HFID describe the access-method order.

Result channelMeaning
Integer returnNO_ERROR or an error code; it is not the page pointer.
req_watcherOn success, pgptr carries the watched fix and the watcher records latch mode, current rank, resolved group, and holder links.
Already-attached watchersThe helper discovers these through the current thread’s holders. A released/refixed watcher regains a pointer with page_was_unfixed=true; after partial failure, some pointers may be restored and others null.

The watcher is an in/out ownership ledger. Success is not complete until the caller checks the status and uses the watcher’s pointer; failure is not understood until every affected watcher is inspected.

06 · Ordered refix

Try cheaply; release only what violates the requested order

A successful conditional fix releases nothing. Reordering begins only after the conditional attempt fails.

  1. Try to fix requested page R conditionally while other watched pages remain held.
  2. If granted, record R and stop: no borrowed lifetime was interrupted.
  3. If rejected, compare every held watcher H with R.
  4. Keep H fixed when H sorts before R.
  5. Fully unfix H when it sorts after R—or when R’s group is still unknown—while registering avoid-deallocation and marking its watcher as having been unfixed.
  6. Fix R unconditionally, then refix released pages in sorted order.
  7. On partial failure, preserve exactly which watchers returned and which remain released so the caller can unwind.

Verified mechanism: pinned ordered helpers and callbacks are page_buffer.c:12268–13531.

07 · Worked heap group

Keep 0|90; insert 0|100 before 0|120

PageRole/orderAction after conditional failure
Held 0|90Heap header; sorts firstKeep continuously fixed.
Requested 0|100Normal; sorts secondFix unconditionally after later pages are released.
Held 0|120Normal; sorts thirdFully unfix, then refix after 0|100; set page_was_unfixed.

The final held order is 0|90 < 0|100 < 0|120. Observations derived from 0|90 remained protected. Observations derived from 0|120 did not. Cross-page conclusions involving 0|120 must also be checked again.

08 · Revalidation boundary

Restored ownership requires fresh page-derived knowledge

For every watcher with page_was_unfixed=true, reconstruct:

  • record and slot pointers,
  • free-space and destination choices,
  • page headers and type/identity-dependent fields,
  • relationships to the other held pages, and
  • the access-method condition that justified the operation.

Do not globally discard continuously protected observations. The watcher flag gives a precise boundary: rebuild knowledge behind the released watcher, and separately revalidate cross-page conclusions that depended on it.

Same lesson as promotion, larger set: pointer equality after refix does not extend the former borrowed lifetime. Ownership was recreated; knowledge must be recreated too.
09 · Partial failure

Audit the final state of every watcher

If R succeeds but a later refix fails, the held set is mixed. Some watchers may already be restored, some still carry release state, and R may itself be held. A correct caller or helper unwind must consume or retain each debt exactly once and preserve avoid-deallocation balance.

Representative caller boundary: heap destination/watcher ownership is pinned heap_file.c:20493–20664. This caller supplies heap meaning that generic page-buffer ordering cannot infer.

10 · Structures, cost, and limits

The holder walk is linear; only the selected set is sorted

Let H be active holder nodes, W all watcher nodes visited, M old pages selected for release, and F represented fix receipts on them.

WorkStructureLocal bookkeeping cost
Choose initial latch conditionHolder-list head and perhaps its next linkO(1)
Find holder after immediate successSingly linked holder listO(H) worst case; a newly created holder is normally the head
Validate/classify reorder setHolder list plus watcher chainsO(H + W)
Sort request plus released pagesTemporary array, qsort()Average O((M+1) log(M+1)) comparisons
Release/rebuild ownershipOrdinary fix/unfix plus watcher appendF unfixes, about F+1 fixes, and O(F) attachment
Caller ordered unfixHolder lookup plus backward watcher searchO(H + W_page) worst case

These bounds exclude latch sleep and storage I/O. The temporary holder array and per-page watcher array have a pinned capacity of 64. That is an internal bounded-work assumption for this protocol, not the general maximum number of holders a thread may own.
