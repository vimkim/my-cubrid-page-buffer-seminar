LECTURE 4 / Acquisition and ownership

Fix debt and release

Each successful fix adds a release obligation. Global and per-thread ledgers make nested ownership visible.

fcntHolderNested fixPAGE_PTRUnfixReuse

One resident page, several users

A and B are execution contexts (threads in these timelines); H1 and H2 are page identities. H1's bytes occupy a frame, and its BCB records identity and use state. H2 is unchanged throughout this close-up. These are constructed schedules, not a runtime measurement.

A successful fix grants temporary use of the resident page and creates one matching unfix obligation. That outstanding use prevents ordinary reuse of its frame. A latch controls access to page bytes: READ permits reading; WRITE permits exclusive modification. Two readers can coexist, but a reader and an independent writer cannot use those bytes simultaneously. Neither permission establishes transaction correctness; no prior transaction-lock lesson is needed here.

Dirty means the in-memory page contains changes that must be preserved before reuse. Releasing use does not itself clean the page. Today we track use, access and replacement eligibility; WAL, recovery, LSA, DWB and the copied-generation protocol belong to the next session.

1. Can B read while A is reading?

Starting assumptions: H1 is clean and resident. There are no waiters, no other users and no background transition in this schedule. A has one granted READ fix: global fcnt = 1, A's holder fix_count = 1, B has no holder. A and B only read.

  1. A keeps using H1 under its READ grant.
  2. B requests a READ fix of H1.

Predict B's permission, both holder counts and whether H1's frame can be reused.

Reveal the next state

B's compatible READ fix succeeds. Global fcnt = 2; A and B each owe one unfix. Both may read H1, neither may modify it under READ, and its frame cannot be reused. Compatibility is not an unconditional promise that a new reader bypasses an existing wait queue: the no-waiter assumption matters.

2. What if B needs to write?

Reset to the same starting checkpoint: H1 is clean and resident; A alone holds one READ fix, global fcnt = 1, B has no holder, and there are initially no waiters. This is an alternative to the two-reader result. B requests an unconditional WRITE fix; A continues reading. Assume no timeout, interruption, competing request or background transition.

  1. B requests WRITE while A still reads H1.
  2. A performs its only unfix.
  3. The waiting request is resumed and granted successfully.

At which step may B change bytes? Does merely requesting WRITE add a granted fix debt?

Reveal the next states

At step 1, B waits: A's debt and global fcnt remain 1, while B has no granted use and cannot touch the bytes. At step 2 A's holder is removed and its contribution reaches zero; B is still not entitled to use the pointer until the grant. At step 3 B holds WRITE, global fcnt = 1, and B's holder count is 1. B may modify bytes under that grant; this is a new use, not a promise that a zero-count frame must be evicted between A and B. A's released pointer grants no further access.

Verified mechanism: pgbuf_latch_bcb_upon_fix() checks compatible requests and routes conflicts to waiting; a successful grant establishes the holder obligation.

01 · Count successful grants

Only successful acquisition creates fix debt

Every successful fix creates exactly one release debt. One matching unfix repays exactly one debt.

A request that returns without a grant—such as an expected resident-only miss, a conditional conflict, a timeout, or an interrupt—creates no successful ownership and therefore no unfix debt. The accounting boundary is the grant, not entry into pgbuf_fix().

Naming guardrail: say fix debt, not “commit debt.” Transaction commit is outside the page-buffer Module.
02 · Two ledgers, two questions

Global exclusion and thread attribution have different jobs

In this closed example, 3 = 2 + 1; the source stores the answers in different owners.

05 · Pointer equality is irrelevant

Three equal addresses still represent three debts

All three successful calls may return the same address because they borrow the same resident frame. That does not collapse their call-level obligations. Count successful grants, not unique pointer values.

After A's first unfix, A still has one nested debt and may continue using the resident bytes under that remaining ownership. After B's unfix, B's holder is removed and B may not use its borrowed pointer. After A's final unfix, neither thread owns access from this sequence.

Lifetime rule: a pointer address may remain numerically unchanged after release, but address stability is not continuing permission and is not page identity.
06 · What unfix changes

Release ownership without inventing side effects

One normal unfix decrements the calling thread's nested holder debt and the BCB global count. The holder record is removed when that thread reaches zero. When global fcnt reaches zero, the BCB may become latch-idle and may re-enter replacement consideration.

Unfix is not commit, flush, eviction, invalidation, or deallocation.

Global zero is necessary for ordinary victim reuse but not sufficient. Dirty/flushing state, waiters, replacement-zone membership, and protected revalidation still matter.

Verified mechanism: holder decrement is at page_buffer.c:6128–6184; global decrement and possible idle transition are at 6636–6703; the caller-facing unfix route is at pinned 3062–3201.

From final unfix to replacement policy

A context's final unfix repays its last outstanding fix and removes its holder. It does not imply that all other contexts have released H1. Only when all granted uses end does global fcnt reach zero. For the next policy example, assume both A and B have released every fix and no waiter takes over.

H1 may still be resident, and its BCB and frame still exist. A clean, unused page is a possible candidate, not an instruction to evict it. Dirty state, an in-progress flush, waiting users, zone membership and a protected current-state recheck still constrain ordinary reuse. A write completing is not permission to skip that recheck, and flushing is not transaction commit.
