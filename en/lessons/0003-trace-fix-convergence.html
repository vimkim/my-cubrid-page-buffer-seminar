01 · Three independent inputs

Read one fix call as three separate answers

Before following hit and miss, ask three questions. What kind of logical page does the caller expect? How may it access the returned bytes? If that access conflicts, may it wait? These answers combine in one call, but none can substitute for another.

ChoiceQuestion answeredShort answer
PAGE_FETCH_MODEWhat kind of page is this, and may a miss materialize it?Select one of seven caller-knowledge modes.
PGBUF_LATCH_MODEMay I share READ access or need exclusive WRITE access?A public fix accepts READ or WRITE.
PGBUF_LATCH_CONDITIONMay an incompatible request sleep?Conditional returns now; unconditional may wait.

All seven fetch modes

A fetch mode is the caller's statement about allocation and residency. It does not choose READ or WRITE.

ModePlain meaningImportant outcome
OLD_PAGEAn allocated page already exists.A miss reads its existing bytes from DWB or the data volume. A PAGE_UNKNOWN image is an error.
NEW_PAGEAllocation already produced this new VPID.A miss initializes a BCB/frame without reading old page bytes. PAGE_UNKNOWN is accepted until the caller initializes the page type.
OLD_PAGE_IF_IN_BUFFERI want the page only if it is resident now.A hash miss returns NULL without claiming a BCB or reading the volume.
OLD_PAGE_PREVENT_DEALLOCAn existing page must survive the gap before latch grant.A temporary avoid-deallocation count bridges identity validation to successful fix; it is removed after grant.
OLD_PAGE_DEALLOCATEDRecovery work needs a deallocated image.The common path may return a PAGE_UNKNOWN image. Deallocation undo uses it to restore the old type.
OLD_PAGE_MAYBE_DEALLOCATEDThe page usually exists but may have been deallocated.A normal image returns. For PAGE_UNKNOWN, the temporary fix is undone and the caller receives NULL.
RECOVERY_PAGERecovery must accept any allocation state.It skips ordinary allocation validation and accepts normal, immature/new, or PAGE_UNKNOWN images.

The five latch-mode enum values

The enum appears in several structures, but the public fix request accepts only READ and WRITE.

ModeMeaningValid fix request?
PGBUF_NO_LATCHIn the BCB field, no READ/WRITE content latch is currently granted. Other owning fields reuse the value for initialization or cancellation.No.
PGBUF_LATCH_READShared page-content access; compatible readers can coexist.Yes.
PGBUF_LATCH_WRITEExclusive page-content access; other threads' READ/WRITE requests conflict.Yes.
PGBUF_LATCH_FLUSHA queue request that waits for flush completion, never a granted content latch.No.
PGBUF_LATCH_INVALIDThe BCB has no usable resident identity.No.

Always qualify PGBUF_NO_LATCH by its owning field. The NO_LATCH audit separates resident-idle BCB state, waiter cancellation, and watcher initialization.

Conditional and unconditional describe conflict handling

PGBUF_CONDITIONAL_LATCH means “do not sleep if the latch conflicts.” A compatible request still succeeds normally. PGBUF_UNCONDITIONAL_LATCH means “waiting is allowed if needed,” so a compatible request still grants immediately. A transaction configured for zero wait converts unconditional to conditional before lookup.

Debt rule: expected non-acquisition creates no debt. An OLD_PAGE_IF_IN_BUFFER miss or a conditional conflict can return NULL without any matching unfix obligation. Interpret NULL through the caller's chosen protocol, not as one universal error.

Interface contract and Verified mechanism: all enum values are at pinned page_buffer.h:172–203. Request validation, zero-wait conversion, fast-path eligibility, resident-only miss, deallocation bridge, and post-latch page-type outcomes are at page_buffer.c:2285–2615.

02 · Different preparation, one success contract

Two paths converge on one postcondition

The normal mutex-protected path is shown; the lock-free READ path is an Advanced continuation.

H

Resident hit

Find a hash candidate, protect its BCB, and recheck that it still represents the requested VPID.

M

Cold miss

Serialize preparation by VPID, obtain a provisional BCB/frame, and read or initialize its bytes.

C

Converge

Confirm that BCB identity and page-header identity agree under protection.

G

Grant

Grant the requested latch, update global and thread debt, then return the borrowed pointer.

The example uses VPID 3|812. Agreement means two integer pairs match; it is not pointer equality or a comparison of the whole page.

PGBUF_BCB.vpid is control metadata: “this reusable slot represents logical page 3|812.” The associated frame starts with FILEIO_PAGE.prv, whose volid and pageid say “these bytes belong to logical page 3|812.” At convergence, the thread holds the BCB mutex and compares those two fields one by one. The mutex prevents detach/rebind across the decision; the later page latch protects caller access to content.

If a new or recovery-immature permanent page has an empty header, the code first copies the BCB VPID into it. Both fields matching allows latch/debt grant to continue. Either field differing returns no PAGE_PTR; a fresh miss returns its BCB to the invalid list and releases the VPID load lock so waiters can retry. Non-permanent volumes bypass this comparison at the pinned revision.

Verified mechanism: BCB field at page_buffer.c:510–518, header initialization at 5433–5471, exact comparison at 11243–11279, and protected convergence/unwind at 2440–2472.

A caller never receives a weaker contract merely because the page was a hit, or a stronger contract merely because it was a miss.

03 · Protected hit

A hash candidate still needs identity validation

The hash chain can identify a BCB whose vpid appears to match. That first comparison is not protected by the BCB mutex. Before the thread acquires that mutex, a victimizer may unlink the BCB and another loader may rebind the reusable slot to a different VPID.

The hit path therefore locks the BCB and compares its VPID again. If it changed, the thread releases that candidate and searches again. BCB storage itself remains safe to inspect because the table lives for the pool lifetime; what may have changed is the identity the slot represents.

Stale-observation boundary: the protected VPID recheck turns an unprotected candidate observation into trustworthy resident-identity evidence for this path.

Verified mechanism: protected hash-candidate rechecks are at pinned page_buffer.c:7594–7722. Pool-lifetime BCB allocation is at 5559–5660.

04 · Serialized cold miss

The waiter wakes and retries the normal lookup

One hash-anchor mutex protects the in-flight load-lock chain and the resident BCB chain.

  1. Thread A misses and registers the VPID load-lock record first, becoming load owner.
  2. Thread B misses on the same VPID, finds A's record, links itself as a waiter, and sleeps.
  3. A obtains a reusable BCB/frame, assigns the VPID, and keeps that provisional object unpublished.
  4. For OLD_PAGE, A consults DWB then the data volume; for NEW_PAGE, it initializes the frame instead.
  5. After identity confirmation and its own ownership grant, A publishes the BCB and releases the load lock.
  6. B wakes, retries lookup, finds a resident hit, and earns a separate grant and debt.
Evidence boundary: this protocol serializes resident-identity preparation. It does not prove “exactly one physical disk I/O”; DWB, filesystem, OS cache, device behavior, errors, and retries are separate layers.

Verified mechanism: load owner/waiter registration and retry are at page_buffer.c:7981–8178; provisional BCB allocation and DWB/data-volume or NEW_PAGE materialization are at pinned 8392–8634.

04A · Before victimization

An early cold miss pops the current invalid-list head

“Allocate a BCB” means claim an existing pool slot, not heap-create a descriptor for this VPID.

At initialization the pool allocates exactly num_buffers BCBs and the same number of frames. For every index i, it permanently wires BCB[i].iopage_buffer to Frame[i] and the frame back to that BCB. It then starts the invalid list at BCB[0]; initialization has already linked BCB[0] → BCB[1] → ….

Therefore, in the simplest no-prior-use and no-concurrency example, the first cold OLD_PAGE miss claims BCB[0] + Frame[0], the next claims index 1, and so on. In a real boot, startup work and concurrent misses may already have popped or returned entries. The rule is not “VPID hashes to BCB index N”; the winning thread takes whichever BCB is the protected invalid-list head at that moment.

  1. pgbuf_allocate_bcb() asks pgbuf_get_bcb_from_invalid_list() first.
  2. The helper locks the invalid-list mutex, pops invalid_top, locks that BCB, and changes its replacement zone from INVALID to VOID.
  3. The load owner assigns the requested VPID and reads the old image from DWB or the data volume into that BCB's already-paired frame.
  4. After identity convergence, the BCB is published in the VPID hash chain and ownership is granted.
  5. At final unfix, a newly materialized page enters the top of its assigned private LRU when it has one; otherwise it enters the middle of a selected shared LRU. Lesson 7 owns the later victim decision.
LifetimeWhat stays stableWhat can change
Pool lifetimeBCB storage, frame storage, and the one-to-one BCB ↔ frame pointer pairing.List membership, current VPID, latch/flags, LSAs, and page bytes.
Resident-identity lifetimeOne VPID ↔ BCB/frame mapping while that resident generation remains valid.Safe invalidation or victimization ends it; the same pair may then represent another VPID.
One fix lifetimeThe caller's borrowed access while its debt remains.Matching unfix ends permission but need not end residency.
Answer: the BCB + frame pair is stable from pool initialization to finalization. The BCB/frame + VPID binding is not; replacement exists precisely to reuse that same physical pool pair for another logical page.

Verified mechanism: table allocation and pairing are at pinned page_buffer.c:5559–5667; invalid-list initialization and top removal are at 5911–5918,8905–8951; invalid-first allocation is at 8181–8244; materialization is at 8470–8634. The first-release LRU destination is an implementation policy described in Lesson 7.

05 · Three checks, three gaps

Keep the three identity checks explicit

Each check validates a different observation under different protection.

CheckGap closedFailure meaning
Hit candidate VPID under BCB mutexUnprotected hash observation → protected BCBThe reusable slot was rebound; retry the chain.
BCB VPID versus page-header identityPrepared control state → prepared bytesThe control block and page image disagree; return no borrowed pointer.
Release-time identity assertionBorrowed-use period → global decrementIn debug builds, detect a caller/pointer identity violation before repaying global debt.

The third check is a debug assertion in the normal mutex-based unfix path. It documents the caller's obligation, but release builds do not gain a runtime guard from that assertion.

06 · State the shared contract

Four facts make acquisition successful

  1. The requested VPID is resident in the BCB/frame.
  2. The requested page latch has been granted.
  3. Global fcnt and the current thread's holder record this acquisition.
  4. The returned PAGE_PTR is borrowed until one matching unfix repays this debt.

Publication is part of a cold miss's preparation. The contract above is what the caller reasons about after either preparation path succeeds.

Not proved here: waiter fairness, lock-free READ memory ordering, every exceptional cleanup path, physical-device I/O count, caller logical correctness, or durability.
