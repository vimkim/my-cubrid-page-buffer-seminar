The problem: keep useful pages while a scan passes through

Imagine requests repeatedly returning to pages H1 and H2. Then a report reads S1, S2, S3, … once each. H1 and H2 form a hot working set: pages likely to be needed again soon. If every newly read scan page receives the strongest protection, the scan can push useful pages out. We call that cache pollution.

This is a shared workload story, not a three-frame database simulation or a measured comparison. The following snapshots show parts of larger pools. Assume clean pages unless stated otherwise; active users still prevent reuse.

For each engine, ask four questions: where does a new page enter, what earns protection, how does protection fade, and where does replacement look? PostgreSQL and InnoDB answer them differently from CUBRID. InnoDB is MySQL's storage engine; the comparison here concerns its buffer pool.

CUBRID recap: choose a domain, then inspect LRU3

Cold does not mean reusable

Ordinary final-unfix transitions update this policy. LRU1 protects hot pages; LRU2 gives an intermediate chance; LRU3 supplies candidates. Ordinary reuse in LRU1 leaves the page in place. LRU2 promotion has a list-age test, while ordinary LRU3 reuse returns the page to LRU1. Zone movement changes metadata, not the frame's physical location.

For H1/H2 and the scan, the result depends on domain assignment, admission, reuse and quota pressure. A private domain does not guarantee isolation from every other access stream. Reusing the frame for a different page requires clean state and protected checks of users, waiters and other state. AOUT is disabled at this revision.

In the preceding constructed CUBRID branches, A and B shared one private domain. When A resumed H1/H2 reads before B scanned S1/S2, both hot pages remained; with A paused, S1 replaced H1 while H2 remained. Reuse timing was the changed input. This bounded result does not promise isolation for private domains or immunity to longer scans.

Expand implementation details and sources
  1. Admission: at the pinned AOUT-disabled baseline, a newly loaded VOID BCB enters private S+p at LRU1 top when its final-unfix execution context has an enabled private-LRU assignment; otherwise it enters shared LRU2 middle.
  2. Reuse: LRU1 stays in place. An LRU2 page returns to LRU1 only when its list-tick age is at least half the current LRU2 count. Ordinary LRU3 reuse returns to LRU1.
  3. Victim: the allocator consumes an advertised LRU index, locks that list, and examines at most 1,000 LRU3 BCBs. Every candidate still needs clean/unfixed/waiter-free identity revalidation.
  4. Scale: lists and mutexes shard ordering. Private quotas use activity; their LRU1 and LRU2 thresholds are each 5% of quota. Shared defaults are 40% and 5% of the shared target.
Scan resistance: private/shared locality and zone admission reduce how one access stream competes with another. The source contains AOUT ghost history, but this pinned build forces its ratio to zero, so do not credit active 2Q behavior.

Pinned CUBRID: admission and hit transitions, bounded LRU3 scan, and quota adjustment.

PostgreSQL: give reused pages a few extra chances

A buffer descriptor is metadata for one frame, comparable in role to a CUBRID BCB. PostgreSQL keeps these descriptors in an array. A clock hand remembers the next array position to inspect; it wraps around at the end. Pages do not move around the array.

Each resident page has a small usage_count: reuse credit. A default-strategy first pin by a backend can add one credit, capped at 5. A backend is a PostgreSQL server process using the page. A pin, like a CUBRID fix for this purpose, prevents frame reuse while the caller uses it. It is separate from a lock protecting page contents.

These are separate steps over time, not one atomic operation. In the 1 → 2 → 3 example, each access starts after that backend has fully released its previous pin, using the default strategy. Nested pins held by the same backend do not keep adding shared credit. A positive count buys another chance; it is neither an exact access count nor a timestamp. Aging happens when the hand visits, not after a fixed number of seconds.

Why this helps: repeated H1/H2 use can earn more chances than a one-time S page. What it loses: two pages with credit 2 have no recorded “more recent” ordering. The hand's position helps decide which is reached first.

PostgreSQL: let a bulk scan reuse a small ring

The clock alone does not recognize every scan. A bulk operation can use an access-strategy ring: a small backend-local array containing IDs of frames in the shared pool. The operation cycles through those slots and tries to reuse their frames.

When reuse succeeds, successive S pages can replace earlier S pages in this small set instead of continually taking more frames. A pinned frame or one with usage_count > 1 is rejected for ring reuse. The latter lets other users' reuse credit protect a page. Ring strategy accesses do not keep increasing credit above 1.

Compared with CUBRID: the ring is an operation's list of shared frame IDs, not a private LRU residency/quota domain. It limits pollution for operations that use it; it does not guarantee protection for every arbitrary scan.

PostgreSQL: the clock reduces reuse credits

PostgreSQL remembers bounded reuse credit, aged by clock visits rather than a recency list. The credit example shows the transitions; the source checklist follows.

Expand implementation details and sources
  1. Admission: a newly claimed shared descriptor receives usage_count = 1.
  2. Reuse: the first pin by a backend increments shared usage_count up to 5. A nested pin by the same backend changes only its private refcount, so it earns no second shared credit.
  3. Victim: the atomic clock hand advances through buffer descriptors. It skips pinned buffers, decrements an unpinned positive count, and claims an unpinned zero. A count of 5 may therefore survive up to six full visits.
  4. Bulk scans: backend-local strategy rings reuse a small set of IDs for bulk read/write and vacuum. They still name frames in the shared pool; they are not private buffer pools.
No LRU order: two descriptors with usage_count = 2 have no “older one first” relation. The count is bounded reuse credit decayed by clock visits, not a timestamp or linked-list rank.

Pinned PostgreSQL: clock selection, maximum usage count 5, and strategy-ring sizes.

InnoDB: give new reads a probationary position

A buffer-pool instance owns a portion of the pool and its own lists. Page identity determines the instance. Inside one instance, young and old are two regions of one resident LRU list. Both hold actual pages in memory; “old” does not mean evicted.

This sketch assumes an established old region in a list longer than 512 entries. A disk-read page enters just after LRU_old, rather than at the young head. The old target defaults to 37%; “midpoint” means an interior insertion point, not an exact 50/50 split. Short lists use head insertion, and a page newly created in memory enters young.

Why this helps: a one-pass scan first competes in the old region. It does not immediately give every S page the same position as a repeatedly useful H page. The regions are maintained dynamically; this is not a promise that H1 and H2 can never be evicted.

InnoDB: later reuse can earn promotion

Reading several rows from one page may touch that page repeatedly during a single scan. Promoting on every immediate touch would mistake that burst for long-term usefulness. Once eviction has begun, the default innodb_old_blocks_time gate requires a qualifying access at least 1,000 ms after the first logical access.

Expand implementation details and sources
  1. Topology: each buffer-pool instance owns an LRU, free list, and flush list. Once the LRU has at least 512 entries, LRU_old splits one physical list into young and old regions.
  2. Admission: once the old region is established, a disk-read page enters immediately after its boundary. Short lists admit at the LRU head. The old target defaults to 37%. A page created directly in memory enters at the young head.
  3. Reuse: an old page normally needs another access at least innodb_old_blocks_time after first access before promotion to the young head; the default delay is 1,000ms.
  4. Victim: allocation takes a free block or scans from the old tail for a clean relocatable page. The first common foreground scan is capped at 100 entries; a later pressure iteration may scan the whole LRU.
Scan resistance: a one-pass scan fills the old region but rapid first touches do not promote every page into young. Old/new are resident regions, not a 2Q ghost list of evicted identities.

Pinned MySQL/InnoDB: midpoint insertion, disk-read caller, 37% and 1,000ms defaults, and free-block pressure loop.

PostgreSQL versus CUBRID: benefits and costs

These are consequences of the structures at the pinned revisions, not measured speed comparisons.

Reuse bookkeeping
Advantage: shared usage credit avoids maintaining a recency-linked list for ordinary buffers. Cost: bounded credit loses fine ordering and repeated hand passes may be needed. CUBRID keeps domain/zone order, but it also avoids a list move for ordinary LRU1 reuse; it is not exact LRU on every hit.
A large scan beside H1/H2
Advantage: an eligible bulk operation can recycle a ring's frames, directly limiting its footprint. Cost: protection depends on the operation choosing the strategy and frames being reusable. CUBRID's domains and quotas address how groups compete across accesses, with more domain policy to maintain.
Finding reusable space
Advantage: the clock searches the shared descriptor pool without first choosing a quota domain. Cost: it may revisit many credited descriptors, and allocation can include dirty-page I/O. CUBRID bounds one selected-list LRU3 scan, but retries and cleaning can still delay allocation. Neither bound is a latency guarantee.

Takeaway: PostgreSQL trades detailed residency ordering for small credits and adds an explicit bulk-operation mechanism. This is a different distribution of work, not proof of lower overhead.

InnoDB versus CUBRID: benefits and costs

Filtering one-pass reads
Advantage: old-region admission and delayed promotion give disk-read pages a probationary path. Cost: a newly useful page can be evicted before a qualifying later access. A slow scan can also meet the time gate. CUBRID instead combines domain-dependent admission with zone transitions and a list-age promotion test.
Organizing competition
Advantage: young/old gives each instance a direct two-region replacement model. Cost: page-to-instance assignment limits where a page competes; a pressured instance does not rank its pages against every page in other instances. CUBRID's private/shared quota domains offer different grouping flexibility, with additional assignment, migration and quota logic.
Making space under pressure
Advantage: tail scanning starts where colder pages are expected, and a free list supplies blocks. Cost: the initial short scan may expand, dirty pages need cleaning, and allocation retries the free list. Another thread may take a freed block first. CUBRID can cooperate with post-flush direct-victim handoff, which requires its own synchronization protocol.

Takeaway: InnoDB makes admission and promotion do explicit scan filtering. The result depends on access timing, residency and available clean candidates.

Conclusion: three ways to decide what deserves another chance

  1. CUBRID asks “which group and which zone?” It gains domain/zone control and avoids moving already-hot LRU1 pages. It pays for quota, migration, candidate-discovery and progress coordination.
  2. PostgreSQL asks “how much reuse credit remains?” It avoids recency-list maintenance and can contain bulk operations with rings. It gives up fine recency order and can spend more visits aging candidates.
  3. InnoDB asks “has this new read earned young placement?” It filters rapid scan touches through admission and a time gate. That gate can delay protection for genuinely useful new pages.

Protecting useful pages and producing a reusable frame are separate jobs. All three need both.

For the H1/H2-plus-scan story, ask whether the policy preserves the hot set, how much work it performs to find space, and who waits for dirty pages. A policy can improve one of these and worsen another. There is no performance winner established by this source comparison.

What might CUBRID learn? Questions to test

Would an explicit scan hint reduce interference? Would a different admission or promotion gate retain a newly hot set better? These are hypotheses, not proposed fixes. Compare the current policy and any prototype under controlled hot-set-plus-scan, changing-hot-set and dirty-pressure workloads. Measure misses, candidate visits, policy-update cost and foreground stalls while preserving correctness. Cross-engine timings also depend on page layout, effective pool size, I/O and durability settings.

Close the journey: one request, a reusable frame, another identity

  1. A caller finds the page needed for a record operation. One operation may visit several pages.
  2. The buffer resolves the page identity to a frame and BCB, loading on a miss. Fix protects its use lifetime; a compatible latch grants access to its bytes.
  3. Matching unfixes repay use debt. Ordinary final unfix can update admission or reuse policy; it does not promise eviction.
  4. Replacement chooses a domain and candidate, then rechecks current safety under protection. Dirty data must be preserved, and background work can help without guaranteeing an immediately reusable frame.
  5. Only after safe detachment and old mapping removal can the same frame carry a new page identity. Its stable address does not preserve the old identity.

H1/H2 survival depends on the established reuse schedule and policy state. The comparison showed other ways to remember reuse, with different costs; it established no speed ranking.
