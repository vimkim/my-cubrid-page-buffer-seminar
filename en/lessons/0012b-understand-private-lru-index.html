Private LRU indexes and selection

Persistent list descriptors, borrowed session indexes, BCB membership, and victim search have distinct lifetimes and rules.

First-principles route ↑

Private and shared organize competition for one pool

A private LRU is a residency and quota domain associated with execution contexts. A shared LRU is a common residency domain. Both link BCBs from the same pool. Private does not grant exclusive page access, and shared does not imply every page is simultaneously on every list.

The design supplies separate placement and pressure accounting rather than one global exact-recency list. Without private domains, a different policy would need to handle competition between a repeated working set and scan traffic. Correctness would not inherently disappear: a shared-only design can still protect identities, owners, and dirty pages. Whether isolation improves performance is workload-dependent.

Example: a new page reaches its first eligible final unfix. With a private assignment it enters private LRU1; without one it enters shared LRU2. A later access from another domain can cause a private member to move to shared LRU2. Its BCB and frame addresses stay the same. The detailed movement rules below include the other guards.

Final unfix chooses ordinary admission

This release-build path requires a zero global fix count, ordinary VOID placement, and no blocked reader/writer or special bottom-placement request. At the pinned AOUT-disabled policy, the top branch chooses private LRU1 when the final-unfix context has an enabled private assignment; the middle branch chooses shared LRU2 otherwise. Vacuum and direct-victim cases have other paths. In debug builds the entry is named pgbuf_unfix_debug.

The pool creates lists; a session borrows one list ID

The default 152 is a count of empty private-LRU descriptors created once during page-buffer startup. Starting a transaction does not create 152 lists.

In the pinned server path, session creation asks for one private-local index. Requests for that session copy the same index into their executing thread. A BCB may later join the corresponding list, but neither the session nor the transaction owns that BCB.

Session index versus BCB list index

A session receives an index within the private region; a BCB records an index in the complete array including shared lists. With 32 shared lists, private index 7 maps to full index 39.

Lists outlive sessions

List descriptors are created with the pool. A new session associates with an existing list; ending that session does not remove or move its pages. List counts depend on configuration and execution mode.

Expand implementation details and sources
  1. Page-buffer startup: pgbuf_initialize_page_quota_parameters() computes P. With automatic configuration, P is MAX_NTRANS + 50.
  2. Pool construction: pgbuf_initialize_lru_list() allocates all S + P descriptors once and initializes every list empty.
  3. Session creation: pgbuf_assign_private_lru() associates that session with one already-existing private list. It creates no descriptor, BCB, or frame.
  4. Request execution: a worker thread temporarily carries the session's local index. BCB membership can outlive that request and is independent of which transaction fixes the page next.
  5. Session destruction: pgbuf_release_private_lru() decrements the association count. It neither empties the list nor moves its BCBs.
  6. Page-buffer finalization: the pool-owned descriptor array is finally destroyed.

Vacuum is a separate context lifetime: enabled vacuum initialization assigns IDs to its preallocated worker records, and the pinned source has no vacuum-side release call before shutdown.

Why 152 in this example? It assumes server mode, automatic private-list configuration, max_clients = 100, HA off, one admin slot, one system transaction, and the compile-time vacuum-worker capacity 50: 102 + 50 = 152. The separately configured worker-pool default is 10; the formula still uses the capacity 50. Change these assumptions or configure the parameter explicitly and P changes; stand-alone mode disables private LRUs.

Associate a session with an existing private list

Assignment prefers lists without associated sessions and with fewer BCBs. Otherwise, it can share a list with low activity. Several sessions may use the same private LRU.

Expand implementation details and sources
  1. Walk the P private descriptors. An idle descriptor with zero BCBs is already the best primary candidate, so that case ends the walk early; otherwise the walk examines all P.
  2. Among descriptors with zero associated sessions, remember the one containing the fewest BCBs.
  3. In parallel, remember the descriptor with the lowest smoothed activity as the fallback.
  4. Prefer the zero-session candidate, convert its full index to local p, and atomically increment session_cnt[p].
  5. If another assignment raced for that idle list, undo and retry up to five times. After the retry budget, sharing is allowed.
  6. Each request copies p into THREAD_ENTRY.private_lru_index; this assignment is not recomputed on every page fix.

“Zero sessions” does not mean “zero pages.” Multiple sessions can use the same private LRU, and a release does not empty or move its resident BCBs. The algorithm balances policy domains; it does not allocate a private page cache or BCB ownership to each transaction.

Source: page_buffer.c:14513–14624; session.c:729–744; server_support.c:2069–2087.

First placement is chosen at final unfix

On the ordinary path for a newly loaded VOID BCB, the context reducing the global fix count to zero selects private LRU1 if it has an enabled private assignment, or shared LRU2 otherwise. Waiters, bottom-placement requests, vacuum and direct-victim handling have separate paths.

Expand implementation details and sources

“Private-domain page” is misleading shorthand. Private domain is not an intrinsic page or BCB property. The precise subject is a newly loaded VOID BCB whose final-unfixing execution context has an enabled private-LRU assignment.

The session receives local p, and the request worker carries it as THREAD_ENTRY.private_lru_index. When private chains exist and p != -1, pgbuf_thread_variables_init() sets m_is_private_lru_enabled. The first eligible final unfix that makes global fcnt zero tests PGBUF_THREAD_HAS_PRIVATE_LRU() and converts the enabled assignment to full index S+p.

The BCB has no session or transaction owner field. Once linked, it records only the current full LRU index and zone. Multiple sessions can share one private LRU, so it is a locality/quota domain rather than an ownership domain.

AOUT-off did not remove either branch. It removed the ghost hit/miss subdivision; in particular, the retained AOUT-miss branch to private LRU2 middle is dormant. Admission ranking chooses only this already loaded BCB's first LRU position. It does not choose the previous victim, prove ownership, or authorize frame reuse.

In stand-alone mode, or when private chains are disabled, no context has an enabled private-LRU assignment and ordinary first placement uses selected shared LRU2 middle only.

Quotas use sampled reuse activity

The policy adjusts competition between more and less active domains in two stages: eligible final unfixes collect samples; an accepted pgbuf_adjust_quotas() pass consumes them and updates activity and quota. Activity is neither an exact cache-hit count nor a session count.

eligible final unfix → per-BCB epoch check → lru_hits[current LRU]++
accepted adjustment → consume/reset hits → rate → smoothed activity → quota

The quota epoch is separate from the list-event ticks used for position and promotion. The following sequential examples assume no counter wrap or concurrent adjustment; they illustrate the pinned policy, not a runtime measurement.

The deduplication unit is the BCB, not the thread or VPID. If a counted BCB moves from private to shared in the same epoch, it adds no shared hit. If migration is its first eligible event in that epoch, registration happens after insertion and charges the shared destination.

2. Which uses become samples?

Ordinary policy runs on the final unfix that makes global fcnt zero. An unfix that leaves another fix outstanding does not enter this policy. Queued reader/writer waiters can defer policy; vacuum and some temporary-page paths deliberately ignore hits. Eligible first LRU placement of a newly loaded page also registers a hit.

Consequently, sampled hits are neither all fix/unfix calls nor cache hits. Repeating one page many times can raise the separate counted-final-unfix counter used to admit an adjustment, while that BCB still contributes at most one sampled hit during the epoch.

3. A 100 ms attempt is not a 100 ms update

The maintenance daemon attempts quota work every 100 ms when the flush daemon is available. Private-LRU assignment and release of the last association can also call it. The admission logic is summarized below; milliseconds are used for readability.

Scheduling and other guards prevent a strict real-time guarantee. Only an accepted pass advances adjust_age. 4. From sampled hits to activity and quota

An accepted pass uses ATOMIC_TAS_32 to take each lru_hits[i] and reset it to zero. It converts that interval's samples to a per-second rate, then updates each private list's activity:

rate = int(1,000,000 × sampled_hits / elapsed_usec)
elapsed < 10 seconds:
  activity_new = int(((10 seconds − elapsed) × activity_old
                      + elapsed × rate) / 10 seconds)
elapsed ≥ 10 seconds:
  activity_new = rate

Constructed example: 20 samples in 0.5 seconds produce a rate of 40 samples/second. If old activity is 100, the new value is int((9.5 × 100 + 0.5 × 40) / 10) = 97. The source truncates the rate and activity to integers. This is elapsed-time-weighted smoothing with a ten-second scale, not an exact moving average backed by the last ten seconds of events.

The overall private target is calculated separately from private/shared rates, low-activity policy and a smoothed private-page ratio. Given that target, each private list receives its share of total private activity:

private_target = int((num_buffers − invalid_count) × private_pages_ratio)
quota[i] = min(int(private_target × activity[i] / sum_private_activity),
               5,000, num_buffers / 2)

For example, assume the already calculated private target is 4,000 BCBs and the pool contains 32,768 buffers. If this list has activity 97 and all other private lists together have 291, its share is 97 / 388 = 25% and its quota is 1,000. Both caps leave it unchanged. Its LRU1 and LRU2 thresholds are each int(1,000 × 0.05) = 50. If total private activity is zero, private quotas and both thresholds become zero instead of dividing by zero. A quota is a policy target, not reserved frames.

Sources and sampling limits

The structural work is O(T + L + D): managed thread-counter entries, LRU descriptors and actual zone demotions, excluding lock waits. Private assignment consults activity as a fallback when no zero-session descriptor is available.

The pinned counter is approximate: registration uses plain increments while consumption uses atomic exchange. BCB reuse does not normally reset hit_age, and epoch wrap has no explicit handling. These are source-level limitations and audit questions, not reproduced failure claims. See the sampling evidence and qualifications and VS-21 uncertainty record.

Migration changes the list, not the frame

On the ordinary final-unfix path, cross-domain access or a same-domain hot-and-old condition can move a private member to shared LRU2. It is unlinked then relinked; the frame is not copied. Access by a private-assigned context alone does not move a shared page back to private.

This is a later rule for a BCB that is already on an LRU, not another description of first placement. Ordinary movement occurs only when an unfix changes global fcnt to zero. pgbuf_should_move_private_to_shared() requests migration when the final-unfixing thread's full private index differs from the BCB's private list—including when the context has no enabled assignment—or when a same-domain BCB is both hot and old enough.

The path is private LRU → VOID → shared LRU2 middle. The source unlinks under the private-list mutex, releases it, chooses a destination with pgbuf_get_shared_lru_index_for_add(), and links under the shared-list mutex. The BCB mutex stays held between list operations.

An already-shared BCB does not move to a private LRU merely because a private-assigned context accessed it.

A known-node unlink/link is O(1), plus D zone demotions: O(1 + D). Shared destination choice is amortized O(1), with a periodic O(S) balance scan; migration therefore has a periodic O(S + D) case, excluding lock wait.

Calculate the accepted quota pass, then choose A's first victim list after explicitly exhausting INVALID.

Choose a list first; inspect eligible BCBs second

pgbuf_get_victim() applies this order:

  1. Own private list, when over quota: try the executing thread's S + p list first only when its quota condition says it is too large. A sufficiently over-quota list also restricts which other private candidates may be borrowed.
  2. One advertised other-private list: when private quota and the page-flush daemon are available, consume a candidate full index from the private-list queue. The code does not walk every session.
  3. One advertised shared list: consume a shared-list candidate index. With private quota disabled, this is the only domain searched. Without the page-flush daemon, the guarded branch may consume additional shared advertisements.
  4. Own private fallback: if the own list was under quota and therefore not tried in step 1, search it now even though it remains under quota.

Each chosen index is passed to pgbuf_get_victim_from_lru_list(). That function examines only the chosen list's LRU3, up to 1,000 positions, and still rejects dirty, flushing, fixed, waited-on, reserved, or mutex-busy BCBs.

Direct victim is later, not a fifth LRU domain. In server mode with page-flush available, if INVALID and ordinary searches fail, allocation may wait for a flusher to clean and reserve a BCB. That handoff can be revoked if the BCB becomes ineligible before consumption.

Verified mechanism: Corrected VS-19 establishes ordinary-private consumption followed by big-private publication as the first-entry path. Queue lifecycle and capacity explain the branch; it does not guarantee progress or fairness.

What happens to the list and pages when a session ends?

Use S = 32 and P = 152. Session A receives local p = 7, so its full private-list index is 39. A request loads page X and final-unfixes it into list 39. Session A then ends, but X remains there. Session B later receives p = 7 and accesses X.

Explain why no LRU was created for either session, why B can access X, why release did not move X, and which full index the victim selector uses. Then repeat with A's list under quota and name exactly when that own list is searched.

List identity outlives a session

Session A releases local private-list ID 7 while its page X remains resident. Does a later session receiving ID 7 own X or create a new LRU?

Explore the explanation

No. Descriptors belong to the pool; a session borrows an association with a list ID. Releasing that association does not move its resident pages or grant ownership to the next session. Page access still follows the normal fix/latch protocol, and victim selection uses the full list index after the shared-index offset.
