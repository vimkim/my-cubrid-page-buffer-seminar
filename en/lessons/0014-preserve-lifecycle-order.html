LECTURE 14 / Recovery and specialized behavior

Startup and shutdown dependencies

Initialization, recovery gates, and finalization must respect the last user of each resource.

01 · Identity ownership

Logical lifecycle decision first; cache coherence second

DecisionOwnerPage-buffer consequence
Allocate/deallocate logical page identityFile/disk/recovery protocolMaterialize, reject, or invalidate resident mapping as requested.
Select NEW_PAGE or recovery fetch modeCaller with allocation/recovery knowledgeApply the matching resident-byte metadata/validation contract; the caller still owns logical payload initialization.
Raw/bypass overwriteFile/disk ownerFlush/invalidate cached mapping as required before external bytes replace it.

Invalidation is a cache-coherence consequence. It does not itself decide whether storage is logically allocated.

Representative sources: allocation ordering file_manager.c:5420–5590; bypass reset/coherence disk_manager.c:721–811.

02 · Dependency graph

The pool sits between its creators and late consumers

Startup creates dependencies before enabling work; shutdown disables consumers before destroying the pool.

Two structural rules: no daemon may touch a finalized pool; log finalization that can propagate pages requires the pool and its write dependencies to remain alive.
03 · Startup and recovery

Create the pool before file users; enable flush work after recovery

  1. Initialize the lock manager.
  2. Call pgbuf_initialize() to create the pool, hashes, lists, frames, and holder anchors.
  3. Initialize file management after the pool exists.
  4. During restart, recover DWB/module metadata before creating page-buffer/DWB daemons.
  5. Create daemon objects with their tasks gated.
  6. Run log recovery through the live pool.
  7. Enable flush daemons only after recovery completes.

“Daemon exists” and “daemon may perform work” are separate lifecycle states. Gating prevents background flush policy from racing unfinished restart recovery.

Verified mechanism: transaction-table setup log_tran_table.c:468–512; boot/recovery boot_sr.c:1974–2801; daemon gates page_buffer.c:16996–17136.

04 · Normal shutdown

Stop producers before finalizing what they use

  1. Stop vacuum/background ownership.
  2. Destroy page-buffer daemons so none can touch pool state afterward.
  3. Run log_final() while the page buffer still exists; final log work can still propagate pages.
  4. Destroy DWB only after the required page propagation completes.
  5. Finalize the page-buffer pool during transaction-table teardown.
  6. Finalize file management after the pool no longer needs it.

Verified mechanism: shutdown boot_sr.c:3055–3113; daemon destruction page_buffer.c:17244–17255; transaction-table teardown log_tran_table.c:580–594.

05 · Counterexamples

Two tempting reorderings violate dependencies

Wrong changeBroken dependencyFailure shape
pgbuf_finalize() before daemon destructionBackground consumer outlives its pool.Daemon can dereference finalized lists, frames, queues, or locks.
pgbuf_finalize() before log_final()Late log finalization loses page-propagation service.Final log work cannot safely fix/flush required pages.
Enable flush daemons before recovery completionBackground policy races recovery ownership.Unfinished recovery state becomes visible to normal flush/replacement work.
Raw overwrite without invalidationCached identity survives external byte reset.Readers can observe stale resident bytes inconsistent with storage.
06 · Restart failure cleanup

Error cleanup preserves the same dependency direction

A failed restart does not permit arbitrary reverse-order destruction. Disable work first, destroy daemon/DWB owners at their safe seam, finalize logging while required services remain, then tear down the pool and file dependencies.

The exact branches differ from normal shutdown, but the invariant is the same: a consumer cannot survive the resource it may still call.

Verified mechanism: restart-error cleanup is pinned within boot_sr.c:2740–2800.

07 · Pause and reason

Repair a dangerous shutdown proposal

Prompt

A proposed cleanup calls pgbuf_finalize(), then destroys daemons, then calls log_final(). A raw volume-reset path also leaves cached mappings intact.

Consider: identify every broken owner/dependency, give the safe order, and explain which rules are structural versus version-sensitive timing policy.

Open the explanation

file disk or recovery code owns logical allocation and raw overwrite decisions, while page-buffer invalidation is the resident coherence consequence -> startup initializes locks, then the page-buffer pool, then file management; restart metadata and DWB recovery precede gated daemon creation, and flush work is enabled only after log recovery -> shutdown stops background ownership and destroys page-buffer daemons before later finalization -> log_final must run while the pool is alive because it may still propagate pages -> DWB and then pool dependencies are torn down only after their last users finish, and file management is finalized after the pool -> finalizing the pool before daemons risks use-after-finalization; finalizing it before log_final removes required page service -> restart-error cleanup preserves the same consumer-before-resource destruction rule.

Primary reading

Trace each dependency through its last use

Read pinned boot_sr.c:2740–2801,3055–3113 beside log_tran_table.c:468–512,580–594. For every create/enable/disable/destroy/finalize call, annotate the consumer it permits and the last operation that may still need it.
