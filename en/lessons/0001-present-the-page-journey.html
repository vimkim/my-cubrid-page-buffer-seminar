LECTURE 1 / Foundations

What does a page buffer do?

Follow how repeated page requests reuse memory, how threads access it safely, and how changes reach storage.

Why keep pages in memory?

First-principles route ↑

A database reads and writes data in pages. A frame is a memory slot for one page. The page buffer manages these slots so that later requests can reuse pages already in memory.

Read page P, do some other work, then request P again. If P is still in memory, this is a hit; otherwise it is a miss. A miss needs a frame. If there is no unused slot, another page must be safely removed.

A hit may still wait for another thread’s latch. A miss may be served by a lower cache, so it does not necessarily cause physical disk I/O.

Use with fix, release with unfix

Threads sharing memory need two protections: a frame must not be reused for another page while it is in use, and access to its contents must be coordinated.

  • Fix: prepare the requested page and obtain the requested page latch and temporary access. On success, PAGE_PTR gives access to its contents.
  • Unfix: release the access obtained by that fix. Its returned pointer must no longer be used. The page itself may remain resident.

The page latch protects concurrent access to memory. Transaction-level locking, logging, and commit remain separate responsibilities.

A page identity is different from its memory slot

P is a page identity; a frame is the slot holding its contents. Later, the same frame can hold Q. Its BCB records which page it currently represents and whether it is in use.

VPID identifies the page, the BCB holds control information, and the frame holds data. fcnt counts granted fixes across threads; holders record each thread’s fixes. The structures page develops these relationships.

Structure recap: arrays and linked lists

An ordinary DB server process has one pgbuf_Pool. Each DB server process manages its own pool; connections and tables do not each create another pool. Below, N is the frame count, S the shared LRU count, and P the private LRU count.

BCBs and frames occupy separate arrays, paired by slot number. Shared/private LRUs divide one descriptor array: buf_LRU_list[0…S−1] is shared and buf_LRU_list[S…S+P−1] is private. Each entry's top/bottom points to BCBs; next_BCB/prev_BCB inside those BCBs form a doubly linked list.

Changing LRU order changes links in existing BCBs; it does not move the BCB array or page bytes. A private LRU is not a separate frame pool. Add S to a private index to obtain its index in the full descriptor array.

The sizes above are an example for Linux x86-64 SERVER_MODE Debug. The 648 B pool size is its control structure, not all allocated memory. The default example N = 32,768, S = 32, P = 152 assumes max_clients = 100, HA off and automatic LRU counts. Page bytes alone occupy 512 MiB; frame back-pointers add 256 KiB. BCB, LRU, hash, holder and other metadata are additional.

Counts are configurable: N follows buffer sizing, while S/P follow LRU settings and server capacity. Disabling private LRUs gives P = 0. The number of BCBs linked to each LRU varies at runtime and is distinct from the descriptor count. The exact frame stride is offsetof(PGBUF_IOPAGE_BUFFER, iopage) + IO_PAGESIZE, plus a guard when CUBRID_DEBUG is enabled. Structure sizes depend on ABI and build options.

One request for page P

1

Request P

Look up whether P is resident.

2

Make room on a miss

Use an unused frame, or safely remove a candidate and read P into its slot.

3

Obtain access

After fix succeeds, use the contents with the granted latch.

4

Read or modify

A modifying caller handles the required logging and dirty marking.

5

Finish using it

Unfix the page. This does not itself mean flush or commit.

6

Write back and reuse

Dirty contents are written with WAL ordering: make the corresponding log durable first. Once safe, the frame can be reused for another page.

This summarizes an ordinary request for an existing page. Not every request writes or evicts it, and flushing can occur in another execution context.

Does the page disappear after use?

Immediately after P is unfixed, another thread requests P. Must it be read again?

Show explanation

No. If P is still resident, the request can use the same frame. Unfix ends one use; eviction removes the resident mapping. The new request must obtain its own fix.
