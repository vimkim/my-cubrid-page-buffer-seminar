01 · Begin at the seam

The Module’s contract with the caller

The page-buffer Module turns a logical page identity plus access intent into temporary, latched access to resident bytes. That is a powerful contract—but it does not finish the caller's logical operation.

A successful normal fix connects VPID to a resident BCB/frame, grants the requested page latch, records one ownership debt, and lends a PAGE_PTR until the matching unfix.

Reasoning guardrail: do not reduce the contract to “it gets a page from memory.” That hides identity validation, miss materialization, latch grant, fix accounting, pointer lifetime, and the work still owned by the caller.

Canonical explanation: Contract and Objects. Pinned source: page_buffer.c:2260–2685, 6277–6634, and 3062–3201.

02 · Keep the nouns separate

One “page” is six different things

Read this as relationships and lifetimes, not as a call flow.

VPID names the logical page. A reusable BCB records which identity is resident and points to a reusable frame. PAGE_PTR is only a borrowed view into those bytes. Global fcnt and the current thread's holder are two ledgers for outstanding fix debt.

Four sentences worth memorizing: fixed is not resident; dirty is not durable; unfix is not flush; eviction is not deallocation.

05 · Evidence boundaries

Label a claim before you strengthen it

The guide uses six claim levels: Interface contract, Verified mechanism, Implementation policy, Inference, Runtime observation, and Historical evidence. This prevents a source-visible branch from becoming a timeless API promise, and prevents one lab run from becoming universal runtime truth.

Example: victim safety predicates are a Verified mechanism at the pinned revision. Exact LRU zones and scan order are Implementation policy. The existing run's lack of eviction is a Runtime observation—not proof that the victim path cannot execute.

Evidence vocabulary: CONTEXT.md. Mutable candidate status: Evidence and uncertainty registry.
