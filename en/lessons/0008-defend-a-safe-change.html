00 · Decode the document labels

VS-11 and VS-12 are registry IDs, not code objects

The guide keeps uncertain and revision-sensitive findings in one document: Unresolved or version-sensitive findings. VS-11 and VS-12 are simply stable row identifiers in that registry. They are not CUBRID error codes, variables, page types, or runtime flags.

A case packet is the capstone's name for one self-contained review exercise: a registry entry, bounded source ranges, a prediction worksheet, proof obligations, and a model answer. It is not a network packet or a page-buffer structure.

Case packetVerified source fact at pinned commitCandidate consequence—not yet established
A · VS-11Some paths grant latch/fix state before a holder allocation that may return NULL; no local rollback is visible in the cited snippets.A grant or fcnt might survive while the caller receives failure.
B · VS-12Flush setup sets FLUSHING and clears old DIRTY before TDE/DWB preparation can return; ordinary rollback is later.FLUSHING might remain or retryable dirty/LSA bookkeeping might be lost.
Are they true statements? Each entry contains a verified Level 1 source-ordering fact and a clearly labelled Candidate consequence. The whole candidate is not yet a verified production defect. Reachability, surviving state, impact, and current-branch status still require evidence.
01 · Proof ladder

A suspicious return is only the first rung

LevelQuestionEvidence that closes it
1 · Source-visible control flowDoes the pinned path change state, call something fallible, and return before visible local cleanup?Exact symbols, ranges, transitions, and callees.
2 · ReachabilityCan a supported target configuration actually make that callee fail at this point?Controlled injection or schedule on the target revision.
3 · Surviving stateWhat ownership or generation debt remains after all surrounding cleanup?Assertions/inspection immediately after the injected return.
4 · Production impactDoes surviving state cause corruption, leak, hang, retry loss, or a caller-visible contract violation?Reproduced consequence across the actual consumer path.
5 · Current-branch statusDoes the same mechanism and consequence still exist on the branch being changed?Re-trace and rerun against that exact commit/configuration.

A strong Level 1 argument earns investigation. It does not inherit Levels 2–5.

03 · Change-impact defense

Make every proposal answer nine questions

  1. Behavior: what observable behavior might change?
  2. Owners: which thread, Module, and caller own each resource or decision?
  3. State: which fields, flags, counters, pointers, queues, or LSAs transition?
  4. Guards: which BCB protection, atomic order, logical lock, or caller precondition protects each transition?
  5. Invariants: what must hold before and after the transition?
  6. Unwind: on every failure/restart, what is restored, transferred, consumed, or awakened?
  7. Caller impact: who observes the return, retained ownership, retry, timing, or contract change?
  8. Evidence seam: what does source tracing establish, and what controlled probe reaches the risk?
  9. Remaining uncertainty: what is inferred, version-sensitive, unreachable, or unobserved?

This template interleaves the Core: object identity, fix debt, caller correctness, flush generations, replacement eligibility, and evidence grammar.

05 · Alternate packet

VS-11 needs three injections, not one general claim

Holder allocation can return NULL at 6000–6055. Normal hit, lock-free READ hit, and awakened waiter grant ownership through different paths before holder recording. Each has a different scheduling and cleanup seam.

Inject holder extension allocation failure separately at all three paths. Inspect the atomic latch tuple, global fcnt, per-thread holder list, waiter/grant state, returned value, and ability to acquire and release afterward. A lock-free or waiter result does not automatically establish the normal-hit variant—or vice versa.

06 · Readiness gate

Change readiness also requires executable evidence

After the source packet, run at least one narrow caller regression or controlled runtime probe on the target revision. Record setup, expected transition, actual observation, unsupported conclusions, and a reproducible receipt.

Before implementation counts as ready, another maintainer should review the ownership ledger, all negative paths, the risk-matched test seam, and remaining uncertainty. This turns the evidence packet into a working review protocol rather than a tour of documentation.
