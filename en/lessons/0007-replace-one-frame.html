LECTURE 7 / CUBRID REPLACEMENT

CUBRID replacement: build the algorithm from its problems

Why each structure exists, what fails without it, and how one request passes through it. Follow repeatedly read pages and scan pages through one pool.

Reveal the result and reasoning

We need both a policy for retaining useful pages and a protocol for reusing their frames safely. We will first construct the policy, then test its safety. The named pages are an excerpt from a larger pool, not a tiny CUBRID configuration or a measured execution.

1. Why evict anything if a free frame exists?

Use and release: a caller fixes a page to keep its frame available while using it, then unfixes to release that use. A frame with an outstanding fix cannot be reused for another page. A dirty page contains changes that must be preserved before reuse; a clean page has no such outstanding dirty changes.

B requests S1 and the resident hash does not find it: a miss. A frame holds page bytes; its BCB records the page identity and state. What if one BCB has no resident page?

Reveal the result and reasoning

An invalid list links BCBs with no resident identity, so allocation can remove one from the head. Without this list, a different structure or a scan would be needed to find free slots. Only when this source is empty do we need a victim. A victim is the resident page selected for removal from memory; its disk page is not deleted.

2. Why not maintain one exact LRU list?

Try a simpler design first: every hit moves a page to the front of one list. The least recently used page is at the back. Assume all example pages are clean and unfixed so that we can isolate policy.

Reveal the result and reasoning

A long scan can push reusable H1/H2 out before A returns. Concurrent workers also contend for a common list lock when they update exact order. One list is a valid design, but these costs motivate separate policy domains and fewer position updates. Multiple lists do not automatically solve scan pollution; admission, quotas and zone rules must work with them.

These are design counterexamples, not a claim that every workload becomes faster or that this was CUBRID’s historical development sequence.

Reveal the result and reasoning

The pool owns the BCB array and frame storage. LRU descriptors hold list endpoints, zone boundaries and a mutex; BCBs supply the previous/next links. A descriptor describes a list, not a frame. Changing membership changes links and metadata, not the frame address or its bytes.

Shared and private descriptors are in one array. A BCB belongs to at most one LRU at a time; a newly loaded or transferring BCB can temporarily belong to none. Hash lookup and fix/latch protection remain separate from that membership.

3a. When does a newly read page enter a list?

Private assignment means choosing in advance which LRU list a session will use for replacement management; in this example, PB names the list assigned to B.

An ordinary server SQL session normally has a private assignment. With the pinned revision’s default configuration, session creation assigns a private LRU, and the thread handling a request receives that session’s assignment.

Why might a private assignment be absent?

  • A server initialized with num_private_chains = 0: private LRU policy is disabled, so the assignment function returns -1.
  • Standalone mode: the source sets the private LRU count to zero, so there is no assignment.
  • A server request with no session attached yet: there is no session assignment to inherit, so the executing thread’s index remains -1.

When all private lists are in use, assignment still proceeds by sharing a less-active list. Vacuum workers also receive private LRUs separately, so background work does not always mean an absent assignment.

Under the ordinary admission conditions below, a new page enters private LRU1 with an assignment or shared LRU2 without one. This describes initial placement; a session with a private assignment can also read pages already in shared lists.

VOID means no current LRU membership, not necessarily an empty frame. In the ordinary path, placement occurs at an eligible final unfix: the last counted use ends. With a private assignment, the page enters private LRU1; without one, it enters shared LRU2. This is the pinned AOUT-disabled behavior. S2 and S3 follow the same admission rule.

A context can release its last fix while another context still has one. Here “final unfix” means the BCB-wide zero crossing, not merely that context’s last release. The fix count fcnt counts outstanding fixes, not distinct sessions. Final unfix takes that count to zero; it is not every unfix. An existing resident page normally keeps its membership while fixed. Move-to-bottom requests, vacuum/temporary-page rules and queued reader/writer waiters can change or defer ordinary placement; the following examples exclude those branches.

4. Why not use only several shared LRUs?

That is possible. But splitting a list alone gives no separate way to manage the replacement pressure from B’s long scan.

For this local example, A is assigned PA and B is assigned PB; these are different private domains. CUBRID does not require different contexts to receive different domains. When PB grows, policy can look there first for frames to reclaim. A quota helps determine protection and search priority; it is neither reserved memory nor a hard size limit.

Private does not restrict access. B can read H1 while it belongs to PA. Shared lists manage pages including those moved out of private lists. Shared pages can still be replaced.

Why splitting lists is not enough

Several shared lists distribute lock contention. Private lists and quotas add a basis for deciding where to reclaim first. Migration removes pages from private accounting when another domain uses them or they satisfy the hot-and-old condition.

Reducing scan interference is an interpretation of the policy, not a guarantee of isolation or performance. Several sessions can share one private list, and ending a session does not immediately remove its pages.

Source: pgbuf_get_victim() · pgbuf_adjust_quotas() · pgbuf_release_private_lru()

4a. Is this policy always useful?

If A reuses H1/H2 and B never revisits its scan pages, there is a reason to manage them differently. If both keep reusing every page, the capacity limit remains.

Assumptions and limits

The policy treats recent activity and reuse within domains as clues to future demand. Activity adjusts quotas; cross-domain access or a hot-and-old state triggers shared migration. This is a design interpretation, not historical design intent or a performance measurement.

Several sessions sharing a private domain, or a sudden workload change, can weaken those predictions. Private lists without quotas lose this size-sensitive reclamation rule. Without migration, a page used by another domain remains charged to its original private list.

Zones reduce some exact-order maintenance at the cost of ordering precision. Other policies can also replace safely, but must preserve fix and dirty-state handling and protected revalidation.

Source: pgbuf_get_victim() · pgbuf_adjust_quotas() · pgbuf_should_move_private_to_shared()

4b. What do age and quota count?

Before using “old enough,” separate three quantities. A list-position tick advances when a BCB is inserted at the top or middle, including a boost to the top. The BCB saves a tick as its position/zone is recorded. The difference from the current list tick is its policy age; it is not elapsed seconds or the number of reads.

QuantityMeaning
tick_list / tick_lru_listCurrent list tick / BCB’s saved tick: used for promotion age.

adjust_age / hit_ageQuota sampling epoch / BCB’s last sampled epoch. Repeated eligible unfixes count at most once per BCB per epoch.

Worked arithmetic: without counter wrap, saved tick 100 and current tick 110 give age 10. With 100 entries in LRU2 the cutoff is 50, so the age test fails. Current tick 150 gives age 50 and passes. The source handles wrap with PGBUF_AGE_DIFF. Passing this test does not itself choose the movement: membership and migration are checked too.

For the rules next, LRU1 is the front protected region, LRU2 is a second protected region, and LRU3 is the candidate region of the same list. Repeated reads alone do not advance the position tick. Quota sampling is a different mechanism; neither clock measures physical page age.

A larger LRU1 with the same conditional promotion rule is another possible design. Source alone does not establish that the current layout is faster or has a better hit rate than that alternative. LRU2 is a region applying a distinct policy rule, not a requirement for safe replacement.

Age here counts list-position events, not seconds. LRU1 membership does not prove frequent reuse: new private pages enter there too. This example explains a policy difference, not measured performance superiority for LRU2.

What if every reuse moves to the front?

That is a valid alternative policy. Merge the two protected regions and move a reused page to the front on every eligible final unfix. Combined protected capacity stays the same, but the update rule changes too; the larger-LRU1 example above changed only the region sizes. It maintains finer recency within each list, rather than one global order across private/shared lists.

Same-list reuseCurrent three-zone policyMerged protected region, move on every reuse
Page already in LRU1, away from the frontKeep positionMove to front
Young page in LRU2Keep positionMove to front
Old-enough page in LRU2Move to LRU1 frontMove to front

A known node in a doubly linked list needs only O(1) unlink/insert work. But doing this on every reuse introduces list synchronization and link writes where the current LRU1 path skips them. The source comment explicitly names avoiding the list mutex and rejecting immediate read-then-write repeats as reasons for conditional boosting. This does not eliminate BCB protection or all unfix work.

LRU2 supplies a region where reuse can renew protection, subject to age, while LRU1 skips reordering. In shared lists it also receives new admissions and private migrations below LRU1. Removing it requires choosing their new entry position: inserting at the front changes that policy; keeping an intermediate entry/age boundary retains part of the distinction under another name. Zone 2 is not necessary for safe replacement. The alternative may win on some workloads; compare hit/miss rate, link updates, mutex wait and throughput before claiming superiority.

8a. What does the saved tick actually remember?

A same-list boost does not reset bcb->tick_lru_list. New-membership helpers save the destination list's current tick. Top and middle insertion advance tick_list; an ordinary boost also advances it, but preserves the BCB's saved value. Boundary demotion does not reset that value either. Age therefore means neither time since the last boost nor time since entering LRU2.

The test is PGBUF_AGE_DIFF(bcb->tick_lru_list, lru_list->tick_list) >= lru_list->count_lru2 / 2. It measures list events against the current LRU2 population, not seconds, distinct accesses or the page's current distance from the front.

Integer division makes both 100 / 2 and 101 / 2 equal 50; 1 / 2 is zero. If LRU2 shrinks from 100 to 80 while the saved/current difference stays 40, the age test changes from false to true without an access to H1. The fraction scales the event gap with list population. The source comment motivates filtering short-gap read/write repeats; it does not prove that one half is optimal or that every immediate repeat is rejected. The saved value can already be old.

At wrap, use PGBUF_AGE_DIFF: when current tick is smaller than saved tick, it computes DB_INT32_MAX - (saved - current). This cyclic counter is not an unbounded elapsed-event history.

B keeps scanning and PB grows. If private lists had no size-sensitive policy, would splitting them alone prevent B from consuming more and more frames?

Reveal the result and reasoning

Quota is a policy target used for protection thresholds and victim-search decisions, not a reserved array slice or a hard list-length limit. The adjustment uses sampled final-unfix activity, smooths it and apportions a private budget. Each private protected-zone threshold is floor(quota × 0.05) at this baseline. With the illustrated thresholds filled, 3800 of the 4000 members are in LRU3.

This is not a universal 5%/5%/90% split of actual list length. Quota can differ from length and can change. Its caps are 5000 pages and half the pool. Shared thresholds follow shared target size and configured ratios. If activity changes but quota never adapts, protection can reflect yesterday’s demand; adaptation is approximate and does not guarantee fairness or a hit rate.

Ten final unfixes of one BCB in a sampling epoch do not contribute ten samples: that BCB is counted at most once in the epoch. This quota epoch and the list-position tick used for promotion are different clocks.

Source: pgbuf_adjust_quotas() · pgbuf_bcb_register_hit_for_lru()

The ordinary order is own private when its quota-related test passes, advertised other private lists, then shared lists, followed by the own-list fallback if it was not already searched. Skip dirty S1: discarding it would lose changes. Skip fixed S2: a caller still holds its bytes. S3 is only a candidate. It must also be not flushing, have no waiters or disqualifying avoid-victim state, and pass the locked recheck. These conditions are independent of the list’s replacement preference.

The selected-list scan starts at a victim hint or the bottom, walks previous links within LRU3, and visits at most 1000 BCBs per call. That is not 1000 lists or a bound on the entire allocation time. If this safety gate were removed, a good hit-rate policy could still corrupt active use or lose dirty data.

13. Why check S3 twice?

Reset to a separate local race; do not change either residency branch. The first observation says S3 is clean and unfixed. Another worker fixes it before the allocator claims its BCB. Is the old observation enough?

Another worker acts

fix(S3) → fcnt = 1

Allocator rechecks

Which current state permits reuse?

A holds the READ fix through the protected recheck; no intervening unfix occurs. The original observation and the recheck therefore describe different current use counts.

Reveal the result and reasoning

The allocator stabilizes the list with its LRU mutex, tries the BCB mutex without waiting, and checks the current conditions again. A failed try-lock or failed recheck means skip. Waiting for the BCB while holding the list mutex could conflict with paths that take BCB protection before the list lock.

Only a successful protected check permits removal from the LRU and return of the still-locked BCB. Without the recheck, the gap between observation and action could let the allocator reuse a page that has become busy. This is a correctness requirement, unlike a choice of quota or zone ratio.

A retains its READ fix while the allocator rechecks. Rejection preserves the S3 resident mapping and bytes. An earlier observation of fcnt 0 does not cancel the new debt. In the next alternative, restart with no new fix rather than silently releasing A.

Reveal the result and reasoning

Policy cannot manufacture safety. Unfix can release use; flushing can preserve dirty changes, but neither alone guarantees a reusable frame. In server mode an allocator can wait for a direct-assigned victim, and must revalidate it if it has become fixed again. Foreground/synchronous paths also exist when the flush daemon is unavailable.

Without a progress path, repeated failed scans would leave the request unable to obtain a frame. That does not justify stealing a fixed page. There is no claim here of a fixed waiting-time bound, guaranteed fairness, or an operational maintenance backup: that backup has a known source-level loop anomaly at this baseline.

17. Did zones make maintenance free?

H1 can stay in LRU1 without relinking. Does that mean every unfix costs the same, or that a promotion always changes only one pointer?

Reveal the result and reasoning

No. A raw known-node unlink or insertion is constant local pointer work, but promotion can adjust multiple boundary entries. If D entries are demoted, that work is O(1 + D), before lock waits. Selected-list search is O(D + K), where K ≤ 1000 is the scan budget for that call and pre-scan demotion D is outside it. Private-to-shared migration takes source and destination list locks sequentially.

Avoided relinking explains one potential saving, not total query latency. Holder bookkeeping, synchronization, allocation retries and I/O still matter. The detailed cost table below keeps these costs separate.

18. Can these structures guarantee a good hit rate?

A repeatedly uses a small working set; B scans. Now change the workload: repeatedly cycle over more pages than the pool can hold. Would private lists and zones remove the capacity problem?

Reveal the result and reasoning

No policy can retain more pages than its capacity, and this policy can still repeatedly miss. Existing controlled native receipts used 4096 frames: a fitting set of 2048 pages hit on repeat passes, while a 4097-page cycle missed on every request in the recorded passes. This was a debug server with observation hooks and controlled maintenance, not a general SQL benchmark.

The example explains why mechanisms exist; measurements establish behavior only under their recorded conditions. An engine read-path event is not proof of a physical-device miss. These receipts are reused here; no new engine experiment was run for this explanation.

19. Reconstruct the whole request

B misses on S4. No invalid BCB exists. PB passes the own-list search condition; its scan sees dirty S1, fixed S2, then clean/unfixed S3. A fixes S3 just before the protected recheck. What happens, and which mechanism would you remove only at a performance risk versus a correctness risk?

Reveal the result and reasoning

S1 and S2 are skipped; the protected recheck rejects S3 too. Allocation must continue through its search/progress paths. If S3 instead remains eligible, detach it, remove the S3 hash mapping, prepare/publish S4 in the same frame, and later place it at eligible final unfix. With B’s private assignment, ordinary admission is PB/LRU1.

Private/shared domains, zone ratios and quota choose how to compete for capacity. Another policy can replace them while preserving safety. Identity removal, use/dirty-state protection and the final recheck prevent incorrect reuse; removing them without an equivalent protocol is unsafe.

Candidate-search structures and costs

Allocation tries the invalid list first, then searches LRU3 in a selected LRU. The 1,000-entry limit applies to one selected-list scan, not to the entire allocation time.

Expand implementation details and sources

The array owns storage. The invalid and LRU links organize subsets of those stable BCB slots at runtime.

At startup, BCB_table is allocated as a contiguous array. Initialization sets each slot's next_BCB to the next slot, so building the initial invalid list is O(N) once. The runtime allocation path does not repeat that array loop.

The invalid list has one invalid_top pointer, a count, and a mutex. Its nodes are BCBs connected through next_BCB. Allocation performs an unlocked empty hint, locks and rechecks, moves the head to its next node, unlocks, then locks the returned BCB and changes it to the void zone. That is one-node O(1) list work—not an array scan. The invalid_mutex may still wait under contention, so constant work does not promise constant wall-clock latency.

Lifetime and initial population: page-buffer initialization creates this one pool-wide invalid list with invalid_top = BCB[0] and invalid_cnt = num_buffers; therefore every BCB starts on it. Runtime allocation pops entries, while failed loads and explicit invalidation can push entries back. The control object and its BCB nodes remain pool-owned until page-buffer finalization. See Lecture 0003 for the startup BCB/frame lifetime and Lecture 0012B for the default calculation: under that baseline's stated assumptions, num_buffers = invalid_cnt = 32,768 at initialization.

“1,000 links” means node visits inside one already-selected LRU

Do not merge three quantities: private-list count P, selected-list LRU3 population Z3, and this call's visit count K.

pgbuf_get_victim_from_lru_list(thread_p, lru_idx) receives one LRU index. It locks that list, starts at its victim_hint or bottom, and follows bufptr->prev_BCB through LRU3. Entering the loop body once means visiting one BCB position: inspect it, perhaps try-lock and recheck it, then return or advance one link. The body runs at most 1,000 times in this call. It does not inspect 1,000 LRU descriptors and does not produce 1,000 victims.

QuantityWhat it countsIs 1,000 its maximum?

The higher-level policy can make several selected-list calls: the caller's private LRU, an advertised other-private list, an advertised shared list, and a final own-list fallback. Each call gets a fresh 1,000-node budget. If a selected private list is over quota, the helper may also demote M boundary nodes before the scan; that work is outside MAX_DEPTH. The helper is therefore O(M + K), while the linked-list scan itself is bounded O(K).

Why other 1,000s are misleading: pinned source separately caps explicitly configured shared num_LRU_chains at 1,000 and targets roughly 1,000 buffers per automatically sized shared list. Neither constant caps private LRU count.
About “how long”: the pinned source gives operation bounds, not a calibrated nanosecond value. It records PSTAT_PB_ALLOC_BCB, PSTAT_PB_ALLOC_BCB_SEARCH_VICTIM, list-search timers, and condition-wait time. Use those counters or a focused benchmark for a target workload; do not convert Big-O into a latency claim.
