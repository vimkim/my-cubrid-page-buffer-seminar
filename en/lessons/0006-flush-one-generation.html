00 · Decode the notation

G names a copied page image; it is not a stored counter

A generation is our reasoning label for one coherent version of the page bytes that a flush treats as a unit.

When flush starts, it copies the resident page. Call that frozen copy G. A writer may then modify the still-resident page while G is being written. Call those newer resident bytes G+1. The source does not store a field named generation, G, or G+1; the labels keep two versions of the same logical page separate in our heads.

ThingWhat it isExample
Generation GConceptual identity of the page-image copy now being flushed.Copied bytes include logged changes through LSA 140.
Generation G+1Conceptual identity of resident bytes changed after G was copied.A writer applies a later change at LSA 170.
Page LSAA real log address stored with page state: the latest logged change included in those particular bytes.G carries 140; G+1 carries 170.

Why generation is not LSA: several logged modifications can move the page LSA from 100 to 140 while still belonging to the same not-yet-copied resident generation. Conversely, a new post-copy generation can exist for a change that is not represented by a new log address. Generation distinguishes page-image versions; LSA locates recovery history.

DIRTY and FLUSHING are two independent yes/no questions

DIRTYFLUSHINGPlain meaning
00No resident change awaits propagation; no copied image is in flight.
10The resident page has propagation debt and needs a future flush.
01Copy G is in flight; the resident page has not changed since that copy.
11Copy G is in flight and the resident page changed afterward—G+1 also needs a later flush.

DIRTY is a to-do flag: current resident bytes include changes not covered by a completed propagation. FLUSHING is an in-progress flag: a previously captured copy is still moving through the flush path. FLUSHING does not freeze the resident page.

Why clear DIRTY when setting FLUSHING? G's old debt has moved into the in-flight operation. Clearing DIRTY creates a clean signal slot: if a writer changes the resident page, it sets DIRTY again. Then DIRTY + FLUSHING unambiguously means “old copy in flight, newer resident work waiting.”
01 · Name the boundary

“Written” hides four different moments

Never move a claim rightward on this chain without stronger evidence.

MomentWhat becomes trueWhat does not follow
Write permissionWRITE latch permits exclusive resident-byte mutation.Recoverability or persistence.
RecoverabilityAppropriate log evidence exists and page LSA reflects the logged image.Commit WAL or home page is durable.
Transaction durabilityCommit WAL has reached its durability boundary.Every changed page is at its home location.

A flush completes a copied generation, not “the page for all time.”

Latest included change and oldest unpropagated change are different coordinates

03 · Ordinary success path

Follow the generation, not just the BCB

  1. Validate identity: confirm the protected BCB still names the intended page.
  2. Open an in-flight generation: set FLUSHING and clear the old DIRTY bit so later mutation can publish a new DIRTY generation.
  3. Capture stable bytes: copy the resident image; transform the copy for TDE and reserve/copy a DWB slot when configured.
  4. Capture recovery coordinates: copy page LSA and oldest-unflush LSA; clear the resident lower bound.
  5. Release BCB protection: I/O need not hold the resident state lock.
  6. Gate by WAL: for a logged non-temporary image, force WAL through the copied page LSA.
  7. Submit the copied image: use the configured DWB or direct data-volume write path.
  8. Complete under protection: clear FLUSHING and wake waiters, or perform the post-flush handoff required under pressure.

Verified mechanism: the ordinary path is pinned page_buffer.c:10723–10962. The configured endpoint must be stated precisely: DWB acceptance and later home-page persistence are not the same observation.

05 · Ordinary failure

Rollback reconstructs retryable generation state

If DWB addition or direct I/O fails on the ordinary post-release path, the code reacquires BCB protection, clears FLUSHING, restores DIRTY when the captured generation was dirty, restores the copied oldest-unflush LSA, wakes waiters, and returns failure.

Review invariant: after ordinary failure, the captured propagation debt must remain discoverable and retryable; no waiter should be stranded behind stale FLUSHING state.

When a concurrent G+1 exists, describe both generations and the concrete interleaving before simplifying the restored state. Do not let one scalar flag name erase two logical debts.

Verified mechanism: ordinary unwind is pinned page_buffer.c:10908–10923.

06 · Evidence boundary

Say exactly what the source and experiment establish

LabelSafe claimUnsafe promotion
Verified mechanismThe pinned ordinary source path orders snapshot, WAL gate, submission, completion, and rollback as described.Every early failure follows the ordinary rollback.
Runtime observationThe recorded experiment observed expected mutation/commit state and an accepted synchronous backup boundary.It proved per-page WAL-before-data, DWB completion, crash recovery, or page-write counts.
Open finding · VS-12Source inspection raises a concern about earlier TDE/DWB preparation returns before ordinary rollback.Calling the concern a current production defect without reachable fault injection.

TDE changes the copied image, not the ownership of resident plaintext. DWB protects page-image integrity but does not replace WAL or recovery. Prefer: “the page-buffer flush path completed at its configured DWB/direct-write boundary.”

07 · Retrieval practice

Track G and G+1 without saying “the page became clean”

Prompt

A clean page starts at LSA 80. Logs at 100 and 140 dirty it. Flush generation G begins; a writer logs at 170 while G is in flight. Predict page LSA, oldest-unflush LSA, DIRTY, and FLUSHING:

  1. just before G begins,
  2. after G captures its image,
  3. after the 170 mutation,
  4. after G succeeds, and
  5. what ordinary failure must preserve instead.
