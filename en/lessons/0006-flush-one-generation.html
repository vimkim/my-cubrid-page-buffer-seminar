Start here · Operation and purpose

Flush propagates one page image out of volatile buffer memory

Flushing is the page-buffer operation that captures a stable image of a resident page and sends that image through the required WAL gate toward persistent page storage.

A database changes the in-memory frame first. That resident image is fast to access but volatile: it does not by itself update the page's home location in the data volume. Marking the BCB DIRTY records this unfinished propagation work. A later flush processes that debt.

QuestionAnswer
What is copied?The current resident page bytes are captured as a stable, private image so later writers do not change the bytes already being submitted.
Why flush?To propagate page changes beyond volatile buffer memory, support checkpoint and shutdown progress, and make a clean, unfixed frame eligible for later replacement.
What does FLUSHING mean?One previously captured image is currently in the flush path. It is an in-progress state, not a command and not proof that the current resident bytes are clean.
What is it not?Flush is not transaction commit, unfix, eviction, or page deallocation. Those are separate lifecycle events.

The WAL rule answers an ordering question: for a logged non-temporary page, the recovery log covering the copied image must reach its required boundary before the page image is submitted. DWB, when enabled, answers a different integrity question about incomplete/torn page writes. Neither concept is the definition of flush.

Concrete outcome: if no writer changes the resident page after its image is captured and submission succeeds, the BCB can finish with neither DIRTY nor FLUSHING set. The page remains resident; a later replacement decision may reuse its frame.
00 · Decode the notation

G names a copied page image; it is not a stored counter

A generation is our reasoning label for one coherent version of the page bytes that a flush treats as a unit.

When flush starts, it copies the resident page. Call that frozen copy G. A writer may then modify the still-resident page while G is being written. Call those newer resident bytes G+1. The source does not store a field named generation, G, or G+1; the labels keep two versions of the same logical page separate in our heads.

ThingWhat it isExample
Generation GConceptual identity of the page-image copy now being flushed.Copied bytes include logged changes through LSA 140.
Generation G+1Conceptual identity of resident bytes changed after G was copied.A writer applies a later change at LSA 170.
Page LSAA real log address stored with page state: the latest logged change included in those particular bytes.G carries 140; G+1 carries 170.

Why generation is not LSA: several logged modifications can move the page LSA from 100 to 140 while still belonging to the same not-yet-copied resident generation. Conversely, a new post-copy generation can exist for a change that is not represented by a new log address. Generation distinguishes page-image versions; LSA locates recovery history.

DIRTY and FLUSHING are two independent yes/no questions

DIRTYFLUSHINGPlain meaning
00No resident change awaits propagation; no copied image is in flight.
10The resident page has propagation debt and needs a future flush.
01Copy G is in flight; the resident page has not changed since that copy.
11Copy G is in flight and the resident page changed afterward—G+1 also needs a later flush.

DIRTY is a to-do flag: current resident bytes include changes not covered by a completed propagation. FLUSHING is an in-progress flag: a previously captured copy is still moving through the flush path. FLUSHING does not freeze the resident page.

Why clear DIRTY when setting FLUSHING? G's old debt has moved into the in-flight operation. Clearing DIRTY creates a clean signal slot: if a writer changes the resident page, it sets DIRTY again. Then DIRTY + FLUSHING unambiguously means “old copy in flight, newer resident work waiting.”
00A · Why a second flag exists

DIRTY describes pending resident work; FLUSHING coordinates captured work

One bit cannot faithfully represent two facts that may be true at the same time: “copy G is in flight” and “resident G+1 needs another flush.”

Reason for FLUSHINGFailure if only DIRTY existed
Preserve a concurrent re-dirtyIf completion simply cleared DIRTY, it could erase a writer's newer dirty publication. With two flags, G completion clears only FLUSHING and leaves G+1 DIRTY.
Exclude overlapping flushesA second flusher could see newly DIRTY G+1 and submit it while older G is still in flight. If storage completions reorder, old G could overwrite newer G+1.
Coordinate synchronous callersA caller that must wait could not distinguish “no propagation running” from “another thread already owns the propagation.” FLUSHING directs it to the BCB wait queue instead of starting another flush.
Close success or failure explicitlyCompletion needs a state to clear and waiters to wake. Failure clears FLUSHING and restores the captured dirty debt/lower bound so it remains retryable.

Use this thought experiment. Start with DIRTY=1, FLUSHING=0. Flusher F captures G, then publishes DIRTY=0, FLUSHING=1: the old debt is owned by F. Writer W changes resident bytes and publishes DIRTY=1, FLUSHING=1: G is still owned by F and G+1 is new work. On success, F changes only FLUSHING to 0. The remaining DIRTY bit still means G+1 must be flushed.

FLUSHING does not freeze writers. It prevents unsafe competing flush ownership and makes wait/completion visible while DIRTY remains free to record a later resident generation.

Verified mechanism: safe flush rejects a concurrent flush and optionally queues a synchronous waiter at pinned page_buffer.c:8809–8901; the source explicitly names out-of-order old-over-new writes at 8839–8847. Flag transitions are at 16077–16137, with completion/failure wakeups at 10908–10951.

00B · Separate copy from destination

Copying the resident page does not mean “write it to DWB”

The flush first creates a stable page image in private memory. DWB is one possible destination for that copied image, not the copy operation itself.

In pgbuf_bcb_flush_with_wal(), page_buf is a local aligned buffer. The code either encrypts the resident page into that buffer for TDE or uses memcpy to copy it. This separates the in-flight bytes G from resident bytes that may become G+1 after BCB protection is released.

Configuration decisionWhat still happensWhere copied G goes after the WAL gate
DWB created and page is non-temporaryStable image copy, captured LSAs, and required WAL force.dwb_add_page() accepts the image into a DWB slot; DWB later coordinates protected home-volume propagation.
DWB disabled, not created, or page is temporaryThe same stable-image separation still happens; logged non-temporary pages still obey the WAL gate.The page-buffer path calls fileio_write() directly for the page's home data-volume location.
If DWB is disabled: flushing does not stop, and the page is not written twice by this DWB mechanism. It takes the direct-write branch instead. What is lost is DWB's torn/incomplete page-image protection and startup repair source; WAL still has its separate ordering and recovery role.

The pinned code chooses uses_dwb = dwb_is_created() && !is_temp before releasing BCB protection. It also contains a test-oriented runtime transition: if DWB disappears while adding the page, the path reacquires BCB protection, recopies the resident page, and retries without DWB. The source comment says live activation/deactivation needs additional work, so do not present runtime toggling as a supported monitoring or administration protocol.

Verified mechanism: local copy and branch selection are at pinned page_buffer.c:10735–10834; WAL gating and DWB/direct submission are at 10836–10899. DWB recovery behavior is a separate startup mechanism.

01 · Name the boundary

“Written” hides four different moments

03 · Ordinary success path

Follow the generation, not just the BCB

  1. Validate identity: confirm the protected BCB still names the intended page.
  2. Open an in-flight generation: set FLUSHING and clear the old DIRTY bit so later mutation can publish a new DIRTY generation.
  3. Capture stable bytes: copy the resident image; transform the copy for TDE and reserve/copy a DWB slot when configured.
  4. Capture recovery coordinates: copy page LSA and oldest-unflush LSA; clear the resident lower bound.
  5. Release BCB protection: I/O need not hold the resident state lock.
  6. Gate by WAL: for a logged non-temporary image, force WAL through the copied page LSA.
  7. Submit the copied image: use the configured DWB or direct data-volume write path.
  8. Complete under protection: clear FLUSHING and wake waiters, or perform the post-flush handoff required under pressure.

Verified mechanism: the ordinary path is pinned page_buffer.c:10723–10962. The configured endpoint must be stated precisely: DWB acceptance and later home-page persistence are not the same observation.

05 · Ordinary failure

Rollback reconstructs retryable generation state

If DWB addition or direct I/O fails on the ordinary post-release path, the code reacquires BCB protection, clears FLUSHING, restores DIRTY when the captured generation was dirty, restores the copied oldest-unflush LSA, wakes waiters, and returns failure.

Review invariant: after ordinary failure, the captured propagation debt must remain discoverable and retryable; no waiter should be stranded behind stale FLUSHING state.

When a concurrent G+1 exists, describe both generations and the concrete interleaving before simplifying the restored state. Do not let one scalar flag name erase two logical debts.

Verified mechanism: ordinary unwind is pinned page_buffer.c:10908–10923.

06 · Evidence boundary

Say exactly what the source and experiment establish

LabelSafe claimUnsafe promotion
Verified mechanismThe pinned ordinary source path orders snapshot, WAL gate, submission, completion, and rollback as described.Every early failure follows the ordinary rollback.
Runtime observationThe recorded experiment observed expected mutation/commit state and an accepted synchronous backup boundary.It proved per-page WAL-before-data, DWB completion, crash recovery, or page-write counts.
Open finding · VS-12Source inspection raises a concern about earlier TDE/DWB preparation returns before ordinary rollback.Calling the concern a current production defect without reachable fault injection.

TDE changes the copied image, not the ownership of resident plaintext. DWB protects page-image integrity but does not replace WAL or recovery. Prefer: “the page-buffer flush path completed at its configured DWB/direct-write boundary.”

07 · Retrieval practice

Track G and G+1 without saying “the page became clean”

Prompt

  1. just before G begins,
  2. after G captures its image,
  3. after the 170 mutation,
  4. after G succeeds, and
  5. what ordinary failure must preserve instead.
