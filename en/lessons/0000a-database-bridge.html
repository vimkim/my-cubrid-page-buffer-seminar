The capacity question travels; the legal choices change

A miss in full fast storage raises the same capacity question in several systems. The cached unit, placement rules, and owner determine which answers are permitted.

System and unitWho manages it?Why an arbitrary victim is wrong
OS virtual memory: pageThe OS maps virtual pages to physical frames, with hardware translation support.Reclaim must preserve mappings and required contents. Pinned pages cannot simply be reclaimed; modified contents may need backing storage.
CPU cache: cache lineHardware handles tags, placement and coherence.In a set-associative cache, an address competes within its mapped set, not against every line. Dirty/coherence obligations constrain removal; this is not an OS-page policy.
Application cache: object or valueThe application or cache library sets the contract.Objects may have different sizes and expiration rules. Dropping a recomputable value differs from discarding the only copy of a pending write; removing an entry need not destroy references held elsewhere.
Database buffer pool: database pageThe database coordinates residency, users of bytes, and recovery.In-use protection and dirty data constrain frame reuse. A database page need not match an OS page or a CPU line.

Exact LRU also makes every access a metadata update. With concurrent users, that bookkeeping needs coordination. Approximation and scan-resistant admission can reduce some costs, but neither names nor asymptotic costs establish throughput.

Before dirty replacement: what must survive?

A pin (or engine-specific fix) keeps a user’s resident page from being replaced while in use. It does not by itself make concurrent reads and writes safe; a latch coordinates access to page bytes. A transaction lock serves a different, logical concurrency purpose. Releasing a pin does not commit a transaction.

A dirty page has modifications whose current state still needs propagation to storage. Writeback/flush propagates a page image; eviction removes its resident identity so a frame can serve another page. A successful flush can leave the page resident. A clean page can still be pinned and unavailable.

Durability means the promised effects of an acknowledged commit survive the failures covered by the database contract. A recovery log records changes used after a crash. Write-ahead logging (WAL) requires the relevant log to reach durable storage before a changed data-page image does. For ordinary logged changes, durable commit need not wait for every modified data page to be written: recovery can replay logged changes. Page flush alone does not mean transaction commit. Configuration and special page classes matter; this is the conceptual rule, not a universal API promise.

Checkpoint DB-A: the oldest page is in use

Fresh constructed database model, not a continuation of any F1 terminal row. Three stable frames hold F0=P, F1=R, F2=S. FIFO admission order is P → R → S. All pages are clean; P is pinned by another user, R/S are unpinned. No other I/O or reservation exists. The model requires loading absent T, forbids bypass/growth, and chooses the oldest eligible page. Eligibility and reuse are checked atomically; pins do not reorder FIFO. Predict the preferred page, the legal victim, and the new frames.

Reveal explanation and state

FIFO prefers P, but its pin excludes reuse. R is the oldest eligible page. Reuse F1 for T: P / T / S; admission order becomes P → S → T. P’s frame and contents remain intact. This is an authored constrained-FIFO example, not the CUBRID victim algorithm.

Policy preference suggests where to look. Safe reuse requires a protected check of current state; a stale “unpinned” observation is insufficient when another user can acquire the page.

Checkpoint DB-B: writing is not evicting

Reset independently to P / R / S and FIFO P → R → S. This branch does not inherit DB-A’s T. P is unpinned and dirty; R/S are clean but pinned. No frame is immediately reusable. T is absent; bypass/growth remain forbidden. The branch chooses to flush P, with no new pin or modification during that flush. Predict the state after successful writeback, then after protected reuse.

Reveal explanation and state

Make the relevant log durable before the data-page write. Successful writeback leaves P / R / S, with P clean and unpinned; it has not evicted P. A fresh protected eligibility check then allows replacing P with T: T / R / S, FIFO R → S → T. The frame remains F0; its page identity changes. The outcome assumes successful I/O and the stated absence of concurrent changes.

Alternative from DB-B, not its successful ending: another user modifies P while an older image is being written. Completion of that older write does not prove the current page clean. Recheck dirty state and ownership; more writeback or retry may be needed. These are schedules for reasoning, not runtime observations.

Safety can hold while allocation cannot finish

Checkpoint DB-C: reset to P / R / S, all clean and pinned. T is absent; no bypass or growth. No frame can be legally reused while the pins remain. Predict whether a “better” recency ranking creates space.

Reveal explanation and state

No ranking releases a pin. Frames remain P / R / S. Progress requires another event, such as an owner releasing its pin, followed by successful protected selection. A system may wait/retry or fail the request according to its contract; waiting itself frees nothing. Flushing already-clean pinned pages cannot solve this checkpoint.

Safety forbids overwriting bytes still in use or losing required updates. Progress asks what event lets the pending allocation finish. Search another eligible candidate, arrange dirty-page cleaning, wait for release, or return an allowed error as the system permits. None of these labels proves eventual success, fairness, or a wall-clock bound under contention.

Two database responses to scan traffic

This conceptual orientation uses the same pinned comparators as the later source lecture: PostgreSQL fd2b89854d93d70fe8c9a69d5b8fafd5b9302cfc and MySQL/InnoDB 06a5c1c99c377fc41b2eba1ea244e8b220bdc3c8. These are Verified mechanism / Implementation policy, not claims about every release.

PostgreSQL: a clock hand visits descriptors, skips pinned buffers, and reduces positive usage_count before claiming an unpinned zero-credit candidate. The count is bounded reuse credit, not an exact recency rank. Bulk-operation strategy rings reuse a limited set of shared-buffer IDs, so a scan need not occupy a fresh share of the global pool on every read. Rings are not private buffer pools. Clock selection; ring reuse.

InnoDB: its midpoint LRU separates new/young and old resident regions. Ordinary disk reads enter the old region; access-age conditions can delay promotion toward the young end. This keeps a first scan access from automatically receiving the strongest retention. These are resident regions, not a history of evicted page identities. Midpoint insertion; promotion gate.

Both distinguish retention policy from protection and writeback. A scan can compete with P/R even when P/R fit by themselves. Rings and delayed promotion are different responses, not proof that either engine wins. Shared metadata, dirtying, I/O, and contention also shape cost.
