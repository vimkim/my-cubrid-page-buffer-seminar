01 · Define promotion

A READ holder asks for WRITE protection

Latch promotion is the attempt to change the current thread’s protection on one resident page from READ to WRITE. The goal is to avoid a full caller-written unfix/refix sequence when the page-buffer protocol can upgrade safely.

Promotion does not grant transaction-level ownership, preserve a B-tree search result by magic, or create another logical fix. It reorganizes the same page-buffer ownership under stronger byte protection.

02 · Four outcomes

Only one path opens an unfixed window

The blocking path moves the saved fix count through the queue but drops this thread’s protection while waiting.

03 · Decision rule

“Am I the only fixer?” determines the easy path

  1. If this holder’s nested fix_count equals the BCB’s global fcnt, every fix belongs to this thread. Unless a promoter is already waiting, promotion can change the latch mode in place.
  2. If other readers exist and the caller requested PGBUF_PROMOTE_ONLY_READER, promotion fails conditionally without releasing READ ownership.
  3. If another promoter is already first in the queue, the new promotion also fails conditionally; at most one promoter waits on a BCB.
  4. Otherwise the shared-reader path releases this thread’s fixes, removes its holder, inserts the promoter at the queue head, and waits for WRITE.

Verified mechanism: pinned promotion is page_buffer.c:2842–3050.

04 · Ownership accounting

The saved fix count moves; it does not multiply

Suppose the caller has nested-fix count 2. Blocking promotion:

  1. subtracts 2 from the BCB’s global fcnt,
  2. removes this thread’s READ holder,
  3. stores requested fix count 2 with the queued promotion request, then
  4. on grant, restores 2 into the global tuple and creates a new WRITE holder with count 2.

Before and after successful promotion, the caller owes two releases—not four. During the wait, it owns no page pointer at all.

05 · Observation lifetime

The same pointer value does not restore old knowledge

Between READ release and WRITE grant, other owners may modify page contents. Therefore the caller must discard or reconstruct every conclusion derived from the former hold:

  • record pointers and slot positions,
  • free-space and insertion decisions,
  • B-tree key ranges, separators, and sibling/child choices,
  • page headers, generation/dirty observations, and related-page relationships,
  • any access-method precondition that assumed the old page bytes.
Common bug shape: promotion returns a page pointer that looks identical, so the caller continues using a slot or record pointer computed before blocking. Pointer equality does not extend the old borrowed lifetime.
06 · Caller policy

Page buffer returns protection; the access method restores meaning

The Module implements the latch/holder transition. B-tree or heap code owns the semantic restart: repeat the search, verify the target record or slot, and reconstruct related-page decisions before mutation.

Representative B-tree callers switch to a WRITE traversal and retry after promotion cannot preserve the intended path. That is access-method policy, not a generic promise that promotion preserves tree navigation.

Representative caller evidence: pinned B-tree restart points are btree.c:28365–28393 and 28638–28696.
