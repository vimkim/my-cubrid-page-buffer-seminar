Four daemons are four loops, not four page writers

For each daemon, identify what wakes it, which shared state it reads, what progress it owns, and whether it starts a page-buffer flush.

TriggerInputWorkOutputCostLifecycle
01 · Topology

One process, four peer threads, four different jobs

The boot gate covers all four tasks. Only the green page-flush row enters the page-generation flush mechanism.

A dirty page is not assigned to one of four workers. DIRTY remains BCB state until a selection policy or explicit caller acts.

  • pgbuf_daemons_init() creates one daemon object per role. Each object owns one std::thread.
  • The task executes, pauses according to its own cubthread::looper, then executes again. There is no common dirty-page work queue shared by four workers.
  • The objects are created around restart, but their tasks return while BO_IS_FLUSH_DAEMON_AVAILABLE() is false. Boot opens the gate only after recovery.
  • pgbuf-flush-control is optional: token-bucket initialization failure leaves that daemon pointer null. Stand-alone mode creates none of the four.

03 · The only producer–consumer pair

Page flush may hand completion to post-flush

allocation pressure / timed wake
  → pgbuf-page-flush
      → choose dirty LRU3 candidates
      → recheck identity + dirty + cold + unfixed + WAL
      → copy generation and submit DWB/direct I/O
      → if a direct-victim waiter exists and flushed_bcbs accepts the pointer:
           produce BCB* → wake pgbuf-page-post-flush
        else:
           complete FLUSHING state in this thread

pgbuf-page-post-flush
  → drain flushed_bcbs (capacity 8,192)
  → lock each BCB and recheck clean + unfixed + LRU3 + quota
  → reserve for one waiting allocator when still eligible
  → clear old FLUSHING state and wake flush waiters

Post-flush does not perform “the second half of every flush.” The handoff happens only on the page-flush path, only when a direct-victim waiter exists, only when the post-flush daemon exists, and only when the bounded queue accepts the pointer. Otherwise the submitting thread completes the BCB itself.

The protected recheck is essential. Between I/O submission and post-processing, another thread may fix the BCB, move it out of LRU3, or create a newer DIRTY generation. Old-generation completion cannot authorize reuse of those newer resident bytes.

04 · Maintenance is policy, not I/O

Quota adjustment is real; the backup assignment loop is anomalous

Every maintenance execution first calls pgbuf_adjust_quotas(). It consumes per-LRU hit samples, estimates private activity, updates private/shared thresholds, demotes zones that exceed those thresholds, republishes candidate-bearing LRUs, and updates the approximate “victim rich” signal.

It then calls pgbuf_direct_victims_maintenance(), whose comment describes a low-activity backup. Its initial value 5 is only an outer continuation budget, not a strict assignment cap: one helper call can inspect up to 1,000 LRU3 entries and assign multiple BCBs. However, both pinned outer for loops initialize index to the saved start index and immediately require index != start_index. The condition is false on the first test, so neither body is entered as written.

Evidence boundary — VS-20: teach quota adjustment as verified. Teach direct-victim maintenance as intended by the comment but blocked by a source-visible loop condition. Other producers still assign direct victims, so this source anomaly alone does not prove a production stall or starvation.
05 · Flush control controls rate

It manages tokens, not BCBs

The flush-control task lives beside page-buffer daemons, but its state is in file_io.c. The first execution records a time origin. Later 50 ms executions calculate an adaptive or configured token rate, replace the shared token budget, reset interval statistics, and broadcast the token-bucket condition variable. A non-log caller stops waiting after ten broadcasts/retries, while a caller holding the log critical section does not wait for missing tokens; this is a soft limiter.

File-I/O paths consume that budget through fileio_compensate_flush() after the OS write call. Waiting therefore delays subsequent progress; these are not permission tokens granted before the write that just completed. This pacing path does not select a dirty page, set FLUSHING, copy bytes, force WAL, or call the page-generation flush mechanism. If initialization fails and the daemon is absent, token acquisition becomes a no-op because the bucket pointer is null; page flushing still exists.

Only the page-flush loop is intentionally I/O-bound

07 · What is outside these four?

Checkpoint, WRITE-owner, explicit caller, and DWB are separate actors

  • The log-checkpoint thread selects pages by oldest_unflush_lsa and calls pgbuf_flush_checkpoint() itself.
  • A foreground storage, recovery, shutdown, or volume operation may synchronously call a page or whole-pool flush.
  • A foreign WRITE owner may receive PGBUF_BCB_ASYNC_FLUSH_REQ and perform the safe copy at unfix.
  • DWB's optional flush-block and file-sync daemons are downstream storage-integrity helpers, not page-buffer daemon workers.

When debugging, ask two questions: who selected this generation, and which thread executed or completed its configured persistence boundary?

08 · Retrieval practice

Route four symptoms to four owners

Prompt

A server shows many allocator waits, frequent dirty-page writes, and file-I/O pacing waits. Explain which daemon owns each kind of progress, how page-flush and post-flush connect, and why waking all four is not a valid fix.

Primary reading

Trace each loop from its initializer

  • Daemon tasks, periods, initialization, and destruction.
  • Victim candidate collection and page-flush submission.
  • Maintenance direct-victim loop conditions and post-flush recheck/handoff.
  • File-I/O token-bucket control and post-write call order.
