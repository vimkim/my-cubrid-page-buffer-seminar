Why move work into background threads?

A daemon here is a managed background thread that repeats a task and waits. It lets shared maintenance or cleaning proceed independently of one request. This is not a separate database server process, and the four page-buffer daemons do not all write pages.

Without background execution, necessary work has to move to foreground callers or another scheduler. That can increase request latency or reduce prepared clean-frame supply; it does not by itself prove corruption. Removing a thread while leaving its queues or wait protocol dependent on it is a different, unsafe change. Stand-alone mode is evidence that synchronous alternatives exist, not a recipe for disabling a live server daemon.

Keep four jobs separate: page-flush submits dirty page images; post-flush completes queued BCB work; maintenance adjusts quotas and zones; flush-control updates soft I/O pacing credits. The next lectures trace each job and its absence consequences.

Each daemon works and waits independently

The four daemons are background threads with distinct roles. A timer or wakeup provides an execution opportunity; current state determines whether useful work follows.

Expand implementation details and sources

create_daemon() creates one managed execution context and one std::thread. Its loop is simple: execute the task, ask its cubthread::looper how long to pause, then execute again. The four names are therefore four independent control loops, rather than interchangeable workers pulling dirty pages from one queue.

The task runs once immediately after construction. A fixed period is a start-to-start target: the looper subtracts the previous execution time. A 100 ms period does not mean “finish work, then always sleep another 100 ms,” and it does not guarantee useful work on every pass.

Work starts after recovery and stops before pool teardown

The server creates the threads during recovery, but useful page-buffer work waits for the boot gate. Normal shutdown stops them before pool teardown. Stand-alone mode does not create these four threads.

Expand implementation details and sources
  1. The page-buffer pool, LRUs, queues, and monitors are initialized first.
  2. Server boot creates the four daemon threads before log recovery finishes.
  3. Their immediate task calls see the boot gate closed and return without useful page-buffer work.
  4. Boot opens the gate after recovery. Opening it does not itself wake every sleeper; a later timer or ordinary work wake lets each role observe the open gate.
  5. Normal shutdown sets each looper's stop flag, wakes a sleeper, joins the OS thread, retires its task/context, and clears the pointer.
  6. log_final() and pool teardown happen after the page-buffer daemons have stopped, so no daemon outlives the shared state it touches.

Stand-alone mode creates none of these four threads. When background page-flush is unavailable, the relevant requester can perform victim flushing synchronously.

Wake is a hint, not a durable event: the generic waiter accepts wakeup() only while it is sleeping. If the task is already running, the call is not stored for its next pause. Each task therefore rechecks shared pressure or queue state when it executes.

Post-flush and flush-control do not write the page again

File-I/O token bucket: a shared balance of page-sized credits. Participating writers spend credits after a successful OS write; when the balance is empty they may pause before continuing. Flush-control periodically replaces the balance, so this is soft pacing rather than permission to perform the write. See the exact producer, consumer, and bypass rules →
Page-flush hands completion to post-flush: page submission has finished, but in-memory BCB bookkeeping remains. Under allocator pressure, page-flush may queue only the BCB pointer for post-flush to finish; it does not pass page bytes or request another write. Cleaning and bookkeeping / policy and pacing

Lecture 6B — page-flush and post-flush: first trace page-flush as it selects and submits one stable generation. Then follow the choice: finish the BCB bookkeeping locally, or queue only its pointer so post-flush can recheck it and possibly wake an allocator.
Lecture 6C — maintenance and flush-control: first follow replacement samples into quotas and zones. Separately, see a successful file write request page credits and the 50 ms control loop replace their shared balance. Neither control path carries a page image.

Checkpoint, the log-flush daemon, foreground/WRITE-owner flushes, and DWB helper daemons are outside this four-role group. They can support or reuse the same durability machinery without becoming page-buffer daemon workers.

Who does what when frames are scarce?

An allocator waits while many pages are dirty. Do all four daemons write pages?

Show explanation

No. Page-flush submits eligible page images. Post-flush finishes delegated BCB work and may assign a safe frame to an allocator. Maintenance handles quotas and zones; flush-control manages pacing credits consumed after successful OS writes.
