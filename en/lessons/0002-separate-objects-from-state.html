Identity → control information → page contents

First-principles route ↑

Separate the page’s identity, its memory slot, and the state of that slot. The page buffer looks up a BCB by page identity, then uses it to locate the frame and check its current state.

The BCB array and LRU array are different. Each frame has one BCB; each LRU descriptor manages a list of many BCBs.

Startup creates the arrays; a miss reuses their slots

On the boot path that does not reuse existing managers, two sibling helpers create paired BCB/frame storage and the shared/private LRU descriptor array. The first does not call the second. LRUs start empty; initially unused BCBs are linked on the invalid list. BCB[42] can later represent P and then Q without becoming another BCB object.

One frame, two records of use

Each BCB is paired with one frame. PAGE_PTR points into that frame; the access granted by its fix ends at matching unfix. The same address can later hold another page.

  • fcnt: granted fixes not yet released across all threads.
  • Holder: records which BCB a thread has fixed and how many times. A thread may hold nested fixes.

Source: holder, atomic-latch fcnt, BCB, and paired frame definitions are in pinned page_buffer.c:460–555; one-to-one table pairing is in 5559–5660.

Reuse preallocated frames and BCBs

With a 512 MiB buffer and 16 KiB pages, there are 32,768 frames and the same number of BCBs. Each fix reuses this storage. BCBs, hashes, holders and other metadata consume memory beyond the configured page capacity.

Expand structures, allocation counts and memory costs

The six names do not describe six peer allocations. A VPID is a value, BCBs and frames are pool arrays, PAGE_PTR is a borrowed pointer, global fcnt is a field inside each BCB, and holders are per-thread ledger entries. The default snapshot below assumes the pinned baseline's 512 MiB data buffer and 16 KiB I/O page size.

Default memory picture: two fixed arrays dominate the core pool—32,768 reusable BCBs paired with 32,768 reusable 16 KiB frames. A fix does not allocate another frame; it creates global and per-thread debt and returns one borrowed pointer into an existing frame.

Storage, page identity and access have different lifetimes

Storage

BCB and frame storage lives from pool initialization to teardown.

Current page

When P leaves and Q enters, the same slot represents a different page.

One use

Access from a successful fix lasts until its matching unfix.

Four separate questions about page state

  • Resident? Which page is in memory?
  • Fixed? Does a granted fix still use this frame?
  • Latch? Who may currently read or modify its contents?
  • Dirty / flushing? Are changes pending, or is a copied image being written?

One answer does not determine the others. A page can remain dirty after use ends.

Use has ended; changes remain

Suppose P is resident with fcnt == 0, NO_LATCH, and DIRTY state.

  • No granted fix remains, but P is still in memory.
  • It has changes that cannot simply be overwritten.
  • Reuse needs writeback and protected rechecks of dirty/flushing state, waiters and other conditions.

The guarantees and limits of a successful lookup

Successful fix grants access to the page. It does not establish that the page is clean or the transaction is complete.

Conditions after fix and release

A successful normal READ fix establishes a resident identity mapping, positive fix debt that includes this acquisition, a granted READ page latch, and a borrowed pointer lifetime. Success alone does not establish clean versus dirty, durable versus not durable, record existence, correct transaction locking, or caller correctness.

After matching unfix: this acquisition's debt and pointer-use lifetime end. The BCB/frame may stay resident; another fix may keep global fcnt positive; and durability state does not change merely because ownership was released.

Source: the normal successful-fix postcondition and matching release are routed through the canonical Core explanation, with pinned paths at page_buffer.c:2260–2685, 6277–6634, and 3062–3201.

Does zero fix count mean an empty slot?

A BCB represents P, has fcnt == 0, and is DIRTY. Can Q overwrite it now?

Show explanation

No. P remains resident and modified even though no fixes remain. Reuse requires checking dirty/flushing state, waiters and other conditions under protection.
