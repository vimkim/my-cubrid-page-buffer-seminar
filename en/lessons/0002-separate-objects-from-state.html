Roles of pages, frames, and BCBs

VPID names a database page using volume and page number. A frame is reusable memory for page bytes. A BCB is the paired control block that records the current identity and access/replacement state. A page may exist on storage without being resident.

This is an object illustration, not a replacement decision or a pool-capacity claim. Reuse changes the binding and bytes; the BCB/frame storage remains. A successful fix lends a PAGE_PTR; the caller must stop using that borrowed access at its matching unfix.

The control state separates outstanding uses (fcnt), compatible content access (page latch), and changes awaiting preservation (dirty). We will work through those rules after the textbook model; none of these facts alone grants permission to overwrite a frame.

Why do we need more than page bytes?

First-principles route ↑

Suppose a thread needs page P from a database file. We want to keep P in memory so the next request can use it again. Later, memory fills up and another page Q needs a place. What must we remember to make this safe?

1. VPID — which page did we ask for?

Could we just remember a memory address? An address tells us where bytes are now. That same address may hold Q after P leaves. We need a name for the requested page that does not depend on its current memory slot.

VPID identifies the page by volume and page number. For this example, P and Q have different VPIDs. Without checking page identity, a caller looking for P could receive Q’s bytes. A VPID alone does not mean the page is already in memory.

2. Frame array — where can P’s bytes stay?

Once we have P’s name, do we have its contents? No. Reading P needs actual memory to hold its page image. One such reusable memory slot is a frame; CUBRID allocates an array of them when the pool starts.

Why reuse a fixed set of slots? If we kept allocating memory for every different page, memory use would keep growing. A bounded pool keeps some pages and eventually reuses a slot for another page.

For example, frame 42 can hold P now and Q later. The frame is the place; the VPID identifies what is currently there. Reusing the place safely requires more information than the page bytes.

3. BCB array — may we overwrite frame 42?

Q needs space. Can we replace P just because we know its address? What if a thread is still reading P? It could see Q halfway through its work. What if P contains changes not yet written back? Overwriting it could lose those changes.

Each frame therefore has a buffer control block (BCB): a record of its current page identity and control state. CUBRID pairs each frame with one entry in the BCB array.

  • Fix count (fcnt): how many granted uses have not ended? A fix grants access; matching unfix releases that use. A positive count prevents ordinary frame reuse.
  • Page latch: which reads or modifications may proceed together? Keeping P in memory alone would not stop conflicting access to its contents.
  • Dirty state: are there changes still to write back? The last user leaving does not erase that obligation.

These facts answer different questions. fcnt == 0 does not mean “empty” or “safe to overwrite.” The BCB and frame remain the same objects when their current page changes from P to Q.

4. Resident hash — is P already here?

A second thread asks for P. Must it read P from storage again? First it should find out whether P is already resident, meaning present in the buffer pool.

We could inspect every BCB’s VPID. That can work, but repeats a pool-wide search. The resident hash uses the requested VPID to narrow the search to candidate BCBs.

Does a matching hash bucket prove that we found P? No. Different VPIDs can share a bucket, and concurrent reuse must be handled. Lookup checks the actual identity under the required protection. Without that check, finding a candidate could be mistaken for finding the requested page.

5. Invalid list — which slots have no page yet?

The pool has just started. Must P evict another page? No. The frames exist, but initially they have no resident page assigned.

The invalid list links the BCBs with no resident page identity. It gives the allocation path a way to find this unused capacity. “Invalid” here does not mean that a database page is corrupt.

Could we manage without this list? We would need another way to find unassigned slots, such as scanning BCBs. Without any such tracking, we could overlook empty capacity and try to replace a resident page unnecessarily. A resident P with zero fixes is different: its slot still holds P.

6. LRU array — when no slot is empty, where do we look?

Q needs a slot and every frame holds a page. Which page should leave? We want to keep useful pages and consider less useful ones for replacement. With no usage-based policy, we could repeatedly discard a page needed again immediately and reread it.

CUBRID organizes BCBs into multiple replacement lists with zones. The LRU array stores the descriptors that manage those lists, including their ends and zone boundaries. The replacement policy uses this organization to guide its search.

Is an LRU descriptor another BCB? No. One BCB describes one frame; one LRU descriptor manages a list containing many BCBs. These are two different arrays.

Does being a replacement candidate make P safe to overwrite? No. List position guides selection; protected checks of fixes, dirty/flushing state, waiters and other conditions still decide whether reuse may proceed. Without those checks, a useful ranking could still lead to lost changes or reuse during access.

P has no remaining fixes but is dirty. Q needs space. Has P become an empty slot?

Reason through the answer

No. The BCB still identifies P, the frame still holds P’s bytes, and the dirty state records changes to preserve. Zero fixes answers only whether granted uses remain. The invalid list tracks unassigned slots; replacement of this resident page requires writeback and protected rechecks.

Startup creates the arrays; a miss reuses their slots

On the boot path that does not reuse existing managers, two sibling helpers create paired BCB/frame storage and the shared/private LRU descriptor array. The first does not call the second. LRUs start empty; initially unused BCBs are linked on the invalid list. BCB[42] can later represent P and then Q without becoming another BCB object.

One frame, two records of use

Each BCB is paired with one frame. PAGE_PTR points into that frame; the access granted by its fix ends at matching unfix. The same address can later hold another page.

  • fcnt: granted fixes not yet released across all threads.
  • Holder: records which BCB a thread has fixed and how many times. A thread may hold nested fixes.

Source: holder, atomic-latch fcnt, BCB, and paired frame definitions are in pinned page_buffer.c:460–555; one-to-one table pairing is in 5559–5660.

Reuse preallocated frames and BCBs

With a 512 MiB buffer and 16 KiB pages, there are 32,768 frames and the same number of BCBs. Each fix reuses this storage. BCBs, hashes, holders and other metadata consume memory beyond the configured page capacity.

Expand structures, allocation counts and memory costs

The six names do not describe six peer allocations. A VPID is a value, BCBs and frames are pool arrays, PAGE_PTR is a borrowed pointer, global fcnt is a field inside each BCB, and holders are per-thread ledger entries. Storage, page identity and access have different lifetimes

Storage

BCB and frame storage lives from pool initialization to teardown.

Current page

When P leaves and Q enters, the same slot represents a different page.

One use

Access from a successful fix lasts until its matching unfix.

Four separate questions about page state

  • Resident? Which page is in memory?
  • Fixed? Does a granted fix still use this frame?
  • Latch? Who may currently read or modify its contents?
  • Dirty / flushing? Are changes pending, or is a copied image being written?

One answer does not determine the others. A page can remain dirty after use ends.

Use has ended; changes remain

Suppose P is resident with fcnt == 0, NO_LATCH, and DIRTY state.

  • No granted fix remains, but P is still in memory.
  • It has changes that cannot simply be overwritten.
  • Reuse needs writeback and protected rechecks of dirty/flushing state, waiters and other conditions.

The guarantees and limits of a successful lookup

Successful fix grants access to the page. It does not establish that the page is clean or the transaction is complete.

Conditions after fix and release

A successful normal READ fix establishes a resident identity mapping, positive fix debt that includes this acquisition, a granted READ page latch, and a borrowed pointer lifetime. Success alone does not establish clean versus dirty, durable versus not durable, record existence, correct transaction locking, or caller correctness.

After matching unfix: this acquisition's debt and pointer-use lifetime end. The BCB/frame may stay resident; another fix may keep global fcnt positive; and durability state does not change merely because ownership was released.

Source: the normal successful-fix postcondition and matching release are routed through the canonical Core explanation, with pinned paths at page_buffer.c:2260–2685, 6277–6634, and 3062–3201.

Does zero fix count mean an empty slot?

A BCB represents P, has fcnt == 0, and is DIRTY. Can Q overwrite it now?

Show explanation

No. P remains resident and modified even though no fixes remain. Reuse requires checking dirty/flushing state, waiters and other conditions under protection.
